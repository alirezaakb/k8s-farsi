ماجرای این فصل: شب حراج پاییزه

در شرکت شاپیفای (Shopify)،‏ یک تیم سه‌نفره‌ی تازه فروشگاه نمونه‌ی کوچکی راه انداخته تا یک ایده‌ی جدید را پیش از عرضه‌ی گسترده بیازماید (روایت فرضی است). اعضای تیم: سارا برنامه‌نویس backend،‏ امید برنامه‌نویس frontend،‏ و شما که مسئول زیرساخت و DevOps هستید. فروشگاه چهار بخش دارد: یک frontend و یک API،‏ پایگاه داده‌ی PostgreSQL و یک گزارش فروش شبانه. همه‌ی این‌ها روی یک server و با docker compose اجرا می‌شوند؛‏ هنوز نه alert دارند و نه کسی on-call است.

اولین حراج پاییزه از نیمه‌شب شروع شد و ترافیک در ساعت اول شش برابر روزهای عادی شد. صبح،‏ جلسه‌ی بررسی حادثه (postmortem) این سه اتفاق را ثبت کرد:

  1. ساعت ۲:۱۰ بامداد process مربوط به API با خطای کمبود memory از کار افتاد. چیزی آن را دوباره اجرا نکرد و چون alertی نبود،‏ تا ساعت ۸ صبح که سارا پیام مشتری‌ها را دید،‏ فروشگاه شش ساعت از دسترس خارج بود.
  2. پیش از آن،‏ برای تحمل ترافیک،‏ سارا دستی دو container دیگر از API اجرا کرده بود؛‏ بعد مجبور شد تنظیمات nginx را روی همان server دستی ویرایش کند تا ترافیک به آن‌ها هم برسد. هیچ‌کدام از این تغییرها جایی ثبت نشد.
  3. صبح،‏ انتشار نسخه‌ی جدید API با docker compose up پنج دقیقه قطعی داشت. نسخه‌ی جدید هم خطا داشت و چون image نسخه‌ی قبل با tag مشخص نگه داشته نشده بود،‏ برگشت به آن نیم ساعت طول کشید.

مدیر تیم می‌پرسد: «ابزاری نیست که این کارها را خودش انجام دهد؟» این فصل جواب همین سؤال است. در پایان فصل،‏ API روی cluster k3s با سه replica اجرا می‌شود: اگر از کار بیفتد خودش برمی‌گردد،‏ یک نشانی ثابت دارد و نسخه‌ی جدیدش بدون قطعی منتشر می‌شود و در صورت خرابی با یک دستور برمی‌گردد.

هدف این فصل

در پایان این فصل می‌توانید:

  • توضیح دهید کوبرنتیز چه مشکلی را حل می‌کند و چه کارهایی را انجام نمی‌دهد؛‏
  • یک cluster k3s نصب کنید،‏ به آن وصل شوید و اولین Pod را اجرا کنید؛‏
  • یک Deployment و یک Service بنویسید و تک‌تک خط‌های آن‌ها را توضیح دهید؛‏
  • رفتار self-healing و rolling update و rollback را روی cluster خودتان ببینید؛‏
  • اجزای یک cluster و نقش kubectl را بشناسید.

پیش‌نیاز: یک ماشین Linux یا VM با دست‌کم ۲ CPU و ۲ گیگابایت RAM؛‏ برای فصل‌های ۶ تا ۸،‏ که محدودیت منابع و دو محیط هم‌زمان را آزمایش می‌کنند،‏ ۴ گیگابایت لازم است. cluster را در همین فصل می‌سازید.

مفاهیم (Concepts)

بخش «مفاهیم» در مستندات رسمی جایی است که با اجزای کوبرنتیز و با مدل‌های انتزاعی‌ای که کوبرنتیز برای توصیف cluster شما به کار می‌برد آشنا می‌شوید. هدف این است که بفهمید کوبرنتیز «از درون» چطور کار می‌کند،‏ نه اینکه فقط چند دستور حفظ کنید. این فصل نقطه‌ی شروع همین مسیر است: اول می‌بینیم کوبرنتیز چیست،‏ چه مشکلی را حل می‌کند و چه کارهایی را انجام نمی‌دهد؛‏ بعد اجزای یک cluster را می‌شناسیم؛‏ و در پایان با kubectl،‏ ابزار اصلی کار با cluster،‏ آشنا می‌شویم.

توضیح تکمیلی: «مدل انتزاعی» یعنی چه؟

مدل انتزاعی (abstraction) یعنی مدلی که جزئیات زیرین را از دید شما پنهان می‌کند. در کوبرنتیز دیگر نمی‌گویید «برنامه را روی server شماره‌ی ۳ با فلان IP اجرا کن»؛‏ به‌جایش درباره‌ی شیءهایی (object) مثل Pod،‏ Deployment و Service سروکار دارید. هر کدام از این شیءها «desired state» (وضعیتی که کاربر اعلام می‌کند می‌خواهد) شما را توصیف می‌کنند و این خود سیستم است که مسئول پیاده‌کردن آن روی ماشین‌های واقعی است.

تقریباً هر فصل این جزوه یکی از همین مدل‌ها را باز می‌کند: شیءها در فصل ۸،‏ Pod در فصل ۳ و workloadها (برنامه‌ای که روی cluster اجرا می‌شود) در فصل ۴.

نگاه کلی (Overview)

تعریف رسمی مستندات این است: کوبرنتیز یک پلتفرم متن‌باز (open source)،‏ قابل‌حمل (portable) و توسعه‌پذیر (extensible) برای مدیریت workloadها و سرویس‌های containerی است که هم پیکربندی اعلانی (declarative configuration) و هم خودکارسازی (automation) را ممکن می‌کند. اکوسیستم بزرگی دارد که به‌سرعت رشد می‌کند و سرویس‌ها،‏ پشتیبانی و ابزارهای مرتبط با آن همه‌جا در دسترس‌اند.

نام کوبرنتیز یونانی است و به معنای «سکان‌دار» یا «ناخدا» (helmsman / pilot) است. کوتاه‌نوشت K8s هم از شمردن هشت حرفِ بین «K» و «s» ساخته شده است. گوگل این پروژه را در سال ۲۰۱۴ متن‌باز کرد. کوبرنتیز حاصل ترکیب بیش از ۱۵ سال تجربه‌ی گوگل در اجرای سرویس‌های عملیاتی در مقیاس بزرگ (با سامانه‌ی داخلی‌ای به نام Borg) با بهترین ایده‌ها و روش‌های جامعه‌ی متن‌باز است.

توضیح تکمیلی: چرا «سکان‌دار»؟

این نام با نقش کوبرنتیز مطابقت دارد: کوبرنتیز خودش container اجرا نمی‌کند؛‏ اجرای واقعی container کارِ «container runtime» (نرم‌افزاری که containerها را روی Node اجرا می‌کند،‏ مثل containerd) مثل containerd یا CRI-O است. کار کوبرنتیز هدایت است: تصمیم می‌گیرد هر container کجا اجرا شود،‏ اگر از کار افتاد چه چیزی جایش را بگیرد،‏ و ترافیک به کدام replica برسد. نماد رسمی پروژه هم یک سکان کشتی با هفت پره است.

دو واژه‌ی کلیدیِ تعریف رسمی را جدی بگیرید،‏ چون کل کوبرنتیز روی همین دو ایده بنا شده:

  • پیکربندی اعلانی (declarative): شما می‌گویید «چه می‌خواهید»،‏ نه «چطور انجامش بده». مثلاً «۳ replica از image نسخه‌ی 1.4 می‌خواهم». این جمله همان desired state است.
  • خودکارسازی: controllerهای کوبرنتیز بی‌وقفه current state (وضعیتی که سیستم در این لحظه واقعاً دارد) را با desired state مقایسه می‌کنند و هر اختلافی ببینند برطرفش می‌کنند. به این فرایند reconciliation (فرایند نزدیک کردن مداوم وضعیت واقعی به وضعیت خواسته‌شده) می‌گویند و پایه‌ی self-healing،‏ rolling update (جایگزینی تدریجی Podهای قدیمی با جدید،‏ بدون قطعی) و مقیاس‌پذیری است.

یک تشبیه ساده که خود مستندات رسمی هم (در صفحه‌ی Controllers) به کار می‌برد: ترموستات. شما دمای ۲۴ درجه را تنظیم می‌کنید (desired state)؛‏ ترموستات مدام دمای اتاق را می‌سنجد (current state) و هر وقت اختلاف دید،‏ کولر را روشن یا خاموش می‌کند. شما هیچ‌وقت نمی‌گویید «ده دقیقه کولر را روشن کن». controllerهای کوبرنتیز دقیقاً همین‌طور کار می‌کنند.

پیشینه: از server فیزیکی تا container (Historical context)

برای اینکه بفهمیم چرا کوبرنتیز این‌قدر به کار می‌آید،‏ کمی به عقب برمی‌گردیم و سه دوره‌ی deployment نرم‌افزار را مرور می‌کنیم.

دوره‌ی traditional deployment (Traditional deployment)

در ابتدا سازمان‌ها برنامه‌هایشان را مستقیم روی serverهای فیزیکی اجرا می‌کردند. هیچ راهی نبود که برای هر برنامه روی یک server «مرز منابع» تعیین کنند،‏ و همین باعث مشکل در تقسیم منابع می‌شد. مثلاً وقتی چند برنامه روی یک server اجرا می‌شدند،‏ ممکن بود یکی از آن‌ها بیشترِ CPU و memory را بگیرد و بقیه کند شوند. راه‌حلِ ظاهری این بود که هر برنامه روی server جداگانه اجرا شود؛‏ اما این روش مقیاس‌پذیر نبود: منابع بیشتر serverها بلااستفاده می‌ماند و نگهداری تعداد زیادی server فیزیکی برای سازمان‌ها گران تمام می‌شد.

دوره‌ی virtualized deployment (Virtualized deployment)

راه‌حل بعدی،‏ مجازی‌سازی بود. مجازی‌سازی اجازه می‌دهد چند virtual machine (VM) روی CPU یک server فیزیکی اجرا شوند. برنامه‌ها در VMهای جدا از هم ایزوله می‌شوند و سطحی از امنیت هم فراهم می‌شود،‏ چون اطلاعات یک برنامه آزادانه در دسترس برنامه‌ی دیگر نیست.

با مجازی‌سازی از منابع server فیزیکی بهتر استفاده می‌شود،‏ مقیاس‌پذیری بهتر می‌شود (چون افزودن یا به‌روزکردن یک برنامه آسان است) و هزینه‌ی سخت‌افزار هم پایین می‌آید. در واقع می‌توانید مجموعه‌ای از منابع فیزیکی را به شکل یک cluster از virtual machineهای «یک‌بارمصرف» (disposable) عرضه کنید.

اما هر VM یک ماشین کامل است که همه‌ی اجزا،‏ از جمله سیستم‌عامل کامل خودش،‏ را روی سخت‌افزار مجازی اجرا می‌کند؛‏ و این یعنی سربار.

دوره‌ی container deployment (Container deployment)

containerها شبیه VMها هستند،‏ با این تفاوت که ایزوله‌سازی‌شان سبک‌تر است (relaxed isolation) تا بتوانند سیستم‌عامل host را بین برنامه‌ها مشترک استفاده کنند. به همین دلیل containerها «سبک» (lightweight) به حساب می‌آیند. container هم مثل VM filesystem خودش،‏ سهم خودش از CPU و memory،‏ فضای process (process space) خودش و موارد دیگر را دارد. و چون به زیرساخت زیرین وابسته نیست،‏ بین cloudهای مختلف و توزیع‌های مختلف سیستم‌عامل قابل‌حمل است.

containerها به خاطر این مزیت‌ها محبوب شده‌اند:

  • ساخت و deployment چابک برنامه: ساختن container image خیلی ساده‌تر و سریع‌تر از ساختن image VM است.
  • توسعه،‏ یکپارچه‌سازی و deployment پیوسته (CI/CD): می‌توان image را مطمئن و مکرر ساخت و deploy کرد و در صورت مشکل سریع به نسخه‌ی قبل برگشت (rollback)،‏ چون image بعد از ساخته‌شدن تغییر نمی‌کند (immutability).
  • جداشدن مسئولیت توسعه و عملیات (Dev و Ops):‏ image در زمان build ساخته می‌شود،‏ نه در زمان deployment؛‏ پس برنامه از زیرساخت جدا می‌شود.
  • مشاهده‌پذیری (Observability): علاوه بر اطلاعات و معیارهای سطح سیستم‌عامل،‏ سلامت خود برنامه و سیگنال‌های دیگر هم قابل‌مشاهده است.
  • یکسان‌بودن محیط در توسعه،‏ تست و عملیات: برنامه روی لپ‌تاپ دقیقاً همان‌طور اجرا می‌شود که روی cloud.
  • قابل‌حمل‌بودن بین cloudها و سیستم‌عامل‌ها: روی Ubuntu،‏ RHEL،‏ CoreOS،‏ serverهای داخلی سازمان،‏ cloudهای عمومی بزرگ و هر جای دیگر اجرا می‌شود.
  • مدیریت برنامه‌محور: سطح انتزاع از «اجرای یک سیستم‌عامل روی سخت‌افزار مجازی» بالا می‌رود به «اجرای یک برنامه روی سیستم‌عامل با منابع منطقی».
  • ریزسرویس‌های مستقل،‏ توزیع‌شده و انعطاف‌پذیر: برنامه به تکه‌های کوچک و مستقل شکسته می‌شود که می‌توان هر کدام را جداگانه و پویا deploy و مدیریت کرد؛‏ به‌جای یک برنامه‌ی یکپارچه‌ی بزرگ (monolith) روی یک ماشین بزرگ تک‌منظوره.
  • ایزوله‌سازی منابع: کارایی برنامه قابل پیش‌بینی می‌شود.
  • بهره‌وری از منابع: کارایی و تراکم بالا؛‏ برنامه‌های بیشتر روی سخت‌افزار کمتر.
توضیح تکمیلی: سه دوره در یک مثال واقعی

فرض کنید یک فروشگاه اینترنتی سه برنامه دارد: shop-api،‏ payment و report-worker.

دورهچیدمانمشکل اصلی
سنتیهر سه روی یک server فیزیکیشب‌ها report-worker کل CPU را می‌گیرد و shop-api کند می‌شود،‏ چون هیچ مرزی برای منابع وجود ندارد. اگر هر کدام را روی server جدا بگذارید،‏ سه server دارید که هر کدام فقط ۱۰٪ استفاده می‌شود.
مجازیسه VM روی یک Hypervisorایزوله‌سازی خوب است،‏ اما هر VM یک سیستم‌عامل کامل دارد (چند گیگابایت disk،‏ صدها مگابایت memory،‏ بوت چنددقیقه‌ای) و باید سه سیستم‌عامل را جدا جدا به‌روز (patch) کنید.
containerیسه container روی یک سیستم‌عامل مشترکراه‌اندازی در حد ثانیه،‏ image چندده‌مگابایتی،‏ و مرز CPU و memory با cgroup. اما حالا یک نفر باید تصمیم بگیرد هر container کجا اجرا شود،‏ اگر از کار افتاد چه کند،‏ ترافیک را چطور پخش کند و نسخه‌ی جدید را چطور بدون قطعی جایگزین کند. این «یک نفر» همان کوبرنتیز است.

نکته‌ی مهم درباره‌ی «ایزوله‌سازی سبک»: چون همه‌ی containerها host kernel را مشترک استفاده می‌کنند،‏ ایزوله‌سازی‌شان از VM ضعیف‌تر است. به همین دلیل در production ابزارهایی مثل securityContext،‏ استانداردهای امنیتی Pod (Pod Security Standards) و RuntimeClass داریم که این مرز را محکم‌تر می‌کنند (فصل ۲ و ۱۴).

درباره‌ی «برگشت سریع به‌خاطر تغییرناپذیری image»: وقتی image با tag یا بهتر از آن با digest مشخص شود،‏ نسخه‌ی قبلی دقیقاً همان بیت‌هایی است که قبلاً درست کار می‌کرد. پس برگشت (rollback) یعنی «برگرد به image قبلی»،‏ نه «تغییرات را دستی روی server برگردان». کمی جلوتر در همین فصل یک rollback واقعی را اجرا می‌کنیم.

چرا به کوبرنتیز نیاز داریم و چه کارهایی می‌کند؟ (Why you need Kubernetes)

container راه خوبی برای بسته‌بندی و اجرای برنامه‌هاست. اما در production باید containerهایی را که برنامه‌ها را اجرا می‌کنند مدیریت کنید و مطمئن باشید سرویس هیچ‌وقت قطع نمی‌شود. مثلاً اگر یک container از کار بیفتد،‏ باید container دیگری فوراً جایش را بگیرد. حالا سؤال این است: بهتر نیست این کارها را یک سیستم خودکار انجام دهد،‏ نه یک آدم که نیمه‌شب بیدار می‌شود؟

اینجاست که کوبرنتیز به کمک می‌آید. کوبرنتیز چارچوبی به شما می‌دهد تا سیستم‌های توزیع‌شده را مقاوم در برابر خرابی (resilient) اجرا کنید. مقیاس‌دهی (scaling) و جایگزینی خودکار در زمان خرابی (failover) را بر عهده می‌گیرد،‏ الگوهای آماده‌ی deployment در اختیارتان می‌گذارد و خیلی کارهای دیگر. مثلاً کوبرنتیز به‌راحتی می‌تواند یک canary deployment را برایتان مدیریت کند.

قابلیت‌هایی که کوبرنتیز در اختیارتان می‌گذارد:

service discovery و توزیع بار (Service discovery and load balancing)

کوبرنتیز می‌تواند یک container را با یک نام DNS یا با IP اختصاصی خودش در دسترس قرار دهد. اگر ترافیک یک container زیاد شود،‏ کوبرنتیز بار را بین replicaها پخش می‌کند تا سرویس پایدار بماند.

توضیح تکمیلی

Podها موقتی‌اند و با هر راه‌اندازی مجدد یا جابه‌جایی،‏ IP تازه می‌گیرند. پس client نمی‌تواند به IP یک Pod تکیه کند. Service این مشکل را حل می‌کند: یک نام DNS ثابت (مثل shop-api.prod.svc.cluster.local) و یک IP مجازی ثابت می‌دهد و ترافیک را بین Podهای سالمی پخش می‌کند که با selector (شرطی برای انتخاب اشیا بر اساس جفت‌های کلید/مقدارشان) آن مطابقت دارند. clientها هیچ‌وقت IP تک‌تک Podها را نمی‌دانند؛‏ فقط نام Service را صدا می‌زنند. جزئیات کامل در فصل ۵.

shell
# از داخل یک Pod دیگر در همان cluster
kubectl exec -it deploy/frontend -n prod -- curl -s http://shop-api/healthz

مدیریت خودکار storage (Storage orchestration)

کوبرنتیز اجازه می‌دهد هر storage system دلخواهی را،‏ از disk محلی گرفته تا سرویس‌های cloud و موارد دیگر،‏ به‌طور خودکار به containerها وصل (mount) کنید.

توضیح تکمیلی

برنامه فقط یک درخواست فضا می‌نویسد (PersistentVolumeClaim)؛‏ مثلاً «۲۰ گیگابایت فضای ReadWriteOnce از StorageClass به نام fast-ssd می‌خواهم». اینکه پشت این فضا یک disk EBS در AWS است،‏ یک Persistent Disk در GCP یا یک LUN از Ceph،‏ به تعریف StorageClass و درایور CSI آن cluster بستگی دارد. در نتیجه همان فایل تعریف برنامه (manifest) روی cloudهای مختلف بدون تغییر کار می‌کند. جزئیات در فصل ۷.

rollout و برگشت خودکار نسخه‌ها (Automated rollouts and rollbacks)

desired state containerهایتان را برای کوبرنتیز توصیف می‌کنید و کوبرنتیز وضعیت واقعی را با سرعتی کنترل‌شده به سمت desired state می‌برد. مثلاً می‌توانید کاری کنید که کوبرنتیز خودش containerهای جدید بسازد،‏ containerهای قدیمی را حذف کند و همه‌ی منابع آن‌ها را به containerهای جدید بسپارد.

توضیح تکمیلی

«سرعت کنترل‌شده» در Deployment با دو فیلد تنظیم می‌شود: maxSurge (چند Pod اضافه را می‌شود موقتاً ساخت) و maxUnavailable (چند Pod در هر لحظه می‌تواند از دسترس خارج باشد). اگر نسخه‌ی جدید سالم اجرا نشود (یعنی readiness probe آن موفق نشود)،‏ rollout (فرایند deployment تدریجی نسخه‌ی جدید) متوقف می‌ماند و نسخه‌ی قدیمی همچنان به کاربران سرویس می‌دهد. نمونه‌ی کامل را در آزمایش عملی پایین همین بخش می‌بینید؛‏ جزئیات Deployment در فصل ۴.

چیدمان خودکار بهینه (Automatic bin packing)

شما مجموعه‌ای از ماشین‌ها (Node) را در اختیار کوبرنتیز می‌گذارید و به او می‌گویید هر container چقدر CPU و memory (RAM) لازم دارد. کوبرنتیز containerها را طوری روی ماشین‌ها می‌چیند که بهترین استفاده از منابع بشود.

توضیح تکمیلی

«bin packing» نام یک مسئله‌ی معروف است: جادادن اجسامی با اندازه‌های مختلف در تعداد محدودی جعبه. در کوبرنتیز،‏ جعبه‌ها Nodeها هستند و اندازه‌ی هر جسم،‏ مقدار resources.requests containerهاست. scheduler (kube-scheduler) فقط Nodeهایی را انتخاب می‌کند که به اندازه‌ی کافی جای خالی دارند (ظرفیت allocatable منهای مجموع requestهای Podهای فعلی) و از بین آن‌ها با امتیازدهی بهترین را برمی‌گزیند.

بخشی از یک Pod spec
containers:
- name: shop-api
  image: registry.example.com/shop-api:1.4.2
  resources:
    requests:        # scheduler با این عدد جا پیدا می‌کند
      cpu: "250m"
      memory: "256Mi"
    limits:          # سقف مصرف در زمان اجرا
      memory: "512Mi"

اگر requests ننویسید،‏ scheduler (جزئی که برای هر Pod،‏ Node مناسب را انتخاب می‌کند) فرض می‌کند Pod تقریباً هیچ منبعی لازم ندارد و ممکن است Podهای زیادی را روی یک Node بچپاند. نتیجه در production معمولاً کندی و خطای کمبود memory (OOMKilled) است. جزئیات در فصل ۶ و ۹.

self-healing

کوبرنتیز containerهایی را که از کار می‌افتند دوباره راه‌اندازی می‌کند،‏ containerها را در صورت لزوم جایگزین می‌کند،‏ containerهایی را که به بررسی سلامت (health check) تعریف‌شده‌ی شما جواب نمی‌دهند متوقف می‌کند،‏ و تا وقتی containerی آماده‌ی سرویس‌دهی نشده،‏ آن را به clientها معرفی نمی‌کند.

صفحه‌ی Self-Healing در بخش معماری cluster این قابلیت را کامل‌تر شرح می‌دهد (بررسی کامل در فصل ۱۲). خلاصه‌اش این است: کوبرنتیز از ابتدا با قابلیت self-healing (جایگزینی خودکار اجزای از کارافتاده) طراحی شده تا سلامت و دسترس‌پذیری workloadها حفظ شود. containerهای خراب را خودکار جایگزین می‌کند،‏ وقتی یک Node در دسترس نیست workloadهایش را جای دیگری اجرا می‌کند و مراقب است desired state سیستم حفظ شود. این قابلیت چهار جزء دارد:

  • راه‌اندازی مجدد در سطح container: بر اساس restartPolicy.
  • جایگزینی replicaها: برای Deployment،‏ StatefulSet و DaemonSet.
  • بازیابی storage: وصل‌کردن دوباره‌ی PersistentVolume به Pod جدید روی Node دیگر.
  • توزیع بار در Serviceها: حذف Pod خراب از فهرست مقصدهای (endpoint) Service.

اجزایی که این کارها را انجام می‌دهند kubelet،‏ controllerهای مربوط به Deployment و ReplicaSet و StatefulSet و DaemonSet و controller مربوط به PersistentVolume هستند. البته محدودیت‌هایی هم هست: خرابی storage ممکن است بازیابی دستی لازم داشته باشد،‏ و کوبرنتیز فقط می‌تواند container را دوباره راه بیندازد؛‏ باگ خودِ برنامه را باید خودتان رفع کنید.

چهار جمله‌ی تعریف رسمی را دقیقاً به چهار سازوکار نگاشت کنید (این جدول در مصاحبه خیلی به کار می‌آید):

مدیریت رمزها و پیکربندی (Secret and configuration management)

کوبرنتیز اجازه می‌دهد اطلاعات حساس مثل password،‏ token OAuth و کلید SSH را ذخیره و مدیریت کنید. می‌توانید رمزها و پیکربندی برنامه را بدون ساختن دوباره‌ی image و بدون فاش‌کردن رمزها در فایل‌های پیکربندی،‏ deploy و به‌روز کنید.

توضیح تکمیلی

یک image واحد،‏ مثلاً shop-api:1.4.2،‏ هم در محیط staging اجرا می‌شود و هم در production. تفاوت‌ها (آدرس database،‏ feature flagها) از ConfigMap و رمزها از Secret می‌آیند و به شکل environment variable یا فایل به container داده می‌شوند. این همان اصل «جداشدن مسئولیت Dev و Ops» است که بالاتر دیدیم.

دام رایج: Secret به‌طور پیش‌فرض فقط با base64 کدگذاری شده،‏ نه encryption! base64 را هر کسی می‌تواند برگرداند. برای امنیت واقعی باید encryption در حالت ذخیره (encryption at rest) و دسترسی‌های RBAC مناسب را تنظیم کنید (فصل ۶ و ۱۴).

اجرای کارهای دسته‌ای (Batch execution)

کوبرنتیز علاوه بر سرویس‌ها می‌تواند کارهای دسته‌ای (batch) و کارهای CI شما را هم مدیریت کند و در صورت تمایل،‏ containerهای ناموفق را جایگزین کند.

توضیح تکمیلی

فرق این دو را خوب بفهمید: سرویس (مثل web server) قرار است «همیشه» روشن بماند؛‏ کار دسته‌ای قرار است «تمام شود» (مثل ساخت گزارش شبانه یا اجرای تست‌ها). برای کارهای دسته‌ای Job و CronJob را داریم که Podهای ناموفق را آن‌قدر دوباره اجرا می‌کنند تا به تعداد اجرای موفق لازم برسند (حداکثر تا سقف backoffLimit). فصل ۴.

مقیاس‌دهی افقی (Horizontal scaling)

برنامه‌تان را با یک دستور ساده،‏ از طریق یک graphical interface،‏ یا به‌صورت خودکار بر اساس مصرف CPU بزرگ یا کوچک کنید.

توضیح تکمیلی
shell
# دستی
kubectl scale deployment/shop-api --replicas=6 -n prod
# خودکار بر اساس CPU (HorizontalPodAutoscaler)
kubectl autoscale deployment/shop-api --min=3 --max=12 --cpu=70% -n prod

افقی یعنی زیادکردن تعداد Podها؛‏ عمودی یعنی بزرگ‌کردن منابع هر Pod. مقیاس‌دهی خودکار بر اساس CPU به نصب metrics-server نیاز دارد. فصل ۱۰.

پشتیبانی هم‌زمان از IPv4 و IPv6 (Dual-stack)

کوبرنتیز می‌تواند به Podها و Serviceها هم آدرس IPv4 و هم IPv6 بدهد.

توضیح تکمیلی

در clusterی که dual-stack پیکربندی شده،‏ هر Pod می‌تواند هم‌زمان یک IPv4 و یک IPv6 داشته باشد (فیلد status.podIPs)،‏ و Service با تنظیم ipFamilyPolicy: PreferDualStack یا RequireDualStack روی هر دو نوع آدرس در دسترس است. این قابلیت برای سازمان‌هایی که به‌تدریج به IPv6 مهاجرت می‌کنند مهم است. فصل ۵.

طراحی‌شده برای توسعه‌پذیری (Designed for extensibility)

می‌توانید بدون تغییر کد منبع اصلی کوبرنتیز،‏ قابلیت‌های تازه به cluster خود اضافه کنید.

توضیح تکمیلی

چند مثال: با CustomResourceDefinition یک نوع شیء تازه تعریف می‌کنید (مثلاً PostgresCluster)؛‏ Operatorها برای همین شیءها controller می‌نویسند؛‏ admission webhookها قوانین سازمان را اعمال می‌کنند؛‏ و CNI pluginها،‏ CSI و CRI به ترتیب شبکه،‏ storage و runtime را فراهم می‌کنند. همه‌ی این‌ها بدون اینکه لازم باشد کد کوبرنتیز را fork کنید. فصل ۱۵.

توضیح تکمیلی: canary deployment که در متن اشاره شد

ایده‌ی canary این است که نسخه‌ی جدید اول فقط بخش کوچکی از ترافیک را بگیرد تا اگر مشکلی داشت،‏ فقط عده‌ی کمی آسیب ببینند (نامش از قناری‌هایی می‌آید که معدنچی‌ها برای تشخیص گاز سمی با خود می‌بردند). ساده‌ترین پیاده‌سازی در کوبرنتیز: دو Deployment که label (جفت کلید/مقدار روی اشیا برای گروه‌بندی و انتخاب آن‌ها) app: shop-api مشترک دارند ولی label track آن‌ها فرق می‌کند (stable و canary)،‏ و یک Service که فقط بر اساس app: shop-api انتخاب می‌کند. با ۹ replica از نسخه‌ی stable و ۱ replica از نسخه‌ی canary،‏ حدود ۱۰٪ درخواست‌ها به نسخه‌ی جدید می‌رسد. اگر خطاها بالا رفت،‏ canary را به صفر برسانید؛‏ اگر سالم بود،‏ stable را به‌روز کنید.

کوبرنتیز چه چیزی نیست؟ (What Kubernetes is not)

کوبرنتیز یک PaaS (Platform as a Service) سنتی و «همه‌چیز در یک بسته» نیست. چون کوبرنتیز در سطح container کار می‌کند نه در سطح سخت‌افزار،‏ برخی قابلیت‌های عمومی PaaSها را دارد،‏ مثل deployment،‏ مقیاس‌دهی و توزیع بار،‏ و اجازه می‌دهد راه‌حل‌های دلخواه خودتان برای ثبت log،‏ پایش (monitoring) و هشدار را به آن وصل کنید. اما کوبرنتیز یکپارچه (monolithic) نیست و این راه‌حل‌های پیش‌فرض همگی اختیاری و قابل‌تعویض (pluggable) هستند. کوبرنتیز «آجرهای سازنده» برای ساختن پلتفرم‌های توسعه را فراهم می‌کند،‏ اما هرجا که مهم باشد،‏ حق انتخاب و انعطاف را به خود کاربر می‌سپارد.

به طور مشخص،‏ کوبرنتیز:

  • نوع برنامه‌ها را محدود نمی‌کند. هدفش پشتیبانی از طیف بسیار متنوعی از workloadها است: stateless،‏ stateful و پردازش داده. قاعده ساده است: اگر برنامه‌ای در container اجرا شود،‏ باید روی کوبرنتیز هم عالی اجرا شود.
  • کد منبع را deploy نمی‌کند و برنامه‌ی شما را build نمی‌کند. فرایندهای CI/CD (یکپارچه‌سازی،‏ تحویل و deployment پیوسته) به فرهنگ و سلیقه‌ی سازمان و نیازهای فنی بستگی دارند و کوبرنتیز در آن‌ها دخالت نمی‌کند.
  • سرویس‌های سطح برنامه را به‌صورت داخلی ارائه نمی‌کند؛‏ مثل میان‌افزار (مثلاً message queue)،‏ چارچوب‌های پردازش داده (مثلاً Spark)،‏ database (مثلاً MySQL)،‏ cache،‏ یا سیستم‌های cluster storage (مثلاً Ceph). این اجزا می‌توانند روی کوبرنتیز اجرا شوند،‏ یا برنامه‌های داخل کوبرنتیز از طریق سازوکارهای قابل‌حمل،‏ مثل Open Service Broker،‏ به آن‌ها دسترسی پیدا کنند.
  • راه‌حل خاصی برای log،‏ پایش یا هشدار را تحمیل نمی‌کند. فقط چند نمونه‌ی یکپارچه‌سازی (در حد اثبات مفهوم) و سازوکارهایی برای جمع‌آوری و صدور معیارها (metrics) دارد.
  • زبان یا سیستم پیکربندی خاصی (مثل Jsonnet) ارائه یا اجبار نمی‌کند. یک API اعلانی دارد که هر نوع توصیف اعلانی دلخواهی می‌تواند با آن کار کند.
  • هیچ سیستم جامعی برای پیکربندی،‏ نگهداری،‏ مدیریت یا self-healing خود ماشین‌ها ارائه نمی‌کند.
  • و مهم‌تر از همه: کوبرنتیز صرفاً یک سیستم «هماهنگ‌سازی» (orchestration) نیست؛‏ در واقع نیاز به orchestration را از بین می‌برد. تعریف فنی orchestration اجرای یک روند از پیش تعیین‌شده است: «اول A،‏ بعد B،‏ بعد C». در مقابل،‏ کوبرنتیز از مجموعه‌ای از فرایندهای کنترلی مستقل و ترکیب‌پذیر ساخته شده که پیوسته current state را به سمت desired state می‌رانند. مهم نیست چطور از A به C برسید،‏ و به کنترل مرکزی هم نیازی نیست. نتیجه،‏ سیستمی است که هم استفاده از آن آسان‌تر است و هم قدرتمندتر،‏ مقاوم‌تر و توسعه‌پذیرتر.

orchestration در برابر reconciliation: یک script orchestration سنتی می‌گوید «۱. VM بساز ۲. image را بگیر ۳. برنامه را اجرا کن ۴. آن را در load balancer ثبت کن». اگر مرحله‌ی ۳ شکست بخورد،‏ script می‌ایستد و یک نفر باید دستی ادامه دهد. در کوبرنتیز شما فقط می‌گویید «۳ replica می‌خواهم و یک Service باید آن‌ها را در دسترس بگذارد». ReplicaSet controller،‏ scheduler،‏ kubelet و EndpointSlice controller هر کدام مستقل و بدون هماهنگ‌کننده‌ی مرکزی،‏ هر وقت اختلافی ببینند برطرفش می‌کنند. اگر kubelet در دریافت image شکست بخورد،‏ دوباره تلاش می‌کند؛‏ اگر یک Node از کار بیفتد،‏ controller Pod جدید می‌سازد. جمله‌ی «مهم نیست چطور از A به C برسید» یعنی سیستم از هر وضعیت میانی،‏ حتی یک وضعیت خراب،‏ می‌تواند به desired state برگردد. مفهوم «control loop» (حلقه‌ای که مدام وضعیت واقعی را با وضعیت خواسته‌شده مقایسه و اختلاف را برطرف می‌کند) در فصل ۱۲ کامل بررسی می‌شود.

دقت کنید: مستندات می‌گوید کوبرنتیز برای ماشین‌ها سیستم self-healing ندارد. self-healingی که در بخش قبل دیدیم در سطح container و Pod است. اگر disk یک Node خراب شود،‏ کوبرنتیز Podها را جای دیگری می‌برد،‏ اما خود Node را تعمیر یا جایگزین نمی‌کند؛‏ این کار ابزارهای مقیاس‌دهی خودکار Node یا تیم زیرساخت است.

کوبرنتیز در یک تصویر (Mental model)

هدف این بخش

پیش از تایپ اولین دستور،‏ بدانیم اصلاً با چه چیزی کار می‌کنیم.

در پایان این بخش می‌توانید:

  • بگویید کوبرنتیز چه کاری برای شما انجام می‌دهد.
  • هشت واژه‌ی پایه را از هم تشخیص دهید.

فرض کنید یک برنامه‌ی وب دارید که در یک container image بسته‌بندی شده است. بدون کوبرنتیز باید خودتان روی یک server دستور اجرای container را بزنید،‏ اگر container از کار افتاد دوباره اجرایش کنید،‏ اگر بار زیاد شد چند instance دیگر روی serverهای دیگر اجرا کنید و جلوی همه یک load balancer بگذارید. کوبرنتیز این کارها را خودکار می‌کند. شما فقط می‌گویید «چه می‌خواهید» (مثلاً «۳ replica از این image همیشه در حال اجرا باشد و از آدرس web در دسترس باشد») و کوبرنتیز مدام تلاش می‌کند واقعیت را با خواسته‌ی شما یکی نگه دارد. به این خواسته desired state (وضعیت خواسته‌شده) و به این تلاش مداوم reconciliation (نزدیک کردن مداوم واقعیت به خواسته) می‌گویند.

در این فصل فقط با این هشت واژه کار دارید؛‏ بقیه را به‌مرور در فصل‌های بعد می‌بینید:

واژهیعنی چه؟تشبیه ساده
clusterمجموعه‌ی ماشین‌هایی که کوبرنتیز مدیریت می‌کندیک کارخانه
Nodeهر ماشین (فیزیکی یا مجازی) داخل clusterیک سالن کارخانه
container و imageimage بسته‌ی برنامه است و container نسخه‌ی در حال اجرای آننقشه‌ی محصول و محصول ساخته‌شده
Podکوچک‌ترین واحد اجرا؛‏ یک یا چند container که با هم روی یک Node اجرا می‌شوندیک ایستگاه کاری
Deploymentشیئی که می‌گوید «از این Pod چند replica همیشه باشد» و خراب‌ها را جایگزین می‌کندسرپرست شیفت
Serviceیک نام و IP ثابت جلوی مجموعه‌ای از Podها که ترافیک را بینشان پخش می‌کندشماره‌ی تلفن ثابت یک بخش

همه‌چیز «شیء» است

هر چیزی که در کوبرنتیز می‌سازید (Pod و Deployment و Service و …) یک شیء (object) است: رکوردی که در پایگاه داده‌ی cluster ذخیره می‌شود و desired state شما را توصیف می‌کند. کوبرنتیز این شیءها را می‌خواند و برایشان کار انجام می‌دهد. پس کار اصلی شما در کوبرنتیز «نوشتن شیء درست» است،‏ نه «اجرای دستور درست». این ایده در آزمایش شاپیفای در همین فصل کاملاً روشن می‌شود.

چرا k3s؟

k3s یک توزیع (distribution) سبک و کامل از کوبرنتیز است که پروژه‌ی CNCF نگهداری‌اش می‌کند. همه‌ی اجزای کوبرنتیز را در یک فایل اجرایی جمع کرده و با یک دستور نصب می‌شود. رابط API آن همان Kubernetes API استاندارد است؛‏ پس هر چیزی که با k3s یاد بگیرید (دستورهای kubectl،‏ فایل‌های YAML،‏ مفاهیم) عیناً روی هر cluster دیگری هم کار می‌کند. فرقش با minikube و kind این است که k3s یک cluster «واقعی» روی سیستم‌عامل Linux می‌سازد،‏ نه شبیه‌سازی داخل Docker؛‏ برای همین برای production سبک (مثل edge و محیط‌های کوچک) هم استفاده می‌شود.

آماده‌سازی ماشین (Prepare a VM)

هدف این بخش

یک ماشین لینوکسی تمیز برای نصب k3s آماده کنیم.

در پایان این بخش می‌توانید:

  • یک VM با منابع کافی بسازید.
  • بدانید k3s به چه portهایی نیاز دارد.

k3s روی Linux اجرا می‌شود. توصیه‌ی این جزوه یک VM با Ubuntu Server 24.04 است. حداقل رسمی برای Node اصلی (server) ۲ هسته‌ی CPU و ۲ گیگابایت RAM است؛‏ برای تمرین راحت‌تر ۲ CPU و ۴ گیگابایت RAM و ۲۰ گیگابایت disk بگذارید. روی Windows می‌توانید از Hyper-V یا VirtualBox و روی macOS از Multipass یا UTM استفاده کنید. اگر Multipass نصب دارید،‏ ساختن VM یک دستور است:

نصب k3s (Install k3s)

هدف این بخش

با یک دستور،‏ یک cluster کوبرنتیز تک‌Nodeی بسازیم و با kubectl به آن وصل شویم.

در پایان این بخش می‌توانید:

/etc/rancher/k3s/registries.yaml
mirrors:
  docker.io:
    endpoint:
      - "https://mirror.example.ir"

sudo systemctl restart k3s

نشانی mirror را با نشانی واقعی جایگزین کنید و فقط از mirror مورد اعتماد استفاده کنید؛‏ imageها زنجیره‌ی تأمین cluster شما هستند.

چه اتفاقی افتاد؟

اسکریپت نصب،‏ فایل اجرایی k3s را گذاشت و یک سرویس systemd ساخت. این یک برنامه همه‌ی اجزای کوبرنتیز را اجرا می‌کند: API server و scheduler و controllerها (control plane؛‏ بخش مدیریتی cluster) و kubelet (عامل هر Node که containerها را اجرا می‌کند) و container runtime به نام containerd. پایگاه داده‌ی cluster در حالت تک‌Node یک SQLite است (و در cluster چند server،‏ پایگاه داده‌ی etcd). در یک cluster معمولی این اجزا برنامه‌های جداگانه‌اند؛‏ k3s فقط آن‌ها را در یک بسته گذاشته است. معماری کامل این اجزا در فصل ۱۲ آمده است.

امتحان کنید 2 تمرین
  1. عملیفایل ~/.kube/config را باز کنید (cat). آدرس API server کجاست و روی چه portی است؟
    پاسخ

    در فیلد server مقدار https://127.0.0.1:6443 را می‌بینید؛‏ یعنی API server روی همین ماشین و port ۶۴۴۳ گوش می‌دهد. اگر بخواهید از لپ‌تاپ خودتان به cluster وصل شوید،‏ این فایل را کپی و ‎127.0.0.1‎ را با IP ماشین عوض می‌کنید (فصل ۱۳،‏ بخش kubeconfig).

  2. مفهومیچرا فایل kubeconfig را با chmod 600 محدود کردیم؟
    پاسخ

    چون این فایل certificate مدیر cluster را دارد؛‏ هر کسی آن را داشته باشد اختیار کامل cluster را دارد. مثل رمز عبور root با آن رفتار کنید.

چک‌لیست پایان بخش
  • kubectl get nodes بدون sudo یک Node در وضعیت Ready نشان می‌دهد.
  • می‌دانید kubeconfig چیست و کجاست.

قالب همه‌ی دستورهای kubectl

تقریباً همه‌ی دستورها این شکل را دارند: kubectl فعل نوع نام گزینه‌ها؛‏ مثلاً kubectl get pods -A یا kubectl describe node k3s-lab. فعل‌های اصلی این فصل: get برای فهرست؛‏ describe برای جزئیات و رخدادها؛‏ logs برای خروجی برنامه؛‏ exec برای اجرای دستور داخل container؛‏ apply برای اعمال فایل؛‏ delete برای حذف. راهنمای هر دستور با --help می‌آید. جزئیات کامل در فصل ۱.

امتحان کنید 2 تمرین
  1. عملیبا kubectl describe node k3s-lab ظرفیت CPU و memory این Node را پیدا کنید.
    پاسخ

    در بخش Capacity و Allocatable تعداد CPU و مقدار memory آمده است. مقدار Allocatable سهمی است که برای Podها می‌ماند (فصل ۱۲).

  2. مفهومیچرا namespace سیستمی kube-system از namespace کار شما جداست؟
    پاسخ

    تا اشیای سیستمی با اشیای برنامه‌های شما قاطی نشوند و بتوان دسترسی را جدا کنترل کرد. کار شما به‌طور پیش‌فرض در namespace به نام default انجام می‌شود (فصل ۸).

چک‌لیست پایان بخش
  • تفاوت kubectl get pods و kubectl get pods -A را می‌دانید.
  • نقش coredns و traefik را می‌دانید.

cluster چیست؟ (What is a Kubernetes cluster)

کوبرنتیز یک پلتفرم متن‌باز و آماده‌ی production است که scheduling (انتخاب Node مناسب برای اجرای Pod) و اجرای application containerها را روی مجموعه‌ای از کامپیوترها هماهنگ می‌کند.

کوبرنتیز چند کامپیوترِ به‌هم‌متصل را طوری هماهنگ می‌کند که مثل یک سیستم واحد و با دسترس‌پذیری بالا (high availability) کار کنند. با مدل‌های انتزاعی کوبرنتیز،‏ برنامه‌های containerی را روی cluster deploy می‌کنید،‏ بی‌آنکه آن‌ها را به ماشین خاصی گره بزنید. شرطش این است که برنامه به هیچ host خاصی وابسته نباشد؛‏ یعنی containerی شده باشد. در مدل‌های قدیمی،‏ برنامه به شکل بسته‌هایی که عمیقاً با سیستم‌عامل host گره خورده بودند،‏ مستقیم روی یک ماشین مشخص نصب می‌شد؛‏ برنامه‌های containerی خیلی انعطاف‌پذیرترند. کوبرنتیز پخش و scheduling این containerها را در سراسر cluster به شکلی کارآمد خودکار می‌کند.

هر cluster کوبرنتیز دو نوع جزء دارد:

  • control plane (اجزای مدیریتی cluster که تصمیم‌ها را می‌گیرند و وضعیت را نگه می‌دارند): cluster را هماهنگ و مدیریت می‌کند؛‏ «مغز» cluster است.
  • Nodeها (گره‌ها): ماشین‌های کارگری هستند که برنامه‌ها واقعاً روی آن‌ها اجرا می‌شوند؛‏ «بازوهای» cluster.

نمودار cluster

control plane مسئول مدیریت cluster است. همه‌ی فعالیت‌های cluster را هماهنگ می‌کند؛‏ از scheduling برنامه‌ها و حفظ desired state خود گرفته تا مقیاس‌دهی و rollout نسخه‌های جدید.

Node یک VM یا ماشین فیزیکی است که در cluster نقش ماشین کارگر را دارد. روی هر Node یک kubelet اجرا می‌شود؛‏ عاملی (agent) که Node را مدیریت می‌کند و با control plane در ارتباط است. هر Node همچنین به ابزاری برای اجرای containerها نیاز دارد،‏ مثل containerd یا CRI-O. در یک چیدمان رایج و پشتیبانی‌شده،‏ اجزای control plane روی Nodeهای اختصاصی خودشان اجرا می‌شوند.

وقتی برنامه‌ای را روی کوبرنتیز deploy می‌کنید،‏ در واقع به control plane می‌گویید application containerها را راه بیندازد. control plane آن containerها را برای اجرا روی Nodeهای cluster schedule می‌کند. اجزای سطح Node مثل kubelet،‏ از طریق API کوبرنتیز که control plane در اختیار می‌گذارد با آن ارتباط برقرار می‌کنند. کاربران هم می‌توانند مستقیماً از همین API برای کار با cluster استفاده کنند.

cluster کوبرنتیز را می‌توان روی ماشین‌های فیزیکی یا مجازی راه انداخت. برای شروع یادگیری و توسعه،‏ Minikube گزینه‌ی خوبی است: یک پیاده‌سازی سبک از کوبرنتیز که روی کامپیوتر شما یک virtual machine (یا container) می‌سازد و یک cluster ساده‌ی تک‌Node در آن راه می‌اندازد. Minikube برای Linux،‏ macOS و Windows موجود است و خط فرمانش عملیات پایه‌ی کار با cluster را فراهم می‌کند: start،‏ stop،‏ status و delete. در این جزوه از k3s استفاده می‌کنیم (بخش «نصب k3s» در همین فصل) که همین نقش را دارد؛‏ مسیر minikube در پیوست (فصل ۱۷) آمده است.

توضیح تکمیلی

در cluster آزمایشی k3s ما تنها Node موجود هم نقش control plane را دارد و هم نقش کارگر. برای یادگیری کافی است،‏ اما در production هرگز cluster تک‌Node ندارید. یک cluster عملیاتی معمولی (خارج از مستندات رسمی) این‌طور است: ۳ Node control plane در سه ناحیه‌ی دسترس‌پذیری (availability zone) تا etcd بتواند به quorum برسد،‏ به‌علاوه‌ی چندین worker Node برای اجرای Podهای برنامه. فصل ۱۳ این طراحی را بررسی می‌کند.

عبارت «بی‌آنکه برنامه را به یک ماشین مشخص گره بزنید» مهم‌ترین تغییر ذهنی در کوبرنتیز است: در فایل تعریف برنامه‌ی شما نام هیچ serverی نمی‌آید. اگر برنامه‌ای به یک فایل محلی یا IP ثابت یک ماشین وابسته باشد،‏ از این مدل سودی نمی‌برد و self-healing را هم خراب می‌کند؛‏ چون Pod جدید که روی Node دیگری ساخته می‌شود،‏ آن فایل را ندارد.

ادامه‌ی مسیر: معماری cluster (فصل ۱۲)

اجزای کوبرنتیز (Kubernetes Components)

این بخش نمایی کلی از اجزای اصلی‌ای می‌دهد که یک cluster کوبرنتیز را تشکیل می‌دهند. اگر فقط یک بخش از این فصل را قرار است عمیق یاد بگیرید،‏ همین بخش است؛‏ تقریباً در هر مصاحبه‌ی کوبرنتیز از آن سؤال می‌شود.

اجزای اصلی

هر cluster کوبرنتیز از یک control plane و یک یا چند worker Node تشکیل شده است.

اجزای control plane (Control Plane Components)

این اجزا وضعیت کلی cluster را مدیریت می‌کنند:

جزءکارش چیست؟
kube-apiserverserver مرکزی که API کوبرنتیز را (روی HTTP) در اختیار همه می‌گذارد. «درِ ورودی» cluster است؛‏ همه،‏ از kubectl گرفته تا اجزای داخلی،‏ فقط از طریق آن کار می‌کنند.
etcdپایگاه داده‌ی کلید-مقدار (key-value) سازگار و با دسترس‌پذیری بالا که همه‌ی داده‌های API server در آن ذخیره می‌شود. «memory» cluster است.
kube-schedulerدنبال Podهایی می‌گردد که هنوز به هیچ Nodeی تخصیص داده نشده‌اند و برای هر کدام یک Node مناسب انتخاب می‌کند.
kube-controller-managercontrollerها را اجرا می‌کند؛‏ همان حلقه‌هایی که رفتار API کوبرنتیز را پیاده می‌کنند (مثلاً Deployment controller یا Node).
cloud-controller-manager (اختیاری)cluster را با cloud provider زیرین یکپارچه می‌کند (مثلاً ساختن load balancer cloud).

اجزای Node (Node Components)

این اجزا روی هر Node اجرا می‌شوند،‏ Podهای در حال اجرا را سرپا نگه می‌دارند و container runtime کوبرنتیز را فراهم می‌کنند:

جزءکارش چیست؟
kubeletمطمئن می‌شود Podها و containerهایشان در حال اجرا و سالم هستند.
kube-proxy (اختیاری)قوانین شبکه را روی Nodeها نگه می‌دارد تا Serviceها کار کنند.
container runtimeنرم‌افزاری که containerها را واقعاً اجرا می‌کند (مثل containerd یا CRI-O). جزئیات در صفحه‌ی Container Runtimes (فصل ۱۳).

ممکن است cluster شما روی هر Node به نرم‌افزار دیگری هم نیاز داشته باشد؛‏ مثلاً روی Nodeهای Linux معمولاً systemd بر اجرای اجزای محلی نظارت می‌کند.

توضیح تکمیلی: سفر یک درخواست از میان اجزا

وقتی در آزمایش قبلی kubectl apply -f shop-api.yaml را اجرا کردید،‏ پشت صحنه این اتفاق‌ها افتاد:

  1. kubectl یک درخواست HTTP به kube-apiserver فرستاد. apiserver هویت شما را احراز کرد (authentication)،‏ مجوزتان را سنجید (authorization)،‏ درخواست را از مرحله‌ی admission گذراند (pluginهایی که می‌توانند درخواست را تغییر دهند یا رد کنند)،‏ درستی‌اش را بررسی کرد (validation) و شیء Deployment را در etcd ذخیره کرد.
  2. Deployment controller داخل kube-controller-manager،‏ که با «watch» مدام منتظر تغییرات apiserver است،‏ یک ReplicaSet ساخت؛‏ و ReplicaSet controller سه Pod ساخت. این Podها هنوز nodeName ندارند،‏ یعنی در وضعیت Pending هستند.
  3. kube-scheduler این Podهای بی‌Node را دید،‏ بر اساس requestها و محدودیت‌ها Node مناسب را انتخاب کرد و این انتخاب (binding) را از طریق apiserver ثبت کرد.
  4. kubelet روی آن Node دید Podی به او سپرده شده؛‏ از طریق interface CRI به container runtime گفت image را بگیرد و container را اجرا کند،‏ probeها را اجرا کرد و وضعیت را به apiserver گزارش داد.
  5. EndpointSlice controller،‏ Podهای آماده (Ready) را به فهرست مقصدهای Service اضافه کرد و kube-proxy روی هر Node قوانین شبکه (در حالت iptables یا nftables؛‏ حالت IPVS از v1.35 منسوخ اعلام شده) را به‌روز کرد تا ترافیکِ IP مجازی Service به Podها برسد.

نکته‌ی کلیدی (و سؤال محبوب مصاحبه): اجزای کوبرنتیز برای هماهنگی مستقیماً با هم ارتباط برقرار نمی‌کنند: scheduler به kubelet «دستور» نمی‌دهد و Deployment controller هم ReplicaSet controller را صدا نمی‌زند. هر کدام شیءها را از apiserver می‌خوانند (با watch) و نتیجه‌ی کارشان را همان‌جا می‌نویسند. تنها جزئی که با etcd ارتباط برقرار می‌کند هم apiserver است. یک استثنا که مصاحبه‌گرها زیاد درباره‌اش می‌پرسند: خود apiserver برای دستورهایی مثل kubectl logs،‏ exec و port-forward مستقیماً به kubelet روی Node وصل می‌شود. نتیجه‌ی این طراحی این است که اگر kube-scheduler چند دقیقه از کار بیفتد،‏ Podهای در حال اجرا هیچ آسیبی نمی‌بینند؛‏ فقط Podهای جدید در وضعیت Pending می‌مانند.

چرا kube-proxy «اختیاری» است؟ چون برخی network pluginها (CNI) خودشان Serviceها را پیاده می‌کنند و جای kube-proxy را می‌گیرند (مثلاً Cilium در حالت kube-proxy replacement؛‏ خارج از مستندات رسمی).‏ cloud-controller-manager هم در clusterهای داخلی سازمان (on-premises) وجود ندارد؛‏ k3s به‌جای آن یک cloud controller سبک داخلی دارد که فقط اطلاعات پایه‌ی Node را تنظیم می‌کند.

Addons

addonها قابلیت‌های کوبرنتیز را گسترش می‌دهند. چند نمونه‌ی مهم:

Addonکاربرد
DNSتبدیل نام به آدرس (DNS resolution) در سطح کل cluster.
web UI (Dashboard)مدیریت cluster از طریق یک interface تحت وب.
پایش منابع containerجمع‌آوری و ذخیره‌ی معیارهای مصرف containerها.
ثبت log در سطح clusterذخیره‌ی log containerها در یک repository مرکزی.
توضیح تکمیلی

addonها جزء «اجباری» کوبرنتیز نیستند،‏ اما در عمل DNS تقریباً همیشه لازم است،‏ چون بدون آن service discovery (پیدا کردن نشانی سرویس‌ها از روی نامشان) با نام (مثل http://shop-api) کار نمی‌کند. بدون ثبت log مرکزی هم،‏ وقتی یک Pod حذف و جایگزین می‌شود،‏ logهای Pod قبلی از بین می‌روند؛‏ برای همین در production logها همیشه به یک repository مرکزی فرستاده می‌شوند (فصل ۱۱). در k3s هر addon یک فایل manifest در پوشه‌ی /var/lib/rancher/k3s/server/manifests روی Node است که k3s خودش آن را اعمال می‌کند؛‏ برای کنار گذاشتن یک addon (جزء اختیاری که قابلیتی به cluster اضافه می‌کند)،‏ هنگام نصب از گزینه‌ی --disable استفاده می‌کنید (مثلاً --disable=traefik).

انعطاف در معماری

کوبرنتیز در نحوه‌ی deployment و مدیریت این اجزا دست شما را باز می‌گذارد. معماری را می‌توان با نیازهای مختلف تطبیق داد؛‏ از یک محیط توسعه‌ی کوچک تا deployment عملیاتی در مقیاس بزرگ. جزئیات هر جزء و روش‌های مختلف چیدمان cluster در صفحه‌ی Cluster Architecture آمده است (فصل ۱۲).

توضیح تکمیلی
محیطچیدمان رایج اجزا (خارج از مستندات رسمی)
لپ‌تاپ یا یک VM (k3s در این جزوه؛‏ یا minikube و kind)همه‌ی اجزا روی یک Node؛‏ در k3s به‌جای etcd به‌طور پیش‌فرض SQLite

اولین Pod (Your first Pod)

هدف این بخش

یک container را در کوبرنتیز اجرا کنیم و چهار دستور اصلی عیب‌یابی را یاد بگیریم.

در پایان این بخش می‌توانید:

  • یک Pod بسازید و وضعیتش را دنبال کنید.
  • با describe و logs و exec داخل آن را ببینید.
  • بفهمید چرا در کار واقعی Pod را مستقیم نمی‌سازیم.

گام ۱. یک Pod با image وب‌سرور nginx بسازید و ساخته شدنش را زنده تماشا کنید (-w یعنی watch؛‏ با Ctrl+C خارج شوید):

  • می‌دانید Pod حذف‌شده خودبه‌خود برنمی‌گردد.

پیش از آزمایش: چهار شیئی که به کار می‌برید (Pod, ReplicaSet, Deployment, Service)

در آزمایش بعدی API فروشگاه را روی cluster می‌برید. پیش از نوشتن اولین خط YAML،‏ این چهار شیء را بشناسید. هر کدام فقط یک مسئولیت دارد و کنار هم مشکل‌های شب حراج را حل می‌کنند.

شیءمسئولیتجواب کدام مشکل شب حراج؟
Podاجرای container برنامه روی یک Node؛‏ یک IP دارد—
ReplicaSetنگه‌داشتن تعداد ثابتی Pod از یک قالباز کار افتادن API ساعت ۲ بامداد
Deploymentاعلام image و تعداد،‏ و انتشار تدریجی نسخه‌هاقطعی هنگام انتشار و برگشت کند
Serviceنشانی ثابت و پخش ترافیک بین Podهاویرایش دستی nginx برای هر container تازه

شیء Pod: کوچک‌ترین واحد اجرا

هر Pod یک یا چند container است که با هم روی یک Node اجرا می‌شوند و یک IP مشترک دارند. نکته‌ی مهم این است که Pod موقتی است: اگر حذف شود یا Node آن از کار بیفتد،‏ خودش برنمی‌گردد. Podی که جایش ساخته می‌شود،‏ نام و IP تازه دارد. برای همین،‏ Pod را تقریباً هیچ‌وقت مستقیم نمی‌سازید و این کار را به شیء بالاتر می‌سپارید (جزئیات در فصل ۳).

شیء ReplicaSet: نگهبان تعداد

هر ReplicaSet یک controller دارد که فقط یک جمله را دنبال می‌کند: «از این Pod template همیشه N عدد باشد». اگر Podی کم شود،‏ تازه می‌سازد و اگر زیاد باشد،‏ حذف می‌کند. شما مستقیم ReplicaSet نمی‌نویسید؛‏ Deployment آن را برایتان می‌سازد.

شیء Deployment: چیزی که شما می‌نویسید

شیء Deployment می‌گوید «از این image،‏ این تعداد Pod بخواه،‏ و نسخه‌ی جدید را این‌طور منتشر کن». برای هر نسخه از Pod template یک ReplicaSet جدا می‌سازد. rolling update یعنی Deployment به‌تدریج ReplicaSet جدید را بزرگ و ReplicaSet قبلی را کوچک می‌کند؛‏ rollback هم یعنی برعکس همین کار (جزئیات در فصل ۴).

شیء Service: نشانی ثابت

چون IP هر Pod موقتی است،‏ clientها نباید مستقیم به Pod وصل شوند. شیء Service یک نام DNS و یک IP مجازی ثابت می‌دهد و ترافیک را بین Podهای آماده پخش می‌کند. Pod تازه خودبه‌خود به Service اضافه می‌شود و Pod حذف‌شده خودبه‌خود کنار می‌رود (جزئیات در فصل ۵).

چسب بین این‌ها: label و selector

هر label یک جفت کلید و مقدار است که روی هر شیء می‌گذارید؛‏ مثل app: shop-api که روی همه‌ی Podهای API فروشگاه می‌گذاریم. هر selector هم شرطی است که با label اشیا را انتخاب می‌کند. شیء Deployment با selector می‌فهمد کدام Podها مال اوست و Service با selector می‌فهمد ترافیک را به کدام Podها بفرستد. بین Service و Pod هیچ پیوند دیگری (مثل نام یا شناسه) وجود ندارد؛‏ اگر label اشتباه باشد،‏ Service هیچ Podی پیدا نمی‌کند. دو شیء Deployment و ReplicaSet علاوه بر selector،‏ مالکیت را با owner reference (فیلدی در metadata که مالک یک شیء را مشخص می‌کند) هم ثبت می‌کنند (فصل ۸).

دو مفهوم کمکی: probe و requests

  • probe: آزمایشی که kubelet مدام روی container انجام می‌دهد. readiness probe می‌پرسد «آماده‌ی گرفتن ترافیک هستی؟» و liveness probe می‌پرسد «هنوز زنده‌ای یا گیر کرده‌ای؟» (فصل ۳).
  • requests: مقدار CPU و memory که برای container رزرو می‌شود؛‏ scheduler بر اساس آن Node مناسب را انتخاب می‌کند (فصل ۶).
چرا این‌قدر لایه؟

ممکن است بپرسید چرا یک شیء همه‌ی این کارها را نمی‌کند. جواب این است که هر لایه یک کار را خوب انجام می‌دهد: کار Pod اجرا کردن است،‏ کار ReplicaSet نگه داشتن تعداد،‏ کار Deployment مدیریت نسخه‌ها و کار Service دادن نشانی. نتیجه‌ی این جداسازی در همین آزمایش دیده می‌شود: rollback فقط یعنی «ReplicaSet قبلی را دوباره بزرگ کن»،‏ و Service در تمام این مدت بدون هیچ تغییری کار می‌کند،‏ چون فقط به label نگاه می‌کند.

خواندن YAML در سه قاعده
  • تورفتگی ساختار را می‌سازد: هر سطح دو فاصله (space) جلوتر است. از Tab استفاده نکنید.
  • کلید و مقدار با «:» و یک فاصله نوشته می‌شوند؛‏ مثل replicas: 3 که تعداد را تعیین می‌کند.
  • خط تیره یعنی یک عضو فهرست؛‏ مثلاً - name: web اولین container در فهرست containerهاست.

لازم نیست فیلدها را حفظ کنید. هر فیلدی را با دستور explain از خود cluster بپرسید؛‏ مثلاً برای strategy:

shell
kubectl explain deployment.spec.strategy

عددهایی مثل ‎(1)‎ که کنار خط‌های YAML این فصل آمده،‏ comment هستند و کوبرنتیز آن‌ها را نادیده می‌گیرد؛‏ فقط برای ارجاع به جدول توضیح زیر هر فایل‌اند.

آزمایش عملی شاپیفای: API با سه replica،‏ بدون قطعی

در این آزمایش مشکل‌های شب حراج را یکی‌یکی روی cluster k3s همین فصل حل می‌کنید. فایل‌ها را گام‌به‌گام می‌سازید و هر خط را پیش از اجرا توضیح می‌دهیم. خروجی‌ها نمونه‌اند؛‏ نام Podها،‏ IPها و زمان‌ها در محیط شما فرق خواهد داشت.

گام ۰: یک namespace برای شاپیفای

از این فصل تا پایان جزوه،‏ همه‌ی اشیای شاپیفای را در namespace به نام shopify می‌سازیم. namespace یک پوشه‌ی منطقی در cluster است و نام‌ها فقط داخل آن باید یکتا باشند (فصل ۸). دستور دوم namespace پیش‌فرض kubectl را عوض می‌کند تا لازم نباشد هر بار -n shopify بنویسید.

kubectl create namespace shopify

گام ۱: اولین Deployment

فایل shop-api.yaml را با ویرایشگر دلخواه بسازید و این محتوا را در آن بگذارید:

shop-api.yaml (گام ۱)
apiVersion: apps/v1          # (1)
kind: Deployment             # (2)
metadata:                    # (3)
  name: shop-api             # (4)
  labels:
    app: shop-api            # (5)
spec:                        # (6)
  replicas: 3                # (7)
  selector:                  # (8)
    matchLabels:
      app: shop-api
  template:                  # (9)
    metadata:
      labels:
        app: shop-api        # (10)
    spec:                    # (11)
      containers:            # (12)
      - name: web            # (13)
        image: nginx:1.26    # (14)
        ports:
        - containerPort: 80  # (15)
خطیعنی چه؟
(1)نسخه‌ی API که این نوع شیء در آن تعریف شده است. Deployment در API group به نام apps و نسخه‌ی v1 است؛‏ Pod و Service در گروه اصلی (core) هستند و فقط v1 می‌نویسند. برای هر نوع شیء،‏ kubectl api-resources مقدار درست را نشان می‌دهد.
(2)نوع شیء. همین کلمه تعیین می‌کند کدام controller مسئول آن است.
(3)شناسنامه‌ی شیء: نام،‏ namespace و labelها.
(4)نام Deployment. در هر namespace برای هر نوع شیء یکتاست و نام ReplicaSet و Podها از آن ساخته می‌شود.
(5)همان label خود Deployment. فقط برای پیدا کردن خود Deployment است (مثلاً kubectl get deploy -l app=shop-api) و روی Podها اثری ندارد.
(6)بخش spec همان desired state است: آنچه می‌خواهید باشد.
(7)تعداد Podهایی که باید همیشه وجود داشته باشند.
(8)شرط انتخاب Podهای این Deployment: هر Pod با label app: shop-api. این فیلد پس از ساخت Deployment قابل تغییر نیست.
(9)Pod template. هر Pod دقیقاً از روی همین قالب ساخته می‌شود. هر تغییر در قالب یعنی نسخه‌ی تازه و rollout.
(10)همان labelی که روی تک‌تک Podها می‌نشیند. باید با selector خط (8) بخواند،‏ وگرنه API server فایل را رد می‌کند.
(11)بخش spec مربوط به خود Pod؛‏ یعنی containerها و تنظیماتشان.
(12)فهرست containerهای Pod. خط تیره یعنی عضو فهرست؛‏ یک Pod می‌تواند چند container داشته باشد.
(13)نام container داخل Pod. در دستورهایی مثل kubectl logs -c web به کار می‌رود.
(14)نام image و tag آن. فعلاً image آماده‌ی nginx جای API واقعی را گرفته است؛‏ در فصل ۲ API واقعی را می‌سازیم و فقط همین خط عوض می‌شود.
(15)شماره‌ی port که container روی آن گوش می‌دهد. این فیلد فقط اطلاع‌رسانی است و port را باز یا بسته نمی‌کند؛‏ ولی نوشتنش خواندن فایل را آسان می‌کند.

  • نام ReplicaSet: نام Deployment به‌اضافه‌ی یک hash از Pod template،‏ مثل 5d8f7b9c6d در این‌جا. قالب که عوض شود،‏ hash و در نتیجه ReplicaSet هم عوض می‌شود.

امتحان کنید: label ناهماهنگ

در فایل،‏ مقدار label خط (10) را به shop تغییر دهید و دوباره apply کنید. این بار API server فایل را رد می‌کند:

این رایج‌ترین خطای نوشتن Deployment است. label را به shop-api برگردانید.

گام ۲: یک نشانی ثابت با Service

فایل دوم را با نام shop-api-svc.yaml بسازید:

shop-api-svc.yaml
apiVersion: v1          # (1)
kind: Service
metadata:
  name: shop-api        # (2)
spec:
  selector:             # (3)
    app: shop-api
  ports:
  - port: 80            # (4)
    targetPort: 80      # (5)
خطیعنی چه؟
(1)مقدار v1 یعنی Service در گروه اصلی API است.
(2)نام Service. همین نام،‏ نام DNS آن هم هست: داخل همین namespace با shop-api و از هر جای cluster با نام کامل shop-api.shopify.svc.cluster.local در دسترس است.
(3)هر Pod با label app: shop-api مقصد ترافیک است؛‏ فرقی نمی‌کند کدام Deployment آن را ساخته باشد.
(4)شماره‌ی port خود Service؛‏ clientها به این port وصل می‌شوند.
(5)شماره‌ی port مقصد روی Pod؛‏ همان containerPort خط (15) فایل Deployment.
—فیلد type نوشته نشده،‏ پس پیش‌فرض ClusterIP است: نشانی فقط داخل cluster در دسترس است. دسترسی مشتری‌ها از بیرون،‏ با Ingress،‏ کار فصل ۵ است.

در این دستور،‏ --rm یعنی Pod پس از پایان کار حذف شود و -it یعنی خروجی را همین‌جا ببینید. نام shop-api را CoreDNS به IP مربوط به Service تبدیل کرد و قواعد شبکه‌ی Node درخواست را به یکی از سه Pod رساندند. frontend شاپیفای هم در آینده API را دقیقاً با همین نام صدا می‌زند و هیچ‌وقت IP هیچ Podی را نمی‌داند.

گام ۳: probeها؛‏ ترافیک فقط به Pod سالم

هر Pod در وضعیت Running لزوماً آماده‌ی جواب دادن نیست؛‏ برنامه ممکن است هنوز در حال راه‌اندازی باشد یا گیر کرده باشد. در فایل shop-api.yaml بخش containers را این‌طور کامل کنید:

shop-api.yaml (گام ۳،‏ فقط بخش containers)
      containers:
      - name: web
        image: nginx:1.26
        ports:
        - containerPort: 80
        readinessProbe:            # (16)
          httpGet:                 # (17)
            path: /
            port: 80
          periodSeconds: 5         # (18)
        livenessProbe:             # (19)
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10  # (20)
          periodSeconds: 10
خطیعنی چه؟
(16)این readiness probe است: «آماده‌ی ترافیک هستی؟» اگر شکست بخورد،‏ Pod از فهرست مقصدهای Service بیرون می‌رود ولی restart نمی‌شود. وقتی دوباره موفق شد،‏ برمی‌گردد.
(17)روش آزمایش: kubelet یک درخواست GET به مسیر ‎/‎ روی port 80 همان Pod می‌فرستد. کد پاسخ ۲۰۰ تا ۳۹۹ یعنی موفق.
(18)هر ۵ ثانیه یک بار (پیش‌فرض ۱۰ ثانیه).
(19)این liveness probe است: «زنده‌ای؟» اگر پشت‌سرهم شکست بخورد (پیش‌فرض ۳ بار)،‏ آنگاه kubelet container را kill و دوباره اجرا می‌کند.
(20)پیش از اولین آزمایش liveness ده ثانیه صبر کن تا برنامه فرصت راه‌اندازی داشته باشد.
چرا هر دو probe همان مسیر را آزمایش می‌کنند؟

برنامه‌ی nginx مسیر جداگانه‌ای برای سلامت ندارد. در API واقعی (فصل‌های ۲ و ۳) دو مسیر جدا می‌سازیم: /healthz فقط زنده بودن process را می‌سنجد و /ready آمادگی را،‏ مثلاً وصل بودن به پایگاه داده. دام: اگر liveness probe به پایگاه داده وابسته باشد،‏ با قطع پایگاه داده همه‌ی Podها پشت‌سرهم restart می‌شوند و مشکل بدتر می‌شود.

shell

kubectl get rs -l app=shop-api
kubectl describe pod -l app=shop-api | grep -E 'Liveness|Readiness' | head -2

دو نکته در این خروجی است. اول،‏ تغییر قالب یک ReplicaSet تازه ساخت و Podهای قبلی به‌تدریج جایگزین شدند؛‏ این اولین rolling update شما بود. ReplicaSet قبلی با صفر Pod نگه داشته می‌شود تا برگشت ممکن باشد (پیش‌فرض تا ۱۰ نسخه). دوم،‏ در خروجی describe مقدارهای پیش‌فرضی را می‌بینید که ننوشته بودید؛‏ مثل timeout=1s و #failure=3 که یعنی مهلت یک‌ثانیه‌ای برای هر آزمایش و سه شکست پیاپی پیش از اقدام.

گام ۴: انتشار امن و رزرو منابع

دو بخش دیگر به فایل اضافه کنید: بخش strategy زیر spec مربوط به Deployment،‏ و بخش resources داخل container که هم‌سطح ports قرار می‌گیرد. بخش‌های افزوده را در قاب زیر می‌بینید:

shop-api.yaml (گام ۴،‏ بخش‌های افزوده)
spec:
  replicas: 3
  strategy:
    type: RollingUpdate     # (21)
    rollingUpdate:
      maxSurge: 1           # (22)
      maxUnavailable: 0     # (23)
  selector:
    ...
        resources:
          requests:
            cpu: 100m       # (24)
            memory: 64Mi    # (25)
خطیعنی چه؟
(21)روش rollout نسخه‌ی جدید. مقدار RollingUpdate یعنی تدریجی؛‏ گزینه‌ی دیگر Recreate است که اول همه‌ی Podهای قدیمی را حذف می‌کند و قطعی دارد.
(22)در حین rollout حداکثر یک Pod بیشتر از تعداد خواسته‌شده (یعنی ۴ Pod) مجاز است.
(23)در حین rollout هیچ Pod آماده‌ای نباید کم شود؛‏ یعنی همیشه دست‌کم ۳ Pod آماده داریم.
(24)رزرو ۱۰۰ میلی‌core یعنی یک‌دهم یک هسته‌ی CPU است. در نتیجه scheduler این Pod را فقط روی Nodeی می‌گذارد که این مقدار آزاد داشته باشد.
(25)رزرو ۶۴ مگابایت (mebibyte) از memory. این عدد سقف نیست؛‏ یعنی container می‌تواند بیشتر مصرف کند. سقف با limits تعیین می‌شود (فصل ۶).
مقدار پیش‌فرض چیست و چرا صریح نوشتیم؟

اگر strategy را ننویسید،‏ پیش‌فرض RollingUpdate با maxSurge و maxUnavailable برابر ۲۵٪ است. درصد surge رو به بالا و درصد unavailable رو به پایین گرد می‌شود؛‏ پس برای ۳ replica،‏ پیش‌فرض هم دقیقاً یک Pod اضافه و صفر Pod ناموجود است. صریح نوشتیم تا خواننده‌ی فایل بی‌حساب‌وکتاب بفهمد و تا وقتی replicas را مثلاً به ۸ رساندیم،‏ رفتار عوض نشود (با ۸ replica،‏ پیش‌فرض ۲ و ۲ می‌شود).

shell
kubectl apply -f shop-api.yaml
kubectl get rs -l app=shop-api
خروجی نمونه
deployment.apps/shop-api configured
NAME                  DESIRED   CURRENT   READY   AGE
shop-api-5d8f7b9c6d   0         0         0       9m
shop-api-6b7f9c8d4d   3         3         3       25s
shop-api-7c9d8f6b5b   0         0         0       3m

باز هم یک ReplicaSet تازه ساخته شد،‏ ولی فقط به خاطر resources که داخل قالب است. تغییر strategy به‌تنهایی rollout ایجاد نمی‌کند،‏ چون بیرون از Pod template است. قاعده: فقط تغییر در template نسخه‌ی تازه می‌سازد.

دو شیء Deployment و Service را می‌توانید در یک فایل با جداکننده‌ی ‎---‎ نگه دارید. نسخه‌ی کامل فایل تا این‌جا (از این به بعد همین فایل را به کار می‌بریم):

shop-api.yaml (نسخه‌ی کامل)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
  labels:
    app: shop-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 1 extra Pod during a rollout
      maxUnavailable: 0    # never fewer than 3 ready Pods
  selector:
    matchLabels:
      app: shop-api
  template:
    metadata:
      labels:
        app: shop-api
    spec:
      containers:
      - name: web
        image: nginx:1.26
        ports:
        - containerPort: 80
        readinessProbe:     # no traffic until ready
          httpGet:
            path: /
            port: 80
          periodSeconds: 5
        livenessProbe:      # restart if stuck
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10
          periodSeconds: 10
        resources:
          requests:
            cpu: 100m
            memory: 64Mi
---
apiVersion: v1
kind: Service
metadata:
  name: shop-api
spec:
  selector:
    app: shop-api
  ports:
  - port: 80
    targetPort: 80

kubectl apply -f shop-api.yaml
rm shop-api-svc.yaml

service/shop-api unchanged

گام ۶: self-healing در سطح Pod؛‏ جواب مشکل اول

یک Pod را حذف کنید؛‏ از دید controller،‏ نتیجه مثل از دست رفتن Pod به هر دلیل دیگری است. فرقش این است که این‌جا جایگزینی فوری است،‏ اما وقتی یک Node از دسترس خارج می‌شود،‏ به‌طور پیش‌فرض حدود ۵ دقیقه طول می‌کشد (تمرین ۳ را ببینید).

shell
# terminal 1
kubectl get pods -l app=shop-api -w
# terminal 2
kubectl delete pod shop-api-6b7f9c8d4d-2xkqp
خروجی ترمینال اول
NAME                        READY   STATUS              RESTARTS   AGE
shop-api-6b7f9c8d4d-2xkqp   1/1     Terminating         0          2m
shop-api-6b7f9c8d4d-q9rjd   0/1     Pending             0          0s
shop-api-6b7f9c8d4d-q9rjd   0/1     ContainerCreating   0          0s

چه اتفاقی افتاد؟ controller مربوط به ReplicaSet دید تعداد Podها از ۳ به ۲ رسیده (current state با desired state فرق دارد) و بلافاصله یک Pod تازه با نام و IP جدید ساخت. به ستون READY دقت کنید: Pod جدید چند ثانیه ‎0/1‎ بود. در این فاصله readiness probe هنوز موفق نشده بود و Service هیچ ترافیکی به آن نمی‌فرستاد؛‏ یعنی «تا آماده نشده،‏ به clientها معرفی نمی‌شود». با Ctrl+C از -w بیرون بیایید.

گام ۷: self-healing در سطح container؛‏ کشتن process اصلی

shell
kubectl exec shop-api-6b7f9c8d4d-8hvzn -- sh -c 'kill 1'
kubectl get pod shop-api-6b7f9c8d4d-8hvzn
خروجی نمونه
NAME                        READY   STATUS    RESTARTS     AGE
shop-api-6b7f9c8d4d-8hvzn   1/1     Running   1 (4s ago)   3m

این بار Pod حذف نشد! دستور exec فرمانی را داخل container اجرا کرد و kill 1 به process شماره‌ی ۱ آن container،‏ یعنی خود nginx،‏ سیگنال پایان فرستاد. kubelet همان container را طبق restartPolicy: Always (برای Podهای یک Deployment تنها مقدار مجاز همین است) دوباره اجرا کرد و ستون RESTARTS یکی بالا رفت. نام و IP Pod ثابت ماند. فرق این گام با گام ۶ را به خاطر بسپارید: راه‌اندازی مجدد container کار kubelet است،‏ جایگزینی Pod کار controller. همین دو سازوکار بودند که ساعت ۲ بامداد شب حراج کم بودند.

گام ۸: rolling update بدون قطعی؛‏ جواب مشکل سوم

اول در ترمینال دوم یک Pod بسازید که هر نیم ثانیه API را صدا بزند و نتیجه را بنویسد؛‏ این نقش مشتری‌های فروشگاه را بازی می‌کند:

shell

اگر یکی دو FAIL دیدید

در لحظه‌ی حذف یک Pod قدیمی،‏ بین شروع خاموش شدن آن و به‌روز شدن قواعد شبکه‌ی Node فاصله‌ی کوتاهی هست و ممکن است یک درخواست به Podی برسد که در حال بسته شدن است. راه‌حل استاندارد،‏ کمی تأخیر پیش از خاموش شدن با preStop hook است (فصل ۳). دستور kubectl set image هم همین کار را بدون ویرایش فایل می‌کند،‏ ولی مثل گام ۵ فایل را از cluster عقب می‌اندازد.

ابزار خط فرمان kubectl (The kubectl command-line tool)

kubectl (تلفظ رایج: «کیوب‌کنترل» یا «کیوب‌سی‌تی‌ال») ابزار اصلی خط فرمان برای کار با cluster کوبرنتیز است. این ابزار از طریق API کوبرنتیز با control plane cluster ارتباط برقرار می‌کند.

kubectl برای پیدا کردن cluster و اطلاعات ورود،‏ به‌طور پیش‌فرض دنبال فایلی به نام config در پوشه‌ی $HOME/.kube می‌گردد. به این فایل «kubeconfig» می‌گویند. اگر بخواهید از فایل دیگری استفاده کنید،‏ یا environment variable KUBECONFIG را تنظیم کنید یا از flag --kubeconfig استفاده کنید.

نقش kubectl

kubectl interface اصلی برای ساختن،‏ بررسی،‏ به‌روزکردن و حذف شیءهای کوبرنتیز است. این ابزار مکمل اجزای کوبرنتیز (که داخل cluster اجرا می‌شوند) و API کوبرنتیز (که همان اجزا پیاده‌اش می‌کنند) است. چه kubectl را روی لپ‌تاپ اجرا کنید و چه داخل یک Pod در cluster،‏ در هر حال درخواست‌هایش به API server می‌رود. clientهای دیگر مثل libraryهای برنامه‌نویسی و داشبوردهای وب مثل Headlamp هم از همین API استفاده می‌کنند. به بیان ساده: kubectl هیچ جادویی ندارد؛‏ فقط یک client HTTP هوشمند برای API کوبرنتیز است.

kubectl چطور کار می‌کند؟

kubectl به API server وصل می‌شود و با استفاده از cluster،‏ کاربر و context تعریف‌شده در فایل kubeconfig authentication می‌کند. وقتی آن را از بیرون cluster اجرا می‌کنید،‏ آدرس API server و اطلاعات ورود را از فایل kubeconfig برمی‌دارد. وقتی داخل یک Pod اجرا شود (مثلاً در یک خط لوله‌ی CI/CD)،‏ می‌تواند از in-cluster authentication استفاده کند؛‏ یعنی از token ServiceAccount که به‌طور خودکار داخل Pod قرار داده شده است.

هر دستوری که اجرا می‌کنید،‏ kubectl خواسته‌ی شما را به یک یا چند درخواست HTTP به API کوبرنتیز تبدیل می‌کند. API server هر درخواست را validation می‌کند،‏ آن را روی وضعیت cluster (که در etcd ذخیره شده) اعمال می‌کند و نتیجه را برمی‌گرداند. یعنی هر کاری با kubectl انجام دهید،‏ از ساختن Deployment تا خواندن log،‏ از همین مسیر مبتنی بر API می‌گذرد.

چون یک فایل kubeconfig می‌تواند چند cluster،‏ چند کاربر و چند context داشته باشد،‏ می‌توانید بدون تغییر تنظیمات بین clusterها جابه‌جا شوید. برای عوض‌کردن context فعال از kubectl config use-context استفاده کنید.

با kubectl چه کارهایی می‌شود کرد؟

کارهای kubectl در این دسته‌ها جا می‌گیرند:

  • مدیریت منابع: ساختن،‏ به‌روزکردن و حذف شیءهایی مثل Pod،‏ Deployment و Service. برای مدیریت اعلانی بر اساس فایل‌های پیکربندی،‏ از kubectl apply استفاده کنید.
  • بررسی وضعیت cluster: فهرست‌کردن و توصیف شیءها (get و describe)،‏ دیدن eventها و بررسی مصرف منابع.
  • عیب‌یابی: دیدن log containerها،‏ اجرای دستور داخل یک container در حال اجرا،‏ یا باز کردن تونل port (port-forward) به یک Pod.
  • عملیات cluster:‏ drain (خالی کردن امن Node از Podها پیش از نگهداری) کردن Nodeها برای نگهداری،‏ علامت‌گذاری Nodeها برای اینکه بار جدید نگیرند (cordon)،‏ و مدیریت پیکربندی cluster.
  • اسکریپت‌نویسی و خودکارسازی: گرفتن خروجی به شکل JSON،‏ YAML یا ستون‌های سفارشی با JSONPath برای استفاده در scriptها و خط لوله‌ها.

نحو دقیق،‏ مرجع دستورها و مثال‌ها در مستندات مرجع kubectl آمده است (ادامه‌ی همین فصل و فصل ۱۷).

توضیح تکمیلی: برای هر دسته یک دستور واقعی
shell
# Manage resources

# Inspect cluster state

kubectl events -n shop --for deployment/shop-api

# Cluster operations
kubectl cordon worker-2
kubectl drain worker-2 --ignore-daemonsets --delete-emptydir-data
kubectl uncordon worker-2
# Script and automate
kubectl get pods -n shop -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}'

اعلانی در برابر دستوری (Declarative vs imperative)

برای workloadهای عملیاتی،‏ مدیریت اعلانی را ترجیح دهید: فایل‌های پیکربندی را در سیستم کنترل نسخه (مثل Git) نگه دارید و با kubectl apply اعمالشان کنید. روش اعلانی کمک می‌کند تغییرات را ردیابی کنید،‏ تیمی کار کنید و با روش‌های GitOps یکپارچه شوید. دستورهای دستوری (imperative) مثل kubectl create یا kubectl run برای توسعه و آزمایش مفیدند،‏ اما بازتولید و ممیزی (audit) آن‌ها سخت‌تر است.

توضیح تکمیلی: یک داستان واقعی

ساعت ۳ بامداد،‏ مهندس کشیک با kubectl scale deploy/shop-api --replicas=10 مشکل را موقتاً حل می‌کند. فردا خط لوله‌ی CI دوباره kubectl apply را با فایل Git اجرا می‌کند که در آن replicas: 3 نوشته شده؛‏ تعداد به ۳ برمی‌گردد و مشکل تکرار می‌شود. در Git هم هیچ ردی از تغییر دیشب نیست. برای همین مستندات برای production روش اعلانی را توصیه می‌کند: تغییر را در Git بدهید،‏ بازبینی شود،‏ بعد اعمال شود. (راه درست برای تعداد replica متغیر،‏ استفاده از HorizontalPodAutoscaler و حذف فیلد replicas از فایل است؛‏ فصل ۱۰.) سه روش مدیریت شیءها در فصل ۸ کامل بررسی می‌شوند.

یک ترفند پرکاربرد: از دستورهای imperative فقط برای «تولید» YAML استفاده کنید و خروجی را در Git ذخیره کنید:

shell
kubectl create deployment shop-api --image=nginx:1.27 --replicas=3 --dry-run=client -o yaml > shop-api.yaml
kubectl diff -f shop-api.yaml     # قبل از apply ببینید چه تغییری می‌کند
kubectl apply -f shop-api.yaml

گسترش kubectl با pluginها (plugins)

می‌توانید با pluginها زیردستورهای تازه به kubectl اضافه کنید. هر plugin یک فایل اجرایی مستقل است که نامش از الگوی kubectl-<plugin-name> پیروی می‌کند. جامعه‌ی کوبرنتیز تعداد زیادی plugin نگهداری می‌کند که می‌توانید آن‌ها را با مدیر plugin به نام Krew نصب و مدیریت کنید.

سازگاری نسخه‌ها

kubectl تا یک نسخه‌ی minor بالاتر یا پایین‌تر از control plane cluster پشتیبانی می‌شود. مثلاً kubectl نسخه‌ی v1.32 با control plane v1.31،‏ v1.32 و v1.33 کار می‌کند. استفاده از نسخه‌ی سازگار جلوی رفتارهای غیرمنتظره را می‌گیرد. جزئیات در «version skew policy» (قواعد اختلاف نسخه‌ی مجاز بین اجزای cluster) آمده است.

توضیح تکمیلی
shell

Kustomize Version: v5.7.1
Server Version: v1.35.4
WARNING: version difference between client (1.37) and server (1.35) exceeds the supported minor version skew of +/-1

تیمی که چند cluster با نسخه‌های مختلف دارد (مثلاً یک cluster قدیمی v1.35 و یک cluster جدید v1.37)،‏ نمی‌تواند با یک فایل kubectl با هر دو در محدوده‌ی پشتیبانی‌شده کار کند. راه‌حل رایج (خارج از مستندات رسمی): نگه‌داشتن چند نسخه‌ی kubectl یا استفاده از ابزارهایی مثل asdf یا mise برای انتخاب نسخه بر اساس cluster،‏ و ثابت‌کردن نسخه‌ی kubectl در image CI.

مرجع ابزار خط فرمان kubectl (Command line tool reference)

این بخش مرجع است

لازم نیست این بخش را پشت‌سرهم بخوانید. برای شروع،‏ نحو کلی دستور و مثال‌های «عملیات رایج» کافی است؛‏ بقیه را هر وقت دستوری لازم شد،‏ این‌جا یا در فصل ۱۷ پیدا کنید. شما همین حالا در آزمایش شاپیفای با دستورهای apply و get و describe و logs و exec و scale و rollout کار کرده‌اید؛‏ این بخش شکل کامل همین دستورهاست.

صفحه‌ی مرجع kubectl جزئیات نحو دستورها،‏ عملیات و مثال‌ها را توضیح می‌دهد. خلاصه‌ی شروع آن همان چیزی است که در بخش قبل دیدیم: kubectl ابزار خط فرمانی است که با API کوبرنتیز با control plane ارتباط برقرار می‌کند؛‏ تنظیماتش را از فایل $HOME/.kube/config می‌خواند و می‌توانید فایل دیگری را با متغیر KUBECONFIG یا flag --kubeconfig به آن بدهید.

این بخش نحو کلی دستور kubectl را توضیح می‌دهد،‏ عملیات مختلف را معرفی می‌کند و مثال‌های رایج می‌آورد. برای جزئیات کامل هر دستور (همه‌ی flagها و زیردستورها) به مستندات مرجع kubectl مراجعه کنید؛‏ برای نصب،‏ صفحه‌ی Installing kubectl؛‏ و برای راهنمای سریع،‏ cheat sheet (فصل ۱۷). اگر به دستور docker عادت دارید،‏ صفحه‌ی «kubectl for Docker Users» معادل دستورهای Docker را در کوبرنتیز نشان می‌دهد.

نحو دستور (Syntax)

شکل کلی هر دستور kubectl این است:

shell
kubectl [command] [TYPE] [NAME] [flags]

که در آن:

  • command: کاری که می‌خواهید روی یک یا چند منبع انجام دهید؛‏ مثل create،‏ get،‏ describe یا delete.
  • TYPE: نوع منبع. نوع منبع به کوچکی و بزرگی حروف حساس نیست و می‌توانید آن را مفرد،‏ جمع یا کوتاه‌شده بنویسید. مثلاً این سه دستور خروجی یکسانی دارند:
    shell
    kubectl get pod pod1
kubectl get pods pod1
kubectl get po pod1
  • NAME: نام منبع. نام‌ها به کوچکی و بزرگی حروف حساس‌اند. اگر نام را ننویسید،‏ همه‌ی منابع آن نوع نمایش داده می‌شوند؛‏ مثلاً kubectl get pods.

    برای کار روی چند منبع هم‌زمان،‏ می‌توانید منابع را با نوع و نام مشخص کنید یا یک یا چند فایل بدهید:

    • مشخص‌کردن با نوع و نام:
      • اگر همه از یک نوع باشند،‏ گروهی بنویسید: TYPE1 name1 name2 name<#>
        مثال: kubectl get pod example-pod1 example-pod2
      • اگر از نوع‌های مختلف باشند،‏ هر کدام را جدا بنویسید: TYPE1/name1 TYPE1/name2 TYPE2/name3 TYPE<#>/name<#>
        مثال: kubectl get pod/example-pod1 replicationcontroller/example-rc1
    • مشخص‌کردن با فایل: -f file1 -f file2 -f file<#>
      • YAML را به JSON ترجیح دهید؛‏ خواندن و نوشتنش برای انسان راحت‌تر است،‏ به‌خصوص در فایل‌های پیکربندی.
        مثال: kubectl get -f ./pod.yaml
  • flags: flagهای اختیاری. مثلاً با -s یا --server می‌توانید آدرس و port API server را مشخص کنید.
هشدار

flagهایی که در خط فرمان می‌دهید،‏ بر مقادیر پیش‌فرض و environment variableهای متناظر اولویت دارند و آن‌ها را نادیده می‌گیرند.

هر وقت به راهنما نیاز داشتید،‏ kubectl help را اجرا کنید.

توضیح تکمیلی

فرق حساسیت به حروف را با یک مثال ببینید: kubectl get PODS و kubectl get Pods هر دو کار می‌کنند،‏ چون TYPE حساس نیست؛‏ اما kubectl get pod Shop-API یک Pod به نام shop-api را پیدا نمی‌کند،‏ چون NAME حساس است (و در عمل نام‌ها باید با حروف کوچک باشند؛‏ فصل ۸).

دو شکل گروه‌بندی با هم فرق مهمی دارند: در kubectl get pod a b هر دو نام از نوع pod فرض می‌شوند؛‏ در kubectl get pod/a svc/b هر مورد نوع خودش را دارد. ترکیب این دو شکل (kubectl get pod a svc/b) مجاز نیست و خطا می‌دهد.

shell
kubectl explain deployment.spec.strategy      # مستندات فیلد از خود API server
kubectl get deploy shop-api -h                # help هر دستور

in-cluster authentication و تغییر namespace پیش‌فرض

kubectl قبل از هر کاری بررسی می‌کند که آیا داخل یک Pod (و در نتیجه داخل cluster) اجرا می‌شود یا نه. برای این کار سه چیز را نگاه می‌کند: environment variableها KUBERNETES_SERVICE_HOST و KUBERNETES_SERVICE_PORT،‏ و وجود فایل token ServiceAccount در مسیر /var/run/secrets/kubernetes.io/serviceaccount/token. اگر هر سه وجود داشته باشند،‏ فرض می‌کند داخل cluster است و از in-cluster authentication استفاده می‌کند.

برای سازگاری با نسخه‌های قدیمی،‏ اگر در این حالت environment variable POD_NAMESPACE هم تنظیم شده باشد،‏ مقدار آن بر namespace پیش‌فرضی که از token ServiceAccount به دست می‌آید اولویت پیدا می‌کند. هر فایل یا ابزاری که روی namespace پیش‌فرض حساب کرده باشد،‏ از این رفتار تأثیر می‌گیرد.

environment variable POD_NAMESPACE

اگر POD_NAMESPACE تنظیم شده باشد،‏ دستورهایی که روی منابع namespaceدار کار می‌کنند به‌طور پیش‌فرض از مقدار آن استفاده می‌کنند. مثلاً اگر مقدارش seattle باشد،‏ kubectl get pods Podهای namespace seattle را برمی‌گرداند؛‏ چون Pod یک منبع namespaceدار است و در دستور namespaceی مشخص نشده. برای اینکه ببینید یک منبع namespaceدار است یا نه،‏ خروجی kubectl api-resources را نگاه کنید.

اگر صریحاً --namespace <value> بدهید،‏ این رفتار نادیده گرفته می‌شود.

kubectl با token ServiceAccount چه می‌کند؟

اگر همه‌ی این شرط‌ها برقرار باشد:

  • فایل token ServiceAccount در مسیر /var/run/secrets/kubernetes.io/serviceaccount/token وجود داشته باشد،‏
  • متغیر KUBERNETES_SERVICE_HOST تنظیم شده باشد،‏
  • متغیر KUBERNETES_SERVICE_PORT تنظیم شده باشد،‏
  • و شما در دستور namespaceی مشخص نکرده باشید،‏

آنگاه kubectl فرض می‌کند داخل cluster اجرا می‌شود،‏ namespace آن ServiceAccount (که همان namespace خود Pod است) را پیدا می‌کند و روی همان کار می‌کند. این با حالت بیرون از cluster فرق دارد: بیرون از cluster،‏ اگر namespaceی ندهید،‏ kubectl روی namespaceی کار می‌کند که برای context فعلی در kubeconfig تنظیم شده. برای عوض‌کردن namespace پیش‌فرض می‌توانید از این دستور استفاده کنید:

برای اطلاعات بیشتر درباره‌ی هر عملیات،‏ مستندات مرجع kubectl را ببینید.

توضیح تکمیلی: عملیاتی که در production هر روز به کار می‌آیند
  • create در برابر apply در برابر replace (سؤال پرتکرار مصاحبه): create اگر شیء از قبل وجود داشته باشد خطای AlreadyExists می‌دهد. apply اگر شیء نباشد می‌سازدش و اگر باشد تغییرات را ادغام (merge) می‌کند؛‏ یعنی اعلانی است. replace کل شیء را با محتوای فایل عوض می‌کند و هر فیلدی که در فایل نباشد پاک می‌شود.
  • cordon،‏ drain،‏ uncordon: سه گام نگهداری یک Node. cordon فقط جلوی آمدن Pod جدید را می‌گیرد. drain علاوه بر cordon،‏ Podهای موجود را هم با رعایت PodDisruptionBudget evict می‌کند. بعد از پایان نگهداری،‏ با uncordon Node دوباره قابل‌استفاده می‌شود.
  • rollout: زیردستورهای status،‏ history،‏ undo،‏ pause،‏ resume و restart را دارد. kubectl rollout restart deployment/shop-api همه‌ی Podها را به‌تدریج از نو می‌سازد؛‏ مثلاً بعد از تغییر یک Secret که به شکل environment variable خوانده می‌شود (environment variable فقط هنگام شروع container خوانده می‌شود).
  • auth: kubectl auth can-i delete pods -n prod و kubectl auth can-i --list --as=system:serviceaccount:ci:deployer برای بررسی دسترسی‌های RBAC بسیار پرکاربردند (فصل ۱۴).
  • wait: در خط لوله‌های CI برای صبرکردن تا آماده‌شدن منبع: kubectl wait --for=condition=available deployment/shop-api --timeout=120s.
  • توضیح autoscale و scale در متن مرجع هنوز از ReplicationController نام می‌برد (متن قدیمی)،‏ اما امروز این دستورها بیشتر روی Deployment،‏ ReplicaSet و StatefulSet به کار می‌روند.

گزینه‌های خروجی (Output options)

در این بخش می‌بینید چطور خروجی برخی دستورها را قالب‌بندی یا مرتب کنید. اینکه کدام دستور از کدام گزینه پشتیبانی می‌کند،‏ در مستندات مرجع kubectl آمده است.

قالب‌بندی خروجی

خروجی پیش‌فرض همه‌ی دستورهای kubectl متن ساده و خوانا برای انسان است. برای دیدن جزئیات با قالبی مشخص،‏ flag -o (یا --output) را به دستوری که از آن پشتیبانی می‌کند اضافه کنید.

نحو

shell
kubectl [command] [TYPE] [NAME] -o <output_format>

بسته به دستور،‏ این قالب‌ها پشتیبانی می‌شوند:

قالب خروجیتوضیح
-o custom-columns=<spec>جدولی با ستون‌های دلخواه شما چاپ می‌کند (ستون‌ها با کاما جدا می‌شوند).
-o custom-columns-file=<filename>جدولی با ستون‌های دلخواه،‏ بر اساس الگوی داخل فایل <filename> چاپ می‌کند.
-o jsonشیء API را با قالب JSON خروجی می‌دهد.
-o jsonpath=<template>فقط فیلدهایی را که با عبارت jsonpath مشخص کرده‌اید چاپ می‌کند.
-o jsonpath-file=<filename>فیلدهای مشخص‌شده با عبارت jsonpath داخل فایل <filename> را چاپ می‌کند.
-o kyamlشیء API را با قالب KYAML خروجی می‌دهد.
-o nameفقط نام منبع را چاپ می‌کند و هیچ چیز دیگر.
-o wideمتن ساده با اطلاعات اضافه؛‏ مثلاً برای Podها نام Node و IP را هم نشان می‌دهد.
-o yamlشیء API را با قالب YAML خروجی می‌دهد. (KYAML گونه‌ای از YAML مخصوص کوبرنتیز است که هر پردازشگر YAML هم می‌تواند آن را بخواند.)

مثال

این دستور جزئیات یک Pod را به شکل YAML نمایش می‌دهد:

shell
kubectl get pod web-pod-13je7 -o yaml
ستون‌های سفارشی

تمرین‌های فصل ۱ ۲۰ تمرین
  1. مفهومیDeployment به نام shop-api با ۳ replica و Service جلوی آن را در نظر بگیرید. Deployment controller،‏ ReplicaSet controller،‏ kube-scheduler،‏ kubelet و EndpointSlice controller هر کدام دقیقاً چه بخشی از رساندن این سیستم به desired state را انجام می‌دهند؟ اگر ثبت یک Pod در EndpointSlice به‌خاطر یک خطای موقت شبکه شکست بخورد،‏ چرا لازم نیست کل عملیات از نو شروع شود؟
    پاسخ

    هیچ controllerی مستقیماً controller دیگر را صدا نمی‌زند؛‏ هر کدام فقط وضعیت را در apiserver می‌خواند/می‌نویسد و مستقل عمل می‌کند: Deployment controller desired state (replicas: 3) را با وضعیت ReplicaSetهای موجود مقایسه می‌کند و ReplicaSet جدید یا به‌روزشده می‌سازد؛‏ ReplicaSet controller تعداد Podهای واقعی را با replicas مقایسه و کمبود را با ساختن Pod جدید (بدون nodeName) جبران می‌کند؛‏ kube-scheduler برای هر Pod بدون Node یک Node مناسب انتخاب و binding را ثبت می‌کند؛‏ kubelet آن Node container را اجرا و probeها را بررسی می‌کند؛‏ و وقتی Pod آماده (Ready) شد،‏ EndpointSlice controller آن را به فهرست endpointهای Service اضافه می‌کند.

    چون هر controller «level-triggered» (واکنش بر اساس current state،‏ نه صرفاً رخداد تغییر) است،‏ در هر دور reconciliation دوباره کل وضعیت را با desired state مقایسه می‌کند،‏ نه فقط به یک event واکنش نشان می‌دهد. اگر ثبت یک endpoint موقتاً شکست بخورد،‏ EndpointSlice controller در دور بعدی reconciliation دوباره تلاش می‌کند و به همان نتیجه می‌رسد؛‏ نیازی به شروع دوباره‌ی کل فرایند یا منطق جبرانی جداگانه نیست (فصل ۱۲ مفهوم controller و watch را کامل باز می‌کند).

  2. مفهومیمستندات containerها را «سبک» می‌داند چون «ایزوله‌سازی سبک‌تری» دارند. (الف) این ایزوله‌سازی سبک دقیقاً یعنی چه و چه هزینه‌ای دارد؟ (ب) کدام‌یک از مزیت‌های container در فهرست مستندات،‏ مستقیماً برگشت سریع (rollback) را ممکن می‌کند و چرا؟ (ج) تیمی می‌خواهد کد غیرقابل‌اعتماد مشتریانش را اجرا کند؛‏ آیا فقط container کافی است؟
    پاسخ

  5. مفهومیدر یک cluster عملیاتی به مدت ۱۰ دقیقه (الف) فقط kube-scheduler،‏ (ب) فقط kube-controller-manager و (ج) فقط kube-apiserver از کار می‌افتد. در هر حالت،‏ Podهای در حال اجرا و کاربران سرویس چه وضعی دارند و چه چیزی کار نمی‌کند؟
    پاسخ

    اصل کلیدی: اجزای control plane «وضعیت کلی cluster را مدیریت می‌کنند» و kubelet «مطمئن می‌شود Podها در حال اجرا هستند». Podهایی که از قبل روی Nodeها اجرا می‌شوند،‏ مستقل از control plane به کارشان ادامه می‌دهند.

    (الف) بدون kube-scheduler:‏ Podهای جدید (مثلاً از افزایش مقیاس،‏ rollout نسخه‌ی جدید یا جایگزینی Pod خراب) به هیچ Nodeی تخصیص نمی‌یابند و در Pending می‌مانند. Podهای موجود و ترافیک کاربران سالم‌اند و راه‌اندازی مجدد container توسط kubelet هم کار می‌کند.

    (ب) بدون kube-controller-manager:‏ controllerها کار نمی‌کنند. اگر Podی حذف شود،‏ ReplicaSet controller جایگزینش را نمی‌سازد،‏ rollout نسخه‌ها پیش نمی‌رود و Node controller،‏ Nodeهای از دست‌رفته را تشخیص نمی‌دهد. self-healing در سطح replica از کار می‌افتد،‏ اما راه‌اندازی مجدد container (کار kubelet) همچنان انجام می‌شود. نکته‌ای که کمتر به آن توجه می‌شود: EndpointSlice controller هم داخل kube-controller-manager است؛‏ پس در این مدت اگر Podی ناسالم شود و readiness را از دست بدهد،‏ از فهرست مقصدهای Service بیرون نمی‌رود و ممکن است همچنان ترافیک بگیرد.

    (ج) بدون kube-apiserver: هیچ clientی،‏ از kubectl گرفته تا controllerها و scheduler،‏ نمی‌تواند چیزی بخواند یا بنویسد،‏ چون همه از طریق API کار می‌کنند. Podهای موجود همچنان اجرا می‌شوند و kubelet containerهای خراب را محلی دوباره راه می‌اندازد،‏ اما هیچ تغییری (deployment،‏ مقیاس‌دهی) ممکن نیست. kube-proxy هم آخرین قوانین شبکه‌ای را که دارد نگه می‌دارد؛‏ پس ترافیک Serviceها برقرار می‌ماند،‏ ولی تغییرات تازه (Pod جدید یا حذف‌شده) به آن نمی‌رسد. به همین دلیل در production چند instance از apiserver پشت یک load balancer و etcd با چند عضو اجرا می‌شود (فصل ۱۲ و ۱۳).

  12. عملیکدام‌یک از این‌ها «subresource» (sub-resource) هستند و نه منبع مستقل: deployments/scale،‏ pods/log،‏ pods/exec؟ برای هر کدام یک دستور kubectl بنویسید که همان subresource (نه منبع اصلی) را صدا بزند،‏ و توضیح دهید چرا subresourceها معمولاً در خروجی kubectl api-resources دیده نمی‌شوند.
    پاسخ
    shell
    kubectl scale deployment/shop-api --replicas=5          # از /scale استفاده می‌کند
kubectl logs shop-api-7d5c6f9b8c-5l2mw                   # از /log استفاده می‌کند
kubectl exec -ti shop-api-7d5c6f9b8c-5l2mw -- /bin/sh    # از /exec استفاده می‌کند

    هر سه subresource هستند: آدرس آن‌ها در REST API به شکل /apis/apps/v1/namespaces/{ns}/deployments/{name}/scale یا /api/v1/namespaces/{ns}/pods/{name}/log است؛‏ یعنی زیرمجموعه‌ی یک شیء دیگرند،‏ نه شیء مستقلی با ساختار کامل خودشان. دستورهای سطح بالای kubectl (مثل scale،‏ logs و exec) همین subresourceها را برایتان صدا می‌زنند. kubectl api-resources فقط منابع اصلی را فهرست می‌کند؛‏ اما در RBAC می‌شود جداگانه روی subresource هم مجوز داد (مثلاً اجازه‌ی get روی pods/log بدون اجازه‌ی get روی pods).

    تشخیص: طبق بخش self-healing،‏ کوبرنتیز «تا وقتی Podها آماده‌ی سرویس‌دهی نشده‌اند،‏ آن‌ها را به clientها معرفی نمی‌کند». دقیقاً همین اتفاق افتاده: ۶ Pod که چهار دقیقه پیش ساخته شده‌اند وضعیت Running دارند،‏ یعنی container زنده است،‏ اما readiness probe آن‌ها با کد ۵۰۳ شکست می‌خورد. پس kubelet آن‌ها را Ready اعلام نمی‌کند و EndpointSlice controller آن‌ها را از فهرست مقصدها بیرون نگه می‌دارد. خروجی get endpoints هم فقط ۶ مقصد دارد (۳ تا نمایش داده شده و بقیه با «+ 3 more»)؛‏ یعنی همان ۶ Pod قدیمی و سالم. پس این یک خرابی سیستم نیست،‏ بلکه محافظت خودکار در برابر فرستادن ترافیک به نمونه‌ی ناسالم است.

    یک جزئیات مهم در خروجی: بخش وسط نام Podها (6f9c8d7b5) hash Pod template (الگویی که controller،‏ Podها را از روی آن می‌سازد) است و برای Podهای ۴ دقیقه‌ای و ۶ ساعته یکی است. پس این Podها از همان ReplicaSet و با همان imageاند و مشکل از rollout نسخه‌ی جدید نیست؛‏ احتمالاً افزایش مقیاس (مثلاً با HPA) یا جایگزینی Podهای یک Node از دست‌رفته است. سؤال بعدی این است که چرا Podهای تازه به وابستگی‌شان نمی‌رسند (مثلاً سقف تعداد اتصال database پر شده،‏ یا مشکل شبکه روی Nodeی که Podهای جدید روی آن نشسته‌اند).

    درباره‌ی Endpoints: از v1.33 به بعد API قدیمی Endpoints منسوخ شده و kubectl هشدار بالا را می‌دهد. معادل امروزی،‏ EndpointSliceها هستند: kubectl get endpointslices -n prod -l kubernetes.io/service-name=checkout-api -o yaml. دقت کنید در EndpointSlice،‏ Podهای آماده‌نشده هم فهرست می‌شوند،‏ اما با conditions.ready: false؛‏ پس برای این تشخیص باید به همین فیلد نگاه کنید،‏ نه فقط به فهرست IPها.

    ریشه‌ی احتمالی: کد ۵۰۳ از آدرس readiness معمولاً یعنی برنامه هنوز به یکی از وابستگی‌هایش (database،‏ cache) وصل نشده یا آن وابستگی از کار افتاده. باید kubectl logs checkout-api-6f9c8d7b5-2k9qp -n prod و اگر container قبلاً ری‌استارت شده،‏ --previous را بررسی کرد.

    رفع: اگر مشکل فقط کندی شروع است،‏ تنظیم readinessProbe.initialDelaySeconds و periodSeconds یا اضافه‌کردن startupProbe (فصل ۳). اگر وابستگی خارجی خراب است،‏ باید همان سرویس درست شود؛‏ کوبرنتیز نمی‌تواند «خطای خود برنامه» را رفع کند (بخش ملاحظات در صفحه‌ی Self-Healing). پیشگیری: هشدار روی نسبت Podهای Ready به تعداد دلخواه هر Deployment،‏ و آزمودن readiness probe در staging پیش از rollout در production (فصل ۱۱).

  14. سناریوی عملیاتیدر یک cluster سه‌Node،‏ تیم گزارش می‌دهد Podهای یک Job پنجاه‌تایی به‌جای پخش‌شدن روی هر سه Node،‏ بیشترشان روی یک Node جمع شده‌اند؛‏ تا جایی که memory آن Node تمام شده و kubelet شروع به evict کردن Podها کرده است. بر اساس بخش «چیدمان خودکار بهینه» توضیح دهید چطور ممکن است این اتفاق افتاده باشد و راه‌حل چیست.
    پاسخ

    تعریف رسمی «چیدمان خودکار بهینه» این است: «شما به کوبرنتیز می‌گویید هر container چقدر CPU و memory لازم دارد و کوبرنتیز containerها را طوری روی Nodeها می‌چیند که بهترین استفاده از منابع بشود». کلید ماجرا بخش اول جمله است: شما باید بگویید. اگر Podهای Job فیلد resources.requests نداشته باشند،‏ scheduler از دید خودش هیچ Nodeی را «پر» نمی‌بیند؛‏ مصرف واقعی memory در تصمیم scheduler نقشی ندارد و فقط requests حساب می‌شود. پس در مرحله‌ی فیلتر،‏ هیچ Nodeی به‌خاطر کمبود جا کنار گذاشته نمی‌شود. در مرحله‌ی امتیازدهی هم scheduler برای Pod بدون requests فقط مقدار پیش‌فرض کوچکی (۱۰۰m CPU و ۲۰۰MB memory) در نظر می‌گیرد که خیلی کمتر از مصرف واقعی است؛‏ پس اگر Nodeهای دیگر از قبل requests بیشتری داشته باشند،‏ Node «به‌ظاهر خالی» مدام امتیاز بالاتری می‌گیرد و Podها روی آن جمع می‌شوند.

    رفع: تعریف resources.requests.memory و cpu در Pod template این Job،‏ تا scheduler بتواند درست چیدمان کند و وقتی ظرفیت یک Node پر شد،‏ Pod بعدی را جای دیگری بگذارد. برای جلوگیری از تکرار: تعریف LimitRange (برای requests پیش‌فرض) و ResourceQuota در namespace (فصل ۶)،‏ و اگر پخش صریح لازم است،‏ topologySpreadConstraints یا podAntiAffinity (فصل ۹). درس این حادثه: «بهترین استفاده از منابع» به اطلاعات درستی که کاربر می‌دهد وابسته است،‏ نه به حدس scheduler.

  15. سناریوی عملیاتییک تیم SRE تصمیم گرفته به‌جای VM جداگانه برای هر ریزسرویس (۴۰ سرویس،‏ هر کدام روی ۲ VM اختصاصی) به کوبرنتیز مهاجرت کند. مدیر مالی می‌پرسد این کار دقیقاً چه صرفه‌جویی‌ای دارد و کدام مفهوم مستندات آن را توضیح می‌دهد؟ یک ریسک این مهاجرت را هم که در بخش «کوبرنتیز چه چیزی نیست» اشاره شده نام ببرید.
    پاسخ

    صرفه‌جویی: بخش پیشینه توضیح می‌دهد که در دوره‌ی مجازی «هر VM یک ماشین کامل است که همه‌ی اجزا،‏ از جمله سیستم‌عامل خودش،‏ را روی سخت‌افزار مجازی اجرا می‌کند». ۴۰ سرویس × ۲ VM یعنی ۸۰ سیستم‌عامل کامل که هر کدام memory و CPU بیکار مصرف می‌کنند و باید جداگانه به‌روز شوند. containerها «سبک» هستند و host kernel را مشترک استفاده می‌کنند؛‏ روی کوبرنتیز همین ۴۰ سرویس به شکل Podهای متعدد روی تعداد کمتری Node مشترک قرار می‌گیرند و scheduler با «چیدمان خودکار بهینه» فضای خالی هر Node را برای Podهای دیگر استفاده می‌کند. نتیجه: تراکم بیشتر و هزینه‌ی زیرساخت کمتر برای همان workload (مزیت «بهره‌وری از منابع» در فهرست مستندات).

    ریسک: کوبرنتیز «یک PaaS همه‌چیزدار نیست»؛‏ CI/CD ندارد و راه‌حل log و پایش و هشدار را تحمیل نمی‌کند. پس مهاجرت به تنهایی لایه‌های عملیاتی را فراهم نمی‌کند؛‏ تیم باید این لایه‌ها را طراحی کند،‏ وگرنه صرفه‌جویی زیرساخت با هزینه‌ی پیچیدگی عملیاتی جدید (از جمله نگهداری خود cluster؛‏ فصل ۱۲ و ۱۳) خنثی می‌شود.

  16. سناریوی عملیاتییک شرکت هم به کاربران IPv4 سرویس می‌دهد و هم به مشتریان سازمانی‌ای که فقط IPv6 دارند. تیم شبکه می‌پرسد آیا باید برای هر پروتکل یک Service جدا بسازند یا کوبرنتیز راه داخلی دارد؟ بر اساس بخش dual-stack پاسخ دهید و یک محدودیت عملی را نام ببرید.
    پاسخ

    طبق مستندات،‏ کوبرنتیز «تخصیص آدرس‌های IPv4 و IPv6 به Podها و Serviceها» را به‌صورت داخلی پشتیبانی می‌کند. پس نیازی به دو Service جدا نیست: با فعال‌کردن dual-stack در cluster و تنظیم ipFamilyPolicy و ipFamilies روی Service،‏ یک Service واحد روی هر دو نوع آدرس در دسترس است و همان Podها به هر دو پاسخ می‌دهند.

    محدودیت عملی: dual-stack باید در همه‌ی لایه‌ها فعال باشد؛‏ network plugin (CNI) باید از آن پشتیبانی کند،‏ و load balancer cloud یا Ingress Controller جلوی cluster هم باید IPv6 را بفهمد. اگر یکی از این‌ها فقط IPv4 باشد،‏ مسیر IPv6 عملاً بی‌اثر می‌ماند؛‏ حتی اگر Podها و Service آدرس IPv6 داشته باشند. جزئیات در فصل ۵.

  17. سناریوی عملیاتیتیم داده هر شب یک گزارش دسته‌ای اجرا می‌کند که معمولاً ۲۰ دقیقه طول می‌کشد،‏ اما گاهی به‌خاطر خطای موقت شبکه وسط کار با panic بسته می‌شود. یک هم‌تیمی می‌گوید: «یک Deployment با یک replica بساز؛‏ همیشه روشن است و خودش ری‌استارت هم می‌شود». بر اساس بخش‌های «اجرای کارهای دسته‌ای» و «self-healing» توضیح دهید چرا این پیشنهاد غلط است و طرح درست چیست.
    پاسخ

    طبق مستندات،‏ کوبرنتیز «علاوه بر سرویس‌ها می‌تواند کارهای دسته‌ای و CI را مدیریت کند و در صورت تمایل containerهای ناموفق را جایگزین کند». این برای workloadی است که «باید تمام شود»،‏ نه چیزی که «همیشه روشن» است. Deployment برای الگوی دوم طراحی شده: اگر container با panic بسته شود،‏ kubelet طبق restartPolicy: Always دوباره راهش می‌اندازد؛‏ اما Deployment هیچ مفهومی از «موفقیت» یا «یک بار اجرا در شب» ندارد. حتی وقتی گزارش با موفقیت تمام شود،‏ container دوباره اجرا می‌شود و گزارش تکراری می‌سازد؛‏ هیچ سقفی برای تلاش و هیچ تاریخچه‌ای از اجراهای موفق و ناموفق هم وجود ندارد.

    طرح درست: یک CronJob که هر شب یک Job می‌سازد. Job با backoffLimit تعداد تلاش‌های مجاز پس از شکست را محدود می‌کند و پس از موفقیت،‏ Pod را «تکمیل‌شده» (Completed) علامت می‌زند؛‏ به‌جای ری‌استارت بی‌پایان. جزئیات Job و CronJob در فصل ۴.

  18. سناریوی عملیاتییک اپراتور تازه‌کار می‌خواهد یک PersistentVolumeClaim را به آرایه‌ی storage شرکت وصل کند که درایور CSI ندارد و می‌پرسد: «مگر کوبرنتیز نباید این را خودش انجام دهد؟». بر اساس بخش «مدیریت خودکار storage» توضیح دهید کوبرنتیز دقیقاً چه بخشی را خودکار می‌کند و چه بخشی کار تیم زیرساخت است.
    پاسخ

    طبق مستندات،‏ کوبرنتیز اجازه می‌دهد «هر storage system دلخواهی را،‏ مثل disk محلی،‏ سرویس‌دهنده‌های cloud و موارد دیگر،‏ به‌طور خودکار وصل کنید». اما این خودکارسازی از لحظه‌ای شروع می‌شود که آن storage system از طریق یک درایور (امروزه تقریباً همیشه CSI،‏ یعنی Container Storage Interface) به cluster معرفی شده باشد. از آن به بعد،‏ PVCی که کاربر می‌سازد خودکار به یک PersistentVolume وصل می‌شود و اتصال به Node و Pod بدون دخالت دستی انجام می‌شود (فصل ۷).

    اگر آرایه‌ی storage درایور نداشته باشد،‏ کوبرنتیز راهی برای شناختنش ندارد. کار تیم زیرساخت: یا نصب درایور CSI آن آرایه (معمولاً سازنده‌اش ارائه می‌دهد)،‏ یا استفاده از یک لایه‌ی میانی که درایور دارد (مثلاً NFS روی همان آرایه). وصل‌کردن دستی بیرون از این سازوکار،‏ آن volume را از چرخه‌ی مدیریت کوبرنتیز خارج می‌کند و بازیابی خودکار و پاک‌سازی روی آن کار نخواهد کرد.

  19. سناریوی عملیاتیدر جلسه‌ی بررسی یک حادثه (postmortem) معلوم می‌شود یک مهندس با kubectl patch مستقیماً image یک Deployment در production را عوض کرده،‏ بدون اینکه فایل YAML را در Git به‌روز کند. این کار چه فرقی با روش اعلانی دارد و چه ریسکی ایجاد کرده؟ بر اساس بخش «اعلانی در برابر دستوری» پاسخ دهید و یک راهکار پیشگیری پیشنهاد کنید.
    پاسخ

    kubectl patch (مثل edit،‏ scale و create) روشی دستوری (imperative) است: مهندس مستقیماً به کوبرنتیز می‌گوید «این فیلد را عوض کن»،‏ بدون اینکه فایل مرجع (منبع حقیقت) به‌روز شود. در روش اعلانی،‏ فایل‌های YAML تحت کنترل نسخه desired state را تعریف می‌کنند و با kubectl apply اعمال می‌شوند. مستندات می‌گوید روش اعلانی به ردیابی تغییرات،‏ همکاری تیمی و یکپارچه‌سازی با GitOps کمک می‌کند،‏ در حالی که بازتولید و ممیزی روش دستوری سخت‌تر است.

    ریسک: حالا وضعیت واقعی cluster و فایل Git با هم فرق دارند (به این «drift» یا انحراف می‌گویند). دفعه‌ی بعد که کسی یا خط لوله‌ی CI همان فایل قدیمی را apply کند،‏ تغییر مهندس بی‌صدا به عقب برمی‌گردد. این نوع انحراف از رایج‌ترین ریشه‌های حادثه‌های غیرمنتظره است.

    پیشگیری: پیاده‌سازی GitOps: هر تغییری در cluster فقط از طریق pull request و اعمال خودکار (مثلاً با Argo CD یا Flux) انجام شود؛‏ اگر تغییر اضطراری دستی لازم شد،‏ بلافاصله در Git هم ثبت شود. همچنین محدودکردن دسترسی مستقیم patch/edit در namespaceهای production با RBAC (فصل ۱۴).

    پاسخ

    (الف) drain یعنی cordon به‌علاوه‌ی evict کردن همه‌ی Podهای Node. سه دسته Pod را بدون اجازه‌ی صریح شما بیرون نمی‌کند:

    • Podهای DaemonSet (مثل kube-proxy): قرار است روی همه‌ی Nodeها باشند و حتی روی Node cordon‌شده هم دوباره ساخته می‌شوند،‏ پس evict کردنشان بی‌فایده است. --ignore-daemonsets یعنی «کاری به آن‌ها نداشته باش»؛‏ با خاموش‌شدن Node متوقف می‌شوند.
    • Podهای دارای emptyDir (مثل report-worker): داده‌ی emptyDir با رفتن Pod از Node پاک می‌شود. --delete-emptydir-data یعنی «می‌دانم این داده از دست می‌رود». چون این Pod controller دارد،‏ جایگزینش روی Node دیگری ساخته می‌شود،‏ اما با emptyDir خالی.
    • Pod بدون controller (مثل debug-shell که احتمالاً با kubectl run ساخته شده): اگر با --force حذف شود،‏ هیچ controllerی جایگزینش نمی‌کند و برای همیشه از دست می‌رود؛‏ همان نکته‌ی بخش self-healing. اول با صاحبش هماهنگ کنید.
    shell
    kubectl drain worker-2 --ignore-daemonsets --delete-emptydir-data

    (ب) drain برای evict کردن Podها از Eviction API استفاده می‌کند که PodDisruptionBudget را رعایت می‌کند. اگر مثلاً برای Deploymentی با ۲ replica یک PDB با minAvailable: 2 تعریف شده باشد،‏ هیچ‌کدام از Podها اجازه‌ی evict شدن ندارند و drain مدام دوباره تلاش می‌کند. راه درست: موقتاً replicas را بیشتر کنید تا PDB اجازه دهد،‏ یا PDB را اصلاح کنید (مثلاً maxUnavailable: 1). دورزدن PDB (مثلاً با --disable-eviction) آخرین راه است،‏ چون همان حفاظتی را که PDB برایش ساخته شده از بین می‌برد.

    (ج) kubectl uncordon worker-2. خط اول خروجی نشان می‌دهد drain خودش Node را cordon کرده؛‏ تا uncordon نکنید،‏ هیچ Pod جدیدی روی آن schedule نمی‌شود.

سؤال‌های مصاحبه‌ی فصل ۱ ۱۸ سؤال · پاسخ کوتاه و دقیق،‏ همان‌طور که در جلسه‌ی مصاحبه باید گفت
  1. پایهکوبرنتیز را در دو جمله تعریف کنید.
    پاسخ

    کوبرنتیز یک پلتفرم متن‌باز برای مدیریت workloadها containerی است که deployment،‏ مقیاس‌دهی و بازیابی خودکار آن‌ها را روی مجموعه‌ای از ماشین‌ها انجام می‌دهد. شما desired state را به‌صورت اعلانی تعریف می‌کنید و controllerهای کوبرنتیز پیوسته وضعیت واقعی را با آن هم‌سو نگه می‌دارند.

    آنچه مصاحبه‌گر می‌خواهد بشنود: دو کلیدواژه‌ی «اعلانی (declarative)» و «reconciliation».

  2. پایهفرق container و virtual machine چیست؟
    پاسخ

    VM یک سیستم‌عامل کامل روی سخت‌افزار مجازی (Hypervisor) اجرا می‌کند؛‏ container kernel سیستم‌عامل host را مشترک استفاده می‌کند و فقط برنامه و وابستگی‌هایش را بسته‌بندی می‌کند. نتیجه: container سبک‌تر است (راه‌اندازی در حد ثانیه،‏ image کوچک،‏ تراکم بالا)،‏ اما ایزوله‌سازی‌اش از VM ضعیف‌تر است. ایزوله‌سازی container در Linux با namespaceها (جداسازی دید processها،‏ شبکه،‏ filesystem) و cgroupها (محدودکردن منابع) انجام می‌شود.

  3. پایهاجزای control plane را نام ببرید و کار هر کدام را در یک جمله بگویید.
    پاسخ
    • kube-apiserver: درِ ورودی cluster؛‏ API را ارائه می‌دهد،‏ درخواست‌ها را authentication،‏ authorization و validate می‌کند.
    • etcd: پایگاه داده‌ی کلید-مقدار (key-value) با سازگاری قوی (strong consistency) که کل وضعیت cluster در آن ذخیره می‌شود.
    • kube-scheduler: برای Podهای بدون Node،‏ Node مناسب انتخاب می‌کند.
    • kube-controller-manager:‏ controllerها (Deployment،‏ ReplicaSet،‏ Node و…) را اجرا می‌کند.
    • cloud-controller-manager (اختیاری): اتصال به cloud provider (load balancer،‏ disk،‏ مسیرها).
  4. پایهروی هر Node چه اجزایی اجرا می‌شود؟
    پاسخ

    kubelet (عامل Node که Podها را از API server می‌گیرد و از طریق CRI اجرا و پایش می‌کند)،‏ container runtime (مثل containerd یا CRI-O) و kube-proxy (اختیاری؛‏ قوانین شبکه برای Serviceها). نکته‌ی امتیازآور: kubelet خودش یک Pod نیست و معمولاً به‌صورت سرویس systemd اجرا می‌شود؛‏ و kube-proxy را می‌شود با CNIهایی مثل Cilium جایگزین کرد.

  5. متوسطوقتی kubectl apply -f deployment.yaml را می‌زنید،‏ قدم‌به‌قدم چه اتفاقی می‌افتد؟ (محبوب‌ترین سؤال مصاحبه)
    پاسخ
    1. kubectl فایل را به درخواست HTTP تبدیل و به kube-apiserver می‌فرستد.
    2. apiserver به ترتیب authentication،‏ authorization (authorization،‏ معمولاً RBAC)،‏ admission controllerهای تغییردهنده (mutating)،‏ validation schema و admission controllerهای اعتبارسنج (validating) را انجام می‌دهد و شیء Deployment را در etcd ذخیره می‌کند.
    3. Deployment controller (با watch) آن را می‌بیند و یک ReplicaSet می‌سازد؛‏ ReplicaSet controller،‏ Podها را می‌سازد (بدون nodeName،‏ وضعیت Pending).
    4. kube-scheduler برای هر Pod با فیلتر و امتیازدهی یک Node انتخاب و binding را ثبت می‌کند.
    5. kubelet آن Node،‏ از طریق CRI image را می‌گیرد و container را اجرا می‌کند (شبکه‌ی Pod را CNI و disk را CSI فراهم می‌کند)،‏ probeها را اجرا می‌کند و وضعیت را گزارش می‌دهد.
    6. وقتی Pod آماده شد،‏ EndpointSlice controller آن را به Service اضافه می‌کند و kube-proxy قوانین شبکه را به‌روز می‌کند.

    جمله‌ی طلایی: «controllerها،‏ scheduler و kubelet مستقیم با هم ارتباط برقرار نمی‌کنند؛‏ همه از طریق apiserver و با watch هماهنگ می‌شوند،‏ و فقط apiserver با etcd صحبت می‌کند.» اگر مصاحبه‌گر پیگیری کرد،‏ استثنا را بگویید: apiserver برای logs،‏ exec و port-forward مستقیماً به kubelet وصل می‌شود.

  6. متوسطمنظور از «desired state» و «control loop» چیست؟ یک مثال بزنید.
    پاسخ

    desired state چیزی است که شما در spec شیء می‌نویسید؛‏ current state چیزی است که در status گزارش می‌شود. control loop یعنی controller مدام این دو را مقایسه کند و برای کم‌کردن فاصله اقدام کند: مشاهده ← مقایسه ← اقدام. مثال: replicas: 3 ولی فقط ۲ Pod زنده است؛‏ ReplicaSet controller یک Pod جدید می‌سازد. تشبیه رایج: ترموستات.

  7. متوسطاگر apiserver از کار بیفتد چه می‌شود؟ اگر etcd quorumاش را از دست بدهد چطور؟ و اگر داده‌ی etcd از بین برود؟ چرا تعداد اعضای etcd را فرد می‌گیرند؟
    پاسخ
    • apiserver از کار بیفتد: Podهای در حال اجرا ادامه می‌دهند و kubelet containerهای خراب را محلی ری‌استارت می‌کند،‏ اما هیچ تغییر،‏ deployment یا جایگزینی Pod ممکن نیست.
    • etcd quorum را از دست بدهد (مثلاً ۲ عضو از ۳ عضو از کار بیفتند): etcd دیگر نوشتن را قبول نمی‌کند و apiserver عملاً قفل می‌شود؛‏ نتیجه برای کاربر شبیه حالت قبل است: Podهای موجود کار می‌کنند،‏ ولی cluster «یخ‌زده» است.
    • داده‌ی etcd از بین برود: کل وضعیت cluster (همه‌ی شیءها،‏ Secretها،‏ تنظیمات) از دست رفته است و فقط با بازگردانی از snapshot برمی‌گردد. برای همین backup منظم (etcdctl snapshot save) و آزمودن بازگردانی ضروری است.

    چرا فرد؟ quorum یعنی اکثریت: از ۳ عضو ۲ تا،‏ از ۴ عضو ۳ تا. پس cluster ۳ عضوی و ۴ عضوی هر دو فقط خرابی یک عضو را تحمل می‌کنند؛‏ عضو چهارم هزینه دارد ولی تحمل خطا را بیشتر نمی‌کند. برای همین ۳ یا ۵ عضو استاندارد است.

  8. متوسطفرق liveness probe و readiness probe چیست؟ هر کدام در صورت شکست چه می‌کند؟
    پاسخ

    liveness می‌پرسد «زنده‌ای؟»؛‏ اگر شکست بخورد،‏ kubelet container را می‌کشد و دوباره راه می‌اندازد. readiness می‌پرسد «آماده‌ی گرفتن ترافیکی؟»؛‏ اگر شکست بخورد،‏ container کشته نمی‌شود،‏ فقط Pod از endpointهای Service بیرون می‌رود. نکته‌ی امتیازآور: برای برنامه‌های کندشروع،‏ startup probe جلوی کشته‌شدن زودهنگام توسط liveness را می‌گیرد؛‏ و liveness را هرگز به وابستگی‌های خارجی (مثل database) وابسته نکنید،‏ وگرنه قطعی database همه‌ی Podها را در حلقه‌ی ری‌استارت می‌اندازد.

  9. متوسطفرق kubectl create،‏ apply و replace چیست؟
    پاسخ

    create دستوری است و اگر شیء وجود داشته باشد خطا می‌دهد. apply اعلانی است: اگر نباشد می‌سازد و اگر باشد تغییرات را ادغام می‌کند (با annotation آخرین پیکربندی یا در Server-Side Apply با مالکیت فیلدها). replace کل شیء را جایگزین می‌کند و فیلدهای غایب در فایل پاک می‌شوند. برای production و GitOps: apply.

    نکته‌ی امتیازآور: apply (در حالت client-side) سه چیز را مقایسه می‌کند: فایل جدید،‏ آخرین پیکربندی اعمال‌شده و current state شیء (three-way merge). برای همین اگر فیلدی را از فایل حذف کنید،‏ apply آن را از شیء هم برمی‌دارد،‏ اما فیلدهایی که دیگران تنظیم کرده‌اند (مثلاً controllerها) دست‌نخورده می‌مانند.

  10. متوسطkubeconfig چیست و context از چه اجزایی تشکیل شده؟
    پاسخ

    kubeconfig فایلی (پیش‌فرض ~/.kube/config) است که سه فهرست دارد: clusters (آدرس API server و certificate CA)،‏ users (اطلاعات ورود: client certificate،‏ token یا exec plugin) و contexts. هر context ترکیب «یک cluster + یک کاربر + یک namespace پیش‌فرض» است و current-context مشخص می‌کند فعلاً کدام فعال است. با KUBECONFIG می‌توان چند فایل را با هم ادغام کرد.

  11. متوسطکوبرنتیز چه کارهایی را انجام نمی‌دهد؟
    پاسخ

    کد را build نمی‌کند و CI/CD ندارد؛‏ database،‏ message queue و cache داخلی ندارد؛‏ راه‌حل log و پایش و هشدار تحمیل نمی‌کند؛‏ زبان پیکربندی خاصی اجبار نمی‌کند؛‏ و ماشین‌ها (Nodeها) را پیکربندی یا تعمیر نمی‌کند. کوبرنتیز «آجرهای سازنده‌ی» یک پلتفرم است،‏ نه یک PaaS کامل. این سؤال برای سنجیدن این است که آیا درک واقع‌بینانه‌ای از هزینه‌ی عملیاتی کوبرنتیز دارید.

  12. متوسطStatic Pod چیست و چه فرقی با Pod معمولی دارد؟
    پاسخ

    Static Pod را خود kubelet مستقیماً از فایل‌های manifest روی Node اجرا می‌کند (در kubeadm پوشه‌ی /etc/kubernetes/manifests)؛‏ نه apiserver در ساختنش نقش دارد و نه scheduler.‏ kubelet برای هر static Pod یک mirror Pod در apiserver می‌سازد تا با kubectl get pods دیده شود،‏ اما این فقط یک نمای فقط‌خواندنی است: اگر آن را با kubectl حذف کنید،‏ kubelet دوباره می‌سازدش. برای تغییر یا حذف واقعی باید فایل روی Node را عوض کنید. کاربرد اصلی: kubeadm اجزای control plane (apiserver،‏ etcd،‏ scheduler،‏ controller-manager) را این‌طور اجرا می‌کند،‏ چون apiserver نمی‌تواند خودش را schedule کند.

  13. متوسطفرق cordon و drain چیست؟
    پاسخ

    cordon فقط Node را unschedulable (علامتی که مانع قرار گرفتن Pod جدید روی Node می‌شود) می‌کند (spec.unschedulable: true)؛‏ Podهای فعلی سر جایشان می‌مانند و فقط Pod جدیدی روی آن نمی‌نشیند. drain یعنی cordon به‌علاوه‌ی evict کردن Podهای موجود از طریق Eviction API،‏ که PodDisruptionBudgetها را رعایت می‌کند. Podهای DaemonSet،‏ Podهای دارای emptyDir و Podهای بدون controller بدون flag صریح evict نمی‌شوند. بعد از پایان نگهداری،‏ uncordon لازم است (تمرین ۲۰).

  14. پیشرفتهیک Node ناگهان خاموش می‌شود. چه اتفاقی برای Podهای آن می‌افتد و چقدر طول می‌کشد تا جایگزین شوند؟
    پاسخ
    1. kubelet دیگر گزارش سلامت (heartbeat،‏ از طریق شیء Lease در namespace kube-node-lease) نمی‌فرستد.
    2. Node controller (داخل kube-controller-manager) پس از گذشت مهلت node-monitor-grace-period (چند ده ثانیه) وضعیت Ready را Unknown می‌کند و taint node.kubernetes.io/unreachable:NoExecute را روی Node می‌گذارد.
    3. هر Pod به‌طور پیش‌فرض این taint را ۳۰۰ ثانیه تحمل می‌کند (tolerationSeconds: 300). بعد از آن Podها evict می‌شوند و controllerهایشان (مثلاً ReplicaSet) Pod جایگزین را روی Nodeهای سالم می‌سازند. یعنی در عمل حدود ۵ دقیقه.

    نکته‌ی امتیازآور: Podهای StatefulSet خودکار جایگزین نمی‌شوند تا مطمئن شویم Pod قبلی واقعاً متوقف شده،‏ چون StatefulSet تضمین می‌کند از هر هویت (مثلاً db-0) حداکثر یک نمونه اجرا شود. در این حالت باید Node را حذف کنید،‏ روی آن taint node.kubernetes.io/out-of-service بگذارید،‏ یا Pod را آگاهانه با force حذف کنید. اگر زمان ۵ دقیقه برای سرویسی زیاد است،‏ می‌توان tolerationSeconds را در spec آن Pod کمتر کرد.

  15. پیشرفتهمکانیزم watch در Kubernetes API چیست و چرا controllerها به‌جای polling از آن استفاده می‌کنند؟
    پاسخ

    watch یک درخواست HTTP طولانی‌مدت به apiserver است (با پارامتر ?watch=true). apiserver به‌جای یک پاسخ یک‌باره،‏ هر تغییر را به شکل event (ADDED،‏ MODIFIED،‏ DELETED) همان لحظه برای client می‌فرستد. هر شیء یک resourceVersion دارد و client می‌تواند بگوید «eventها را از این نسخه به بعد بفرست».

    controllerها از الگوی list-then-watch استفاده می‌کنند (در client-go با informer): اول یک LIST کامل می‌گیرند و در یک cache محلی نگه می‌دارند،‏ بعد از resourceVersion همان LIST یک WATCH باز می‌کنند و فقط تغییرات را دریافت می‌کنند. هر تغییر،‏ کلید آن شیء را در یک صف کاری (work queue) می‌گذارد و حلقه‌ی reconcile برای آن اجرا می‌شود. controller برای خواندن هم از همین cache محلی استفاده می‌کند،‏ نه از apiserver.

    چرا نه polling؟ polling یعنی هر چند ثانیه کل فهرست را دوباره بخوانید: واکنش تا دور بعدی عقب می‌افتد و با زیادشدن controllerها و شیءها بار سنگینی روی apiserver و etcd می‌افتد. watch واکنش تقریباً بی‌درنگ را با بار کم می‌دهد.

    نکته‌ی امتیازآور: اتصال watch ممکن است قطع شود،‏ یا resourceVersion آن‌قدر قدیمی شود که apiserver خطای 410 Gone بدهد؛‏ در این حالت informer دوباره LIST و بعد WATCH می‌کند (relist). جدا از این،‏ informer یک resync دوره‌ای هم دارد که همه‌ی شیءهای cache محلی را دوباره در صف می‌گذارد،‏ بدون اینکه سراغ apiserver برود. این‌ها کنار هم باعث می‌شوند controller «level-triggered» بماند: تصمیمش را بر اساس current state می‌گیرد،‏ نه بر اساس اینکه کدام event را دیده؛‏ پس گم‌شدن یک event نتیجه را خراب نمی‌کند.

  16. پیشرفتهچرا requests در scheduling مهم‌اند؟ اگر هیچ Podی requests نداشته باشد چه اتفاقی می‌افتد؟
    پاسخ

    scheduler فقط بر اساس requests تصمیم می‌گیرد،‏ نه مصرف واقعی. بدون requests،‏ scheduler هیچ Nodeی را پر نمی‌بیند و ممکن است Podهای زیادی را روی یک Node بچیند؛‏ نتیجه: رقابت بر سر CPU،‏ کمبود memory،‏ OOMKill و eviction (eviction Pod از Node توسط خود سیستم) Podها. همچنین Pod بدون requests و limits در کلاس QoS «BestEffort» قرار می‌گیرد و اولین قربانی در کمبود منابع است. راه‌حل: requests برای همه،‏ و LimitRange برای مقادیر پیش‌فرض در namespace. نکته: اگر فقط limits بنویسید و requests را خالی بگذارید،‏ کوبرنتیز requests را برابر همان limits در نظر می‌گیرد.

  17. پیشرفتهversion skew policy (version skew) برای kubectl چیست و در ارتقای cluster چه ترتیبی را رعایت می‌کنید؟
    پاسخ

    kubectl تا یک نسخه‌ی minor بالاتر یا پایین‌تر از apiserver پشتیبانی می‌شود. در ارتقای cluster،‏ اول control plane (apiserverها) ارتقا می‌یابد و بعد Nodeها (kubelet)؛‏ چون kubelet هرگز نباید جدیدتر از apiserver باشد (ولی می‌تواند تا سه نسخه‌ی minor قدیمی‌تر باشد).‏ kube-controller-manager و kube-scheduler هم نباید از apiserver جدیدتر باشند (تا یک نسخه قدیمی‌تر مجازند)؛‏ پس در cluster HA اول همه‌ی apiserverها ارتقا می‌یابند. ارتقا هم باید نسخه‌به‌نسخه‌ی minor انجام شود (مثلاً 1.35 ← 1.36 ← 1.37)،‏ نه پرشی. جزئیات دقیق در فصل ۱۳.

  18. پیشرفتهدر یک cluster مدیریت‌شده (EKS/GKE/AKS) چه چیزهایی مسئولیت شماست و چه چیزهایی مسئولیت سرویس‌دهنده؟
    پاسخ

    سرویس‌دهنده control plane را اجرا،‏ ارتقا و backup می‌کند (apiserver،‏ etcd،‏ scheduler،‏ controller-manager) و دسترس‌پذیری بالای آن را تضمین می‌کند. مسئولیت شما: worker Nodeها (یا حداقل تنظیم گروه‌های Node و ارتقایشان)،‏ addonها (CNI،‏ CSI،‏ Ingress)،‏ امنیت (RBAC،‏ سیاست‌های شبکه،‏ مدیریت Secret)،‏ پایش و log،‏ backup از workloadها و داده‌ها،‏ و البته خود برنامه‌ها. به این «مدل مسئولیت مشترک» (shared responsibility) می‌گویند.

خلاصه‌ی فصل ۱ در یک نگاه برای مرور سریع؛‏ جزئیات در متن فصل

ایده‌ی محوری: کوبرنتیز یک سیستم اعلانی است. شما desired state را در API ثبت می‌کنید و control loopهای مستقل،‏ بدون هماهنگ‌کننده‌ی مرکزی،‏ current state را مدام به آن نزدیک می‌کنند؛‏ self-healing،‏ rollout و scaling همه از همین ایده می‌آیند؛‏ و همه‌ی این‌ها را روی یک cluster k3s با دست خودتان می‌بینید.

۱. کوبرنتیز چیست؟
  • تعریف: پلتفرم open source،‏ portable و extensible برای مدیریت workloadها و سرویس‌های containerی؛‏ دو ستون اصلی: declarative configuration و automation.
  • مدل ذهنی: شما desired state را اعلام می‌کنید،‏ controllerها مدام current state را با آن مقایسه و اختلاف را رفع می‌کنند (reconciliation). تشبیه: ترموستات.
  • ریشه: «کوبرنتیز» یونانی و به معنای سکان‌دار؛‏ در K8s عدد ۸ یعنی هشت حرف میان K و s؛‏ متن‌باز شدن توسط گوگل در ۲۰۱۴،‏ بر پایه‌ی بیش از ۱۵ سال تجربه با Borg.
  • نقش: خودش container اجرا نمی‌کند (کار container runtime مثل containerd و CRI-O است)؛‏ فقط تصمیم می‌گیرد چه چیزی کجا اجرا شود و چه چیزی جایگزینش شود.

۳. قابلیت‌ها و سازوکار پشت هر کدام
  • service discovery و load balancing: هر Service یک نام DNS و IP مجازی ثابت می‌دهد،‏ چون IP هر Pod موقتی است.
  • storage orchestration: برنامه فقط PVC می‌نویسد؛‏ StorageClass و درایور CSI تعیین می‌کنند فضا از کجا بیاید.
  • rollout و rollback خودکار: سرعت با maxSurge و maxUnavailable؛‏ اگر readiness نسخه‌ی جدید موفق نشود،‏ rollout می‌ایستد و نسخه‌ی قدیم سرویس می‌دهد.
  • bin packing: انتخاب Node توسط scheduler بر اساس resources.requests. دام: بدون requests،‏ Podها روی یک Node انباشته می‌شوند و نتیجه کندی و OOMKilled است.
  • Secret و config: جداسازی پیکربندی در ConfigMap و Secret،‏ بدون build دوباره‌ی image؛‏ یک image برای staging و production. دام: هر Secret به‌طور پیش‌فرض فقط base64 است؛‏ encryption at rest و RBAC لازم است.
  • batch: اجرای Job و CronJob تا رسیدن به اجرای موفق دوباره تلاش می‌کنند (حداکثر تا backoffLimit).
  • horizontal scaling: با دستور،‏ UI یا خودکار بر اساس CPU (نیازمند metrics-server). مقیاس افقی یعنی تعداد Pod،‏ مقیاس عمودی یعنی منابع هر Pod.
  • dual-stack: پشتیبانی هم‌زمان از IPv4 و IPv6 (فیلدهای status.podIPs و ipFamilyPolicy).
  • extensibility بدون fork: با CRD،‏ Operator،‏ admission webhook و CNI،‏ CSI و CRI.
  • canary: دو Deployment با label مشترک app و track متفاوت،‏ زیر یک Service؛‏ ۹ replica پایدار و ۱ canary یعنی حدود ۱۰٪ ترافیک.

۵. کوبرنتیز چه چیزی نیست؟
  • یک PaaS همه‌چیز در یک بسته نیست؛‏ اجزای پیش‌فرض اختیاری و pluggable هستند.
  • محدودیتی در نوع برنامه ندارد (stateless،‏ stateful،‏ پردازش داده).
  • کار build و CI/CD را انجام نمی‌دهد؛‏ middleware،‏ database و cache داخلی ندارد؛‏ راه‌حل log و monitoring را تحمیل نمی‌کند؛‏ زبان پیکربندی (مثل Jsonnet) را اجباری نمی‌کند؛‏ ماشین‌ها را self-heal نمی‌کند.
  • سیستم orchestration نیست: به‌جای روند ثابت «اول A،‏ بعد B»،‏ control loopهای مستقل و ترکیب‌پذیر بدون کنترل مرکزی دارد که از هر وضعیت میانی،‏ حتی خراب،‏ به desired state برمی‌گردند.
  • آنچه تیم باید خودش بیاورد: CI/CD (مثلاً Argo CD)،‏ database مدیریت‌شده یا Operator،‏ ابزار observability (مثل Prometheus و Loki)،‏ Helm یا Kustomize،‏ و ابزار مدیریت ماشین.
۶. نقشه‌ی ذهنی
  • ایده: شما desired state را اعلام می‌کنید و کوبرنتیز با reconciliation مدام واقعیت را به آن نزدیک می‌کند.

  • k3s: همه‌ی اجزای کوبرنتیز در یک فایل اجرایی؛‏ API استاندارد؛‏ پایگاه داده‌ی تک‌Node از نوع SQLite.
۷. نصب و اتصال
  • نیاز: سیستم‌عامل Linux با دست‌کم ۲ CPU و ۲ گیگابایت RAM (برای تمرین ۴ گیگابایت).
  • نصب: اسکریپت get.k3s.io با نسخه‌ی ثابت در INSTALL_K3S_VERSION؛‏ سرویس systemd به نام k3s.
  • kubeconfig: فایل /etc/rancher/k3s/k3s.yaml (فقط root)؛‏ کپی در ~/.kube/config با مجوز ۶۰۰ و تنظیم KUBECONFIG. دام: این فایل کلید مدیر cluster است.
  • شبکه‌ی محدود: نصب air-gap با فایل k3s و بسته‌ی imageها و INSTALL_K3S_SKIP_DOWNLOAD=true؛‏ mirror در registries.yaml و ری‌استارت k3s.
  • اجزای همراه: شامل coredns و traefik و ServiceLB و local-path-provisioner و metrics-server.
۸. cluster
  • cluster: شامل control plane (مغز: تصمیم و نگهداری وضعیت) و Nodeها (بازوها: VM یا ماشین فیزیکی با kubelet و container runtime).
  • اصل مهم: برنامه نباید به host خاص گره بخورد؛‏ وابستگی به فایل محلی یا IP ثابت،‏ self-healing را خراب می‌کند.
  • محیط یادگیری: یک cluster تک‌Node با k3s (بخش «نصب k3s») که همان Node هم control plane است و هم worker؛‏ API server روی https://127.0.0.1:6443. مسیر جایگزین minikube در پیوست (فصل ۱۷).
  • production: سه Node برای control plane در سه zone تا etcd به quorum برسد،‏ به‌اضافه‌ی چند worker.

۱۰. سفر یک kubectl apply
  1. درخواست HTTP به kube-apiserver می‌رسد و به ترتیب authentication،‏ authorization،‏ admission و validation را می‌گذراند و در etcd ذخیره می‌شود.
  2. سپس Deployment controller یک ReplicaSet می‌سازد و ReplicaSet controller سه Pod بدون nodeName (Pending).
  3. بعد scheduler برای هر Pod یک Node انتخاب می‌کند و binding را در apiserver ثبت می‌کند.
  4. آنگاه kubelet آن Node از طریق CRI،‏ image را می‌گیرد،‏ container را اجرا می‌کند،‏ probeها را اجرا و وضعیت را گزارش می‌کند.
  5. در پایان EndpointSlice controller،‏ Podهای Ready را به Service اضافه می‌کند و kube-proxy قوانین شبکه را به‌روز می‌کند.

دام: اجزا مستقیماً به هم دستور نمی‌دهند؛‏ همه با watch از apiserver می‌خوانند و نتیجه را همان‌جا می‌نویسند. استثنا: apiserver برای logs،‏ exec و port-forward مستقیماً به kubelet وصل می‌شود.

۱۱. اولین Pod و چهار دستور اصلی
  • دستورها: فرمان get برای فهرست؛‏ describe برای جزئیات و Events؛‏ logs برای خروجی برنامه؛‏ exec برای اجرای دستور داخل container.
  • دسترسی موقت: با kubectl port-forward.
  • دام: Pod حذف‌شده برنمی‌گردد؛‏ در کار واقعی Pod را مستقیم نمی‌سازیم.
۱۲. آزمایش شاپیفای: چهار شیء و فیلدهای YAML
  • چهار شیء: اجرای container با Pod؛‏ ثابت نگه‌داشتن تعداد با ReplicaSet؛‏ نسخه و rollout با Deployment؛‏ نشانی ثابت و پخش ترافیک با Service. چسب همه: label و selector.
  • فیلدهای Deployment: فیلد replicas برای تعداد؛‏ selector.matchLabels برای انتخاب Podها؛‏ template برای Pod template. دام: label قالب باید با selector بخواند و selector پس از ساخت تغییرناپذیر است.
  • قاعده‌ی نسخه: هر تغییر در template یعنی ReplicaSet تازه و rollout؛‏ تغییر replicas یا strategy یعنی نه. ReplicaSetهای قبلی با صفر Pod می‌مانند (پیش‌فرض تا ۱۰ نسخه).
  • Service: نام آن همان نام DNS است؛‏ نوع پیش‌فرض ClusterIP (فقط داخل cluster)؛‏ فیلد port برای Service و targetPort برای container.
  • probeها: شکست readiness یعنی خروج از Service بدون restart؛‏ شکست liveness (پیش‌فرض سه بار پیاپی) یعنی restart container. دام: liveness وابسته به پایگاه داده،‏ restart زنجیره‌ای می‌سازد.
  • rolling update: پیش‌فرض maxSurge و maxUnavailable برابر ۲۵٪ است (surge رو به بالا و unavailable رو به پایین گرد می‌شود)؛‏ برای ۳ replica یعنی یک Pod اضافه و صفر Pod ناموجود.
  • requests: رزرو برای scheduler؛‏ سقف نیست (سقف با limits،‏ فصل ۶). فیلد containerPort هم فقط اطلاع‌رسانی است.
  • اعلانی: دام: بعد از kubectl scale یا rollout undo فایل را هم درست کنید؛‏ apply بعدی فایل را معیار می‌گیرد.

۱۴. kubectl: اتصال و روش کار
  • ماهیت: یک client HTTP برای Kubernetes API؛‏ هر دستور به یک یا چند درخواست HTTP تبدیل می‌شود (با -v دیده می‌شود).
  • kubeconfig: پیش‌فرض ~/.kube/config؛‏ فایل دیگر با متغیر KUBECONFIG یا flag --kubeconfig. هر context ترکیب cluster،‏ user و namespace است؛‏ جابه‌جایی با kubectl config use-context. دام: اجرای دستور روی context اشتباه؛‏ پیش از دستور خطرناک current-context را ببینید یا --context بدهید.
  • in-cluster authentication: اگر KUBERNETES_SERVICE_HOST،‏ KUBERNETES_SERVICE_PORT و فایل token مربوط به ServiceAccount هر سه موجود باشند،‏ kubectl از هویت ServiceAccount و namespace همان Pod استفاده می‌کند. POD_NAMESPACE بر آن اولویت دارد و --namespace بر هر دو. خطای Forbidden یعنی authentication موفق بوده ولی authorization نه.
  • version skew: پشتیبانی kubectl فقط تا یک نسخه‌ی minor بالاتر یا پایین‌تر از control plane پشتیبانی می‌شود (v1.32 با 1.31 تا 1.33).
  • declarative در برابر imperative: برای production فایل در Git و kubectl apply (قابل ردیابی،‏ GitOps)؛‏ create،‏ run و scale برای آزمایش. دام: هر scale دستی با apply بعدی برمی‌گردد؛‏ برای replica متغیر HPA بگذارید و فیلد replicas را از فایل حذف کنید. ترفند: تولید YAML با --dry-run=client -o yaml.
  • plugin: هر فایل اجرایی kubectl-NAME در PATH؛‏ دسترسی ویژه ندارد و با مجوزهای خود شما کار می‌کند (از منبع ناشناس نصب نکنید)؛‏ فایل هم‌نام بعدی shadowed می‌شود؛‏ مدیر plugin:‏ Krew.
۱۵. kubectl: نحو،‏ عملیات و خروجی
  • نحو: شکل کلی kubectl [command] [TYPE] [NAME] [flags] است. نام TYPE به بزرگی و کوچکی حروف حساس نیست (مفرد،‏ جمع یا short name)،‏ ولی NAME حساس است. چند منبع: TYPE a b یا TYPE/a TYPE2/b؛‏ ترکیب این دو خطاست. فایل با -f (YAML بهتر از JSON).‏ flag خط فرمان بر environment variable و مقدار پیش‌فرض اولویت دارد.
  • create،‏ apply و replace: دستور create اگر شیء باشد خطای AlreadyExists می‌دهد؛‏ apply می‌سازد یا ادغام می‌کند؛‏ replace کل شیء را عوض می‌کند و فیلدهای جاافتاده پاک می‌شوند.
  • نگهداری Node: ابتدا cordon (بدون Pod جدید)،‏ سپس drain (cordon و evict با رعایت PDB)،‏ در پایان uncordon.
  • ابزارهای روزمره: زیردستورهای rollout status|history|undo|pause|resume|restart (restart مثلاً پس از تغییر Secretی که در env خوانده می‌شود)؛‏ auth can-i؛‏ wait --for=condition=available؛‏ diff پیش از apply.
  • get در برابر describe: دستور get فهرست می‌دهد و -o و -w دارد؛‏ describe با چند درخواست،‏ نمای کامل و eventها را می‌آورد (علت Pending را آنجا ببینید).

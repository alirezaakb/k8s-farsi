Autoscaling:‏ HPA،‏ VPA و Node Autoscaling

مرجع: workloads/autoscaling · workloads/autoscaling/horizontal-pod-autoscale · workloads/autoscaling/vertical-pod-autoscale · tasks/run-application/horizontal-pod-autoscale-walkthrough · concepts/cluster-administration/node-autoscaling · tasks/configure-pod-container/resize-container-resources · tasks/run-application/scale-stateful-set · tasks/administer-cluster/dns-horizontal-autoscaling · tasks/debug/debug-cluster/resource-metrics-pipeline

در کوبرنتیز،‏ می‌توانید یک workload را بسته به تقاضای فعلی resourceها scale کنید. این کار به cluster شما اجازه می‌دهد که با انعطاف‌پذیری و کارایی بیشتری به تغییرات تقاضای resource واکنش نشان دهد.

وقتی یک workload را scale می‌کنید،‏ می‌توانید تعداد replicaهایی که توسط آن workload مدیریت می‌شوند را افزایش یا کاهش دهید،‏ یا resourceهای در دسترس replicaها را به‌صورت in-place تنظیم کنید.

روش اول horizontal scaling نامیده می‌شود،‏ در حالی که روش دوم vertical scaling نامیده می‌شود.

روش‌های manual و automatic برای scale کردن workloadها وجود دارد که بسته به use case شما متفاوت است.

توضیح تکمیلی: نقشه‌ی ذهنی این فصل

این فصل چهار محور دارد که در ادامه به‌ترتیب پوشش داده می‌شوند:

  • HorizontalPodAutoscaler (HPA): بخش core Kubernetes API که تعداد replicaهای یک workload (Deployment،‏ StatefulSet و ...) را بر اساس metricهایی مثل CPU یا memory utilization تنظیم می‌کند.
  • VerticalPodAutoscaler (VPA): یک add-on (نه core API) که requests/limits containerهای یک Pod را بر اساس مصرف واقعی resource تنظیم می‌کند.
  • Node autoscaling:‏ scale کردن خود infrastructure،‏ یعنی اضافه یا حذف کردن Nodeها با ابزارهایی مثل Cluster Autoscaler یا Karpenter.
  • In-place Pod resize: مکانیزم زیرساختی که VPA (در برخی modeها) و کاربر (به‌صورت دستی) برای تغییر CPU/memory یک container (process ایزوله‌شده‌ای که برنامه را همراه وابستگی‌هایش اجرا می‌کند) در حال اجرا،‏ بدون recreate کردن Pod،‏ از آن استفاده می‌کنند.

نکته‌ی مهم: HPA و VPA دو مسیر مستقل هستند و اگر هر دو روی یک resource یکسان (مثلا CPU) پیکربندی شوند،‏ می‌توانند با هم تداخل ایجاد کنند (به تمرین‌های پایان فصل مراجعه کنید).

ماجرای این فصل: Black Friday

Black Friday و Cyber Monday نزدیک است. در حراج پاییزه‌ی پارسال (فصل ۱) ترافیک ساعت اول شش برابر روزهای عادی شد؛‏ امسال با کمپین‌های بیشتر،‏ تا هشت برابر پیش‌بینی می‌شود،‏ ولی کسی نمی‌داند اوج دقیقاً چه ساعتی است و هر کمپین تبلیغاتی ممکن است جهش تازه‌ای بسازد. نگه‌داشتن هشت برابر Pod و Node در تمام سال هزینه را چند برابر می‌کند و کم گذاشتنش در روز حراج،‏ یعنی از دست رفتن فروش در پرترافیک‌ترین ساعت‌های سال.

scale کردن دستی workloadها (Scaling workloads manually)

کوبرنتیز از manual scaling workloadها پشتیبانی می‌کند. Horizontal scaling را می‌توان با CLI کوبرنتیز یعنی kubectl انجام داد. برای vertical scaling،‏ باید resource definition workload خود را patch کنید.

  • Horizontal scaling:‏ Running multiple instances of your app (اجرای چند instance از برنامه)
  • Vertical scaling:‏ Resizing CPU and memory resources assigned to containers (تغییر اندازه‌ی CPU و memory اختصاص‌یافته به containerها؛‏ در بخش In-place Pod resize همین فصل به‌طور کامل پوشش داده می‌شود)
آزمایش عملی: horizontal scaling دستی با kubectl scale
lab/scale-demo.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 1
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: web
        image: nginx:1.27
        resources:
          requests: {cpu: 100m, memory: 64Mi}
          limits: {cpu: 200m, memory: 128Mi}
shell
kubectl apply -f scale-demo.yaml
kubectl get deployment web
kubectl scale deployment web --replicas=4
kubectl get deployment web

kubectl scale مستقیما field .spec.replicas Deployment را patch می‌کند. برای vertical scaling دستی به همین شکل باید .spec.template.spec.containers[*].resources را patch یا apply کنید (که یک rollout جدید ایجاد می‌کند)،‏ مگر آنکه از in-place Pod resize استفاده کنید که نیازی به recreate کردن Pod ندارد.

scale کردن خودکار workloadها (Scaling workloads automatically)

کوبرنتیز همچنین از automatic scaling workloadها پشتیبانی می‌کند،‏ که موضوع اصلی این فصل است.

مفهوم Autoscaling در کوبرنتیز به توانایی به‌روزرسانی خودکار یک object که مجموعه‌ای از Podها را مدیریت می‌کند (مثلا یک Deployment) اشاره دارد.

scale کردن افقی workloadها (Scaling workloads horizontally)

در کوبرنتیز،‏ می‌توانید یک workload را به‌صورت خودکار و افقی با استفاده از یک HorizontalPodAutoscaler (HPA) scale کنید.

این به‌صورت یک Kubernetes API resource و یک controller پیاده‌سازی شده و به‌طور دوره‌ای تعداد replicaهای یک workload را با resource utilization مشاهده‌شده‌ای مثل CPU یا memory usage تطبیق می‌دهد.

یک walkthrough tutorial برای پیکربندی یک HorizontalPodAutoscaler برای یک Deployment در همین فصل آمده است.

scale کردن عمودی workloadها (Scaling workloads vertically)

FEATURE STATE: Kubernetes v1.25 [stable]

می‌توانید یک workload را به‌صورت خودکار و عمودی با استفاده از یک VerticalPodAutoscaler (VPA) scale کنید. برخلاف HPA،‏ VPA به‌طور پیش‌فرض همراه کوبرنتیز نمی‌آید،‏ بلکه یک add-on است که شما یا مدیر cluster باید پیش از استفاده آن را deploy کنید.

پس از نصب،‏ به شما اجازه می‌دهد برای workloadهایتان CustomResourceDefinition (CRD) بسازید که مشخص می‌کند چگونه و چه زمانی resourceهای replicaهای مدیریت‌شده scale شوند.

برای اینکه VPA کار کند،‏ باید Metrics Server روی cluster شما نصب شده باشد.

In-place pod vertical scaling

FEATURE STATE: Kubernetes v1.35 [stable] (feature gate InPlacePodVerticalScaling،‏ همیشه فعال)

در Kubernetes 1.37،‏ VPA هنوز از resize کردن Podها به‌صورت in-place پشتیبانی نمی‌کند،‏ اما این integration در حال کار است. یادداشت نویسنده: این جمله از صفحه‌ی کلی autoscaling در مستندات است؛‏ صفحه‌ی خود VPA در همین فصل حالت‌های InPlaceOrRecreate و InPlace را معرفی می‌کند که از in-place resize استفاده می‌کنند (InPlace در VPA هنوز alpha است). یعنی پشتیبانی در خود پروژه‌ی VPA آمده،‏ ولی هنوز کامل و پایدار نیست. برای resize کردن دستی Podها به‌صورت in-place،‏ به Resize Container Resources In-Place همین فصل مراجعه کنید.

autoscaling بر اساس اندازه‌ی cluster (Autoscaling based on cluster size)

برای workloadهایی که باید بر اساس اندازه‌ی Cluster scale شوند (مثلا cluster-dns یا سایر system componentها)،‏ می‌توانید از Cluster Proportional Autoscaler استفاده کنید. درست مانند VPA،‏ این هم جزو core کوبرنتیز نیست،‏ بلکه به‌عنوان یک پروژه‌ی مستقل روی GitHub میزبانی می‌شود.

Cluster Proportional Autoscaler تعداد Nodeهای schedulable و coreها را رصد می‌کند و تعداد replicaهای workload هدف را متناسب با آن‌ها scale می‌کند.

اگر بخواهید تعداد replicaها ثابت بماند،‏ می‌توانید workloadهای خود را به‌صورت عمودی و متناسب با اندازه‌ی cluster با Cluster Proportional Vertical Autoscaler scale کنید. این پروژه در حال حاضر در مرحله‌ی beta است و روی GitHub قرار دارد.

در حالی که Cluster Proportional Autoscaler تعداد replicaهای یک workload را scale می‌کند،‏ Cluster Proportional Vertical Autoscaler resource requestهای یک workload (مثلا یک Deployment یا DaemonSet) را بر اساس تعداد Nodeها و/یا coreهای cluster تنظیم می‌کند.

در بخش Autoscale the DNS Service in a Cluster همین فصل،‏ یک استفاده‌ی واقعی از Cluster Proportional Autoscaler برای scale کردن CoreDNS نشان داده شده است.

autoscaling بر اساس event (Event driven Autoscaling)

همچنین می‌توان workloadها را بر اساس eventها scale کرد،‏ برای مثال با Kubernetes Event Driven Autoscaler (KEDA).

KEDA یک پروژه‌ی graduated در CNCF است که به شما امکان می‌دهد workloadهای خود را بر اساس تعداد eventهایی که باید پردازش شوند scale کنید،‏ مثلا تعداد پیام‌های یک queue. طیف گسترده‌ای از adapterها برای منابع event مختلف وجود دارد که می‌توانید از میان آن‌ها انتخاب کنید.

autoscaling بر اساس schedule (Autoscaling based on schedules)

راهبرد دیگر برای scale کردن workloadها،‏ schedule کردن عملیات scaling است،‏ برای مثال به‌منظور کاهش مصرف resource در ساعت‌های off-peak.

مشابه event driven autoscaling،‏ این رفتار را می‌توان با KEDA در ترکیب با scaler Cron آن به‌دست آورد. scaler Cron به شما امکان می‌دهد schedule (و timezone) را برای scale کردن workloadهای خود به داخل یا بیرون (in یا out) تعریف کنید.

scale کردن infrastructure مربوط به cluster (Scaling cluster infrastructure)

اگر scale کردن workloadها برای برآورده کردن نیازهایتان کافی نباشد،‏ می‌توانید infrastructure مربوط به خود cluster را نیز scale کنید.

Scale کردن infrastructure مربوط به cluster معمولا به معنای اضافه یا حذف کردن Node است. برای اطلاعات بیشتر بخش Node autoscaling همین فصل را بخوانید.

Horizontal Pod Autoscaling

در کوبرنتیز،‏ یک HorizontalPodAutoscaler یک workload resource (مثل یک Deployment یا StatefulSet) را به‌صورت خودکار به‌روزرسانی می‌کند،‏ با این هدف که capacity به‌طور خودکار با تقاضا (demand) هماهنگ شود.

Horizontal scaling یعنی پاسخ به افزایش بار،‏ deploy کردن Podهای بیشتر است. این با vertical scaling فرق دارد که در کوبرنتیز به معنای اختصاص resourceهای بیشتر (مثلا memory یا CPU) به Podهایی است که از قبل برای آن workload در حال اجرا هستند.

اگر بار کاهش یابد و تعداد Podها بالاتر از حداقل پیکربندی‌شده باشد،‏ HorizontalPodAutoscaler به workload resource (Deployment،‏ StatefulSet یا resource مشابه) دستور می‌دهد که دوباره scale down کند.

Horizontal pod autoscaling روی objectهایی که قابل scale شدن نیستند (برای مثال یک DaemonSet) اعمال نمی‌شود.

HorizontalPodAutoscaler به‌صورت یک Kubernetes API resource و یک controller پیاده‌سازی شده است. آن resource رفتار controller را تعیین می‌کند. horizontal pod autoscaling controller که درون control plane (اجزای مدیریتی cluster که تصمیم‌ها را می‌گیرند و وضعیت را نگه می‌دارند) اجرا می‌شود،‏ به‌طور دوره‌ای scale مطلوب (desired scale) هدف خود (برای مثال یک Deployment) را طوری تنظیم می‌کند که با metricهای مشاهده‌شده مثل میانگین CPU utilization،‏ میانگین memory utilization یا هر custom metric دیگری که مشخص کنید،‏ هماهنگ شود.

توضیح تکمیلی: چرا DaemonSet قابل autoscale افقی نیست؟

تعداد Podهای یک DaemonSet را «تعداد Nodeهای واجد شرایط» تعیین می‌کند،‏ نه یک field به نام replicas. به همین دلیل DaemonSet اصلا subresource (مسیر فرعی یک شیء در API مثل status یا scale) به نام scale ندارد و HPA چیزی برای تغییر دادن پیدا نمی‌کند. اگر بخواهید تعداد Podهای یک DaemonSet بیشتر شود،‏ باید Node اضافه کنید (Node autoscaling)،‏ و اگر هر Pod آن resource بیشتری لازم دارد،‏ باید سراغ vertical scaling بروید. قاعده‌ی کلی: HPA فقط روی resourceهایی کار می‌کند که subresource /scale دارند؛‏ مثل Deployment،‏ ReplicaSet،‏ StatefulSet،‏ ReplicationController و CRDهایی که scale subresource را تعریف کرده‌اند.

shell
# which resources expose a scale subresource?
kubectl get --raw /apis/apps/v1 | jq -r '.resources[].name' | grep '/scale'

deployments/scale

همان‌طور که می‌بینید،‏ daemonsets/scale در این فهرست وجود ندارد.

HorizontalPodAutoscaler چگونه کار می‌کند؟ (How does a HorizontalPodAutoscaler work?)

کوبرنتیز مکانیزم horizontal pod autoscaling را به‌صورت یک control loop پیاده‌سازی می‌کند که به‌صورت متناوب اجرا می‌شود (یک فرایند پیوسته نیست). فاصله‌ی این اجراها با پارامتر --horizontal-pod-autoscaler-sync-period در kube-controller-manager تنظیم می‌شود (و مقدار پیش‌فرض آن ۱۵ ثانیه است).

در هر دوره،‏ controller manager مقدار resource utilization را در برابر metricهایی که در هر تعریف HorizontalPodAutoscaler مشخص شده‌اند query می‌کند. controller manager،‏ target resource تعریف‌شده در scaleTargetRef را پیدا می‌کند،‏ سپس Podها را بر اساس labelهای .spec.selector آن target resource انتخاب می‌کند و metricها را یا از resource metrics API (برای per-pod resource metrics) یا از custom metrics API (برای همه‌ی metricهای دیگر) دریافت می‌کند.

  • برای per-pod resource metrics (مثل CPU):‏ controller،‏ metricها را از resource metrics API برای هر Pod که هدف HorizontalPodAutoscaler است fetch می‌کند. سپس اگر یک target utilization value تعیین شده باشد،‏ controller مقدار utilization را به‌صورت درصدی از resource request معادل روی containerهای هر Pod محاسبه می‌کند. اگر یک target raw value تعیین شده باشد،‏ مقادیر خام metric مستقیما استفاده می‌شوند. سپس controller میانگین utilization یا مقدار خام (بسته به نوع target مشخص‌شده) را روی همه‌ی Podهای هدف می‌گیرد و یک نسبت (ratio) تولید می‌کند که برای scale کردن تعداد replicaهای مطلوب استفاده می‌شود.

    لطفا توجه کنید که اگر برای برخی از containerهای Pod،‏ resource request مربوطه تنظیم نشده باشد،‏ CPU utilization آن Pod تعریف‌نشده خواهد بود و autoscaler هیچ اقدامی برای آن metric انجام نخواهد داد. برای اطلاعات بیشتر درباره‌ی نحوه‌ی کار الگوریتم autoscaling،‏ بخش Algorithm details را در ادامه ببینید.

  • برای per-pod custom metrics:‏ controller مشابه per-pod resource metrics عمل می‌کند،‏ با این تفاوت که با مقادیر خام (raw values) کار می‌کند،‏ نه مقادیر utilization.
  • برای object metrics و external metrics: یک metric منفرد fetch می‌شود که object مورد نظر را توصیف می‌کند. این metric با مقدار target مقایسه می‌شود تا مانند بالا یک ratio تولید شود. در نسخه‌ی API autoscaling/v2،‏ این مقدار را می‌توان به‌صورت اختیاری پیش از مقایسه بر تعداد Podها تقسیم کرد.

کاربرد رایج HorizontalPodAutoscaler این است که آن را برای fetch کردن metricها از aggregated APIها (metrics.k8s.io،‏ custom.metrics.k8s.io یا external.metrics.k8s.io) پیکربندی کنید. API metrics.k8s.io معمولا توسط یک add-on به نام Metrics Server فراهم می‌شود که باید جداگانه راه‌اندازی شود. برای اطلاعات بیشتر درباره‌ی resource metrics،‏ بخش Resource metrics pipeline و Metrics Server همین فصل را ببینید.

بخش Support for metrics APIs تضمین‌های پایداری و وضعیت پشتیبانی این APIهای مختلف را توضیح می‌دهد.

HorizontalPodAutoscaler controller به workload resourceهای متناظری که از scaling پشتیبانی می‌کنند (مثل Deploymentها و StatefulSet) دسترسی پیدا می‌کند. هرکدام از این resourceها یک subresource به نام scale دارند؛‏ یک interface که به شما اجازه می‌دهد تعداد replicaها را به‌صورت پویا تنظیم کنید و current state هرکدام را بررسی کنید. برای اطلاعات عمومی درباره‌ی subresourceها در Kubernetes API،‏ به Kubernetes API Concepts (فصل ۸) مراجعه کنید.

  1. هر ۱۵ ثانیه (sync period)،‏ HPA controller درون kube-controller-manager بیدار می‌شود.
  2. scaleTargetRef (مثلا Deployment/php-apache) را می‌خواند و از طریق subresource /scale مقدار فعلی replicas و selector را می‌گیرد.
  3. با آن selector (شرطی که اشیای هدف را بر اساس labelها انتخاب می‌کند)،‏ Podها را پیدا می‌کند و برای هر Pod از metrics.k8s.io مصرف CPU/memory را می‌خواند (یا از custom.metrics.k8s.io / external.metrics.k8s.io برای انواع دیگر).
  4. utilization را نسبت به request (نه limit) حساب می‌کند،‏ Podهای not-ready و بدون metric را کنار می‌گذارد،‏ ratio را حساب و tolerance را اعمال می‌کند.
  5. پیشنهاد را در stabilization window ثبت می‌کند،‏ policyهای behavior را اعمال می‌کند و بین minReplicas و maxReplicas محدود می‌کند.
  6. در نهایت فقط field spec.replicas روی subresource /scale را به‌روزرسانی می‌کند. بقیه‌ی کار (ساخت ReplicaSet/Pod) را Deployment controller و ReplicaSet controller انجام می‌دهند.

نکته‌ی مهم: HPA خودش هیچ Podی نمی‌سازد و حذف نمی‌کند؛‏ فقط یک عدد را عوض می‌کند. به همین دلیل اگر Pod جدید به دلیل کمبود capacity در وضعیت Pending بماند،‏ HPA کاری نمی‌تواند بکند و این وظیفه‌ی Node autoscaling است.

جزئیات الگوریتم (Algorithm details)

از ساده‌ترین دیدگاه،‏ HorizontalPodAutoscaler controller بر اساس نسبت بین مقدار مطلوب metric و مقدار فعلی metric عمل می‌کند:

formula
desiredReplicas = ceil[ currentReplicas × ( currentMetricValue / desiredMetricValue ) ]

برای مثال،‏ اگر مقدار فعلی metric برابر 200m و مقدار مطلوب 100m باشد،‏ تعداد replicaها دو برابر می‌شود،‏ چون ‎200.0 ÷ 100.0 = 2.0‎. اگر مقدار فعلی به جای آن 50m باشد،‏ تعداد replicaها نصف می‌شود،‏ چون ‎50.0 ÷ 100.0 = 0.5‎. Control Plane اگر این نسبت به‌اندازه‌ی کافی به 1.0 نزدیک باشد (در محدوده‌ی یک tolerance قابل پیکربندی که به‌طور پیش‌فرض 0.1 است)،‏ هر اقدام scaling را نادیده می‌گیرد.

وقتی یک targetAverageValue یا targetAverageUtilization مشخص شده باشد،‏ currentMetricValue با گرفتن میانگین metric مورد نظر روی همه‌ی Podهای scale target آن HorizontalPodAutoscaler محاسبه می‌شود.

پیش از بررسی tolerance و تصمیم‌گیری درباره‌ی مقادیر نهایی،‏ Control Plane همچنین بررسی می‌کند که آیا metricی گم شده (missing) است یا نه،‏ و چند Pod در وضعیت Ready هستند. برای per-pod resource metrics،‏ همه‌ی Podهایی که deletion timestamp دارند (objectهایی با deletion timestamp در حال خاموش شدن / حذف شدن هستند) نادیده گرفته می‌شوند،‏ و همه‌ی Podهای failed کنار گذاشته (discard) می‌شوند. برای external و object metrics،‏ تعداد replica بر اساس تعداد Podهای Running و Ready تعیین می‌شود؛‏ Podهای در حال termination که هنوز Ready هستند همچنان در این شمارش حساب می‌شوند.

اگر یک Pod خاص metric نداشته باشد،‏ برای بعد کنار گذاشته می‌شود؛‏ Podهای بدون metric برای تنظیم مقدار نهایی scaling استفاده خواهند شد.

هنگام scale کردن بر اساس CPU،‏ اگر هر Pod هنوز ready نشده باشد (هنوز در حال initialize است،‏ یا احتمالا unhealthy است) یا آخرین نقطه‌ی metric آن Pod مربوط به پیش از ready شدنش باشد،‏ آن Pod هم کنار گذاشته می‌شود.

به دلیل محدودیت‌های فنی،‏ HorizontalPodAutoscaler controller نمی‌تواند دقیقا تعیین کند که یک Pod اولین بار چه زمانی ready شده است،‏ وقتی می‌خواهد تصمیم بگیرد برخی CPU metricها را کنار بگذارد یا نه. در عوض،‏ یک Pod را «هنوز ready نشده» در نظر می‌گیرد اگر unready باشد و در یک پنجره‌ی زمانی کوتاه و قابل پیکربندی از زمان شروعش به ready تغییر وضعیت داده باشد. این مقدار با گزینه‌ی خط فرمان --horizontal-pod-autoscaler-initial-readiness-delay پیکربندی می‌شود و پیش‌فرض آن ۳۰ ثانیه است. وقتی یک Pod ready شد،‏ هر تغییر وضعیت به ready را اولین تغییر در نظر می‌گیرد اگر در یک بازه‌ی زمانی طولانی‌تر و قابل پیکربندی از زمان شروعش رخ داده باشد. این مقدار با گزینه‌ی خط فرمان --horizontal-pod-autoscaler-cpu-initialization-period پیکربندی می‌شود و پیش‌فرض آن ۵ دقیقه است.

سپس نسبت پایه‌ی scale یعنی currentMetricValue / desiredMetricValue با استفاده از Podهای باقی‌مانده‌ای که کنار گذاشته یا discard نشده‌اند محاسبه می‌شود.

اگر metricهای missing وجود داشت،‏ Control Plane میانگین را محافظه‌کارانه‌تر دوباره محاسبه می‌کند: فرض می‌کند آن Podها در حالت scale down،‏ ۱۰۰٪ مقدار مطلوب را مصرف می‌کنند و در حالت scale up،‏ ۰٪. این کار دامنه‌ی هر scale احتمالی را کاهش می‌دهد (dampen می‌کند).

علاوه بر این،‏ اگر Podهای not-yet-ready وجود داشتند و workload بدون در نظر گرفتن metricهای missing یا Podهای not-yet-ready،‏ scale up می‌شد،‏ controller محافظه‌کارانه فرض می‌کند که Podهای not-yet-ready،‏ ۰٪ از metric مطلوب را مصرف می‌کنند،‏ که دامنه‌ی scale up را بیشتر کاهش می‌دهد.

پس از لحاظ کردن Podهای not-yet-ready و metricهای missing،‏ controller نسبت مصرف (usage ratio) را دوباره محاسبه می‌کند. اگر نسبت جدید جهت scale را برعکس کند،‏ یا در محدوده‌ی tolerance باشد،‏ controller هیچ اقدام scalingی انجام نمی‌دهد. در سایر موارد،‏ نسبت جدید برای تصمیم‌گیری درباره‌ی هر تغییر در تعداد Podها استفاده می‌شود.

توجه کنید که مقدار اصلی میانگین utilization،‏ بدون در نظر گرفتن Podهای not-yet-ready یا metricهای missing،‏ از طریق status مربوط به HorizontalPodAutoscaler گزارش می‌شود،‏ حتی وقتی نسبت مصرف جدید استفاده شده باشد.

اگر چند metric در یک HorizontalPodAutoscaler مشخص شده باشد،‏ این محاسبه برای هر metric انجام می‌شود و سپس بزرگ‌ترین تعداد replica مطلوب انتخاب می‌شود. اگر هرکدام از این metricها قابل تبدیل به یک تعداد replica مطلوب نباشد (مثلا به دلیل خطا در fetch کردن metric از metrics APIها) و metricهایی که قابل fetch هستند scale down را پیشنهاد کنند،‏ scaling نادیده گرفته می‌شود. یعنی HPA همچنان می‌تواند scale up کند اگر یک یا چند metric مقدار desiredReplicas بزرگ‌تر از مقدار فعلی بدهند.

در نهایت،‏ درست پیش از آنکه HPA هدف را scale کند،‏ پیشنهاد scale (scale recommendation) ثبت می‌شود. controller همه‌ی پیشنهادهای درون یک پنجره‌ی قابل پیکربندی را در نظر می‌گیرد و بالاترین پیشنهاد از درون آن پنجره را انتخاب می‌کند. این مقدار را می‌توانید با گزینه‌ی خط فرمان --horizontal-pod-autoscaler-downscale-stabilization پیکربندی کنید که پیش‌فرض آن ۵ دقیقه است. این یعنی scale downها به‌تدریج رخ می‌دهند و اثر مقادیر metric که سریع نوسان می‌کنند را هموار می‌کنند.

readiness در Pod و metricهای autoscaling (Pod readiness and autoscaling metrics)

HorizontalPodAutoscaler (HPA) controller دو گزینه‌ی خط فرمان دارد که بر نحوه‌ی جمع‌آوری CPU metricها از Podها در زمان startup اثر می‌گذارند:

  1. --horizontal-pod-autoscaler-cpu-initialization-period (پیش‌فرض: ۵ دقیقه)

    این گزینه یک پنجره‌ی زمانی پس از شروع یک Pod تعریف می‌کند که در طول آن مصرف CPU آن Pod نادیده گرفته می‌شود،‏ مگر اینکه:

    • Pod در وضعیت Ready باشد و
    • نمونه‌ی metric به‌طور کامل در دوره‌ای گرفته شده باشد که Pod در آن Ready بوده است.

    این گزینه کمک می‌کند مصرف CPU بالا و گمراه‌کننده Podهای در حال initialize (برای مثال: برنامه‌های Java در حال warm up) از تصمیم‌های scaling در HPA کنار گذاشته شود.

  2. --horizontal-pod-autoscaler-initial-readiness-delay (پیش‌فرض: ۳۰ ثانیه)

    این گزینه یک دوره‌ی تأخیر کوتاه پس از شروع یک Pod تعریف می‌کند که در طول آن HPA controller با Podهایی که در حال حاضر Unready هستند مثل Podهای هنوز در حال initialize رفتار می‌کند،‏ حتی اگر قبلا به‌طور کوتاه به Ready تغییر وضعیت داده باشند.

    هدف طراحی آن:

    • جلوگیری از لحاظ کردن Podهایی که هنگام startup سریع بین Ready و Unready نوسان می‌کنند.
    • اطمینان از پایداری سیگنال readiness اولیه پیش از آنکه HPA metricهای آن‌ها را معتبر بداند.

این گزینه‌های خط فرمان را فقط می‌توانید به‌صورت cluster-wide (برای کل cluster) تنظیم کنید.

رفتارهای کلیدی readiness (Key behaviors for pod readiness)

  • اگر یک Pod در وضعیت Ready باشد و Ready بماند،‏ حتی درون دوره‌ی تأخیر هم می‌تواند به‌عنوان مشارکت‌کننده در metricها حساب شود.
  • اگر یک Pod سریع بین Ready و Unready جابه‌جا شود،‏ metricهای آن نادیده گرفته می‌شوند تا زمانی که به‌طور پایدار Ready در نظر گرفته شود.

روش خوب برای readiness (Good practice for pod readiness)

  • یک startupProbe پیکربندی کنید که تا زمانی که مصرف بالای CPU تمام نشده،‏ pass نشود،‏ یا
  • مطمئن شوید readinessProbe شما فقط پس از فروکش کردن جهش CPU وضعیت Ready را گزارش می‌دهد،‏ با استفاده از initialDelaySeconds.

و در حالت ایده‌آل،‏ --horizontal-pod-autoscaler-cpu-initialization-period را هم طوری تنظیم کنید که مدت startup را پوشش دهد.

آزمایش عملی: جلوگیری از scale up کاذب توسط warm up برنامه‌ی Java

یک سرویس Spring Boot در ۶۰ ثانیه‌ی اول،‏ هنگام JIT compile و بارگذاری cache،‏ CPU خود را تا ۱۰۰٪ limit مصرف می‌کند. اگر readinessProbe بلافاصله pass شود،‏ HPA این مصرف را واقعی می‌بیند و در هر scale up،‏ Podهای جدید دوباره CPU را بالا می‌برند؛‏ نتیجه یک زنجیره‌ی scale up بی‌دلیل است. راه‌حل طبق Good practice بالا:

lab/java-api-probes.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  selector:
    matchLabels: {app: orders-api}
  template:
    metadata:
      labels: {app: orders-api}
    spec:
      containers:
      - name: app
        image: example.com/orders-api:3.2.0
        resources:
          requests: {cpu: 500m, memory: 768Mi}
          limits:   {cpu: "2",  memory: 768Mi}
        # startupProbe fails until warm-up is done
        startupProbe:
          httpGet: {path: /actuator/health/warmup, port: 8080}
          periodSeconds: 5
          failureThreshold: 30     # up to 150s for warm-up
        readinessProbe:
          httpGet: {path: /actuator/health/readiness, port: 8080}
          periodSeconds: 5

تا وقتی startupProbe موفق نشده،‏ Pod Ready نیست و طبق قاعده‌ی cpu-initialization-period مصرف CPU آن در محاسبه‌ی HPA لحاظ نمی‌شود. اگر warm up بیش از ۵ دقیقه طول می‌کشد،‏ مدیر cluster باید گزینه‌ی --horizontal-pod-autoscaler-cpu-initialization-period را روی kube-controller-manager افزایش دهد (در clusterهای managed معمولا این گزینه در دسترس نیست؛‏ خارج از مستندات رسمی).

API object

HorizontalPodAutoscaler یک API kind در API group autoscaling کوبرنتیز است. نسخه‌ی stable فعلی در API version autoscaling/v2 قرار دارد که از scaling بر اساس memory و custom metricها پشتیبانی می‌کند. fieldهای جدیدی که در autoscaling/v2 معرفی شده‌اند،‏ هنگام کار با autoscaling/v1 به‌صورت annotation حفظ می‌شوند.

وقتی یک API object از نوع HorizontalPodAutoscaler می‌سازید،‏ مطمئن شوید نام مشخص‌شده یک DNS subdomain name معتبر باشد. جزئیات بیشتر درباره‌ی این API object در HorizontalPodAutoscaler Object آمده است.

توضیح تکمیلی: ساختار کامل یک HPA در autoscaling/v2
hpa-anatomy.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web                 # must be a valid DNS subdomain name
spec:
  scaleTargetRef:           # what to scale (needs a scale subresource)
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2            # default 1; 0 only with Object/External metrics
  maxReplicas: 20           # required
  metrics:                  # one or more; the largest recommendation wins
  - type: Resource          # Resource | ContainerResource | Pods | Object | External
    resource:
      name: cpu
      target:
        type: Utilization   # Utilization | AverageValue | Value
        averageUtilization: 60
  behavior:                 # optional: policies, stabilization window, tolerance
    scaleDown:
      stabilizationWindowSeconds: 300
status:                     # filled in by the controller
  currentReplicas: 2
  desiredReplicas: 2
  currentMetrics: [...]
  conditions: [...]         # AbleToScale، ScalingActive، ScalingLimited، ScaledToZero

اگر یک HPA را با autoscaling/v1 بخوانید (که فقط targetCPUUtilizationPercentage دارد)،‏ fieldهای v2 مثل metrics اضافی و behavior از بین نمی‌روند،‏ بلکه در annotationها نگه داشته می‌شوند؛‏ اما برای هر کار جدید همیشه از autoscaling/v2 استفاده کنید.

پایداری scale یک workload؛‏ flapping (Stability of workload scale)

هنگام مدیریت scale یک گروه از replicaها با HorizontalPodAutoscaler،‏ ممکن است تعداد replicaها به دلیل ماهیت پویای metricهای ارزیابی‌شده،‏ مرتبا نوسان کند. این وضعیت گاهی thrashing یا flapping نامیده می‌شود. این مشابه مفهوم hysteresis در سایبرنتیک است.

autoscaling در حین rolling update (Autoscaling during rolling update)

کوبرنتیز به شما اجازه می‌دهد روی یک Deployment یک rolling update (جایگزینی تدریجی Podهای قدیمی با Podهای جدید بدون قطعی) انجام دهید. در این حالت،‏ Deployment،‏ ReplicaSetهای زیرین را برای شما مدیریت می‌کند. وقتی autoscaling را برای یک Deployment پیکربندی می‌کنید،‏ یک HorizontalPodAutoscaler را به یک Deployment منفرد bind می‌کنید. HorizontalPodAutoscaler field replicas مربوط به Deployment را مدیریت می‌کند. deployment controller مسئول تنظیم replicas در ReplicaSetهای زیرین است،‏ به‌طوری که مجموع آن‌ها در طول rollout و پس از آن به عدد مناسبی برسد.

اگر یک rolling update روی یک StatefulSet انجام دهید که تعداد replicaهای آن autoscale می‌شود،‏ StatefulSet مستقیما مجموعه‌ی Podهای خود را مدیریت می‌کند (هیچ resource میانی مشابه ReplicaSet وجود ندارد).

توضیح تکمیلی: چرا HPA را به Deployment وصل می‌کنیم و نه به ReplicaSet؟

در یک rollout،‏ Deployment یک ReplicaSet جدید می‌سازد و به‌تدریج ReplicaSet قدیمی را کوچک می‌کند (فصل ۴). اگر HPA را مستقیم به ReplicaSet فعلی وصل کنید،‏ با اولین rollout آن ReplicaSet به صفر می‌رسد و HPA به یک object مرده اشاره می‌کند،‏ در حالی که ReplicaSet جدید اصلا autoscale نمی‌شود. با اتصال HPA به Deployment،‏ HPA فقط Deployment.spec.replicas را تعیین می‌کند (مثلا ۱۰) و Deployment controller با رعایت maxSurge/maxUnavailable این عدد را بین ReplicaSet قدیم و جدید تقسیم می‌کند.

خروجی نمونه در میانه‌ی rollout (HPA روی 10)
$ kubectl get rs -l app=web
NAME             DESIRED   CURRENT   READY   AGE
web-7c9d8f6b5d   5         5         5       3d     # old ReplicaSet
web-5f4b7c9e8a   7         7         4       40s    # new ReplicaSet (maxSurge=25%)

یک نکته‌ی عملی: در طول rollout،‏ Podهای جدید تازه start شده‌اند و ممکن است هنوز Ready نباشند؛‏ طبق قواعد بخش Algorithm details،‏ این Podها در محاسبه‌ی CPU کنار گذاشته می‌شوند و HPA در این مدت محافظه‌کارانه‌تر عمل می‌کند.

پشتیبانی از resource metrics (Support for resource metrics)

هر HPA target می‌تواند بر اساس مصرف resource Podهای درون scaling target خودش scale شود. هنگام تعریف specification یک Pod،‏ resource requestهایی مثل cpu و memory باید مشخص شوند. این مقادیر برای تعیین resource utilization استفاده می‌شوند و HPA controller از آن‌ها برای scale up یا scale down کردن target استفاده می‌کند. برای استفاده از scaling بر اساس resource utilization،‏ یک metric source به این شکل مشخص کنید:

yaml
type: Resource
resource:
  name: cpu
  target:
    type: Utilization
    averageUtilization: 60

با این metric،‏ HPA controller میانگین utilization Podهای درون scaling target را روی ۶۰٪ نگه می‌دارد. Utilization نسبت بین مصرف فعلی resource به resource درخواستی (requested) Pod است. برای جزئیات بیشتر درباره‌ی نحوه‌ی محاسبه و میانگین‌گیری utilization به بخش Algorithm details همین فصل مراجعه کنید.

نکته

از آنجا که resource usage همه‌ی containerها با هم جمع می‌شود،‏ ممکن است utilization کل Pod به‌درستی نشان‌دهنده‌ی مصرف resource هر container منفرد نباشد. این می‌تواند منجر به وضعیتی شود که یک container به‌تنهایی با مصرف بالا در حال اجراست،‏ اما چون مصرف کل Pod همچنان در محدوده‌ی قابل‌قبول است،‏ HPA scale out نمی‌کند.

metricهای resource هر container (Container resource metrics)

FEATURE STATE: Kubernetes v1.30 [stable] (پیش‌فرض true،‏ feature gate HPAContainerMetrics)

API مربوط به HorizontalPodAutoscaler همچنین از یک container metric source پشتیبانی می‌کند که به HPA اجازه می‌دهد مصرف resource یک container منفرد را در مجموعه‌ای از Podها دنبال کند،‏ تا target resource را scale کند. این به شما امکان می‌دهد آستانه‌های scaling را برای containerهایی که در یک Pod خاص اهمیت بیشتری دارند پیکربندی کنید. برای مثال،‏ اگر یک برنامه‌ی وب و یک container کناری (sidecar) که logging فراهم می‌کند دارید،‏ می‌توانید بر اساس مصرف resource برنامه‌ی وب scale کنید و container کناری و مصرف resource آن را نادیده بگیرید.

اگر target resource را با مجموعه‌ای متفاوت از containerها بازبینی کنید،‏ اگر آن container تازه اضافه‌شده هم باید برای scaling استفاده شود،‏ باید HPA spec را نیز بازبینی کنید. اگر containerی که در metric source مشخص شده وجود نداشته باشد یا فقط در زیرمجموعه‌ای از Podها حضور داشته باشد،‏ آن Podها نادیده گرفته می‌شوند و توصیه (recommendation) دوباره محاسبه می‌شود. برای جزئیات بیشتر درباره‌ی این محاسبه،‏ بخش Algorithm details را ببینید. برای استفاده از resourceهای container برای autoscaling،‏ یک metric source این‌گونه تعریف کنید:

yaml
type: ContainerResource
containerResource:
  name: cpu
  container: application
  target:
    type: Utilization
    averageUtilization: 60

در مثال بالا،‏ HPA controller،‏ target را طوری scale می‌کند که میانگین utilization CPU درون container با نام application در همه‌ی Podها برابر ۶۰٪ باشد.

نکته

اگر نام containerی را که یک HorizontalPodAutoscaler دنبال می‌کند تغییر دهید،‏ می‌توانید این تغییر را با یک ترتیب خاص انجام دهید تا scaling در طول اعمال تغییر همچنان در دسترس و مؤثر بماند. پیش از به‌روزرسانی resourceی که container را تعریف می‌کند (مثلا یک Deployment)،‏ ابتدا HPA مرتبط را به‌روزرسانی کنید تا هم نام container جدید و هم قدیمی را دنبال کند. به این ترتیب،‏ HPA می‌تواند در طول فرایند به‌روزرسانی همچنان یک scaling recommendation محاسبه کند.

پس از rollout تغییر نام container به workload resource،‏ با حذف نام container قدیمی از HPA specification،‏ آن را تمیز کنید (tidy up).

آزمایش عملی: scale کردن بر اساس container خاص،‏ نه کل Pod

یک Pod با یک container اصلی app و یک sidecar log-shipper در نظر بگیرید که به‌طور دائم CPU کمی مصرف می‌کند. اگر HPA را روی resource metric عادی (نوع Resource) تنظیم کنید،‏ مصرف log-shipper هم وارد میانگین می‌شود و اگر app در واقع تحت فشار باشد اما sidecar کم‌مصرف باشد،‏ ممکن است utilization کل Pod به آستانه نرسد.

lab/hpa-container-metric.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 15
  metrics:
  - type: ContainerResource
    containerResource:
      name: cpu
      container: app          # only this container, not log-shipper
      target:
        type: Utilization
        averageUtilization: 65
shell
kubectl apply -f hpa-container-metric.yaml
kubectl get hpa web

scale کردن بر اساس custom metric (Scaling on custom metrics)

FEATURE STATE: Kubernetes v1.23 [stable] (نسخه‌ی API autoscaling/v2beta2 پیش‌تر همین قابلیت را به‌صورت beta فراهم می‌کرد)

به شرطی که از نسخه‌ی API autoscaling/v2 استفاده کنید،‏ می‌توانید یک HorizontalPodAutoscaler را طوری پیکربندی کنید که بر اساس یک custom metric (که در کوبرنتیز یا هیچ کدام از componentهای آن built-in نیست) scale شود. HorizontalPodAutoscaler controller سپس این custom metricها را از Kubernetes API query می‌کند. برای الزامات آن به بخش Support for metrics APIs مراجعه کنید.

scale کردن بر اساس چند metric (Scaling on multiple metrics)

FEATURE STATE: Kubernetes v1.23 [stable] (نسخه‌ی API autoscaling/v2beta2 پیش‌تر همین قابلیت را به‌صورت beta فراهم می‌کرد)

به شرطی که از نسخه‌ی API autoscaling/v2 استفاده کنید،‏ می‌توانید چند metric را برای یک HorizontalPodAutoscaler برای scale کردن مشخص کنید. سپس HorizontalPodAutoscaler controller هر metric را ارزیابی می‌کند و بر اساس آن metric یک scale جدید پیشنهاد می‌دهد. HorizontalPodAutoscaler بزرگ‌ترین scale پیشنهادشده برای هر metric را می‌گیرد و workload را روی آن سایز تنظیم می‌کند (به شرطی که از حداکثر کلی‌ای که پیکربندی کرده‌اید بزرگ‌تر نباشد).

پشتیبانی از metrics APIها (Support for metrics APIs)

به‌طور پیش‌فرض،‏ HorizontalPodAutoscaler controller،‏ metricها را از مجموعه‌ای از APIها دریافت می‌کند. برای اینکه بتواند به این APIها دسترسی پیدا کند،‏ مدیران cluster باید اطمینان حاصل کنند که:

  • API aggregation layer فعال است.
  • APIهای متناظر register شده‌اند:
    • برای resource metrics،‏ این API همان metrics.k8s.io است که معمولا توسط metrics-server فراهم می‌شود و می‌تواند به‌عنوان یک cluster add-on راه‌اندازی شود.
      نکته

      HorizontalPodAutoscaler در حال حاضر از API metrics.k8s.io/v1beta1 برای resource metrics پشتیبانی می‌کند. هنوز از metrics.k8s.io/v1 پشتیبانی نمی‌کند.

    • برای custom metrics،‏ این API همان custom.metrics.k8s.io است. توسط API serverهای «adapter» فراهم می‌شود که vendorهای راهکار metrics آن‌ها را ارائه می‌دهند. از metrics pipeline خودتان بپرسید که آیا یک Kubernetes metrics adapter در دسترس است یا نه.
    • برای external metrics،‏ این API همان external.metrics.k8s.io است. ممکن است توسط همان custom metrics adapterهای بالا فراهم شود.

برای اطلاعات بیشتر درباره‌ی این مسیرهای مختلف metric و تفاوت آن‌ها،‏ design proposalهای مربوط به HPA V2،‏ custom.metrics.k8s.io و external.metrics.k8s.io را ببینید.

برای مثال‌هایی از نحوه‌ی استفاده از آن‌ها،‏ بخش‌های Autoscaling on multiple metrics and custom metrics و external metrics در walkthrough همین فصل را ببینید.

رفتار قابل پیکربندی scaling (Configurable scaling behavior)

FEATURE STATE: Kubernetes v1.23 [stable] (نسخه‌ی API autoscaling/v2beta2 پیش‌تر همین قابلیت را به‌صورت beta فراهم می‌کرد)

اگر از نسخه‌ی API v2 HorizontalPodAutoscaler استفاده کنید،‏ می‌توانید از field behavior (به API reference مراجعه کنید) برای پیکربندی رفتار جداگانه‌ی scale-up و scale-down استفاده کنید. این رفتارها را با تنظیم scaleUp و/یا scaleDown زیر field behavior مشخص می‌کنید.

Scaling policyها به شما امکان می‌دهند نرخ تغییر replicaها را در حین scaling کنترل کنید. همچنین دو تنظیم برای جلوگیری از flapping استفاده می‌شوند: می‌توانید یک stabilization window برای هموار کردن (smoothing) تعداد replicaها مشخص کنید،‏ و یک tolerance برای نادیده گرفتن نوسانات جزئی metric زیر یک آستانه‌ی مشخص.

policyهای scaling (Scaling policies)

یک یا چند scaling policy می‌توانند در بخش behavior از spec مشخص شوند. وقتی چند policy مشخص شده باشد،‏ policyی که اجازه‌ی بیشترین میزان تغییر را می‌دهد،‏ به‌طور پیش‌فرض انتخاب می‌شود. مثال زیر این رفتار را هنگام scale down نشان می‌دهد:

yaml
behavior:
  scaleDown:
    policies:
    - type: Pods
      value: 4
      periodSeconds: 60
    - type: Percent
      value: 10
      periodSeconds: 60

periodSeconds طول زمانی در گذشته را نشان می‌دهد که policy باید در آن بازه صادق باشد. حداکثر مقداری که می‌توانید برای periodSeconds تنظیم کنید ۱۸۰۰ (نیم ساعت) است. policy اول (Pods) اجازه می‌دهد حداکثر ۴ replica در یک دقیقه scale down شود. policy دوم (Percent) اجازه می‌دهد حداکثر ۱۰٪ از replicaهای فعلی در یک دقیقه scale down شود.

از آنجا که به‌طور پیش‌فرض policyی که اجازه‌ی بیشترین میزان تغییر را می‌دهد انتخاب می‌شود،‏ policy دوم فقط زمانی استفاده می‌شود که تعداد replicaهای Pod بیش از ۴۰ باشد. با ۴۰ یا کمتر replica،‏ policy اول اعمال می‌شود. برای مثال اگر ۸۰ replica وجود داشته باشد و target باید به ۱۰ replica scale down شود،‏ در گام اول ۸ replica کاهش می‌یابد. در iteration بعدی وقتی تعداد replicaها ۷۲ است،‏ ۱۰٪ از Podها برابر ۷.۲ است اما این عدد به بالا رند می‌شود و ۸ می‌شود. در هر loop از autoscaler controller،‏ تعداد Podهایی که باید تغییر کنند بر اساس تعداد replica فعلی دوباره محاسبه می‌شود. وقتی تعداد replicaها به زیر ۴۰ برسد،‏ policy اول (Pods) اعمال می‌شود و هر بار ۴ replica کاهش می‌یابد.

انتخاب policy را می‌توان با مشخص کردن field selectPolicy برای یک جهت scaling تغییر داد. با تنظیم مقدار روی Min،‏ policyی انتخاب می‌شود که کمترین میزان تغییر را در تعداد replica اجازه می‌دهد. تنظیم مقدار روی Disabled کاملا scaling در آن جهت را غیرفعال می‌کند.

پنجره‌ی پایدارسازی (Stabilization window)

stabilization window برای محدود کردن flapping تعداد replica زمانی که metricهای استفاده‌شده برای scaling مرتبا نوسان می‌کنند استفاده می‌شود. الگوریتم autoscaling از این پنجره برای استنتاج یک desired state قبلی و اجتناب از تغییرات ناخواسته در scale workload استفاده می‌کند.

برای مثال،‏ در قطعه کد مثال زیر،‏ یک stabilization window برای scaleDown مشخص شده است.

yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300

وقتی metricها نشان دهند که target باید scale down شود،‏ الگوریتم به desired stateهای محاسبه‌شده‌ی قبلی نگاه می‌کند و بالاترین مقدار از فاصله‌ی زمانی مشخص‌شده را استفاده می‌کند. در مثال بالا،‏ همه‌ی desired stateهای ۵ دقیقه‌ی گذشته در نظر گرفته می‌شوند.

این کار به یک rolling maximum شبیه است و از اینکه الگوریتم scaling مرتب Podها را حذف کند و فقط چند لحظه بعد دوباره یک Pod معادل بسازد جلوگیری می‌کند.

Tolerance

FEATURE STATE: Kubernetes v1.37 [stable] (پیش‌فرض true،‏ feature gate HPAConfigurableTolerance)

field tolerance یک آستانه برای نوسانات metric پیکربندی می‌کند و از scale کردن autoscaler برای تغییراتی زیر آن مقدار جلوگیری می‌کند.

این tolerance به‌صورت میزان نوسان حول مقدار مطلوب metric تعریف می‌شود که در آن هیچ scalingی رخ نمی‌دهد. برای مثال،‏ یک HorizontalPodAutoscaler را در نظر بگیرید که با target memory consumption برابر ۱۰۰MiB و یک scale-up tolerance برابر ۵٪ پیکربندی شده است:

yaml
behavior:
  scaleUp:
    tolerance: 0.05 # 5% tolerance for scale up

با این پیکربندی،‏ الگوریتم HPA فقط زمانی scale up را در نظر می‌گیرد که مصرف memory بیشتر از ۱۰۵MiB باشد (یعنی ۵٪ بالاتر از target).

اگر این field را تنظیم نکنید،‏ HPA مقدار پیش‌فرض cluster-wide tolerance که ۱۰٪ است را اعمال می‌کند. این پیش‌فرض را می‌توان هم برای scale-up و هم برای scale-down با آرگومان خط فرمان --horizontal-pod-autoscaler-tolerance در kube-controller-manager به‌روزرسانی کرد. (نمی‌توانید از Kubernetes API برای پیکربندی این مقدار پیش‌فرض استفاده کنید.)

رفتار پیش‌فرض (Default behavior)

برای استفاده از scaling سفارشی،‏ لازم نیست همه‌ی fieldها مشخص شوند. فقط مقادیری که باید سفارشی شوند می‌توانند مشخص شوند. این مقادیر سفارشی با مقادیر پیش‌فرض merge می‌شوند. مقادیر پیش‌فرض با رفتار موجود در الگوریتم HPA مطابقت دارند.

yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max

برای scale down،‏ stabilization window برابر ۳۰۰ ثانیه است (یا مقدار آرگومان خط فرمان --horizontal-pod-autoscaler-downscale-stabilization،‏ در صورتی که مشخص شده باشد). برای scale down فقط یک policy وجود دارد که اجازه می‌دهد ۱۰۰٪ از replicaهای در حال اجرا حذف شوند،‏ یعنی scaling target می‌تواند تا حداقل replica مجاز کاهش یابد. برای scale up هیچ stabilization windowی وجود ندارد. وقتی metricها نشان دهند target باید scale up شود،‏ target بلافاصله scale up می‌شود. دو policy وجود دارد که هر ۱۵ ثانیه حداکثر ۴ Pod یا ۱۰۰٪ از replicaهای در حال اجرا اضافه می‌شوند تا HPA به steady state برسد.

مثال: تغییر stabilization window برای scale down (Example: change downscale stabilization window)

برای فراهم کردن یک stabilization window سفارشی برای downscale به مدت یک دقیقه،‏ این behavior به HPA اضافه می‌شود:

yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 60

Example:‏ limit scale down rate — برای محدود کردن نرخی که HPA Podها را حذف می‌کند به ۱۰٪ در دقیقه،‏ behavior زیر اضافه می‌شود:

yaml
behavior:
  scaleDown:
    policies:
    - type: Percent
      value: 10
      periodSeconds: 60

برای اطمینان از اینکه حداکثر ۵ Pod در دقیقه حذف نشود،‏ می‌توانید یک policy دوم برای scale-down با اندازه‌ی ثابت ۵ اضافه کنید و selectPolicy را روی minimum تنظیم کنید. تنظیم selectPolicy روی Min یعنی autoscaler policyی را انتخاب می‌کند که کمترین تعداد Pod را تحت تأثیر قرار می‌دهد:

yaml
behavior:
  scaleDown:
    policies:
    - type: Percent
      value: 10
      periodSeconds: 60
    - type: Pods
      value: 5
      periodSeconds: 60
    selectPolicy: Min

Example:‏ disable scale down — مقدار Disabled برای selectPolicy،‏ scaling در آن جهت را خاموش می‌کند. پس برای جلوگیری از downscaling این policy استفاده می‌شود:

yaml
behavior:
  scaleDown:
    selectPolicy: Disabled
توضیح تکمیلی: یک پیکربندی behavior production-ready

ترکیبی که در بسیاری از تیم‌های production دیده می‌شود: scale up سریع و تهاجمی (چون هزینه‌ی زیر-provision شدن،‏ از دست دادن ترافیک است)،‏ و scale down محافظه‌کارانه و تدریجی (چون هزینه‌ی over-provision شدن فقط پول است،‏ نه از دست دادن کاربر):

hpa-behavior-prod.yaml (قطعه)
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0      # react immediately
    tolerance: 0.05                    # more sensitive than the 10% default
    policies:
    - type: Percent
      value: 100                       # may double every 30s
      periodSeconds: 30
    - type: Pods
      value: 10                        # or add up to 10 Pods every 30s
      periodSeconds: 30
    selectPolicy: Max
  scaleDown:
    stabilizationWindowSeconds: 600    # use the highest recommendation of the last 10 min
    tolerance: 0.1
    policies:
    - type: Percent
      value: 10                        # remove at most 10% per minute
      periodSeconds: 60
    selectPolicy: Min

این پیکربندی سناریوی اول «توضیح تکمیلی: flapping در عمل» در همین فصل را کاملا خنثی می‌کند: burst در چند ثانیه با policy تهاجمی scale up پاسخ می‌گیرد،‏ اما پس از افت بار،‏ به دلیل stabilization window ده‌دقیقه‌ای،‏ تا وقتی که مطمئن نشویم بار واقعا افت کرده،‏ Podها حذف نمی‌شوند.

پشتیبانی kubectl از HPA (Support for HorizontalPodAutoscaler in kubectl)

HorizontalPodAutoscaler،‏ مانند هر API resource دیگر،‏ به‌شکل استاندارد توسط kubectl پشتیبانی می‌شود. می‌توانید با دستور kubectl create یک autoscaler جدید بسازید. می‌توانید با kubectl get hpa فهرست autoscalerها را ببینید یا با kubectl describe hpa توضیح جزئی دریافت کنید. در نهایت،‏ می‌توانید با kubectl delete hpa یک autoscaler را حذف کنید.

علاوه بر این،‏ یک دستور مخصوص به نام kubectl autoscale برای ساختن یک HorizontalPodAutoscaler object وجود دارد. برای مثال،‏ اجرای kubectl autoscale rs foo --min=2 --max=5 --cpu=80% یک autoscaler برای ReplicaSet foo می‌سازد،‏ با target CPU utilization برابر ‎80%‎ و تعداد replica بین ۲ و ۵.

scale کردن به/از صفر (Scaling to and from zero)

FEATURE STATE: Kubernetes v1.37 [beta] (پیش‌فرض true،‏ feature gate HPAScaleToZero)

برای HorizontalPodAutoscalerهایی که بر اساس metric custom (object) یا external scale می‌شوند،‏ می‌توانید spec.minReplicas را روی ‎0‎ تنظیم کنید. وقتی بار وجود نداشته باشد،‏ workload به‌طور کامل به صفر replica scale down می‌شود،‏ و وقتی metric نشان دهد حداقل یک replica لازم است،‏ دوباره scale up می‌شود. این برای workloadهایی که مدت‌های طولانی idle هستند و نگه‌داشتنشان گران است مفید است،‏ مثل consumerهای یک queue که به‌ندرت استفاده می‌شوند یا jobهایی که به hardware اختصاصی مثل GPU نیاز دارند.

Scaling to zero فقط برای object و external metric پشتیبانی می‌شود. برای resource metric (مثل CPU یا memory utilization) در دسترس نیست،‏ چون این‌ها فقط روی Podهای در حال اجرا قابل اندازه‌گیری هستند. تنظیم minReplicas: 0 نیازمند پیکربندی حداقل یک object یا external metric است؛‏ در غیر این صورت،‏ API server آن HorizontalPodAutoscaler را رد می‌کند.

این رفتار با feature gate به نام HPAScaleToZero کنترل می‌شود که به‌طور پیش‌فرض فعال است. این feature gate باید هم روی kube-apiserver (که اجازه‌ی minReplicas: 0 را می‌دهد) و هم روی kube-controller-manager (که scaling را انجام می‌دهد) فعال باشد.

وقتی HPA یک workload را در صفر replica نگه می‌دارد،‏ یک condition به نام ScaledToZero با مقدار True روی status آن HorizontalPodAutoscaler ثبت می‌کند. HPA از این condition برای تمایز بین workloadی که خودش آن را به صفر scale کرده (و دوباره وقتی metric برگشت،‏ آن را scale up می‌کند) و workloadی که به‌صورت دستی deactivate شده با تنظیم replica count روی ‎0‎ استفاده می‌کند. وقتی workload دوباره scale up شود،‏ condition روی False با reason به نام NotScaledToZero تنظیم می‌شود.

غیرفعال‌سازی ضمنی حالت maintenance (Implicit maintenance-mode deactivation)

می‌توانید HPA را برای یک target به‌صورت ضمنی و بدون نیاز به تغییر پیکربندی خود HPA غیرفعال کنید. اگر تعداد replica مطلوب target روی ۰ تنظیم شده باشد و حداقل replica count در HPA بزرگ‌تر از ۰ باشد،‏ HPA تنظیم target را متوقف می‌کند (و Condition به نام ScalingActive روی خودش را روی false تنظیم می‌کند) تا زمانی که آن را با تنظیم دستی تعداد replica مطلوب target یا حداقل replica HPA دوباره فعال کنید.

مهاجرت به autoscaling افقی (Migrating Deployments and StatefulSets to horizontal autoscaling)

وقتی یک HPA فعال است،‏ توصیه می‌شود مقدار spec.replicas Deployment و/یا StatefulSet از manifestهای آن حذف شود. اگر این کار انجام نشود،‏ هر بار که تغییری روی آن object اعمال شود،‏ برای مثال از طریق kubectl apply -f deployment.yaml،‏ این کار به کوبرنتیز دستور می‌دهد تعداد فعلی Podها را به مقدار field spec.replicas scale کند. این ممکن است مطلوب نباشد و وقتی HPA فعال است می‌تواند دردسرساز باشد و منجر به thrashing یا رفتار flapping شود.

توجه کنید که حذف spec.replicas ممکن است باعث یک کاهش یک‌باره در تعداد Podها شود،‏ زیرا مقدار پیش‌فرض این field برابر ۱ است (به Deployment Replicas در فصل ۴ مراجعه کنید). با این به‌روزرسانی،‏ همه‌ی Podها به جز ۱ عدد،‏ فرایند termination خود را شروع می‌کنند. هر deployment application بعدی به‌طور عادی رفتار می‌کند و پیکربندی rolling update موردنظر را رعایت می‌کند. می‌توانید از این کاهش با انتخاب یکی از دو روش زیر،‏ بسته به اینکه چگونه Deploymentهای خود را تغییر می‌دهید،‏ جلوگیری کنید:

  • Client Side Apply (پیش‌فرض):
    1. kubectl apply edit-last-applied deployment/<deployment_name>
    2. در ویرایشگر،‏ spec.replicas را حذف کنید. پس از ذخیره و خروج از ویرایشگر،‏ kubectl به‌روزرسانی را اعمال می‌کند. در این مرحله هیچ تغییری در تعداد Pod رخ نمی‌دهد.
    3. اکنون می‌توانید spec.replicas را از manifest حذف کنید. اگر از source code management استفاده می‌کنید،‏ تغییرات را commit کنید یا هر مرحله‌ی دیگری که برای پیگیری به‌روزرسانی‌ها مناسب است انجام دهید.
    4. از این پس می‌توانید kubectl apply -f deployment.yaml را اجرا کنید.
  • Server Side Apply: وقتی از Server-Side Apply استفاده می‌کنید،‏ می‌توانید راهنمای transferring ownership را دنبال کنید که دقیقا همین use case را پوشش می‌دهد.

مطالب بیشتر: HorizontalPodAutoscaler Walkthrough،‏ مستندات kubectl autoscale،‏ اگر می‌خواهید یک custom metrics adapter خودتان بنویسید،‏ boilerplate را ببینید،‏ و API reference HorizontalPodAutoscaler را بخوانید.

HorizontalPodAutoscaler Walkthrough

یک HorizontalPodAutoscaler (به اختصار HPA) به‌صورت خودکار یک workload resource (مثل یک Deployment یا StatefulSet) را به‌روزرسانی می‌کند،‏ با این هدف که workload به‌طور خودکار با تقاضا هماهنگ شود.

Horizontal scaling یعنی پاسخ به افزایش بار،‏ deploy کردن Podهای بیشتر است. این با vertical scaling فرق دارد که در کوبرنتیز به معنای اختصاص resourceهای بیشتر (مثلا memory یا CPU) به Podهایی است که از قبل برای آن workload در حال اجرا هستند.

اگر بار کاهش یابد و تعداد Podها بالاتر از حداقل پیکربندی‌شده باشد،‏ HorizontalPodAutoscaler به workload resource (Deployment،‏ StatefulSet یا resource مشابه) دستور می‌دهد که دوباره scale down کند.

این سند شما را با مثالی از فعال‌سازی HorizontalPodAutoscaler برای مدیریت خودکار scale یک برنامه‌ی وب نمونه راهنمایی می‌کند. این workload نمونه،‏ Apache httpd است که مقداری کد PHP اجرا می‌کند.

پیش‌نیازها (Before you begin)

اگر یک release قدیمی‌تر از کوبرنتیز را اجرا می‌کنید،‏ به نسخه‌ی مستندات مربوط به آن release مراجعه کنید.

برای دنبال کردن این walkthrough،‏ باید از یک cluster استفاده کنید که یک Metrics Server روی آن deploy و پیکربندی شده باشد. Kubernetes Metrics Server،‏ resource metricها را از kubeletهای cluster شما جمع‌آوری می‌کند و آن metricها را از طریق Kubernetes API،‏ با استفاده از یک APIService که انواع جدیدی از resource برای نمایش خواندن metric اضافه می‌کند،‏ در دسترس قرار می‌دهد.

برای یادگیری نحوه‌ی deploy کردن Metrics Server،‏ به مستندات metrics-server مراجعه کنید.

اگر روی minikube اجرا می‌کنید،‏ برای فعال‌سازی metrics-server دستور زیر را اجرا کنید:

shell
minikube addons enable metrics-server

اجرا و expose کردن سرور php-apache (Run and expose php-apache server)

برای نشان دادن یک HorizontalPodAutoscaler،‏ ابتدا یک Deployment که یک container با image به نام hpa-example اجرا می‌کند شروع می‌کنید و آن را با این manifest به‌عنوان یک service expose می‌کنید:

application/php-apache.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: php-apache
spec:
  selector:
    matchLabels:
      run: php-apache
  template:
    metadata:
      labels:
        run: php-apache
    spec:
      containers:
      - name: php-apache
        image: registry.k8s.io/hpa-example
        ports:
        - containerPort: 80
        resources:
          limits:
            cpu: 500m
          requests:
            cpu: 200m
---
apiVersion: v1
kind: Service
metadata:
  name: php-apache
  labels:
    run: php-apache
spec:
  ports:
  - port: 80
  selector:
    run: php-apache

برای این کار،‏ دستور زیر را اجرا کنید:

shell
kubectl apply -f https://k8s.io/examples/application/php-apache.yaml
خروجی
deployment.apps/php-apache created
service/php-apache created

ساختن HorizontalPodAutoscaler (Create the HorizontalPodAutoscaler)

حالا که سرور در حال اجراست،‏ autoscaler را با استفاده از kubectl بسازید. دستور فرعی kubectl autoscale،‏ بخشی از kubectl،‏ به شما در این کار کمک می‌کند.

به‌زودی دستوری را اجرا می‌کنید که یک HorizontalPodAutoscaler می‌سازد که بین ۱ تا ۱۰ replica از Podهای کنترل‌شده توسط Deployment php-apache که در گام اول این راهنما ساختید نگه می‌دارد.

به‌طور تقریبی،‏ HPA controller تعداد replicaها را افزایش و کاهش می‌دهد (با به‌روزرسانی Deployment) تا میانگین CPU utilization روی همه‌ی Podها را روی ۵۰٪ نگه دارد. سپس Deployment،‏ ReplicaSet را به‌روزرسانی می‌کند — این بخشی از نحوه‌ی کار همه‌ی Deploymentها در کوبرنتیز است — و سپس ReplicaSet بر اساس تغییر در .spec خودش،‏ Podها را اضافه یا حذف می‌کند.

از آنجا که هر Pod طبق manifest بالا ۲۰۰ میلی‌کور درخواست می‌کند،‏ این یعنی میانگین مصرف CPU برابر ۱۰۰ میلی‌کور است. برای جزئیات بیشتر درباره‌ی الگوریتم به بخش Algorithm details همین فصل مراجعه کنید.

HorizontalPodAutoscaler را بسازید:

shell
kubectl autoscale deployment php-apache --cpu=50% --min=1 --max=10
خروجی
horizontalpodautoscaler.autoscaling/php-apache autoscaled

می‌توانید current state HorizontalPodAutoscaler تازه‌ساخته‌شده را با اجرای دستور زیر بررسی کنید:

shell
# You can use "hpa" or "horizontalpodautoscaler"; either name works OK.
kubectl get hpa
خروجی نمونه
NAME         REFERENCE                     TARGET    MINPODS   MAXPODS   REPLICAS   AGE
php-apache   Deployment/php-apache/scale   0% / 50%  1         10        1          18s

(اگر HorizontalPodAutoscalerهای دیگری با نام‌های متفاوت مشاهده کردید،‏ یعنی از قبل وجود داشته‌اند و معمولا مشکلی نیست.)

لطفا توجه کنید که مصرف فعلی CPU برابر ۰٪ است،‏ چون هیچ clientی در حال ارسال request به سرور نیست (ستون TARGET میانگین را روی همه‌ی Podهای کنترل‌شده توسط Deployment متناظر نشان می‌دهد).

افزایش بار (Increase the load)

در ادامه،‏ ببینید autoscaler چگونه به افزایش بار واکنش نشان می‌دهد. برای این کار،‏ یک Pod دیگر به‌عنوان client اجرا می‌کنید. container درون Pod client در یک حلقه‌ی بی‌نهایت اجرا می‌شود و به service php-apache query ارسال می‌کند.

kubectl run -i --tty load-generator --rm --image=busybox:1.28 --restart=Never -- /bin/sh -c "while sleep 0.01; do wget -q -O- http://php-apache; done"

autoscaling بر اساس چند metric و custom metric (Autoscaling on multiple metrics and custom metrics)

می‌توانید با استفاده از نسخه‌ی API autoscaling/v2،‏ metricهای اضافی را برای autoscale کردن Deployment php-apache معرفی کنید.

ابتدا،‏ YAML مربوط به HorizontalPodAutoscaler خودتان را به فرم autoscaling/v2 دریافت کنید:

shell
kubectl get hpa php-apache -o yaml > /tmp/hpa-v2.yaml

فایل /tmp/hpa-v2.yaml را در یک ویرایشگر باز کنید و باید YAMLی شبیه این ببینید:

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
status:
  observedGeneration: 1
  lastScaleTime: <some-time>
  currentReplicas: 1
  desiredReplicas: 1
  currentMetrics:
  - type: Resource
    resource:
      name: cpu
      current:
        averageUtilization: 0
        averageValue: 0

توجه کنید که field targetCPUUtilizationPercentage با یک آرایه به نام metrics جایگزین شده است. metric مصرف CPU یک resource metric است،‏ چون به‌صورت درصدی از یک resource مشخص‌شده روی containerهای Pod نمایش داده می‌شود. توجه کنید که می‌توانید resource metricهای دیگری غیر از CPU هم مشخص کنید. به‌طور پیش‌فرض،‏ تنها resource metric دیگر پشتیبانی‌شده memory است. نام این resourceها بین clusterهای مختلف تغییر نمی‌کند و تا زمانی که API metrics.k8s.io در دسترس است،‏ باید همیشه در دسترس باشند.

می‌توانید resource metricها را به‌صورت مقادیر مستقیم هم مشخص کنید،‏ به جای درصدی از مقدار درخواستی،‏ با استفاده از target.type برابر با AverageValue به جای Utilization،‏ و تنظیم field متناظر target.averageValue به جای target.averageUtilization.

yaml
  metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 500Mi

دو نوع metric دیگر وجود دارد که هر دو custom metric محسوب می‌شوند: pod metricها و object metricها. این metricها ممکن است نام‌هایی داشته باشند که مخصوص یک cluster هستند و نیازمند یک پیکربندی پیشرفته‌تر برای cluster monitoring هستند.

اولین نوع از این metricهای دیگر،‏ pod metric است. این metricها Podها را توصیف می‌کنند و روی همه‌ی Podها میانگین‌گیری می‌شوند و با یک مقدار target مقایسه می‌شوند تا تعداد replica تعیین شود. مانند resource metric عمل می‌کنند،‏ با این تفاوت که فقط از نوع target برابر AverageValue پشتیبانی می‌کنند.

pod metricها با یک بلوک metric به این شکل مشخص می‌شوند:

yaml
type: Pods
pods:
  metric:
    name: packets-per-second
  target:
    type: AverageValue
    averageValue: 1k

دومین نوع metric دیگر،‏ object metric است. این metricها یک object متفاوت در همان namespace (محدوده‌ای برای جدا کردن نام‌ها و منابع درون یک cluster) را توصیف می‌کنند،‏ به جای اینکه Podها را توصیف کنند. metricها لزوما از خود آن object fetch نمی‌شوند؛‏ فقط آن را توصیف می‌کنند. object metricها از هر دو نوع target یعنی Value و AverageValue پشتیبانی می‌کنند. با Value،‏ target مستقیما با metric بازگردانده‌شده از API مقایسه می‌شود. با AverageValue،‏ مقدار بازگردانده‌شده از custom metrics API قبل از مقایسه با target،‏ بر تعداد Podها تقسیم می‌شود. مثال زیر نمایش YAML متریک requests-per-second است.

yaml
type: Object
object:
  metric:
    name: requests-per-second
  describedObject:
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    name: main-route
  target:
    type: Value
    value: 2k

اگر چند بلوک metric از این نوع فراهم کنید،‏ HorizontalPodAutoscaler هر metric را به‌نوبت در نظر می‌گیرد. HorizontalPodAutoscaler تعداد replicaهای پیشنهادی برای هر metric را محاسبه می‌کند،‏ و سپس بیشترین آن را انتخاب می‌کند.

برای مثال،‏ اگر سیستم monitoring شما metricهایی درباره‌ی ترافیک شبکه جمع‌آوری کند،‏ می‌توانید تعریف بالا را با استفاده از kubectl edit به این شکل به‌روزرسانی کنید:

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  - type: Pods
    pods:
      metric:
        name: packets-per-second
      target:
        type: AverageValue
        averageValue: 1k
  - type: Object
    object:
      metric:
        name: requests-per-second
      describedObject:
        apiVersion: networking.k8s.io/v1
        kind: Ingress
        name: main-route
      target:
        type: Value
        value: 10k
status:
  observedGeneration: 1
  lastScaleTime: <some-time>
  currentReplicas: 1
  desiredReplicas: 1
  currentMetrics:
  - type: Resource
    resource:
      name: cpu
    current:
      averageUtilization: 0
      averageValue: 0
  - type: Object
    object:
      metric:
        name: requests-per-second
      describedObject:
        apiVersion: networking.k8s.io/v1
        kind: Ingress
        name: main-route
      current:
        value: 10k

در این حالت،‏ HorizontalPodAutoscaler شما تلاش می‌کند مطمئن شود که هر Pod تقریبا ۵۰٪ از CPU درخواستی خود را مصرف می‌کند،‏ ۱۰۰۰ packet در ثانیه سرویس‌دهی می‌کند،‏ و همه‌ی Podهای پشت Ingress به نام main-route در مجموع ۱۰۰۰۰ request در ثانیه سرویس‌دهی می‌کنند.

autoscaling بر اساس metricهای دقیق‌تر (Autoscaling on more specific metrics)

بسیاری از metrics pipelineها به شما اجازه می‌دهند metricها را یا با نام یا با مجموعه‌ای از توصیف‌گرهای اضافی به نام _labelها_ توصیف کنید. برای همه‌ی انواع non-resource metric (pod،‏ object و external،‏ که در ادامه توضیح داده می‌شود)،‏ می‌توانید یک label selector اضافی مشخص کنید که به metric pipeline شما ارسال می‌شود. برای مثال،‏ اگر یک metric به نام http_requests با label به نام verb جمع‌آوری می‌کنید،‏ می‌توانید بلوک metric زیر را برای scale کردن فقط بر اساس GET requestها مشخص کنید:

yaml
type: Object
object:
  metric:
    name: http_requests
    selector: {matchLabels: {verb: GET}}

این selector از همان syntax مربوط به label selectorهای کامل کوبرنتیز استفاده می‌کند. اگر نام و selector با چند سری (series) مطابقت داشته باشند،‏ monitoring pipeline تعیین می‌کند که چگونه چند سری را به یک مقدار منفرد فروبکاهد (collapse). این selector additive است و نمی‌تواند metricهایی را انتخاب کند که objectهایی غیر از target object را توصیف می‌کنند (Podهای هدف در مورد نوع Pods،‏ و object توصیف‌شده در مورد نوع Object).

autoscaling بر اساس metricهای غیرمرتبط با objectهای کوبرنتیز (Autoscaling on metrics not related to Kubernetes objects)

برنامه‌های در حال اجرا روی کوبرنتیز ممکن است نیاز داشته باشند بر اساس metricهایی autoscale شوند که رابطه‌ی واضحی با هیچ objectی در cluster کوبرنتیز ندارند،‏ مانند metricهایی که یک سرویس میزبانی‌شده را توصیف می‌کنند و ارتباط مستقیمی با namespaceهای کوبرنتیز ندارند. در Kubernetes 1.10 و بعد از آن،‏ می‌توانید این use case را با _external metricها_ برطرف کنید.

استفاده از external metricها نیازمند آشنایی با سیستم monitoring شماست؛‏ راه‌اندازی آن مشابه custom metricها است. external metricها به شما اجازه می‌دهند cluster خود را بر اساس هر metric موجود در سیستم monitoring خود autoscale کنید. یک بلوک metric با name و selector،‏ مانند بالا،‏ فراهم کنید و به جای Object از نوع metric External استفاده کنید. اگر چند time series با metricSelector مطابقت داشته باشند،‏ مجموع مقادیر آن‌ها توسط HorizontalPodAutoscaler استفاده می‌شود. external metricها از هر دو نوع target یعنی Value و AverageValue پشتیبانی می‌کنند که دقیقا مشابه زمانی که از نوع Object استفاده می‌کنید عمل می‌کنند.

برای مثال اگر برنامه‌ی شما taskها را از یک queue service میزبانی‌شده پردازش می‌کند،‏ می‌توانید بخش زیر را به manifest HorizontalPodAutoscaler خود اضافه کنید تا مشخص کنید به یک worker به ازای هر ۳۰ task معلق (outstanding) نیاز دارید.

yaml
- type: External
  external:
    metric:
      name: queue_messages_ready
      selector:
        matchLabels:
          queue: "worker_tasks"
    target:
      type: AverageValue
      averageValue: 30

وقتی امکان‌پذیر باشد،‏ ترجیحا از نوع custom metric target به جای external metric استفاده کنید،‏ چون امن‌سازی custom metrics API برای مدیران cluster ساده‌تر است. external metrics API به‌طور بالقوه امکان دسترسی به هر metric را فراهم می‌کند،‏ پس مدیران cluster باید هنگام expose کردن آن دقت کنند.

status conditionهای HPA (Appendix: Horizontal Pod Autoscaler Status Conditions)

وقتی از فرم autoscaling/v2 HorizontalPodAutoscaler استفاده می‌کنید،‏ می‌توانید status conditionهایی که توسط کوبرنتیز روی HorizontalPodAutoscaler تنظیم می‌شوند را ببینید. این status conditionها نشان می‌دهند که آیا HorizontalPodAutoscaler می‌تواند scale کند یا نه،‏ و اینکه آیا در حال حاضر به شکلی محدود شده یا نه.

این conditionها در field status.conditions ظاهر می‌شوند. برای دیدن conditionهای مؤثر روی یک HorizontalPodAutoscaler،‏ می‌توانیم از kubectl describe hpa استفاده کنیم:

مقادیر Quantity (Quantities)

همه‌ی metricهای موجود در HorizontalPodAutoscaler و metrics APIها با استفاده از یک نمایش عددی خاص که در کوبرنتیز به عنوان quantity شناخته می‌شود مشخص می‌شوند. برای مثال،‏ quantity 10500m در نمایش decimal به‌صورت ‎10.5‎ نوشته می‌شود. metrics APIها در صورت امکان اعداد صحیح را بدون پسوند برمی‌گردانند و در غیر این صورت،‏ معمولا quantityها را در واحد میلی (milli-units) برمی‌گردانند. این یعنی ممکن است ببینید مقدار metric شما بین ‎1‎ و 1500m،‏ یا بین ‎1‎ و ‎1.5‎ در نمایش decimal نوسان کند.

سایر سناریوهای ممکن (Other possible scenarios)

Creating the autoscaler declaratively — به جای استفاده از دستور kubectl autoscale برای ساختن یک HorizontalPodAutoscaler به‌صورت imperative،‏ می‌توانیم از manifest زیر برای ساختن آن به‌صورت declarative استفاده کنیم:

application/hpa/php-apache.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50

سپس،‏ autoscaler را با اجرای دستور زیر بسازید:

shell
kubectl create -f https://k8s.io/examples/application/hpa/php-apache.yaml
خروجی
horizontalpodautoscaler.autoscaling/php-apache created
توضیح تکمیلی: چرا تعداد replica در walkthrough به ۷ رسید،‏ نه ۱۰؟

CPU request هر Pod برابر 200m است و target utilization برابر ۵۰٪ است،‏ یعنی مقدار مطلوب هر Pod برابر ۱۰۰m است. وقتی load-generator شروع به کار کرد،‏ مصرف واقعی هر Pod به ۳۰۵٪ (یعنی حدود ۶۱۰m) رسید. طبق فرمول الگوریتم:

محاسبه
desiredReplicas = ceil( 1 × (305 / 50) ) = ceil(6.1) = 7

یادداشت نویسنده: عدد ۳۰۵٪ از خروجی نمونه‌ی مستندات است. در manifest همین مثال limit برابر 500m است،‏ پس یک Pod تنها نمی‌تواند بیش از ۲۵۰٪ از request را مصرف کند و در اجرای واقعی TARGETS را حداکثر حدود ۲۵۰٪ می‌بینید؛‏ در این حالت گام اول به ceil(1 × 250/50) = 5 replica می‌رسد و اگر بار هنوز زیاد باشد،‏ گام‌های بعدی تعداد را بالاتر می‌برند.

یعنی یک Pod تنها با ظرفیت درخواستی خودش نمی‌تواند بار busybox را جواب دهد،‏ و HPA ۷ Pod می‌خواهد تا میانگین utilization به نزدیک ۵۰٪ برسد. چون maxReplicas برابر ۱۰ است،‏ HPA هرگز بیش از ۱۰ Pod نمی‌سازد،‏ حتی اگر بار بیشتر هم شود.

Vertical Pod Autoscaler

در کوبرنتیز،‏ یک VerticalPodAutoscaler یک workload management resource (مثل یک Deployment یا StatefulSet) را به‌صورت خودکار به‌روزرسانی می‌کند،‏ با این هدف که resource requestها و limitهای زیرساخت به‌طور خودکار با مصرف واقعی هماهنگ شوند.

Vertical scaling یعنی پاسخ به افزایش تقاضای resource،‏ اختصاص resourceهای بیشتر (مثلا memory یا CPU) به Podهایی است که از قبل برای آن workload در حال اجرا هستند. این با نام rightsizing یا گاهی autopilot هم شناخته می‌شود. این با horizontal scaling فرق دارد که در کوبرنتیز به معنای deploy کردن Podهای بیشتر برای پخش بار است.

اگر مصرف resource کاهش یابد و resource requestهای Pod بالاتر از سطح بهینه باشند،‏ VerticalPodAutoscaler به workload resource (Deployment،‏ StatefulSet یا resource مشابه) دستور می‌دهد resource requestها را دوباره کاهش دهد،‏ تا از هدررفت (waste) resource جلوگیری شود.

VerticalPodAutoscaler به‌صورت یک Kubernetes API resource و یک controller پیاده‌سازی شده است. آن resource رفتار controller را تعیین می‌کند. vertical pod autoscaling controller که درون data plane کوبرنتیز اجرا می‌شود،‏ به‌طور دوره‌ای resource requestها و limitهای target خود (برای مثال یک Deployment) را بر اساس تحلیل مصرف تاریخی resource،‏ مقدار resource در دسترس در cluster،‏ و رویدادهای real-time مثل شرایط out-of-memory (OOM) تنظیم می‌کند.

API object

VerticalPodAutoscaler به‌صورت یک Custom Resource Definition (CRD) در کوبرنتیز تعریف شده است. برخلاف HorizontalPodAutoscaler که بخشی از core Kubernetes API است،‏ VPA باید جداگانه در cluster شما نصب شود.

نسخه‌ی stable فعلی API برابر autoscaling.k8s.io/v1 است. جزئیات بیشتر درباره‌ی نصب و API آن را می‌توانید در مخزن GitHub مربوط به VPA بیابید.

VerticalPodAutoscaler چگونه کار می‌کند؟ (How does a VerticalPodAutoscaler work?)

کوبرنتیز مکانیزم vertical pod autoscaling را از طریق چند component همکار که به‌صورت متناوب اجرا می‌شوند (فرایند پیوسته نیست) پیاده‌سازی می‌کند. VPA از سه component اصلی تشکیل شده است:

  • _recommender_،‏ که مصرف resource را تحلیل می‌کند و پیشنهاد می‌دهد.
  • _updater_،‏ که resource requestهای Pod را یا با eviction (بیرون کردن Pod از Node و پایان دادن به اجرای آن) یا با تغییر in-place به‌روزرسانی می‌کند.
  • و webhook _admission controller_ مربوط به VPA،‏ که توصیه‌های resource را روی Podهای جدید یا recreate‌شده اعمال می‌کند.

در هر دوره،‏ Recommender مصرف resource Podهای هدف هر تعریف VerticalPodAutoscaler را query می‌کند. Recommender target resource تعریف‌شده در targetRef را پیدا می‌کند،‏ سپس Podها را بر اساس labelهای .spec.selector آن target resource انتخاب می‌کند،‏ و metricها را از resource metrics API دریافت می‌کند تا مصرف واقعی CPU و memory را تحلیل کند.

Recommender هم داده‌های مصرف resource فعلی و هم تاریخی (CPU و memory) را برای هر Pod هدف بررسی می‌کند. این بررسی شامل موارد زیر است:

  • الگوهای مصرف تاریخی در طول زمان برای شناسایی روندها
  • مصرف اوج (peak) و واریانس برای اطمینان از سرریز (headroom) کافی
  • رویدادهای out-of-memory (OOM) و دیگر رخدادهای مرتبط با resource

بر اساس این تحلیل،‏ Recommender سه نوع توصیه محاسبه می‌کند:

  • Target recommendation (resourceهای بهینه برای مصرف عادی)
  • Lower bound (حداقل resource قابل‌اجرا)
  • Upper bound (حداکثر resource معقول).

این توصیه‌ها در field .status.recommendation مربوط به resource VerticalPodAutoscaler ذخیره می‌شوند.

component _updater_ resourceهای VerticalPodAutoscaler را رصد می‌کند و resource requestهای فعلی Pod را با توصیه‌ها مقایسه می‌کند. وقتی تفاوت از آستانه‌های پیکربندی‌شده بیشتر شود و update policy اجازه دهد،‏ updater می‌تواند یکی از این کارها را انجام دهد:

  • Podها را evict کند،‏ که باعث ساخته‌شدن دوباره‌ی آن‌ها با resource requestهای جدید می‌شود (روش سنتی)
  • resource Pod را in-place و بدون eviction به‌روزرسانی کند،‏ وقتی cluster از in-place Pod resource updates پشتیبانی کند

روش انتخاب‌شده به update mode پیکربندی‌شده،‏ قابلیت‌های cluster و نوع تغییر resource موردنیاز بستگی دارد. به‌روزرسانی‌های in-place،‏ وقتی در دسترس باشند،‏ از اختلال (disruption) در Pod جلوگیری می‌کنند اما ممکن است محدودیت‌هایی درباره‌ی اینکه کدام resourceها قابل تغییر هستند داشته باشند. updater برای کاهش اثر روی سرویس،‏ PodDisruptionBudgetها (سقف تعداد Podهایی که هم‌زمان می‌توانند به‌طور داوطلبانه از دسترس خارج شوند) را رعایت می‌کند.

_admission controller_ به‌صورت یک mutating webhook عمل می‌کند که requestهای ساخت Pod را intercept می‌کند. بررسی می‌کند که آیا آن Pod هدف یک VerticalPodAutoscaler است،‏ و اگر بله،‏ resource requestها و limitهای توصیه‌شده را پیش از ساخته‌شدن Pod اعمال می‌کند. به‌طور خاص‌تر،‏ admission controller از Target recommendation موجود در بخش .status.recommendation resource VerticalPodAutoscaler به‌عنوان resource requestهای جدید استفاده می‌کند. admission controller اطمینان می‌دهد Podهای جدید با تخصیص resource مناسبی شروع به کار کنند،‏ چه در طول deploy اولیه ساخته شده باشند،‏ چه بعد از eviction توسط updater،‏ یا به دلیل عملیات scaling.

VerticalPodAutoscaler به یک منبع metric نیاز دارد،‏ مثل add-on به نام Metrics Server مربوط به کوبرنتیز،‏ که باید در cluster نصب شود. componentهای VPA metricها را از API metrics.k8s.io دریافت می‌کنند. Metrics Server باید به‌صورت جداگانه راه‌اندازی شود،‏ چون در بیشتر clusterها به‌طور پیش‌فرض deploy نمی‌شود. برای اطلاعات بیشتر درباره‌ی resource metrics،‏ بخش Metrics Server همین فصل را ببینید.

modeهای به‌روزرسانی (Update modes)

یک VerticalPodAutoscaler از update modeهای مختلفی پشتیبانی می‌کند که کنترل می‌کنند چگونه و چه زمانی توصیه‌های resource روی Podهای شما اعمال شوند. update mode را با field updateMode در VPA spec زیر updatePolicy پیکربندی می‌کنید:

yaml
---
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: my-app
  updatePolicy:
    updateMode: "Recreate"  # Off, Initial, Recreate, InPlaceOrRecreate, InPlace
Off

در update mode Off،‏ VPA recommender همچنان مصرف resource را تحلیل می‌کند و توصیه تولید می‌کند،‏ اما این توصیه‌ها به‌طور خودکار روی Podها اعمال نمی‌شوند. توصیه‌ها فقط در field .status object VPA ذخیره می‌شوند.

می‌توانید از ابزاری مثل kubectl برای مشاهده‌ی .status و توصیه‌های آن استفاده کنید.

Initial

در mode Initial،‏ VPA فقط هنگام ساخته‌شدن Podها برای اولین بار،‏ resource requestها را تنظیم می‌کند. resourceهای Podهای در حال اجرا را به‌روزرسانی نمی‌کند،‏ حتی اگر توصیه‌ها در طول زمان تغییر کنند. توصیه‌ها فقط در زمان ساخت Pod اعمال می‌شوند.

Recreate

در mode Recreate،‏ VPA به‌طور فعال resourceهای Pod را مدیریت می‌کند،‏ با evict کردن Podها وقتی resource requestهای فعلی آن‌ها به‌طور معناداری با توصیه‌ها فرق دارد. وقتی یک Pod evict شود،‏ workload controller (که یک Deployment،‏ StatefulSet و... را مدیریت می‌کند) یک Pod جایگزین می‌سازد و VPA admission controller،‏ resource requestهای به‌روزرسانی‌شده را روی Pod جدید اعمال می‌کند.

InPlaceOrRecreate

در mode InPlaceOrRecreate،‏ VPA تلاش می‌کند resource requestها و limitهای Pod را بدون restart کردن Pod،‏ در صورت امکان،‏ به‌روزرسانی کند. با این حال،‏ اگر به‌روزرسانی‌های in-place برای یک تغییر resource خاص قابل انجام نباشد،‏ VPA به eviction کردن Pod برمی‌گردد (مشابه mode Recreate) و اجازه می‌دهد workload controller یک Pod جایگزین با resourceهای به‌روزرسانی‌شده بسازد.

در این mode،‏ updater توصیه‌ها را با استفاده از قابلیت Resize Container Resources In-Place به‌صورت in-place اعمال می‌کند.

InPlace

این mode به‌صورت یک قابلیت alpha در VPA نسخه‌ی 1.7.0 در دسترس است و نیازمند Kubernetes 1.33 یا بالاتر با feature gate cluster-wide به نام InPlacePodVerticalScaling فعال،‏ و feature gate InPlace فعال روی updater و admission controller مربوط به VPA است. این mode از قابلیت in-place Pod resize برای اعمال به‌روزرسانی‌ها بدون ایجاد اختلال در Pod استفاده می‌کند.

در mode InPlace،‏ VPA تلاش می‌کند resource requestها و limitهای Pod را بدون restart یا evict کردن آن به‌روزرسانی کند. برخلاف InPlaceOrRecreate،‏ این mode هرگز به eviction برنمی‌گردد. اگر یک به‌روزرسانی in-place قابل‌اعمال نباشد (برای مثال،‏ چون Node ظرفیت کافی ندارد)،‏ VPA به‌روزرسانی را به تعویق می‌اندازد و آن را در reconciliation loop بعدی دوباره تلاش می‌کند.

برای استفاده از mode InPlace،‏ feature gate InPlace را هم روی VPA updater و هم روی admission controller فعال کنید:

shell
--feature-gates=InPlace=true

سپس updateMode را در VPA spec خود روی "InPlace" تنظیم کنید:

yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: my-app
  updatePolicy:
    updateMode: "InPlace"

تفاوت کلیدی با InPlaceOrRecreate: وقتی یک resize به تعویق افتاده،‏ در حال انجام،‏ یا غیرقابل‌اجرا باشد،‏ mode InPlace همیشه صبر می‌کند و دوباره تلاش می‌کند — هیچ‌وقت Pod را evict نمی‌کند،‏ بدون توجه به اینکه به‌روزرسانی چقدر معلق مانده باشد.

Auto (منسوخ‌شده)
نکته

update mode به نام Auto از نسخه‌ی VPA 1.4.0 منسوخ (deprecated) شده است. برای به‌روزرسانی مبتنی بر eviction از Recreate و برای به‌روزرسانی in-place با fallback به eviction از InPlaceOrRecreate استفاده کنید.

mode Auto در حال حاضر یک نام مستعار (alias) برای mode Recreate است و دقیقا مشابه آن رفتار می‌کند. این نام معرفی شده بود تا امکان گسترش آینده‌ی راهبردهای به‌روزرسانی خودکار را فراهم کند.

resource policyها (Resource policies)

resource policyها به شما اجازه می‌دهند نحوه‌ی تولید توصیه و اعمال به‌روزرسانی توسط VerticalPodAutoscaler را به‌دقت تنظیم کنید. می‌توانید مرزهایی برای توصیه‌های resource تعیین کنید،‏ مشخص کنید کدام resourceها مدیریت شوند،‏ و برای containerهای مختلف درون یک Pod policyهای متفاوتی پیکربندی کنید.

resource policyها را در field resourcePolicy در VPA spec تعریف می‌کنید:

yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: my-app
  updatePolicy:
    updateMode: "Recreate"
  resourcePolicy:
    containerPolicies:
    - containerName: "application"
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 2
        memory: 2Gi
      controlledResources:
      - cpu
      - memory
      controlledValues: RequestsAndLimits
minAllowed و maxAllowed

این fieldها مرزهایی برای توصیه‌های VPA تعیین می‌کنند. VPA هرگز توصیه‌ای پایین‌تر از minAllowed یا بالاتر از maxAllowed نمی‌دهد،‏ حتی اگر داده‌های مصرف واقعی مقادیر متفاوتی را نشان دهند.

controlledResources

field controlledResources مشخص می‌کند VPA چه نوع resourceهایی را برای یک container درون یک Pod مدیریت کند. اگر مشخص نشده باشد،‏ VPA به‌طور پیش‌فرض هم CPU و هم memory را مدیریت می‌کند. می‌توانید VPA را محدود کنید تا فقط resourceهای مشخصی را مدیریت کند. نام‌های معتبر resource شامل cpu و memory است.

controlledValues

field controlledValues تعیین می‌کند VPA کدام مقادیر را کنترل کند: requestها،‏ limitها،‏ یا هر دو:

RequestsAndLimits
VPA هم requestها و هم limitها را تنظیم می‌کند. limit به‌صورت متناسب بر اساس نسبت request-to-limit تعریف‌شده در spec Pod scale می‌شود. این mode پیش‌فرض است.
RequestsOnly
VPA فقط requestها را تنظیم می‌کند و limitها را دست‌نخورده می‌گذارد. limitها همچنان رعایت می‌شوند و می‌توانند در صورت عبور مصرف از آن‌ها،‏ throttling یا out-of-memory kill ایجاد کنند.

برای یادگیری بیشتر درباره‌ی این دو مفهوم به requests and limits مراجعه کنید.

resourceهای LimitRange (LimitRange resources)

componentهای admission controller و updater مربوط به VPA،‏ توصیه‌ها را برای رعایت محدودیت‌های تعریف‌شده در LimitRangeها post-process می‌کنند. resourceهای LimitRange با type برابر Pod و Container در cluster کوبرنتیز بررسی می‌شوند.

برای مثال،‏ اگر field max در یک resource LimitRange از نوع Container بیشتر از مقدار مجاز باشد،‏ هر دو component VPA،‏ limit را به مقدار تعریف‌شده در field max کاهش می‌دهند و request به‌صورت متناسب کاهش می‌یابد تا نسبت request-to-limit در spec Pod حفظ شود.

Resource metrics pipeline و Metrics Server

برای کوبرنتیز،‏ Metrics API مجموعه‌ای پایه از metricها را برای پشتیبانی از automatic scaling و use caseهای مشابه فراهم می‌کند. این API اطلاعاتی درباره‌ی مصرف resource برای node و pod،‏ شامل metricهای CPU و memory،‏ در دسترس قرار می‌دهد. اگر Metrics API را در cluster خود deploy کنید،‏ clientهای Kubernetes API می‌توانند این اطلاعات را query کنند،‏ و می‌توانید با استفاده از مکانیزم‌های access control کوبرنتیز،‏ دسترسی به آن را مدیریت کنید.

HorizontalPodAutoscaler (HPA) و VerticalPodAutoscaler (VPA) از داده‌های Metrics API برای تنظیم replicaها و resourceهای workload برای برآورده کردن تقاضای مشتری استفاده می‌کنند.

همچنین می‌توانید resource metricها را با دستور kubectl top مشاهده کنید.

نکته

Metrics API،‏ و metrics pipelineی که فعال می‌کند،‏ فقط حداقل metricهای CPU و memory لازم برای فعال‌سازی automatic scaling با HPA و/یا VPA را فراهم می‌کند. اگر می‌خواهید مجموعه‌ی کامل‌تری از metricها فراهم کنید،‏ می‌توانید Metrics API ساده را با deploy کردن یک metrics pipeline دوم که از Custom Metrics API استفاده می‌کند تکمیل کنید.

معماری resource metrics pipeline شامل componentهای زیر است (از راست به چپ در نمودار مستندات):

  • cAdvisor:‏ daemon مربوط به جمع‌آوری،‏ تجمیع (aggregate) و expose کردن metricهای container که در Kubelet قرار دارد.
  • kubelet:‏ node agent برای مدیریت resourceهای container.‏ resource metricها از طریق endpointهای API kubelet یعنی /metrics/resource و /stats قابل‌دسترسی هستند.
  • node level resource metrics:‏ API فراهم‌شده توسط kubelet برای کشف و بازیابی آماره‌های خلاصه‌شده‌ی هر Node که از طریق endpoint /metrics/resource در دسترس است.
  • metrics-server:‏ component add-on مربوط به cluster که resource metricها را از هر kubelet جمع‌آوری و تجمیع می‌کند. API server،‏ Metrics API را برای استفاده‌ی HPA،‏ VPA و دستور kubectl top سرویس‌دهی می‌کند. Metrics Server یک پیاده‌سازی مرجع (reference implementation) از Metrics API است.
  • Metrics API:‏ API کوبرنتیز که دسترسی به CPU و memory استفاده‌شده برای workload autoscaling را پشتیبانی می‌کند. برای اینکه این کار در cluster شما کار کند،‏ به یک API extension server نیاز دارید که Metrics API را فراهم کند.
    نکته

    cAdvisor از خواندن metricها از cgroupها پشتیبانی می‌کند،‏ که با container runtimeهای معمول در Linux کار می‌کند. اگر از یک container runtime استفاده می‌کنید که از مکانیزم isolation resource دیگری استفاده می‌کند،‏ برای مثال virtualization،‏ آن container runtime باید از CRI Container Metrics پشتیبانی کند تا metricها برای kubelet در دسترس باشند.

اندازه‌گیری مصرف resource (Measuring resource usage)

CPU

CPU به‌صورت میانگین مصرف core،‏ اندازه‌گیری‌شده به واحد cpu،‏ گزارش می‌شود. یک cpu در کوبرنتیز معادل ۱ vCPU/Core برای providerهای cloud،‏ و ۱ hyper-thread روی پردازنده‌های bare-metal Intel است.

این مقدار با گرفتن یک rate از یک شمارنده‌ی cumulative CPU که توسط kernel (هم Linux و هم Windows kernel) فراهم می‌شود محاسبه می‌شود. بازه‌ی زمانی استفاده‌شده برای محاسبه‌ی CPU در field window در Metrics API نشان داده می‌شود.

برای یادگیری بیشتر درباره‌ی نحوه‌ی تخصیص و اندازه‌گیری resourceهای CPU توسط کوبرنتیز،‏ بخش meaning of CPU را ببینید.

Memory

Memory به‌صورت working set،‏ اندازه‌گیری‌شده به بایت،‏ در لحظه‌ی جمع‌آوری metric گزارش می‌شود.

در دنیای ایده‌آل،‏ «working set» مقدار حافظه‌ای در حال استفاده است که نمی‌توان آن را تحت فشار حافظه (memory pressure) آزاد کرد. با این حال،‏ محاسبه‌ی working set بسته به سیستم‌عامل میزبان متفاوت است و به‌طور کلی از heuristicهای زیادی برای تولید یک تخمین استفاده می‌کند.

مدل کوبرنتیز برای working set یک container انتظار دارد که container runtime (نرم‌افزاری که containerها را روی Node اجرا می‌کند)،‏ حافظه‌ی anonymous مرتبط با آن container را بشمارد. metric working set معمولا شامل مقداری حافظه‌ی cached (file-backed) هم می‌شود،‏ چون سیستم‌عامل میزبان همیشه نمی‌تواند صفحات را بازیابی کند.

برای یادگیری بیشتر درباره‌ی نحوه‌ی تخصیص و اندازه‌گیری resourceهای memory توسط کوبرنتیز،‏ بخش meaning of memory را ببینید.

Metrics Server

metrics-server،‏ resource metricها را از kubeletها fetch می‌کند و آن‌ها را در Kubernetes API server از طریق Metrics API برای استفاده‌ی HPA و VPA expose می‌کند. همچنین می‌توانید این metricها را با دستور kubectl top مشاهده کنید.

metrics-server از Kubernetes API برای ردیابی nodeها و podهای cluster شما استفاده می‌کند. metrics-server هر node را از طریق HTTP query می‌کند تا metricها را fetch کند. metrics-server همچنین یک نمای داخلی از metadata مربوط به pod می‌سازد و یک cache از سلامت pod نگه می‌دارد. آن اطلاعات cache‌شده‌ی سلامت pod از طریق extension APIی که metrics-server در دسترس قرار می‌دهد قابل‌دسترسی است.

برای مثال با یک HPA query،‏ metrics-server باید مشخص کند کدام podها label selectorهای موجود در deployment را برآورده می‌کنند.

metrics-server از API kubelet برای جمع‌آوری metricها از هر node فراخوانی می‌کند. بسته به نسخه‌ی metrics-server،‏ یکی از موارد زیر استفاده می‌شود:

  • endpoint Metrics resource یعنی /metrics/resource در نسخه‌ی v0.6.0 به بعد،‏ یا
  • endpoint Summary API یعنی /stats/summary در نسخه‌های قدیمی‌تر
توضیح تکمیلی: زنجیره‌ی end-to-end یک عدد CPU که HPA می‌بیند
  1. container runtime آمار مصرف را در cgroup آن container ثبت می‌کند.
  2. cAdvisor داخل kubelet این آمار cgroup را می‌خواند و تجمیع می‌کند.
  3. kubelet این آمار را از طریق endpoint /metrics/resource خودش expose می‌کند.
  4. metrics-server هر Node را به‌صورت دوره‌ای (پیش‌فرض هر ۱۵ ثانیه) poll می‌کند و این اعداد را جمع‌آوری و در حافظه (نه در etcd؛‏ metrics-server تاریخچه نگه نمی‌دارد) نگه می‌دارد.
  5. وقتی HPA controller یا kubectl top از metrics.k8s.io query کند،‏ kube-apiserver آن request را از طریق aggregation layer به metrics-server forward می‌کند.

نکته‌ی مهم: چون metrics-server هیچ تاریخچه‌ای نگه نمی‌دارد،‏ اگر خودش restart شود،‏ HPA به‌طور موقت metric نخواهد داشت (تا نمونه‌ی بعدی جمع‌آوری شود) — دقیقا سناریوی «Pod با metric گم‌شده» که در بخش Algorithm details بحث شد.

Resize Container Resources In-Place

FEATURE STATE: Kubernetes v1.35 [stable] (feature gate InPlacePodVerticalScaling،‏ همیشه فعال)

این بخش توضیح می‌دهد چگونه resource requestها و limitهای CPU و memory اختصاص‌یافته به یک container را بدون recreate کردن Pod تغییر دهید.

به‌طور سنتی،‏ تغییر resource requirementهای یک Pod نیازمند حذف Pod موجود و ساختن یک جایگزین بود،‏ که معمولا توسط یک workload controller مدیریت می‌شد. In-place Pod Resize به شما اجازه می‌دهد تخصیص CPU/memory containerها را درون یک Pod در حال اجرا تغییر دهید،‏ در حالی که به‌طور بالقوه از اختلال در برنامه جلوگیری می‌کند.

مفاهیم کلیدی:

  • Desired Resources:‏ field spec.containers[*].resources یک container،‏ resourceهای مطلوب برای آن container را نشان می‌دهد و برای CPU و memory mutable (قابل‌تغییر) است.
  • Actual Resources:‏ field status.containerStatuses[*].resources resourceهای فعلا پیکربندی‌شده روی یک container در حال اجرا را منعکس می‌کند. برای containerهایی که هنوز شروع نشده یا restart شده‌اند،‏ این field resourceهای تخصیص‌یافته در شروع بعدی آن‌ها را منعکس می‌کند.
  • Triggering a Resize: می‌توانید با به‌روزرسانی requests و limits مطلوب در specification Pod،‏ یک resize درخواست کنید. این کار معمولا با kubectl patch،‏ kubectl apply یا kubectl edit با هدف subresource resize Pod انجام می‌شود. وقتی resourceهای مطلوب با resourceهای تخصیص‌یافته مطابقت نداشته باشند،‏ Kubelet تلاش می‌کند container را resize کند.
  • Allocated Resources (Advanced):‏ field status.containerStatuses[*].allocatedResources مقادیر resourceی که توسط Kubelet تأیید شده را دنبال می‌کند،‏ که عمدتا برای منطق داخلی scheduling استفاده می‌شود. برای بیشتر اهداف نظارتی و اعتبارسنجی،‏ روی status.containerStatuses[*].resources تمرکز کنید.

اگر یک Node دارای Podهایی با resize معلق یا ناقص باشد (به بخش Pod Resize Status در ادامه مراجعه کنید)،‏ scheduler هنگام تصمیم‌گیری درباره‌ی scheduling (انتخاب Node مناسب برای اجرای هر Pod)،‏ از بیشترین مقدار بین requestهای مطلوب،‏ requestهای تخصیص‌یافته و requestهای واقعی از status یک container استفاده می‌کند.

پیش‌نیازها (Before you begin)

feature gate به نام InPlacePodVerticalScaling باید برای control plane و همه‌ی nodeهای cluster شما فعال باشد. یادداشت نویسنده: در v1.37 این gate در مرحله‌ی stable و قفل‌شده (locked) است؛‏ پس همیشه فعال است و کاری لازم نیست.

برای فعال‌سازی automatic scheduler preemption برای resize requestهای به تعویق‌افتاده،‏ feature gate InPlacePodVerticalScalingSchedulerPreemption نیز باید روی control plane شما فعال باشد.

برای resize کردن پویا حجم‌های memory-backed (medium: Memory) از نوع emptyDir،‏ feature gate InPlacePodVerticalScalingMemoryBackedVolumes نیز باید روی control plane و nodeها فعال باشد و Nodeهای زیرین باید cgroup v2 اجرا کنند.

نسخه‌ی client kubectl باید حداقل v1.32 باشد تا بتوانید از flag --subresource=resize استفاده کنید.

status مربوط به resize (Pod resize status)

Kubelet،‏ status conditionهای Pod را برای نشان دادن وضعیت یک resize request به‌روزرسانی می‌کند:

  • type: PodResizePending: Kubelet نمی‌تواند فورا این request را اعطا کند. field message توضیح می‌دهد چرا.
    • reason: Infeasible: resize درخواستی روی Node فعلی غیرممکن است (برای مثال،‏ درخواست resource بیشتر از آنچه Node دارد).
    • reason: Deferred: resize درخواستی در حال حاضر ممکن نیست،‏ اما شاید بعدا ممکن شود (برای مثال اگر یک Pod دیگر حذف شود).‏ Kubelet این resize را دوباره تلاش می‌کند.
  • type: PodResizeInProgress: Kubelet این resize را پذیرفته و resourceها را تخصیص داده است،‏ اما تغییرات هنوز در حال اعمال هستند. این معمولا کوتاه است اما ممکن است بسته به نوع resource و رفتار runtime بیشتر طول بکشد. هر خطایی در طول actuation در field message (همراه با reason: Error) گزارش می‌شود.
نحوه‌ی retry و preempt شدن resizeهای معلق (How deferred resizes are retried and preempted)

اگر resize درخواستی _Deferred_ باشد،‏ kubelet به‌صورت دوره‌ای دوباره تلاش می‌کند آن را اعمال کند،‏ برای مثال وقتی Pod دیگری حذف یا scale down شود.

نکته

FEATURE STATE: Kubernetes v1.37 [alpha] (پیش‌فرض false،‏ feature gate InPlacePodVerticalScalingSchedulerPreemption)

وقتی feature gate InPlacePodVerticalScalingSchedulerPreemption فعال باشد،‏ kube-scheduler Podهایی با وضعیت resize Deferred را رصد می‌کند. اگر یک Node ظرفیت کافی برای برآورده کردن یک resize request از یک Pod با priority بالاتر را نداشته باشد،‏ scheduler می‌تواند Podهای priority پایین‌تر روی آن Node را preempt (evict) کند تا ظرفیت CPU یا memory موردنیاز آزاد شود. برای جزئیات بیشتر،‏ بخش «Preemption for in-place Pod resize» در فصل ۹ (Scheduling،‏ Preemption و Eviction) را ببینید.

اگر چند resize معلق وجود داشته باشد،‏ طبق این اولویت دوباره تلاش می‌شوند:

  • Podهایی با Priority بالاتر (بر اساس PriorityClass) زودتر resize مجدد آن‌ها تلاش می‌شود.
  • اگر دو Pod Priority یکسانی داشته باشند،‏ resize Podهای guaranteed پیش از resize Podهای burstable دوباره تلاش می‌شود.
  • اگر همه چیز یکسان باشد،‏ Podهایی که مدت بیشتری در وضعیت Deferred بوده‌اند در اولویت قرار می‌گیرند.

معلق ماندن یک resize با priority بالاتر،‏ باقی‌مانده‌ی resizeهای معلق را مسدود نمی‌کند؛‏ همه‌ی resizeهای معلق باقی‌مانده همچنان دوباره تلاش می‌شوند،‏ حتی اگر یک resize با priority بالاتر دوباره deferred شود.

استفاده از fieldهای observedGeneration (Leveraging observedGeneration Fields)

FEATURE STATE: Kubernetes v1.35 [stable] (feature gate PodObservedGenerationTracking،‏ همیشه فعال)

  • field سطح‌بالای status.observedGeneration مقدار metadata.generation متناظر با آخرین specification Podی که kubelet آن را تأیید کرده نشان می‌دهد. می‌توانید از این برای تعیین جدیدترین resize requestی که kubelet پردازش کرده استفاده کنید.
  • در condition PodResizeInProgress،‏ field conditions[].observedGeneration مقدار metadata.generation پیکربندی Pod را در زمان شروع resize در حال انجام فعلی نشان می‌دهد.
  • در condition PodResizePending،‏ field conditions[].observedGeneration مقدار metadata.generation پیکربندی Pod را در زمانی که آخرین‌بار تخصیص آن resize معلق تلاش شده نشان می‌دهد.

policyهای resize برای container (Container resize policies)

می‌توانید کنترل کنید که آیا یک container هنگام resize باید restart شود یا نه،‏ با تنظیم resizePolicy در specification container. این کار امکان کنترل دقیق بر اساس نوع resource (CPU یا memory) را فراهم می‌کند.

yaml
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired
    - resourceName: memory
      restartPolicy: RestartContainer
  • NotRequired: (پیش‌فرض) تغییر resource را روی container در حال اجرا بدون restart کردن آن اعمال می‌کند.
  • RestartContainer: container را restart می‌کند تا مقادیر resource جدید اعمال شوند. این معمولا برای تغییرات memory لازم است،‏ چون بسیاری از برنامه‌ها و runtimeها نمی‌توانند تخصیص memory خود را به‌صورت پویا تنظیم کنند.

اگر resizePolicy[*].restartPolicy برای یک resource مشخص نشده باشد،‏ به‌طور پیش‌فرض روی NotRequired تنظیم می‌شود.

نکته

اگر restartPolicy کلی یک Pod برابر Never باشد،‏ هر resizePolicy container باید برای همه‌ی resourceها برابر NotRequired باشد. نمی‌توانید یک resize policy پیکربندی کنید که نیازمند restart باشد در چنین Podهایی.

سناریوی مثال: یک container را با restartPolicy: NotRequired برای CPU و restartPolicy: RestartContainer برای memory در نظر بگیرید.

  • اگر فقط resourceهای CPU تغییر کنند،‏ container به‌صورت in-place resize می‌شود.
  • اگر فقط resourceهای memory تغییر کنند،‏ container restart می‌شود.
  • اگر هر دو resource CPU و memory هم‌زمان تغییر کنند،‏ container restart می‌شود (به دلیل policy memory).

resize کردن volumeهای emptyDir مبتنی بر memory (Resizing memory-backed emptyDir volumes)

FEATURE STATE: Kubernetes v1.37 [alpha] (پیش‌فرض false،‏ feature gate InPlacePodVerticalScalingMemoryBackedVolumes)

وقتی feature gate InPlacePodVerticalScalingMemoryBackedVolumes فعال باشد،‏ subresource /resize Pod از به‌روزرسانی sizeLimit حجم‌های memory-backed (medium: Memory) از نوع emptyDir روی Podهای در حال اجرا،‏ بدون restart کردن containerها یا recreate کردن Pod،‏ پشتیبانی می‌کند.

وقتی sizeLimit یک حجم از طریق subresource /resize به‌روزرسانی شود،‏ Kubelet mount زیرین tmpfs را به‌صورت پویا و بدون اختلال در container به‌روزرسانی می‌کند،‏ در حالی که به‌شکل ایمن از خطاهای out-of-memory یا triggerهای false-positive eviction جلوگیری می‌کند.

برای resize کردن یک حجم emptyDir حافظه‌محور،‏ spec.volumes[].emptyDir.sizeLimit را با هدف subresource resize Pod به‌روزرسانی کنید:

shell
kubectl patch pod <pod-name> --subresource resize --patch \
  '{"spec":{"volumes":[{"name":"cache-volume", "emptyDir":{"sizeLimit":"200Mi"}}]}}'

می‌توانید پیشرفت resize را با status conditionهای Pod (PodResizePending و PodResizeInProgress) رصد کنید. پس از تکمیل،‏ می‌توانید ظرفیت واقعی حجم را درون container در حال اجرا تأیید کنید (برای مثال،‏ با استفاده از kubectl exec برای اجرای df -h).

محدودیت‌ها (Limitations)

برای Kubernetes 1.37،‏ resize کردن in-place resourceهای Pod محدودیت‌های زیر را دارد:

  • Resource Types: فقط resourceهای CPU و memory قابل resize هستند.
  • Memory Decrease: اگر resize policy مربوط به memory برابر NotRequired باشد (یا مشخص نشده باشد)،‏ kubelet تلاشی به‌شکل best-effort می‌کند تا هنگام کاهش memory limitها از oom-kill جلوگیری کند،‏ اما هیچ تضمینی نمی‌دهد. پیش از کاهش memory limit یک container،‏ اگر مصرف memory از limit درخواستی بیشتر باشد،‏ resize رد می‌شود و status در وضعیت «In Progress» باقی می‌ماند. این best-effort در نظر گرفته می‌شود چون همچنان تحت یک race condition است که مصرف memory ممکن است درست بعد از انجام بررسی جهش کند.
  • QoS Class:‏ Quality of Service (QoS) class اصلی Pod (Guaranteed،‏ Burstable یا BestEffort) در زمان ساخت تعیین می‌شود و با resize قابل‌تغییر نیست. مقادیر resource resize‌شده باید همچنان از قوانین QoS class اصلی پیروی کنند:
    • Guaranteed:‏ requestها باید پس از resize همچنان برای CPU و memory با limitها برابر باشند.
    • Burstable:‏ requestها و limitها نمی‌توانند هم‌زمان برای هر دو CPU و memory برابر شوند (چون این کار QoS را به Guaranteed تغییر می‌دهد).
    • BestEffort:‏ resource requirementها (requests یا limits) نمی‌توانند اضافه شوند (چون این کار QoS را به Burstable یا Guaranteed تغییر می‌دهد).
  • Container Types:‏ init containerهای non-restartable و ephemeral containerها قابل resize نیستند. Sidecar containerها قابل resize هستند.
  • Resource Removal:‏ resource requestها و limitها پس از تنظیم به‌طور کامل قابل‌حذف نیستند؛‏ فقط می‌توانند به مقادیر متفاوتی تغییر کنند.
  • Operating System:‏ Podهای Windows از in-place resize پشتیبانی نمی‌کنند.
  • Node Policies:‏ Podهای مدیریت‌شده توسط policyهای استاتیک CPU یا Memory manager قابل resize in-place نیستند.
  • Swap:‏ Podهایی که از swap memory استفاده می‌کنند نمی‌توانند memory request خود را resize کنند،‏ مگر اینکه resizePolicy مربوط به memory برابر RestartContainer باشد.
  • Memory-Backed Volume Resizing:‏ resize کردن in-place حجم‌های memory-backed (medium: Memory) از نوع emptyDir نیازمند Nodeهایی است که cgroup v2 اجرا می‌کنند. روی Nodeهای cgroup v1،‏ requestهای resize in-place حجم به‌عنوان infeasible رد می‌شوند. حجم‌های emptyDir disk-backed و persistent volumeها از طریق subresource /resize Pod قابل‌resize نیستند.

این محدودیت‌ها ممکن است در نسخه‌های آینده‌ی کوبرنتیز کاهش یابند.

آزمایش عملی کامل: resize کردن CPU بدون restart،‏ و memory با restart

ابتدا یک namespace بسازید تا resourceهایی که در این تمرین می‌سازید از باقی cluster جدا باشند:

shell
kubectl create namespace qos-example

مثال ۱: resize کردن CPU بدون restart. ابتدا یک Pod برای resize in-place CPU و resize memory با restart بسازید:

pods/resource/pod-resize.yaml
apiVersion: v1
kind: Pod
metadata:
  name: resize-demo
  namespace: qos-example
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.8
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired # Default, but explicit here
    - resourceName: memory
      restartPolicy: RestartContainer
    resources:
      limits:
        memory: "200Mi"
        cpu: "700m"
      requests:
        memory: "200Mi"
        cpu: "700m"
shell
kubectl create -f pod-resize.yaml -n qos-example
# Wait a moment for the pod to be running
kubectl get pod resize-demo --output=yaml -n qos-example

باید spec.containers[0].resources و status.containerStatuses[0].resources را با manifest مطابق ببینید (۷۰۰m CPU،‏ ۲۰۰Mi memory). به status.containerStatuses[0].restartCount توجه کنید (باید ۰ باشد).

حالا CPU request و limit را به 800m افزایش دهید. از kubectl patch با آرگومان خط فرمان --subresource resize استفاده کنید.

shell
kubectl patch pod resize-demo -n qos-example --subresource resize --patch \
  '{"spec":{"containers":[{"name":"pause", "resources":{"requests":{"cpu":"800m"}, "limits":{"cpu":"800m"}}}]}}'

# Alternative methods:
# kubectl -n qos-example edit pod resize-demo --subresource resize
# kubectl -n qos-example apply -f <updated-manifest> --subresource resize --server-side
نکته

آرگومان خط فرمان --subresource resize نیازمند نسخه‌ی kubectl client v1.32.0 یا بالاتر است. نسخه‌های قدیمی‌تر خطای invalid subresource گزارش می‌کنند.

وضعیت pod را بعد از patch دوباره بررسی کنید:

shell
kubectl get pod resize-demo --output=yaml --namespace=qos-example

باید ببینید:

  • spec.containers[0].resources اکنون cpu: 800m نشان می‌دهد.
  • status.containerStatuses[0].resources نیز cpu: 800m نشان می‌دهد،‏ که نشان‌دهنده‌ی موفقیت resize روی node است.
  • status.containerStatuses[0].restartCount همچنان ‎0‎ می‌ماند،‏ چون resizePolicy مربوط به CPU برابر NotRequired بود.

مثال ۲: resize کردن memory با restart. حالا memory همان Pod را با افزایش آن به 300Mi resize کنید. از آنجا که resizePolicy مربوط به memory برابر RestartContainer است،‏ انتظار می‌رود container restart شود.

shell
kubectl patch pod resize-demo -n qos-example --subresource resize --patch \
  '{"spec":{"containers":[{"name":"pause", "resources":{"requests":{"memory":"300Mi"}, "limits":{"memory":"300Mi"}}}]}}'

وضعیت pod را کمی بعد از patch بررسی کنید:

shell
kubectl get pod resize-demo --output=yaml --namespace=qos-example

باید اکنون ببینید:

  • spec.containers[0].resources مقدار memory: 300Mi نشان می‌دهد.
  • status.containerStatuses[0].resources نیز مقدار memory: 300Mi نشان می‌دهد.
  • status.containerStatuses[0].restartCount به ‎1‎ (یا بیشتر،‏ اگر restart قبلی هم رخ داده بود) افزایش یافته،‏ که نشان می‌دهد container برای اعمال تغییر memory restart شده است.

عیب‌یابی: resize request غیرقابل‌اجرا (Infeasible). در ادامه،‏ مقدار غیرمنطقی از CPU درخواست کنید،‏ مثلا ۱۰۰۰ core کامل (به‌صورت ‎"1000"‎ نوشته می‌شود،‏ نه "1000m" برای میلی‌کور)،‏ که احتمالا از ظرفیت Node بیشتر است.

shell
# Attempt to patch with an excessively large CPU request
kubectl patch pod resize-demo -n qos-example --subresource resize --patch \
  '{"spec":{"containers":[{"name":"pause", "resources":{"requests":{"cpu":"1000"}, "limits":{"cpu":"1000"}}}]}}'

جزئیات Pod را query کنید:

shell
kubectl get pod resize-demo --output=yaml --namespace=qos-example

تغییراتی که نشان‌دهنده‌ی مشکل هستند را می‌بینید:

  • spec.containers[0].resources حالت مطلوب (cpu: "1000") را منعکس می‌کند.
  • یک condition با type: PodResizePending و reason: Infeasible به Pod اضافه شده است.
  • message آن condition دلیل را توضیح می‌دهد (Node didn't have enough capacity: cpu, requested: 1000000, capacity: ...؛‏ مقدار requested به میلی‌کور است و مستندات اینجا به‌اشتباه 800000 نوشته است)
  • مهم‌تر اینکه status.containerStatuses[0].resources هنوز مقادیر قبلی را نشان می‌دهد (cpu: 800m،‏ memory: 300Mi)،‏ چون resize غیرقابل‌اجرا توسط Kubelet اعمال نشده است.
  • restartCount به دلیل این تلاش ناموفق تغییر نکرده است.

برای رفع این مشکل،‏ باید دوباره Pod را با مقادیر resource قابل‌اجرا patch کنید.

پاک‌سازی. namespace خود را حذف کنید. این کار همه‌ی Podهایی که برای این کار ساختید را حذف می‌کند:

shell
kubectl delete namespace qos-example

Scale a StatefulSet

این بخش نشان می‌دهد چگونه یک StatefulSet را scale کنید. scale کردن یک StatefulSet به معنای افزایش یا کاهش تعداد replicaها است.

پیش‌نیازها (Before you begin)

  • StatefulSetها فقط در کوبرنتیز نسخه‌ی ۱.۵ یا بالاتر در دسترس هستند. برای بررسی نسخه‌ی کوبرنتیز خود،‏ kubectl version را اجرا کنید.
  • همه‌ی برنامه‌های stateful به‌خوبی scale نمی‌شوند. اگر درباره‌ی اینکه آیا باید StatefulSetهای خود را scale کنید مطمئن نیستید،‏ به مفاهیم StatefulSet یا StatefulSet tutorial (فصل ۴) مراجعه کنید.
  • scaling را فقط زمانی انجام دهید که مطمئن باشید کل cluster برنامه‌ی stateful شما کاملا سالم است.

استفاده از kubectl برای scale کردن StatefulSetها (Use kubectl to scale StatefulSets)

ابتدا StatefulSetی که می‌خواهید scale کنید را پیدا کنید:

shell
kubectl get statefulsets <stateful-set-name>

تعداد replicaهای StatefulSet خود را تغییر دهید:

shell
kubectl scale statefulsets <stateful-set-name> --replicas=<new-replicas>

به‌روزرسانی‌های in-place روی StatefulSetها (Make in-place updates on your StatefulSets)

به‌طور جایگزین،‏ می‌توانید روی StatefulSetهای خود به‌روزرسانی in-place انجام دهید.

اگر StatefulSet شما در ابتدا با kubectl apply ساخته شده بود،‏ .spec.replicas مربوط به manifest StatefulSet را به‌روزرسانی کنید،‏ سپس یک kubectl apply اجرا کنید:

shell
kubectl apply -f <stateful-set-file-updated>

در غیر این صورت،‏ آن field را با kubectl edit ویرایش کنید:

shell
kubectl edit statefulsets <stateful-set-name>

یا از kubectl patch استفاده کنید:

shell
kubectl patch statefulsets <stateful-set-name> -p '{"spec":{"replicas":<new-replicas>}}'

عیب‌یابی (Troubleshooting)

scale down به‌درستی کار نمی‌کند (Scaling down does not work right)

وقتی هر کدام از Podهای stateful مدیریت‌شده توسط یک StatefulSet ناسالم (unhealthy) باشد،‏ نمی‌توانید آن StatefulSet را scale down کنید. Scale down فقط پس از اینکه آن Podهای stateful در حال اجرا و آماده (ready) شوند رخ می‌دهد.

اگر spec.replicas > 1 باشد،‏ Kubernetes نمی‌تواند دلیل ناسالم بودن یک Pod را تعیین کند. ممکن است نتیجه‌ی یک خطای دائمی یا یک خطای گذرا (transient) باشد. یک خطای گذرا می‌تواند به دلیل یک restart لازم برای upgrade یا نگهداری ایجاد شده باشد.

اگر Pod به دلیل یک خطای دائمی ناسالم است،‏ scaling بدون رفع آن خطا ممکن است منجر به وضعیتی شود که عضویت StatefulSet به زیر حداقل تعداد replicaی لازم برای کارکرد صحیح برسد. این ممکن است باعث شود StatefulSet شما در دسترس نباشد.

اگر Pod به دلیل یک خطای گذرا ناسالم است و ممکن است دوباره در دسترس شود،‏ آن خطای گذرا ممکن است در عملیات scale-up یا scale-down شما اختلال ایجاد کند. برخی پایگاه‌داده‌های توزیع‌شده وقتی nodeها هم‌زمان join و leave می‌کنند مشکل دارند. در این موارد بهتر است در سطح برنامه درباره‌ی عملیات scaling استدلال کنید،‏ و scaling را فقط زمانی انجام دهید که مطمئن باشید cluster برنامه‌ی stateful شما کاملا سالم است.

توضیح تکمیلی: HPA روی StatefulSet چه فرقی با Deployment دارد؟

StatefulSet هم subresource /scale دارد و می‌تواند مانند Deployment هدف یک HPA باشد. تفاوت اصلی این است که StatefulSet هیچ ReplicaSet میانی ندارد و مستقیما مجموعه‌ی Podهای خود (با نام‌های پایدار مثل web-0،‏ web-1،‏ ...) را مدیریت می‌کند؛‏ به همین دلیل در بخش «Autoscaling during rolling update» این فصل گفته شد که هنگام rolling update یک StatefulSet با replica خودکار،‏ هیچ resource میانی مشابه ReplicaSet وجود ندارد. برای برنامه‌های stateful (پایگاه‌داده‌های توزیع‌شده،‏ message brokerهایی مثل Kafka)،‏ معمولا HPA روی CPU/memory کمتر مناسب است،‏ چون افزودن یا حذف یک replica معمولا نیازمند rebalance کردن داده است (که کند و پرهزینه است)؛‏ برای همین بسیاری از این workloadها بهتر است به‌جای HPA خودکار،‏ با توجه به بخش Troubleshooting بالا،‏ به‌صورت دستی و کنترل‌شده scale شوند.

Autoscale the DNS Service in a Cluster

این بخش نشان می‌دهد چگونه autoscaling سرویس DNS در cluster کوبرنتیز خود را فعال و پیکربندی کنید.

پیش‌نیازها (Before you begin)

  • این راهنما فرض می‌کند Nodeهای شما از معماری CPU AMD64 یا Intel 64 استفاده می‌کنند.
  • مطمئن شوید Kubernetes DNS فعال است.

فعال‌سازی DNS horizontal autoscaling (Enable DNS horizontal autoscaling)

در این بخش،‏ یک Deployment جدید می‌سازید. Podهای درون این Deployment یک container بر اساس image به نام cluster-proportional-autoscaler-amd64 اجرا می‌کنند.

یک فایل با نام dns-horizontal-autoscaler.yaml با این محتوا بسازید:

admin/dns/dns-horizontal-autoscaler.yaml
kind: ServiceAccount
apiVersion: v1
metadata:
  name: kube-dns-autoscaler
  namespace: kube-system
---
kind: ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  name: system:kube-dns-autoscaler
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["list", "watch"]
  - apiGroups: [""]
    resources: ["replicationcontrollers/scale"]
    verbs: ["get", "update"]
  - apiGroups: ["apps"]
    resources: ["deployments/scale", "replicasets/scale"]
    verbs: ["get", "update"]
# Remove the configmaps rule once below issue is fixed:
# kubernetes-incubator/cluster-proportional-autoscaler#16
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "create"]
---
kind: ClusterRoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  name: system:kube-dns-autoscaler
subjects:
  - kind: ServiceAccount
    name: kube-dns-autoscaler
    namespace: kube-system
roleRef:
  kind: ClusterRole
  name: system:kube-dns-autoscaler
  apiGroup: rbac.authorization.k8s.io

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kube-dns-autoscaler
  namespace: kube-system
  labels:
    k8s-app: kube-dns-autoscaler
    kubernetes.io/cluster-service: "true"
spec:
  selector:
    matchLabels:
      k8s-app: kube-dns-autoscaler
  template:
    metadata:
      labels:
        k8s-app: kube-dns-autoscaler
    spec:
      priorityClassName: system-cluster-critical
      securityContext:
        seccompProfile:
          type: RuntimeDefault
        supplementalGroups: [ 65534 ]
        fsGroup: 65534
      nodeSelector:
        kubernetes.io/os: linux
      containers:
      - name: autoscaler
        image: registry.k8s.io/cpa/cluster-proportional-autoscaler:1.8.4
        resources:
            requests:
                cpu: "20m"
                memory: "10Mi"
        command:
          - /cluster-proportional-autoscaler
          - --namespace=kube-system
          - --configmap=kube-dns-autoscaler
          # Should keep target in sync with cluster/addons/dns/coredns/coredns.yaml.base
          - --target=<SCALE_TARGET>
          # When cluster is using large nodes(with more cores), "coresPerReplica" should dominate.
          # If using small nodes, "nodesPerReplica" should dominate.
          - --default-params={"linear":{"coresPerReplica":256,"nodesPerReplica":16,"preventSinglePointFailure":true,"includeUnschedulableNodes":true}}
          - --logtostderr=true
          - --v=2
      tolerations:
      - key: "CriticalAddonsOnly"
        operator: "Exists"
      serviceAccountName: kube-dns-autoscaler

در فایل،‏ <SCALE_TARGET> را با scale target خودتان جایگزین کنید.

shell
kubectl apply -f dns-horizontal-autoscaler.yaml

خروجی یک دستور موفق این است:

خروجی

DNS horizontal autoscaling اکنون فعال است.

تنظیم پارامترهای DNS autoscaling (Tune DNS autoscaling parameters)

بررسی کنید ConfigMap به نام kube-dns-autoscaler وجود دارد:

shell
kubectl get configmap --namespace=kube-system

خروجی چیزی شبیه این است:

خروجی نمونه
NAME                  DATA      AGE
...
kube-dns-autoscaler   1         ...
...

داده‌ی درون ConfigMap را تغییر دهید:

shell
kubectl edit configmap kube-dns-autoscaler --namespace=kube-system

دنبال این خط بگردید:

yaml
linear: '{"coresPerReplica":256,"min":1,"nodesPerReplica":16}'

fieldها را طبق نیاز خودتان تغییر دهید. field «min» حداقل تعداد backendهای DNS را نشان می‌دهد. تعداد واقعی backendها با این معادله محاسبه می‌شود:

formula
replicas = max( ceil( cores × 1/coresPerReplica ) , ceil( nodes × 1/nodesPerReplica ) )

توجه کنید مقادیر هر دوی coresPerReplica و nodesPerReplica عدد اعشاری (float) هستند.

ایده این است که وقتی یک cluster از Nodeهایی با تعداد core زیاد استفاده می‌کند،‏ coresPerReplica غالب می‌شود. وقتی یک cluster از Nodeهایی با core کمتر استفاده می‌کند،‏ nodesPerReplica غالب می‌شود.

الگوهای scaling پشتیبانی‌شده‌ی دیگری هم وجود دارند. برای جزئیات به cluster-proportional-autoscaler مراجعه کنید.

چند گزینه برای تنظیم DNS horizontal autoscaling وجود دارد. اینکه کدام گزینه را استفاده کنید بسته به شرایط مختلف است.

نحوه‌ی کار DNS horizontal autoscaling (Understanding how DNS horizontal autoscaling works)

  • برنامه‌ی cluster-proportional-autoscaler جدا از سرویس DNS deploy می‌شود.
  • یک Pod به‌عنوان autoscaler یک client اجرا می‌کند که سرور API کوبرنتیز را برای تعداد nodeها و coreهای Cluster poll می‌کند.
  • یک تعداد replica مطلوب بر اساس nodeها و coreهای schedulable فعلی و پارامترهای scaling داده‌شده محاسبه و روی backendهای DNS اعمال می‌شود.
  • پارامترها و نقاط داده‌ی scaling از طریق یک ConfigMap به autoscaler فراهم می‌شود و آن جدول پارامترها را در هر poll interval تازه‌سازی می‌کند تا با آخرین پارامترهای scaling مطلوب به‌روز باشد.
  • تغییرات در پارامترهای scaling بدون rebuild یا restart کردن Pod مربوط به autoscaler مجاز هستند.
  • autoscaler یک controller interface برای پشتیبانی از دو الگوی کنترل فراهم می‌کند: linear و ladder.

Node autoscaling

برای اجرای workloadها در cluster خود،‏ به Node نیاز دارید. Nodeهای cluster شما می‌توانند autoscale شوند: به‌صورت پویا _provision_ شوند یا _consolidate_ شوند تا ظرفیت موردنیاز را با بهینه‌سازی هزینه فراهم کنند. Autoscaling توسط Node _autoscalerها_ انجام می‌شود.

Node provisioning

اگر Podهایی در یک cluster وجود داشته باشند که نتوانند روی Nodeهای موجود scheduled شوند،‏ Nodeهای جدید می‌توانند به‌طور خودکار برای پذیرفتن آن Podها به cluster اضافه شوند — این را provisioning می‌نامند. این به‌ویژه زمانی مفید است که تعداد Podها با زمان تغییر کند،‏ برای مثال در نتیجه‌ی ترکیب horizontal workload autoscaling با Node autoscaling.

Autoscalerها Nodeها را با ساختن و حذف کردن resourceهای cloud provider پشت آن‌ها provision می‌کنند. رایج‌ترین حالت این است که resourceهای پشت Node،‏ Virtual Machine باشند.

هدف اصلی provisioning این است که همه‌ی Podها schedulable شوند. این هدف همیشه قابل‌دستیابی نیست،‏ به دلایل مختلفی از جمله رسیدن به محدودیت‌های provisioning پیکربندی‌شده،‏ ناسازگاری پیکربندی provisioning با مجموعه‌ای خاص از Podها،‏ یا کمبود ظرفیت cloud provider. در حین provisioning،‏ Node autoscalerها اغلب سعی می‌کنند اهداف اضافی را نیز برآورده کنند (برای مثال کمینه کردن هزینه‌ی Nodeهای provision‌شده یا توازن تعداد Nodeها بین failure domainها).

دو ورودی اصلی برای یک Node autoscaler هنگام تعیین Nodeهایی که باید provision شوند وجود دارد: محدودیت‌های scheduling Pod و محدودیت‌های Node تحمیل‌شده توسط پیکربندی autoscaler.

پیکربندی autoscaler همچنین ممکن است شامل triggerهای دیگری برای provisioning Node باشد (برای مثال کاهش تعداد Nodeها به زیر یک حداقل پیکربندی‌شده).

Provisioning پیش‌تر در Cluster Autoscaler با نام scale-up شناخته می‌شد.

محدودیت‌های scheduling برای Pod (Pod scheduling constraints)

Podها می‌توانند محدودیت‌های scheduling را بیان کنند تا محدودیت‌هایی درباره‌ی نوع Nodeهایی که می‌توانند روی آن‌ها scheduled شوند اعمال کنند. Node autoscalerها این محدودیت‌ها را در نظر می‌گیرند تا اطمینان دهند Podهای pending می‌توانند روی Nodeهای provision‌شده scheduled شوند.

رایج‌ترین نوع محدودیت‌های scheduling،‏ resource requestهای مشخص‌شده توسط containerهای Pod هستند. autoscalerها اطمینان می‌دهند Nodeهای provision‌شده resource کافی برای برآورده کردن آن requestها دارند. با این حال،‏ مصرف واقعی resource Podها را پس از اجرا مستقیما در نظر نمی‌گیرند. برای autoscale کردن Nodeها بر اساس مصرف واقعی resource workload،‏ می‌توانید horizontal workload autoscaling را با Node autoscaling ترکیب کنید.

سایر محدودیت‌های رایج scheduling Pod شامل Node affinity،‏ inter-Pod affinity،‏ یا نیازمندی برای یک storage volume خاص است.

محدودیت‌های Node تحمیل‌شده توسط پیکربندی autoscaler (Node constraints imposed by autoscaler configuration)

جزئیات Nodeهای provision‌شده (برای مثال مقدار resource،‏ وجود یک label خاص) به پیکربندی autoscaler بستگی دارد. autoscalerها می‌توانند آن‌ها را از یک مجموعه‌ی از پیش تعریف‌شده‌ی پیکربندی‌های Node انتخاب کنند،‏ یا از auto-provisioning استفاده کنند.

provisioning خودکار (Auto-provisioning)

Node auto-provisioning یک mode از provisioning است که در آن کاربر مجبور نیست به‌طور کامل جزئیات Nodeهایی که می‌توانند provision شوند را پیکربندی کند. در عوض،‏ autoscaler به‌صورت پویا پیکربندی Node را بر اساس Podهای pendingی که به آن‌ها واکنش نشان می‌دهد،‏ همراه با محدودیت‌های از پیش پیکربندی‌شده (برای مثال،‏ حداقل مقدار resource یا نیاز به یک label خاص) انتخاب می‌کند.

Node consolidation

ملاحظه‌ی اصلی هنگام اجرای یک cluster،‏ اطمینان از اجرای همه‌ی pod schedulable است،‏ در حالی که هزینه‌ی cluster تا حد ممکن پایین نگه داشته می‌شود. برای رسیدن به این هدف،‏ resource requestهای Podها باید تا حد ممکن از resourceهای Nodeها استفاده کنند. از این دیدگاه،‏ Node utilization کلی در یک cluster می‌تواند به‌عنوان یک proxy برای اینکه cluster چقدر مقرون‌به‌صرفه است استفاده شود.

نکته

تنظیم درست resource requestهای Podهای شما به‌اندازه‌ی بهینه‌سازی Node utilization برای مقرون‌به‌صرفه بودن کلی یک cluster اهمیت دارد. ترکیب Node autoscaling با vertical workload autoscaling می‌تواند به رسیدن به این هدف کمک کند.

Nodeهای cluster شما می‌توانند به‌طور خودکار consolidate شوند تا Node utilization کلی،‏ و در نتیجه مقرون‌به‌صرفگی cluster بهبود یابد. Consolidation از طریق حذف مجموعه‌ای از Nodeهای کم‌استفاده از cluster رخ می‌دهد. اختیاری،‏ می‌توان یک مجموعه‌ی متفاوت از Nodeها را برای جایگزینی آن‌ها provision کرد.

Consolidation،‏ مانند provisioning،‏ فقط resource requestهای Pod را در نظر می‌گیرد و نه مصرف واقعی resource،‏ هنگام تصمیم‌گیری.

برای اهداف consolidation،‏ یک Node خالی (empty) در نظر گرفته می‌شود اگر فقط Podهای DaemonSet و static روی آن در حال اجرا باشند. حذف Nodeهای خالی در طول consolidation ساده‌تر از Nodeهای غیرخالی است و autoscalerها اغلب بهینه‌سازی‌هایی مخصوص consolidate کردن Nodeهای خالی دارند.

حذف Nodeهای غیرخالی در طول consolidation مخرب است — Podهای در حال اجرا روی آن‌ها terminate می‌شوند و احتمالا باید دوباره ساخته شوند (برای مثال توسط یک Deployment). با این حال،‏ همه‌ی چنین Podهای دوباره‌ساخته‌شده‌ای باید بتوانند روی Nodeهای موجود در cluster،‏ یا Nodeهای جایگزینی که به‌عنوان بخشی از consolidation provision شده‌اند scheduled شوند. به‌طور معمول هیچ Podی نباید در نتیجه‌ی consolidation در وضعیت pending قرار بگیرد.

نکته

autoscalerها پیش‌بینی می‌کنند که یک Pod دوباره‌ساخته‌شده احتمالا پس از provision یا consolidate شدن یک Node چگونه scheduled می‌شود،‏ اما scheduling واقعی را کنترل نمی‌کنند. به همین دلیل،‏ برخی Podها ممکن است در نتیجه‌ی consolidation به وضعیت pending بروند — برای مثال اگر یک Pod کاملا جدید در حین انجام consolidation ظاهر شود.

پیکربندی autoscaler همچنین ممکن است trigger شدن consolidation توسط شرایط دیگری را فعال کند (برای مثال،‏ زمان سپری‌شده از زمان ساخت یک Node)،‏ به‌منظور بهینه‌سازی ویژگی‌های مختلف (برای مثال،‏ حداکثر طول عمر Nodeها در یک cluster).

جزئیات نحوه‌ی انجام consolidation به پیکربندی هر autoscaler بستگی دارد.

نکته

Consolidation پیش‌تر در Cluster Autoscaler با نام scale-down شناخته می‌شد.

Node autoscalerها (Autoscalers)

قابلیت‌های توصیف‌شده در بخش‌های قبل توسط Node autoscalerها فراهم می‌شوند. علاوه بر Kubernetes API،‏ autoscalerها همچنین باید با APIهای cloud provider تعامل داشته باشند تا Nodeها را provision و consolidate کنند. این یعنی باید به‌طور صریح با هر cloud provider پشتیبانی‌شده integrate شوند. عملکرد و مجموعه‌ی feature یک autoscaler خاص می‌تواند بین integrationهای مختلف cloud provider متفاوت باشد.

پیاده‌سازی‌های autoscaler (Autoscaler implementations)

Cluster Autoscaler و Karpenter دو Node autoscaler هستند که در حال حاضر توسط SIG Autoscaling حمایت می‌شوند.

از دیدگاه یک کاربر cluster،‏ هر دو autoscaler باید تجربه‌ی مشابهی از Node autoscaling ارائه دهند. هر دو برای Podهای unschedulable Nodeهای جدید provision می‌کنند و هر دو Nodeهایی که دیگر به‌طور بهینه استفاده نمی‌شوند را consolidate می‌کنند.

autoscalerهای مختلف ممکن است ویژگی‌هایی خارج از حیطه‌ی Node autoscaling توصیف‌شده در این صفحه هم فراهم کنند و آن ویژگی‌های اضافی ممکن است بین آن‌ها متفاوت باشد.

بخش‌های زیر و مستندات مرتبط با هر autoscaler را برای تصمیم‌گیری درباره‌ی اینکه کدام autoscaler با use case شما بهتر تناسب دارد بررسی کنید.

Cluster Autoscaler

Cluster Autoscaler Nodeها را به Node groupهای از پیش پیکربندی‌شده اضافه یا از آن‌ها حذف می‌کند. Node groupها معمولا به نوعی از resource group مربوط به cloud provider (رایج‌ترین حالت،‏ یک گروه Virtual Machine) نگاشت می‌شوند. یک نمونه‌ی منفرد از Cluster Autoscaler می‌تواند به‌طور هم‌زمان چند Node group را مدیریت کند. هنگام provisioning،‏ Cluster Autoscaler Nodeها را به گروهی که با requestهای Podهای pending بهترین تطابق را دارد اضافه می‌کند. هنگام consolidating،‏ Cluster Autoscaler همیشه Nodeهای خاصی را برای حذف انتخاب می‌کند،‏ برخلاف اینکه فقط resource group زیرین cloud provider را resize کند.

Karpenter

Karpenter بر اساس پیکربندی‌های NodePool که توسط اپراتور cluster فراهم می‌شود،‏ به‌طور خودکار Nodeها را provision می‌کند. Karpenter همه‌ی جنبه‌های lifecycle یک node را مدیریت می‌کند،‏ نه فقط autoscaling. این شامل تازه‌سازی خودکار Nodeها پس از رسیدن به یک عمر مشخص،‏ و auto-upgrade کردن Nodeها وقتی image جدید worker Node منتشر می‌شود،‏ است. Karpenter مستقیما با resourceهای منفرد cloud provider (رایج‌ترین حالت،‏ Virtual Machineهای منفرد) کار می‌کند و به resource groupهای cloud provider وابسته نیست.

مقایسه‌ی پیاده‌سازی (Implementation comparison)

تفاوت‌های اصلی بین Cluster Autoscaler و Karpenter:

  • Cluster Autoscaler ویژگی‌های مرتبط با فقط Node autoscaling را فراهم می‌کند. Karpenter دامنه‌ی وسیع‌تری دارد و ویژگی‌های مربوط به مدیریت کل lifecycle Node را نیز فراهم می‌کند (برای مثال،‏ استفاده از disruption برای auto-recreate کردن Nodeها پس از رسیدن به یک عمر مشخص،‏ یا auto-upgrade کردن آن‌ها به نسخه‌های جدید).
  • Cluster Autoscaler از auto-provisioning پشتیبانی نمی‌کند؛‏ Node groupهایی که می‌تواند از آن‌ها provision کند باید از پیش پیکربندی شده باشند. Karpenter از auto-provisioning پشتیبانی می‌کند،‏ پس کاربر فقط باید مجموعه‌ای از محدودیت‌ها برای Nodeهای provision‌شده پیکربندی کند،‏ به جای اینکه به‌طور کامل گروه‌های همگن را پیکربندی کند.
  • Cluster Autoscaler integrationهای cloud provider را مستقیما فراهم می‌کند،‏ یعنی این integrationها بخشی از پروژه‌ی کوبرنتیز هستند. برای Karpenter،‏ پروژه‌ی کوبرنتیز،‏ Karpenter را به‌عنوان یک library منتشر می‌کند که cloud providerها می‌توانند با آن integrate شوند تا یک Node autoscaler بسازند.
  • Cluster Autoscaler integration با تعداد زیادی cloud provider،‏ از جمله providerهای کوچک‌تر و کمترمعروف،‏ فراهم می‌کند. تعداد cloud providerهایی که با Karpenter integrate می‌شوند کمتر است،‏ از جمله AWS و Azure.

ترکیب workload و Node autoscaling (Combine workload and Node autoscaling)

ترکیب با horizontal workload autoscaling (Horizontal workload autoscaling)

Node autoscaling معمولا در پاسخ به Podها کار می‌کند — Nodeهای جدید برای پذیرفتن Podهای unschedulable provision می‌کند،‏ و سپس وقتی دیگر لازم نباشند،‏ Nodeها را consolidate می‌کند.

Horizontal workload autoscaling به‌طور خودکار تعداد replicaهای workload را برای نگه‌داشتن یک میانگین resource utilization مطلوب در همه‌ی replicaها scale می‌کند. به عبارت دیگر،‏ به‌طور خودکار Podهای جدید را در پاسخ به بار برنامه می‌سازد،‏ و سپس وقتی بار کاهش یابد،‏ آن Podها را حذف می‌کند.

می‌توانید از Node autoscaling همراه با horizontal workload autoscaling استفاده کنید تا Nodeهای cluster خود را بر اساس میانگین مصرف واقعی resource Podهای خود autoscale کنید.

اگر بار برنامه افزایش یابد،‏ میانگین utilization Podهای آن نیز باید افزایش یابد،‏ که workload autoscaling را وامی‌دارد Podهای جدید بسازد. Node autoscaling سپس باید Nodeهای جدیدی برای پذیرفتن آن Podهای جدید provision کند.

وقتی بار برنامه کاهش یابد،‏ workload autoscaling باید Podهای غیرضروری را حذف کند. Node autoscaling نیز،‏ به‌نوبه‌ی خود،‏ باید Nodeهایی که دیگر لازم نیستند را consolidate کند.

اگر به‌درستی پیکربندی شود،‏ این الگو تضمین می‌کند برنامه‌ی شما همیشه ظرفیت Node لازم برای مدیریت جهش‌های بار را دارد،‏ اما مجبور نیستید بابت آن ظرفیت وقتی لازم نیست هزینه بدهید.

ترکیب با vertical workload autoscaling (Vertical workload autoscaling)

هنگام استفاده از Node autoscaling،‏ تنظیم درست resource requestهای Pod اهمیت دارد. اگر requestهای یک Pod خاص خیلی کم باشند،‏ provision کردن یک Node جدید برای آن ممکن است کمکی نکند تا Pod واقعا اجرا شود. اگر requestهای یک Pod خاص خیلی زیاد باشند،‏ ممکن است به‌اشتباه از consolidate شدن Node آن جلوگیری کند.

Vertical workload autoscaling به‌طور خودکار resource requestهای Podهای شما را بر اساس مصرف تاریخی resource آن‌ها تنظیم می‌کند.

می‌توانید از Node autoscaling همراه با vertical workload autoscaling استفاده کنید تا resource requestهای Podهای خود را تنظیم کنید در حالی که قابلیت‌های Node autoscaling در cluster خود را حفظ می‌کنید.

هشدار

هنگام استفاده از Node autoscaling،‏ توصیه نمی‌شود vertical workload autoscaling را برای Podهای DaemonSet راه‌اندازی کنید. Autoscalerها باید پیش‌بینی کنند Podهای DaemonSet روی یک Node جدید چگونه خواهند بود تا resourceهای Node در دسترس را پیش‌بینی کنند. Vertical workload autoscaling ممکن است این پیش‌بینی‌ها را غیرقابل‌اعتماد کند و منجر به تصمیم‌های scaling نادرست شود.

این بخش componentهایی که قابلیت‌های مرتبط با Node autoscaling فراهم می‌کنند را توصیف می‌کند.

Descheduler

descheduler componentی است که قابلیت Node consolidation بر اساس policyهای سفارشی،‏ و همچنین سایر ویژگی‌های مرتبط با بهینه‌سازی Nodeها و Podها (برای مثال حذف Podهایی که مرتب restart می‌شوند) را فراهم می‌کند.

HPA کار خودش را انجام داده (عدد spec.replicas را بالا برده)،‏ اما نمی‌تواند ظرفیت تازه provision کند. Node autoscaler (Cluster Autoscaler یا Karpenter) این Podهای unschedulable را (با condition از نوع PodScheduled برابر False و reason برابر Unschedulable) می‌بیند و یک Node جدید provision می‌کند. اگر Node autoscaling فعال نباشد،‏ این Pod تا ابد در وضعیت Pending می‌ماند. این دقیقا همان نکته‌ای است که در بخش «مسیر کامل یک تصمیم HPA» ابتدای این فصل اشاره شد.

مطالب بیشتر: workload-level autoscaling (همین فصل).

تمرین‌های فصل ۱۰ ۲۱ تمرین
  1. مفهومیچرا نمی‌توان یک HorizontalPodAutoscaler را مستقیم به یک DaemonSet متصل کرد؟ چه فرقی بین Deployment/StatefulSet و DaemonSet از نظر subresource وجود دارد؟
    پاسخ

    HPA فقط روی resourceهایی کار می‌کند که یک subresource به نام scale دارند (رابطی که تعداد replicas را می‌توان از طریق آن خواند/نوشت).‏ Deployment،‏ ReplicaSet،‏ StatefulSet و ReplicationController این subresource را دارند. DaemonSet ندارد،‏ چون تعداد Podهای آن با تعداد Nodeهای واجد شرایط تعیین می‌شود،‏ نه یک field replicas مستقل. با kubectl get --raw /apis/apps/v1 | jq -r '.resources[].name' | grep /scale می‌توان این را تأیید کرد.

  2. مفهومیدر ستون TARGETS خروجی kubectl get hpa عددی مثل ۱۲۰٪ نشان داده می‌شود اما HPA به‌جای scale up تهاجمی،‏ محافظه‌کارانه scale up کرده است. چرا؟
    پاسخ

    مقدار نشان‌داده‌شده در status همیشه میانگین اصلی (بدون در نظر گرفتن Podهای not-yet-ready یا missing metric) است. اما الگوریتم واقعی scaling،‏ وقتی metric گم‌شده یا Pod not-yet-ready وجود داشته باشد،‏ محافظه‌کارانه فرض می‌کند آن Podها در حالت scale up فقط ۰٪ (و در scale down،‏ ۱۰۰٪) مصرف می‌کنند تا از over-reaction جلوگیری شود. به همین دلیل عدد نمایش‌داده‌شده و رفتار واقعی HPA می‌توانند متفاوت به‌نظر برسند.

  3. مفهومیتفاوت بین updateMode: "Recreate" و updateMode: "InPlace" در VPA چیست؟ چرا InPlace هرگز به eviction برنمی‌گردد؟
    پاسخ

    Recreate همیشه Pod را evict می‌کند و اجازه می‌دهد workload controller یک Pod جدید با resource توصیه‌شده بسازد. InPlace فقط از قابلیت in-place resize استفاده می‌کند و اگر resize قابل‌اجرا نباشد (مثلا کمبود ظرفیت Node)،‏ آن را به تعویق می‌اندازد و دوباره تلاش می‌کند،‏ بدون اینکه هرگز Pod را evict کند. این برای برنامه‌های حساس به restart (مثل stateful workloadها) مهم است،‏ چون آن‌ها ترجیح می‌دهند صبر کنند تا اینکه restart شوند و state از دست بدهند.

  4. مفهومیچرا نباید یک HPA و یک VPA (در mode غیر Off) هر دو روی همان resource یکسان (مثلا CPU) یک Deployment پیکربندی شوند؟
    پاسخ

    HPA بر اساس درصد utilization نسبت به requests.cpu تصمیم می‌گیرد. اگر VPA همزمان مقدار requests.cpu را تغییر دهد،‏ مخرج این نسبت عوض می‌شود بدون اینکه بار واقعی تغییر کرده باشد؛‏ نتیجه یک حلقه‌ی تداخل بین دو controller مستقل است (VPA درخواست را بالا می‌برد ⇐ درصد utilization HPA پایین می‌آید ⇐ HPA فکر می‌کند بار کم شده و replica کم می‌کند). راه‌حل: VPA را روی یک resource (مثلا فقط memory با controlledResources) بگذارید و HPA را روی resource دیگر (CPU)،‏ یا VPA را روی Off نگه دارید و فقط توصیه ببینید.

  5. مفهومی--horizontal-pod-autoscaler-cpu-initialization-period و --horizontal-pod-autoscaler-initial-readiness-delay چه مشکلی را حل می‌کنند و چه تفاوتی دارند؟
    پاسخ

    هر دو برای جلوگیری از تصمیم‌های scaling نادرست ناشی از Podهای تازه‌start‌شده هستند. cpu-initialization-period (پیش‌فرض ۵ دقیقه) یک پنجره پس از شروع Pod تعریف می‌کند که مصرف CPU در آن نادیده گرفته می‌شود مگر Pod به‌طور کامل و پایدار Ready بوده باشد؛‏ هدفش کنار گذاشتن CPU spike دوران warm-up (مثل JIT در برنامه‌های Java) است. initial-readiness-delay (پیش‌فرض ۳۰ ثانیه) دوره‌ی کوتاه‌تری است که در آن با Podهایی که Unready هستند،‏ حتی اگر لحظه‌ای Ready شده باشند،‏ به‌عنوان «هنوز در حال initialize» رفتار می‌شود؛‏ هدفش جلوگیری از لحاظ کردن Podهایی است که در startup سریع بین Ready/Unready نوسان می‌کنند.

  6. عملیروی یک Cluster kind یا minikube،‏ metrics-server را نصب کنید و با kubectl top nodes و kubectl top pods تأیید کنید که resource metrics در دسترس است.
    پاسخ

    در minikube: minikube addons enable metrics-server. در kind،‏ باید metrics-server را با --kubelet-insecure-tls نصب کنید،‏ چون kind از گواهی self-signed برای kubelet استفاده می‌کند:

kubectl top pods -A

    پاسخ

  8. عملییک HPA با autoscaling/v2 بسازید که هم CPU (utilization ۶۰٪) و هم memory (averageValue ۲۰۰Mi) را به‌عنوان metric داشته باشد. توضیح دهید HPA کدام یک را برای تصمیم نهایی استفاده می‌کند.
    پاسخ

    مثال manifest:

    hpa-multi.yaml
    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 60}}
  - type: Resource
    resource: {name: memory, target: {type: AverageValue, averageValue: 200Mi}}

    طبق بخش Scaling on multiple metrics،‏ controller برای هر metric جداگانه یک تعداد replica مطلوب محاسبه می‌کند و در نهایت بیشترین عدد پیشنهادی را انتخاب می‌کند (نه میانگین). یعنی اگر CPU بگوید ۴ replica کافی است ولی memory بگوید ۷ replica لازم است،‏ HPA به ۷ می‌رود.

  9. عملییک VPA با updateMode: "Off" برای یک Deployment با request خیلی کم بسازید و بعد از چند دقیقه kubectl describe vpa را اجرا کنید. توضیح دهید سه نوع مقدار توصیه‌شده (Target،‏ Lower Bound،‏ Upper Bound) به چه معناست.
    پاسخ

    Target مقدار توصیه‌شده برای مصرف عادی است (چیزی که admission controller در mode فعال استفاده می‌کند).‏ Lower Bound حداقل resource قابل‌اجرا (اگر request زیر این مقدار باشد،‏ ریسک throttling/OOM بالاست).‏ Upper Bound حداکثر resource معقول برای پوشش دادن peakها است. در mode Off هیچ‌کدام اعمال نمی‌شوند و فقط در .status.recommendation ذخیره می‌شوند.

  13. سناریوی Productionیک API با ۴ replica پشت یک HPA (minReplicas: 2،‏ maxReplicas: 20،‏ target CPU ۵۰٪) هر چند دقیقه بین ۴ و ۱۸ replica نوسان می‌کند و تیم on-call از cold start مکرر شکایت دارد. لاگ HPA و kubectl get hpa --watch نوسان سریع TARGET بین ۳۰٪ و ۸۰٪ را نشان می‌دهد که با burstهای کوتاه ۴۵ ثانیه‌ای ترافیک هماهنگ است. علت را تشخیص دهید و راهکار پیشنهاد دهید.
    پاسخ

    تشخیص: این الگوی کلاسیک flapping/thrashing است (بخش Stability of workload scale). چون behavior پیش‌فرض HPA برای scale down یک stabilization window ۵ دقیقه‌ای دارد اما برای scale up هیچ stabilization windowی ندارد،‏ هر burst کوتاه بلافاصله باعث scale up می‌شود.

    راه‌حل: یک behavior.scaleUp با stabilizationWindowSeconds کوچک اما غیرصفر (مثلا ۳۰-۶۰ ثانیه) و یک tolerance بزرگ‌تر (مثلا ۰.۱۵ به‌جای پیش‌فرض ۰.۱) تنظیم کنید تا نوسانات کوتاه فیلتر شوند،‏ و یک policy با type: Pods برای محدود کردن نرخ افزایش replica در هر iteration اضافه کنید:

    fix.yaml
    behavior:
  scaleUp:
    stabilizationWindowSeconds: 45
    tolerance: 0.15
    policies:
    - type: Pods
      value: 3
      periodSeconds: 60
  scaleDown:
    stabilizationWindowSeconds: 300

    پیشگیری: روی dashboard مانیتورینگ،‏ نرخ تغییر REPLICAS در طول زمان را رصد کنید (alert روی بیش از N تغییر در ساعت)؛‏ در طراحی اولیه از الگوریتم قسمت Algorithm details استفاده کنید تا بفهمید چرا HPA بدون tolerance مناسب به هر جهش کوچک واکنش نشان می‌دهد.

  14. سناریوی Productionیک تیم HPA را روی یک Deployment با target CPU ۸۰٪ پیکربندی کرده،‏ اما هیچ‌کدام از containerهای Pod آن resources.requests.cpu تنظیم نشده. بعد از یک هفته متوجه می‌شوند که با وجود بار بالا،‏ HPA هیچ‌وقت scale up نکرده. علت را با استفاده از مستندات پیدا کنید.
    پاسخ

    طبق بخش How does a HorizontalPodAutoscaler work?: «لطفا توجه کنید که اگر برای برخی از containerهای Pod،‏ resource request مربوطه تنظیم نشده باشد،‏ CPU utilization آن Pod تعریف‌نشده خواهد بود و autoscaler هیچ اقدامی برای آن metric انجام نخواهد داد.» یعنی چون requests.cpu تنظیم نشده،‏ درصد utilization اصلا قابل‌محاسبه نیست و HPA ساکت می‌ماند (در kubectl get hpa ستون TARGETS مقدار <unknown> نشان می‌دهد و kubectl describe hpa condition با نام ScalingActive را False با پیامی درباره‌ی نبود request برای cpu نشان می‌دهد).

    راه‌حل: resources.requests.cpu را برای همه‌ی containerهای هدف تنظیم کنید (طبق فصل ۶،‏ Configuration و Policies،‏ شاید با یک LimitRange پیش‌فرض هم این ریسک را کاهش دهید). پیشگیری: یک admission policy (مثل Kyverno یا OPA Gatekeeper) اضافه کنید که ساخت هر Deployment بدون resources.requests را رد کند.

  15. سناریوی Productionیک StatefulSet برای Kafka با ۶ broker در حال اجراست. یک مهندس junior برای «صرفه‌جویی هزینه» یک HPA با minReplicas: 3, maxReplicas: 6 روی این StatefulSet تنظیم می‌کند. طی یک scale down شبانه،‏ cluster Kafka بعد از حذف دو broker دچار under-replicated partitions می‌شود. توضیح دهید چرا این طراحی اشتباه بود و چه جایگزینی مطابق مستندات مناسب‌تر است.
    پاسخ

    مشکل این است که HPA فقط عدد replicas را عوض می‌کند و هیچ آگاهی از state پایگاه‌داده/message broker ندارد. برای StatefulSetهای stateful توزیع‌شده (مثل Kafka)،‏ حذف یک replica یعنی از دست دادن یک broker که ممکن است partition leader داشته باشد؛‏ replication و rebalance باید به‌صورت کنترل‌شده در سطح برنامه انجام شود،‏ نه به‌صورت خودکار توسط یک controller عمومی مثل HPA که فقط CPU/memory را می‌بیند.

    طبق بخش Troubleshooting در Scale a StatefulSet: «بهتر است در سطح برنامه درباره‌ی عملیات scaling استدلال کنید،‏ و scaling را فقط زمانی انجام دهید که مطمئن باشید cluster کاملا سالم است.» راه‌حل درست: حذف HPA از روی این StatefulSet،‏ و اگر لازم است scale کاهش یابد،‏ این کار را دستی و با هماهنگی broker rebalance (drain کردن partitionهای broker مورد نظر پیش از کاهش replica) انجام دهید.

  16. سناریوی Productionدر یک Cluster ۵ نودی با Cluster Autoscaler فعال،‏ تیم متوجه شده Nodeهای جدید هرگز provision نمی‌شوند حتی وقتی چند Pod ساعت‌ها در وضعیت Pending می‌مانند. kubectl describe pod می‌گوید 0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector. علت را تحلیل کنید.
    پاسخ

    طبق بخش Pod scheduling constraints:‏ Node autoscalerها محدودیت‌های scheduling Pod (از جمله Node affinity) را در نظر می‌گیرند تا مطمئن شوند Podهای pending می‌توانند روی Nodeهای provision‌شده اجرا شوند. اگر پیکربندی Node group/NodePool موجود هیچ Nodeی با label مطابق آن affinity نسازد (auto-provisioning غیرفعال یا محدودیت‌های آن با affinity سازگار نیست)،‏ Cluster Autoscaler اصلا تصمیم به provision کردن نمی‌گیرد،‏ چون هیچ Node groupی وجود ندارد که با پیش‌بینی،‏ این Pod را schedulable کند.

    راه‌حل: یا یک Node group جدید با label/taint مطابق آن affinity برای Cluster Autoscaler تعریف کنید،‏ یا (اگر می‌خواهید auto-provisioning واقعی داشته باشید) به Karpenter مهاجرت کنید که طبق بخش Auto-provisioning می‌تواند پیکربندی Node را به‌صورت پویا بر اساس محدودیت‌های Pod انتخاب کند. پیشگیری: alert روی Podهای Pending با سن بیش از N دقیقه،‏ و بررسی دوره‌ای مطابقت Node group labelها با nodeSelector/affinityهای رایج در cluster.

    پاسخ

    طبق بخش Autoscale the DNS Service in a Cluster،‏ این دقیقا use caseی است که cluster-proportional-autoscaler برای آن طراحی شده: تعداد replicaهای CoreDNS باید متناسب با تعداد Node/core Cluster scale شود،‏ نه ثابت بماند. ابتدا با kubectl get deployment --namespace=kube-system بررسی کنید kube-dns-autoscaler وجود دارد یا نه؛‏ چون در این سناریو وجود ندارد (Deployment ثابت روی ۲ مانده)،‏ باید manifest رسمی dns-horizontal-autoscaler.yaml را با --target=Deployment/coredns اعمال کنید.

    تنظیم پارامتر: با توجه به فرمول replicas = max(ceil(cores/coresPerReplica), ceil(nodes/nodesPerReplica))،‏ برای ۲۰۰ Node و nodesPerReplica=16 پیش‌فرض،‏ حداقل ۱۳ replica پیشنهاد می‌شود که خیلی بیشتر از ۲ فعلی است. پیشگیری: بعد از فعال‌سازی،‏ ConfigMap kube-dns-autoscaler را متناسب با اندازه‌ی معمول Cluster (مثلا کاهش nodesPerReplica اگر latency هنوز بالاست) دوباره تنظیم کنید و آن را در runbook مربوط به scale کردن clusterهای بزرگ مستند کنید.

  18. سناریوی Productionیک برنامه‌ی Spring Boot با HPA بر اساس CPU (target ۶۰٪) هنگام هر rolling update دچار یک «scale up توهمی» موقت می‌شود: با هر deploy جدید،‏ تعداد replica به‌طور غیرمنتظره تا سقف maxReplicas می‌رود و چند دقیقه بعد خودش پایین می‌آید. توضیح دهید چرا و راهکار بدهید.
    پاسخ

    در طول warm-up (JIT compilation،‏ class loading،‏ cache warming)،‏ برنامه‌های JVM موقتا مصرف CPU بسیار بالایی دارند. اگر readinessProbe بلافاصله بعد از باز شدن پورت pass شود،‏ HPA این مصرف warm-up را به‌عنوان بار واقعی می‌بیند و scale up می‌کند؛‏ چون Podهای تازه هم در حال warm-up هستند،‏ مشکل تشدید می‌شود.

    راه‌حل طبق بخش Good practice for pod readiness: یک startupProbe اضافه کنید که تا پایان warm-up (مثلا یک endpoint /actuator/health/warmup) pass نشود،‏ تا مصرف CPU این دوره طبق قاعده‌ی cpu-initialization-period نادیده گرفته شود؛‏ نمونه‌ی کامل YAML در آزمایش عملی بخش Pod readiness and autoscaling metrics همین فصل آمده است. اگر warm-up بیش از ۵ دقیقه (پیش‌فرض cpu-initialization-period) طول می‌کشد،‏ مدیر cluster باید این flag را روی kube-controller-manager افزایش دهد.

  19. سناریوی Productionیک تیم متوجه می‌شود resource request Podهای یک workload به‌طور مداوم بیش از حد بزرگ است (over-provisioned) و هزینه‌ی cluster را بالا نگه داشته،‏ اما نمی‌خواهند بدون بررسی،‏ به‌طور خودکار و ناگهانی resourceها کاهش یابند چون این workload به eviction حساس است. چه پیکربندی VPA پیشنهاد می‌کنید؟
    پاسخ

    ترکیب دو مرحله: ابتدا VPA را با updateMode: "Off" برای مدتی (مثلا ۱-۲ هفته) اجرا کنید تا توصیه‌ها در .status.recommendation جمع شوند،‏ بدون هیچ اعمال خودکار. تیم این توصیه‌ها را با kubectl describe vpa بررسی و تأیید می‌کند. سپس،‏ به‌جای Recreate (که eviction تهاجمی دارد)،‏ به InPlaceOrRecreate یا InPlace سوییچ کنید (in-place resize در v1.37 همیشه فعال است،‏ ولی حالت InPlace در خود VPA هنوز alpha است) تا اکثر resizeها بدون eviction انجام شوند. همچنین resourcePolicy.containerPolicies[].minAllowed/maxAllowed را طبق بخش Resource policies تنظیم کنید تا VPA هرگز پایین‌تر از یک کف امن نرود.

  20. سناریوی Productionیک worker queue-processor باید فقط زمانی که پیام در صف باشد Pod داشته باشد و در زمان idle هیچ Podی اجرا نکند (برای صرفه‌جویی در هزینه‌ی instanceهای GPU). چگونه طبق مستندات این HPA را پیکربندی می‌کنید و چه محدودیتی وجود دارد؟
    پاسخ

    باید از قابلیت Scaling to and from zero استفاده کنید: spec.minReplicas: 0 را با یک external یا object metric ترکیب کنید (مثلا queue_messages_ready). محدودیت مهم مستندات: scale-to-zero فقط برای metric نوع object یا external پشتیبانی می‌شود،‏ برای resource metric مثل CPU/memory در دسترس نیست (چون آن‌ها فقط روی Pod در حال اجرا قابل‌اندازه‌گیری هستند).‏ API server،‏ هر HPA با minReplicas: 0 که هیچ metric object/external نداشته باشد را رد می‌کند.

    hpa-scale-to-zero.yaml
    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: queue-worker
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: queue-worker}
  minReplicas: 0
  maxReplicas: 5
  metrics:
  - type: External
    external:
      metric: {name: queue_messages_ready, selector: {matchLabels: {queue: "gpu_jobs"}}}
      target: {type: AverageValue, averageValue: "10"}

    feature gate با نام HPAScaleToZero باید هم روی kube-apiserver و هم روی kube-controller-manager فعال باشد؛‏ در v1.37 در مرحله‌ی beta است و به‌طور پیش‌فرض فعال است. وضعیت ScaledToZero=True در status نشان می‌دهد HPA خودش این workload را به صفر رسانده (نه یک deactivation دستی).

  21. سناریوی Productionپس از فعال‌سازی HPA روی یک Deployment قدیمی که در manifest آن spec.replicas: 10 نوشته شده بود،‏ تیم DevOps با اجرای pipeline CI/CD (که همیشه kubectl apply -f deployment.yaml اجرا می‌کند) متوجه شد که هر بار deploy،‏ replicaها موقتا به ۱۰ می‌پرند و بعد HPA دوباره آن‌ها را به مقدار درست برمی‌گرداند و باعث یک نوسان بی‌مورد می‌شود. توضیح دهید چرا و راه‌حل رسمی چیست.
    پاسخ

    این دقیقا سناریوی بخش Migrating Deployments and StatefulSets to horizontal autoscaling است. وقتی HPA فعال است اما spec.replicas هنوز در manifest نوشته شده،‏ هر kubectl apply مقدار replica را به همان عدد نوشته‌شده در فایل (۱۰) برمی‌گرداند،‏ حتی اگر HPA آن را قبلا به عدد دیگری تنظیم کرده بود؛‏ این باعث thrashing/flapping می‌شود.

    راه‌حل: field spec.replicas باید از manifest حذف شود. با روش Client Side Apply مستندات: ابتدا kubectl apply edit-last-applied deployment/<name> و حذف spec.replicas از آن (بدون تغییر Pod count در این مرحله)،‏ سپس حذف همان field از فایل manifest در git،‏ و commit کردن. از این پس kubectl apply -f deployment.yaml دیگر تعداد replica را override نمی‌کند. اگر از Server-Side Apply استفاده می‌شود،‏ باید از روال transferring ownership استفاده شود.

سؤال‌های مصاحبه‌ی فصل ۱۰ ۱۲ سؤال · پاسخ کوتاه و دقیق،‏ همان‌طور که در جلسه‌ی مصاحبه باید گفت
  1. پایهHorizontalPodAutoscaler چطور کار می‌کند و هر چند وقت تصمیم می‌گیرد؟
    پاسخ

    HPA یک control loop درون kube-controller-manager است که به‌طور پیش‌فرض هر ۱۵ ثانیه (--horizontal-pod-autoscaler-sync-period) اجرا می‌شود. metricها را از metrics.k8s.io یا APIهای custom و external می‌خواند،‏ تعداد مطلوب را با ceil(currentReplicas × current / desired) حساب می‌کند،‏ اگر نسبت در محدوده‌ی tolerance (پیش‌فرض ۱۰٪) باشد کاری نمی‌کند،‏ و نتیجه را بین minReplicas و maxReplicas روی subresource به نام scale می‌نویسد.

    نکته‌ی امتیازآور: HPA خودش Pod نمی‌سازد؛‏ فقط spec.replicas را عوض می‌کند و ساختن Pod کار Deployment و ReplicaSet است.

  2. پایهHPA،‏ VPA و Node autoscaler هر کدام چه چیزی را scale می‌کنند؟
    پاسخ

    HPA تعداد replicaهای یک workload را تغییر می‌دهد و جزو core API است. VPA مقدار requests و limitهای containerها را تنظیم می‌کند و add-on جداگانه است. Node autoscaler (Cluster Autoscaler یا Karpenter) Node اضافه یا حذف می‌کند. در production معمولاً هر سه با هم کار می‌کنند: VPA برای اندازه‌ی درست هر Pod،‏ HPA برای تعداد Pod و Node autoscaler برای ظرفیت زیرساخت.

  3. پایهچرا HPA روی CPU برای Podی که requests.cpu ندارد کار نمی‌کند؟
    پاسخ

    utilization نسبت مصرف به request است؛‏ بدون request این درصد تعریف نمی‌شود و autoscaler برای آن metric هیچ اقدامی نمی‌کند. در kubectl describe hpa condition با نام ScalingActive برابر False است و پیام به نبود request اشاره می‌کند.

    نکته‌ی امتیازآور: utilization نسبت به request حساب می‌شود،‏ نه limit. برای الزام request می‌توان از LimitRange یا admission policy استفاده کرد.

  4. متوسطیک Deployment چهار replica دارد،‏ target برابر ۵۰٪ است و میانگین utilization به ۸۰٪ رسیده. HPA چند replica می‌خواهد؟
    پاسخ

    نسبت ۸۰ به ۵۰ برابر ۱٫۶ است و از tolerance بیرون است؛‏ ceil(4 × 1.6) = ceil(6.4) = 7. اگر Podی metric نداشته باشد یا هنوز Ready نشده باشد،‏ controller برای scale up مصرف آن را صفر فرض می‌کند و عدد نهایی کمتر می‌شود؛‏ ستون TARGETS اما همان میانگین اصلی را نشان می‌دهد.

  5. متوسطچرا scale up سریع است ولی scale down چند دقیقه طول می‌کشد؟
    پاسخ

    در behavior پیش‌فرض،‏ scale down یک stabilization window برابر ۳۰۰ ثانیه دارد: controller بیشترین پیشنهاد پنج دقیقه‌ی اخیر را برمی‌دارد تا با افت لحظه‌ای بار Podها حذف نشوند. scale up پنجره ندارد و هر ۱۵ ثانیه تا ۱۰۰٪ یا ۴ Pod (هر کدام بیشتر بود) اضافه می‌کند.

    نکته‌ی امتیازآور: این مقدارها با behavior.scaleUp و behavior.scaleDown در autoscaling/v2 قابل تغییرند.

  6. متوسطHPA مدام بین تعداد کم و زیاد replica نوسان می‌کند (flapping). چه ابزارهایی دارید؟
    پاسخ

    (۱) stabilization window برای جهت مشکل‌دار؛‏ (۲) policyهای Pods یا Percent همراه با selectPolicy برای محدود کردن سرعت تغییر؛‏ (۳) tolerance جداگانه برای scale up و scale down؛‏ (۴) readiness درست و startupProbe تا مصرف CPU دوره‌ی warm-up شمرده نشود.

    نکته‌ی امتیازآور: اگر manifest در CI مقدار spec.replicas دارد،‏ هر deploy هم نوسان می‌سازد؛‏ این field را از manifest حذف کنید.

  7. متوسطآیا می‌توان HPA و VPA را روی یک Deployment با هم استفاده کرد؟
    پاسخ

    روی یک resource مشترک (مثلاً CPU) نه: VPA مقدار request را عوض می‌کند،‏ مخرج utilization در HPA تغییر می‌کند و دو controller بی‌آن‌که بار واقعی عوض شده باشد با هم درگیر می‌شوند. راه رایج: HPA روی CPU یا یک custom metric و VPA فقط روی memory با controlledResources،‏ یا VPA در حالت Off فقط برای دیدن توصیه.

  8. متوسطmetrics-server چه می‌دهد و چه نمی‌دهد؟
    پاسخ

    metrics-server هر Node را به‌طور دوره‌ای (پیش‌فرض ۱۵ ثانیه) از راه /metrics/resource در kubelet poll می‌کند و مصرف لحظه‌ای CPU و memory را از راه aggregation layer با API metrics.k8s.io در اختیار HPA،‏ VPA و kubectl top می‌گذارد. تاریخچه ندارد،‏ در etcd ذخیره نمی‌کند و metric برنامه (مثل request در ثانیه) نمی‌دهد؛‏ برای آن به یک adapter برای custom.metrics.k8s.io یا external.metrics.k8s.io نیاز دارید.

  9. متوسطچطور یک worker را بر اساس طول صف scale می‌کنید و آیا می‌تواند به صفر برسد؟
    پاسخ

    با metric از نوع External (یا Object) و target از نوع AverageValue،‏ مثلاً یک worker به ازای هر ۳۰ پیام. در v1.37 با minReplicas: 0 هم ممکن است،‏ چون HPAScaleToZero در مرحله‌ی beta و به‌طور پیش‌فرض فعال است؛‏ این فقط با metric از نوع object یا external کار می‌کند. ابزار رایج دیگر KEDA است که همین الگو را با scalerهای آماده فراهم می‌کند.

  10. پیشرفتهin-place Pod resize چیست و چه محدودیت‌هایی دارد؟
    پاسخ

    از v1.35 stable است: CPU و memory یک container در حال اجرا با subresource به نام resize (مثلاً kubectl patch --subresource resize) بدون ساختن Pod تازه تغییر می‌کند. resizePolicy برای هر resource تعیین می‌کند container restart شود یا نه. اگر Node جا نداشته باشد،‏ condition با نام PodResizePending و reason برابر Deferred یا Infeasible ثبت می‌شود.

    نکته‌ی امتیازآور: QoS class با resize عوض نمی‌شود،‏ فقط CPU و memory قابل resize است و Podهای Windows پشتیبانی نمی‌شوند.

  11. پیشرفتهCluster Autoscaler بر چه اساسی Node اضافه یا حذف می‌کند؟
    پاسخ

    Node تازه وقتی provision می‌شود که Podی unschedulable باشد و یک Node group بتواند آن را با در نظر گرفتن requests،‏ affinity،‏ taint و volume جا دهد. حذف (consolidation) هم بر اساس requests است،‏ نه مصرف واقعی: Node کم‌استفاده حذف می‌شود اگر Podهایش جای دیگری جا شوند. Cluster Autoscaler فقط Node groupهای از پیش تعریف‌شده را scale می‌کند؛‏ Karpenter با auto-provisioning نوع Node را از روی محدودیت‌های Pod انتخاب می‌کند.

    نکته‌ی امتیازآور: Podی که affinity آن با هیچ Node group سازگار نیست،‏ Node تازه نمی‌گیرد و برای همیشه Pending می‌ماند.

  12. پیشرفتهبعد از فعال کردن HPA،‏ با هر deploy از CI تعداد replica به عدد manifest برمی‌گردد. چرا و چطور درستش می‌کنید؟
    پاسخ

    manifest هنوز spec.replicas دارد و هر kubectl apply آن را بازنویسی می‌کند. باید field را از manifest حذف کرد. اگر مستقیم حذف کنید،‏ apply مقدار را به پیش‌فرض ۱ برمی‌گرداند؛‏ پس با Client Side Apply اول kubectl apply edit-last-applied را اجرا کنید و field را از last-applied حذف کنید،‏ و با Server-Side Apply مالکیت field را به HPA منتقل کنید.

خلاصه‌ی فصل ۱۰ در یک نگاه برای مرور سریع؛‏ جزئیات در متن فصل

ایده‌ی محوری: autoscaling سه لایه دارد؛‏ HPA تعداد Pod را،‏ VPA و in-place resize اندازه‌ی Pod را و Node autoscaler ظرفیت cluster را با تقاضا هماهنگ می‌کنند و همه بر پایه‌ی requests تصمیم می‌گیرند.

۱. انواع scaling
  • دستی: فرمان kubectl scale برای تعداد و patch کردن resources برای اندازه.
  • افقی و عمودی: تعداد replica در برابر resource هر Pod.
  • اندازه‌ی cluster: پروژه‌های Cluster Proportional Autoscaler و نسخه‌ی vertical آن.
  • event و زمان‌بندی: پروژه‌ی KEDA و scaler از نوع Cron.
  • دام: برای DaemonSet هیچ subresource به نام scale وجود ندارد و HPA روی آن کار نمی‌کند.
۲. الگوریتم HPA
  1. هر ۱۵ ثانیه scaleTargetRef و selector آن خوانده می‌شود.
  2. مصرف Podها از metrics API نسبت به request حساب می‌شود.
  3. فرمول ceil(current × metric / target) با tolerance ده درصد.
  4. با چند metric،‏ بیشترین پیشنهاد برنده است.
  5. نتیجه بین minReplicas و maxReplicas روی subresource از نوع scale نوشته می‌شود.
  • دام: برای Pod بدون metric یا هنوز Ready نشده،‏ در scale up صفر و در scale down صد درصد فرض می‌شود؛‏ ستون TARGETS همان میانگین خام است.
  • دام: بدون requests.cpu هیچ scaling بر پایه‌ی utilization انجام نمی‌شود.
۳. readiness و warm-up
  • cpu-initialization-period: مقدار پیش‌فرض ۵ دقیقه؛‏ CPU پیش از Ready پایدار شمرده نمی‌شود.
  • initial-readiness-delay: مقدار پیش‌فرض ۳۰ ثانیه برای Podهای نوسانی.
  • راه‌حل: یک startupProbe که تا پایان warm-up موفق نشود.
۴. behavior و flapping
  • policy: نوع Pods یا Percent با periodSeconds تا ۱۸۰۰؛‏ گزینه‌ی selectPolicy با مقدار Max یا Min یا Disabled.
  • stabilization window: بیشترین پیشنهاد در پنجره؛‏ پیش‌فرض ۳۰۰ ثانیه برای scale down و صفر برای scale up.
  • tolerance: قابل تنظیم برای هر جهت؛‏ در v1.37 stable.
  • پیش‌فرض scale up: حداکثر ۱۰۰٪ یا ۴ Pod در هر ۱۵ ثانیه،‏ هر کدام بیشتر.

۶. صفر replica و مهاجرت
  • scale to zero: در v1.37 beta و پیش‌فرض فعال؛‏ فقط با metric از نوع object یا external؛‏ condition با نام ScaledToZero.

  • مهاجرت: حذف spec.replicas از manifest با edit-last-applied یا انتقال مالکیت در SSA.
۷. VPA
  • componentها: مؤلفه‌های recommender و updater و admission webhook.
  • توصیه: مقادیر Target و Lower Bound و Upper Bound در status.recommendation.
  • modeها: حالت‌های Off و Initial و Recreate و InPlaceOrRecreate و InPlace؛‏ حالت Auto منسوخ و همان Recreate است.
  • resourcePolicy: فیلدهای minAllowed و maxAllowed و controlledResources و controlledValues.
  • دام: اگر HPA و VPA روی یک resource تنظیم شوند،‏ با هم درگیر می‌شوند.
۸. resource metrics pipeline
  1. آمار cgroup توسط cAdvisor در kubelet خوانده می‌شود.
  2. مسیر /metrics/resource در kubelet آن را expose می‌کند.
  3. metrics-server هر ۱۵ ثانیه poll می‌کند و فقط در حافظه نگه می‌دارد.
  4. درخواست به metrics.k8s.io از راه aggregation layer به metrics-server می‌رسد.
  • واحدها: مقدار CPU به‌صورت rate و memory به‌صورت working set.
  • دام: HPA هنوز از نسخه‌ی v1beta1 در metrics.k8s.io استفاده می‌کند.
۹. in-place resize
  • سازوکار: subresource با نام resize؛‏ kubectl از v1.32.
  • resizePolicy: مقدار NotRequired یا RestartContainer برای هر resource.
  • وضعیت: condition با نام PodResizePending (Deferred یا Infeasible) و PodResizeInProgress.
  • دام: مقدار QoS class ثابت می‌ماند؛‏ فقط CPU و memory؛‏ Windows پشتیبانی نمی‌شود.
۱۰. StatefulSet و DNS
  • StatefulSet: با Pod ناسالم scale down انجام نمی‌شود؛‏ برای پایگاه‌داده scale دستی و هماهنگ.
  • DNS: پروژه‌ی cluster-proportional-autoscaler با الگوی linear یا ladder از روی تعداد Node و core.
۱۱. Node autoscaling
  • provisioning: بر پایه‌ی Podهای unschedulable و requests،‏ نه مصرف واقعی.
  • consolidation: حذف Nodeهای کم‌استفاده وقتی Podهایشان جای دیگری جا شوند.
  • پیاده‌سازی‌ها: Cluster Autoscaler با Node groupهای از پیش تعریف‌شده؛‏ Karpenter با auto-provisioning و مدیریت lifecycle.
  • دام: اجرای VPA روی Podهای DaemonSet پیش‌بینی Node autoscaler را خراب می‌کند.
  • دام: بدون Node autoscaler،‏ HPA فقط Podهای Pending اضافه می‌کند.

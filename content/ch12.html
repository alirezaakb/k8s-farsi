مرجع: architecture · nodes · control-plane-node-communication · controller · leases · cloud-controller · cgroups · self-healing · garbage-collection · mixed-version-proxy · node-shutdown · coordinated-leader-election · node-status · swap-memory-management

در فصل ۱ دیدیم کوبرنتیز «چه کاری» می‌کند؛‏ این فصل نشان می‌دهد «چطور». سازوکار درونی کوبرنتیز را بررسی می‌کنیم و به این سؤال‌ها پاسخ می‌دهیم: cluster از چه اجزایی ساخته شده؟ Nodeها چطور ثبت و پایش (monitoring) می‌شوند؟ control plane (اجزای مدیریتی cluster که تصمیم‌ها را می‌گیرند و وضعیت را نگه می‌دارند) چطور با Nodeها ارتباط برقرار می‌کند؟ controllerها با چه الگویی current state (وضعیتی که سیستم در این لحظه واقعاً دارد) را به desired state (وضعیتی که کاربر اعلام می‌کند می‌خواهد) نزدیک می‌کنند؟ Leaseها در heartbeat (سیگنال زنده‌بودن) Nodeها و leader election چه نقشی دارند؟ cloud-controller-manager چه می‌کند؟ cgroup v1 و v2 چه فرقی دارند؟ self-healing (جایگزینی خودکار اجزای از کارافتاده) و garbage collection (پاک‌سازی خودکار اشیایی که دیگر لازم نیستند یا مالک ندارند) را دقیقاً کدام اجزا انجام می‌دهند؟ و وقتی یک Node مرتب یا ناگهانی خاموش می‌شود چه اتفاقی می‌افتد؟

در هر بخش اول محتوای مستندات رسمی به زبان ساده آمده،‏ بعد توضیح تکمیلی،‏ آزمایش عملی و مثال‌هایی از production. این فصل پایه‌ی تقریباً همه‌ی سؤال‌های «معماری» در مصاحبه‌هاست؛‏ پس با حوصله بخوانید.

ماجرای این فصل: وقتی خود cluster جواب نمی‌دهد

بخش سوم جزوه از این‌جا شروع می‌شود: فروشگاه بزرگ شده و به production واقعی می‌رود. یک شب ساعت ۳ بامداد،‏ kubectl به هیچ دستوری جواب نداد،‏ Podهای موجود همچنان کار می‌کردند،‏ اما هیچ انتشار و scaleی انجام نمی‌شد و تیم نمی‌دانست کدام جزء مقصر است. در k3s همه‌ی اجزای control plane داخل یک process هستند و دیده نمی‌شوند؛‏ از این فصل با clusterی کار می‌کنیم که مثل kubeadm هر جزء control plane را جدا و به شکل static Pod اجرا می‌کند تا هر جزء را جدا ببینیم؛‏ برای آزمایش‌های این فصل kind کافی است و ساختن cluster واقعی با kubeadm در فصل ۱۳ می‌آید.

معماری cluster (Cluster Architecture)

هر cluster کوبرنتیز از یک control plane و مجموعه‌ای از ماشین‌های کارگر به نام Node تشکیل شده که برنامه‌های containerی را اجرا می‌کنند. هر cluster برای اجرای Pod دست‌کم به یک worker Node نیاز دارد.

worker Nodeها host Podهایی هستند که اجزای برنامه را تشکیل می‌دهند،‏ و control plane این Nodeها و Podهای درون cluster را مدیریت می‌کند. در production،‏ control plane معمولاً روی چند کامپیوتر اجرا می‌شود و cluster هم چندین Node دارد؛‏ این‌طوری سیستم در برابر خرابی مقاوم (fault-tolerant) و همیشه در دسترس (highly available) می‌ماند.

شکل ۱۲-۱ یک معماری مرجع نمونه را نشان می‌دهد. البته چیدمان واقعی اجزا بسته به تنظیمات و نیازهای هر cluster می‌تواند فرق کند.

در این نمودار روی هر Node جزء kube-proxy اجرا می‌شود. روی هر Node به یک پراکسی شبکه نیاز دارید تا Serviceها و رفتارهای مرتبط با آن‌ها روی شبکه‌ی cluster کار کنند. اما بعضی network pluginها (برنامه‌ای که شبکه‌ی Podها را برقرار می‌کند،‏ معمولاً از نوع CNI) پیاده‌سازی مخصوص خودشان را برای این کار دارند؛‏ اگر از چنین plugin استفاده کنید،‏ دیگر لازم نیست روی Nodeها kube-proxy اجرا کنید.

توضیح تکمیلی: نقشه‌ی ذهنی کل معماری در یک نگاه

ساده‌ترین مدل ذهنی این است: kube-apiserver تنها «درِ ورودی» cluster است و etcd تنها «memory ماندگار» آن. بقیه‌ی اجزا (scheduler،‏ controller-manager،‏ kubelet،‏ kube-proxy،‏ CoreDNS و controllerهایی که خودتان می‌نویسید) همگی فقط client همین API server هستند؛‏ هیچ‌کدام مستقیم با etcd ارتباط برقرار نمی‌کنند و برای هماهنگی هم به هم پیام نمی‌دهند. (یک استثنا که در بخش «ارتباط بین Nodeها و control plane» می‌بینیم: خود API server برای logs،‏ exec و port-forward مستقیماً به kubelet وصل می‌شود.) هر جزء با watch تغییرات شیءهایی (object) را که برایش مهم است دنبال می‌کند و نتیجه‌ی کارش را دوباره به شکل یک شیء یا فیلد status در API می‌نویسد. به همین دلیل می‌گوییم کوبرنتیز «اعلانی (declarative)» و «level-triggered» (واکنش بر اساس current state،‏ نه صرفاً رخداد تغییر) است.

مسیر ساختن یک Deployment را دنبال کنید:

  1. kubectl apply درخواست را به kube-apiserver می‌فرستد؛‏ API server بعد از authentication (تشخیص هویت درخواست‌دهنده)،‏ authorization و عبور از admission controllerها،‏ شیء را در etcd ذخیره می‌کند.
  2. Deployment controller (داخل kube-controller-manager) با watch متوجه Deployment جدید می‌شود و یک ReplicaSet می‌سازد.
  3. ReplicaSet controller می‌بیند تعداد Podها کمتر از replicas است و شیء Pod می‌سازد (هنوز spec.nodeName خالی است).
  4. kube-scheduler Podهای بی‌Node را می‌بیند،‏ Node مناسب را انتخاب می‌کند و یک binding به API می‌فرستد.
  5. kubelet روی آن Node،‏ Pod جدیدی را که به او سپرده شده می‌بیند و از طریق CRI به runtime (containerd یا CRI-O) می‌گوید image را بگیرد و container را اجرا کند؛‏ بعد status را گزارش می‌دهد.
  6. EndpointSlice controller آدرس Pod آماده را به EndpointSliceهای Service اضافه می‌کند و kube-proxy روی همه‌ی Nodeها قوانین شبکه را به‌روز می‌کند.

هیچ‌کدام از این مراحل «فرمان مستقیم» به جزء بعدی نیست؛‏ هر جزء فقط وضعیت را در API تغییر می‌دهد و جزء دیگر به آن واکنش نشان می‌دهد. این همان «الگوی controller» است که در بخش controllerها کامل توضیح داده می‌شود.

اجزای control plane (Control plane components)

اجزای control plane تصمیم‌های سراسری cluster را می‌گیرند (مثلاً scheduling Podها) و eventهای cluster را تشخیص می‌دهند و به آن‌ها پاسخ می‌دهند (مثلاً وقتی تعداد Podهای یک Deployment از replicas کمتر است،‏ Pod جدید راه می‌اندازند).

این اجزا را می‌توان روی هر ماشینی از cluster اجرا کرد،‏ اما برای سادگی،‏ scriptهای نصب معمولاً همه‌شان را روی یک ماشین اجرا می‌کنند و روی آن ماشین container کاربر اجرا نمی‌کنند. برای نمونه‌ای که control plane را روی چند ماشین اجرا می‌کند،‏ «ساختن cluster با دسترس‌پذیری بالا (high availability) با kubeadm» را در فصل ۱۳ ببینید.

kube-apiserver

API server جزئی از control plane است که API کوبرنتیز را در اختیار می‌گذارد؛‏ یعنی front end control plane است.

پیاده‌سازی اصلی آن kube-apiserver است که طوری طراحی شده که به‌صورت افقی مقیاس بگیرد؛‏ یعنی با اجرای instanceهای بیشتر ظرفیتش بالا می‌رود. می‌توانید چند instance از آن اجرا کنید و ترافیک را با load balancer بینشان پخش کنید.

etcd

یک پایگاه داده‌ی کلید-مقدار (key-value) با سازگاری قوی (consistent) و دسترس‌پذیری بالا که همه‌ی داده‌های cluster در آن ذخیره می‌شود.

اگر cluster شما از etcd استفاده می‌کند،‏ حتماً برای داده‌هایش برنامه‌ی backup داشته باشید. اطلاعات عمیق‌تر درباره‌ی etcd در مستندات رسمی خود etcd آمده است.

kube-scheduler

جزئی از control plane که Podهای تازه‌ای را که هنوز Nodeی ندارند زیر نظر دارد و برای هر کدام یک Node انتخاب می‌کند.

عواملی که در این تصمیم حساب می‌شوند: نیاز منابع هر Pod و مجموع Podها،‏ محدودیت‌های سخت‌افزاری،‏ نرم‌افزاری و سیاست‌ها،‏ قواعد affinity و anti-affinity،‏ نزدیکی به داده (data locality)،‏ تداخل بین workloadها (برنامه‌ای که روی cluster اجرا می‌شود) و مهلت‌ها (deadline). جزئیات کامل در فصل ۹.

kube-controller-manager

جزئی از control plane که processهای controller را اجرا می‌کند.

از نظر منطقی هر controller یک process جداست،‏ اما برای کم‌کردن پیچیدگی،‏ همه در یک فایل اجرایی واحد کامپایل می‌شوند و در یک process اجرا می‌شوند.

controllerهای زیادی وجود دارد؛‏ چند نمونه:

  • Node controller: متوجه می‌شود که Nodeی از دسترس خارج شده و به آن واکنش نشان می‌دهد.
  • Job controller: شیءهای Job را که نماینده‌ی کارهای یک‌باره‌اند زیر نظر دارد و Podهایی می‌سازد تا آن کارها تا آخر انجام شوند.
  • EndpointSlice controller: شیءهای EndpointSlice را پر می‌کند تا بین Serviceها و Podها پیوند برقرار شود.
  • ServiceAccount controller: برای namespaceهای جدید،‏ ServiceAccount پیش‌فرض (default) می‌سازد.

این فهرست کامل نیست.

cloud-controller-manager

جزئی از control plane که منطق کنترلی مخصوص cloud را در خود دارد. این جزء اجازه می‌دهد cluster را به API cloud provider وصل کنید،‏ و اجزایی را که با پلتفرم cloud کار می‌کنند از اجزایی که فقط با cluster کار دارند جدا می‌کند.

cloud-controller-manager فقط controllerهای مخصوص cloud provider شما را اجرا می‌کند. اگر کوبرنتیز را داخل سازمان (on-premises) یا برای یادگیری روی کامپیوتر خودتان اجرا کنید،‏ cluster شما cloud-controller-manager ندارد.

مثل kube-controller-manager،‏ این جزء هم چند control loop (حلقه‌ای که مدام وضعیت واقعی را با وضعیت خواسته‌شده مقایسه و اختلاف را برطرف می‌کند) منطقاً مستقل را در یک فایل اجرایی و یک process ترکیب می‌کند. می‌توانید آن را افقی مقیاس دهید (بیش از یک instance اجرا کنید) تا کارایی یا تحمل خرابی بالا برود.

این controllerها می‌توانند به cloud provider وابسته باشند:

  • Node controller: وقتی Nodeی جواب نمی‌دهد،‏ از cloud provider می‌پرسد آیا آن ماشین در cloud حذف شده یا نه.
  • Route controller: مسیرها (routeها) را در زیرساخت شبکه‌ی cloud تنظیم می‌کند.
  • Service controller:‏ load balancerهای cloud را می‌سازد،‏ به‌روز می‌کند و حذف می‌کند.
توضیح تکمیلی: چرا «یک فایل اجرایی،‏ چند controller» و چرا فقط یک رهبر؟

اگر هر controller process جداگانه‌ای بود،‏ اپراتور باید ده‌ها process را deploy،‏ پایش و ارتقا می‌داد. با ترکیب همه در یک فایل اجرایی،‏ فقط یک Pod (یا یک سرویس) برای همه‌ی controllerها داریم.

اما مشکلی پیش می‌آید: در control plane با دسترس‌پذیری بالا،‏ سه instance از kube-controller-manager اجرا می‌شود. اگر هر سه هم‌زمان فعال بودند،‏ مثلاً ReplicaSet controller سه بار Pod اضافه می‌ساخت! برای همین kube-controller-manager و kube-scheduler از leader election مبتنی بر Lease استفاده می‌کنند: فقط یکی فعال است و بقیه آماده‌به‌کار (standby) می‌مانند (بخش Leases و Coordinated Leader Election در همین فصل). در مقابل،‏ kube-apiserver stateless است؛‏ همه‌ی instanceهایش هم‌زمان فعال‌اند و پشت load balancer قرار می‌گیرند.

اجزای Node (Node components)

اجزای Node روی هر Node اجرا می‌شوند،‏ Podهای در حال اجرا را سرپا نگه می‌دارند و container runtime کوبرنتیز را فراهم می‌کنند.

kubelet

عاملی (agent) که روی هر Node اجرا می‌شود و مطمئن می‌شود containerهای هر Pod در حال اجرا هستند.

kubelet مجموعه‌ای از مشخصات Pod (PodSpec) را که از راه‌های مختلف به دستش می‌رسد می‌گیرد و تضمین می‌کند containerهای توصیف‌شده در آن‌ها در حال اجرا و سالم باشند. kubelet containerهایی را که کوبرنتیز نساخته،‏ مدیریت نمی‌کند.

kube-proxy (اختیاری)

kube-proxy یک پراکسی شبکه است که روی هر Node اجرا می‌شود و بخشی از مفهوم Service را پیاده می‌کند.

kube-proxy قوانین شبکه را روی Nodeها نگه می‌دارد؛‏ قوانینی که اجازه می‌دهند از داخل یا بیرون cluster به Podها وصل شوید.

اگر سیستم‌عامل قابلیت فیلتر بسته‌ها (packet filtering،‏ مثل iptables یا nftables) داشته باشد،‏ kube-proxy از آن استفاده می‌کند؛‏ وگرنه خودش ترافیک را جابه‌جا می‌کند. اگر از plugin شبکه‌ای استفاده کنید که خودش هدایت بسته‌ها برای Serviceها را انجام می‌دهد و رفتاری معادل kube-proxy دارد،‏ دیگر لازم نیست kube-proxy را اجرا کنید.

container runtime

جزء بنیادی‌ای که به کوبرنتیز امکان می‌دهد containerها را اجرا کند و مسئول اجرا و چرخه‌ی عمر containerهاست.

کوبرنتیز از container runtimeهایی مثل containerd،‏ CRI-O و هر پیاده‌سازی دیگری از CRI (Container Runtime Interface؛‏ رابط استاندارد بین kubelet و container runtime) پشتیبانی می‌کند.

توضیح تکمیلی: «kubelet containerهایی را که خودش نساخته مدیریت نمی‌کند» در عمل یعنی چه؟

اگر روی یک Node مستقیماً با nerdctl run یا ctr containerی اجرا کنید،‏ kubelet آن را نمی‌شناسد: دوباره راهش نمی‌اندازد،‏ در kubectl get pods دیده نمی‌شود،‏ در محاسبه‌ی requests توسط scheduler (جزئی که برای هر Pod،‏ Node مناسب را انتخاب می‌کند) حساب نمی‌شود (بخش ردیابی ظرفیت منابع) و garbage collection در kubelet هم پاکش نمی‌کند (مستندات: «kubelet فقط containerهایی را جمع‌آوری می‌کند که خودش مدیریت می‌کند»). در production،‏ برای عامل‌هایی که بیرون از کوبرنتیز روی Node اجرا می‌شوند (مثل عامل امنیتی یا backup) باید با system-reserved یا kube-reserved منابع کنار گذاشت؛‏ وگرنه Node بیش از ظرفیتش بار می‌گیرد (overcommit).

kubelet مشخصات Pod را از چند منبع می‌گیرد: API server (مسیر اصلی)،‏ فایل‌های static Pod در یک پوشه (مثل /etc/kubernetes/manifests که kubeadm برای control plane استفاده می‌کند) و (خارج از این صفحه‌ی مستندات) یک آدرس HTTP. برای هر static Pod یک mirror Pod فقط‌خواندنی در API ساخته می‌شود.

Addons

addonها (جزء اختیاری که قابلیتی به cluster اضافه می‌کند) با منابع خود کوبرنتیز (DaemonSet،‏ Deployment و…) قابلیت‌های cluster را پیاده می‌کنند. چون این قابلیت‌ها در سطح cluster هستند،‏ منابع namespaceدار addonها در namespace kube-system قرار می‌گیرند.

چند addon منتخب در ادامه آمده؛‏ فهرست کامل‌تر در صفحه‌ی Addons است.

DNS

addonهای دیگر الزامی نیستند،‏ اما هر cluster کوبرنتیز باید DNS clusterی داشته باشد،‏ چون بسیاری از اجزا به آن وابسته‌اند.

DNS cluster یک server DNS است (در کنار serverهای DNS دیگر محیط شما) که رکوردهای DNS مربوط به Serviceهای کوبرنتیز را پاسخ می‌دهد. containerهایی که کوبرنتیز اجرا می‌کند،‏ این server DNS را به‌طور خودکار در جست‌وجوهای DNS خود دارند (فصل ۵).

web UI (Dashboard)

Dashboard یک web UI همه‌منظوره برای clusterها کوبرنتیز است که به کاربران اجازه می‌دهد برنامه‌های داخل cluster و خود cluster را مدیریت و عیب‌یابی (troubleshooting) کنند.

پایش منابع container

معیارهای سری زمانی (time-series) عمومی containerها را در یک پایگاه داده‌ی مرکزی ثبت می‌کند و interfaceی برای مرور آن‌ها فراهم می‌کند.

ثبت log در سطح cluster

سازوکاری که log containerها را در یک repository مرکزی با امکان جست‌وجو و مرور ذخیره می‌کند (فصل ۱۱).

network pluginها

نرم‌افزارهایی که مشخصات CNI (Container Network Interface؛‏ رابط استاندارد بین container runtime و plugin شبکه) را پیاده می‌کنند. کارشان تخصیص IP به Podها و برقراری ارتباط Podها با هم در cluster است.

گونه‌های معماری (Architecture variations)

اجزای اصلی کوبرنتیز ثابت‌اند،‏ اما شیوه‌ی deployment و مدیریتشان می‌تواند فرق کند. شناختن این گونه‌ها برای طراحی و نگهداری clusterهایی که نیاز عملیاتی مشخصی دارند ضروری است.

ملاحظات محل اجرای workloadها

اینکه workloadها (از جمله اجزای control plane) کجا اجرا شوند،‏ به اندازه‌ی cluster،‏ نیاز کارایی و سیاست‌های عملیاتی بستگی دارد:

  • در clusterهای کوچک یا توسعه،‏ اجزای control plane و workloadهای کاربر ممکن است روی همان Nodeها اجرا شوند.
  • clusterهای عملیاتی بزرگ‌تر معمولاً Nodeهای مشخصی را به control plane اختصاص می‌دهند و آن را از workloadهای کاربر جدا می‌کنند.
  • بعضی سازمان‌ها addonهای حیاتی یا ابزارهای پایش را روی Nodeهای control plane اجرا می‌کنند.

ابزارهای مدیریت cluster

ابزارهایی مثل kubeadm،‏ kops و Kubespray هر کدام رویکرد خودشان را برای deployment و مدیریت cluster و چیدمان اجزا دارند.

سفارشی‌سازی و توسعه‌پذیری

  • می‌توانید schedulerهای سفارشی را کنار scheduler پیش‌فرض اجرا کنید یا کاملاً جایگزینش کنید.
  • API server را می‌شود با CustomResourceDefinition و API Aggregation گسترش داد (فصل ۱۵).
  • سرویس‌دهنده‌های cloud می‌توانند از طریق cloud-controller-manager عمیقاً با کوبرنتیز یکپارچه شوند.

این انعطاف به سازمان‌ها اجازه می‌دهد cluster را متناسب با نیاز خودشان بسازند و بین پیچیدگی عملیاتی،‏ کارایی و سربار مدیریت تعادل برقرار کنند.

توضیح تکمیلی: kubeadm چطور Nodeهای control plane را از workloadها جدا می‌کند؟

kubeadm روی Nodeهای control plane هم label (جفت کلید/مقدار روی اشیا برای گروه‌بندی و انتخاب آن‌ها) node-role.kubernetes.io/control-plane و هم taint node-role.kubernetes.io/control-plane:NoSchedule می‌گذارد (جزئیات در فصل ۱۳). نتیجه: Podهای عادی آنجا schedule نمی‌شوند،‏ مگر اینکه toleration آن taint را داشته باشند. در cluster آزمایشی تک‌Node می‌توانید این taint را بردارید:

shell
kubectl describe node cp-1 | grep -A2 Taints
kubectl taint nodes cp-1 node-role.kubernetes.io/control-plane:NoSchedule-

در production این کار را نکنید: اگر یک Pod پرمصرف روی Node control plane بنشیند و memory تمام شود،‏ ممکن است etcd یا kube-apiserver قربانی OOM شوند و کل cluster مختل شود.

Nodeها (Nodes)

کوبرنتیز workload شما را این‌طور اجرا می‌کند: containerها را داخل Podها می‌گذارد و Podها را روی Nodeها اجرا می‌کند. Node بسته به cluster می‌تواند یک VM یا ماشین فیزیکی باشد. هر Node را control plane مدیریت می‌کند و سرویس‌های لازم برای اجرای Podها روی آن نصب است.

معمولاً یک cluster چندین Node دارد؛‏ در محیط یادگیری یا با منابع محدود ممکن است فقط یک Node داشته باشید.

اجزای هر Node عبارت‌اند از kubelet،‏ یک container runtime و kube-proxy.

مدیریت Nodeها (Management)

دو راه اصلی برای اضافه‌شدن Node به API server وجود دارد:

  1. kubelet روی Node خودش را در control plane ثبت می‌کند (self-registration).
  2. شما (یا یک کاربر دیگر) شیء Node را دستی اضافه می‌کنید.

بعد از اینکه شیء Node ساخته شد (دستی یا با self-registration توسط kubelet)،‏ control plane بررسی می‌کند که این شیء معتبر است یا نه. مثلاً اگر بخواهید یک Node را از این فایل JSON بسازید:

Node manifest (JSON)
{
  "kind": "Node",
  "apiVersion": "v1",
  "metadata": {
    "name": "10.240.79.157",
    "labels": {
      "name": "my-first-k8s-node"
    }
  }
}

کوبرنتیز یک شیء Node در داخل خودش می‌سازد و بررسی می‌کند که آیا kubeletی با نامی برابر metadata.name در API server ثبت شده یا نه. اگر Node سالم باشد (یعنی همه‌ی سرویس‌های لازم در حال اجرا باشند)،‏ می‌تواند Pod بگیرد. در غیر این صورت،‏ تا وقتی سالم نشده،‏ در هیچ فعالیتی از cluster به حساب نمی‌آید.

نکته

کوبرنتیز شیء Node نامعتبر را نگه می‌دارد و مدام بررسی می‌کند که سالم شده یا نه. برای متوقف‌کردن این بررسی،‏ شما یا یک controller باید صراحتاً شیء Node را حذف کنید.

نام شیء Node باید یک نام زیردامنه‌ی DNS معتبر باشد.

یکتایی نام Node

نام،‏ هویت Node است؛‏ دو Node نمی‌توانند هم‌زمان یک نام داشته باشند. کوبرنتیز فرض می‌کند منبعی با نام یکسان،‏ همان شیء است. در مورد Node یعنی فرض می‌شود ماشینی که از آن نام استفاده می‌کند همان وضعیت (مثلاً تنظیمات شبکه و محتوای disk اصلی) و همان ویژگی‌ها (مثل labelها) را دارد. اگر ماشین عوض شود ولی نامش همان بماند،‏ ممکن است ناسازگاری پیش بیاید. پس اگر Node باید جایگزین یا به‌طور اساسی به‌روز شود،‏ اول شیء Node قدیمی را از API server حذف کنید و بعد از به‌روزرسانی دوباره اضافه‌اش کنید.

توضیح تکمیلی: یک سناریوی واقعی از نقض یکتایی نام

تیم زیرساخت VMی به نام worker-07 را حذف می‌کند و با image جدید (سیستم‌عامل جدید،‏ کارت GPU جدید) و همان hostname دوباره می‌سازد. kubelet جدید با همان نام ثبت می‌شود،‏ اما شیء Node قدیمی هنوز labelهایی مثل disktype=ssd یا gpu=false دارد که دیگر درست نیستند (labelها فقط هنگام ثبت Node تنظیم می‌شوند؛‏ نکته‌ی بخش بعد را ببینید).‏ scheduler بر اساس labelهای کهنه تصمیم می‌گیرد و Podهای GPU هیچ‌وقت به این Node نمی‌رسند. راه درست:

shell
kubectl drain worker-07 --ignore-daemonsets --delete-emptydir-data
kubectl delete node worker-07
# rebuild the machine; the kubelet then re-registers itself with the new labels
kubectl get node worker-07 --show-labels

self-registration Nodeها (Self-registration)

وقتی flag --register-node در kubelet برابر true باشد (مقدار پیش‌فرض)،‏ kubelet سعی می‌کند خودش را در API server ثبت کند. این روش ترجیحی است و بیشتر توزیع‌ها از آن استفاده می‌کنند.

برای self-registration،‏ kubelet با این گزینه‌ها اجرا می‌شود:

flagتوضیح
--kubeconfigمسیر اطلاعات ورود برای authentication kubelet نزد API server.
--cloud-providerچطور با cloud provider ارتباط برقرار کند تا اطلاعات (metadata) خودش را بخواند.
--register-nodeself-registration در API server.
--register-with-taintsNode را با فهرستی از taintها ثبت می‌کند (جداشده با کاما،‏ به شکل <key>=<value>:<effect>). اگر register-node برابر false باشد،‏ اثری ندارد.
--node-ipفهرست اختیاری IPهای Node (جداشده با کاما)؛‏ برای هر خانواده‌ی آدرس (IPv4 یا IPv6) فقط یک آدرس. مثلاً در cluster تک‌پشته‌ی IPv4 (single-stack)،‏ آن را برابر IPv4ای بگذارید که kubelet باید برای Node استفاده کند. اگر این گزینه را ندهید،‏ kubelet از IPv4 پیش‌فرض Node استفاده می‌کند و اگر Node هیچ IPv4ای نداشته باشد،‏ از IPv6 پیش‌فرض.
--node-labelslabelهایی که هنگام ثبت Node اضافه می‌شوند (به محدودیت‌های NodeRestriction plugin دقت کنید).
--node-status-update-frequencyهر چند وقت یک بار kubelet وضعیت Node را به API server بفرستد.

وقتی حالت authorization Node و NodeRestriction admission plugin فعال باشند،‏ هر kubelet فقط اجازه دارد شیء Node خودش را بسازد یا تغییر دهد.

نکته

همان‌طور که در بخش یکتایی نام گفتیم،‏ وقتی پیکربندی Node باید عوض شود،‏ بهتر است Node را دوباره در API server ثبت کنید. مثلاً اگر kubelet با مجموعه‌ی جدیدی از --node-labels restart شود اما با همان نام،‏ تغییر اعمال نمی‌شود؛‏ چون labelها فقط هنگام ثبت Node تنظیم می‌شوند.

اگر پیکربندی Node هنگام restart kubelet عوض شود،‏ Podهایی که قبلاً روی آن schedule شده‌اند ممکن است رفتار نادرست داشته باشند. مثلاً یک Pod در حال اجرا ممکن است با labelهای جدید Node ناسازگار باشد،‏ در حالی که Podهای دیگری که با آن Pod ناسازگارند بر اساس همین label جدید روی این Node schedule شوند. ثبت دوباره‌ی Node تضمین می‌کند همه‌ی Podها drain (خالی کردن امن Node از Podها پیش از نگهداری) و درست از نو schedule شوند.

توضیح تکمیلی: این flagها در عمل (kubeadm)

در clusterهای kubeadm،‏ بیشتر این تنظیمات در فایل /var/lib/kubelet/config.yaml (شیء KubeletConfiguration) و آرگومان‌های اضافه در /var/lib/kubelet/kubeadm-flags.env هستند (خارج از این صفحه‌ی مستندات). مثال: یک Node مخصوص GPU که از لحظه‌ی تولد نباید Pod معمولی بگیرد:

/var/lib/kubelet/kubeadm-flags.env (نمونه)
KUBELET_KUBEADM_ARGS="--container-runtime-endpoint=unix:///run/containerd/containerd.sock --node-ip=10.20.0.31 --node-labels=accelerator=nvidia-l4 --register-with-taints=nvidia.com/gpu=present:NoSchedule"

مزیت --register-with-taints نسبت به زدن kubectl taint بعد از پیوستن Node این است که هیچ «پنجره‌ی زمانی» پیش نمی‌آید که scheduler،‏ Podهای معمولی را روی Node تازه بگذارد. ضمناً NodeRestriction اجازه نمی‌دهد kubelet labelهایی با پیشوند node-restriction.kubernetes.io/ را روی خودش بگذارد؛‏ این labelها را فقط مدیر cluster می‌تواند تنظیم کند و برای جداسازی امن workloadها مناسب‌اند (فصل ۱۴).

مدیریت دستی Nodeها

می‌توانید شیءهای Node را با kubectl بسازید و تغییر دهید. اگر می‌خواهید Nodeها را دستی بسازید،‏ در kubelet flag --register-node=false را تنظیم کنید.

تغییردادن شیءهای Node،‏ مستقل از مقدار --register-node،‏ همیشه ممکن است؛‏ مثلاً می‌توانید روی یک Node label بگذارید یا آن را «unschedulable» (علامتی که مانع قرار گرفتن Pod جدید روی Node می‌شود) کنید.

برای تعیین نقش (role) اختیاری Nodeها،‏ یک یا چند label به شکل node-role.kubernetes.io/<role>: <role> اضافه کنید (کاراکترهای <role> تابع قواعد نحو labelها هستند). کوبرنتیز مقدار این label را نادیده می‌گیرد؛‏ طبق قرارداد،‏ مقدار را برابر همان نام نقش می‌گذارند.

با ترکیب labelهای Node و node selector (شرطی در Pod که Nodeهای مجاز را بر اساس labelهایشان انتخاب می‌کند) در Podها می‌توانید scheduling (انتخاب Node مناسب برای اجرای Pod) را کنترل کنید؛‏ مثلاً Pod را محدود کنید که فقط روی زیرمجموعه‌ای از Nodeها اجرا شود.

unschedulable کردن Node باعث می‌شود scheduler Pod جدیدی روی آن نگذارد،‏ اما روی Podهای موجود اثری ندارد. این کار قدم اول پیش از reboot یا نگهداری Node است:

shell
kubectl cordon $NODENAME

جزئیات بیشتر در راهنمای «Safely Drain a Node».

نکته

آدرس‌ها

کاربرد این فیلدها به cloud provider یا پیکربندی server فیزیکی بستگی دارد.

  • HostName: نام host،‏ همان‌طور که kernel Node گزارش می‌کند. با پارامتر --hostname-override در kubelet می‌توان آن را تغییر داد.

  • InternalIP: معمولاً IPی از Node که فقط درون cluster قابل‌دسترسی است.

نکته

اگر با ابزار خط فرمان جزئیات یک Node که cordon شده را ببینید،‏ در ستون وضعیت SchedulingDisabled دیده می‌شود. اما SchedulingDisabled یک شرط (Condition) واقعی در API نیست؛‏ Nodeهای cordon‌شده فقط در spec خود با Unschedulable علامت خورده‌اند.

در API،‏ شرایط Node بخشی از .status آن است. مثلاً این ساختار JSON یک Node سالم را توصیف می‌کند:

وقتی Node مشکلی پیدا می‌کند،‏ control plane به‌طور خودکار taintهایی متناسب با آن شرایط روی Node می‌گذارد. مثلاً اگر وضعیت شرط Ready بیشتر از NodeMonitorGracePeriod در kube-controller-manager (پیش‌فرض ۵۰ ثانیه) در حالت Unknown یا False بماند،‏ taint node.kubernetes.io/unreachable (برای Unknown) یا node.kubernetes.io/not-ready (برای False) به Node اضافه می‌شود.

این taintها روی Podهای منتظر (Pending) اثر می‌گذارند،‏ چون scheduler هنگام انتخاب Node taintها را در نظر می‌گیرد. Podهایی هم که از قبل روی Node هستند ممکن است به‌خاطر taintهای نوع NoExecute evict (بیرون رانده شدن و حذف Pod از Node توسط سیستم) شوند،‏ مگر اینکه toleration مناسب داشته باشند. (Taint Based Evictions و Taint Nodes by Condition در فصل ۹.)

ظرفیت و مقدار allocatable

منابع Node را توصیف می‌کند: CPU،‏ memory و حداکثر تعداد Podهایی که روی Node جا می‌شوند. بلوک capacity کل منابع Node را نشان می‌دهد و بلوک allocatable (بخشی از منابع Node که واقعاً می‌توان به Podها داد) مقداری را که واقعاً برای Podهای عادی در دسترس است (بعد از کسر سهم سیستم).

اطلاعات کلی (Info)

اطلاعات عمومی Node مثل نسخه‌ی kernel،‏ نسخه‌ی کوبرنتیز (نسخه‌ی kubelet و kube-proxy)،‏ جزئیات container runtime و سیستم‌عامل. kubelet این‌ها را از Node جمع می‌کند و در API منتشر می‌کند.

قابلیت‌های اعلام‌شده (Declared features)

وضعیت قابلیت: Kubernetes v1.37 [stable] (feature gate NodeDeclaredFeatures قفل‌شده روی true؛‏ همیشه فعال است)

این فیلد قابلیت‌هایی از کوبرنتیز را فهرست می‌کند که فعلاً از طریق feature gateها روی kubelet آن Node فعال‌اند. kubelet آن‌ها را به شکل فهرستی از رشته‌ها در فیلد .status.declaredFeatures گزارش می‌کند؛‏ scheduler و admission controller با این اطلاعات جلوی قرارگرفتن Pod روی Nodeی را می‌گیرند که قابلیت لازمِ Pod را ندارد.

این فیلد برای قابلیت‌های جدیدی است که در حال توسعه‌اند؛‏ قابلیت‌هایی که بالغ شده‌اند و دیگر feature gate لازم ندارند «پایه» حساب می‌شوند و اینجا اعلام نمی‌شوند. دقت کنید این فیلد فعال‌بودن قابلیت‌های کوبرنتیز را نشان می‌دهد،‏ نه توانایی‌های سیستم‌عامل یا kernel Node را.

heartbeat Nodeها (Node heartbeats)

heartbeat (سیگنال زنده‌بودن) پیام‌هایی است که Nodeها مرتب می‌فرستند تا cluster بفهمد هر Node هنوز در دسترس است و اگر خرابی تشخیص داد،‏ اقدام کند.

heartbeat Nodeها دو شکل دارد:

  • به‌روزرسانی‌های .status خود Node.
  • شیءهای Lease در namespace kube-node-lease؛‏ هر Node یک Lease مخصوص خودش دارد.

در مقایسه با به‌روزکردن .status کامل Node،‏ Lease منبعی سبک است. استفاده از Lease برای heartbeat،‏ هزینه‌ی این به‌روزرسانی‌ها را در clusterهای بزرگ خیلی کم می‌کند.

kubelet مسئول ساختن و به‌روزکردن .status Node و Lease مربوط به آن است:

  • kubelet فیلد .status را یا وقتی چیزی تغییر کند به‌روز می‌کند،‏ یا اگر مدتی به‌روز نشده باشد. این بازه به‌طور پیش‌فرض ۵ دقیقه است؛‏ خیلی بیشتر از مهلت پیش‌فرض برای تشخیص Nodeهای غیرقابل‌دسترس. (متن مستندات اینجا هنوز «۴۰ ثانیه» نوشته،‏ در حالی که مقدار پیش‌فرض فعلی node-monitor-grace-period همان ۵۰ ثانیه‌ای است که در جدول شرایط Node آمد.)
  • kubelet شیء Lease خودش را می‌سازد و بعد هر ۱۰ ثانیه (پیش‌فرض) renew می‌کند. renew کردن Lease مستقل از به‌روزرسانی .status است. اگر renew شکست بخورد،‏ kubelet با تأخیر نمایی (exponential backoff) از ۲۰۰ میلی‌ثانیه تا حداکثر ۷ ثانیه دوباره تلاش می‌کند.

Node controller

Node controller جزئی از control plane است که جنبه‌های مختلف Nodeها را مدیریت می‌کند و در طول عمر هر Node سه نقش دارد:

نقش اول: هنگام ثبت Node،‏ یک بازه‌ی آدرس (CIDR block) به آن تخصیص می‌دهد (اگر تخصیص CIDR فعال باشد).

نقش دوم: فهرست داخلی Nodeهایش را با فهرست ماشین‌های موجود در cloud provider هماهنگ نگه می‌دارد. در محیط cloud،‏ هر وقت Nodeی ناسالم شود،‏ Node controller از cloud provider می‌پرسد آیا VM آن هنوز وجود دارد؛‏ اگر نه،‏ آن Node را از فهرست حذف می‌کند.

نقش سوم: پایش سلامت Nodeها. Node controller مسئول این کارهاست:

  • وقتی Nodeی از دسترس خارج شود،‏ شرط Ready در .status آن را به Unknown تغییر می‌دهد.
  • اگر Node همچنان در دسترس نباشد،‏ برای همه‌ی Podهای آن eviction از طریق API (API-initiated eviction) را آغاز می‌کند. به‌طور پیش‌فرض بین علامت‌زدن Node به Unknown و اولین درخواست eviction ۵ دقیقه صبر می‌کند.

Node controller به‌طور پیش‌فرض هر ۵ ثانیه وضعیت Nodeها را بررسی می‌کند؛‏ این دوره با flag --node-monitor-period در kube-controller-manager قابل تنظیم است.

محدودیت نرخ eviction (Rate limits on eviction)

در بیشتر موارد،‏ Node controller نرخ eviction را به --node-eviction-rate (پیش‌فرض 0.1 در ثانیه) محدود می‌کند؛‏ یعنی از بیش از یک Node در هر ۱۰ ثانیه Pod evict نمی‌کند.

وقتی Nodeی در یک ناحیه‌ی دسترس‌پذیری (availability zone) ناسالم می‌شود،‏ رفتار عوض می‌شود. controller بررسی می‌کند چند درصد از Nodeهای آن ناحیه هم‌زمان ناسالم‌اند (شرط Ready برابر Unknown یا False):

  • اگر سهم Nodeهای ناسالم دست‌کم --unhealthy-zone-threshold (پیش‌فرض 0.55) باشد،‏ نرخ eviction کم می‌شود:
  • اگر cluster کوچک باشد (تعداد Nodeها کمتر یا مساوی --large-cluster-size-threshold،‏ پیش‌فرض ۵۰)،‏ eviction متوقف می‌شود.
  • در غیر این صورت،‏ نرخ به --secondary-node-eviction-rate (پیش‌فرض 0.01 در ثانیه) کاهش می‌یابد.

این سیاست‌ها برای هر ناحیه جداگانه اعمال می‌شوند،‏ چون ممکن است یک ناحیه از control plane جدا شود (partition) در حالی که بقیه وصل‌اند. اگر cluster شما در چند ناحیه پخش نشده باشد،‏ این سازوکار دسترس‌ناپذیری به تفکیک ناحیه را در نظر نمی‌گیرد.

یکی از دلایل اصلی پخش‌کردن Nodeها در چند ناحیه این است که اگر یک ناحیه کاملاً از کار افتاد،‏ workload به ناحیه‌های سالم منتقل شود. برای همین اگر همه‌ی Nodeهای یک ناحیه ناسالم باشند،‏ controller با نرخ عادی --node-eviction-rate evict می‌کند. حالت خاص وقتی است که همه‌ی ناحیه‌ها کاملاً ناسالم باشند (هیچ Node سالمی در cluster نباشد). در این حالت controller فرض می‌کند مشکل از ارتباط control plane با Nodeهاست و هیچ Podی را evict نمی‌کند. (اگر بعد از قطعی بعضی Nodeها برگردند،‏ controller،‏ Podهای Nodeهایی را که همچنان ناسالم یا غیرقابل‌دسترس‌اند evict می‌کند.)

Node controller همچنین Podهای در حال اجرا روی Nodeهایی با taint NoExecute را evict می‌کند،‏ مگر اینکه آن Podها toleration آن taint را داشته باشند. به‌علاوه taintهایی متناسب با مشکلات Node (مثل unreachable یا not-ready) اضافه می‌کند؛‏ پس scheduler Pod جدیدی روی Nodeهای ناسالم نمی‌گذارد.

ردیابی ظرفیت منابع (Resource capacity tracking)

شیء Node ظرفیت منابع Node را نگه می‌دارد؛‏ مثلاً مقدار memory و تعداد CPUها. Nodeهایی که خودشان ثبت‌نام می‌کنند،‏ ظرفیتشان را هنگام ثبت گزارش می‌دهند. اگر Node را دستی اضافه کنید،‏ باید اطلاعات ظرفیتش را هم خودتان تنظیم کنید.

scheduler کوبرنتیز تضمین می‌کند منابع کافی برای همه‌ی Podهای روی یک Node وجود دارد: بررسی می‌کند مجموع requestهای containerهای روی Node از ظرفیت Node بیشتر نشود. این مجموع شامل همه‌ی containerهایی است که kubelet مدیریت می‌کند،‏ اما containerهایی که مستقیم با runtime ساخته شده‌اند و هر process که بیرون از کنترل kubelet اجرا می‌شود را شامل نمی‌شود.

نکته

اگر می‌خواهید صراحتاً برای processهای غیر Pod منابع رزرو کنید،‏ راهنمای «reserve resources for system daemons» را ببینید.

توضیح تکمیلی: Capacity در برابر Allocatable با یک مثال عددی

یک Node با ۱۶ گیگابایت memory و این پیکربندی kubelet (جزئیات در صفحه‌ی reserve-compute-resources):

KubeletConfiguration (بخشی)
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
systemReserved:
  memory: 1Gi
  cpu: 500m
kubeReserved:
  memory: 1Gi
  cpu: 500m
evictionHard:
  memory.available: "500Mi"

memory Allocatable = 16Gi − 1Gi − 1Gi − 500Mi ≈ 13.5Gi. scheduler فقط تا 13.5Gi از requestها را روی این Node می‌گذارد. اگر یک عامل امنیتی بیرون از کوبرنتیز روی Node 2Gi مصرف کند و برایش رزرو نکرده باشید،‏ scheduler از آن خبر ندارد و Node زیر فشار memory به MemoryPressure و eviction Podها می‌رسد (فصل ۹).

توپولوژی Node (Node topology)

وضعیت قابلیت: Kubernetes v1.27 [stable] (feature gate TopologyManager پس از v1.28 حذف شده و این قابلیت همیشه فعال است)

با Topology Manager،‏ kubelet می‌تواند هنگام تخصیص منابع از «راهنمایی‌های توپولوژی» (topology hints) استفاده کند. جزئیات در صفحه‌ی «Control Topology Management Policies on a Node».

توضیح تکمیلی

روی serverهای multi-socket (معماری NUMA)،‏ اگر CPUهای اختصاصی یک container روی NUMA node صفر باشند و GPU یا کارت شبکه‌ی SR-IOV آن روی NUMA node یک،‏ هر دسترسی به memory باید از گذرگاه بین socketها عبور کند و تأخیر بالا می‌رود. Topology Manager از CPU Manager،‏ Device Manager و Memory Manager «راهنمایی» می‌گیرد و سعی می‌کند همه‌ی منابع یک container را روی یک NUMA node هم‌تراز کند (سیاست‌هایش: none،‏ best-effort،‏ restricted و single-numa-node). این موضوع برای workloadهای HPC،‏ استنتاج یادگیری ماشین و پردازش بسته‌های شبکه (5G/NFV) اهمیت دارد.

مدیریت swap memory (Swap memory management)

این بخش از صفحه‌ی مستقل «Swap memory management» آمده،‏ چون رفتار swap بخشی از مدیریت Node است.

می‌توان کوبرنتیز را طوری پیکربندی کرد که روی Node از swap استفاده کند؛‏ یعنی kernel بتواند صفحه‌های memory را به disk منتقل کند و memory فیزیکی آزاد کند. این در چند حالت مفید است: برنامه‌هایی با مصرف memory بزرگ که در هر لحظه فقط بخشی از آن را استفاده می‌کنند؛‏ جلوگیری از کشته‌شدن Podها در اوج‌های کوتاه فشار memory؛‏ محافظت از Node در برابر اوج‌های memory سطح سیستم؛‏ و مدیریت انعطاف‌پذیرتر memory.

پشتیبانی سیستم‌عامل

  • Nodeهای Linux از swap پشتیبانی می‌کنند،‏ اما باید هر Node را برایش پیکربندی کنید. به‌طور پیش‌فرض،‏ kubelet روی Node لینوکسی که swap فعال دارد اجرا نمی‌شود.
  • Nodeهای Windows برعکس به swap نیاز دارند؛‏ kubelet به‌طور پیش‌فرض روی Node ویندوزی بدون swap اجرا نمی‌شود.

چطور کار می‌کند؟

اگر kubelet از قبل روی Node اجرا می‌شود،‏ بعد از فعال‌کردن swap باید restart شود تا آن را ببیند. وقتی kubelet روی Nodeی با swap فعال و با تنظیم failSwapOn: false اجرا شود: می‌تواند با وجود swap اجرا شود،‏ و به‌طور پیش‌فرض به runtime (CRI) می‌گوید به workloadهای کوبرنتیز صفر swap بدهد.

مدیر cluster رفتار swap هر Node را با memorySwap.swapBehavior در KubeletConfiguration تعیین می‌کند؛‏ Nodeهای مختلف می‌توانند رفتار متفاوت داشته باشند:

swapBehaviorمعنی
NoSwap (پیش‌فرض)Podهای این Node از swap استفاده نمی‌کنند و نمی‌توانند استفاده کنند.
LimitedSwapworkloadهای کوبرنتیز (با محدودیت‌هایی که پایین‌تر آمده) می‌توانند از swap استفاده کنند.
نکته

اگر NoSwap را انتخاب کنید و kubelet را طوری تنظیم کنید که swap را تحمل کند (failSwapOn: false)،‏ workloadهای شما swap نمی‌گیرند؛‏ اما processهای بیرون از containerهای کوبرنتیز،‏ مثل سرویس‌های systemd (و حتی خود kubelet!)،‏ می‌توانند از swap استفاده کنند.

یکپارچه‌سازی با runtime (runtime integration):‏ kubelet از طریق API runtime به آن می‌گوید چه تنظیمی اعمال کند (مثلاً در cgroup v2 مقدار memory.swap.max) و runtime این تنظیم را در cgroup container می‌نویسد.

مشاهده‌پذیری (observability):‏ kubelet معیارهای سطح Node و container را از آدرس‌های /metrics/resource (برای ابزارهایی مثل Prometheus) و /stats/summary (برای Autoscalerها) ارائه می‌دهد؛‏ از جمله node_swap_usage_bytes،‏ container_swap_usage_bytes و container_swap_limit_bytes. معیار machine_swap_bytes در cadvisor ظرفیت فیزیکی swap را نشان می‌دهد. همچنین kubectl top با flag --show-swap و فیلد node.status.nodeInfo.swap.capacity در دسترس‌اند:

هشدار

encryption فضای swap قویاً توصیه می‌شود. volumeهای مبتنی بر memory (مثل secret یا emptyDir با medium: Memory) با tmpfs پیاده می‌شوند و kubelet برای اینکه محتوایشان (مثلاً رمزها) به disk swap نرود،‏ از گزینه‌ی noswap در tmpfs استفاده می‌کند (رسماً از kernel 6.3؛‏ روی kernelهای قدیمی‌تر kubelet پشتیبانی را آزمایش می‌کند و در صورت نبود،‏ هشدار در log ثبت می‌کند).

ریسک‌ها و روش‌های خوب: swap پیش‌بینی‌پذیری را کم و خطر noisy neighbor را زیاد می‌کند. scheduler فعلاً مصرف swap را در نظر نمی‌گیرد (Podها فقط memory درخواست می‌کنند)؛‏ پس Nodeهای دارای swap را taint کنید تا فقط workloadهای مجاز آنجا بروند. آستانه‌ی eviction kubelet را کمی پایین‌تر از vm.min_free_kbytes بگذارید تا Node پیش از eviction فرصت swap داشته باشد ولی به OOM killer نرسد. برای slice سیستمی مقدار memory.swap.max=0 و اولویت io.latency بالاتر بگذارید؛‏ Nodeهای control plane را بدون swap اجرا کنید؛‏ و برای swap از disk اختصاصی و سریع (SSD یا NVMe،‏ نه HDD) استفاده کنید.

ارتباط بین Nodeها و control plane (Communication between Nodes and the Control Plane)

این بخش مسیرهای ارتباطی بین API server و cluster را فهرست می‌کند. هدف این است که بتوانید نصب خود را طوری مقاوم‌سازی (harden) کنید که cluster حتی روی یک شبکه‌ی غیرقابل‌اعتماد (یا روی IPهای کاملاً عمومی در cloud) امن کار کند.

از Node به control plane

الگوی ارتباطی کوبرنتیز hub-and-spoke (ستاره‌ای) است: همه‌ی درخواست‌های API از سمت Nodeها (یا Podهای روی آن‌ها) به API server ختم می‌شوند. هیچ جزء دیگری از control plane برای ارائه‌ی سرویس به بیرون طراحی نشده است. API server روی یک port HTTPS امن (معمولاً 443) به اتصال‌های بیرونی گوش می‌دهد و یک یا چند روش client authentication در آن فعال است. یک یا چند روش authorization (بررسی اینکه درخواست‌دهنده اجازه‌ی این کار را دارد یا نه) هم باید فعال باشد،‏ به‌خصوص اگر درخواست‌های ناشناس یا tokenهای ServiceAccount مجاز باشند.

Nodeها باید certificate ریشه‌ی (root certificate) عمومی cluster را داشته باشند تا بتوانند با اطلاعات ورود معتبر،‏ امن به API server وصل شوند. روش خوب این است که اطلاعات ورود kubelet به شکل client certificate باشد؛‏ برای صدور خودکار این certificateها،‏ «kubelet TLS bootstrapping» را ببینید.

Podهایی که می‌خواهند به API server وصل شوند،‏ می‌توانند با یک ServiceAccount این کار را امن انجام دهند: کوبرنتیز هنگام ساختن Pod به‌طور خودکار certificate ریشه‌ی عمومی و یک token معتبر را داخل آن قرار می‌دهد. Service به نام kubernetes (در namespace default) یک IP مجازی دارد که (از طریق kube-proxy) به آدرس HTTPS API server هدایت می‌شود.

اجزای control plane هم از طریق همین port امن با API server ارتباط برقرار می‌کنند. در نتیجه،‏ اتصال‌های Nodeها و Podها به control plane به‌طور پیش‌فرض امن‌اند و می‌توانند روی شبکه‌های غیرقابل‌اعتماد یا عمومی کار کنند.

از control plane به Node

دو مسیر اصلی از control plane (API server) به Nodeها وجود دارد: اول،‏ از API server به kubelet process روی هر Node؛‏ دوم،‏ از API server به هر Node،‏ Pod یا Service از طریق قابلیت proxy در API server.

از API server به kubelet

این اتصال‌ها برای این کارها استفاده می‌شوند:

  • گرفتن log Podها (kubectl logs)؛‏
  • وصل‌شدن به Podهای در حال اجرا (kubectl attach و exec)؛‏
  • قابلیت هدایت port (kubectl port-forward).

این اتصال‌ها به آدرس HTTPS kubelet ختم می‌شوند. اما به‌طور پیش‌فرض API server certificate kubelet را تأیید نمی‌کند؛‏ این یعنی اتصال در برابر حمله‌ی مرد میانی (man-in-the-middle) آسیب‌پذیر است و اجرایش روی شبکه‌های غیرقابل‌اعتماد یا عمومی ناامن است.

برای تأیید این اتصال،‏ با flag --kubelet-certificate-authority یک بسته‌ی certificate ریشه (root certificate) به API server بدهید تا certificate kubelet را با آن تأیید کند. اگر این ممکن نیست،‏ در صورت نیاز بین API server و kubelet تونل SSH بزنید تا اتصال از شبکه‌ی ناامن عبور نکند. و در نهایت،‏ authentication و authorization kubelet را فعال کنید تا API خود kubelet امن شود.

از API server به Nodeها،‏ Podها و Serviceها

این اتصال‌ها به‌طور پیش‌فرض HTTP ساده‌اند؛‏ نه authentication دارند و نه encryption. می‌توان با افزودن پیشوند https: به نام Node،‏ Pod یا Service در آدرس API آن‌ها را روی HTTPS برد،‏ اما در این حالت هم certificate طرف مقابل تأیید نمی‌شود و اطلاعات ورود client هم ارسال نمی‌شود. پس با اینکه اتصال encrypt می‌شود،‏ تضمینی برای یکپارچگی (integrity) آن نیست. این اتصال‌ها فعلاً برای اجرا روی شبکه‌های غیرقابل‌اعتماد یا عمومی امن نیستند.

تونل‌های SSH

کوبرنتیز از تونل SSH برای محافظت از مسیر control plane به Nodeها پشتیبانی می‌کند: API server به server SSH هر Node (port 22) وصل می‌شود و همه‌ی ترافیکی را که مقصدش kubelet،‏ Node،‏ Pod یا Service است از داخل تونل عبور می‌دهد،‏ تا ترافیک بیرون از شبکه‌ی Nodeها دیده نشود.

نکته

تونل‌های SSH فعلاً منسوخ (deprecated) هستند؛‏ مگر اینکه دقیقاً بدانید چه می‌کنید،‏ از آن‌ها استفاده نکنید. جایگزینشان سرویس Konnectivity است.

سرویس Konnectivity

وضعیت قابلیت: Kubernetes v1.18 [beta]

سرویس Konnectivity جایگزین تونل‌های SSH است و یک پراکسی در سطح TCP برای ارتباط control plane با cluster فراهم می‌کند. دو بخش دارد: server Konnectivity در شبکه‌ی control plane،‏ و عامل‌های Konnectivity در شبکه‌ی Nodeها. عامل‌ها اتصال را به server آغاز می‌کنند و آن را باز نگه می‌دارند؛‏ بعد از فعال‌شدن این سرویس،‏ همه‌ی ترافیک control plane به Nodeها از همین اتصال‌ها عبور می‌کند. برای راه‌اندازی،‏ راهنمای «Konnectivity service task» را دنبال کنید.

controllerها (Controllers)

در رباتیک و خودکارسازی،‏ control loop حلقه‌ای بی‌پایان است که وضعیت یک سیستم را تنظیم می‌کند.

مثال ساده‌اش ترموستات اتاق است: وقتی دما را تنظیم می‌کنید،‏ desired state را به ترموستات می‌گویید. دمای واقعی اتاق current state است. ترموستات با روشن و خاموش کردن دستگاه،‏ current state را به desired state نزدیک می‌کند.

در کوبرنتیز،‏ controllerها همین control loopها‌اند: وضعیت cluster را زیر نظر دارند و هر جا لازم باشد،‏ تغییری ایجاد می‌کنند یا درخواست می‌دهند. هر controller تلاش می‌کند current state cluster را به desired state نزدیک‌تر کند.

الگوی controller (Controller pattern)

هر controller دست‌کم یک نوع منبع کوبرنتیز را دنبال می‌کند. این شیءها فیلدی به نام spec دارند که desired state را نشان می‌دهد،‏ و controller(های) آن منبع مسئول‌اند current state را به آن نزدیک کنند.

controller ممکن است خودش کار را انجام دهد،‏ اما در کوبرنتیز رایج‌تر این است که به API server پیام‌هایی بفرستد که اثر جانبی مفیدی دارند؛‏ نمونه‌هایش را در ادامه می‌بینید.

بعضی controllerهای داخلی،‏ مثل namespace controller،‏ روی شیءهایی کار می‌کنند که spec ندارند؛‏ برای سادگی این جزئیات را کنار می‌گذاریم.

کنترل از طریق API server

Job controller نمونه‌ای از controllerهای داخلی است. controllerهای داخلی وضعیت را از طریق تعامل با API server مدیریت می‌کنند.

Job منبعی است که یک یا چند Pod را اجرا می‌کند تا کاری انجام شود و بعد متوقف می‌شود. (شیء Pod بعد از scheduling،‏ بخشی از desired state یک kubelet می‌شود.)

وقتی Job controller کار جدیدی می‌بیند،‏ مطمئن می‌شود که جایی در cluster،‏ kubeletها تعداد درستی Pod برای انجام کار اجرا می‌کنند. Job controller خودش هیچ Pod یا containerی اجرا نمی‌کند؛‏ فقط به API server می‌گوید Podها را بسازد یا حذف کند. اجزای دیگر control plane به این اطلاعات جدید واکنش نشان می‌دهند (Podهای جدیدی هست که باید scheduling و اجرا شوند) و در نهایت کار انجام می‌شود.

بعد از ساختن یک Job،‏ desired state این است که آن Job تمام شود. Job controller با ساختن Podهایی که کار را انجام می‌دهند،‏ Job را به تکمیل نزدیک می‌کند.

controllerها شیءهایی را که پیکربندی می‌کنند هم به‌روز می‌کنند؛‏ مثلاً وقتی کار یک Job تمام شد،‏ Job controller آن را Finished علامت می‌زند. (شبیه ترموستاتی که وقتی اتاق به دمای تنظیم‌شده رسید،‏ یک چراغ را خاموش می‌کند.)

کنترل مستقیم

برخلاف Job،‏ بعضی controllerها باید چیزهایی را بیرون از cluster تغییر دهند. مثلاً controllerی که مطمئن می‌شود Node کافی در cluster هست،‏ باید در صورت نیاز با سیستمی بیرونی Node جدید راه بیندازد.

این controllerها،‏ desired state را از API server می‌خوانند و بعد مستقیماً با سیستم بیرونی ارتباط برقرار می‌کنند تا current state را به آن نزدیک کنند. (چنین controllerی واقعاً وجود دارد: پروژه‌ی kubernetes/autoscaler که Nodeهای cluster را افقی مقیاس می‌دهد.)

نکته‌ی مهم این است که controller تغییرات را اعمال می‌کند و بعد current state را به API server گزارش می‌دهد تا control loopهای دیگر آن را ببینند و کار خودشان را انجام دهند. در مثال ترموستات،‏ اگر اتاق خیلی سرد باشد،‏ ممکن است controller دیگری یک بخاری ضدیخ را هم روشن کند. در clusterها کوبرنتیز،‏ control plane به‌طور غیرمستقیم با ابزارهای مدیریت IP،‏ سرویس‌های storage،‏ APIهای cloud و سرویس‌های دیگر کار می‌کند؛‏ از طریق گسترش کوبرنتیز (فصل ۱۵).

desired state در برابر current state

کوبرنتیز نگاهی cloud-native به سیستم‌ها دارد و برای مدیریت تغییر مداوم ساخته شده. cluster شما ممکن است در هر لحظه،‏ هم‌زمان با کار control loopها و رفع خودکار خرابی‌ها،‏ در حال تغییر باشد؛‏ یعنی ممکن است هیچ‌وقت به وضعیت کاملاً پایدار نرسد. تا وقتی controllerها در حال اجرا هستند و می‌توانند تغییرات مفید ایجاد کنند،‏ پایدار بودن یا نبودن وضعیت کلی اهمیتی ندارد.

طراحی

اصل طراحی کوبرنتیز این است که controllerهای زیادی داشته باشد که هر کدام جنبه‌ی خاصی از وضعیت cluster را مدیریت کند. معمولاً یک controller از یک نوع منبع به‌عنوان desired state استفاده می‌کند و نوع دیگری را مدیریت می‌کند تا آن وضعیت محقق شود. مثلاً Job controller،‏ شیءهای Job را دنبال می‌کند (تا کار جدید را کشف کند) و شیءهای Pod را هم (تا Jobها را اجرا کند و بفهمد کار کی تمام شده). در این مورد،‏ چیز دیگری Jobها را می‌سازد و Job controller،‏ Podها را.

داشتن controllerهای ساده بهتر از یک مجموعه‌ی یکپارچه از control loopهای درهم‌تنیده است. controllerها ممکن است از کار بیفتند و کوبرنتیز طوری طراحی شده که این را تحمل کند.

نکته

ممکن است چند controller یک نوع شیء را بسازند یا به‌روز کنند. controllerهای کوبرنتیز مطمئن می‌شوند که فقط به منابع مرتبط با منبعِ کنترل‌کننده‌ی خودشان توجه کنند. مثلاً هم Deployment و هم Job،‏ Pod می‌سازند؛‏ اما Job controller،‏ Podهای Deployment را حذف نمی‌کند،‏ چون اطلاعاتی (labelها) هست که controllerها با آن Podها را از هم تشخیص می‌دهند.

روش‌های اجرای controllerها

کوبرنتیز با مجموعه‌ای از controllerهای داخلی عرضه می‌شود که داخل kube-controller-manager اجرا می‌شوند و رفتارهای هسته‌ای مهمی را فراهم می‌کنند (مثل Deployment controller و Job). کوبرنتیز اجازه می‌دهد control planeی مقاوم داشته باشید،‏ طوری که اگر یکی از controllerهای داخلی از کار افتاد،‏ بخش دیگری از control plane کار را بر عهده بگیرد.

controllerهایی هم هستند که بیرون از control plane اجرا می‌شوند تا کوبرنتیز را گسترش دهند،‏ و اگر بخواهید می‌توانید خودتان controller جدید بنویسید؛‏ به شکل مجموعه‌ای از Podها یا بیرون از کوبرنتیز. انتخاب بهتر به کاری بستگی دارد که controller انجام می‌دهد.

توضیح تکمیلی: reconciliation (فرایند نزدیک کردن مداوم وضعیت واقعی به وضعیت خواسته‌شده) level-triggered و یک controller حداقلی

controllerهای کوبرنتیز «edge-triggered» (واکنش فقط به رخداد تغییر) نیستند،‏ بلکه «level-triggered» هستند: در هر دور،‏ کل desired state را با current state مقایسه می‌کنند. برای همین اگر controller-manager ده دقیقه از کار بیفتد و eventهایی را از دست بدهد،‏ بعد از برگشت،‏ با یک فهرست‌گیری کامل و مقایسه،‏ همه چیز را درست می‌کند. جمله‌ی مستندات «controllerها ممکن است از کار بیفتند و کوبرنتیز طوری طراحی شده که این را تحمل کند» دقیقاً به همین خاصیت اشاره دارد.

یک مثال برای فهم فرق این دو: controller edge-triggered مثل کسی است که فقط به زنگ در واکنش نشان می‌دهد؛‏ اگر زنگ را نشنود،‏ مهمان پشت در می‌ماند. controller level-triggered هر چند دقیقه در را باز می‌کند و نگاه می‌کند چه کسی پشت آن است؛‏ هیچ مهمانی جا نمی‌ماند.

شبه‌کد یک reconcile ساده (خارج از مستندات رسمی؛‏ الگوی sample-controller و controller-runtime):

pseudo-code
for {
  key := queue.Get()                       # e.g. "shop/checkout-api"
  desired := lister.Get(key)               # read from the local informer cache
  actual  := podLister.List(selector(desired))
  diff    := desired.Spec.Replicas - len(activePods(actual))
  if diff > 0 { create diff Pods with ownerReference -> desired }
  if diff < 0 { delete -diff Pods (prefer not-ready / newest) }
  updateStatus(desired, len(activePods(actual)))
  queue.Done(key)
}

Leaseها (Leases)

سیستم‌های توزیع‌شده معمولاً به سازوکاری به نام lease (در لغت «اجاره») نیاز دارند؛‏ سازوکاری برای قفل‌کردن منابع مشترک و هماهنگ‌کردن فعالیت اعضای یک مجموعه. در کوبرنتیز این مفهوم با شیء Lease در API group (دسته‌ای از منابع API،‏ مثل apps یا batch) coordination.k8s.io پیاده شده و برای قابلیت‌های حیاتی مثل heartbeat Nodeها و leader election بین instanceهای یک جزء استفاده می‌شود.

تشبیه ساده: Lease مثل کلید اتاقی است که فقط یک نفر می‌تواند داشته باشد و باید مرتب «renew» کند؛‏ اگر renew نکرد،‏ کلید آزاد می‌شود و نفر بعدی برمی‌دارد.

heartbeat Nodeها

کوبرنتیز با Lease API heartbeat kubelet را به API server می‌رساند. برای هر Node یک شیء Lease هم‌نام در namespace kube-node-lease وجود دارد. هر heartbeat kubelet در واقع یک درخواست update روی این Lease است که فیلد spec.renewTime را به‌روز می‌کند. control plane از همین زمان برای تشخیص در دسترس بودن Node استفاده می‌کند. (جزئیات در بخش «heartbeat Nodeها».)

Leader election

کوبرنتیز با Leaseها تضمین می‌کند که در هر لحظه فقط یک instance از یک جزء فعال باشد. اجزای control plane مثل kube-controller-manager و kube-scheduler در پیکربندی‌های با دسترس‌پذیری بالا از این قابلیت استفاده می‌کنند: فقط یک instance فعالانه کار می‌کند و بقیه آماده‌به‌کار می‌مانند.

برای اینکه ببینید کوبرنتیز چطور بر پایه‌ی Lease تصمیم می‌گیرد کدام instance رهبر باشد،‏ بخش «leader election هماهنگ» را (کمی جلوتر در همین فصل) بخوانید.

آزادکردن قفل kube-controller-manager هنگام خروج

وضعیت قابلیت: Kubernetes v1.36 [alpha] (به‌طور پیش‌فرض غیرفعال؛‏ feature gate ControllerManagerReleaseLeaderElectionLockOnExit)

با فعال‌بودن این قابلیت،‏ kube-controller-manager هنگام جابه‌جایی رهبر،‏ قفل leader election را فعالانه آزاد می‌کند،‏ به‌جای اینکه صبر کند تا مدت اعتبار (TTL) قفل تمام شود. در نتیجه رهبر جدید سریع‌تر انتخاب می‌شود و تأخیر جابه‌جایی کمتر می‌شود.

هویت API server

وضعیت قابلیت: Kubernetes v1.26 [beta] (به‌طور پیش‌فرض فعال؛‏ feature gate APIServerIdentity)

از نسخه‌ی v1.26،‏ هر kube-apiserver با Lease API هویت خودش را به بقیه‌ی سیستم اعلام می‌کند. این به‌تنهایی کاربرد زیادی ندارد،‏ اما به clientها امکان می‌دهد بفهمند چند instance از kube-apiserver control plane را اداره می‌کنند،‏ و راه را برای قابلیت‌هایی باز می‌کند که به هماهنگی بین apiserverها نیاز دارند (مثل Mixed Version Proxy در ادامه‌ی همین فصل).

استفاده از Lease در workloadهای خودتان

workload شما هم می‌تواند از Lease استفاده کند. مثلاً controller سفارشی‌ای دارید که در آن فقط یک عضو اصلی (رهبر) کارهایی را انجام می‌دهد که بقیه انجام نمی‌دهند. یک Lease تعریف می‌کنید تا instanceهای controller با کمک API کوبرنتیز رهبر انتخاب کنند. روش خوب این است که نام Lease به‌وضوح به محصول یا جزء مربوط اشاره کند؛‏ مثلاً برای جزئی به نام Example Foo،‏ Leaseی به نام example-foo.

اگر ممکن است یک اپراتور یا کاربر چند instance از یک جزء را deploy کند،‏ یک پیشوند نام انتخاب کنید و سازوکاری (مثل hash نام Deployment) برای جلوگیری از تداخل نام Leaseها در نظر بگیرید. هر روش دیگری هم که همین نتیجه را بدهد (محصولات مختلف با هم تداخل نداشته باشند) قابل قبول است.

leader election هماهنگ (Coordinated Leader Election)

وضعیت قابلیت: Kubernetes v1.33 [beta] (به‌طور پیش‌فرض غیرفعال؛‏ feature gate CoordinatedLeaderElection)

کوبرنتیز 1.37 قابلیتی در مرحله‌ی beta دارد که به اجزای control plane اجازه می‌دهد با leader election هماهنگ،‏ رهبر را به شکل قطعی (deterministic) انتخاب کنند. این کار برای رعایت محدودیت‌های اختلاف نسخه (version skew) هنگام ارتقای cluster مفید است. فعلاً تنها راهبرد داخلی انتخاب OldestEmulationVersion است: نامزدی ترجیح داده می‌شود که کمترین emulation version را دارد؛‏ در صورت برابری،‏ کمترین binary version،‏ و بعد قدیمی‌ترین زمان ساخت.

فعال‌سازی

هنگام اجرای API Server،‏ feature gate CoordinatedLeaderElection و API group coordination.k8s.io/v1beta1 را فعال کنید؛‏ با flagهای --feature-gates="CoordinatedLeaderElection=true" و --runtime-config="coordination.k8s.io/v1beta1=true".

پیکربندی اجزا

وقتی هر دو شرط بالا برقرار باشد،‏ اجزای سازگار control plane به‌طور خودکار از APIهای LeaseCandidate و Lease برای leader election استفاده می‌کنند. در کوبرنتیز 1.37 دو جزء kube-controller-manager و kube-scheduler این کار را انجام می‌دهند.

leader election برای اجزای کوبرنتیز

کوبرنتیز با Lease API بین چند instance از یک جزء control plane (مثل kube-controller-manager یا kube-scheduler) در clusterی با دسترس‌پذیری بالا رهبر انتخاب می‌کند. Lease مثل یک قفل توزیع‌شده‌ی سبک عمل می‌کند که در API server ذخیره می‌شود. همه‌ی instanceهای در حال اجرا،‏ شیء Lease را watch می‌کنند یا مرتب می‌خوانند تا بفهمند رهبر فعلی کیست.

فیلدهای مهم Lease:

فیلدمعنی
holderIdentityهویت رهبر فعلی (مثلاً نام Pod یا رشته‌ای بر پایه‌ی hostname).
acquireTimeزمانی که رهبری به دست آمد.
renewTimeزمان آخرین renew توسط رهبر.
leaseDurationSecondsمدت اعتبار Lease؛‏ نامزدها باید همین مدت (به‌علاوه‌ی کمی مهلت) صبر کنند و بعد برای گرفتن Lease منقضی‌شده تلاش کنند.
leaseTransitionsشمارنده‌ی دفعاتی که رهبری جابه‌جا شده.

وقتی Lease وجود ندارد یا منقضی شده (زمان فعلی بزرگ‌تر از renewTime + leaseDurationSeconds)،‏ نامزدها سعی می‌کنند Lease را با هویت خودشان به‌روز کنند. کوبرنتیز برای این کار به کنترل هم‌روندی خوش‌بینانه با فیلد resourceVersion تکیه می‌کند: از بین تلاش‌های هم‌زمان،‏ به‌خاطر ناهمخوانی نسخه فقط یکی موفق می‌شود و همان instance رهبر می‌شود.

کوبرنتیز انتخاب‌ها را با LeaseCandidate API مدیریت می‌کند: اجزایی مثل kube-controller-manager و kube-scheduler با ساختن شیء LeaseCandidate خود را نامزد معرفی می‌کنند. این شیءها همه‌ی instanceهای رقیب را فهرست می‌کنند و اطلاعاتی مثل هویت نامزد،‏ binary version و emulation version دارند.

در هر انتخاب،‏ نامزدها از طریق یک Lease مشترک هماهنگ می‌شوند؛‏ control plane تضمین می‌کند فقط یکی Lease را بگیرد و رهبر شود و بقیه پیرو (follower) بمانند. اگر رهبر فعلی نتواند در مهلت تعیین‌شده Lease را renew کند،‏ بقیه برای رهبری رقابت می‌کنند.

رهبر مرتب با به‌روزکردن renewTime Lease را renew می‌کند (مثلاً هر leaseDurationSeconds ÷ 2 تا نزدیک انقضا به تداخل نخورد). در kube-controller-manager و kube-scheduler با مقادیر پیش‌فرض،‏ رهبر هر ۲ ثانیه (--leader-elect-retry-period) برای renew تلاش می‌کند و اگر تا ۱۰ ثانیه (--leader-elect-renew-deadline) موفق نشود،‏ خودش رهبری را رها می‌کند و processاش خارج می‌شود؛‏ این کار جلوی حالتی را می‌گیرد که دو instance هم‌زمان خود را رهبر بدانند. تا وقتی renewها قبل از انقضا انجام شوند،‏ رهبر رهبری را حفظ می‌کند. اگر رهبر از کار بیفتد،‏ از دسترس خارج شود یا renew را متوقف کند،‏ Lease منقضی می‌شود و instanceهای سالم دیگر انتخاب جدیدی را شروع می‌کنند.

نتیجه: حتی با وجود چند instance از یک جزء برای پایداری،‏ در هر لحظه فقط یک instance فعالانه کارهای کنترلی را انجام می‌دهد و بقیه آماده‌به‌کار،‏ Lease را زیر نظر دارند تا در صورت نیاز سریع جایگزین شوند.

توضیح تکمیلی: چرا leader election معمولی هنگام ارتقا مشکل‌ساز است؟

در leader election کلاسیک،‏ «هر کس زودتر Lease را بگیرد» رهبر است. فرض کنید control plane سه‌تایی را از 1.36 به 1.37 ارتقا می‌دهید: cp-1 ارتقا یافته و kube-controller-manager نسخه‌ی 1.37 آن رهبر شده،‏ در حالی که kube-apiserverهای cp-2 و cp-3 هنوز 1.36 هستند. طبق version skew policy،‏ kube-controller-manager نباید از apiserverهایی که با آن‌ها ارتباط برقرار می‌کند جدیدتر باشد (فصل ۱۳)؛‏ controller جدید ممکن است از فیلدها یا APIهایی استفاده کند که apiserver قدیمی نمی‌شناسد.

با OldestEmulationVersion،‏ control plane عمداً نامزدی را که قدیمی‌ترین emulation version را دارد رهبر می‌کند؛‏ پس در کل مدت ارتقا controller قدیمی‌تر فعال می‌ماند و فقط وقتی همه ارتقا یافتند،‏ رهبری به نسخه‌ی جدید می‌رسد. دیدن نامزدها (وقتی قابلیت فعال است):

مدیر controllerهای cloud (Cloud Controller Manager)

وضعیت قابلیت: Kubernetes v1.11 [beta]

زیرساخت‌های cloud اجازه می‌دهند کوبرنتیز را روی cloudهای عمومی،‏ خصوصی و ترکیبی (hybrid) اجرا کنید. فلسفه‌ی کوبرنتیز زیرساخت خودکار و مبتنی بر API است،‏ بدون وابستگی تنگاتنگ بین اجزا.

cloud-controller-manager جزئی از control plane است که منطق کنترلی مخصوص cloud را در خود دارد؛‏ اجازه می‌دهد cluster را به API cloud provider وصل کنید و اجزایی را که با cloud کار دارند از اجزایی که فقط با cluster کار دارند جدا می‌کند.

با جداکردن منطق تعامل کوبرنتیز و زیرساخت cloud،‏ سرویس‌دهنده‌های cloud می‌توانند قابلیت‌هایشان را با سرعتی مستقل از پروژه‌ی اصلی کوبرنتیز منتشر کنند. این جزء ساختار plugin دارد تا هر cloud provider بتواند پلتفرم خودش را با کوبرنتیز یکپارچه کند.

طراحی

cloud-controller-manager در control plane به شکل مجموعه‌ای از processهای تکثیرشده اجرا می‌شود (معمولاً containerهایی در Podها). هر instance چند controller را در یک process پیاده می‌کند.

نکته

می‌توانید cloud-controller-manager را به‌جای بخشی از control plane،‏ به شکل یک addon در کوبرنتیز اجرا کنید.

کارکردهای cloud-controller-manager

Node controller

وقتی serverهای جدید در زیرساخت cloud ساخته می‌شوند،‏ این controller شیءهای Node را به‌روز می‌کند و اطلاعات hostهای در حال اجرای شما را از cloud provider می‌گیرد. کارهایش:

  1. ثبت شناسه‌ی یکتای server (که از API cloud می‌گیرد) در شیء Node.
  2. افزودن labelها و annotationهای مخصوص cloud به Node،‏ مثل منطقه (region) و ناحیه (zone) محل deployment و منابع در دسترس (CPU،‏ memory و…).
  3. گرفتن hostname و آدرس‌های شبکه‌ی Node.
  4. بررسی سلامت Node: اگر Node پاسخ ندهد،‏ از API cloud می‌پرسد که آیا server غیرفعال،‏ حذف یا خاتمه‌یافته است؛‏ اگر از cloud حذف شده باشد،‏ شیء Node را از cluster پاک می‌کند.

بعضی پیاده‌سازی‌ها این وظایف را بین یک Node controller و یک node lifecycle controller تقسیم می‌کنند.

Route controller

مسیرها (route) را در شبکه‌ی cloud طوری تنظیم می‌کند که containerهای روی Nodeهای مختلف بتوانند با هم ارتباط برقرار کنند. بسته به سرویس‌دهنده،‏ ممکن است بازه‌های IP را هم برای شبکه‌ی Podها تخصیص دهد.

Service controller

Serviceها با اجزای زیرساخت cloud مثل load balancerهای مدیریت‌شده،‏ آدرس‌های IP،‏ فیلتر بسته‌ها و بررسی سلامت مقصدها یکپارچه می‌شوند. وقتی Serviceی تعریف می‌کنید که به این‌ها نیاز دارد (مثلاً type: LoadBalancer)،‏ Service controller با API cloud آن‌ها را راه می‌اندازد.

گروه‌های کنترلی (cgroups)

در Linux،‏ گروه‌های کنترلی (control group یا به‌اختصار cgroup) منابعی را که به processها داده می‌شود محدود می‌کنند. kubelet و container runtime برای اعمال مدیریت منابع Podها و containerها (فصل ۶)،‏ یعنی همان requests و limits برای CPU و memory،‏ با cgroupها کار می‌کنند.

تشبیه ساده: اگر namespaceهای Linux «دیوار» بین containerها باشند (هر container فقط اتاق خودش را می‌بیند)،‏ cgroupها «کنتور» هستند (هر اتاق فقط به اندازه‌ی سهمش برق و آب می‌گیرد).

Linux دو نسخه از cgroup دارد: cgroup v1 و cgroup v2؛‏ نسخه‌ی v2 نسل جدید API است.

cgroup v2 چیست؟

وضعیت قابلیت: پایدار (stable) از v1.25

cgroup v2 نسخه‌ی بعدی API گروه‌های کنترلی در Linux است و یک سیستم کنترل یکپارچه با قابلیت‌های پیشرفته‌تر مدیریت منابع فراهم می‌کند. بهبودهایش نسبت به v1:

  • طراحی یک سلسله‌مراتب (hierarchy) یکپارچه‌ی واحد در API؛‏
  • sub-tree delegation امن‌تر به containerها؛‏
  • قابلیت‌های تازه مثل Pressure Stall Information (PSI؛‏ اندازه‌گیری اینکه processها چقدر منتظر منابع مانده‌اند)؛‏
  • مدیریت و ایزوله‌سازی پیشرفته‌تر منابع:
    • حسابداری یکپارچه برای انواع مصرف memory (memory شبکه،‏ kernel memory و…)؛‏
    • حسابداری مصرف‌های غیرفوری مثل نوشتن page cache روی disk.

بعضی قابلیت‌های کوبرنتیز فقط با cgroup v2 کار می‌کنند؛‏ مثلاً MemoryQoS (فصل ۳) کیفیت سرویس memory را بهتر می‌کند و به ابزارهای cgroup v2 تکیه دارد.

استفاده از cgroup v2

روش توصیه‌شده این است که از توزیعی از Linux استفاده کنید که به‌طور پیش‌فرض cgroup v2 را فعال کرده است. برای بررسی،‏ بخش «تشخیص نسخه‌ی cgroup» را پایین‌تر ببینید.

پیش‌نیازها

  • توزیع سیستم‌عامل cgroup v2 را فعال کرده باشد؛‏
  • نسخه‌ی kernel Linux ۵٫۸ یا بالاتر باشد؛‏
  • container runtime از cgroup v2 پشتیبانی کند؛‏ مثلاً:
    • containerd نسخه‌ی v1.4 و بالاتر
    • cri-o نسخه‌ی v1.20 و بالاتر
  • kubelet و runtime برای استفاده از درایور cgroup از نوع systemd (فصل ۱۳) پیکربندی شده باشند.

پشتیبانی توزیع‌های Linux از cgroup v2

فهرست توزیع‌هایی که از cgroup v2 استفاده می‌کنند در مستندات cgroup v2 آمده است:

  • Container Optimized OS (از M97)
  • Ubuntu (از 21.10؛‏ 22.04 به بعد توصیه می‌شود)
  • Debian GNU/Linux (از Debian 11 bullseye)
  • Fedora (از 31)
  • Arch Linux (از آوریل 2021)
  • RHEL و توزیع‌های مشابه (از 9)

می‌توانید cgroup v2 را دستی هم با تغییر آرگومان‌های بوت kernel فعال کنید: اگر توزیعتان از GRUB استفاده می‌کند،‏ systemd.unified_cgroup_hierarchy=1 را به GRUB_CMDLINE_LINUX در /etc/default/grub اضافه کنید و sudo update-grub را اجرا کنید. اما روش توصیه‌شده همان استفاده از توزیعی است که از قبل v2 را فعال کرده.

مهاجرت به cgroup v2

مطمئن شوید پیش‌نیازها برقرارند،‏ سپس به نسخه‌ای از kernel ارتقا دهید که به‌طور پیش‌فرض cgroup v2 را فعال می‌کند. kubelet خودش تشخیص می‌دهد سیستم‌عامل روی cgroup v2 است و بدون پیکربندی اضافه مطابق آن رفتار می‌کند.

پس از جابه‌جایی نباید تفاوت محسوسی در تجربه‌ی کاربر باشد،‏ مگر برای کسانی که مستقیماً به filesystem cgroup دسترسی دارند (روی Node یا از داخل containerها). چون API نسخه‌ی v2 فرق می‌کند،‏ هر برنامه‌ای که مستقیماً filesystem cgroup را می‌خواند باید به نسخه‌ای که از v2 پشتیبانی می‌کند ارتقا یابد. برای مثال:

  • برخی عامل‌های پایش و امنیت شخص ثالث به filesystem cgroup وابسته‌اند؛‏ آن‌ها را به نسخه‌های سازگار با v2 به‌روز کنید.
  • اگر cAdvisor را جداگانه به شکل DaemonSet اجرا می‌کنید،‏ آن را به v0.43.0 یا بالاتر ارتقا دهید.
  • برای برنامه‌های Java،‏ نسخه‌هایی را ترجیح دهید که کاملاً از cgroup v2 پشتیبانی می‌کنند:
    • OpenJDK / HotSpot:‏ jdk8u372،‏ 11.0.16،‏ 15 و بالاتر
    • IBM Semeru Runtimes: 8.0.382.0،‏ 11.0.20.0،‏ 17.0.8.0 و بالاتر
    • IBM Java: 8.0.8.6 و بالاتر
  • اگر از بسته‌ی uber-go/automaxprocs استفاده می‌کنید،‏ نسخه‌ی v1.5.1 یا بالاتر لازم است.
  • برای برنامه‌های Node.js،‏ نسخه‌هایی را ترجیح دهید که محدودیت memory cgroup v2 را تشخیص می‌دهند: از Node.js v20.3.0 (از طریق libuv). خط نسخه‌ی v18 این محدودیت را به‌طور قابل‌اعتماد تشخیص نمی‌دهد و ممکن است به‌جای limit تعیین‌شده برای Pod،‏ کل host memory را بخواند؛‏ نتیجه: اندازه‌ی نادرست heap و کشته‌شدن با OOM. روی این نسخه‌ها اندازه‌ی heap را صریحاً تنظیم کنید،‏ مثلاً با --max-old-space-size.

تشخیص نسخه‌ی cgroup روی Nodeهای Linux

نسخه‌ی cgroup به توزیع Linux و تنظیم پیش‌فرض سیستم‌عامل بستگی دارد. برای بررسی،‏ روی Node دستور stat -fc %T /sys/fs/cgroup/ را اجرا کنید:

shell
stat -fc %T /sys/fs/cgroup/

خروجی cgroup2fs یعنی cgroup v2،‏ و tmpfs یعنی cgroup v1.

منسوخ‌شدن cgroup v1

وضعیت قابلیت: منسوخ (deprecated) از v1.35

کوبرنتیز cgroup v1 را منسوخ کرده و حذف آن طبق سیاست منسوخ‌سازی کوبرنتیز انجام خواهد شد. kubelet دیگر به‌طور پیش‌فرض روی Nodeی با cgroup v1 اجرا نمی‌شود؛‏ برای غیرفعال‌کردن این رفتار،‏ مدیر cluster باید failCgroupV1 را در فایل پیکربندی kubelet (فصل ۱۳) برابر false بگذارد.

توضیح تکمیلی: درایور cgroup چیست و چرا مهم است؟

cgroupها سازوکاری در kernelاند،‏ اما یک process باید آن‌ها را بسازد و مدیریت کند؛‏ به این process درایور cgroup می‌گویند. در کوبرنتیز دو گزینه هست: cgroupfs (kubelet و runtime مستقیماً با filesystem cgroup کار می‌کنند) و systemd (مدیریت cgroup به systemd،‏ یعنی process init،‏ سپرده می‌شود). از کوبرنتیز 1.22،‏ پیش‌فرض kubeadm درایور systemd است؛‏ چون وقتی systemd سیستم init است،‏ بهتر است فقط یک مدیر cgroup روی سیستم باشد. اگر cgroupfs کنار systemd استفاده شود،‏ دو مدیر مختلف تصویر متفاوتی از فشار منابع می‌بینند و سیستم ناپایدار می‌شود. نکته‌ی مهم: درایور kubelet و runtime باید یکی باشند؛‏ ناهمخوانی آن‌ها از خطاهای رایج نصب است (فصل ۱۳).

در عمل،‏ فرق v1 و v2 برای کاربر معمولی کوبرنتیز معمولاً نامرئی است،‏ چون kubelet خودکار تشخیصش می‌دهد. اما دو مورد اهمیت عملیاتی دارد: (۱) قابلیت‌هایی مثل MemoryQoS و معیارهای PSI فقط روی v2 هستند؛‏ (۲) اگر ابزار پایش یا عامل امنیتی قدیمی مستقیماً مسیرهای v1 (مثل /sys/fs/cgroup/memory/...) را بخواند،‏ روی Node با v2 کار نمی‌کند،‏ چون چیدمان مسیرها یکپارچه شده.

shell

self-healing

کوبرنتیز با قابلیت‌های self-healing طراحی شده تا سلامت و دسترس‌پذیری workloadها حفظ شود: containerهای خراب را خودکار جایگزین می‌کند،‏ وقتی Nodeی در دسترس نیست workloadهایش را جای دیگر schedule می‌کند،‏ و مراقب است desired state سیستم حفظ شود.

قابلیت‌های self-healing

  • راه‌اندازی مجدد در سطح container: اگر containerی در یک Pod از کار بیفتد،‏ کوبرنتیز بر اساس restartPolicy (فصل ۳) دوباره راهش می‌اندازد.
  • جایگزینی replicaها: اگر Podی از یک Deployment یا StatefulSet (فصل ۴) از کار بیفتد،‏ کوبرنتیز Pod جایگزین می‌سازد تا تعداد replicaها حفظ شود. اگر Pod یک DaemonSet از کار بیفتد،‏ control plane،‏ Pod جایگزین را روی همان Node می‌سازد.
  • بازیابی storage ماندگار: اگر Nodeی که Podی با PersistentVolume (PV) وصل‌شده دارد از کار بیفتد،‏ کوبرنتیز می‌تواند آن volume را به Pod جدید روی Node دیگری وصل کند.
  • توزیع بار (load balancing) در Serviceها: اگر Podی پشت یک Service (فصل ۵) از کار بیفتد،‏ کوبرنتیز خودکار آن را از مقصدهای Service حذف می‌کند تا ترافیک فقط به Podهای سالم برسد.

اجزای کلیدی که self-healing را فراهم می‌کنند:

  • kubelet: مطمئن می‌شود containerها در حال اجرا هستند و خراب‌ها را دوباره راه می‌اندازد.
  • Deployment controller (از طریق ReplicaSet) و controllerهای ReplicaSet و StatefulSet و DaemonSet: تعداد دلخواه replicaهای Pod را حفظ می‌کنند.
  • PersistentVolume controller: وصل و جداکردن volumeها را برای workloadهای stateful مدیریت می‌کند.

ملاحظات

  • خرابی storage: اگر یک volume ماندگار در دسترس نباشد،‏ ممکن است بازیابی دستی لازم شود.
  • خطاهای برنامه: کوبرنتیز می‌تواند container را دوباره راه بیندازد،‏ اما مشکل اصلی برنامه را باید جداگانه حل کنید.

مطالعه‌ی بیشتر: Podها (فصل ۳) · controllerها (همین فصل) · PersistentVolumeها (فصل ۷) · مقیاس‌دهی (scaling) خودکار Nodeها (فصل ۱۰؛‏ که در صورت خرابی Nodeها هم نوعی ترمیم خودکار فراهم می‌کند).

توضیح تکمیلی: self-healing جادو نیست؛‏ مجموع چند control loop است

«self-healing» یک قابلیت یا جزء واحد نیست؛‏ نتیجه‌ی کار هم‌زمان چند control loop مستقل است که در بخش‌های قبلی این فصل دیدیم: Node controller که Nodeهای بی‌پاسخ را تشخیص می‌دهد و Podهایشان را evict می‌کند؛‏ kubelet که restartPolicy را روی containerها اجرا می‌کند؛‏ controllerهای ReplicaSet و Deployment و StatefulSet و DaemonSet (فصل ۴) که تعداد replicaها را هم‌سو نگه می‌دارند؛‏ و EndpointSlice controller که Podهای ناآماده را از Service بیرون می‌برد (فصل ۵).

نتیجه‌ی مهم: اگر هر کدام از این‌ها از کار بیفتد (مثلاً kube-controller-manager دچار crash شود)،‏ بخشی از self-healing متوقف می‌شود،‏ حتی اگر بقیه‌ی سیستم سالم باشد. برای همین دسترس‌پذیری بالای control plane (بخش گونه‌های معماری) پیش‌نیاز واقعی self-healing در production است.

garbage collection

«garbage collection» اصطلاحی کلی برای سازوکارهای مختلفی است که کوبرنتیز برای پاک‌سازی منابع cluster به کار می‌برد؛‏ از جمله پاک‌کردن:

  • Podهای خاتمه‌یافته (فصل ۳)
  • Jobهای تمام‌شده (فصل ۴)
  • شیءهایی که دیگر مالک (owner) ندارند
  • containerها و imageهای بلااستفاده
  • PersistentVolumeهای پویا که reclaim policy آن‌ها در StorageClass برابر Delete است (فصل ۷)
  • درخواست‌های امضای certificate (CSR) کهنه یا منقضی
  • Nodeهایی که در این حالت‌ها حذف شده‌اند:
    • در cloud،‏ وقتی cluster از cloud-controller-manager استفاده می‌کند؛‏
    • داخل سازمان،‏ وقتی cluster addonی مشابه cloud-controller-manager دارد.
  • شیءهای Lease مربوط به Nodeها

مالکان و وابسته‌ها (Owners and dependents)

خیلی از شیءهای کوبرنتیز از طریق owner reference (ارجاعی در metadata که مالک یک شیء را مشخص می‌کند) به هم وصل‌اند. این ارجاع‌ها به control plane می‌گویند کدام شیء به کدام وابسته است،‏ تا control plane و clientهای دیگر بتوانند قبل از حذف یک شیء،‏ منابع مرتبط با آن را پاک کنند. در بیشتر موارد کوبرنتیز این ارجاع‌ها را خودکار مدیریت می‌کند. مثلاً Deployment مالک ReplicaSet است و ReplicaSet مالک Podها؛‏ درست مثل درخت خانوادگی.

مالکیت با سازوکار labelها و selectorها (فصل ۸) فرق دارد. مثلاً Service شیءهای EndpointSlice می‌سازد و با label مشخص می‌کند کدام EndpointSliceها مال اوست؛‏ اما علاوه بر label،‏ هر EndpointSlice که از طرف یک Service مدیریت می‌شود یک owner reference هم دارد. owner referenceها کمک می‌کنند بخش‌های مختلف کوبرنتیز در شیءهایی که کنترلشان نمی‌کنند دخالت نکنند.

نکته

owner reference بین namespaceهای مختلف عمداً مجاز نیست. وابسته‌ی namespaceدار می‌تواند مالکی در سطح cluster یا namespaceدار داشته باشد؛‏ اما مالک namespaceدار باید در همان namespace وابسته باشد. در غیر این صورت ارجاع «ناموجود» حساب می‌شود و وقتی تأیید شود همه‌ی مالکان ناموجودند،‏ وابسته حذف می‌شود.

وابسته‌های سطح cluster فقط می‌توانند مالک سطح cluster داشته باشند. از v1.20،‏ اگر یک وابسته‌ی سطح cluster یک نوع namespaceدار را مالک خود معرفی کند،‏ ارجاع «حل‌نشدنی» حساب می‌شود و آن وابسته جمع‌آوری نمی‌شود.

از v1.20،‏ اگر garbage collection یک ownerReference نامعتبر بین‌namespaceی،‏ یا وابسته‌ی سطح clusterی با مالک namespaceدار پیدا کند،‏ یک event هشدار با دلیل OwnerRefInvalidNamespace گزارش می‌دهد. این eventها را این‌طور ببینید:

shell
kubectl get events -A --field-selector=reason=OwnerRefInvalidNamespace

cascading deletion

کوبرنتیز شیءهایی را که دیگر owner reference ندارند (مثل Podهایی که بعد از حذف ReplicaSetشان باقی مانده‌اند) بررسی و حذف می‌کند. وقتی شیئی را حذف می‌کنید،‏ می‌توانید تعیین کنید که آیا وابسته‌هایش هم خودکار حذف شوند یا نه؛‏ به این cascading deletion (حذف خودکار اشیای وابسته همراه با مالک) می‌گویند. دو نوع دارد:

  • cascading deletion پیش‌زمینه (Foreground)
  • cascading deletion پس‌زمینه (Background)

با finalizerها هم می‌توانید کنترل کنید که garbage collection کی و چطور منابع دارای owner reference را حذف کند.

cascading deletion پیش‌زمینه

در این روش،‏ شیء مالک ابتدا وارد وضعیت در حال حذف (deletion in progress) می‌شود:

  • API server فیلد metadata.deletionTimestamp را برابر زمان علامت‌گذاری برای حذف می‌گذارد؛‏
  • API server فیلد metadata.finalizers را برابر foregroundDeletion می‌گذارد؛‏
  • شیء تا پایان فرایند حذف همچنان از طریق API دیده می‌شود.

بعد controller وابسته‌هایی را که می‌شناسد حذف می‌کند،‏ و وقتی همه حذف شدند،‏ خود مالک را حذف می‌کند؛‏ از این لحظه دیگر در API دیده نمی‌شود.

در این روش،‏ فقط وابسته‌هایی جلوی حذف مالک را می‌گیرند که فیلد ownerReference.blockOwnerDeletion=true دارند و در cache controller garbage collection هستند. این cache ممکن است شیءهایی را که نوعشان قابل list/watch نیست،‏ یا شیءهایی را که هم‌زمان با حذف مالک ساخته شده‌اند،‏ شامل نشود. جزئیات در Use foreground cascading deletion.

cascading deletion پس‌زمینه

در این روش،‏ API server فوراً مالک را حذف می‌کند و controller garbage collection (پیش‌فرض یا سفارشی) وابسته‌ها را در پس‌زمینه پاک می‌کند. اگر finalizerی وجود داشته باشد،‏ تضمین می‌کند شیءها تا پایان کارهای پاک‌سازی لازم حذف نشوند. کوبرنتیز به‌طور پیش‌فرض از background deletion استفاده می‌کند،‏ مگر اینکه خودتان foreground deletion یا orphan (شیء وابسته‌ای که مالکش حذف شده ولی خودش باقی مانده) کردن وابسته‌ها را انتخاب کنید.

وابسته‌های orphan

وقتی کوبرنتیز مالکی را حذف می‌کند،‏ وابسته‌هایی که باقی می‌مانند شیءهای orphan نام دارند. به‌طور پیش‌فرض کوبرنتیز وابسته‌ها را حذف می‌کند؛‏ برای تغییر این رفتار،‏ راهنمای «Delete owner objects and orphan dependents» را ببینید.

جمع‌آوری containerها و imageهای بلااستفاده

kubelet هر پنج دقیقه imageهای بلااستفاده و هر یک دقیقه containerهای بلااستفاده را جمع‌آوری می‌کند. از ابزارهای بیرونی garbage collection استفاده نکنید،‏ چون ممکن است رفتار kubelet را خراب کنند و containerهایی را که باید بمانند پاک کنند.

برای تنظیم این رفتار،‏ kubelet را با یک فایل پیکربندی (فصل ۱۳) پیکربندی کنید و پارامترهای مربوط را در شیء KubeletConfiguration تغییر دهید.

چرخه‌ی عمر imageها

کوبرنتیز چرخه‌ی عمر همه‌ی imageها را با مدیر image (بخشی از kubelet) و با همکاری cadvisor مدیریت می‌کند. kubelet برای تصمیم‌گیری دو آستانه‌ی مصرف disk را در نظر می‌گیرد:

  • HighThresholdPercent
  • LowThresholdPercent

وقتی مصرف disk از HighThresholdPercent بالاتر برود،‏ جمع‌آوری شروع می‌شود و imageها به ترتیب آخرین زمان استفاده (از قدیمی‌ترین) حذف می‌شوند،‏ تا مصرف disk به LowThresholdPercent برسد. مثل کمدی که وقتی ۸۵٪ پر شد،‏ قدیمی‌ترین لباس‌ها را بیرون می‌ریزید تا به ۸۰٪ برسد.

جمع‌آوری imageها بر اساس سن

می‌توانید تعیین کنید یک image محلی حداکثر چه مدت می‌تواند بلااستفاده بماند،‏ مستقل از مصرف disk. این تنظیم kubelet است و برای هر Node جداگانه پیکربندی می‌شود: فیلد imageMaximumGCAge در فایل پیکربندی kubelet،‏ با قالب «مدت زمان» کوبرنتیز (duration؛‏ فصل ۱۷). مثلاً 12h45m یعنی ۱۲ ساعت و ۴۵ دقیقه.

نکته

این قابلیت استفاده از image را در طول restartهای kubelet دنبال نمی‌کند. اگر kubelet restart شود،‏ سن ثبت‌شده‌ی imageها صفر می‌شود و kubelet باید دوباره کل مدت imageMaximumGCAge را صبر کند تا imageها بر اساس سن قابل حذف شوند.

جمع‌آوری containerها

kubelet containerهای بلااستفاده را بر اساس این متغیرها جمع‌آوری می‌کند:

  • MinAge: حداقل سن container برای اینکه قابل جمع‌آوری باشد. با ‎0‎ غیرفعال می‌شود.
  • MaxPerPodContainer: حداکثر تعداد container مرده برای هر Pod. با مقدار منفی غیرفعال می‌شود.
  • MaxContainers: حداکثر تعداد کل containerهای مرده. با مقدار منفی غیرفعال می‌شود.

علاوه بر این‌ها،‏ kubelet containerهای ناشناس و حذف‌شده را هم (معمولاً از قدیمی‌ترین) جمع‌آوری می‌کند.

MaxPerPodContainer و MaxContainers ممکن است با هم تعارض پیدا کنند؛‏ وقتی نگه‌داشتن حداکثر container برای هر Pod از سقف کل بیشتر شود. در این حالت kubelet مقدار MaxPerPodContainer را کم می‌کند؛‏ در بدترین حالت تا ‎1‎،‏ و قدیمی‌ترین containerها حذف می‌شوند. containerهای Podهای حذف‌شده هم بعد از گذشتن از MinAge پاک می‌شوند.

نکته

kubelet فقط containerهایی را جمع‌آوری می‌کند که خودش مدیریت می‌کند.

پیکربندی garbage collection

garbage collection هر منبع با گزینه‌های controllerی که آن منبع را مدیریت می‌کند تنظیم می‌شود:

  • پیکربندی cascading deletion شیءها
  • پیکربندی پاک‌سازی Jobهای تمام‌شده (فصل ۴)

مطالعه‌ی بیشتر: مالکیت شیءها · finalizerهای کوبرنتیز · TTL controller که Jobهای تمام‌شده را پاک می‌کند (فصل ۴).

توضیح تکمیلی: blockOwnerDeletion و رفتار واقعی kubectl delete

وقتی kubectl delete deployment web را اجرا می‌کنید،‏ kubectl به‌طور پیش‌فرض از background deletion استفاده می‌کند: Deployment فوراً حذف می‌شود و بلافاصله بعدش ReplicaSetش (که به Deployment owner reference دارد)،‏ و به همین ترتیب Podهای آن ReplicaSet. اما اگر بخواهید مطمئن باشید همه چیز واقعاً حذف شده و بعد اعلام پایان کنید (مثلاً در خط لوله‌ی CI که بلافاصله می‌خواهد همان نام را دوباره بسازد)،‏ از --cascade=foreground استفاده کنید:

shell
kubectl delete deployment web --cascade=foreground --wait=true

با این گزینه،‏ دستور تا حذف واقعی Deployment و همه‌ی وابسته‌هایش (آن‌هایی که blockOwnerDeletion=true دارند) منتظر می‌ماند. برای orphan کردن Podها (نگه‌داشتنشان بدون مالک) از --cascade=orphan استفاده می‌شود؛‏ کاربرد رایجش حذف یک StatefulSet یا Deployment بدون دست‌زدن به Podهای در حال اجراست (مثلاً برای بررسی دستی پیش از حذف نهایی،‏ یا تغییر فیلدهای غیرقابل‌تغییر StatefulSet).

آزمایش عملی: cascading deletion و owner referenceها را ببینید
shell
kubectl create deployment web --image=nginx --replicas=2
RS=$(kubectl get rs -l app=web -o jsonpath='{.items[0].metadata.name}')
kubectl get rs $RS -o jsonpath='{.metadata.ownerReferences}'
echo
kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.ownerReferences}'
خروجی نمونه
[{"apiVersion":"apps/v1","kind":"Deployment","name":"web","uid":"a1b2...","controller":true,"blockOwnerDeletion":true}]
[{"apiVersion":"apps/v1","kind":"ReplicaSet","name":"web-6f8d9c7b8f","uid":"c3d4...","controller":true,"blockOwnerDeletion":true}]

حالا ReplicaSet را با حالت orphan حذف کنید و ببینید Podها می‌مانند ولی owner reference آن‌ها از بین می‌رود:

shell
kubectl delete rs $RS --cascade=orphan
kubectl get pods -l app=web
# the Pods are still Running and briefly have no owner
kubectl get rs,pods -l app=web
# the Deployment creates a new ReplicaSet; the Pod template is unchanged, so hash and name are the same
# and it adopts the orphan Pods that match its selector; no new Pod is created

پراکسی نسخه‌های مختلط (Mixed Version Proxy)

وضعیت قابلیت: Kubernetes v1.36 [beta] (به‌طور پیش‌فرض فعال؛‏ feature gate UnknownVersionInteroperabilityProxy)

کوبرنتیز 1.37 قابلیتی در مرحله‌ی beta دارد که به یک API server اجازه می‌دهد درخواست‌ها را به API serverهای همتا (peer) هدایت (proxy) کند. همچنین clientها از طریق discovery دیدی کامل و یکپارچه از همه‌ی منابعی که در کل cluster ارائه می‌شود پیدا می‌کنند. این وقتی به کار می‌آید که چند API server با نسخه‌های مختلف کوبرنتیز در یک cluster اجرا می‌شوند؛‏ مثلاً در طول یک ارتقای طولانی.

این قابلیت به مدیران cluster کمک می‌کند clusterهای با دسترس‌پذیری بالا را امن‌تر ارتقا دهند:

  1. controllerهایی که برای کارهای مهم به فهرست کامل منابع در discovery تکیه دارند،‏ همیشه دید کامل همه‌ی منابع را می‌گیرند. به این discovery کامل در سطح cluster Peer-aggregated discovery می‌گویند.
  2. درخواست‌های منابعی که در طول ارتقا ساخته می‌شوند،‏ به kube-apiserver درست می‌رسند. این هدایت جلوی خطاهای غیرمنتظره‌ی 404 Not Found ناشی از ارتقا را می‌گیرد؛‏ به این سازوکار Mixed Version Proxy می‌گویند.

فعال‌سازی

مطمئن شوید هنگام اجرای API server،‏ feature gate UnknownVersionInteroperabilityProxy فعال است:

shell
# required flags for this feature (the gate is on by default since v1.36)
# --requestheader-allowed-names may be empty to allow any Common Name
# --peer-advertise-ip/--peer-advertise-port are optional
kube-apiserver \
  --feature-gates=UnknownVersionInteroperabilityProxy=true \
  --peer-ca-file=<path to kube-apiserver CA cert> \
  --proxy-client-cert-file=<path to aggregator proxy cert> \
  --proxy-client-key-file=<path to aggregator proxy key> \
  --requestheader-client-ca-file=<path to aggregator CA cert> \
  --requestheader-allowed-names=<valid Common Names for the proxy client cert> \
  --peer-advertise-ip=<IP that peers use to reach this kube-apiserver> \
  --peer-advertise-port=<port that peers use to reach this kube-apiserver>
  # ...plus the other flags you normally use

یادداشت نویسنده: در نمونه‌ی مستندات،‏ کامنت‌ها وسط دستور چندخطی آمده و انتهای چند flag ویرگول اضافه دارد؛‏ آن نسخه در shell اجرا نمی‌شود. اینجا به شکل یک دستور معتبر بازنویسی شده است. از v1.36 این gate به‌طور پیش‌فرض فعال است و flag مربوط به آن فقط برای صراحت آمده است.

ارتباط و authentication بین API serverها

  • kube-apiserver مبدأ از همان flagهای موجود client authentication API server (فصل ۱۵)،‏ یعنی --proxy-client-cert-file و --proxy-client-key-file،‏ برای معرفی خودش استفاده می‌کند و همتای مقصد این هویت را بر اساس --requestheader-client-ca-file تأیید می‌کند.
  • برای تأیید server certificate مقصد،‏ روی API server مبدأ با flag --peer-ca-file یک بسته‌ی certificate CA تنظیم کنید.

تنظیم آدرس همتاها

برای تعیین آدرس شبکه‌ای که همتاها برای هدایت درخواست به یک kube-apiserver استفاده می‌کنند،‏ از flagهای --peer-advertise-ip و --peer-advertise-port (یا فیلدهای معادل در فایل پیکربندی) استفاده کنید. اگر تنظیم نشوند،‏ همتاها از --advertise-address یا --bind-address استفاده می‌کنند،‏ و اگر آن‌ها هم نباشند،‏ از network interface پیش‌فرض host.

Peer-aggregated discovery

با فعال‌بودن این قابلیت،‏ درخواست‌های discovery به‌طور پیش‌فرض سندی جامع برمی‌گردانند که همه‌ی منابع ارائه‌شده توسط همه‌ی apiserverهای cluster را فهرست می‌کند. اگر سند غیرتجمیعی (فقط منابع همان apiserver) را می‌خواهید،‏ این سرآیند Accept را به درخواست اضافه کنید:

HTTP Accept header
application/json;g=apidiscovery.k8s.io;v=v2;as=APIGroupDiscoveryList;profile=nopeer
نکته

Peer-aggregated discovery فقط برای درخواست‌های Aggregated Discovery (فصل ۸) به آدرس /apis پشتیبانی می‌شود،‏ نه برای Discovery قدیمی (غیرتجمیعی) (فصل ۸).

هدایت درخواست بین نسخه‌ها

با فعال‌بودن این قابلیت،‏ aggregation layer (لایه‌ای در kube-apiserver که APIهای دیگر را زیر همان API server ارائه می‌کند؛‏ فصل ۱۵) فیلتری ویژه بارگذاری می‌کند که:

  • وقتی درخواستی به API serverی می‌رسد که نمی‌تواند آن API را ارائه دهد (چون نسخه‌اش قدیمی‌تر از معرفی آن API است،‏ یا API روی آن خاموش است)،‏ سعی می‌کند درخواست را به همتایی بفرستد که می‌تواند. این کار با تشخیص group/version/resourceهایی انجام می‌شود که server محلی نمی‌شناسد.
  • اگر همتا پاسخ ندهد،‏ API server مبدأ خطای 503 (Service Unavailable) برمی‌گرداند.

پشت صحنه چطور کار می‌کند؟

وقتی API server درخواستی می‌گیرد،‏ اول با سند discovery غیرتجمیعی بررسی می‌کند کدام API serverها می‌توانند آن منبع را ارائه دهند:

  • اگر منبع در سند discovery خود همین API server باشد (مثلاً GET /api/v1/pods/some-pod)،‏ درخواست محلی رسیدگی می‌شود.
  • اگر منبع (مثلاً GET /apis/resource.k8s.io/v1beta1/resourceclaims) در سند خود این server (server رسیدگی‌کننده) نباشد،‏ احتمالاً چون آن API در نسخه‌ی جدیدتری معرفی شده و این server قدیمی‌تر است،‏ server رسیدگی‌کننده با بررسی اسناد discovery همه‌ی همتاها،‏ همتایی را که آن group/version/resource را ارائه می‌دهد پیدا می‌کند و درخواست را به آن می‌فرستد.
  • اگر هیچ همتایی آن منبع را نشناسد،‏ درخواست به زنجیره‌ی رسیدگی خود server می‌رود که در نهایت 404 (Not Found) برمی‌گرداند.
  • اگر همتایی انتخاب شد ولی پاسخ نداد (مثلاً مشکل شبکه،‏ یا رقابتی بین رسیدن درخواست و ثبت اطلاعات همتا)،‏ server رسیدگی‌کننده 503 (Service Unavailable) برمی‌گرداند.
توضیح تکمیلی: چرا این قابلیت در rolling upgrade (ارتقای یکی‌یکی اجزا،‏ بدون قطعی) control plane مهم است؟

در control planeی با دسترس‌پذیری بالا،‏ ارتقا معمولاً تدریجی روی instanceهای kube-apiserver انجام می‌شود: یکی ارتقا می‌یابد،‏ بعد بعدی و الی آخر. در این فاصله،‏ بعضی apiserverها نسخه‌ی جدیدند (و APIهای جدید را می‌شناسند) و بعضی هنوز قدیمی. بدون این قابلیت،‏ اگر clientی (مثلاً یک controller یا kubectl) پشت load balancer به‌طور تصادفی به apiserver قدیمی برسد،‏ برای منبعی که واقعاً در cluster وجود دارد خطای 404 می‌گیرد. با این قابلیت،‏ همان apiserver قدیمی درخواست را به همتایی که منبع را می‌شناسد می‌فرستد و کاربر هرگز این 404 گذرا را نمی‌بیند. زیرساخت این کار همان Leaseهای هویت API server (بخش Leaseها) است: هر apiserver باید بتواند همتاهایش را کشف کند.

خاموش‌شدن Node (Node Shutdown)

در یک cluster کوبرنتیز،‏ Node ممکن است طبق برنامه و به‌صورت مرتب (graceful) خاموش شود،‏ یا ناگهانی و نامرتب (non-graceful)؛‏ مثلاً به‌خاطر قطع برق یا عوامل بیرونی دیگر. اگر Node پیش از خاموش‌شدن drain نشده باشد،‏ خاموش‌شدنش می‌تواند باعث خرابی workloadها شود.

هشدار

بسته‌ی unattended-upgrades در Debian با پیکربندی معمولش با graceful shutdown (خاموش شدن مرتب،‏ با فرصت دادن به Podها برای پایان کار) Node تداخل دارد: این بسته مهلت خاموش‌شدن server را تغییر می‌دهد و در نتیجه kubelet نمی‌تواند قفل لازم برای رسیدگی درست به event خاموش‌شدن را بگیرد.

این مشکل وقتی رخ می‌دهد که shutdownGracePeriod بیشتر از ۳۰ ثانیه باشد. برای جلوگیری،‏ بخشی از پیکربندی unattended-upgrades را خنثی کنید: فایل /etc/systemd/logind.conf.d/unattended-upgrades-logind-maxdelay.conf را به شکل یک پیوند نمادین (symlink) به /dev/null بسازید. جزئیات در مستندات logind.conf.

graceful shutdown Node (Graceful node shutdown)

kubelet سعی می‌کند خاموش‌شدن سیستم Node را تشخیص دهد و Podهای در حال اجرا را خاتمه دهد. kubelet تضمین می‌کند Podها در این فرایند از روند عادی خاتمه‌ی Pod (فصل ۳) پیروی کنند و در این مدت هیچ Pod جدیدی نمی‌پذیرد (حتی اگر از قبل به این Node سپرده شده باشد).

فعال‌سازی

Linux: وضعیت قابلیت: beta از v1.21؛‏ پیش‌فرض فعال؛‏ feature gate GracefulNodeShutdown

روی Linux این قابلیت با feature gate GracefulNodeShutdown کنترل می‌شود که از 1.21 به‌طور پیش‌فرض فعال است.

نکته

این قابلیت به systemd وابسته است،‏ چون از قفل‌های بازدارنده‌ی systemd (inhibitor locks) برای به تأخیر انداختن خاموش‌شدن Node به مدت مشخص استفاده می‌کند.

Windows: وضعیت قابلیت: beta از v1.34؛‏ پیش‌فرض فعال؛‏ feature gate WindowsGracefulNodeShutdown

روی Windows این قابلیت با WindowsGracefulNodeShutdown کنترل می‌شود که در 1.32 به‌صورت alpha معرفی شد و از 1.34 در مرحله‌ی beta و به‌طور پیش‌فرض فعال است.

نکته

این قابلیت روی Windows به این وابسته است که kubelet به شکل سرویس ویندوز اجرا شود؛‏ در این حالت یک service control handler ثبت می‌کند تا event پیش از خاموش‌شدن (preshutdown) را به مدت مشخص به تأخیر بیندازد. graceful shutdown روی Windows قابل لغو نیست.

اگر kubelet به شکل سرویس ویندوز اجرا نشود،‏ نمی‌تواند event Preshutdown را تنظیم و پایش کند،‏ و Node باید از روند «non-graceful shutdown» (پایین‌تر) عبور کند. در این حالت kubelet از کار نمی‌افتد،‏ اما در log خطا ثبت می‌کند که باید به شکل سرویس ویندوز اجرا شود.

پیکربندی graceful shutdown

دقت کنید که به‌طور پیش‌فرض هر دو گزینه‌ی زیر،‏ یعنی shutdownGracePeriod و shutdownGracePeriodCriticalPods،‏ برابر صفرند؛‏ پس این قابلیت عملاً کاری نمی‌کند. برای فعال‌شدن،‏ هر دو باید مقدار غیرصفر مناسب داشته باشند.

وقتی kubelet از خاموش‌شدن Node باخبر می‌شود،‏ شرط NotReady را با reason برابر "node is shutting down" روی Node می‌گذارد. kube-scheduler به این شرط احترام می‌گذارد و هیچ Podی روی این Node schedule نمی‌کند (انتظار می‌رود schedulerهای شخص ثالث هم همین منطق را دنبال کنند).‏ kubelet علاوه بر این در مرحله‌ی پذیرش Pod (PodAdmission) هم Podها را رد می‌کند،‏ تا حتی Podهایی که toleration node.kubernetes.io/not-ready:NoSchedule را دارند هم آنجا اجرا نشوند.

هم‌زمان با ثبت این شرط،‏ kubelet خاتمه‌ی Podهای محلی را شروع می‌کند،‏ در دو مرحله:

  1. خاتمه‌ی Podهای عادی؛‏
  2. خاتمه‌ی Podهای حیاتی (critical pods؛‏ فصل ۹).

این قابلیت با دو گزینه در KubeletConfiguration (فصل ۱۳) پیکربندی می‌شود:

  • shutdownGracePeriod: کل مدتی که Node خاموش‌شدن را به تأخیر می‌اندازد؛‏ یعنی کل مهلت خاتمه برای Podهای عادی و حیاتی روی هم.
  • shutdownGracePeriodCriticalPods: مدتی که برای خاتمه‌ی Podهای حیاتی کنار گذاشته می‌شود؛‏ باید کمتر از shutdownGracePeriod باشد.
نکته

گاهی خاموش‌شدن Node توسط سیستم (یا دستی توسط مدیر) لغو می‌شود. در این حالت Node به وضعیت Ready برمی‌گردد،‏ اما Podهایی که خاتمه‌شان شروع شده بود توسط kubelet برگردانده نمی‌شوند و باید دوباره schedule شوند.

مثال: با shutdownGracePeriod=30s و shutdownGracePeriodCriticalPods=10s،‏ kubelet خاموش‌شدن را ۳۰ ثانیه عقب می‌اندازد: ۲۰ ثانیه‌ی اول (۳۰ منهای ۱۰) برای خاتمه‌ی Podهای عادی و ۱۰ ثانیه‌ی آخر برای Podهای حیاتی.

نکته

Podهایی که در graceful shutdown evict می‌شوند،‏ «خاموش‌شده» علامت می‌خورند: kubectl get pods وضعیتشان را Terminated نشان می‌دهد و kubectl describe pod می‌گوید به دلیل خاموش‌شدن Node evict شده‌اند:

output
Reason:         Terminated
Message:        Pod was terminated in response to imminent node shutdown.

graceful shutdown بر اساس اولویت Pod

وضعیت قابلیت: beta از v1.24؛‏ پیش‌فرض فعال؛‏ feature gate GracefulNodeShutdownBasedOnPodPriority

برای انعطاف بیشتر در ترتیب خاموش‌شدن Podها،‏ این قابلیت از PriorityClass (شیئی که اولویت Podها را تعیین می‌کند) Podها پیروی می‌کند و به مدیر cluster اجازه می‌دهد ترتیب خاموش‌شدن را صراحتاً بر اساس کلاس‌های اولویت (فصل ۹) تعریف کند.

graceful shutdown معمولی،‏ Podها را در دو مرحله خاموش می‌کند (عادی،‏ بعد حیاتی). اگر ترتیب دقیق‌تری لازم دارید،‏ از این روش استفاده کنید: خاموش‌شدن در چند مرحله انجام می‌شود و هر مرحله یک PriorityClass را با مهلت مشخص خودش خاموش می‌کند.

فرض کنید این کلاس‌های اولویت در cluster تعریف شده‌اند:

نام PriorityClassمقدار
custom-class-a100000
custom-class-b10000
custom-class-c1000
regular/unset0

تنظیم shutdownGracePeriodByPodPriority در پیکربندی kubelet (فصل ۱۳) می‌تواند این باشد:

مقدار اولویتمهلت خاموش‌شدن

10000۱۸۰ ثانیه

معادل YAML آن:

  - priority: 100000
    shutdownGracePeriodSeconds: 10
  - priority: 10000
    shutdownGracePeriodSeconds: 180
  - priority: 1000
    shutdownGracePeriodSeconds: 120
  - priority: 0

لازم نیست برای همه‌ی کلاس‌ها مقدار بدهید؛‏ مثلاً این تنظیم هم معتبر است:

مقدار اولویتمهلت خاموش‌شدن

در این حالت Podهای custom-class-b در همان دسته‌ی custom-class-c خاموش می‌شوند.

اگر در یک بازه هیچ Podی نباشد،‏ kubelet منتظرش نمی‌ماند و فوراً سراغ بازه‌ی بعدی می‌رود. اگر قابلیت فعال باشد ولی هیچ پیکربندی‌ای داده نشود،‏ هیچ ترتیب‌دهی‌ای انجام نمی‌شود.

برای استفاده،‏ feature gate GracefulNodeShutdownBasedOnPodPriority باید فعال باشد و ShutdownGracePeriodByPodPriority در پیکربندی kubelet (فصل ۱۳) با مقادیر اولویت و مهلت‌های متناظر تنظیم شود.

نکته

این قابلیت در v1.23 به‌صورت alpha معرفی شد و در کوبرنتیز 1.37 در مرحله‌ی beta و به‌طور پیش‌فرض فعال است.

معیارهای graceful_shutdown_start_time_seconds و graceful_shutdown_end_time_seconds در زیرسیستم kubelet برای پایش خاموش‌شدن Nodeها منتشر می‌شوند.

رسیدگی به non-graceful shutdown Node (Non-graceful node shutdown)

وضعیت قابلیت: stable از v1.28؛‏ پیش‌فرض فعال؛‏ feature gate NodeOutOfServiceVolumeDetach پس از v1.31 حذف شده و قابلیت همیشه فعال است

ممکن است مدیر خاموش‌شدن kubelet (Node Shutdown Manager) خاموش‌شدن Node را تشخیص ندهد؛‏ یا چون فرمان خاموش‌شدن قفل‌های بازدارنده‌ی kubelet را فعال نمی‌کند،‏ یا به خاطر خطای کاربر (یعنی ShutdownGracePeriod و ShutdownGracePeriodCriticalPods درست تنظیم نشده‌اند).

در این حالت،‏ Podهای متعلق به StatefulSet روی Node خاموش‌شده در وضعیت Terminating گیر می‌کنند و نمی‌توانند به Node سالم دیگری منتقل شوند. دلیلش این است که kubelet روی Node خاموش در دسترس نیست تا Podها را حذف کند،‏ پس StatefulSet نمی‌تواند Pod جدیدی با همان نام بسازد. اگر Podها volume داشته باشند،‏ VolumeAttachmentها هم از Node خاموش حذف نمی‌شوند و volumeها نمی‌توانند به Node جدید وصل شوند. در نتیجه برنامه‌ی آن StatefulSet درست کار نمی‌کند. اگر Node اصلی دوباره روشن شود،‏ kubelet آن Podها را حذف می‌کند و Podهای جدید روی Node دیگری ساخته می‌شوند؛‏ اما اگر روشن نشود،‏ این Podها برای همیشه در Terminating می‌مانند.

برای رفع این وضعیت،‏ کاربر می‌تواند دستی taint node.kubernetes.io/out-of-service را با اثر NoExecute یا NoSchedule به Node اضافه کند تا آن را «خارج از سرویس» علامت بزند. در این صورت،‏ Podهای روی Node که toleration این taint را ندارند به‌زور حذف می‌شوند و volumeهای Podهای در حال خاتمه فوراً جدا می‌شوند؛‏ پس Podها سریع روی Node دیگری بازیابی می‌شوند.

در non-graceful shutdown،‏ Podها در دو مرحله خاتمه می‌یابند:

  1. حذف اجباری Podهایی که toleration out-of-service را ندارند؛‏
  2. جداکردن فوری volumeهای این Podها.
نکته

پیش از افزودن taint node.kubernetes.io/out-of-service باید مطمئن شوید Node واقعاً خاموش است (و در حال restart نیست).

بعد از اینکه Podها به Node جدید منتقل شدند و بررسی کردید Node خاموش‌شده بازیابی شده،‏ باید taint را دستی حذف کنید؛‏ چون خودتان اضافه‌اش کرده بودید.

جداکردن اجباری storage پس از مهلت

در هر شرایطی که حذف یک Pod به مدت ۶ دقیقه موفق نشود،‏ اگر Node در آن لحظه ناسالم باشد،‏ کوبرنتیز volumeهایی را که در حال unmount هستند به‌زور جدا می‌کند. هر workload که هنوز روی آن Node اجرا می‌شود و از volume جداشده استفاده می‌کند،‏ مشخصات CSI را نقض می‌کند؛‏ مشخصاتی که می‌گوید ControllerUnpublishVolume باید فقط بعد از موفقیت همه‌ی NodeUnstageVolume و NodeUnpublishVolumeها صدا زده شود. در این شرایط ممکن است داده‌های volume خراب شوند.

این رفتار اختیاری است و می‌توان به‌جای آن از روند «non-graceful shutdown» استفاده کرد. برای غیرفعال‌کردنش،‏ disable-force-detach-on-timeout را در kube-controller-manager تنظیم کنید؛‏ در این صورت VolumeAttachment (فصل ۷) مربوط به volume روی Nodeی که بیش از ۶ دقیقه ناسالم بوده حذف نمی‌شود،‏ و Podهای ناسالمی که هنوز به volume وصل‌اند باید از طریق روند non-graceful shutdown بازیابی شوند.

نکته

در استفاده از روند non-graceful shutdown احتیاط کنید؛‏ انحراف از مراحل مستندشده می‌تواند به خرابی داده منجر شود.

مطالعه‌ی بیشتر: وبلاگ Non-Graceful Node Shutdown · معماری cluster:‏ Nodeها (همین فصل).

توضیح تکمیلی: مرتب یا نامرتب،‏ کدام در چه سناریویی؟

graceful shutdown برای وقتی است که kubelet فرصت دارد خاموش‌شدن را ببیند: خاموش‌کردن دستی Node برای نگهداری (systemctl poweroff)،‏ یا بازپس‌گیری VM در cloud با هشدار قبلی (مثل VMهای preemptible که سیگنال ACPI می‌فرستند). در این حالت‌ها قفل بازدارنده‌ی systemd به kubelet وقت می‌دهد Podها را طبق ترتیب اولویت یا مراحل عادی/حیاتی درست خاتمه دهد،‏ قبل از اینکه ماشین واقعاً خاموش شود.

non-graceful shutdown برای وقتی است که هیچ هشداری نبوده: قطع ناگهانی برق در دیتاسنتر،‏ VMی که به‌زور کشته شده (نه متوقف)،‏ یا Nodeی که هنگ کرده و اصلاً پاسخ نمی‌دهد. اینجا Podها (مخصوصاً Podهای StatefulSet با PersistentVolume) در Terminating گیر می‌کنند؛‏ چون control plane نمی‌داند Node واقعاً مرده یا فقط شبکه‌اش قطع شده (partition)،‏ و برای حفظ امنیت داده صبر می‌کند (تا مبادا دو Pod هم‌زمان روی یک volume از نوع ReadWriteOnce بنویسند). اینجاست که مدیر باید دستی taint node.kubernetes.io/out-of-service را بگذارد و به کوبرنتیز بگوید: «من تضمین می‌کنم این Node واقعاً خاموش است؛‏ جلو برو».

آزمایش عملی: پیکربندی graceful shutdown با ترتیب مبتنی بر اولویت (روی یک VM آزمایشی)

یک پیکربندی kubelet با graceful shutdown و ترتیب بر اساس اولویت بسازید (روی هر Node یا از طریق KubeletConfiguration در kubeadm):

/var/lib/kubelet/config.yaml (بخش مربوطه)
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# do NOT also set shutdownGracePeriod / shutdownGracePeriodCriticalPods here
shutdownGracePeriodByPodPriority:
  - priority: 2000001000   # system-node-critical
    shutdownGracePeriodSeconds: 20
  - priority: 1000         # PriorityClass defined for the checkout team
    shutdownGracePeriodSeconds: 30
  - priority: 0
    shutdownGracePeriodSeconds: 10
shell (بعد از restart kubelet و شبیه‌سازی shutdown)
sudo systemctl restart kubelet
sudo shutdown -h +1   # on a test worker node, never the control plane!

# about a minute later (once shutdown has started), from another machine:
kubectl get node worker-3 -o jsonpath='{.status.conditions[?(@.type=="Ready")]}'
kubectl get pods -o wide --field-selector spec.nodeName=worker-3
خروجی نمونه
{"type":"Ready","status":"False","reason":"KubeletNotReady","message":"node is shutting down"}
NAME              READY   STATUS        RESTARTS   AGE   NODE
checkout-7f9-abc  0/1     Terminating   0          2h    worker-3

دقت کنید Pod با اولویت ۱۰۰۰ (تیم checkout) تا ۳۰ ثانیه برای خاتمه‌ی مرتب فرصت دارد،‏ در حالی که Pod با اولویت پیش‌فرض صفر فقط ۱۰ ثانیه؛‏ دقیقاً طبق جدول shutdownGracePeriodByPodPriority. Podهای system-cluster-critical (اولویت 2000000000) به ردیف 1000 می‌افتند،‏ چون ردیف جداگانه‌ای برایشان تعریف نشده. کل تأخیر خاموش‌شدن برابر مجموع مهلت‌هاست (۲۰+۳۰+۱۰ = ۶۰ ثانیه).

هشدار

کنار shutdownGracePeriodByPodPriority،‏ فیلدهای shutdownGracePeriod و shutdownGracePeriodCriticalPods را تنظیم نکنید. validation پیکربندی kubelet این ترکیب را با خطای Cannot specify both shutdownGracePeriodByPodPriority and shutdownGracePeriod at the same time رد می‌کند و kubelet اجرا نمی‌شود؛‏ یا این یکی یا آن دو.

  1. مفهومیچرا کوبرنتیز control plane را از worker Nodeها جدا می‌کند؟ اگر همه‌ی اجزا (kube-apiserver،‏ etcd،‏ scheduler،‏ controller-manager و kubelet) روی یک ماشین اجرا شوند،‏ چه معماری‌ای داریم و چه محدودیت‌هایی دارد؟
    پاسخ

    این جداسازی اجازه می‌دهد منابع متناسب با هر نقش تخصیص یابد (control plane سبک اما حیاتی،‏ worker Nodeهای سنگین برای workload)،‏ هر کدام مستقل مقیاس بگیرند،‏ و مهم‌تر از همه مقاومت در برابر خرابی و دسترس‌پذیری بالا فراهم شود: اگر یک worker Node از بین برود،‏ control plane روی ماشین‌های دیگر سالم است و Podها را جای دیگر schedule می‌کند. اگر همه روی یک ماشین باشند (مثل minikube تک‌Node)،‏ cluster کاملاً معتبری است اما یک نقطه‌ی شکست واحد (single point of failure) دارد: با از کار افتادن آن ماشین،‏ هم control plane و هم workloadها از بین می‌روند. به همین دلیل مستندات تأکید می‌کند در production control plane روی چند کامپیوتر اجرا شود.

(۲) certificateها: --peer-ca-file روی apiserver مبدأ،‏ و --proxy-client-cert-file/key-file و --requestheader-client-ca-file باید روی همه‌ی instanceها درست و سازگار تنظیم شده باشند؛‏ خطا در این‌ها باعث شکست اتصال بین همتاها و خطای 503 (نه لزوماً 404) می‌شود. (۳) اگر --peer-advertise-ip/port تنظیم نشده و --advertise-address یا --bind-address نادرست است،‏ همتاها آدرس اشتباهی برای هدایت درخواست پیدا می‌کنند. بعد از این بررسی‌ها،‏ سند discovery را جداگانه از هر apiserver بگیرید (kubectl get --raw /apis مستقیم به آدرس هر instance) تا مطمئن شوید discovery تجمیعی کامل است،‏ و Leaseهای هویت apiserverها را هم در kube-system بررسی کنید.

    سازوکاری که به kubelet اجازه می‌دهد خاموش‌شدن ماشین را به تأخیر بیندازد تا Podها درست خاتمه یابند،‏ «قفل بازدارنده‌ی systemd» (inhibitor lock) است؛‏ قابلیتی مشخص از systemd که به یک process اجازه می‌دهد موقتاً جلوی خاموش‌شدن یا reboot را بگیرد. بدون آن،‏ راه استانداردی نیست که kubelet به سیستم بگوید «چند ثانیه صبر کن». روی Windows معادلش این است که kubelet به شکل سرویس ویندوز اجرا شود و یک service control handler برای event preshutdown ثبت کند.

  18. عملییک PriorityClass با مقدار ۱۰۰۰ برای Podهای یک namespace بسازید،‏ shutdownGracePeriodByPodPriority متناظر را در پیکربندی kubelet تنظیم کنید و نشان دهید Podهای آن namespace مهلت متفاوتی از Podهای پیش‌فرض می‌گیرند.
    پاسخ
    priorityclass.yaml
    apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: checkout-critical
value: 1000
globalDefault: false
description: "checkout path Pods; shut down later during node shutdown"
    shell
    kubectl apply -f priorityclass.yaml
kubectl patch deployment checkout -p '{"spec":{"template":{"spec":{"priorityClassName":"checkout-critical"}}}}'
kubectl get pods -l app=checkout -o jsonpath='{.items[0].spec.priority}'

    باید عدد ‎1000‎ برگردد که با ردیف priority: 1000, shutdownGracePeriodSeconds: 120 در پیکربندی نمونه‌ی مستندات (بخش «graceful shutdown بر اساس اولویت Pod») مطابقت دارد؛‏ یعنی این Podها در graceful shutdown ۱۲۰ ثانیه فرصت دارند،‏ در حالی که Podهای با اولویت صفر فقط ۶۰ ثانیه.

  19. سناریوی عملیاتییک StatefulSet از PostgreSQL دارید (pg-primary-0 با یک PersistentVolume از نوع ReadWriteOnce). برق rack مربوط به worker-7 کاملاً قطع می‌شود. بعد از ۱۵ دقیقه:
    خروجی
    NAME           STATUS     AGE
worker-7       NotReady   120d

NAME           READY   STATUS        NODE
pg-primary-0   0/1     Terminating   worker-7
    StatefulSet نمی‌تواند Pod جدید بسازد و برنامه از دسترس خارج است. طبق بخش «non-graceful shutdown Node»،‏ دقیقاً چرا این گیر پیش آمده و چه دستوری اجرا می‌کنید؟ این اقدام چه ریسکی دارد و چطور کمش می‌کنید؟
    پاسخ

    چون kubelet روی worker-7 در دسترس نیست،‏ کسی نمی‌تواند شیء Pod را واقعاً از API حذف کند و VolumeAttachment را جدا کند. StatefulSet هویت ثابت دارد (نام ثابت pg-primary-0) و تا Pod قبلی واقعاً حذف نشود،‏ نمی‌تواند Pod هم‌نام جدید بسازد؛‏ volume از نوع ReadWriteOnce هم نمی‌تواند هم‌زمان جای دیگری وصل شود. (توجه: بعد از ۶ دقیقه،‏ جداکردن اجباری volume ممکن است خودکار انجام شود،‏ اما مشکل نام Pod همچنان باقی است.)

    راه‌حل: پس از تأیید قطعی اینکه worker-7 واقعاً خاموش است (نه فقط قطع شبکه)،‏ دستور kubectl taint nodes worker-7 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute را اجرا کنید تا Pod به‌زور حذف و volume فوراً جدا شود و StatefulSet یک pg-primary-0 جدید روی Node سالم بسازد. بعد از بازیابی،‏ taint را دستی بردارید.

    ریسک اصلی: اگر worker-7 در واقع روشن باشد و فقط شبکه‌اش قطع شده باشد،‏ دو process PostgreSQL ممکن است هم‌زمان روی یک volume بنویسند و داده خراب شود. برای همین مستندات تأکید می‌کند پیش از گذاشتن taint،‏ خاموش‌بودن Node را تأیید کنید؛‏ از طریق پایش سطح rack یا hypervisor یا کنسول مدیریتی سخت‌افزار (IPMI/iLO)،‏ نه فقط وضعیت NotReady در کوبرنتیز. بهتر است در صورت امکان Node را از طریق همان کنسول صراحتاً خاموش کنید (fencing).

  20. مفهومیفرق Lease heartbeat Node و Lease leader election چیست،‏ با اینکه هر دو در API group coordination.k8s.io هستند؟
    پاسخ

    Lease heartbeat Node شیئی در namespace kube-node-lease است که نامش دقیقاً نام Node است و هر heartbeat kubelet فقط spec.renewTime آن را به‌روز می‌کند؛‏ هدفش این است که control plane ارزان و سریع (بدون به‌روزکردن کل شیء Node) بفهمد Node زنده است یا نه. Lease leader election (معمولاً در kube-system) برای اجزایی مثل kube-controller-manager و kube-scheduler در پیکربندی با دسترس‌پذیری بالا است و تضمین می‌کند در هر لحظه فقط یک instance فعال (رهبر) کار کند و بقیه آماده‌به‌کار بمانند،‏ تا دو control loop هم‌زمان روی یک منبع کار نکنند. اولی «آیا زنده‌ای؟» را جواب می‌دهد و دومی «چه کسی رئیس است؟».

  21. عملیLease heartbeat یک Node مشخص را بخوانید و renewTime آن را با زمان فعلی مقایسه کنید.
    پاسخ
    shell
    kubectl -n kube-node-lease get lease worker-1 -o jsonpath='{.spec.renewTime}'
date -u +"%Y-%m-%dT%H:%M:%SZ"

    اگر فاصله‌ی این دو زمان بیشتر از چند ثانیه باشد (Lease معمولاً هر ۱۰ ثانیه renew می‌شود)،‏ احتمالاً kubelet مشکل دارد یا Node در حال از دست دادن ارتباط است؛‏ همان چیزی که Node controller برای تصمیم Ready یا NotReady از آن استفاده می‌کند.

  22. سناریوی عملیاتیclusterی با ۵ instance kube-apiserver پشت یک load balancer دارید. یکی از خط لوله‌های CI گزارش می‌دهد kubectl get روی یک منبع خاص گاهی چند صد میلی‌ثانیه کندتر از معمول است،‏ اما هرگز شکست نمی‌خورد؛‏ این مشکل فقط در طول یک ارتقای در جریان دیده می‌شود. با مفاهیم Lease هویت API server و Mixed Version Proxy این رفتار را توضیح دهید و بگویید نگران‌کننده است یا نه.
    پاسخ

    این رفتار طبیعی Mixed Version Proxy در طول ارتقاست: اگر load balancer درخواست را به apiserver قدیمی‌تری بفرستد که آن منبع را نمی‌شناسد،‏ آن apiserver اول سند discovery غیرتجمیعی خودش را بررسی می‌کند،‏ بعد همتای مناسب را (که از طریق Leaseهای apiserver-<hash> در kube-system کشف شده) پیدا و درخواست را به آن هدایت می‌کند. این یک hop اضافه و در نتیجه کمی تأخیر است،‏ اما 404 نمی‌دهد. وقتی ارتقا تمام شود و همه‌ی apiserverها هم‌نسخه شوند،‏ این تأخیر باید از بین برود؛‏ اگر بعد از پایان ارتقا ادامه داشت،‏ مشکل جای دیگری است (مثلاً load balancer یا یک apiserver پرفشار). برای بررسی،‏ Leaseها را با kubectl -n kube-system get lease -l apiserver.kubernetes.io/identity=kube-apiserver ببینید و نسخه‌ی هر apiserver را جداگانه چک کنید.

  23. سناریوی عملیاتییک API فروشگاه اینترنتی با ۱۲ replica روی ۳ Node پشت یک Ingress دارید. تیم پلتفرم می‌خواهد هر ۳ Node را یکی‌یکی patch و reboot کند. با مفاهیم این فصل (graceful shutdown،‏ Node controller،‏ self-healing،‏ و PodDisruptionBudget که در فصل ۹ می‌آید) روالی امن طراحی کنید که هیچ قطعی‌ای برای کاربران ایجاد نکند.
    پاسخ

    روال پیشنهادی: (۱) مطمئن شوید shutdownGracePeriod و shutdownGracePeriodCriticalPods روی همه‌ی Nodeها غیرصفرند تا حتی reboot ناخواسته هم مرتب باشد. (۲) برای Deployment یک PodDisruptionBudget با minAvailable مناسب (مثلاً ۹) تعریف کنید تا drain هرگز ظرفیت را زیر حد لازم نبرد. (۳) برای هر Node به ترتیب: kubectl drain <node> --ignore-daemonsets --delete-emptydir-data (که خودش cordon هم می‌کند) تا Podها کنترل‌شده evict شوند و جایگزین‌ها روی Nodeهای دیگر آماده شوند؛‏ این کار self-healing را زودتر و کنترل‌شده فعال می‌کند. (۴) patch و reboot،‏ بعد kubectl uncordon <node>،‏ و صبر تا همه‌ی Podها Ready شوند و سپس رفتن سراغ Node بعدی.

    چرا نه reboot مستقیم بدون drain؟ چون در آن صورت Podهای Node تا حدود ۵۰ ثانیه ترافیک می‌گیرند در حالی که مرده‌اند (تا Node NotReady شود)،‏ و جایگزینی‌شان هم فقط بعد از tolerationSeconds پیش‌فرض ۳۰۰ ثانیه آغاز می‌شود؛‏ روشی کند و غیرقابل‌کنترل. ضمناً ظرفیت اضافه را هم حساب کنید: دو Node باقی‌مانده باید بتوانند ۱۲ replica را جا دهند.

  24. سناریوی عملیاتیcluster شما ۳ عضو control plane دارد (cp-1،‏ cp-2 و cp-3؛‏ هر کدام با kube-apiserver،‏ etcd،‏ kube-scheduler و kube-controller-manager). یک شب cp-2 به‌خاطر خرابی سخت‌افزار کاملاً از کار می‌افتد. تیم گزارش می‌دهد deploymentهای جدید هنوز کار می‌کنند. با مفاهیم Lease (leader election) و quorum etcd توضیح دهید چرا سیستم هنوز کار می‌کند و اگر یک عضو دیگر هم از دست برود چه می‌شود.
    پاسخ

    etcd برای ثبت هر نوشتن به quorum،‏ یعنی اکثریت اعضا،‏ یعنی floor(n/2)+1،‏ نیاز دارد؛‏ با ۳ عضو،‏ quorum ۲ است. با از دست رفتن cp-2 هنوز ۲ عضو هست و quorum حفظ می‌شود؛‏ پس خواندن و نوشتن API کار می‌کند (load balancer هم باید apiserver مرده را از چرخه خارج کند). از نظر Lease،‏ اگر رهبر kube-scheduler یا kube-controller-manager روی cp-2 بود،‏ Leaseش renew نمی‌شود و بعد از حدود leaseDurationSeconds (۱۵ ثانیه) یکی از دو instance دیگر رهبر می‌شود.

    اما اگر یک عضو دیگر هم برود،‏ فقط ۱ عضو etcd می‌ماند که کمتر از quorum (حداقل تعداد عضوی که برای تصمیم‌گیری باید در دسترس باشند) است؛‏ etcd دیگر نمی‌تواند نوشتن را ثبت کند و API عملاً از کار می‌افتد (هیچ تغییری ممکن نیست).‏ Podهای در حال اجرا روی Nodeها ادامه می‌دهند،‏ اما cluster «یخ می‌زند». برای همین تعداد اعضای etcd باید فرد و حداقل ۳ (برای تحمل خرابی ۱ عضو) یا ۵ (برای تحمل ۲ عضو) باشد؛‏ و عدد زوج (مثلاً ۴) تحمل خرابی را بیشتر نمی‌کند.

  25. سناریوی عملیاتیدر یک cluster ۵۰ Nodeی که در ۳ ناحیه پخش شده،‏ تیم SRE یک تغییر اشتباه در شبکه اعمال می‌کند و ۱۵ Node (از هر سه ناحیه) هم‌زمان ارتباطشان با kube-apiserver قطع می‌شود،‏ اما خودشان و Podهایشان سالم‌اند. بر اساس بخش «محدودیت نرخ eviction» توضیح دهید چه اتفاقی برای Podهای این Nodeها می‌افتد و چرا eviction آن‌ها «فوری و یک‌جا» نیست.
    پاسخ

    اول: هیچ Podی فوراً evict نمی‌شود؛‏ حدود ۵۰ ثانیه طول می‌کشد تا Nodeها Unknown شوند و بعد Podها به‌طور پیش‌فرض ۳۰۰ ثانیه با taint unreachable روی Node می‌مانند (toleration پیش‌فرض). اگر شبکه در این ۶ دقیقه درست شود،‏ هیچ جابه‌جایی‌ای رخ نمی‌دهد.

    دوم: وقتی eviction شروع شود،‏ محدودیت نرخ اعمال می‌شود. در این سناریو ۱۵ Node از ۵۰ ناسالم‌اند و در هر ناحیه تقریباً ۳۰٪؛‏ یعنی کمتر از آستانه‌ی --unhealthy-zone-threshold (۰٫۵۵). پس نرخ عادی --node-eviction-rate (یک Node در هر ۱۰ ثانیه) اعمال می‌شود و eviction ۱۵ Node حدود ۱۵۰ ثانیه طول می‌کشد،‏ نه یک‌باره. اگر ناسالم‌ها در یک ناحیه متمرکز بودند و از ۵۵٪ آن ناحیه بیشتر می‌شدند (اما نه همه‌ی آن)،‏ نرخ به --secondary-node-eviction-rate (یک Node در هر ۱۰۰ ثانیه) کم نمی‌شد،‏ بلکه eviction در آن ناحیه کاملاً متوقف می‌شد،‏ چون اندازه از --large-cluster-size-threshold (۵۰) بزرگ‌تر نیست. (مستندات این را «اندازه‌ی cluster» می‌نامد،‏ اما در پیاده‌سازی controller،‏ تعداد Nodeهای همان ناحیه با این آستانه مقایسه می‌شود که اینجا حدود ۱۷ است؛‏ در هر دو برداشت نتیجه توقف است.) نرخ کاهش‌یافته‌ی --secondary-node-eviction-rate فقط وقتی به کار می‌رود که این اندازه از ۵۰ بیشتر باشد. و اگر همه‌ی ناحیه‌ها کاملاً ناسالم بودند،‏ هیچ evictionی انجام نمی‌شد.

    چرا این طراحی؟ اگر مشکل واقعاً قطعی شبکه باشد نه خرابی Node،‏ eviction تهاجمی همه‌ی Podها و scheduling دوباره‌شان روی ۳۵ Node باقی‌مانده می‌تواند با پدیده‌ی thundering herd آن‌ها را هم از کار بیندازد و خرابی زنجیره‌ای بسازد. محدودیت نرخ فرصت می‌دهد مشکل شبکه پیش از آسیب بزرگ‌تر رفع شود.

سؤال‌های مصاحبه‌ی فصل ۱۲ ۱۶ سؤال · پاسخ کوتاه و دقیق،‏ همان‌طور که در جلسه‌ی مصاحبه باید گفت
  1. پایهچرا etcd فقط با kube-apiserver ارتباط برقرار می‌کند و بقیه‌ی اجزا مستقیم به آن وصل نمی‌شوند؟
    پاسخ

    چون apiserver تنها جایی است که authentication،‏ authorization (RBAC)،‏ admission controllerها،‏ validation و نسخه‌بندی شیءها انجام می‌شود. اگر اجزا مستقیم در etcd می‌نوشتند،‏ همه‌ی این لایه‌ها دور زده می‌شد،‏ سازگاری داده‌ها تضمین نمی‌شد و امنیت از بین می‌رفت. همچنین apiserver با cache و watch بار etcd را کم می‌کند.

    آنچه مصاحبه‌گر می‌خواهد بشنود: «apiserver تنها دروازه است؛‏ etcd فقط منبع حقیقت است».

  2. پایهkube-scheduler دقیقاً چه کاری انجام می‌دهد و چه کاری انجام نمی‌دهد؟
    پاسخ

    فقط برای Podهای بدون Node (فیلد spec.nodeName خالی) یک Node مناسب انتخاب می‌کند: اول Nodeهای نامناسب را فیلتر می‌کند (کمبود منابع،‏ taintها،‏ affinity و…)،‏ بعد بین بقیه امتیازدهی می‌کند،‏ و نتیجه را با یک binding در API ثبت می‌کند. Pod را اجرا نمی‌کند (کار kubelet است)،‏ Pod را نمی‌سازد (کار controllerهاست) و Podهای در حال اجرا را جابه‌جا نمی‌کند (برای این کار ابزاری مثل descheduler لازم است).

  3. پایهstatic Pod چیست و چه فرقی با Pod معمولی دارد؟
    پاسخ

    static Pod را kubelet مستقیماً از یک فایل روی disk Node (مثلاً /etc/kubernetes/manifests) اجرا می‌کند،‏ بدون اینکه API server یا scheduler دخالت کنند. kubelet برای هر کدام یک mirror Pod فقط‌خواندنی در API می‌سازد تا در kubectl get pods دیده شود؛‏ اما حذف آن از طریق kubectl فایده ندارد و باید فایل را پاک کرد. kubeadm اجزای control plane را همین‌طور اجرا می‌کند؛‏ این حل مسئله‌ی «مرغ و تخم‌مرغ» است: apiserver نمی‌تواند خودش را schedule کند.

  4. پایهCapacity و Allocatable در وضعیت Node چه فرقی دارند و scheduler با کدام کار می‌کند؟
    پاسخ

    Capacity کل منابع فیزیکی Node است؛‏ Allocatable مقداری است که بعد از کسر رزرو سیستم (systemReserved)،‏ رزرو کوبرنتیز (kubeReserved) و آستانه‌ی eviction برای Podها باقی می‌ماند. scheduler فقط Allocatable و مجموع requestها را مقایسه می‌کند؛‏ مصرف واقعی و processهای بیرون از kubelet را نمی‌بیند.

  5. متوسطkubelet چطور به control plane اعلام می‌کند که زنده است؟ اگر Node قطع شود،‏ مرحله‌به‌مرحله چه اتفاقی می‌افتد؟
    پاسخ

    با renew کردن Lease خودش در kube-node-lease هر ۱۰ ثانیه (و به‌روزکردن .status هنگام تغییر یا حداکثر هر ۵ دقیقه). اگر Node قطع شود: بعد از حدود ۵۰ ثانیه (node-monitor-grace-period) Node controller شرط Ready را Unknown و taintهای unreachable را اضافه می‌کند؛‏ Podهای آن Node از endpointهای Service خارج می‌شوند؛‏ بعد از tolerationSeconds پیش‌فرض ۳۰۰ ثانیه،‏ Podها (با محدودیت نرخ) evict و controllerها جایگزینشان را روی Nodeهای سالم می‌سازند. Podهای StatefulSet تا تأیید مرگ Node (یا taint out-of-service) جایگزین نمی‌شوند.

  6. متوسطچرا kube-controller-manager و kube-scheduler leader election دارند ولی kube-apiserver ندارد؟
    پاسخ

    controllerها و scheduler «کار انجام می‌دهند»؛‏ اگر دو instance هم‌زمان فعال باشند،‏ کار تکراری می‌شود (مثلاً Pod اضافه ساخته می‌شود یا یک Pod دو بار schedule می‌شود). پس فقط یک رهبر فعال است و بقیه آماده‌به‌کارند (active-standby با Lease).‏ apiserver stateless است و وضعیت را در etcd نگه می‌دارد،‏ و etcd خودش با Raft و کنترل هم‌روندی (resourceVersion) سازگاری را تضمین می‌کند؛‏ پس همه‌ی instanceهای apiserver می‌توانند هم‌زمان فعال باشند (active-active پشت load balancer).

  7. متوسطفرق controller «level-triggered» و «edge-triggered» چیست و کوبرنتیز کدام را استفاده می‌کند؟
    پاسخ

    controller edge-triggered فقط به «تغییر» واکنش نشان می‌دهد؛‏ اگر eventی از دست برود،‏ سیستم در وضعیت نادرست می‌ماند. controller level-triggered هر بار «current state» را با «desired state» مقایسه می‌کند،‏ پس از دست رفتن event اهمیتی ندارد. کوبرنتیز level-triggered است: eventهای watch فقط بهانه‌ی بیدار شدن controller هستند و تصمیم همیشه بر اساس current state (از cache محلی informer) گرفته می‌شود. دو سازوکار این را محکم می‌کنند: resync دوره‌ای informer که همه‌ی شیءهای cache را دوباره در صف می‌گذارد (بدون تماس با apiserver)،‏ و LIST دوباره وقتی watch قطع شود یا خطای 410 Gone بگیرد؛‏ و بعد از restart هم controller کارش را با یک LIST کامل شروع می‌کند. نتیجه: تحمل خرابی و restart controllerها.

  8. متوسطownerReferences چیست و در حذف یک Deployment چه نقشی دارد؟
    پاسخ

    فیلدی در metadata که نشان می‌دهد این شیء متعلق به کدام شیء است (Pod ←‏ ReplicaSet ←‏ Deployment). وقتی Deployment حذف می‌شود،‏ garbage collection با دنبال کردن این ارجاع‌ها وابسته‌ها را پاک می‌کند. سه حالت دارد: background (پیش‌فرض؛‏ مالک فوراً حذف و وابسته‌ها بعداً)،‏ foreground (اول وابسته‌های دارای blockOwnerDeletion،‏ بعد مالک) و orphan (--cascade=orphan؛‏ وابسته‌ها بی‌مالک باقی می‌مانند).‏ owner reference بین namespaceهای مختلف مجاز نیست.

  9. متوسطfinalizer چیست و چرا یک namespace (محدوده‌ای برای جدا کردن نام‌ها و منابع درون یک cluster) یا PVC ممکن است برای همیشه در وضعیت Terminating بماند؟
    پاسخ

    finalizer رشته‌ای در metadata.finalizers است که به apiserver می‌گوید «این شیء را هنوز واقعاً پاک نکن؛‏ یک controller باید اول کار پاک‌سازی‌اش را انجام دهد». با درخواست حذف،‏ apiserver فقط deletionTimestamp را می‌گذارد و شیء در Terminating می‌ماند؛‏ هر controller بعد از انجام کارش finalizer خودش را برمی‌دارد و وقتی فهرست خالی شد،‏ شیء واقعاً حذف می‌شود. نمونه‌ها: kubernetes.io/pvc-protection (PVC در حال استفاده‌ی یک Pod حذف نمی‌شود) و foregroundDeletion (همین فصل).

    اگر controller مسئول وجود نداشته باشد یا خراب باشد (مثلاً Operatorی که CRD و finalizer گذاشته،‏ قبل از پاک‌شدن منابعش حذف شده)،‏ finalizer هرگز برداشته نمی‌شود و شیء برای همیشه Terminating می‌ماند. namespace هم تا وقتی شیئی داخلش باقی است حذف نمی‌شود؛‏ علتش را در status.conditions خود namespace ببینید (kubectl get ns <name> -o yaml). راه درست پیدا کردن و درست‌کردن controller مسئول است؛‏ برداشتن دستی finalizer با kubectl patch آخرین راه است،‏ چون پاک‌سازی بیرونی (مثلاً disk یا load balancer cloud) انجام نشده باقی می‌ماند.

  10. متوسطcordon،‏ drain و uncordon را توضیح دهید. drain چه چیزهایی را رعایت می‌کند؟
    پاسخ

    cordon Node را unschedulable می‌کند (spec.unschedulable=true) اما Podهای موجود را دست نمی‌زند. drain اول cordon می‌کند و بعد Podها را از طریق Eviction API evict می‌کند؛‏ با رعایت PodDisruptionBudget و مهلت خاتمه‌ی Podها. Podهای DaemonSet را نمی‌تواند evict کند (flag --ignore-daemonsets) و Podهای بدون controller یا دارای emptyDir را بدون flag صریح evict نمی‌کند. uncordon Node را دوباره schedulable می‌کند.

  11. متوسطkubectl get pods کار می‌کند اما kubectl logs و kubectl exec با timeout شکست می‌خورند. مشکل کجاست؟
    پاسخ

    get فقط از apiserver می‌خواند (که داده را از cache خودش یا etcd می‌آورد)،‏ اما logs و exec نیاز دارند apiserver به kubelet روی Node (port 10250) وصل شود. پس مسیر «control plane به Node» خراب است: فایروال port 10250 را بسته،‏ مسیر شبکه بین شبکه‌ی control plane و Nodeها قطع است،‏ یا (در clusterهای مدیریت‌شده) عامل/server Konnectivity مشکل دارد. معمولاً metrics-server هم در همین شرایط از کار می‌افتد.

  12. پیشرفتهچرا etcd باید تعداد فرد عضو داشته باشد؟ cluster ۴ عضوی چند خرابی را تحمل می‌کند؟
    پاسخ

    quorum برابر floor(n/2)+1 است. با ۳ عضو،‏ quorum ۲ است و ۱ خرابی تحمل می‌شود. با ۴ عضو،‏ quorum ۳ است و باز هم فقط ۱ خرابی تحمل می‌شود؛‏ یعنی عضو چهارم هیچ تحمل خرابی اضافه نمی‌دهد،‏ ولی هزینه‌ی تکثیر (replication) و احتمال خرابی را زیاد می‌کند. ۵ عضو ۲ خرابی را تحمل می‌کند. در تقسیم شبکه،‏ قاعده‌ی اکثریت (نه فرد بودن) تضمین می‌کند حداکثر یک طرف بتواند بنویسد؛‏ فرد بودن فقط جلوی حالتی را می‌گیرد که شبکه دقیقاً نصف‌نصف شود (مثلاً ۲-۲ در cluster ۴ عضوی) و هیچ طرفی اکثریت نداشته باشد و کل cluster از کار بیفتد.

  13. پیشرفتهیک Pod از StatefulSet بعد از خاموشی ناگهانی Node در Terminating گیر کرده. چرا کوبرنتیز خودش آن را جای دیگر نمی‌سازد و راه درست چیست؟
    پاسخ

    StatefulSet تضمین «حداکثر یک instance» با هویت ثابت می‌دهد. کوبرنتیز نمی‌تواند بین «Node مرده» و «Node زنده ولی جداشده از شبکه» فرق بگذارد؛‏ اگر Pod جدید بسازد و Node قدیمی زنده باشد،‏ دو instance با یک هویت و یک volume از نوع ReadWriteOnce هم‌زمان می‌نویسند و داده خراب می‌شود. پس امن‌ترین کار صبر است. راه درست: تأیید بیرونی خاموش‌بودن Node (fencing)،‏ بعد taint node.kubernetes.io/out-of-service=nodeshutdown:NoExecute که حذف اجباری Pod و جداشدن فوری volume را انجام می‌دهد. kubectl delete pod --force --grace-period=0 هم شیء Pod را از API پاک می‌کند اما همان ریسک را دارد و volume را فوراً جدا نمی‌کند؛‏ Pod جدید تا جدا شدن volume (در بدترین حالت جداسازی اجباری پس از ۶ دقیقه) در ContainerCreating می‌ماند.

  14. پیشرفتهدرایور cgroup در kubelet و containerd باید چه باشد و ناهمخوانی آن‌ها چه علامتی دارد؟
    پاسخ

    روی سیستم‌هایی که systemd سیستم init است (تقریباً همه‌ی توزیع‌های امروزی)،‏ هر دو باید systemd باشند (در kubelet فیلد cgroupDriver و در containerd گزینه‌ی SystemdCgroup = true در runc). مستندات برای cgroup v2 هم درایور systemd را جزو پیش‌نیازها آورده است. در نسخه‌های جدید،‏ kubelet می‌تواند درایور cgroup را از خود runtime (از طریق CRI) بخواند و این ناهمخوانی کمتر پیش می‌آید،‏ اما با containerd قدیمی یا پیکربندی دستی هنوز رایج است. ناهمخوانی باعث می‌شود دو مدیر مختلف cgroup روی یک سیستم کار کنند؛‏ علامت‌ها: Podهایی که در ContainerCreating گیر می‌کنند،‏ خطاهای ساخت sandbox،‏ restartهای مکرر kubelet،‏ یا ناپایداری Node تحت فشار منابع.

  15. پیشرفتهدر یک cluster کوچک تک‌ناحیه‌ای،‏ سوئیچ شبکه می‌سوزد و ۷۰٪ Nodeها NotReady می‌شوند،‏ اما کوبرنتیز هیچ Podی را جابه‌جا نمی‌کند. باگ است؟
    پاسخ

    نه،‏ عمدی است. وقتی سهم Nodeهای ناسالم یک ناحیه از --unhealthy-zone-threshold (۰٫۵۵) بیشتر شود و cluster کوچک باشد (۵۰ Node یا کمتر)،‏ Node controller،‏ eviction را متوقف می‌کند؛‏ در clusterهای بزرگ‌تر نرخ را به یک Node در هر ۱۰۰ ثانیه کم می‌کند. منطق: خرابی هم‌زمان اکثر Nodeها بیشتر شبیه مشکل شبکه است تا خرابی Nodeها،‏ و جابه‌جا کردن همه‌ی Podها روی ۳۰٪ باقی‌مانده آن‌ها را هم از پا درمی‌آورد (خرابی زنجیره‌ای). اگر همه‌ی ناحیه‌ها کاملاً ناسالم باشند،‏ هیچ evictionی انجام نمی‌شود.

  16. پیشرفتهاگر بخواهید یک controller (Operator) سفارشی با سه instance برای دسترس‌پذیری بالا اجرا کنید،‏ چه نکاتی را از این فصل رعایت می‌کنید؟
    پاسخ

    (۱) leader election با Lease (مثلاً با library client-go/tools/leaderelection یا گزینه‌ی مربوط در controller-runtime) با نامی یکتا و مرتبط با محصول،‏ تا فقط یک instance reconciliation انجام دهد. (۲) منطق level-triggered و idempotent: هر بار کل وضعیت را مقایسه کند و اجرای چندباره مشکلی ایجاد نکند. (۳) تنظیم ownerReferences روی منابعی که می‌سازد تا garbage collection آن‌ها را همراه مالک پاک کند،‏ و finalizer برای پاک‌سازی منابع بیرونی. (۴) نوشتن نتیجه در status و استفاده از resourceVersion برای جلوگیری از تداخل نوشتن‌ها. (۵) حداقل دسترسی RBAC برای ServiceAccount آن.

خلاصه‌ی فصل ۱۲ در یک نگاه برای مرور سریع؛‏ جزئیات در متن فصل

ایده‌ی محوری: کوبرنتیز مجموعه‌ای از control loopهای مستقل است که همه از راه kube-apiserver و etcd وضعیت را می‌خوانند و می‌نویسند؛‏ سلامت Nodeها با Lease سنجیده می‌شود،‏ و eviction و garbage collection و shutdown همگی با پیش‌فرض‌های محتاطانه جلوی آسیب زنجیره‌ای را می‌گیرند.

۱. معماری کلی و مدل ذهنی
  • دو بخش: یک control plane و دست‌کم یک worker Node؛‏ روی هر Node سه جزء kubelet و container runtime و kube-proxy (که اختیاری است،‏ اگر CNI plugin جایش را بگیرد).
  • مدل ذهنی: تنها درِ ورودی kube-apiserver است و تنها storage پایدار etcd؛‏ بقیه‌ی اجزا client همین API هستند و با watch کار می‌کنند.
  • دام: جمله‌ی «هیچ جزئی مستقیم با دیگری ارتباط ندارد» مطلق نیست؛‏ برای logs و exec و port-forward خود apiserver مستقیماً به kubelet وصل می‌شود.
  • سبک کار: مدل declarative و level-triggered؛‏ هر جزء فقط شیء‌ها را می‌خواند و می‌نویسد.
  • سفر یک Deployment:

۱. اجرای kubectl apply و ذخیره در etcd؛‏ ۲. ساخت ReplicaSet توسط Deployment controller؛‏ ۳. ساخت Podها توسط ReplicaSet controller؛‏ ۴. انتخاب Node و binding توسط scheduler؛‏ ۵. اجرای containerها توسط kubelet از راه CRI؛‏ ۶. به‌روز شدن EndpointSlice و قواعد kube-proxy.

  • دام: خود kubelet و runtime معمولاً سرویس systemd هستند،‏ نه Pod.

۳. اجزای Node و addonها
  • kubelet: اجرای containerهای Podها بر اساس PodSpec؛‏ containerهایی را که خودش نساخته مدیریت نمی‌کند و scheduler آن‌ها را نمی‌شمارد؛‏ برای این مصرف از system-reserved و kube-reserved استفاده کنید.
  • static Pod: مستقیماً توسط kubelet از فایل ساخته می‌شود و در API یک mirror Pod فقط‌خواندنی دارد.
  • kube-proxy: پیاده‌سازی Service با قواعد iptables یا nftables.
  • container runtime: هر پیاده‌سازی CRI؛‏ مثل containerd و CRI-O.
  • addonها: تنها addon ضروری DNS است؛‏ بقیه شامل Dashboard و monitoring و logging و CNI plugin.

۴. گونه‌های معماری
  • استقرار control plane: چهار شکل سنتی (سرویس systemd) و static Pod (روش kubeadm) و self-hosted و managed.
  • ابزارها: ساخت cluster با kubeadm یا kops یا Kubespray.
  • توسعه‌پذیری: امکان scheduler سفارشی؛‏ CRD و aggregation layer؛‏ cloud-controller-manager.
  • kubeadm: روی Nodeهای control plane یک label نقش و taint با اثر NoSchedule می‌گذارد. دام: برداشتن این taint در production خطر OOM و از دست رفتن control plane دارد.
۵. ثبت،‏ نام‌گذاری و مدیریت Node
  • دو راه ثبت: self-registration با --register-node (پیش‌فرض true) یا ساخت دستی شیء Node.
  • اعتبار: شیء Node نامعتبر حذف نمی‌شود؛‏ نگه داشته و مرتب بررسی می‌شود تا سالم شود.
  • نام: باید DNS subdomain معتبر و یکتا باشد. دام: اگر ماشین عوض شد،‏ اول شیء Node را حذف کنید؛‏ labelها فقط هنگام ثبت اعمال می‌شوند.
  • flagهای kubelet: شامل --kubeconfig و --cloud-provider و --register-node و --register-with-taints (بدون فاصله‌ی زمانی برای schedule) و --node-ip و --node-labels و --node-status-update-frequency.
  • NodeRestriction: هر kubelet فقط Node خودش را تغییر می‌دهد و نمی‌تواند labelهای پیشوند node-restriction.kubernetes.io/ را بگذارد.
  • label نقش: کلید node-role.kubernetes.io/<role>؛‏ مقدارش نادیده گرفته می‌شود.
  • cordon: مقدار spec.unschedulable را true می‌کند و taint مربوط به unschedulable را می‌گذارد؛‏ Podهای موجود دست نمی‌خورند. Podهای DaemonSet این taint را tolerate می‌کنند و در drain از --ignore-daemonsets استفاده می‌شود.
۶. وضعیت Node
  • آدرس‌ها: سه نوع HostName (قابل تغییر با --hostname-override) و ExternalIP و InternalIP.
  • شرایط: شامل Ready و DiskPressure و MemoryPressure و PIDPressure و NetworkUnavailable.
  • Ready: مقدار Unknown یعنی گذشتن node-monitor-grace-period (پیش‌فرض ۵۰ ثانیه) بدون خبر از kubelet؛‏ آنگاه taint مربوط به unreachable (برای Unknown) یا not-ready (برای False) اضافه می‌شود.
  • دام: عبارت SchedulingDisabled که kubectl نشان می‌دهد شرط واقعی نیست؛‏ نتیجه‌ی cordon است.
  • ظرفیت: مقدار capacity کل منابع است و allocatable سهم Podها؛‏ scheduler با allocatable کار می‌کند.
  • بقیه: بخش info (نسخه‌ی kernel و runtime و kubelet) و declared features (قابلیت NodeDeclaredFeatures که در v1.37 پایدار است).
۷. سازوکار heartbeat در Node
  • دو شکل: به‌روزرسانی .status و Lease در namespace kube-node-lease.
  • status: با هر تغییر یا دست‌کم هر ۵ دقیقه به‌روز می‌شود. دام: مستندات در این بخش ۴۰ ثانیه نوشته،‏ ولی مهلت پیش‌فرض فعلی ۵۰ ثانیه است.
  • Lease: هر ۱۰ ثانیه renew می‌شود؛‏ در صورت شکست،‏ backoff نمایی از ۲۰۰ میلی‌ثانیه تا ۷ ثانیه.
  • چرا Lease:‏ renew کردن یک شیء کوچک به‌جای نوشتن کل شیء بزرگ Node؛‏ فشار کمتر روی apiserver و etcd.
  • مالکیت: مالک Lease همان Node است و با حذف Node جمع‌آوری می‌شود؛‏ مقدار leaseDurationSeconds برابر ۴۰ است ولی Node controller با grace period تصمیم می‌گیرد.
۸. Node controller و محدودیت نرخ eviction
  • سه نقش: تخصیص CIDR به Node؛‏ هماهنگی با cloud (حذف Node وقتی VM از بین رفته)؛‏ پایش سلامت Nodeها.
  • پایش: هر ۵ ثانیه بررسی می‌کند (--node-monitor-period).
  • نرخ عادی: مقدار --node-eviction-rate برابر ۰٫۱ در ثانیه،‏ یعنی یک Node در هر ۱۰ ثانیه.
  • ناحیه‌ی ناسالم: اگر سهم Nodeهای ناسالم ناحیه از --unhealthy-zone-threshold (۰٫۵۵) بیشتر شود: اگر cluster حداکثر ۵۰ Node داشته باشد eviction متوقف می‌شود؛‏ در cluster بزرگ‌تر نرخ به ۰٫۰۱ در ثانیه کم می‌شود.
  • حالت‌های مرزی: اگر یک ناحیه کاملاً از دست برود،‏ نرخ عادی اعمال می‌شود؛‏ اگر همه‌ی ناحیه‌ها ناسالم باشند،‏ هیچ evictionی رخ نمی‌دهد (احتمال مشکل از خود control plane).
  • حالت‌های درونی ناحیه: سه حالت Normal و PartialDisruption و FullDisruption.
  • چرا: قطع شبکه با خرابی Node فرق دارد؛‏ eviction تهاجمی با thundering herd به خرابی زنجیره‌ای می‌رسد.
۹. خط زمانی از دست رفتن یک Node (پیش‌فرض‌ها)

۱. در ثانیه‌ی ۵۰: وضعیت Unknown و taint مربوط به unreachable؛‏ Podها not Ready و خارج از EndpointSlice؛‏ ۲. حدود ۵ دقیقه و ۵۰ ثانیه: پایان tolerationSeconds برابر ۳۰۰ و eviction؛‏ Podها در Terminating می‌مانند و ReplicaSet جایگزین می‌سازد؛‏ ۳. حدود ۱۱ دقیقه و ۵۰ ثانیه: جدا کردن اجباری volume پس از ۶ دقیقه.

  • منشأ ۳۰۰ ثانیه: یک admission controller به نام DefaultTolerationSeconds؛‏ flag قدیمی --pod-eviction-timeout دیگر وجود ندارد.
  • دام: در StatefulSet جایگزینی خودکار نیست؛‏ برای هر هویت حداکثر یک instance،‏ پس تا حذف واقعی Pod قدیمی صبر می‌کند.
  • راه دستی: گذاشتن taint مربوط به out-of-service؛‏ اگر VM واقعاً از بین رفته باشد،‏ cloud-controller-manager خود Node را حذف می‌کند.
  • درس‌ها: داشتن retry در clientها؛‏ کم کردن tolerationSeconds با احتیاط؛‏ داشتن runbook.
۱۰. ظرفیت منابع و topology
  • قاعده: جمع requestهای Podهای روی Node از capacity بیشتر نمی‌شود؛‏ processهای بیرون از کنترل kubelet حساب نمی‌شوند،‏ پس باید رزرو شوند.
  • مثال allocatable: حافظه‌ی ۱۶Gi منهای ۱Gi برای kube-reserved و ۱Gi برای system-reserved و ۵۰۰Mi آستانه‌ی eviction،‏ تقریباً ۱۳٫۵Gi.
  • TopologyManager: هم‌ترازی NUMA برای CPU و دستگاه‌ها (پایدار از v1.27)؛‏ سیاست‌های none و best-effort و restricted و single-numa-node.
۱۱. استفاده از swap روی Node
  • پیش‌فرض Linux: اگر swap فعال باشد kubelet اجرا نمی‌شود (failSwapOn)؛‏ روی Windows swap لازم است.
  • swapBehavior: دو حالت NoSwap (پیش‌فرض؛‏ daemonهای سیستم هنوز می‌توانند swap کنند) و LimitedSwap.
  • LimitedSwap: فقط Podهای Burstable که اولویت بالا ندارند؛‏ سهم هر container به نسبت request memory آن به کل memory Node،‏ ضرب در swap در دسترس. برابر گذاشتن request و limit یعنی انصراف.
  • پایش: معیارهایی مثل node_swap_usage_bytes و دستور kubectl top --show-swap و فیلد status.nodeInfo.swap.capacity.
  • امنیت: رمزنگاری swap؛‏ tmpfs برای secret و emptyDir حافظه‌ای با گزینه‌ی noswap (نیازمند kernel ۶٫۳).
  • بهترین روش: جدا کردن و taint کردن Nodeهای دارای swap؛‏ نبود swap روی control plane؛‏ استفاده از SSD.
۱۲. ارتباط Node و control plane
  • الگو: ساختار hub-and-spoke؛‏ همه‌ی ارتباط‌ها از Node به apiserver روی port ۴۴۳ با authentication و authorization.
  • هویت‌ها: برای kubelet یک client certificate از راه TLS bootstrapping؛‏ برای Podها،‏ token مربوط به ServiceAccount و CA؛‏ IP مربوط به Service به نام kubernetes به apiserver می‌رسد.
  • جهت معکوس: مسیر apiserver به kubelet روی port ۱۰۲۵۰ برای logs و exec و attach و port-forward؛‏ HTTPS ولی به‌طور پیش‌فرض بدون تأیید certificate kubelet.
  • رفع: با --kubelet-certificate-authority و فعال کردن authentication و authorization در kubelet؛‏ یا تونل SSH (منسوخ) یا سرویس Konnectivity (در مرحله‌ی beta از v1.18) که در آن agentها از سمت Node به بیرون وصل می‌شوند.
  • proxy مربوط به apiserver: به Node و Pod و Service با HTTP ساده؛‏ با پیشوند https رمزنگاری می‌شود ولی تأیید نمی‌شود.
  • دام: اگر kubectl get کار می‌کند ولی logs و exec به timeout می‌خورند،‏ مسیر شبکه‌ی port ۱۰۲۵۰ را بررسی کنید.
۱۳. الگوی controller
  • تعریف: یک control loop که current state را به desired state (مقدار spec) نزدیک می‌کند؛‏ مثل ترموستات.
  • دو روش: کنترل از راه apiserver (Job controller فقط شیء Pod می‌سازد و Job را تمام‌شده علامت می‌زند) و کنترل مستقیم با سیستم بیرونی (مثل cluster autoscaler).
  • طراحی: چند controller ساده به‌جای یک controller بزرگ؛‏ محدود کردن دامنه با label و owner reference؛‏ cluster هرگز کاملاً پایدار نیست.
  • محل اجرا: controllerهای داخلی در kube-controller-manager؛‏ controller سفارشی داخل یا بیرون cluster.
  • level-triggered: کار بر اساس current state،‏ نه فقط eventها (مثال زنگ در)؛‏ پس reconcile باید idempotent باشد و controller سفارشی با چند instance به leader election نیاز دارد.
۱۴. شیء Lease و leader election
  • API group: گروه coordination.k8s.io؛‏ سه کاربرد heartbeat Node و leader election و هویت apiserver.
  • تفاوت دو Lease: نوع مربوط به Node در kube-node-lease می‌پرسد «زنده‌ای؟»؛‏ نوع مربوط به leader election در kube-system می‌پرسد «رهبر کیست؟».
  • پیش‌فرض‌ها: مدت ۱۵ ثانیه،‏ مهلت renew ۱۰ ثانیه،‏ تلاش دوباره هر ۲ ثانیه؛‏ رهبری که ظرف ۱۰ ثانیه نتواند renew کند کنار می‌رود.
  • فیلدها: شامل holderIdentity و acquireTime و renewTime و leaseDurationSeconds و leaseTransitions.
  • همزمانی: رقابت با optimistic concurrency روی resourceVersion؛‏ بازنده خطای Conflict می‌گیرد.
  • هویت apiserver: قابلیت APIServerIdentity (در مرحله‌ی beta از v1.26)؛‏ Leaseهایی با نام apiserver-<sha256> و label هویت؛‏ hostname باید یکتا باشد؛‏ Lease منقضی پس از ۱ ساعت پاک می‌شود.
  • آزاد کردن قفل هنگام خروج: قابلیت ControllerManagerReleaseLeaderElectionLockOnExit که در v1.36 در مرحله‌ی alpha است.
  • coordinated leader election: مرحله‌ی beta از v1.33 و خاموش به‌طور پیش‌فرض؛‏ نیازمند gate به نام CoordinatedLeaderElection و API نسخه‌ی v1beta1. نامزدها شیء LeaseCandidate می‌سازند و با راهبرد OldestEmulationVersion قدیمی‌ترین نسخه رهبر می‌شود (برای version skew هنگام ارتقا).
۱۵. جزء cloud-controller-manager
  • هدف: جدا کردن منطق cloud از هسته؛‏ plugin از راه interface به نام CloudProvider در Go (در مرحله‌ی beta از v1.11).
  • controllerها: Node controller (providerID و labelها و آدرس و حذف Node)؛‏ Route controller؛‏ Service controller برای LoadBalancer.
  • RBAC: برای هر controller مجوزهای مشخص روی Node و Service و event.
  • ثبت Node: با --cloud-provider=external روی Node یک taint به نام uninitialized می‌نشیند تا این جزء آن را مقداردهی کند.
  • دام: اگر این جزء خراب باشد،‏ Podها Pending می‌مانند و EXTERNAL-IP مربوط به Service در حالت pending می‌ماند.
۱۶. سازوکار cgroup و نسخه‌ی v2
  • مدل ذهنی: دیوار همان namespace است و کنتور همان cgroup؛‏ اعمال request و limit بدون cgroup ممکن نیست.
  • cgroup v2: پایدار (stable) از v1.25؛‏ سلسله‌مراتب یکپارچه و PSI و delegation امن؛‏ پیش‌نیاز MemoryQoS.
  • پیش‌نیازها: نسخه‌ی ۵٫۸ به بالای kernel؛‏ containerd نسخه‌ی ۱٫۴ یا CRI-O نسخه‌ی ۱٫۲۰؛‏ درایور systemd.
  • تشخیص: دستور stat -fc %T /sys/fs/cgroup؛‏ خروجی cgroup2fs یعنی v2 و tmpfs یعنی v1.
  • مهاجرت: ابزارهای وابسته به مسیرهای v1 می‌شکنند؛‏ حداقل نسخه‌ها cAdvisor نسخه‌ی v0.43 و Java از jdk8u372 و 11.0.16 و automaxprocs نسخه‌ی v1.5.1 و Node.js از v20.3.0.
  • منسوخ شدن v1: از v1.35؛‏ kubelet روی v1 اجرا نمی‌شود مگر failCgroupV1: false. دام: راه‌حل ابزار قدیمی،‏ ارتقای ابزار است نه برگشت به v1.
  • درایور: مقدار systemd پیش‌فرض kubeadm از ۱٫۲۲ است و درایور kubelet و runtime باید یکی باشد.
۱۷. قابلیت self-healing
  • چهار سازوکار: راه‌اندازی دوباره‌ی container توسط kubelet؛‏ جایگزینی replica توسط controllerهای workload (برای DaemonSet روی همان Node)؛‏ وصل دوباره‌ی PV توسط PersistentVolume controller؛‏ حذف Pod ناسالم از endpointهای Service.
  • ماهیت: حاصل چند control loop مستقل؛‏ پس دسترس‌پذیری بالای control plane پیش‌نیاز آن است.
  • محدودیت‌ها: خرابی storage و باگ برنامه را درمان نمی‌کند.
۱۸. سازوکار garbage collection در سطح API
  • موضوع‌ها: شامل Podهای خاتمه‌یافته؛‏ Jobهای تمام‌شده؛‏ شیء‌های بی‌مالک؛‏ container و image بلااستفاده؛‏ PV پویا با سیاست Delete؛‏ CSR کهنه؛‏ Node حذف‌شده؛‏ Lease مربوط به Node.
  • مالکیت: رابطه‌ی owner و dependent با ownerReferences؛‏ با label فرق دارد (مثال EndpointSlice).
  • قاعده‌ی namespace: مالک namespaceدار باید در همان namespace وابسته باشد؛‏ وابسته‌ی سطح cluster فقط مالک سطح cluster؛‏ نقض آن event هشدار OwnerRefInvalidNamespace می‌دهد.

۱۹. جمع‌آوری container و image در kubelet
  • دوره‌ها: جمع‌آوری image هر ۵ دقیقه و container هر ۱ دقیقه. دام: ابزار garbage collection بیرونی استفاده نکنید؛‏ از وضعیت kubelet (مثلاً container لازم برای logs --previous) خبر ندارد.
  • image بر اساس disk: بالاتر از HighThresholdPercent جمع‌آوری شروع می‌شود و از قدیمی‌ترین استفاده تا رسیدن به LowThresholdPercent ادامه دارد (مثل ۸۵٪ و ۸۰٪).
  • image بر اساس سن: فیلد imageMaximumGCAge (مثلاً 12h45m)؛‏ با restart شدن kubelet شمارش سن صفر می‌شود.
  • container: سه متغیر MinAge (صفر یعنی غیرفعال) و MaxPerPodContainer و MaxContainers (منفی یعنی غیرفعال)؛‏ در تعارض،‏ سقف هر Pod تا حداقل ۱ کم می‌شود. kubelet فقط containerهای خودش را جمع می‌کند.
  • فشار disk: اگر حتی پس از حذف imageها فضا آزاد نشد،‏ مقصر logها و لایه‌ی قابل‌نوشتن container است؛‏ تنظیم containerLogMaxSize و انتقال نوشتن به volume.
۲۰. قابلیت Mixed Version Proxy
  • وضعیت: مرحله‌ی beta از v1.36 و فعال به‌طور پیش‌فرض (gate به نام UnknownVersionInteroperabilityProxy).
  • مسئله: در rolling upgrade چند apiserver،‏ instance قدیمی API جدید را نمی‌شناسد و خطای ۴۰۴ گذرا می‌دهد.
  • سازوکار: هر apiserver با discovery غیرتجمیعی خودش بررسی می‌کند؛‏ اگر منبع را نشناسد،‏ درخواست را به همتایی که آن را می‌شناسد هدایت می‌کند؛‏ نبود همتا یعنی ۴۰۴ و پاسخ ندادن همتا یعنی ۵۰۳. هزینه‌اش یک hop اضافه است.
  • Peer-aggregated discovery: پاسخ discovery در /apis شامل منابع همه‌ی apiserverها؛‏ فقط برای Aggregated Discovery.
  • پیکربندی: authentication همتاها با --proxy-client-cert-file و --requestheader-client-ca-file؛‏ تأیید مقصد با --peer-ca-file؛‏ آدرس با --peer-advertise-ip و port متناظر. کشف همتاها از راه Leaseهای هویت apiserver.
۲۱. خاموش شدن مرتب Node (graceful shutdown)
  • Linux: مرحله‌ی beta از v1.21 و فعال؛‏ وابسته به inhibitor lock در systemd.
  • Windows: مرحله‌ی beta از v1.34؛‏ kubelet باید سرویس ویندوز باشد تا event پیش از خاموشی را بگیرد.
  • دام: پیش‌فرض هر دو فیلد shutdownGracePeriod و shutdownGracePeriodCriticalPods صفر است؛‏ یعنی قابلیت عملاً خاموش است.
  • رفتار: شرط NotReady با reason مربوط به shutdown؛‏ رد Podهای تازه در admission؛‏ خاتمه در دو مرحله: اول Podهای عادی و بعد Podهای حیاتی.
  • مثال: با ۳۰ ثانیه کل و ۱۰ ثانیه برای حیاتی،‏ ۲۰ ثانیه برای Podهای عادی می‌ماند.
  • بر اساس اولویت: فیلد shutdownGracePeriodByPodPriority (در مرحله‌ی beta از v1.24)؛‏ خاموشی از کم‌اولویت به پراولویت و هر Pod در ردیف بزرگ‌ترین مقدار کمتر یا برابر اولویتش؛‏ کل تأخیر جمع مهلت‌هاست. دام: ترکیب آن با دو فیلد قبلی را validation رد می‌کند و kubelet اجرا نمی‌شود.
  • نکته‌ها: وضعیت Podهای evict شده به شکل Terminated نمایش داده می‌شود؛‏ اگر خاموشی لغو شود،‏ Podها برنمی‌گردند. بسته‌ی unattended-upgrades در Debian با مهلت بیش از ۳۰ ثانیه تداخل دارد.
۲۲. خاموش شدن نامرتب Node و جدا کردن اجباری volume
  • مسئله: وقتی kubelet خاموشی را نبیند (قطع برق یا هنگ کردن)،‏ Podهای StatefulSet در Terminating گیر می‌کنند و VolumeAttachment آزاد نمی‌شود.
  • راه‌حل: گذاشتن دستی taint به نام node.kubernetes.io/out-of-service با اثر NoExecute یا NoSchedule (پایدار از v1.28)؛‏ حذف اجباری Podهای بدون toleration و جدا کردن فوری volumeها؛‏ پس از بازیابی،‏ taint را دستی بردارید.
  • دام: اول مطمئن شوید Node واقعاً خاموش است (کنسول سخت‌افزار یا hypervisor،‏ یا fencing)؛‏ اگر فقط شبکه قطع باشد،‏ دو instance روی volume از نوع ReadWriteOnce می‌نویسند و داده خراب می‌شود.
  • جدا کردن خودکار: اگر حذف Pod روی Node ناسالم ۶ دقیقه طول بکشد،‏ volume به‌زور جدا می‌شود (نقض مشخصات CSI و خطر خرابی داده)؛‏ با disable-force-detach-on-timeout خاموش می‌شود.

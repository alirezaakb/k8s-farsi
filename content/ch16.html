پروژه‌ی جامع Production

ترکیب همه‌ی فصل‌ها؛‏ الهام‌گرفته از آموزش‌های Guestbook و WordPress + MySQL در مستندات

این فصل برخلاف فصل‌های قبلی یک concept تازه معرفی نمی‌کند؛‏ بلکه دو تمرین رسمی و شناخته‌شده‌ی مستندات کوبرنتیز را از ابتدا تا انتها،‏ با تمام manifestها و دستورات،‏ دنبال می‌کند و در هر قدم نشان می‌دهد که کدام مفهوم از کدام فصل قبلی در حال استفاده است. هدف این است که تصویری end-to-end از یک برنامه‌ی چندلایه (multi-tier) روی کوبرنتیز به دست بیاورید: از Pod و container (فصل ۲ و ۳) تا Deployment و ReplicaSet (فصل ۴)،‏ از Service و load balancing (فصل ۵) تا PersistentVolume و PersistentVolumeClaim (فصل ۷)،‏ از Secret و ConfigMap (فصل ۶) تا نکات امنیتی (فصل ۱۴)،‏ و در آزمایش عملی پایانی،‏ autoscaling (فصل ۱۰) و مفاهیم اضافه بر مستندات رسمی.

توضیح تکمیلی: نقشه‌ی این فصل

فصل به دو بخش اصلی تقسیم می‌شود که هر دو مستقیماً از مستندات رسمی کوبرنتیز گرفته شده‌اند:

  • Guestbook (stateless application): یک برنامه‌ی چندلایه‌ی ساده شامل یک Redis leader،‏ دو Redis follower و چند replica از یک frontend به زبان PHP. این tutorial هیچ Volumeای ندارد و صرفاً Deployment و Service را نشان می‌دهد؛‏ بنابراین بهترین نقطه‌ی شروع برای مرور فصل ۴ (Deployment/ReplicaSet) و فصل ۵ (Services) است.
  • WordPress + MySQL با PersistentVolume (stateful application): یک برنامه‌ی دو‌لایه (WordPress + MySQL) که برخلاف Guestbook،‏ داده را persist می‌کند. این tutorial،‏ PersistentVolumeClaim (فصل ۷)،‏ Secret برای رمز عبور (فصل ۶) و کار با Kustomize را معرفی می‌کند.

در پایان،‏ یک آزمایش عملی سرتاسری (خارج از مستندات رسمی) پروژه‌ی WordPress را با HorizontalPodAutoscaler،‏ NetworkPolicy،‏ PodDisruptionBudget،‏ resource requests/limits و probeها به یک پیکربندی نزدیک‌تر به production ارتقا می‌دهد.

مانند مستندات رسمی،‏ این پروژه‌ها آماده‌ی production نیستند (خود مستندات Guestbook می‌گوید «not production ready» و مستندات WordPress می‌گوید «not suitable for production use cases»)؛‏ هدف آموزش pattern طراحی چندلایه است،‏ نه ارائه‌ی یک reference architecture کامل. برای WordPress در production واقعی،‏ مستندات به WordPress Helm Chart ارجاع می‌دهند.

ماجرای این فصل: تمرین کامل پیش از روز انتشار

بخش اول: Guestbook — یک برنامه‌ی stateless چندلایه

این tutorial نشان می‌دهد چگونه یک برنامه‌ی وب چندلایه (multi-tier)،‏ ساده و not production ready،‏ را با استفاده از کوبرنتیز و Docker بسازید و deploy کنید. این مثال شامل componentهای زیر است:

  • یک instance تکی از Redis برای ذخیره‌ی ورودی‌های guestbook
  • چند instance از frontend وب

اهداف (Objectives)

  • راه‌اندازی یک Redis leader.
  • راه‌اندازی دو Redis follower.
  • راه‌اندازی frontend مربوط به guestbook.
  • Expose و مشاهده‌ی Service مربوط به Frontend.
  • پاک‌سازی (Clean up).
توضیح تکمیلی: چرا Redis leader/follower؟

Guestbook از یک الگوی معماری کلاسیک استفاده می‌کند: یک instance Redis که هم read و هم write را قبول می‌کند (leader) و چند instance Redis که فقط از leader replicate می‌کنند و فقط به درخواست‌های read پاسخ می‌دهند (follower). این جداسازی باعث می‌شود بار خواندن (که معمولاً حجم بیشتری دارد) بین چند Pod پخش شود،‏ در حالی که نوشتن همچنان روی یک منبع واحد (leader) متمرکز است تا سازگاری داده (consistency) حفظ شود. در دنیای واقعی این pattern را در پایگاه‌داده‌هایی مثل MySQL (primary/replica)،‏ PostgreSQL و همین Redis می‌بینید. توجه کنید که این معماری خودش highly available نیست: اگر Pod مربوط به leader از بین برود،‏ Deployment یک Pod جدید می‌سازد (self-healing،‏ فصل ۴) اما داده‌ی in-memory آن از دست می‌رود،‏ چون هیچ PersistentVolumeای در این تمرین وجود ندارد.

راه‌اندازی پایگاه‌داده‌ی Redis (Start up the Redis Database)

برنامه‌ی guestbook از Redis برای ذخیره‌ی داده‌های خود استفاده می‌کند.

ساختن Deployment برای Redis (Creating the Redis Deployment)

فایل manifest زیر،‏ یک Deployment controller را مشخص می‌کند که یک Redis Pod تک‌replica اجرا می‌کند.

application/guestbook/redis-leader-deployment.yaml
# SOURCE: https://cloud.google.com/kubernetes-engine/docs/tutorials/guestbook
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis-leader
  labels:
    app: redis
    role: leader
    tier: backend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
        role: leader
        tier: backend
    spec:
      containers:
      - name: leader
        image: "registry.k8s.io/redis@sha256:cb111d1bd870a6a471385a4a69ad17469d326e9dd91e0e455350cacf36e1b3ee"
        resources:
          requests:
            cpu: 100m
            memory: 100Mi
        ports:
        - containerPort: 6379

  2. Redis Deployment را از فایل redis-leader-deployment.yaml apply کنید:
    shell

  3. فهرست Podها را بررسی کنید تا مطمئن شوید Redis Pod در حال اجراست:

توضیح تکمیلی: هر field این Deployment چه می‌کند

این manifest دقیقاً همان الگوی Deployment است که در فصل ۴ دیدید؛‏ در اینجا کاربرد هر field در متن این پروژه را مرور می‌کنیم:

fieldمقدارتوضیح در متن Guestbook
spec.replicas1Redis leader باید تک‌instance باشد؛‏ چون تنها یک کپی از داده باید نوشتنی باشد. اگر این عدد بیشتر از ۱ بود،‏ چند Pod مستقل با state جداگانه ساخته می‌شد که با هم sync نمی‌شوند (Redis خودش replication را انجام نمی‌دهد مگر با پیکربندی صریح در سطح container).
spec.selector.matchLabelsapp: redisReplicaSet زیرین را به Podهایی که label app: redis دارند متصل می‌کند. توجه کنید این selector فقط app: redis است،‏ نه ترکیب کامل labelهای template (که شامل role: leader و tier: backend هم هست)؛‏ این یعنی از نظر API این selector به‌تنهایی همه‌ی Podهای Redis (چه leader چه follower) را می‌تواند match کند اگر labelهای دیگر یکسان تعریف نشوند — در عمل template این Deployment فقط Pod با role: leader می‌سازد،‏ پس تداخلی رخ نمی‌دهد. دلیلش این است که ReplicaSet هر Deployment علاوه بر selector اصلی،‏ label به نام pod-template-hash را هم در selector خود دارد و هر Pod فقط یک ownerReference با controller: true دارد. با این حال مستندات Deployment صریحاً می‌گوید selectorهای همپوشان نسازید؛‏ در تمرین‌های پایان فصل به آن برمی‌گردیم.
imageregistry.k8s.io/redis@sha256:...image با digest pin شده است،‏ نه با tag. این یک best practice برای reproducibility است (فصل ۲): تضمین می‌کند که همیشه دقیقاً همان bit-for-bit image pull شود،‏ صرف‌نظر از اینکه tag دوباره push شده باشد یا نه.
resources.requestscpu: 100m, memory: 100Miفقط request تعریف شده،‏ بدون limit. این یعنی scheduler تضمین می‌کند حداقل این مقدار resource برای Pod وجود دارد،‏ اما container می‌تواند بیشتر از آن هم مصرف کند (تا سقف ظرفیت Node یا تا وقتی throttle/OOM شود). این یک تصمیم آموزشی ساده‌شده است؛‏ در آزمایش عملی پایان فصل limit هم اضافه می‌کنیم.

ساختن Service برای Redis leader (Creating the Redis leader Service)

برنامه‌ی guestbook باید با Redis برای نوشتن داده‌های خود ارتباط برقرار کند. باید یک Service apply کنید تا ترافیک را به Redis Pod proxy کند. یک Service یک policy برای دسترسی به Podها تعریف می‌کند.

application/guestbook/redis-leader-service.yaml
# SOURCE: https://cloud.google.com/kubernetes-engine/docs/tutorials/guestbook
apiVersion: v1
kind: Service
metadata:
  name: redis-leader
  labels:
    app: redis
    role: leader
    tier: backend
spec:
  ports:
  - port: 6379
    targetPort: 6379
  selector:
    app: redis
    role: leader
    tier: backend
  1. Redis Service را از فایل زیر یعنی redis-leader-service.yaml apply کنید:
    shell
    kubectl apply -f https://k8s.io/examples/application/guestbook/redis-leader-service.yaml
  2. فهرست Serviceها را بررسی کنید تا مطمئن شوید Redis Service در حال اجراست:
    shell
    kubectl get service
    پاسخ باید چیزی شبیه این باشد:
    خروجی نمونه
    NAME           TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE
kubernetes     ClusterIP   10.96.0.1      <none>        443/TCP    3d19h
redis-leader   ClusterIP   10.103.78.24   <none>        6379/TCP   16s

این manifest یک Service با نام redis-leader می‌سازد با مجموعه‌ای از labelها (جفت کلید-مقدار روی اشیا برای گروه‌بندی و انتخاب) که با labelهای تعریف‌شده‌ی قبلی مطابقت دارند،‏ بنابراین Service ترافیک شبکه را به Redis Pod هدایت می‌کند.

توضیح تکمیلی: چرا این Service به‌جای type صریح از ClusterIP پیش‌فرض استفاده می‌کند

در فصل ۵ دیدید که وقتی spec.type نوشته نشود،‏ مقدار پیش‌فرض ClusterIP است — یعنی یک IP داخلی که فقط از درون cluster قابل دسترسی است. برای Redis leader این دقیقاً رفتار درست است: نیازی نیست Redis از بیرون cluster در دسترس باشد؛‏ فقط Podهای frontend (که خودشان داخل cluster اجرا می‌شوند) باید بتوانند با نام redis-leader به آن وصل شوند. این نام از طریق DNS داخلی cluster (که در فصل ۵ توضیح داده شد) resolve می‌شود،‏ بدون نیاز به دانستن IP واقعی Pod. restart شدن container آن IP را عوض نمی‌کند،‏ اما هر بار که Pod جایگزین شود (مثلاً پس از حذف یا evict شدن)،‏ Pod تازه IP دیگری می‌گیرد.

نکته‌ی مهم دیگر این است که selector این Service شامل هر سه label یعنی app: redis،‏ role: leader و tier: backend است،‏ برخلاف selector خود Deployment که فقط app: redis بود. این یعنی اگر بعداً یک Deployment دیگر با role: follower اضافه شود (که دقیقاً در بخش بعدی همین اتفاق می‌افتد)،‏ این Service همچنان فقط Podهای leader را انتخاب می‌کند،‏ نه followerها؛‏ چون selector سطح Service محدودتر و دقیق‌تر تعریف شده است.

راه‌اندازی Redis followerها (Set up Redis followers)

اگرچه Redis leader یک Pod تکی است،‏ می‌توانید با اضافه‌کردن چند Redis follower (یا replica) آن را highly available کنید و به حجم ترافیک پاسخ دهید.

application/guestbook/redis-follower-deployment.yaml
# SOURCE: https://cloud.google.com/kubernetes-engine/docs/tutorials/guestbook
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis-follower
  labels:
    app: redis
    role: follower
    tier: backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
        role: follower
        tier: backend
    spec:
      containers:
      - name: follower
        image: us-docker.pkg.dev/google-samples/containers/gke/gb-redis-follower:v2
        resources:
          requests:
            cpu: 100m
            memory: 100Mi
        ports:
        - containerPort: 6379

  2. با بررسی فهرست Podها مطمئن شوید دو replica Redis follower در حال اجرا هستند:

هشدار

توجه کنید که selector.matchLabels این Deployment هم دقیقاً مثل Deployment مربوط به leader فقط app: redis است،‏ یعنی selector دو Deployment همپوشان است. مستندات Deployment هشدار می‌دهد که controllerهایی با selector همپوشان با هم «دعوا» می‌کنند و درست رفتار نمی‌کنند. اینجا مشکلی پیش نمی‌آید،‏ چون Deployment controller فقط ReplicaSetهایی را مدیریت می‌کند که ownerReference آن‌ها به خودش اشاره دارد و selector هر ReplicaSet،‏ label به نام pod-template-hash را هم دارد؛‏ پس هیچ ReplicaSetی Pod دیگری را تصاحب نمی‌کند. با این حال ابزارهایی که فقط selector را نگاه می‌کنند (مثل kubectl get pods -l app=redis یا یک PodDisruptionBudget با همین selector) هر دو گروه را با هم می‌بینند. یک best practice امن‌تر این است که selector هر Deployment شامل همان labelهای متمایزکننده (مثل role) هم باشد تا از تداخل احتمالی جلوگیری شود.

توضیح تکمیلی: چرا یک Service جدا برای followerها؟

چون هر Service با selector خودش دقیقاً یک مجموعه ثابت از Podها را هدف می‌گیرد (فصل ۵)،‏ نمی‌توان یک Service واحد ساخت که هم به leader و هم به followerها ترافیک بفرستد و در عین حال بین «نوشتن» و «خواندن» تمایز قائل شود؛‏ این تمایز باید در سطح application (کد PHP frontend) انجام شود: کد frontend،‏ آدرس redis-leader را برای write و آدرس redis-follower را برای read استفاده می‌کند. Service مربوط به follower به‌طور خودکار بین دو Pod follower load balance می‌کند (رفتار پیش‌فرض kube-proxy،‏ فصل ۵)،‏ بنابراین بار خواندن بین آن‌ها تقسیم می‌شود.

راه‌اندازی و expose کردن frontend (Set up and Expose the Guestbook Frontend)

حالا که storage مربوط به Redis برای guestbook شما راه‌اندازی و در حال اجراست،‏ وب‌سرورهای guestbook را شروع کنید. مانند Redis followerها،‏ frontend هم با استفاده از یک Deployment deploy می‌شود.

برنامه‌ی guestbook از یک frontend به زبان PHP استفاده می‌کند. این frontend به‌گونه‌ای پیکربندی شده که با Service مربوط به Redis follower یا leader ارتباط برقرار کند،‏ بسته به اینکه درخواست یک read باشد یا یک write.‏ frontend یک JSON interface را expose می‌کند،‏ و یک رابط کاربری مبتنی بر jQuery-Ajax ارائه می‌کند.

ساختن Deployment برای frontend (Creating the Guestbook Frontend Deployment)

برخلاف دو Deployment مربوط به Redis که هرکدام یک role ثابت (leader یا follower) داشتند،‏ frontend یک workload کاملاً stateless است: هر سه replica کاملاً یکسان هستند و هیچ‌کدام state محلی مهمی ندارند (تمام state واقعی در Redis نگه‌داری می‌شود). به همین دلیل replicas می‌تواند هر عددی باشد بدون آنکه نگران sync شدن بین replicaها باشیم — این دقیقاً تعریف یک Deployment ایده‌آل از دید فصل ۴ است: هر replica باید قابل جایگزینی (interchangeable) و بدون state محلی حیاتی باشد.

environment variable GET_HOSTS_FROM: "dns" به کد PHP می‌گوید که آدرس Redis leader و follower را از طریق DNS داخلی cluster (یعنی نام Service مثل redis-leader و redis-follower) resolve کند،‏ نه از طریق environment variableها که کوبرنتیز به‌طور خودکار برای Serviceهای موجود هنگام start شدن Pod تزریق می‌کند. این روش پایدارتر است،‏ چون تزریق خودکار environment variable فقط برای Serviceهایی کار می‌کند که پیش از ساخته‌شدن Pod وجود داشته باشند،‏ در حالی که DNS در هر لحظه از عمر Pod قابل query شدن است (به فصل ۵،‏ بخش Service discovery مراجعه کنید).

ساختن Service برای frontend (Creating the Frontend Service)

Serviceهای مربوط به Redis که apply کردید تنها از درون cluster کوبرنتیز قابل دسترسی هستند،‏ چون نوع پیش‌فرض یک Service،‏ ClusterIP است. ClusterIP یک آدرس IP واحد برای مجموعه Podهایی که Service به آن‌ها اشاره می‌کند فراهم می‌کند. این آدرس IP فقط از درون cluster قابل دسترسی است.

اگر می‌خواهید مهمانان بتوانند به guestbook شما دسترسی داشته باشند،‏ باید Service مربوط به frontend را به‌گونه‌ای پیکربندی کنید که از بیرون قابل مشاهده باشد،‏ تا یک client بتواند Service را از بیرون cluster کوبرنتیز درخواست کند. با این حال یک کاربر کوبرنتیز می‌تواند از kubectl port-forward برای دسترسی به service استفاده کند حتی اگر از یک ClusterIP استفاده کند.

وقتی از مرورگر روی Submit کلیک می‌کنید،‏ این مسیر طی می‌شود:

  1. مرورگر یک HTTP request به Service frontend می‌فرستد (روی port ۸۰،‏ یا از طریق kubectl port-forward یا از طریق IP بیرونی LoadBalancer).
  2. kube-proxy (فصل ۵) این ترافیک را با ruleهای iptables یا nftables به یکی از سه Pod frontend (یا بیشتر،‏ پس از scale) می‌فرستد؛‏ انتخاب Pod تصادفی است و session affinity پیش‌فرض ندارد.
  3. کد PHP داخل آن Pod،‏ چون این یک عملیات write است،‏ به نام redis-leader وصل می‌شود. این نام از طریق CoreDNS داخل cluster به ClusterIP مربوط به Service redis-leader resolve می‌شود.
  4. Service redis-leader ترافیک را به تنها Pod backend خودش (که role: leader دارد) هدایت می‌کند و پیام در Redis نوشته می‌شود.
  5. برای خواندن پیام‌های قبلی (رندر صفحه)،‏ کد PHP به‌جای آن به redis-follower وصل می‌شود،‏ که ترافیک را بین دو Pod follower پخش می‌کند.

این مثال به‌خوبی نشان می‌دهد چرا Service abstraction (فصل ۵) مهم است: کد frontend هرگز IP واقعی هیچ Podای را نمی‌داند و نیازی هم به دانستن آن ندارد؛‏ حتی اگر Redis leader Pod در اثر یک node failure از بین برود و Deployment یک Pod جدید با IP متفاوت بسازد،‏ نام redis-leader بدون تغییر به IP جدید resolve می‌شود.

بخش دوم: WordPress + MySQL با PersistentVolume

این tutorial نشان می‌دهد چگونه یک سایت WordPress و یک پایگاه‌داده MySQL را با استفاده از Minikube deploy کنید. هر دو برنامه از PersistentVolumeها و PersistentVolumeClaimها برای ذخیره‌ی داده استفاده می‌کنند.

یک PersistentVolume (PV) قطعه‌ای از storage در cluster است که یا به‌صورت دستی توسط یک administrator provision شده،‏ یا به‌صورت پویا توسط کوبرنتیز با استفاده از یک StorageClass provision شده است. یک PersistentVolumeClaim (PVC) درخواستی برای storage توسط یک کاربر است که می‌تواند با یک PV برآورده شود. PersistentVolumeها و PersistentVolumeClaimها مستقل از lifecycle یک Pod هستند و داده را در طول restart،‏ reschedule و حتی delete شدن Podها حفظ می‌کنند.

ساختن PersistentVolumeClaim و PersistentVolume (Create PersistentVolumeClaims and PersistentVolumes)

MySQL و WordPress هرکدام به یک PersistentVolume برای ذخیره‌ی داده نیاز دارند. PersistentVolumeClaim مربوط به آن‌ها در مرحله‌ی deployment ساخته می‌شود.

بسیاری از محیط‌های cluster یک StorageClass پیش‌فرض نصب‌شده دارند. وقتی یک StorageClass در PersistentVolumeClaim مشخص نشود،‏ از StorageClass پیش‌فرض cluster به‌جای آن استفاده می‌شود.

وقتی یک PersistentVolumeClaim ساخته می‌شود،‏ یک PersistentVolume به‌صورت پویا بر اساس پیکربندی StorageClass provision می‌شود.

نکته

در clusterهای local،‏ StorageClass پیش‌فرض از provisioner با نام hostPath استفاده می‌کند. Volumeهای hostPath فقط برای development و testing مناسب هستند. با Volumeهای hostPath،‏ داده‌ی شما در مسیر /tmp روی Nodeی که Pod روی آن schedule شده زندگی می‌کند و بین Nodeها جابه‌جا نمی‌شود. اگر یک Pod از بین برود و روی Node دیگری در cluster schedule شود،‏ یا Node reboot شود،‏ داده از دست می‌رود.

اگر در حال بالا آوردن یک cluster هستید که نیاز به استفاده از provisioner با نام hostPath دارد،‏ flag با نام --enable-hostpath-provisioner باید در component با نام controller-manager تنظیم شود.

اگر یک cluster کوبرنتیز در حال اجرا روی Google Kubernetes Engine دارید،‏ لطفا این راهنما را دنبال کنید.

توضیح تکمیلی: چرا این‌جا PVC مستقیماً در همین manifest ساخته می‌شود،‏ اما PV نه؟

این یکی از تفاوت‌های اصلی این پروژه با Guestbook است. در فصل ۷ دیدید که کوبرنتیز دو مدل provisioning دارد: static provisioning (یک administrator از قبل چند PV می‌سازد) و dynamic provisioning (یک StorageClass به‌صورت خودکار وقتی یک PVC ساخته می‌شود،‏ یک PV متناظر می‌سازد). این tutorial از مدل دوم استفاده می‌کند: تنها چیزی که در manifestها می‌بینید یک PersistentVolumeClaim است؛‏ هیچ object از نوع PersistentVolume یا StorageClass صریحاً نوشته نشده،‏ چون فرض بر این است که cluster (مثلاً Minikube) از قبل یک StorageClass پیش‌فرض دارد. وقتی PVC ساخته می‌شود،‏ provisioner همان StorageClass به‌صورت خودکار یک PV می‌سازد و PersistentVolume controller آن دو را به هم bind می‌کند.

افزودن Secret generator (Add a Secret generator)

یک Secret یک object است که یک قطعه داده‌ی حساس مانند یک رمز عبور یا کلید را ذخیره می‌کند. از نسخه‌ی ۱.۱۴،‏ kubectl از مدیریت objectهای کوبرنتیز با استفاده از یک kustomization file پشتیبانی می‌کند. می‌توانید یک Secret را با generatorها در kustomization.yaml بسازید.

یک Secret generator در kustomization.yaml از دستور زیر اضافه کنید. باید YOUR_PASSWORD را با رمز عبوری که می‌خواهید استفاده کنید جایگزین کنید.

shell
cat <<EOF >./kustomization.yaml
secretGenerator:
- name: mysql-pass
  literals:
  - password=YOUR_PASSWORD
EOF
توضیح تکمیلی: Kustomize چیست و چرا اینجا استفاده شده؟

Kustomize یک ابزار template-free برای سفارشی‌سازی manifestهای کوبرنتیز است که از نسخه‌ی ۱.۱۴ مستقیماً در kubectl ادغام شده (با flag -k). برخلاف Helm که از یک زبان templating استفاده می‌کند،‏ Kustomize یک فایل kustomization.yaml را می‌خواند که فهرستی از resourceهای پایه و یک سری «patch» یا «generator» روی آن‌ها را توصیف می‌کند.

secretGenerator دقیقاً معادل دستوری است که در فصل ۶ دیدید: kubectl create secret generic mysql-pass --from-literal=password=YOUR_PASSWORD. تفاوت اصلی این است که Kustomize به‌صورت پیش‌فرض یک hash از محتوای Secret را به نام آن اضافه می‌کند (مثلاً mysql-pass-c57bb4t7mf)،‏ تا هر بار محتوای Secret تغییر کند،‏ نام آن هم تغییر کند. این کار content-hash naming (نام‌گذاری بر اساس hash محتوا) است،‏ نه immutable Secret؛‏ immutable فیلد جداگانه‌ای است (immutable: true) که تغییر محتوای همان object را ممنوع می‌کند. مزیت hash در نام این است که Kustomize ارجاع‌ها را در Deploymentها هم به نام تازه به‌روز می‌کند؛‏ پس spec.template تغییر می‌کند و Deployment یک rollout تازه (فصل ۴) شروع می‌کند تا Podها مقدار جدید را بخوانند (برای MySQL با strategy برابر Recreate). Secret قدیمی هم باقی می‌ماند و rollback به آن ممکن است.

دام مهم: تصویر رسمی MySQL متغیرهای MYSQL_ROOT_PASSWORD و MYSQL_PASSWORD را فقط وقتی به کار می‌برد که data directory خالی باشد (اولین اجرا). وقتی داده روی PersistentVolume وجود دارد،‏ عوض کردن Secret و rollout،‏ رمز را در خود پایگاه‌داده تغییر نمی‌دهد؛‏ WordPress با رمز تازه وصل می‌شود و خطا می‌گیرد. rotate کردن رمز باید ابتدا در خود MySQL (با ALTER USER) انجام شود؛‏ تمرین‌های پایان فصل این روند را نشان می‌دهند.

افزودن manifestهای MySQL و WordPress (Add resource configs for MySQL and WordPress)

manifest زیر یک Deployment تک‌instance از MySQL را توصیف می‌کند. container مربوط به MySQL،‏ PersistentVolume را در مسیر /var/lib/mysql mount می‌کند. environment variable MYSQL_ROOT_PASSWORD،‏ رمز عبور پایگاه‌داده را از Secret تنظیم می‌کند.

application/wordpress/mysql-deployment.yaml
apiVersion: v1
kind: Service
metadata:
  name: wordpress-mysql
  labels:
    app: wordpress
spec:
  ports:
    - port: 3306
  selector:
    app: wordpress
    tier: mysql
  clusterIP: None
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pv-claim
  labels:
    app: wordpress
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: wordpress-mysql
  labels:
    app: wordpress
spec:
  selector:
    matchLabels:
      app: wordpress
      tier: mysql
  strategy:
    type: Recreate
  template:
    metadata:
      labels:
        app: wordpress
        tier: mysql
    spec:
      containers:
      - image: mysql:8.0
        name: mysql
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-pass
              key: password
        - name: MYSQL_DATABASE
          value: wordpress
        - name: MYSQL_USER
          value: wordpress
        - name: MYSQL_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-pass
              key: password
        ports:
        - containerPort: 3306
          name: mysql
        volumeMounts:
        - name: mysql-persistent-storage
          mountPath: /var/lib/mysql
      volumes:
      - name: mysql-persistent-storage
        persistentVolumeClaim:
          claimName: mysql-pv-claim

توضیح تکمیلی: تحلیل field-به-field این دو manifest
fieldدر کدام manifestتوضیح
clusterIP: NoneService wordpress-mysqlاین یک Headless Service است (فصل ۵). به‌جای یک ClusterIP واحد که load balance می‌کند،‏ DNS مستقیماً به IP خود Pod (نه یک IP مجازی Service) resolve می‌شود. چون فقط یک replica MySQL وجود دارد،‏ نیازی به load balancing نیست؛‏ Headless Service اینجا صرفاً برای stable DNS name استفاده می‌شود،‏ و kube-proxy هیچ ruleی برای آن نمی‌سازد.
accessModes: [ReadWriteOnce]هر دو PVCهمان‌طور که در فصل ۷ دیدید،‏ ReadWriteOnce (RWO) یعنی Volume تنها می‌تواند به‌صورت read-write توسط یک Node واحد mount شود (نه لزوماً یک Pod واحد،‏ اما در عمل معمولاً با یک Pod همراه است). این مناسب MySQL و WordPress تک‌instance است؛‏ اگر بخواهید چند replica WordPress با یک Volume مشترک داشته باشید،‏ باید از ReadWriteMany (که همه‌ی provisionerها آن را پشتیبانی نمی‌کنند) استفاده کنید.
storage: 20Giهر دو PVCمقدار درخواستی storage.‏ StorageClass با توجه به provisioner خودش،‏ یک PV با ظرفیت حداقل این مقدار می‌سازد.
strategy.type: Recreateهر دو Deploymentاین مهم‌ترین تفاوت با فصل ۴ (که پیش‌فرض RollingUpdate را پوشش داد) است. با استراتژی پیش‌فرض RollingUpdate،‏ Pod جدید پیش از حذف Pod قدیمی ساخته می‌شود. چون Volume از نوع ReadWriteOnce فقط به یک Node attach می‌شود،‏ اگر Pod جدید روی Node دیگری schedule شود با خطای Multi-Attach error در وضعیت ContainerCreating می‌ماند. اگر روی همان Node بیفتد،‏ RWO مانع نمی‌شود (محدودیت در سطح Node است،‏ نه Pod) و دو process به نام mysqld روی یک data directory اجرا می‌شوند؛‏ InnoDB قفل فایل را نمی‌گیرد و Pod دوم شکست می‌خورد یا داده در خطر می‌افتد. Recreate این مشکل را حل می‌کند: ابتدا تمام Podهای قدیمی را کاملاً خاموش می‌کند،‏ سپس Pod جدید را می‌سازد — به قیمت یک downtime کوتاه در حین هر update.
MYSQL_DATABASE / MYSQL_USERDeployment MySQLساده‌سازی با plaintext value (نه از Secret)،‏ چون این مقادیر حساس محسوب نمی‌شوند (نام پایگاه‌داده و نام کاربری،‏ نه رمز عبور).
type: LoadBalancerService wordpressبرخلاف Guestbook که این خط comment شده بود،‏ اینجا صریحاً LoadBalancer است چون هدف این tutorial،‏ دسترسی مستقیم و بیرونی به سایت WordPress است. در Minikube،‏ این Service هرگز EXTERNAL-IP واقعی نمی‌گیرد (چون Minikube یک cloud provider واقعی نیست)؛‏ دستور minikube service این محدودیت را دور می‌زند (به بخش بعد مراجعه کنید).

توضیح تکمیلی: چرا این یک single point of failure دوگانه است

این معماری،‏ برخلاف Guestbook،‏ داده را persist می‌کند (به لطف PersistentVolume،‏ فصل ۷)،‏ اما هنوز highly available نیست: هم MySQL و هم WordPress فقط یک replica دارند (و با Volume از نوع RWO،‏ replica دوم روی Node دیگر نمی‌تواند همان Volume را attach کند). اگر Node میزبان یکی از این دو Pod از دست برود،‏ برنامه تا مدتی در دسترس نیست: حدود ۵۰ ثانیه تا Node به‌عنوان NotReady شناخته شود،‏ ۳۰۰ ثانیه tolerationSeconds تا Pod evict شود،‏ و سپس زمان detach شدن Volume از Node مرده (attach/detach controller پس از ۶ دقیقه force detach می‌کند،‏ مگر این‌که Node را با taint به نام node.kubernetes.io/out-of-service علامت بزنید). به این مجموع failover time می‌گویند. برای پایگاه‌داده در production واقعی معمولاً از یک StatefulSet (که در فصل ۴ معرفی شد) با replication در سطح خود پایگاه‌داده استفاده می‌شود،‏ یا از یک managed database service بیرون از cluster.

آزمایش عملی سرتاسری: ارتقای WordPress به پیکربندی نزدیک‌تر به production؛ خارج از مستندات رسمی

هشدار

هر چیزی که در این بخش می‌آید بخشی از مستندات رسمی tutorial WordPress + MySQL نیست. این محتوا برای نشان‌دادن اینکه چگونه مفاهیم فصل‌های ۳ و ۵ و ۶ و ۷ و ۹ و ۱۰ روی همین پروژه‌ی واقعی اعمال می‌شوند نوشته شده است. تمام manifestهای این بخش دستی نوشته شده‌اند (نه از مستندات کپی شده‌اند) اما با رفتار و API واقعی کوبرنتیز که در فصل‌های قبل پوشش داده شد سازگار و صحیح هستند.

پروژه‌ی WordPress که در بخش دوم ساختید،‏ از نظر persistence بهتر از Guestbook بود،‏ اما هنوز چند مشکل production جدی دارد:

  • هیچ resource limit روی containerها تعریف نشده — یک memory leak در WordPress یا MySQL می‌تواند کل Node را تحت فشار بگذارد (فصل ۳،‏ QoS class).
  • هیچ liveness یا readiness probe تعریف نشده — اگر Apache داخل container WordPress hang کند،‏ kubelet هیچ‌وقت متوجه نمی‌شود و ترافیک همچنان به آن Pod ارسال می‌شود (فصل ۳،‏ Pods).
  • WordPress فقط یک replica دارد و امکان scale کردن آن به‌سادگی وجود ندارد،‏ چون از یک PVC با ReadWriteOnce و استراتژی Recreate استفاده می‌کند (فصل ۷،‏ Storage).
  • هیچ NetworkPolicy وجود ندارد — هر Pod دیگری در namespace می‌تواند مستقیماً به port ۳۳۰۶ مربوط به MySQL وصل شود (فصل ۵).
  • هیچ PodDisruptionBudget وجود ندارد — یک kubectl drain یا node upgrade می‌تواند به‌طور هم‌زمان همه‌ی replicaهای WordPress را پایین ببرد (فصل ۹).

در ادامه هر مشکل را با یک تغییر مشخص برطرف می‌کنیم.

پیش‌نیاز scale کردن WordPress: از ReadWriteOnce به ReadWriteMany

پیش از افزودن HorizontalPodAutoscaler،‏ باید یک نکته‌ی مهم را حل کنیم که مستقیماً نتیجه‌ی چیزی است که در فصل ۷ درباره‌ی accessModes یاد گرفتید: PVC فعلی wp-pv-claim با ReadWriteOnce تعریف شده،‏ یعنی فقط یک Node می‌تواند آن را هم‌زمان mount کند. اگر replicas در Deployment مربوط به WordPress را بیشتر از ۱ کنیم بدون تغییر این mode،‏ Podهایی که روی Node دیگری schedule شوند با Multi-Attach error در وضعیت ContainerCreating می‌مانند (مگر همه روی یک Node باشند،‏ که تضمین‌شده نیست).

راه‌حل صحیح،‏ استفاده از یک StorageClass که از ReadWriteMany (RWX) پشتیبانی کند (مثلاً یک backend مبتنی بر NFS یا یک filesystem توزیع‌شده‌ی cloud) و تغییر استراتژی Deployment از Recreate به RollingUpdate است،‏ چون دیگر محدودیت انحصاری بودن Volume وجود ندارد.

یک نکته‌ی عملی: accessModes در PVC موجود قابل تغییر نیست؛‏ apply کردن همان نام با mode تازه با خطای spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims رد می‌شود. برای همین manifest زیر یک PVC تازه به نام wp-pv-rwx می‌سازد؛‏ فایل‌های /var/www/html را باید یک بار از Volume قدیمی به Volume تازه کپی کنید (مثلاً با یک Job موقت که هر دو PVC را mount می‌کند،‏ وقتی WordPress متوقف است).

lab/wordpress-deployment-scaled.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: wp-pv-rwx
  labels:
    app: wordpress
spec:
  accessModes:
    - ReadWriteMany            # instead of ReadWriteOnce: many Pods on many Nodes
  storageClassName: nfs-rwx    # hypothetical StorageClass that supports RWX
  resources:
    requests:
      storage: 20Gi
---

kind: Deployment
metadata:
  name: wordpress
  labels:
    app: wordpress
spec:
  replicas: 2
  selector:
    matchLabels:
      app: wordpress
      tier: frontend
  strategy:
    type: RollingUpdate        # possible now: the volume is no longer exclusive
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:
    metadata:
      labels:
        app: wordpress
        tier: frontend
    spec:
      containers:
      - image: wordpress:6.2.1-apache
        name: wordpress
        env:
        - name: WORDPRESS_DB_HOST
          value: wordpress-mysql
        - name: WORDPRESS_DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-pass
              key: password
        - name: WORDPRESS_DB_USER
          value: wordpress
        ports:
        - containerPort: 80
          name: wordpress
        resources:
          requests:
            cpu: 250m
            memory: 256Mi

            cpu: 500m

توضیح تکمیلی: چرا مسیر /wp-admin/install.php برای probe؟

این مسیر همیشه یک پاسخ HTTP (معمولاً ۲۰۰ یا یک redirect) برمی‌گرداند،‏ چه WordPress نصب شده باشد چه نشده،‏ بدون نیاز به authentication — که آن را به یک انتخاب امن و پایدار برای liveness/readiness probe تبدیل می‌کند (فصل ۳). مسیر ریشه (‎/‎) هم کار می‌کند،‏ اما اگر pluginی صفحه‌ی اصلی را redirect یا cache کند ممکن است رفتار غیرمنتظره‌ای داشته باشد. تفاوت readinessProbe و livenessProbe در اینجا: readiness با فاصله‌ی کوتاه‌تر (۵ ثانیه) بررسی می‌شود تا Service سریع بفهمد Pod برای دریافت ترافیک آماده است یا نه؛‏ liveness با delay اولیه‌ی بیشتر (۳۰ ثانیه) اجرا می‌شود تا به Apache زمان کافی برای راه‌اندازی کامل (bootstrap) بدهد و از یک restart loop کاذب جلوگیری شود.

افزودن resources و probe به MySQL

برای MySQL هم باید مشابه همین کار را انجام دهیم. چون MySQL یک HTTP endpoint ندارد،‏ از exec probe استفاده می‌کنیم که دستور mysqladmin ping را داخل container اجرا می‌کند (این دقیقاً همان الگوی exec probe است که در فصل ۳ دیدید).

lab/mysql-deployment-probes.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: wordpress-mysql
  labels:
    app: wordpress
spec:
  selector:
    matchLabels:
      app: wordpress
      tier: mysql
  strategy:
    type: Recreate   # still one replica; the volume stays RWO
  template:
    metadata:
      labels:
        app: wordpress
        tier: mysql
    spec:
      containers:
      - image: mysql:8.0
        name: mysql
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-pass
              key: password
        - name: MYSQL_DATABASE
          value: wordpress
        - name: MYSQL_USER
          value: wordpress
        - name: MYSQL_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-pass
              key: password
        ports:
        - containerPort: 3306
          name: mysql
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
        readinessProbe:
          exec:
            command: ["sh", "-c", "mysqladmin ping -uroot -p$MYSQL_ROOT_PASSWORD"]
          initialDelaySeconds: 10
          periodSeconds: 10
          timeoutSeconds: 3
        livenessProbe:
          exec:
            command: ["sh", "-c", "mysqladmin ping -uroot -p$MYSQL_ROOT_PASSWORD"]
          initialDelaySeconds: 30
          periodSeconds: 20
          timeoutSeconds: 5
          failureThreshold: 3
        volumeMounts:
        - name: mysql-persistent-storage
          mountPath: /var/lib/mysql
      volumes:
      - name: mysql-persistent-storage
        persistentVolumeClaim:
          claimName: mysql-pv-claim
نکته

برای MySQL همچنان replicas روی ۱ باقی مانده و strategy.type همچنان Recreate است،‏ چون PVC مربوط به MySQL هنوز ReadWriteOnce است و MySQL خودش (بدون پیکربندی replication در سطح پایگاه‌داده) توانایی چند-writer ندارد. Scale افقی کردن یک پایگاه‌داده رابطه‌ای مثل MySQL موضوع پیچیده‌تری است (معمولاً با primary/replica در سطح خود MySQL،‏ شبیه به آنچه در بخش Guestbook با Redis leader/follower دیدید) و خارج از محدوده‌ی این tutorial است.

افزودن HorizontalPodAutoscaler برای WordPress

حالا که WordPress می‌تواند بیش از یک replica داشته باشد (به لطف RWX Volume) و resource requests دارد (پیش‌نیاز HPA مبتنی بر CPU،‏ طبق فصل ۱۰)،‏ می‌توانیم یک HorizontalPodAutoscaler تعریف کنیم.

  maxReplicas: 6
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:

        averageUtilization: 70

افزودن PodDisruptionBudget برای WordPress

با ۲ تا ۶ replica از WordPress،‏ حالا باید مطمئن شویم که عملیات‌های داوطلبانه مثل kubectl drain یا node upgrade به‌طور هم‌زمان همه‌ی replicaها را پایین نمی‌آورند (فصل ۹).

lab/wordpress-pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: wordpress-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: wordpress
      tier: frontend

افزودن NetworkPolicy برای محدودکردن دسترسی به MySQL

طبق فصل ۵ و فصل ۱۴،‏ به‌صورت پیش‌فرض هر Pod در یک namespace می‌تواند به هر Pod دیگری (از جمله MySQL روی port ۳۳۰۶) وصل شود،‏ مگر یک NetworkPolicy این ترافیک را محدود کند. یک NetworkPolicy می‌نویسیم که فقط به Podهای با label tier: frontend (یعنی WordPress) اجازه‌ی اتصال به MySQL را می‌دهد.

lab/mysql-networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mysql-allow-wordpress-only
spec:
  podSelector:
    matchLabels:
      app: wordpress
      tier: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: wordpress
          tier: frontend
    ports:
    - protocol: TCP
      port: 3306
shell
kubectl apply -f mysql-networkpolicy.yaml
kubectl describe networkpolicy mysql-allow-wordpress-only
هشدار

NetworkPolicy فقط زمانی اعمال می‌شود که CNI plugin نصب‌شده روی cluster از NetworkPolicy پشتیبانی کند (مثلاً Calico،‏ Cilium یا Weave Net؛‏ نه پیاده‌سازی پیش‌فرض کاملاً ساده‌ی برخی توزیع‌های local). اگر CNI پشتیبانی نکند،‏ اعمال این manifest بدون خطا موفق می‌شود اما هیچ اثری روی ترافیک واقعی نمی‌گذارد — این یک دام رایج در production است که در فصل ۵ به آن اشاره شد.

از آنجا که podSelector این NetworkPolicy روی Pod با tier: mysql است و تنها یک قاعده‌ی Ingress تعریف شده،‏ هر ترافیک ورودی دیگری (مثلاً از یک Pod debugging یا Pod مهاجم که در همان namespace اجرا شده) به‌طور پیش‌فرض drop می‌شود،‏ چون به‌محض تعریف حتی یک NetworkPolicy با policyTypes: [Ingress] برای یک Pod،‏ رفتار پیش‌فرض آن Pod از «allow-all» به «deny-all-except-explicitly-allowed» تغییر می‌کند (دقیقاً مطابق مدل امنیتی NetworkPolicy که در فصل ۵ توضیح داده شد).

تمرین‌های فصل ۱۶ ۲۱ تمرین
  1. مفهومیچرا در Guestbook یک Service جدا برای Redis leader و یک Service جدا برای Redis follower تعریف شده،‏ به‌جای یک Service واحد برای هر دو؟
    پاسخ

    چون Service یک abstraction ساده است که صرفاً ترافیک را بین مجموعه‌ای از Podهای منطبق با selector پخش می‌کند؛‏ هیچ منطقی برای تشخیص read/write ندارد. کد frontend باید صریحاً بداند که برای write باید به redis-leader و برای read باید به redis-follower وصل شود. اگر یک Service واحد با selector مشترک (مثلاً فقط app: redis) تعریف می‌شد،‏ ترافیک write می‌توانست به‌اشتباه به یک follower برسد که قابل نوشتن نیست (یا برعکس،‏ اگر رفتار Redis follower اجازه‌ی نوشتن نمی‌دهد،‏ خطا می‌گرفتیم). جداسازی Service دقیقاً معادل جداسازی endpoint در سطح شبکه است که با معماری leader/follower سازگار است.

  2. مفهومیدر فایل redis-follower-deployment.yaml،‏ فیلد selector.matchLabels فقط app: redis است،‏ نه ترکیب کامل با role: follower. آیا این می‌تواند مشکلی ایجاد کند؟ توضیح دهید.
    پاسخ

    selector دو Deployment (leader و follower) همپوشان است و مستندات Deployment صریحاً هشدار می‌دهد که controllerهایی با selector همپوشان با هم دعوا می‌کنند. در عمل اینجا دعوایی رخ نمی‌دهد: Deployment controller فقط ReplicaSetهایی را مدیریت می‌کند که ownerReference آن‌ها به خودش اشاره می‌کند،‏ و selector هر ReplicaSet علاوه بر app: redis،‏ label به نام pod-template-hash را هم دارد؛‏ پس هر ReplicaSet فقط Podهای خودش را می‌بیند و Pod دارای controller دیگر را تصاحب نمی‌کند.

    مشکل جای دیگری ظاهر می‌شود: هر چیزی که فقط با selector کار می‌کند هر دو گروه را با هم می‌گیرد؛‏ مثلاً kubectl get pods -l app=redis،‏ یک PodDisruptionBudget یا NetworkPolicy با همین selector،‏ یا Service با selector ناقص. best practice این است که selector هر Deployment labelهای متمایزکننده (مثل role) را هم داشته باشد. دقت کنید spec.selector در Deployment پس از ساخت immutable است،‏ پس اصلاح آن یعنی ساختن Deployment تازه.

  3. مفهومیچرا Deployment مربوط به MySQL در tutorial WordPress از strategy: Recreate استفاده می‌کند،‏ در حالی که پیش‌فرض Deployment در فصل ۴،‏ RollingUpdate بود؟
    پاسخ

    RollingUpdate پیش از حذف Pod قدیمی،‏ Pod تازه را می‌سازد؛‏ یعنی مدتی دو instance از MySQL هم‌زمان وجود دارند. PVC از نوع ReadWriteOnce است و این محدودیت در سطح Node است،‏ نه Pod: اگر Pod تازه روی Node دیگری schedule شود،‏ Volume با Multi-Attach error attach نمی‌شود و Pod در ContainerCreating می‌ماند؛‏ اگر روی همان Node بیفتد،‏ هر دو Pod Volume را mount می‌کنند و دو mysqld روی یک data directory اجرا می‌شوند که InnoDB اجازه نمی‌دهد (خطای قفل فایل) یا داده را به خطر می‌اندازد.

    Recreate ابتدا همه‌ی Podهای قدیمی را حذف می‌کند و بعد Pod تازه را می‌سازد؛‏ با این کار همیشه حداکثر یک writer وجود دارد،‏ به قیمت downtime کوتاه در هر rollout. اگر حتی روی یک Node هم نباید دو Pod هم‌زمان Volume را داشته باشند،‏ access mode به نام ReadWriteOncePod این را در سطح Pod تضمین می‌کند.

  4. مفهومیدر manifest Service مربوط به wordpress-mysql،‏ فیلد clusterIP: None چه معنایی دارد و چرا در اینجا استفاده شده؟
    پاسخ

    clusterIP: None این Service را به یک Headless Service تبدیل می‌کند (فصل ۵). به‌جای اختصاص یک ClusterIP مجازی که ترافیک را load balance می‌کند،‏ DNS داخلی cluster نام wordpress-mysql را مستقیماً به IP خود Pod (یا Podها) resolve می‌کند. چون فقط یک replica MySQL وجود دارد،‏ نیازی به load balancing نیست و Headless Service صرفاً یک نام DNS پایدار فراهم می‌کند بدون overhead مسیریابی اضافه.

  5. مفهومیچرا اضافه‌کردن یک HorizontalPodAutoscaler به Deployment مربوط به MySQL در این پروژه بی‌معنی است؟
    پاسخ

    چون HPA فقط تعداد replicaهای Deployment را تغییر می‌دهد،‏ اما معماری فعلی MySQL (PVC با ReadWriteOnce و strategy: Recreate) صراحتاً فقط یک replica هم‌زمان را تحمل می‌کند. اگر HPA بخواهد replicas را بیشتر از ۱ کند،‏ Podهای اضافی یا روی Node دیگر با Multi-Attach error در ContainerCreating می‌مانند یا روی همان Node به قفل data directory در MySQL برمی‌خورند؛‏ در نتیجه اضافه‌کردن HPA به MySQL نه‌تنها فایده‌ای ندارد،‏ بلکه باعث سردرگمی و خطاهای بی‌مورد می‌شود. برای scale کردن پایگاه‌داده باید از یک راه‌حل دیگر مثل replication در سطح خود پایگاه‌داده یا یک managed database استفاده کرد.

  6. مفهومیدر Secret generator بخش kustomization.yaml،‏ چرا Kustomize یک hash به انتهای نام Secret (مثل mysql-pass-c57bb4t7mf) اضافه می‌کند؟ این چه مزیتی نسبت به نام ثابت دارد و چه محدودیتی؟
    پاسخ

    این content-hash naming است: hash از محتوای Secret ساخته می‌شود،‏ پس با هر تغییر محتوا نام Secret هم عوض می‌شود و Kustomize ارجاع‌ها را در Deploymentها به نام تازه به‌روز می‌کند. چون spec.template تغییر کرده،‏ Deployment یک rollout تازه انجام می‌دهد و Podهای تازه مقدار جدید را می‌خوانند؛‏ با نام ثابت،‏ Podهای در حال اجرا مقدار قدیمی environment variable را نگه می‌داشتند (environment variable پس از start شدن container به‌روز نمی‌شود،‏ فصل ۶). Secret قدیمی هم باقی می‌ماند،‏ پس rollback به revision قبلی کار می‌کند. این با immutable Secret (فیلد immutable: true که تغییر همان object را ممنوع می‌کند) فرق دارد.

    نکته‌ی امتیازآور: rollout فقط مقدار را به Podها می‌رساند. تصویر MySQL متغیرهای MYSQL_* را فقط هنگام مقداردهی اولیه‌ی data directory خالی می‌خواند؛‏ پس تغییر رمز در Secret،‏ رمز داخل پایگاه‌داده‌ی موجود را عوض نمی‌کند.

  7. عملییک kind cluster محلی بسازید و کل بخش Guestbook را از ابتدا تا انتها اجرا کنید (چهار manifest:‏ redis-leader Deployment/Service،‏ redis-follower Deployment/Service،‏ frontend Deployment/Service). سپس با kubectl port-forward svc/frontend 8080:80 صفحه را باز کنید و یک پیام ثبت کنید.

    پاسخ

    تشخیص زمان‌بندی: MySQL تک‌replica است و هیچ Pod دیگری جای آن را نمی‌گیرد تا مراحل زیر طی شوند: (۱) حدود ۵۰ ثانیه (node-monitor-grace-period) تا Node در وضعیت NotReady قرار بگیرد و taint به نام node.kubernetes.io/unreachable بخورد؛‏ (۲) ۳۰۰ ثانیه tolerationSeconds که admission plugin به نام DefaultTolerationSeconds به Pod داده،‏ پیش از evict شدن (فصل ۱۲)؛‏ (۳) Pod تازه روی Node دیگر ساخته می‌شود،‏ اما Volume از نوع RWO هنوز به Node مرده attach است و Pod با Multi-Attach error در ContainerCreating می‌ماند تا attach/detach controller پس از ۶ دقیقه انتظار،‏ Volume را force detach کند. جمع این‌ها بیش از ۱۰ دقیقه است. اگر Volume از نوع hostPath یا local روی همان Node بوده باشد،‏ Pod تازه اصلاً به داده‌ی قبلی دسترسی ندارد.

    سرنوشت سفارش‌ها: سفارش‌ها «گم» نشده‌اند؛‏ در این مدت WordPress به MySQL وصل نمی‌شد و درخواست‌ها شکست خوردند،‏ پس هیچ‌وقت ذخیره نشدند. داده‌ای که پیش از خرابی commit شده بود روی disk شبکه‌ای سالم است.

    بهبود: (۱) وقتی مطمئنید Node واقعاً خاموش است،‏ taint به نام node.kubernetes.io/out-of-service را روی آن بگذارید تا Pod و Volume بلافاصله آزاد شوند (non-graceful node shutdown)؛‏ (۲) کوتاه کردن tolerationSeconds برای این Pod زمان eviction را کم می‌کند ولی با قطعی‌های کوتاه شبکه هم Pod را جابه‌جا می‌کند؛‏ (۳) راه‌حل اصلی،‏ MySQL چند replica با replication (StatefulSet همراه با Operator یا Group Replication) یا یک managed database است؛‏ (۴) storage با replication در سطح disk و alert روی وضعیت Nodeها و در دسترس بودن پایگاه‌داده؛‏ (۵) در سطح برنامه،‏ صف یا retry برای ثبت سفارش تا قطعی کوتاه پایگاه‌داده باعث رد شدن سفارش نشود.

    پاسخ

    تشخیص: این دقیقاً همان محدودیت accessModes: ReadWriteOnce است که در متن فصل توضیح داده شد (فصل ۷). یک Volume از نوع RWO فقط می‌تواند هم‌زمان توسط یک Node mount شود. وقتی Pod اول از قبل آن را (روی Node A) mount کرده،‏ تلاش Pod دوم/سوم برای mount کردن همان PVC روی Node دیگر (یا حتی همان Node در برخی CSI driverها بدون پشتیبانی چند-mount) با خطای Multi-Attach رد می‌شود.

    راه‌حل: این مشکل را نمی‌توان صرفاً با افزایش replicas حل کرد. باید یا (۱) دقیقاً مطابق آزمایش عملی این فصل،‏ PVC را به یک StorageClass با پشتیبانی ReadWriteMany مهاجرت داد (مثلاً NFS یا یک filesystem توزیع‌شده) و استراتژی را به RollingUpdate تغییر داد،‏ یا (۲) معماری را طوری بازطراحی کرد که فایل‌های آپلودی WordPress (پوشه‌ی wp-content/uploads) در یک object storage خارجی (مثل S3) ذخیره شوند و PersistentVolume فقط برای فایل‌های core که نیازی به اشتراک‌گذاری ندارند استفاده شود. راه‌حل اشتباه،‏ افزایش صرف replicas بدون تغییر Volume است.

    پاسخ

    تشخیص: بدون PodDisruptionBudget،‏ هیچ محدودیتی روی تعداد Podهایی که kubectl drain می‌تواند هم‌زمان evict کند وجود ندارد؛‏ اگر به‌طور تصادفی چند replica WordPress روی چند Node مختلفی باشند که هم‌زمان (یا با فاصله‌ی کم) drain می‌شوند،‏ eviction API آن‌ها را بدون هماهنگی با یکدیگر قبول می‌کند،‏ چون هیچ budget مشترکی این عملیات‌ها را محدود نمی‌کند (فصل ۹).

    راه‌حل: یک PodDisruptionBudget مثل نمونه‌ی این فصل (minAvailable: 1،‏ یا برای این مقیاس بهتر minAvailable: 2 یا maxUnavailable: 1) تعریف می‌کند که eviction API چند Pod را هم‌زمان مجاز می‌داند. با این budget،‏ هر kubectl drain که بخواهد بیش از حد مجاز Pod evict کند،‏ بلوکه می‌شود تا یک Pod جایگزین Ready شود،‏ و در نتیجه upgrade kernel در Nodeها به‌جای هم‌زمان،‏ به‌صورت طبیعی throttle و serialize می‌شود.

    پاسخ

    تشخیص: بدون readiness probe،‏ کوبرنتیز به‌محض اینکه container به وضعیت Running برسد (فقط process شروع شده باشد)،‏ آن Pod را Ready در نظر می‌گیرد و Service بلافاصله شروع به فرستادن ترافیک به آن می‌کند (فصل ۳ و ۵). اما Apache و WordPress ممکن است چند ثانیه (یا در بار سنگین،‏ بیشتر) طول بکشد تا کاملاً initialize شوند و به درخواست‌های HTTP پاسخ صحیح بدهند؛‏ در این فاصله،‏ کاربران ممکن است خطای ۵۰۲/۵۰۳ یا صفحه‌ی نیمه‌بارگذاری‌شده ببینند.

    راه‌حل: readinessProbe این فصل (httpGet روی /wp-admin/install.php) دقیقاً این مشکل را حل می‌کند: تا وقتی این endpoint یک پاسخ موفق برنگرداند،‏ kubelet آن Pod را NotReady علامت می‌زند و Service آن را از لیست endpointهای فعال حذف می‌کند (فصل ۳)؛‏ در نتیجه در طول یک rolling update،‏ ترافیک فقط به Podهایی می‌رود که واقعاً آماده‌ی سرویس‌دهی هستند،‏ و ترکیب readinessProbe با maxUnavailable/maxSurge استراتژی RollingUpdate (فصل ۴) یک rollout بدون downtime قابل مشاهده برای کاربر ایجاد می‌کند.

  18. سناریوی Productionپس از فعال‌کردن HPA روی WordPress،‏ تیم متوجه می‌شود که در ساعات پرترافیک،‏ Podها به‌سرعت به maxReplicas: 6 می‌رسند اما همچنان کند هستند،‏ و kubectl top pods نشان می‌دهد CPU هر Pod نزدیک به limits.cpu: 500m است (throttling). بررسی بیشتر نشان می‌دهد که واقعاً bottleneck،‏ CPU خود WordPress نیست بلکه MySQL (که هیچ HPA و فقط یک replica دارد) است که با تاخیر query به درخواست‌ها پاسخ می‌دهد و همین باعث می‌شود هر request بیشتر طول بکشد و CPU بیشتری مصرف کند. طراحی این incident را تحلیل کنید و راهکار پیشنهاد دهید.
    پاسخ

    تشخیص: این یک مثال کلاسیک از scale کردن اشتباه لایه است. HPA فقط روی metric CPU خود WordPress نگاه می‌کند (فصل ۱۰)؛‏ نمی‌داند که علت واقعی کندی،‏ bottleneck پایین‌دستی (MySQL) است. با افزایش تعداد Pod WordPress،‏ تعداد connectionهای هم‌زمان به MySQL هم افزایش می‌یابد،‏ که فشار بیشتری روی همان یک instance پایگاه‌داده می‌آورد و ممکن است حتی وضعیت را بدتر کند (thundering herd به سمت پایگاه‌داده).

    راه‌حل: (۱) به‌جای تکیه‌ی صرف بر CPU metric،‏ یک custom metric مرتبط با latency واقعی application (مثلاً از طریق Prometheus Adapter،‏ که در فصل ۱۰ به آن اشاره شد) برای HPA تعریف کنید تا تصویر دقیق‌تری از سلامت end-to-end داشته باشد. (۲) مشکل ریشه‌ای را حل کنید: MySQL را scale (با read replica،‏ caching در سطح query با چیزی مثل Redis،‏ یا یک connection pooler مثل ProxySQL) کنید تا bottleneck واقعی برطرف شود. (۳) یک سقف منطقی‌تر برای maxReplicas بگذارید و alert روی kubectl top pods MySQL و connection count آن تنظیم کنید (فصل ۱۱) تا این الگو زودتر شناسایی شود.

Secret به نام mysql-pass را با kubectl edit secret mysql-pass ویرایش می‌کنند (به‌جای secretGenerator در Kustomize) و سپس kubectl rollout restart deployment wordpress wordpress-mysql می‌زنند. پس از آن سایت با خطای Error establishing a database connection از کار می‌افتد و صبر کردن هم فایده‌ای ندارد. علت را توضیح دهید و روند درست rotate را بنویسید.
    پاسخ

    تشخیص: environment variableها فقط هنگام start شدن container از Secret خوانده می‌شوند،‏ پس restart لازم بود؛‏ اما مشکل اصلی جای دیگری است: تصویر رسمی MySQL متغیرهای MYSQL_ROOT_PASSWORD و MYSQL_PASSWORD را فقط وقتی به کار می‌برد که data directory خالی است. روی PersistentVolume از قبل داده وجود دارد،‏ پس MySQL با همان رمزهای قدیمی ذخیره‌شده در جدول کاربرانش بالا می‌آید،‏ در حالی که WordPress رمز تازه را می‌فرستد. همین اتفاق با تغییر literals در secretGenerator هم می‌افتد؛‏ hash در نام فقط rollout را خودکار می‌کند.

    روند درست:

    sh
    # 1. Change the password inside MySQL first (old password still works for this session)
kubectl exec -it deploy/wordpress-mysql -- \
  mysql -uroot -p -e "ALTER USER 'wordpress'@'%' IDENTIFIED BY 'NEW_PASSWORD';
                     ALTER USER 'root'@'%' IDENTIFIED BY 'NEW_PASSWORD'; FLUSH PRIVILEGES;"

# 2. Update the Secret (kustomization literals or kubectl edit), then apply
kubectl apply -k ./

# 3. Restart WordPress so it reads the new value
kubectl rollout restart deployment wordpress

    بعد از این،‏ فقط WordPress به restart نیاز دارد. برای rotate بدون downtime،‏ کاربر دوم یا رمز دوگانه (dual password در MySQL 8) را در نظر بگیرید،‏ و در production از ابزاری مثل External Secrets Operator یا Vault برای مدیریت چرخه‌ی رمز استفاده کنید. mount کردن Secret به‌صورت فایل هم کمک می‌کند: kubelet فایل را به‌روز می‌کند،‏ ولی برنامه باید فایل را دوباره بخواند.

  20. سناریوی Productionدر حین یک incident review،‏ مشخص می‌شود که یک مهندس،‏ هنگام debug کردن یک مشکل،‏ به‌اشتباه دستور kubectl scale deployment wordpress-mysql --replicas=0 را روی MySQL اجرا کرده و کل سایت برای ۱۰ دقیقه از دسترس خارج شده تا کسی متوجه شود. با معماری‌ای که در این فصل دیدید (بدون تغییر اضافه)،‏ چه مکانیزمی می‌توانست این incident را زودتر تشخیص دهد یا حتی از وقوع آن جلوگیری کند؟
    پاسخ

    تشخیص: این یک human error کلاسیک است،‏ نه یک خطای خودکار کوبرنتیز؛‏ kubectl scale --replicas=0 یک دستور کاملاً معتبر است که Deployment را به عمد به صفر Pod می‌رساند و کوبرنتیز آن را دقیقاً اجرا می‌کند (فصل ۴،‏ desired state).

    راه‌حل چندلایه: (۱) Observability (فصل ۱۱): یک alert روی kube_deployment_status_replicas_available برای wordpress-mysql که به صفر برسد،‏ می‌توانست ظرف چند ثانیه به تیم هشدار دهد،‏ به‌جای اینکه ۱۰ دقیقه طول بکشد. (۲) readinessProbe/livenessProbe این فصل مانع این incident نمی‌شوند (چون کل Pod حذف شده،‏ نه اینکه فقط health check آن خراب شده)،‏ اما یک PodDisruptionBudget هم در برابر scale دستی به صفر محافظتی ایجاد نمی‌کند (PDB فقط eviction داوطلبانه را کنترل می‌کند،‏ نه دستور scale مستقیم).‏ (۳) راهکار واقعی،‏ RBAC محدودتر (فصل ۱۴) است: دسترسی به عملیات update/patch روی Deploymentهای حیاتی production را به یک نقش جداگانه (مثلاً از طریق یک approval workflow یا GitOps pipeline به‌جای kubectl مستقیم) محدود کنید،‏ تا تغییرات دستی و بدون بازبینی روی resourceهای حیاتی امکان‌پذیر نباشد.

  21. سناریوی Productionتیم QA پس از deploy کردن نسخه‌ی HPA‌دار WordPress یک بار تست ناگهانی اجرا می‌کند: ۳۰ ثانیه ترافیک سنگین و سپس قطع کامل. تعداد replicaها هیچ‌وقت بالا نمی‌رود،‏ با این‌که kubectl top pods برای چند ثانیه CPU بالای ۹۰٪ نشان داده است. علت را با توجه به رفتار پیش‌فرض HPA توضیح دهید.
    پاسخ

    تشخیص: stabilization window پیش‌فرض برای scale up صفر است،‏ پس مانع کار نیست؛‏ مشکل زمان‌بندی اندازه‌گیری است. HPA هر ۱۵ ثانیه (--horizontal-pod-autoscaler-sync-period) metric را از metrics-server می‌خواند،‏ و metrics-server خودش هر ۱۵ ثانیه از kubeletها scrape می‌کند و مصرف CPU را به‌صورت میانگین روی یک بازه‌ی زمانی گزارش می‌دهد. یک spike سی‌ثانیه‌ای در این میانگین رقیق می‌شود و ممکن است هیچ نمونه‌ای از آستانه‌ی ۷۰٪ (میانگین روی همه‌ی Podها نسبت به request) بالاتر نرود. حتی اگر scale up شروع شود،‏ Podهای تازه پیش از Ready شدن (با readinessProbe چند ثانیه‌ای) به بار نمی‌رسند و بار تمام شده است. kubectl top همان داده‌ی metrics-server را نشان می‌دهد،‏ پس عدد لحظه‌ای ۹۰٪ لزوماً همان چیزی نیست که HPA در لحظه‌ی تصمیم دیده است.

    راه‌حل: HPA برای spikeهای چندثانیه‌ای طراحی نشده. (۱) minReplicas را برای ظرفیت پایه بالاتر بگذارید (over-provisioning عمدی)؛‏ (۲) برای رویدادهای قابل پیش‌بینی،‏ scale از پیش با CronJob یا ابزاری مثل KEDA؛‏ (۳) metric واکنش‌پذیرتر مثل request per second از Prometheus Adapter؛‏ (۴) limits.cpu سخاوتمندانه‌تر (یا بدون limit برای CPU) تا Podهای موجود burst کوتاه را جذب کنند.

سؤال‌های مصاحبه‌ی فصل ۱۶ ۱۲ سؤال · پاسخ کوتاه و دقیق،‏ همان‌طور که در جلسه‌ی مصاحبه باید گفت
  1. پایهیک برنامه‌ی سه‌لایه را روی کوبرنتیز deploy می‌کنید. برای هر لایه از چه objectهایی استفاده می‌کنید؟
    پاسخ

    لایه‌ی stateless (frontend یا API) با Deployment و یک Service از نوع ClusterIP،‏ و برای دسترسی بیرونی Ingress یا Service از نوع LoadBalancer. لایه‌ی داده با StatefulSet (یا یک Operator) و PersistentVolumeClaim،‏ پشت یک headless Service. پیکربندی در ConfigMap و رمزها در Secret. برای production هم probeها،‏ resources،‏ PodDisruptionBudget،‏ HPA برای لایه‌ی stateless و NetworkPolicy برای محدود کردن دسترسی به پایگاه‌داده.

    نکته‌ی امتیازآور: لایه‌ها فقط با نام DNS در Service به هم وصل می‌شوند،‏ نه IP؛‏ همین جدا شدن،‏ scale و جایگزینی Podها را شفاف می‌کند.

  2. پایهheadless Service چیست و چرا برای MySQL در WordPress استفاده شده است؟
    پاسخ

    Service با clusterIP: None که IP مجازی ندارد؛‏ DNS آن مستقیماً IP خود Podها را برمی‌گرداند و kube-proxy برایش ruleی نمی‌سازد. برای یک instance پایگاه‌داده load balancing لازم نیست و فقط نام پایدار می‌خواهیم. در StatefulSet همین نوع Service نام DNS ثابت برای هر Pod (مثل mysql-0.mysql) می‌سازد.

    نکته‌ی امتیازآور: در تست NetworkPolicy،‏ IP نشان‌داده‌شده IP خود Pod است (مثلاً از 10.244.x.x)،‏ نه یک ClusterIP.

  3. پایهچرا Deployment با Volume از نوع ReadWriteOnce معمولاً با strategy: Recreate نوشته می‌شود؟
    پاسخ

    RollingUpdate پیش از حذف Pod قدیمی Pod تازه را می‌سازد. RWO در سطح Node است: Pod تازه روی Node دیگر با Multi-Attach error در ContainerCreating می‌ماند و روی همان Node دو writer روی یک Volume ایجاد می‌کند. Recreate اول Pod قدیمی را حذف می‌کند.

    نکته‌ی امتیازآور: برای تضمین در سطح Pod از access mode به نام ReadWriteOncePod استفاده کنید؛‏ و برای پایگاه‌داده StatefulSet از Deployment مناسب‌تر است.

  4. پایهkubectl port-forward svc/frontend 8080:80 دقیقاً چه کار می‌کند؟ آیا ترافیک بین Podها پخش می‌شود؟
    پاسخ

    kubectl از طریق API server به kubelet یک Pod پشت آن Service وصل می‌شود و port محلی را به port آن Pod tunnel می‌کند. Service فقط برای پیدا کردن یک Pod استفاده می‌شود؛‏ همه‌ی ترافیک به همان یک Pod می‌رود و از kube-proxy عبور نمی‌کند. اگر آن Pod حذف شود،‏ اتصال قطع می‌شود.

    نکته‌ی امتیازآور: port-forward ابزار debugging است،‏ نه راه expose کردن برنامه.

  5. متوسطدو Deployment با selector همپوشان (app: redis) دارید. آیا با هم دعوا می‌کنند؟
    پاسخ

    در عمل نه: Deployment فقط ReplicaSetهایی را که ownerReference آن‌ها به خودش اشاره دارد مدیریت می‌کند و selector هر ReplicaSet،‏ pod-template-hash را هم دارد. اما مستندات صریحاً هشدار می‌دهد و هر چیزی که فقط selector را نگاه می‌کند (PodDisruptionBudget،‏ NetworkPolicy،‏ kubectl get -l) هر دو گروه را با هم می‌گیرد.

    نکته‌ی امتیازآور: selector در Deployment پس از ساخت immutable است؛‏ پس از ابتدا labelهای متمایزکننده را در selector بگذارید.

  6. متوسطsecretGenerator در Kustomize چرا نام Secret را با hash می‌سازد و آیا این کار rotate رمز پایگاه‌داده را حل می‌کند؟
    پاسخ

    content-hash naming باعث می‌شود با تغییر محتوا نام Secret و در نتیجه Pod template در Deploymentها عوض شود و rollout خودکار رخ دهد؛‏ Secret قدیمی هم برای rollback می‌ماند. اما rollout فقط مقدار تازه را به Podها می‌رساند. تصویر MySQL متغیرهای MYSQL_* را فقط هنگام مقداردهی اولیه‌ی data directory خالی می‌خواند،‏ پس رمز داخل پایگاه‌داده عوض نمی‌شود و WordPress با رمز تازه شکست می‌خورد.

    نکته‌ی امتیازآور: روند درست: ALTER USER در MySQL،‏ سپس به‌روزرسانی Secret،‏ سپس restart برنامه.

  7. متوسطچرا Guestbook متغیر GET_HOSTS_FROM=dns دارد؟ فرق service discovery با DNS و با environment variable چیست؟
    پاسخ

    kubelet برای Serviceهایی که هنگام ساخت Pod در همان namespace وجود دارند environment variable (مثل REDIS_LEADER_SERVICE_HOST) تزریق می‌کند؛‏ Serviceی که بعد ساخته شود دیده نمی‌شود. DNS (CoreDNS) همیشه نام Service را به ClusterIP آن resolve می‌کند،‏ پس ترتیب ساخت مهم نیست.

    نکته‌ی امتیازآور: متغیرهای Service در namespaceهای شلوغ زیاد می‌شوند؛‏ با enableServiceLinks: false در Pod می‌توان آن‌ها را خاموش کرد.

  8. متوسطHPA روی WordPress مقدار cpu: <unknown>/70% نشان می‌دهد. چه چیزهایی را بررسی می‌کنید؟
    پاسخ

    (۱) نصب و سلامت metrics-server (kubectl get apiservice v1beta1.metrics.k8s.io و kubectl top pods)؛‏ (۲) وجود resources.requests.cpu برای همه‌ی containerهای Pod،‏ چون utilization نسبت به request محاسبه می‌شود؛‏ (۳) eventها و conditionها در kubectl describe hpa (مثل FailedGetResourceMetric)؛‏ (۴) این‌که Podها Ready هستند و تازه ساخته نشده‌اند.

    نکته‌ی امتیازآور: اگر حتی یک container (مثلاً sidecar) request نداشته باشد،‏ metric کل Pod قابل محاسبه نیست.

  9. متوسطPodDisruptionBudget با minAvailable: 1 برای WordPress با دو replica،‏ در چه موقعیت‌هایی محافظت نمی‌کند؟
    پاسخ

    PDB فقط eviction داوطلبانه از طریق Eviction API را محدود می‌کند (مثل kubectl drain یا ابزارهای upgrade). خرابی Node،‏ OOM kill،‏ kubectl delete pod،‏ تغییر replicas یا rollout در Deployment و scale به صفر را محدود نمی‌کند.

    نکته‌ی امتیازآور: با یک replica و minAvailable: 1،‏ drain هیچ‌وقت تمام نمی‌شود؛‏ برای workloadهای تک‌replica از maxUnavailable یا قبل از drain از scale موقت استفاده کنید.

  10. پیشرفتهNode میزبان MySQL با Volume شبکه‌ای از نوع RWO خاموش می‌شود. چه مدت طول می‌کشد تا MySQL دوباره بالا بیاید و چطور کوتاهش می‌کنید؟
    پاسخ

    حدود ۵۰ ثانیه تا Node در وضعیت NotReady قرار بگیرد،‏ ۳۰۰ ثانیه tolerationSeconds برای taint به نام node.kubernetes.io/unreachable تا Pod evict شود،‏ و سپس Pod تازه با Multi-Attach error منتظر می‌ماند تا attach/detach controller پس از ۶ دقیقه Volume را force detach کند؛‏ در مجموع بیش از ۱۰ دقیقه.

    نکته‌ی امتیازآور: اگر مطمئنید Node خاموش است،‏ taint به نام node.kubernetes.io/out-of-service (non-graceful node shutdown) Pod را force delete و Volume را بلافاصله detach می‌کند؛‏ راه‌حل اصلی replication در سطح پایگاه‌داده است.

  11. پیشرفتهبرای scale کردن WordPress،‏ accessModes در PVC موجود را از RWO به RWX تغییر می‌دهید و apply می‌کنید. چه می‌شود و روند درست چیست؟
    پاسخ

    درخواست رد می‌شود،‏ چون spec در PVC پس از ساخت immutable است (به‌جز resources.requests برای بزرگ کردن و volumeAttributesClassName). باید یک PVC تازه با StorageClass پشتیبان RWX (مثل NFS یا CephFS یا Filestore) ساخت،‏ داده را با یک Job موقت کپی کرد،‏ Deployment را به PVC تازه اشاره داد و strategy را RollingUpdate کرد.

    نکته‌ی امتیازآور: برای WordPress راه بهتر این است که uploadها به object storage بروند تا Podها stateless شوند و اصلاً volume مشترک لازم نباشد.

  12. پیشرفتهبعد از اعمال NetworkPolicy برای MySQL،‏ تست با Pod بدون label هنوز وصل می‌شود. علت‌های احتمالی چیست؟
    پاسخ

    (۱) CNI در cluster از NetworkPolicy پشتیبانی نمی‌کند (policy بی‌صدا نادیده گرفته می‌شود)؛‏ (۲) podSelector در policy با labelهای Pod در MySQL مطابقت ندارد یا policy در namespace دیگری ساخته شده؛‏ (۳) policy دیگری در همان namespace این ترافیک را allow می‌کند (policyها جمع‌پذیرند و deny صریح ندارند)؛‏ (۴) Pod تست label مجاز را دارد یا در namespaceی است که با namespaceSelector انتخاب شده.

    نکته‌ی امتیازآور: با NetworkPolicy بسته‌ها drop می‌شوند،‏ پس نشانه‌ی درست اعمال policy معمولاً timeout است نه connection refused.

۱. معماری Guestbook

  • دام: selector دو Deployment همپوشان است؛‏ pod-template-hash و ownerReference مانع دعوا هستند ولی مستندات آن را منع می‌کند.
۲. کار با Guestbook

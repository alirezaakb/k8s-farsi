آموزش مبانی کوبرنتیز (Learn Kubernetes Basics)

اهداف

این مجموعه‌ی آموزشی،‏ گام‌به‌گام شما را با مبانی مدیریت cluster در کوبرنتیز آشنا می‌کند. هر بخش (module) هم توضیح پس‌زمینه درباره‌ی قابلیت‌ها و مفاهیم اصلی دارد و هم یک تمرین عملی برای دنبال‌کردن.

با این آموزش‌ها یاد می‌گیرید:

  • یک برنامه‌ی containerی را روی cluster deploy کنید؛‏
  • تعداد replicaهای آن را کم و زیاد کنید؛‏
  • برنامه را به نسخه‌ی جدید نرم‌افزار به‌روز کنید؛‏
  • و مشکلات برنامه را عیب‌یابی (debug) کنید.

کوبرنتیز چه کاری برای شما می‌کند؟

کاربران امروزی انتظار دارند وب‌سرویس‌ها شبانه‌روز و هفت روز هفته (24/7) در دسترس باشند،‏ و توسعه‌دهنده‌ها می‌خواهند چند بار در روز نسخه‌ی جدید منتشر کنند. containerization کمک می‌کند نرم‌افزار طوری بسته‌بندی شود که بتوان آن را بدون قطعی منتشر و به‌روز کرد. کوبرنتیز هم تضمین می‌کند این برنامه‌های containerی هر جا و هر وقت که می‌خواهید اجرا شوند،‏ و کمک می‌کند منابع و ابزارهای مورد نیازشان را پیدا کنند. کوبرنتیز یک پلتفرم متن‌باز و آماده‌ی production است که بر پایه‌ی تجربه‌ی انباشته‌ی گوگل در مدیریت containerها (process ایزوله‌شده‌ای که برنامه را همراه وابستگی‌هایش اجرا می‌کند) و بهترین ایده‌های جامعه‌ی متن‌باز طراحی شده است.

ساختن cluster با Minikube (Using Minikube to Create a Cluster)

مفهوم cluster کوبرنتیز در فصل ۱ (بخش «cluster چیست؟») آمده است؛‏ اینجا با Minikube یک cluster ساده می‌سازید.

اهداف

  • بفهمید cluster کوبرنتیز چیست.
  • بفهمید Minikube چیست.
  • یک cluster کوبرنتیز روی کامپیوتر خودتان راه بیندازید.

پیش از شروع

فرض این آموزش این است که minikube را از قبل نصب کرده‌اید. راهنمای نصب را در صفحه‌ی minikube start (minikube.sigs.k8s.io/docs/start) ببینید.

نکته

از آن صفحه فقط گام ۱: نصب (Installation) را انجام دهید. بقیه‌ی مراحل در همین آموزش پوشش داده می‌شود.

به kubectl هم نیاز دارید؛‏ راهنمای نصبش در صفحه‌ی Install tools (و بخش «نصب ابزارها» در همین پیوست) آمده است.

دستورهای این آموزش با نحو (syntax) پوسته‌های سازگار با POSIX نوشته شده‌اند که پوسته‌ی پیش‌فرض بیشتر سیستم‌های Linux و macOS (مثل bash،‏ zsh یا sh) همین است. کاربران Windows باید از یک پوسته‌ی سازگار با POSIX مثل WSL (Windows Subsystem for Linux) یا Git Bash استفاده کنند تا دستورها را همان‌طور که نوشته شده‌اند اجرا کنند. دستورهایی که از export،‏ ‎$()‎ و ساختارهای مشابه استفاده می‌کنند،‏ در PowerShell یا Command Prompt ویندوز کار نمی‌کنند.

ساختن cluster minikube

برای راه‌اندازی cluster:

shell
minikube start

برای بررسی وضعیت cluster:

shell

برای یک آموزش کامل‌تر،‏ شامل deploy کردن اولین برنامه و گشتن در داشبورد کوبرنتیز،‏ آموزش Hello Minikube را در همین پیوست ببینید.

ابزار kubectl

ابزار خط فرمان کوبرنتیز،‏ یعنی kubectl،‏ اجازه می‌دهد روی clusterها دستور اجرا کنید: برنامه deploy کنید،‏ منابع cluster را بررسی و مدیریت کنید و logها را ببینید. فهرست کامل عملیاتش در مستندات مرجع kubectl آمده؛‏ مرجع سریع آن هم در همین پیوست است.

kubectl روی توزیع‌های مختلف Linux،‏ macOS و Windows نصب می‌شود:

  • نصب kubectl روی Linux
  • نصب kubectl روی macOS
  • نصب kubectl روی Windows

ابزار kind

kind کوبرنتیز را روی کامپیوتر خودتان اجرا می‌کند و به نصب Docker یا Podman نیاز دارد. صفحه‌ی Quick Start آن مراحل راه‌اندازی را نشان می‌دهد.

ابزار minikube

minikube هم مثل kind کوبرنتیز را محلی اجرا می‌کند: یک cluster همه‌در‌یک (all-in-one) یا چند Node روی کامپیوتر شخصی (Windows،‏ macOS یا Linux)،‏ برای امتحان کوبرنتیز یا توسعه‌ی روزانه. راهنمای رسمی Get Started! را دنبال کنید؛‏ وقتی کار کرد،‏ می‌توانید با آن یک برنامه‌ی نمونه اجرا کنید (بخش Hello Minikube در همین پیوست).

ابزار kubeadm

با kubeadm می‌توانید cluster بسازید و مدیریت کنید. kubeadm کارهای لازم برای بالا آوردن یک cluster «حداقلی،‏ قابل‌اجرا و امن» (minimum viable, secure) را به شکلی کاربرپسند انجام می‌دهد. صفحه‌ی Installing kubeadm نصبش را نشان می‌دهد و بعد می‌توانید با آن cluster بسازید (فصل ۱۳).

نصب و راه‌اندازی kubectl روی Linux (Install and Set Up kubectl on Linux)

پیش از شروع

نسخه‌ی kubectl باید حداکثر یک نسخه‌ی minor با cluster شما فاصله داشته باشد. مثلاً client v1.37 با control plane v1.36،‏ v1.37 و v1.38 کار می‌کند. استفاده از آخرین نسخه‌ی سازگار kubectl جلوی مشکلات پیش‌بینی‌نشده را می‌گیرد.

توضیح تکمیلی: قاعده‌ی اختلاف نسخه در عمل

قاعده «یک minor بالاتر یا پایین‌تر» است. فرض کنید تیم شما سه cluster دارد: dev روی v1.38،‏ staging روی v1.37 و prod روی v1.36. kubectl نسخه‌ی v1.37 با هر سه سازگار است،‏ اما kubectl نسخه‌ی v1.38 با prod (v1.36) دو minor فاصله دارد و خارج از محدوده‌ی پشتیبانی است؛‏ ممکن است فیلدهایی بفرستد که API server قدیمی نمی‌شناسد یا خروجی را متفاوت تفسیر کند. برای همین تیم‌های DevOps معمولاً نسخه‌ی kubectl را در image ابزارهای CI ثابت (pin) می‌کنند. بررسی سریع:

shell
kubectl version
output
Client Version: v1.37.0
Kustomize Version: v5.x.x
Server Version: v1.36.4

اگر فاصله بیش از یک minor باشد،‏ kubectl هشداری (WARNING:‏ version difference ...) هم چاپ می‌کند.

روش‌های نصب kubectl روی Linux

  • نصب فایل اجرایی kubectl با curl
  • نصب با مدیر بسته‌ی بومی توزیع (apt،‏ dnf،‏ zypper)
  • نصب با مدیرهای بسته‌ی دیگر (snap،‏ Homebrew)

نصب فایل اجرایی kubectl با curl

  1. آخرین نسخه را دانلود کنید (برای x86-64 و ARM64):

    x86-64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
    ARM64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/arm64/kubectl"
    نکته

    برای دانلود نسخه‌ی مشخص،‏ بخش $(curl -L -s https://dl.k8s.io/release/stable.txt) را با نسخه‌ی موردنظر عوض کنید. مثلاً برای نسخه‌ی 1.37.0 روی Linux x86-64:

    shell
    curl -LO https://dl.k8s.io/release/v1.37.0/bin/linux/amd64/kubectl

    و برای Linux ARM64:

    shell
    curl -LO https://dl.k8s.io/release/v1.37.0/bin/linux/arm64/kubectl

  2. فایل اجرایی را validate کنید (اختیاری). فایل checksum را دانلود کنید:

    x86-64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl.sha256"
    ARM64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/arm64/kubectl.sha256"

    فایل اجرایی را با checksum مقایسه کنید:

    shell
    echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check

    اگر معتبر باشد،‏ خروجی این است:

    output
    kubectl: OK

    اگر بررسی شکست بخورد،‏ sha256sum با کد خروج غیرصفر تمام می‌شود و خروجی‌ای شبیه این می‌دهد:

    output
    kubectl: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
    نکته

    فایل اجرایی و checksum را از یک نسخه دانلود کنید.

  3. kubectl را نصب کنید:

    shell
    sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
    نکته

    اگر روی سیستم دسترسی root ندارید،‏ می‌توانید kubectl را در پوشه‌ی ~/.local/bin نصب کنید:

    shell
    chmod +x kubectl
mkdir -p ~/.local/bin
mv ./kubectl ~/.local/bin/kubectl
# and then append (or prepend) ~/.local/bin to $PATH

  4. بررسی کنید نسخه‌ی نصب‌شده درست است:

    shell
    kubectl version --client

    یا برای نمایش جزئیات بیشتر نسخه:

    shell
    kubectl version --client --output=yaml
توضیح تکمیلی: هر بخش از این دستورها چه می‌کند؟
  • https://dl.k8s.io/release/stable.txt فقط یک خط متن برمی‌گرداند،‏ مثلاً v1.37.0،‏ یعنی آخرین نسخه‌ی پایدار. ‎$(...)‎ در shell این متن را داخل آدرس قرار می‌دهد.
  • curl -L تغییر مسیرها (redirect) را دنبال می‌کند (dl.k8s.io به CDN هدایت می‌کند) و -O فایل را با همان نام اصلی ذخیره می‌کند.
  • ورودی sha256sum --check باید به شکل «hash،‏ دو فاصله،‏ نام فایل» باشد؛‏ برای همین در دستور echo بین hash و kubectl دو فاصله هست.
  • install -o root -g root -m 0755 در یک قدم فایل را کپی می‌کند،‏ مالکش (owner) را root می‌گذارد و مجوز اجرا (rwxr-xr-x) می‌دهد.

چرا checksum در production مهم است؟ اگر در خط لوله‌ی CI فایل از یک mirror داخلی یا proxy دانلود شود،‏ تطبیق checksum تضمین می‌کند فایل دستکاری یا ناقص نشده؛‏ ابزاری که قرار است اطلاعات ورود به cluster production را در دست بگیرد باید قابل‌اعتماد باشد.

نصب با مدیر بسته‌ی بومی

توزیع‌های مبتنی بر Debian

  1. فهرست بسته‌های apt را به‌روز کنید و بسته‌های لازم برای استفاده از repository apt کوبرنتیز را نصب کنید:

    shell
    sudo apt-get update
# apt-transport-https may be a dummy package; if so, you can skip that package
sudo apt-get install -y apt-transport-https ca-certificates curl gnupg

  2. کلید امضای عمومی مخازن کوبرنتیز را دانلود کنید. این کلید برای همه‌ی مخازن یکی است،‏ پس نسخه‌ی داخل آدرس اهمیتی ندارد:

    shell
    # If the folder `/etc/apt/keyrings` does not exist, it should be created before the curl command, read the note below.
# sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
sudo chmod 644 /etc/apt/keyrings/kubernetes-apt-keyring.gpg # allow unprivileged APT programs to read this keyring
    نکته

    در نسخه‌های قدیمی‌تر از Debian 12 و Ubuntu 22.04،‏ پوشه‌ی /etc/apt/keyrings به‌طور پیش‌فرض وجود ندارد و باید پیش از دستور curl ساخته شود.

  3. repository apt مناسب را اضافه کنید. برای نسخه‌ای غیر از v1.37،‏ عدد v1.37 را در دستور زیر با نسخه‌ی minor موردنظر عوض کنید:

    shell
    # This overwrites any existing configuration in /etc/apt/sources.list.d/kubernetes.list
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.37/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo chmod 644 /etc/apt/sources.list.d/kubernetes.list   # helps tools such as command-not-found to work correctly
    نکته

    برای ارتقای kubectl به نسخه‌ی minor دیگر،‏ باید نسخه را در /etc/apt/sources.list.d/kubernetes.list عوض کنید و بعد apt-get update و apt-get upgrade را اجرا کنید. جزئیات در Changing The Kubernetes Package Repository.

  4. فهرست بسته‌ها را به‌روز کنید و kubectl را نصب کنید:

    shell
    sudo apt-get update
sudo apt-get install -y kubectl

توزیع‌های مبتنی بر Red Hat

  1. repository yum کوبرنتیز را اضافه کنید (برای نسخه‌ی دیگر،‏ v1.37 را عوض کنید):

    shell
    # This overwrites any existing configuration in /etc/yum.repos.d/kubernetes.repo
cat <<EOF | sudo tee /etc/yum.repos.d/kubernetes.repo
[kubernetes]
name=Kubernetes
baseurl=https://pkgs.k8s.io/core:/stable:/v1.37/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/v1.37/rpm/repodata/repomd.xml.key

بررسی پیکربندی kubectl

kubectl برای پیدا کردن cluster و دسترسی به آن به یک فایل kubeconfig نیاز دارد. این فایل وقتی clusterی را با kube-up.sh می‌سازید یا cluster Minikube را با موفقیت راه می‌اندازید،‏ خودکار ساخته می‌شود. محل پیش‌فرض آن ~/.kube/config است.

با گرفتن وضعیت cluster بررسی کنید kubectl درست پیکربندی شده:

shell
kubectl cluster-info

اگر در پاسخ یک آدرس (URL) دیدید،‏ همه چیز درست است. اگر پیامی شبیه زیر دیدید،‏ kubectl درست پیکربندی نشده یا نمی‌تواند به cluster وصل شود:

output
The connection to the server <server-name:port> was refused - did you specify the right host or port?

مثلاً اگر قصد دارید cluster را روی لپ‌تاپ اجرا کنید،‏ اول باید ابزاری مثل Minikube نصب کنید و بعد دستورهای بالا را دوباره اجرا کنید.

اگر kubectl cluster-info آدرس برمی‌گرداند اما باز هم به cluster دسترسی ندارید،‏ با این دستور جزئیات را بررسی کنید:

shell
kubectl cluster-info dump

رفع خطای «No Auth Provider Found»

در کوبرنتیز 1.26،‏ authentication داخلی kubectl برای سرویس‌های کوبرنتیز مدیریت‌شده‌ی این cloud providerها حذف شد. این providerها pluginهای kubectl منتشر کرده‌اند که authentication مخصوص خودشان را فراهم می‌کنند:

  • Azure AKS: kubelogin plugin
  • Google Kubernetes Engine: gke-gcloud-auth-plugin

همین پیام ممکن است دلایل دیگری هم داشته باشد که ربطی به این تغییر ندارند.

پیکربندی‌ها و pluginهای اختیاری

فعال‌کردن تکمیل خودکار (autocompletion)

kubectl برای Bash،‏ Zsh،‏ Fish و PowerShell تکمیل خودکار دارد که در تایپ خیلی صرفه‌جویی می‌کند.

Bash:‏ script تکمیل برای Bash با kubectl completion bash ساخته می‌شود و source کردنش تکمیل خودکار را فعال می‌کند. اما این script به bash-completion وابسته است،‏ پس اول آن را نصب کنید (با type _init_completion می‌توانید بررسی کنید نصب هست یا نه).

نصب bash-completion: بیشتر مدیرهای بسته آن را دارند: apt-get install bash-completion یا dnf install bash-completion. این کار فایل /usr/share/bash-completion/bash_completion را می‌سازد. بسته به مدیر بسته،‏ ممکن است لازم باشد آن را دستی در ~/.bashrc source کنید. shell را دوباره باز کنید و type _init_completion را اجرا کنید؛‏ اگر موفق نبود،‏ این خط را به ~/.bashrc اضافه کنید:

~/.bashrc
source /usr/share/bash-completion/bash_completion

shell را دوباره باز کنید و با type _init_completion مطمئن شوید bash-completion درست نصب شده.

فعال‌کردن تکمیل kubectl در Bash: باید مطمئن شوید script تکمیل kubectl در همه‌ی نشست‌های shell بارگذاری می‌شود. دو راه دارد:

User
echo 'source <(kubectl completion bash)' >>~/.bashrc
System
kubectl completion bash | sudo tee /etc/bash_completion.d/kubectl > /dev/null
sudo chmod a+r /etc/bash_completion.d/kubectl

اگر برای kubectl یک alias (مثل k) دارید،‏ می‌توانید تکمیل خودکار را به آن هم گسترش دهید:

shell
echo 'alias k=kubectl' >>~/.bashrc
echo 'complete -o default -F __start_kubectl k' >>~/.bashrc
نکته

bash-completion همه‌ی scriptهای پوشه‌ی /etc/bash_completion.d را بارگذاری می‌کند.

هر دو روش معادل‌اند. بعد از باز کردن دوباره‌ی shell،‏ تکمیل خودکار کار می‌کند. برای فعال‌شدن در همین نشست فعلی:

shell
source ~/.bashrc

نصب plugin kubectl convert

این plugin (جزء قابل‌اتصالی که رفتار سیستم را گسترش می‌دهد) برای kubectl،‏ فایل‌های manifest را بین نسخه‌های مختلف API تبدیل می‌کند. به‌خصوص برای مهاجرت manifestها به نسخه‌ای از API که در نسخه‌های جدید کوبرنتیز منسوخ نشده مفید است. migrate to non deprecated apis را ببینید.

  1. آخرین نسخه را دانلود کنید:

    x86-64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl-convert"
    ARM64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/arm64/kubectl-convert"

  2. فایل را validate کنید (اختیاری). فایل checksum را دانلود کنید:

    x86-64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl-convert.sha256"
    ARM64
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/arm64/kubectl-convert.sha256"

    مقایسه با checksum:

    shell
    echo "$(cat kubectl-convert.sha256) kubectl-convert" | sha256sum --check

    اگر معتبر باشد:

    output
    kubectl-convert: OK

    اگر بررسی شکست بخورد،‏ sha256sum با کد خروج غیرصفر تمام می‌شود و خروجی‌ای شبیه این می‌دهد:

    output
    kubectl-convert: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
    نکته

    فایل اجرایی و checksum را از یک نسخه دانلود کنید.

  3. kubectl-convert را نصب کنید:

    shell
    sudo install -o root -g root -m 0755 kubectl-convert /usr/local/bin/kubectl-convert

  4. بررسی کنید plugin نصب شده:

    shell
    kubectl convert --help

    اگر خطایی ندیدید،‏ plugin با موفقیت نصب شده است.

  5. فایل‌های نصب را پاک کنید:

    shell
    rm kubectl-convert kubectl-convert.sha256
توضیح تکمیلی: plugin چطور پیدا می‌شود؟

kubectl هر فایل اجرایی در PATH را که نامش با kubectl- شروع شود plugin می‌شناسد؛‏ پس kubectl-convert با دستور kubectl convert اجرا می‌شود (سازوکار pluginها در فصل ۱ و ۱۵). کاربرد واقعی: پیش از ارتقای cluster،‏ manifestهای قدیمی repository GitOps را که هنوز نسخه‌ی API حذف‌شده دارند،‏ با kubectl convert -f old.yaml --output-version <group>/<version> به نسخه‌ی جدید تبدیل می‌کنید.

نصب فایل اجرایی با curl

  1. آخرین نسخه را دانلود کنید (برای Intel یا Apple Silicon):

    Intel
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/darwin/amd64/kubectl"
    Apple Silicon
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/darwin/arm64/kubectl"

    shell
    echo "$(cat kubectl.sha256)  kubectl" | shasum -a 256 --check

    اگر معتبر باشد،‏ خروجی kubectl: OK است؛‏ اگر نه،‏ kubectl: FAILED و shasum: WARNING: 1 computed checksum did NOT match (با کد خروج غیرصفر). فایل اجرایی و checksum باید از یک نسخه باشند.

    shell
    chmod +x ./kubectl
sudo mv ./kubectl /usr/local/bin/kubectl
sudo chown root: /usr/local/bin/kubectl
    نکته

    مطمئن شوید /usr/local/bin در environment variable PATH هست.

  4. نسخه را بررسی کنید (kubectl version --client یا kubectl version --client --output=yaml) و بعد فایل checksum را پاک کنید:

    shell
    rm kubectl.sha256

سلام Minikube (Hello Minikube)

این آموزش نشان می‌دهد چطور یک برنامه‌ی نمونه را با minikube روی کوبرنتیز اجرا کنید. آموزش یک container image فراهم می‌کند که همه‌ی درخواست‌ها را عیناً برمی‌گرداند (echo).

اهداف

  • یک برنامه‌ی نمونه را روی minikube deploy کنید؛‏
  • برنامه را اجرا کنید؛‏
  • logهای برنامه را ببینید.

پیش از شروع

فرض این آموزش این است که minikube را نصب کرده‌اید؛‏ راهنمای نصب در گام ۱ صفحه‌ی minikube start است.

نکته

فقط گام ۱ (Installation) را انجام دهید؛‏ بقیه در همین صفحه پوشش داده می‌شود.

به kubectl هم نیاز دارید؛‏ راهنمای نصبش در Install tools است.

ساختن cluster minikube

shell

نکته

minikube start یک cluster تک‌Node می‌سازد که هم نقش control plane را دارد و هم نقش worker Node. این با بیشتر production clusterها فرق دارد؛‏ در آن‌ها Nodeهای control plane معمولاً با taintها از worker Nodeها جدا می‌شوند یا کاملاً از دید کاربر پنهان‌اند.

توضیح تکمیلی: minikube start دقیقاً چه می‌کند؟

(این جزئیات مربوط به رفتار minikube است.) minikube start بر اساس driver انتخاب‌شده (docker،‏ virtualbox،‏ hyperkit،‏ kvm2 و…) یک «ماشین» می‌سازد،‏ container runtime و kubelet را داخلش راه می‌اندازد،‏ control plane را اجرا می‌کند و در نهایت یک cluster،‏ یک user و یک context به نام minikube به فایل ~/.kube/config اضافه می‌کند و current-context را روی آن می‌گذارد. خروجی شبیه این است:

حالا می‌توانید از این آدرس استفاده کنید و به ترمینال اول برگردید.

ساختن یک Deployment

یک Pod در کوبرنتیز گروهی از یک یا چند container است که برای مدیریت و شبکه به هم گره خورده‌اند؛‏ Pod این آموزش فقط یک container دارد. یک Deployment سلامت Pod شما را بررسی می‌کند و اگر container داخلش خاتمه یابد،‏ آن را دوباره راه می‌اندازد. Deployment روش توصیه‌شده برای ساختن و مقیاس‌دهی Podهاست.

  1. با kubectl create یک Deployment بسازید که یک Pod را مدیریت کند. Pod یک container از image داده‌شده اجرا می‌کند:

    shell
    # Run a test container image that includes a webserver
kubectl create deployment hello-node --image=registry.k8s.io/e2e-test-images/agnhost:2.53 -- /agnhost netexec --http-port=8080

  2. Deployment را ببینید:

    shell
    kubectl get deployments

    خروجی چیزی شبیه این است:

    output
    NAME         READY   UP-TO-DATE   AVAILABLE   AGE
hello-node   1/1     1            1           1m

    (ممکن است کمی طول بکشد تا Pod آماده شود؛‏ اگر "0/1" دیدید،‏ چند ثانیه بعد دوباره امتحان کنید.)

  3. Pod را ببینید:

    shell
    kubectl get pods

    خروجی چیزی شبیه این است:

    output
    NAME                          READY     STATUS    RESTARTS   AGE
hello-node-5f76cf6ccf-br9b5   1/1       Running   0          1m

  4. eventهای cluster را ببینید:

    shell
    kubectl get events

  5. پیکربندی kubectl را ببینید:

    shell
    kubectl config view

  6. logهای container Pod را ببینید (نام Pod را با نامی که از kubectl get pods گرفتید عوض کنید).

    نکته

    در دستور kubectl logs،‏ hello-node-5f76cf6ccf-br9b5 را با نام Pod خودتان عوض کنید.

    shell
    kubectl logs hello-node-5f76cf6ccf-br9b5

    خروجی چیزی شبیه این است:

    output
    I0911 09:19:26.677397       1 log.go:195] Started HTTP server on port 8080
I0911 09:19:26.677586       1 log.go:195] Started UDP server on port  8081
نکته

برای اطلاعات بیشتر درباره‌ی دستورهای kubectl،‏ kubectl overview را ببینید.

توضیح تکمیلی: نام Pod از کجا می‌آید و خروجی events و config view چه شکلی است؟

نام hello-node-5f76cf6ccf-br9b5 سه بخش دارد: نام Deployment (hello-node)،‏ یک hash از Pod template (الگویی که controller،‏ Podها را از روی آن می‌سازد) که نام ReplicaSet را می‌سازد (5f76cf6ccf)،‏ و یک پسوند تصادفی برای خود Pod (br9b5). یعنی زنجیره‌ی مالکیت Deployment ←‏ ReplicaSet ←‏ Pod است (فصل ۴). بخش -- /agnhost netexec --http-port=8080 در دستور create هم فرمان container را عوض می‌کند؛‏ هر چیزی بعد از ‎--‎ به‌عنوان command و args در Pod template قرار می‌گیرد.

ساختن یک Service

Pod به‌طور پیش‌فرض فقط با IP داخلی‌اش و از داخل cluster در دسترس است. برای اینکه container hello-node از بیرون شبکه‌ی مجازی کوبرنتیز در دسترس باشد،‏ باید Pod را با یک Service در دسترس بگذارید.

هشدار

container agnhost یک آدرس /shell دارد که برای عیب‌یابی مفید است،‏ اما در دسترس گذاشتنش روی اینترنت عمومی خطرناک است. این آموزش را روی clusterی که به اینترنت باز است یا production cluster اجرا نکنید.

  1. با kubectl expose Pod را در دسترس بگذارید:

    shell
    kubectl expose deployment hello-node --type=LoadBalancer --port=8080

    flag --type=LoadBalancer یعنی می‌خواهید Service بیرون از cluster در دسترس باشد. کد برنامه در این image آزمایشی فقط روی port TCP 8080 گوش می‌دهد؛‏ اگر با kubectl expose port دیگری را در دسترس می‌گذاشتید،‏ clientها نمی‌توانستند وصل شوند.

  2. Service ساخته‌شده را ببینید:

    shell
    kubectl get services

    خروجی چیزی شبیه این است:

    output
    NAME         TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)          AGE
hello-node   LoadBalancer   10.108.144.78   <pending>     8080:30369/TCP   21s
kubernetes   ClusterIP      10.96.0.1       <none>        443/TCP          23m

    در cloud providerهایی که load balancer دارند،‏ یک IP خارجی تخصیص داده می‌شود. در minikube،‏ Service از نوع LoadBalancer از طریق دستور minikube service در دسترس قرار می‌گیرد.

  3. این دستور را اجرا کنید:

    shell
    minikube service hello-node

    پنجره‌ای از مرورگر باز می‌شود که پاسخ برنامه را نشان می‌دهد.

توضیح تکمیلی: خواندن ستون PORT(S) و چرا EXTERNAL-IP در حالت pending می‌ماند

در 8080:30369/TCP،‏ عدد اول port خود Service روی ClusterIP است و عدد دوم nodePort است که کوبرنتیز از بازه‌ی پیش‌فرض 30000 تا 32767 تخصیص داده؛‏ چون LoadBalancer در واقع روی NodePort ساخته می‌شود (فصل ۵). <pending> یعنی هیچ controllerی (برنامه‌ای که مدام current state را به desired state نزدیک می‌کند) در cluster نیست که load balancer واقعی بسازد و آدرسش را در status.loadBalancer بنویسد. در minikube می‌توانید با اجرای minikube tunnel در ترمینال جدا چنین IPی بگیرید. در clusterهای داخل سازمان (bare-metal) هم دقیقاً همین اتفاق می‌افتد،‏ مگر اینکه پیاده‌سازی load balancer مثل MetalLB نصب شده باشد (فصل ۵).

Service به نام kubernetes در namespace default خودکار ساخته می‌شود و به API server اشاره می‌کند؛‏ Podها از طریق آن (kubernetes.default.svc) به API دسترسی دارند.

توضیح تکمیلی: stop در برابر delete

minikube stop ماشین را خاموش می‌کند اما disk،‏ imageهای دانلودشده و همه‌ی objectهای cluster (در etcd) حفظ می‌شوند؛‏ minikube start بعدی همان cluster را برمی‌گرداند. minikube delete ماشین و داده‌ها را کاملاً پاک می‌کند و ورودی‌های minikube را از kubeconfig حذف می‌کند. اگر cluster به حالت عجیبی رفت (مثلاً بعد از تغییر driver یا نسخه)،‏ delete و start ساده‌ترین راه برگشت به حالت تمیز است؛‏ همان فلسفه‌ی «محیط یادگیری را بی‌نگرانی بساز و خراب کن».

آموزش مبانی – بخش ۲: ساختن Deployment با kubectl (Using kubectl to create a Deployment)

مسیر «آموزش مبانی کوبرنتیز» یک دوره‌ی عملی کامل است: بخش ۲ یک Deployment می‌سازد،‏ بخش ۳ Podها و Nodeها را بررسی می‌کند،‏ بخش ۴ برنامه را با Service در دسترس می‌گذارد،‏ بخش ۵ آن را مقیاس می‌دهد و بخش ۶ rolling update (جایگزینی تدریجی Podهای قدیمی با Podهای جدید بدون قطعی) و برگشت را انجام می‌دهد. همه‌ی این بخش‌ها را پشت سر هم روی همان cluster minikube (یا هر cluster دیگری) اجرا کنید.

اهداف

  • آشنایی با Deployment برنامه‌ها؛‏
  • deploy کردن اولین برنامه روی کوبرنتیز با kubectl.

پیش از شروع

دستورهای این آموزش با نحو پوسته‌های سازگار با POSIX نوشته شده‌اند (پوسته‌ی پیش‌فرض بیشتر سیستم‌های Linux و macOS،‏ مثل bash،‏ zsh یا sh). کاربران Windows باید از پوسته‌ای سازگار با POSIX مثل WSL یا Git Bash استفاده کنند؛‏ دستورهایی که از export،‏ ‎$()‎ و ساختارهای مشابه استفاده می‌کنند در PowerShell یا Command Prompt کار نمی‌کنند. (همین پیش‌نیاز در بخش‌های ۳ تا ۶ هم برقرار است.)

Deploymentهای کوبرنتیز

Deployment مسئول ساختن و به‌روزرسانی instanceهای برنامه‌ی شماست. (instance یعنی هر کپی در حال اجرای برنامه.)

نکته

container این آموزش به معماری AMD64 نیاز دارد. اگر minikube را روی کامپیوتری با معماری دیگر (مثلاً Apple Silicon) اجرا می‌کنید،‏ از driverی استفاده کنید که AMD64 را شبیه‌سازی کند؛‏ مثلاً driver مربوط به Docker Desktop.

وقتی یک cluster در حال اجرا دارید،‏ می‌توانید برنامه‌های containerized خود را روی آن deploy کنید. برای این کار یک Deployment می‌سازید که به کوبرنتیز می‌گوید instanceهای برنامه را چطور بسازد و به‌روز کند. بعد از ساختن Deployment،‏ control plane،‏ instanceهای برنامه را روی Nodeهای مختلف cluster schedule می‌کند.

پس از ساخته‌شدن instanceها،‏ Deployment controller مدام آن‌ها را پایش (monitoring) می‌کند. اگر Nodeی که host یک instance است از کار بیفتد یا حذف شود،‏ controller آن instance را با instanceی روی Node دیگر جایگزین می‌کند. این یک سازوکار self-healing (جایگزینی خودکار اجزای از کارافتاده) برای مقابله با خرابی ماشین یا نگهداری آن است.

پیش از ابزارهای orchestration،‏ معمولاً از scriptهای نصب برای راه‌اندازی برنامه‌ها استفاده می‌شد،‏ اما این scriptها نمی‌توانستند بعد از خرابی ماشین برنامه را بازیابی کنند. Deploymentهای کوبرنتیز با ساختن instanceها و سرپا نگه‌داشتن آن‌ها روی Nodeها،‏ رویکردی اساساً متفاوت برای مدیریت برنامه دارند.

deploy کردن اولین برنامه روی کوبرنتیز

برنامه‌ها باید در یکی از قالب‌های containerی پشتیبانی‌شده بسته‌بندی شوند تا بتوان آن‌ها را روی کوبرنتیز deploy کرد.

Deployment را با command-line interface کوبرنتیز،‏ kubectl،‏ می‌سازید و مدیریت می‌کنید؛‏ kubectl برای کار با cluster از API کوبرنتیز استفاده می‌کند. در این بخش رایج‌ترین دستورهای لازم برای ساختن Deployment را یاد می‌گیرید.

هنگام ساختن Deployment،‏ container image برنامه و تعداد replicaهایی را که می‌خواهید اجرا کنید مشخص می‌کنید. می‌توانید این اطلاعات را بعداً با به‌روزرسانی Deployment تغییر دهید؛‏ بخش ۵ و بخش ۶ مقیاس‌دهی و به‌روزرسانی را نشان می‌دهند.

برای اولین Deployment از یک برنامه‌ی ساده استفاده می‌کنید که در یک Docker container بسته‌بندی شده. (اگر هنوز آموزش Hello Minikube را انجام نداده‌اید،‏ می‌توانید اول آن را انجام دهید.) kubectl هم باید نصب باشد (install tools). حالا که می‌دانید Deployment چیست،‏ اولین برنامه را deploy کنیم!

مبانی kubectl

قالب رایج دستورهای kubectl این است: kubectl action resource؛‏ یعنی عمل مشخص‌شده (مثل create،‏ describe یا delete) روی منبع مشخص‌شده (مثل node یا deployment) انجام می‌شود. با افزودن --help بعد از هر زیردستور،‏ اطلاعات پارامترهایش را می‌بینید (مثلاً kubectl get nodes --help).

با kubectl version بررسی کنید که kubectl نصب است و به cluster وصل است؛‏ باید هم نسخه‌ی client و هم نسخه‌ی server را ببینید. با kubectl get nodes Nodeهای در دسترس را ببینید؛‏ کوبرنتیز بر اساس منابع هر Node تصمیم می‌گیرد برنامه کجا deploy شود.

shell
kubectl version
kubectl get nodes
kubectl get nodes --help
output (نمونه روی minikube)
Client Version: v1.37.0
Kustomize Version: v5.x.x
Server Version: v1.37.0
NAME       STATUS   ROLES           AGE   VERSION
minikube   Ready    control-plane   10m   v1.37.0

deploy کردن یک برنامه

اولین برنامه را با دستور kubectl create deployment deploy کنیم. باید نام Deployment و محل image برنامه را بدهیم (برای imageهایی که بیرون از Docker Hub هستند،‏ آدرس کامل repository را بنویسید).

shell
kubectl create deployment kubernetes-bootcamp --image=gcr.io/google-samples/kubernetes-bootcamp:v1

عالی! همین حالا اولین برنامه‌تان را deploy کردید. این دستور چند کار برایتان انجام داد:

  • یک Node مناسب برای اجرای instance برنامه پیدا کرد (فعلاً فقط ۱ Node داریم)؛‏
  • برنامه را برای اجرا روی آن Node schedule کرد؛‏
  • cluster را طوری تنظیم کرد که در صورت نیاز instance را روی Node دیگری از نو schedule کند.

برای فهرست Deploymentها از kubectl get deployments استفاده کنید:

shell
kubectl get deployments

می‌بینیم ۱ Deployment یک instance از برنامه را اجرا می‌کند؛‏ این instance داخل یک container روی Node شما در حال اجراست.

output (نمونه)
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
kubernetes-bootcamp   1/1     1            1           30s
توضیح تکمیلی: دستوری (imperative) در برابر اعلانی (declarative)

kubectl create deployment یک دستور دستوری است: به کوبرنتیز می‌گویید «این را بساز». پشت صحنه،‏ kubectl یک object از نوع Deployment می‌سازد و به API server می‌فرستد. می‌توانید manifest معادل را بدون ساختن object ببینید:

shell
kubectl create deployment kubernetes-bootcamp --image=gcr.io/google-samples/kubernetes-bootcamp:v1 --dry-run=client -o yaml

دیدن برنامه

Podها روی یک شبکه‌ی خصوصی و ایزوله اجرا می‌شوند. به‌طور پیش‌فرض از Podها و Serviceهای دیگر همان cluster دیده می‌شوند،‏ اما از بیرون آن شبکه نه. وقتی از kubectl استفاده می‌کنیم،‏ از طریق یک آدرس API با برنامه ارتباط می‌گیریم.

راه‌های دیگر در دسترس گذاشتن برنامه بیرون از cluster را در بخش ۴ می‌بینیم. توضیح مفصل Pod هم در فصل‌های بعد می‌آید.

دستور kubectl proxy proxyی می‌سازد که ارتباط را به شبکه‌ی خصوصی cluster هدایت می‌کند. proxy با Ctrl+C بسته می‌شود و در حین اجرا خروجی‌ای نشان نمی‌دهد.

برای اجرای proxy،‏ یک ترمینال دوم باز کنید.

shell (terminal دوم)
kubectl proxy

حالا بین ترمینال ما و cluster یک اتصال داریم و proxy دسترسی مستقیم به API را از این ترمینال‌ها ممکن می‌کند. مثلاً می‌توانیم نسخه را مستقیماً از API با curl بپرسیم:

shell
curl http://localhost:8001/version
نکته

اگر port 8001 در دسترس نیست،‏ مطمئن شوید kubectl proxy در ترمینال دوم هنوز اجرا می‌شود.

API server برای هر Pod بر اساس نامش یک آدرس می‌سازد که از طریق proxy هم در دسترس است. اول نام Pod را در environment variable POD_NAME ذخیره کنیم:

shell
export POD_NAME=$(kubectl get pods -o go-template --template '{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}')
echo Name of the Pod: $POD_NAME

با این دستور از طریق API proxy‌شده به Pod دسترسی پیدا می‌کنید:

shell
curl http://localhost:8001/api/v1/namespaces/default/pods/$POD_NAME:8080/proxy/

برای اینکه Deployment بدون proxy در دسترس باشد،‏ به یک Service نیاز داریم که در بخش ۴ توضیح داده می‌شود.

توضیح تکمیلی: مسیر یک درخواست از طریق kubectl proxy

kubectl proxy روی ‎127.0.0.1:8001‎ گوش می‌دهد و هر درخواست را با اطلاعات ورود kubeconfig شما (certificate یا token) به API server می‌فرستد؛‏ پس curl لازم نیست خودش authenticate کند. خروجی curl http://localhost:8001/version شبیه این است:

output
{
  "major": "1",
  "minor": "37",
  "gitVersion": "v1.37.0",
  "platform": "linux/amd64",
  ...
}

آدرس دوم از subresource (بخش جداگانه‌ی یک منبع با endpoint خودش،‏ مثل /status یا /scale) proxy روی Pod استفاده می‌کند: /api/v1/namespaces/default/pods/<POD>:8080/proxy/. مسیر درخواست: curl ←‏ kubectl proxy ←‏ API server ← (مستقیم به IP Pod) ←‏ port 8080 داخل container. پاسخ برنامه‌ی bootcamp این است:

output
Hello Kubernetes bootcamp! | Running on: kubernetes-bootcamp-9bc58d867-x4wqc | v=1

قالب go-template فقط روی .items (فهرست Podها) حلقه می‌زند و نام هر Pod را در یک خط چاپ می‌کند؛‏ اگر بیش از یک Pod داشته باشید،‏ POD_NAME چند خطی می‌شود و آدرس خراب می‌شود. معادل دقیق‌تر برای clusterهای شلوغ: kubectl get pods -l app=kubernetes-bootcamp -o jsonpath='{.items[0].metadata.name}'.

هشدار امنیتی: kubectl proxy هر کسی را که به localhost:8001 دسترسی دارد با هویت شما به API server وصل می‌کند. هرگز آن را با --address=0.0.0.0 روی server مشترک اجرا نکنید؛‏ برای عیب‌یابی یک Pod خاص،‏ kubectl port-forward محدودتر و امن‌تر است.

بخش ۳: دیدن Podها و Nodeها (Viewing Pods and Nodes)

اهداف

  • آشنایی با Podها؛‏
  • آشنایی با Nodeها؛‏
  • عیب‌یابی برنامه‌های deployed.

Podهای کوبرنتیز

Pod گروهی از یک یا چند application container است،‏ همراه با storage مشترک (volumeها)،‏ آدرس IP و اطلاعات مربوط به نحوه‌ی اجرای آن‌ها.

وقتی در بخش ۲ Deployment را ساختید،‏ کوبرنتیز یک Pod ساخت تا نمونه‌ی برنامه را میزبانی کند. Pod یک مدل انتزاعی است که گروهی از یک یا چند container و منابع مشترکشان را نمایش می‌دهد:

  • storage مشترک،‏ به شکل Volume؛‏
  • شبکه،‏ به شکل یک آدرس IP یکتا در cluster؛‏
  • اطلاعات نحوه‌ی اجرای هر container،‏ مثل نسخه‌ی image (بسته‌ی فقط‌خواندنی شامل برنامه و وابستگی‌هایش که container از آن ساخته می‌شود) یا portهایی که باید استفاده شوند.

Pod یک «host منطقی» مخصوص برنامه را مدل می‌کند و می‌تواند containerهای مختلفی داشته باشد که نسبتاً به هم وابسته‌اند (tightly coupled). مثلاً یک Pod ممکن است هم container برنامه‌ی Node.js و هم containerی را داشته باشد که داده‌هایی را که web server منتشر می‌کند فراهم می‌کند. containerهای یک Pod آدرس IP و فضای port مشترک دارند،‏ همیشه کنار هم (co-located) و با هم schedule می‌شوند (co-scheduled) و در یک زمینه‌ی مشترک روی یک Node اجرا می‌شوند.

Pod واحد اتمی پلتفرم کوبرنتیز است: وقتی Deployment می‌سازیم،‏ Deployment Podهایی با containerهای داخلشان می‌سازد (نه اینکه مستقیماً container بسازد). هر Pod به Nodeی که روی آن schedule شده گره خورده و تا خاتمه (بر اساس restart policy) یا حذف همان‌جا می‌ماند. اگر Node خراب شود،‏ Podهای مشابه روی Nodeهای دیگر cluster schedule می‌شوند.

نمای کلی Podها

containerها فقط وقتی باید در یک Pod باشند که به هم وابسته‌اند و باید منابعی مثل disk را مشترک استفاده کنند.

Nodeها

Pod همیشه روی یک Node اجرا می‌شود. Node یک ماشین worker در کوبرنتیز است که بسته به cluster می‌تواند مجازی یا فیزیکی باشد،‏ و control plane آن را مدیریت می‌کند. هر Node می‌تواند چند Pod داشته باشد؛‏ control plane،‏ Podها را خودکار روی Nodeها schedule می‌کند (یعنی برای هر Pod،‏ Node مناسب را انتخاب می‌کند) و منابع در دسترس هر Node را هم در نظر می‌گیرد.

روی هر Node دست‌کم این‌ها اجرا می‌شوند:

  • Kubelet:‏ processی که ارتباط control plane و Node را برقرار می‌کند و Podها و containerهای در حال اجرا روی ماشین را مدیریت می‌کند.
  • یک container runtime (مثل containerd) که image را از registry (مخزنی که imageها در آن نگهداری و از آن دریافت می‌شوند) می‌گیرد،‏ باز می‌کند و برنامه را اجرا می‌کند.

نمای کلی Nodeها

توضیح تکمیلی: چرا Pod و نه container؟

فرض کنید یک web server و یک container کمکی (sidecar) دارید که هر دقیقه فایل‌های سایت را از Git می‌گیرد و روی یک volume مشترک می‌نویسد. اگر این دو در دو Pod جدا باشند،‏ ممکن است روی دو Node مختلف بروند و دیگر disk مشترکی نداشته باشند. قرار دادنشان در یک Pod تضمین می‌کند کنار هم باشند،‏ یک volume را ببینند و از طریق localhost با هم ارتباط برقرار کنند. اما قرار دادن frontend و backend در یک Pod اشتباه است: نمی‌توانید جداگانه مقیاسشان دهید و خرابی یکی روی دیگری اثر می‌گذارد (فصل ۳). ستون READY در kubectl get pods هم به همین دلیل به شکل ‎1/1‎ یا ‎2/2‎ است: تعداد containerهای آماده از کل containerهای Pod.

عیب‌یابی با kubectl

در بخش ۲ از kubectl استفاده کردید؛‏ در این بخش هم برای گرفتن اطلاعات برنامه‌ها و محیطشان از آن استفاده می‌کنید. رایج‌ترین عملیات با این زیردستورها انجام می‌شود:

  • kubectl get: فهرست منابع
  • kubectl describe: نمایش اطلاعات مفصل یک منبع
  • kubectl logs: چاپ logهای یک container در یک Pod
  • kubectl exec: اجرای یک دستور در یک container از Pod

با این دستورها می‌بینید برنامه کی deploy شده،‏ current state (وضعیتی که سیستم در این لحظه واقعاً دارد) آن چیست،‏ کجا اجرا می‌شود و پیکربندی‌اش چیست.

بررسی پیکربندی برنامه

بررسی کنیم برنامه‌ی بخش قبل در حال اجراست. با kubectl get دنبال Podها می‌گردیم:

shell
kubectl get pods

اگر هیچ Podی در حال اجرا نیست،‏ چند ثانیه صبر کنید و دوباره فهرست بگیرید. وقتی Pod در حال اجرا دیدید،‏ ادامه دهید.

بعد برای دیدن containerهای داخل Pod و imageهایشان،‏ kubectl describe pods را اجرا می‌کنیم:

shell
kubectl describe pods

نمایش برنامه در ترمینال

یادآوری: Podها در شبکه‌ای ایزوله و خصوصی اجرا می‌شوند،‏ پس برای عیب‌یابی و کار با آن‌ها باید دسترسی را proxy کنیم. با kubectl proxy در یک ترمینال دوم proxy اجرا کنید:

shell (terminal دوم)
kubectl proxy

حالا دوباره نام Pod را می‌گیریم و مستقیماً از طریق proxy از آن می‌پرسیم. ذخیره‌ی نام Pod در POD_NAME:

shell
export POD_NAME="$(kubectl get pods -o go-template --template '{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}')"
echo Name of the Pod: $POD_NAME

برای دیدن خروجی برنامه،‏ یک درخواست با curl بفرستید:

shell
curl http://localhost:8001/api/v1/namespaces/default/pods/$POD_NAME:8080/proxy/

این آدرس مسیر رسیدن به API مربوط به Pod است.

نکته

لازم نیست نام container را بدهیم،‏ چون Pod فقط یک container دارد.

اجرای دستور داخل container

وقتی Pod بالا و در حال اجراست،‏ می‌توانیم مستقیماً داخل container دستور اجرا کنیم؛‏ با زیردستور exec و نام Pod. فهرست environment variableها:

shell
kubectl exec "$POD_NAME" -- env

باز هم نام container را حذف کردیم چون Pod فقط یک container دارد. حالا یک نشست bash داخل container باز می‌کنیم:

shell
kubectl exec -ti $POD_NAME -- bash

حالا یک shell باز روی containerی داریم که برنامه‌ی NodeJS را اجرا می‌کند. کد منبع برنامه در فایل server.js است:

shell
cat server.js

با یک curl بررسی کنید برنامه بالاست:

shell
curl http://localhost:8080

اینجا از localhost استفاده کردیم چون دستور را داخل Pod اجرا می‌کنیم. اگر به localhost:8080 وصل نمی‌شوید،‏ مطمئن شوید kubectl exec را اجرا کرده‌اید و داخل Pod هستید.

برای بستن اتصال به container،‏ exit را تایپ کنید.

توضیح تکمیلی: flagهای -ti و جداکننده‌ی --

-t یک ترمینال (TTY) اختصاص می‌دهد و -i ورودی استاندارد را باز نگه می‌دارد؛‏ بدون این دو،‏ bash تعاملی فوراً بسته می‌شود. ‎--‎ مرز بین flagهای kubectl و دستوری است که داخل container اجرا می‌شود؛‏ بدون آن،‏ flagهایی مثل -la در ls -la ممکن است توسط خود kubectl تفسیر شوند. اگر Pod چند container داشت،‏ با -c <container-name> container را انتخاب می‌کردید.

نکته‌ی عملیاتی: kubectl exec روی production باید با RBAC محدود (subresource pods/exec) و ممیزی (audit) شود،‏ چون عملاً یک shell روی برنامه‌ی زنده است (فصل ۱۴). همچنین بسیاری از imageهای production (مثل distroless) اصلاً bash ندارند؛‏ برای آن‌ها ephemeral container (container موقتی که برای عیب‌یابی به Pod در حال اجرا اضافه می‌شود) و kubectl debug مناسب است (فصل ۱۱).

نمونه‌ی خروجی kubectl exec "$POD_NAME" -- env: متغیرهایی مثل HOSTNAME=kubernetes-bootcamp-9bc58d867-x4wqc،‏ KUBERNETES_SERVICE_HOST=10.96.0.1 و KUBERNETES_SERVICE_PORT=443 که کوبرنتیز برای service discovery (پیدا کردن نشانی سرویس‌ها از روی نامشان) از طریق environment variable به container تزریق می‌کند (فصل ۵).

بخش ۴: در دسترس گذاشتن برنامه با Service (Using a Service to Expose Your App)

اهداف

  • آشنایی با Service در کوبرنتیز؛‏
  • فهم رابطه‌ی labelها و selectorها با Service؛‏
  • در دسترس گذاشتن برنامه بیرون از cluster.

نگاهی به Serviceهای کوبرنتیز

Podها «فانی»اند و چرخه‌ی عمر دارند. وقتی یک worker Node از کار می‌افتد،‏ Podهای روی آن هم از بین می‌روند؛‏ سپس یک ReplicaSet ممکن است با ساختن Podهای جدید cluster را به desired state برگرداند. مثال دیگر: یک backend پردازش تصویر با ۳ replica. این replicaها جایگزین‌پذیرند؛‏ frontend نباید اهمیت دهد به کدام replica وصل است،‏ یا حتی اینکه یک Pod از بین رفته و دوباره ساخته شده. اما هر Pod یک IP یکتا دارد (حتی Podهای یک Node)،‏ پس باید راهی باشد که تغییرات Podها خودکار مدیریت شود تا برنامه‌ها کار کنند.

Service یک لایه‌ی انتزاعی است که مجموعه‌ای منطقی از Podها را تعریف می‌کند و در دسترس گذاشتن آن‌ها برای ترافیک خارجی،‏ توزیع بار (load balancing) و service discovery را ممکن می‌کند.

Service مجموعه‌ای منطقی از Podها و سیاستی برای دسترسی به آن‌ها تعریف می‌کند و باعث می‌شود Podهای وابسته به هم «سست‌پیوند» (loosely coupled) باشند. Service هم مثل همه‌ی objectهای کوبرنتیز با YAML یا JSON تعریف می‌شود. مجموعه‌ی Podهای هدف معمولاً با یک label selector (شرطی برای انتخاب اشیا بر اساس جفت‌های کلید/مقدارشان) تعیین می‌شود (پایین‌تر می‌بینیم چرا گاهی Service بدون selector لازم است).

با اینکه هر Pod IP یکتا دارد،‏ این IPها بدون Service بیرون از cluster در دسترس نیستند. Service اجازه می‌دهد برنامه ترافیک بگیرد و با تعیین type در spec به روش‌های مختلفی در دسترس قرار می‌گیرد:

  • ClusterIP (پیش‌فرض): Service روی یک IP داخلی cluster در دسترس است؛‏ یعنی فقط از داخل cluster.
  • NodePort:‏ Service روی یک port یکسان در همه‌ی Nodeهای انتخاب‌شده (با NAT) در دسترس است؛‏ از بیرون با NodeIP:NodePort. شامل ClusterIP هم هست.
  • LoadBalancer: در cloud فعلی (اگر پشتیبانی شود) یک load balancer خارجی می‌سازد و یک IP ثابت خارجی به Service می‌دهد. شامل NodePort هم هست.
  • ExternalName:‏ Service را با برگرداندن یک رکورد CNAME به مقدار فیلد externalName (مثلاً foo.bar.example.com) نگاشت می‌کند؛‏ هیچ proxyی راه‌اندازی نمی‌شود.

اطلاعات بیشتر در آموزش Using Source IP و Connecting Applications with Services (فصل ۵).

بعضی کاربردهای Service بدون selector تعریف می‌شوند. Service بدون selector،‏ EndpointSlice متناظر (و object قدیمی Endpoints که از v1.33 منسوخ شده است) را خودکار نمی‌سازد؛‏ این اجازه می‌دهد Service را دستی به مقصدهای مشخصی نگاشت کنید (مثلاً یک پایگاه داده‌ی بیرون از cluster). حالت دیگر بدون selector،‏ استفاده از type: ExternalName است.

Serviceها و labelها

Service ترافیک را بین مجموعه‌ای از Podها پخش می‌کند و اجازه می‌دهد Podها بمیرند و تکثیر شوند بی‌آنکه برنامه آسیب ببیند. کشف و مسیریابی بین Podهای وابسته (مثل frontend و backend) را Serviceها انجام می‌دهند.

Service مجموعه‌ی Podهایش را با labelها و selectorها پیدا می‌کند؛‏ ابزار پایه‌ای برای گروه‌بندی که عملیات منطقی روی objectها را ممکن می‌کند. labelها زوج‌های کلید/مقدارند که به objectها وصل می‌شوند و کاربردهای زیادی دارند:

  • مشخص‌کردن objectهای محیط توسعه،‏ تست و عملیات؛‏
  • افزودن label نسخه؛‏
  • دسته‌بندی objectها.

labelها را می‌توان هنگام ساخت یا بعداً به objectها وصل کرد و هر زمان تغییرشان داد. حالا برنامه را با یک Service در دسترس بگذاریم و چند label اعمال کنیم.

گام ۱: ساختن Service جدید

بررسی کنیم برنامه در حال اجراست:

shell

اگر Podی در حال اجرا نیست،‏ یعنی objectهای آموزش‌های قبل پاک شده‌اند؛‏ برگردید و Deployment را از بخش ۲ دوباره بسازید،‏ چند ثانیه صبر کنید و دوباره Podها را فهرست کنید.

بعد Serviceهای فعلی cluster را فهرست کنیم:

shell
kubectl get services

برای در دسترس گذاشتن Deployment برای ترافیک خارجی،‏ از kubectl expose با گزینه‌ی --type=NodePort استفاده می‌کنیم:

shell
kubectl expose deployment/kubernetes-bootcamp --type="NodePort" --port 8080

حالا Serviceی به نام kubernetes-bootcamp داریم که یک ClusterIP یکتا،‏ یک port داخلی و یک IP خارجی (IP مربوط به Node) گرفته است.

توضیح تکمیلی: دو فیلد مهم در describe

قاعده‌ی طلایی عیب‌یابی (و سؤال محبوب مصاحبه): اگر Service پاسخ نمی‌دهد و Endpoints خالی است (<none>)،‏ مشکل تقریباً همیشه ناهمخوانی selector با labelهای Pod یا آماده نبودن Podهاست،‏ نه شبکه (فصل ۵ و ۱۱). عبارت go-template {{(index .spec.ports 0).nodePort}} هم یعنی «از آرایه‌ی spec.ports عضو صفرم را بردار و فیلد nodePort آن را چاپ کن».

گام ۲: استفاده از labelها

Deployment خودکار یک label برای Pod ساخت. با describe deployment نام (کلید) آن را ببینید:

shell
kubectl describe deployment

از این label برای جست‌وجوی Podها استفاده کنیم؛‏ با kubectl get pods و پارامتر -l و مقدار label:

shell
kubectl get pods -l app=kubernetes-bootcamp

همین کار را برای Serviceها هم می‌شود کرد:

shell
kubectl get services -l app=kubernetes-bootcamp

نام Pod را در متغیر POD_NAME ذخیره کنید:

shell
export POD_NAME="$(kubectl get pods -o go-template --template '{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}')"
echo "Name of the Pod: $POD_NAME"

برای افزودن label جدید،‏ زیردستور label را با نوع شیء،‏ نام شیء و label جدید بنویسید:

shell
kubectl label pods "$POD_NAME" version=v1

این label جدیدی به Pod اضافه می‌کند (نسخه‌ی برنامه را به Pod سنجاق کردیم) و با describe pod بررسی‌اش می‌کنیم:

shell
kubectl describe pods "$POD_NAME"

label حالا به Pod وصل است و می‌توانیم Podها را با label جدید جست‌وجو کنیم:

shell
kubectl get pods -l version=v1

و Pod را می‌بینیم.

آزمایش عملی: label اضافه روی Pod چه اثری روی Service دارد؟
shell
kubectl get pods --show-labels
kubectl get endpointslices -l kubernetes.io/service-name=kubernetes-bootcamp
output (نمونه)

افزودن version=v1 هیچ اثری روی Service ندارد،‏ چون selector فقط app=kubernetes-bootcamp را می‌خواهد و Pod هنوز آن را دارد. اما اگر label app را از Pod بردارید (kubectl label pods "$POD_NAME" app-)،‏ دو اتفاق می‌افتد: Service آن Pod را از مقصدهایش حذف می‌کند،‏ و ReplicaSet (که Podهایش را با همان selector می‌شمارد) فکر می‌کند یک Pod کم دارد و Pod جدیدی می‌سازد. ReplicaSet آن Pod را رها (release) می‌کند و owner reference آن را برمی‌دارد؛‏ Pod قدیمی orphan (objectی بدون owner) می‌شود ولی همچنان اجرا می‌شود. این ترفند برای ایزوله کردن یک Pod مشکل‌دار جهت عیب‌یابی در production استفاده می‌شود (مفهومش در صفحه‌ی ReplicaSet،‏ فصل ۴). در پایان label را برگردانید یا Pod اضافه را حذف کنید.

گام ۳: حذف Service

برای حذف Service از delete service استفاده کنید؛‏ اینجا هم می‌توان از label استفاده کرد:

shell
kubectl delete service -l app=kubernetes-bootcamp

تأیید کنید Service حذف شده:

shell
kubectl get services

برای اطمینان از اینکه مسیر دیگر باز نیست،‏ IP و port قبلی را curl کنید:

shell
curl http://"$(minikube ip):$NODE_PORT"

این ثابت می‌کند برنامه دیگر از بیرون cluster در دسترس نیست. اما با یک curl از داخل Pod می‌بینید برنامه هنوز اجرا می‌شود:

shell
kubectl exec -ti $POD_NAME -- curl http://localhost:8080

برنامه بالاست،‏ چون Deployment آن را مدیریت می‌کند. برای خاموش‌کردن برنامه باید Deployment را هم حذف کنید.

هشدار

kubectl delete service -l app=kubernetes-bootcamp همه‌ی Serviceهای دارای این label را در namespace فعلی حذف می‌کند،‏ نه فقط یکی. در production،‏ پیش از هر حذف مبتنی بر label،‏ اول همان selector را با kubectl get اجرا کنید تا ببینید دقیقاً چه چیزی حذف می‌شود،‏ و مطمئن شوید context و namespace درست است (بخش context در همین پیوست).

بخش ۵: اجرای چند instance از برنامه (Running Multiple Instances of Your App)

اهداف

  • مقیاس‌دهی دستی یک برنامه‌ی موجود با kubectl.

مقیاس‌دهی برنامه

می‌توانید از همان ابتدا Deployment را با چند instance بسازید؛‏ با پارامتر --replicas در دستور kubectl create deployment.

قبلاً یک Deployment ساختیم و آن را با یک Service در دسترس گذاشتیم. Deployment فقط یک Pod برای اجرای برنامه ساخت. وقتی ترافیک زیاد می‌شود،‏ باید برنامه را مقیاس دهیم تا پاسخ‌گوی کاربران باشد.

اگر بخش‌های قبل را انجام نداده‌اید،‏ از ساختن cluster با minikube شروع کنید.

مقیاس‌دهی با تغییر تعداد replicaها در Deployment انجام می‌شود.

نکته

اگر این بخش را بعد از بخش قبل انجام می‌دهید،‏ ممکن است Service را حذف کرده باشید یا Serviceی از نوع NodePort ساخته باشید. این بخش فرض می‌کند برای Deployment به نام kubernetes-bootcamp یک Service از نوع LoadBalancer وجود دارد.

اگر Service بخش قبل را حذف نکرده‌اید،‏ اول آن را حذف کنید و بعد با این دستور یک Service جدید از نوع LoadBalancer بسازید:

shell
kubectl expose deployment/kubernetes-bootcamp --type="LoadBalancer" --port 8080

نمای کلی مقیاس‌دهی

افزایش مقیاس (scale out) یک Deployment تضمین می‌کند Podهای جدید ساخته و روی Nodeهای دارای منابع کافی schedule شوند؛‏ تعداد Podها تا desired state جدید بالا می‌رود. کوبرنتیز از مقیاس‌دهی خودکار Podها هم پشتیبانی می‌کند که خارج از این آموزش است (فصل ۱۰). مقیاس صفر هم ممکن است و همه‌ی Podهای Deployment را خاتمه می‌دهد.

اجرای چند instance به راهی برای پخش ترافیک بین آن‌ها نیاز دارد. Service یک load balancer داخلی دارد که ترافیک را بین همه‌ی Podهای Deployment پخش می‌کند و با پایش مداوم Podها از طریق endpointها،‏ ترافیک را فقط به Podهای در دسترس می‌فرستد.

با داشتن چند instance،‏ می‌توانید rolling update را بدون قطعی انجام دهید؛‏ موضوع بخش بعد. حالا به ترمینال برویم و برنامه را مقیاس دهیم.

مقیاس‌دهی یک Deployment

فهرست Deploymentها:

shell
kubectl get deployments

خروجی باید شبیه این باشد:

output
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
kubernetes-bootcamp   1/1     1            1           11m

باید ۱ Pod داشته باشیم؛‏ اگر نه،‏ دستور را دوباره اجرا کنید. ستون‌ها:

  • NAME: نام Deploymentها.
  • READY: نسبت replicaهای آماده به replicaهای دلخواه (CURRENT/DESIRED).
  • UP-TO-DATE: تعداد replicaهایی که برای رسیدن به desired state به‌روز شده‌اند.
  • AVAILABLE: تعداد replicaهایی که برای کاربران در دسترس‌اند.
  • AGE: مدت زمان اجرای برنامه.

برای دیدن ReplicaSetی که Deployment ساخته:

shell
kubectl get rs

نام ReplicaSet همیشه به شکل [DEPLOYMENT-NAME]-[RANDOM-STRING] است؛‏ این رشته در واقع همان مقدار label به نام pod-template-hash است که از hash مربوط به Pod template ساخته می‌شود.

output (نمونه)
NAME                            DESIRED   CURRENT   READY   AGE
kubernetes-bootcamp-9bc58d867   1         1         1       11m

دو ستون مهم:

  • DESIRED: تعداد دلخواه replicaها که هنگام ساختن Deployment تعیین می‌کنید؛‏ یعنی desired state.
  • CURRENT: تعداد replicaهایی که الان اجرا می‌شوند.

حالا Deployment را به ۴ replica برسانیم؛‏ با kubectl scale و نوع Deployment،‏ نام و تعداد دلخواه:

shell
kubectl scale deployments/kubernetes-bootcamp --replicas=4

دوباره فهرست Deploymentها:

shell
kubectl get deployments

تغییر اعمال شد و ۴ instance در دسترس داریم. بررسی تعداد Podها:

shell
kubectl get pods -o wide

حالا ۴ Pod با IPهای مختلف داریم. این تغییر در eventهای Deployment ثبت شده:

shell
kubectl describe deployments/kubernetes-bootcamp

در خروجی این دستور هم ۴ replica را می‌بینید.

توزیع بار

بررسی کنیم Service بار را پخش می‌کند. برای پیدا کردن IP و port،‏ مثل بخش قبل از describe service استفاده می‌کنیم:

shell
kubectl describe services/kubernetes-bootcamp

environment variable NODE_PORT را بسازید:

shell
export NODE_PORT="$(kubectl get services/kubernetes-bootcamp -o go-template='{{(index .spec.ports 0).nodePort}}')"

حالا چند بار به IP و port curl بزنید:

shell
curl http://"$(minikube ip):$NODE_PORT"

توضیح تکمیلی: چرا توزیع دقیقاً نوبتی (round-robin) نیست؟

در خروجی نمونه،‏ یک Pod دو بار و Pod دیگری دو بار دیده شده و یکی از چهار Pod اصلاً دیده نشده. در حالت پیش‌فرض (kube-proxy در حالت iptables یا nftables)،‏ هر اتصال جدید به‌صورت تصادفی بین مقصدها پخش می‌شود،‏ نه نوبتی دقیق؛‏ با تعداد درخواست زیاد،‏ توزیع تقریباً یکنواخت می‌شود (فصل ۵).

پیامد مهم عملیاتی: توزیع بار Service در سطح اتصال (لایه‌ی ۴) است،‏ نه درخواست. clientهایی که اتصال طولانی دارند (keep-alive،‏ gRPC،‏ WebSocket) بعد از افزایش مقیاس خودبه‌خود به Podهای جدید نمی‌روند؛‏ برای توزیع در سطح درخواست به یک proxy لایه‌ی ۷ (Ingress/Gateway یا service mesh) یا توزیع بار سمت client نیاز دارید.

کاهش مقیاس

برای رساندن Deployment به ۲ replica،‏ دوباره scale را اجرا کنید:

shell
kubectl scale deployments/kubernetes-bootcamp --replicas=2

با get deployments بررسی کنید تغییر اعمال شده:

shell
kubectl get deployments

تعداد replicaها به ۲ رسید. فهرست Podها:

shell
kubectl get pods -o wide

این تأیید می‌کند ۲ Pod خاتمه یافتند.

توضیح تکمیلی: هنگام کاهش مقیاس کدام Podها حذف می‌شوند؟

ReplicaSet controller برای انتخاب Podهای حذفی اولویت‌هایی دارد: Podهای منتظر یا schedule‌نشده زودتر از Podهای در حال اجرا،‏ Podهای ناآماده زودتر از آماده‌ها،‏ و به‌طور کلی Podهای جدیدتر زودتر از قدیمی‌تر (جزئیات در صفحه‌ی ReplicaSet،‏ فصل ۴؛‏ با annotation controller.kubernetes.io/pod-deletion-cost هم می‌شود روی این انتخاب اثر گذاشت). بلافاصله بعد از کاهش مقیاس ممکن است دو Pod را چند ثانیه در وضعیت Terminating ببینید؛‏ در این فاصله Service آن‌ها را از مقصدها بیرون برده و برنامه فرصت graceful shutdown (خاموش شدن مرتب،‏ با فرصت دادن به Podها برای پایان کار) دارد.

بخش ۶: rolling update (Performing a Rolling Update)

اهداف

  • انجام یک rolling update با kubectl.

پیش از شروع

مثل بخش‌های قبل،‏ دستورها با نحو پوسته‌ی POSIX نوشته شده‌اند؛‏ کاربران Windows از WSL یا Git Bash استفاده کنند،‏ چون دستورهایی مثل export و ‎$()‎ در PowerShell یا Command Prompt کار نمی‌کنند.

به‌روزرسانی برنامه

rolling update اجازه می‌دهد Deployment بدون قطعی به‌روز شود؛‏ با جایگزینی تدریجی instanceهای Pod با instanceهای جدید.

کاربران انتظار دارند برنامه همیشه در دسترس باشد و توسعه‌دهنده‌ها می‌خواهند چند بار در روز نسخه‌ی جدید منتشر کنند. در کوبرنتیز این کار با rolling update انجام می‌شود: Podهای فعلی کم‌کم با Podهای جدید جایگزین می‌شوند. Podهای جدید روی Nodeهای دارای منابع کافی schedule می‌شوند و کوبرنتیز صبر می‌کند تا Podهای جدید راه بیفتند و بعد Podهای قدیمی را حذف کند.

در بخش قبل برنامه را روی چند instance اجرا کردیم؛‏ این پیش‌نیاز به‌روزرسانی بدون اثر روی دسترس‌پذیری است. به‌طور پیش‌فرض،‏ حداکثر تعداد Podهایی که در طول به‌روزرسانی می‌توانند در دسترس نباشند و حداکثر تعداد Podهای جدیدی که می‌توانند اضافه ساخته شوند،‏ هر دو برابر یک است. هر دو را می‌توان به‌صورت عدد یا درصد تنظیم کرد. در کوبرنتیز به‌روزرسانی‌ها نسخه‌دار (versioned) هستند و هر به‌روزرسانی Deployment را می‌توان به نسخه‌ی پایدار قبلی برگرداند.

نمای کلی rolling update

اگر Deployment به‌صورت عمومی در دسترس باشد،‏ Service فقط به Podهایی ترافیک می‌فرستد که آماده‌ی پاسخ‌گویی‌اند؛‏ پس کاربران در طول به‌روزرسانی همچنان به برنامه دسترسی دارند. rolling update این کارها را ممکن می‌کند:

  • ارتقای برنامه از یک محیط به محیط دیگر (با به‌روزکردن container image)؛‏
  • برگشت به نسخه‌های قبلی (rollback)؛‏
  • یکپارچه‌سازی و تحویل پیوسته (CI/CD) بدون قطعی.

در ادامه برنامه را به نسخه‌ی جدید به‌روز می‌کنیم و یک برگشت هم انجام می‌دهیم.

توضیح تکمیلی: maxUnavailable و maxSurge

این رفتار را دو فیلد در strategy.rollingUpdate کنترل می‌کنند (جزئیات در فصل ۴): maxUnavailable،‏ حداکثر تعداد یا درصد Podهایی که می‌توانند در طول به‌روزرسانی در دسترس نباشند (پیش‌فرض ۲۵٪)؛‏ و maxSurge،‏ حداکثر تعداد یا درصد Podهای اضافه بر تعداد دلخواه (پیش‌فرض ۲۵٪). مقدار درصدی برای maxUnavailable به پایین و برای maxSurge به بالا گرد می‌شود؛‏ پس با ۴ replica هر دو برابر یک Pod می‌شوند. اما چون Deployment این آموزش در پایان بخش ۵ به ۲ replica رسید،‏ در همین به‌روزرسانی maxUnavailable صفر و maxSurge یک است. جمله‌ی مستندات («هر دو برابر یک است») فقط برای همین اندازه‌های کوچک درست است؛‏ مقدار پیش‌فرض واقعی ۲۵٪ است.

در سرویسی با ۱۲ replica،‏ پیش‌فرض ۲۵٪ یعنی تا ۳ Pod هم‌زمان می‌توانند در دسترس نباشند و تا ۳ Pod اضافه ساخته شوند. برای سرویس‌های حساس معمولاً maxUnavailable: 0 و maxSurge: 1 (یا بیشتر) تنظیم می‌شود تا ظرفیت هرگز کمتر از مقدار دلخواه نشود؛‏ به قیمت منابع اضافه در طول rollout (فرایند deployment تدریجی نسخه‌ی جدید).

به‌روزکردن نسخه‌ی برنامه

فهرست Deploymentها:

shell
kubectl get deployments

فهرست Podهای در حال اجرا:

shell
kubectl get pods

برای دیدن نسخه‌ی فعلی image،‏ describe pods را اجرا کنید و دنبال فیلد Image بگردید:

shell
kubectl describe pods

برای به‌روزکردن image به نسخه‌ی ۲،‏ از set image با نام Deployment و نسخه‌ی جدید image استفاده کنید:

shell
kubectl set image deployments/kubernetes-bootcamp kubernetes-bootcamp=docker.io/jocatalin/kubernetes-bootcamp:v2

این دستور به Deployment گفت از image دیگری استفاده کند و یک rolling update را آغاز کرد. با get pods وضعیت Podهای جدید و خاتمه‌ی Pod قدیمی را ببینید:

shell
kubectl get pods

تأیید به‌روزرسانی

اول بررسی کنید Service در حال اجراست (ممکن است در بخش قبل حذفش کرده باشید): describe services/kubernetes-bootcamp. اگر نبود،‏ دوباره بسازیدش:

shell
kubectl expose deployment/kubernetes-bootcamp --type="NodePort" --port 8080

environment variable NODE_PORT را بسازید:

shell
export NODE_PORT="$(kubectl get services/kubernetes-bootcamp -o go-template='{{(index .spec.ports 0).nodePort}}')"
echo "NODE_PORT=$NODE_PORT"

سپس به IP و port curl بزنید:

shell
curl http://"$(minikube ip):$NODE_PORT"

هر بار به Pod متفاوتی می‌رسید و همه‌ی Podها حالا آخرین نسخه (v2) را اجرا می‌کنند.

با rollout status هم می‌توانید به‌روزرسانی را تأیید کنید:

shell
kubectl rollout status deployments/kubernetes-bootcamp

و با describe pods نسخه‌ی image را ببینید:

shell
kubectl describe pods

در فیلد Image تأیید کنید که نسخه‌ی v2 اجرا می‌شود.

برگشت به نسخه‌ی قبل

یک به‌روزرسانی دیگر انجام دهیم و imageی با تگ v10 را deploy کنیم:

shell
kubectl set image deployments/kubernetes-bootcamp kubernetes-bootcamp=gcr.io/google-samples/kubernetes-bootcamp:v10

وضعیت Deployment را با get deployments ببینید:

shell
kubectl get deployments

دقت کنید خروجی تعداد دلخواه Podهای در دسترس را نشان نمی‌دهد. همه‌ی Podها را فهرست کنید:

shell
kubectl get pods

بعضی Podها وضعیت ImagePullBackOff دارند. برای جزئیات،‏ describe pods را اجرا کنید:

shell
kubectl describe pods

در بخش Events Podهای مشکل‌دار می‌بینید که نسخه‌ی v10 image در repository وجود ندارد.

برای برگرداندن Deployment به آخرین نسخه‌ی سالم،‏ از rollout undo استفاده کنید:

shell
kubectl rollout undo deployments/kubernetes-bootcamp

rollout undo Deployment را به آخرین وضعیت شناخته‌شده (image v2) برمی‌گرداند. به‌روزرسانی‌ها نسخه‌دارند و می‌توانید به هر وضعیت شناخته‌شده‌ی قبلی برگردید.

دوباره Podها را فهرست کنید:

shell
kubectl get pods

و image Podهای در حال اجرا را بررسی کنید:

shell
kubectl describe pods

Deployment دوباره از نسخه‌ی پایدار (v2) استفاده می‌کند؛‏ برگشت موفق بود.

توضیح تکمیلی: چرا برگشت خودکار به‌جای اصلاح دستی؟ و چرا rollout خراب کاربران را اذیت نکرد؟

هر بار که .spec.template یک Deployment عوض شود،‏ یک revision جدید در تاریخچه‌ی rollout ثبت می‌شود (kubectl rollout history deployments/kubernetes-bootcamp). هر revision با یک ReplicaSet جدا نگه داشته می‌شود،‏ پس rollout undo فقط ReplicaSet قبلی را بزرگ و ReplicaSet فعلی را کوچک می‌کند؛‏ این خودش هم یک rolling update است،‏ پس در طول برگشت هم برنامه در دسترس می‌ماند.

چرا rollout خراب v10 باعث قطعی نشد؟ چون Podهای جدید هیچ‌وقت Ready نشدند و به خاطر محدودیت maxUnavailable،‏ Deployment controller بیش از حد مجاز Podهای قدیمی سالم را حذف نکرد. rollout فقط «گیر کرد». بعد از progressDeadlineSeconds (پیش‌فرض ۶۰۰ ثانیه) هم Deployment شرط Progressing=False با دلیل ProgressDeadlineExceeded می‌گیرد؛‏ اما کوبرنتیز خودکار برنمی‌گردد و برگشت کار شما (یا ابزار CD) است.

در production معمولاً از kubectl rollout undo deployments/NAME --to-revision=N برای برگشت به revision مشخص استفاده می‌شود. همچنین پیش از هر rollout،‏ readiness probe مناسب (فصل ۳) باید تنظیم شده باشد؛‏ وگرنه کوبرنتیز نمی‌تواند بفهمد Pod جدید واقعاً سالم است و ممکن است یک rollout خراب (مثلاً برنامه‌ای که اجرا می‌شود ولی خطای 500 می‌دهد) را «موفق» گزارش کند.

حالا cluster محلی را پاک‌سازی کنید:

shell
kubectl delete deployments/kubernetes-bootcamp services/kubernetes-bootcamp
آزمایش عملی: تاریخچه‌ی rollout و برگشت به یک revision مشخص

یک Deployment جدید بسازید و چند بار imageاش را عوض کنید تا چند revision ساخته شود،‏ سپس تاریخچه را ببینید:

shell
kubectl create deployment web --image=nginx:1.25
kubectl set image deployment/web nginx=nginx:1.26
kubectl rollout history deployment/web
output (نمونه)
deployment.apps/web
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

جزئیات یک revision مشخص:

shell
kubectl rollout history deployment/web --revision=1

و برگشت مستقیم به همان revision (به‌جای «یکی قبل»):

shell
kubectl rollout undo deployment/web --to-revision=1

دقت کنید ستون CHANGE-CAUSE خالی است چون annotation kubernetes.io/change-cause تنظیم نشده. برای پر کردنش از kubectl annotate deployment/web kubernetes.io/change-cause="upgrade to 1.26" استفاده کنید (flag قدیمی --record منسوخ شده و نباید به آن تکیه کرد).

context و پیکربندی kubectl (Kubectl context and configuration)

تعیین این‌که kubectl با کدام cluster کوبرنتیز ارتباط برقرار کند و ویرایش اطلاعات پیکربندی. برای جزئیات کامل فایل config به مستند Authenticating Across Clusters with kubeconfig مراجعه کنید.

bash
kubectl config view # Show Merged kubeconfig settings.

# use multiple kubeconfig files at the same time and view merged config
KUBECONFIG=~/.kube/config:~/.kube/kubconfig2

kubectl config view

# Show merged kubeconfig settings and raw certificate data and exposed secrets
kubectl config view --raw

# get the password for the e2e user
kubectl config view -o jsonpath='{.users[?(@.name == "e2e")].user.password}'

# get the certificate for the e2e user
kubectl config view --raw -o jsonpath='{.users[?(.name == "e2e")].user.client-certificate-data}' | base64 -d

kubectl config view -o jsonpath='{.users[].name}'    # display the first user
kubectl config view -o jsonpath='{.users[*].name}'   # get a list of users
kubectl config get-contexts                          # display list of contexts
kubectl config get-contexts -o name                  # get all context names
kubectl config current-context                       # display the current-context
kubectl config use-context my-cluster-name           # set the default context to my-cluster-name

kubectl config set-cluster my-cluster-name           # set a cluster entry in the kubeconfig

# configure the URL to a proxy server to use for requests made by this client in the kubeconfig
kubectl config set-cluster my-cluster-name --proxy-url=my-proxy-url

# add a new user to your kubeconf that supports basic auth
kubectl config set-credentials kubeuser/foo.kubernetes.com --username=kubeuser --password=kubepassword

# permanently save the namespace for all subsequent kubectl commands in that context.

# set a context utilizing a specific username and namespace.

kubectl config unset users.foo                       # delete user foo

alias kx='f() { [ "$1" ] && kubectl config use-context $1 || kubectl config current-context ; } ; f'
alias kn='f() { [ "$1" ] && kubectl config set-context --current --namespace $1 || kubectl config view --minify | grep namespace | cut -d" " -f6 ; } ; f'
توضیح تکمیلی

کوتاه‌نویسی kx و kn نمونه‌ای است از تعریف alias برای کار سریع با چند cluster و namespace (محدوده‌ای برای جدا کردن نام‌ها و منابع درون یک cluster). در یک تیم Platform که مهندسان روزانه بین چندین context (مثلاً staging،‏ prod-eu،‏ prod-us) جابه‌جا می‌شوند،‏ این aliasها ریسک اجرای اشتباه دستور روی production cluster را کاهش می‌دهند؛‏ با این‌حال بهتر است prompt shell طوری تنظیم شود که context جاری همیشه در خط فرمان نمایش داده شود (مثلاً با ابزار kube-ps1،‏ خارج از مستندات رسمی).

آزمایش عملی: مدیریت چند context

روی یک cluster kind یا minikube،‏ دو namespace بسازید و context جداگانه برای هرکدام تعریف کنید:

bash
kubectl create namespace team-a
kubectl create namespace team-b

# read cluster and user names from the current context (minikube, kind-kind, ...)
CLUSTER=$(kubectl config view --minify -o jsonpath='{.contexts[0].context.cluster}')
KUSER=$(kubectl config view --minify -o jsonpath='{.contexts[0].context.user}')

kubectl config set-context team-a --cluster="$CLUSTER" --user="$KUSER" --namespace=team-a
kubectl config set-context team-b --cluster="$CLUSTER" --user="$KUSER" --namespace=team-b
kubectl config use-context team-a
kubectl config get-contexts
kubectl config view --minify -o jsonpath='{..namespace}{"\n"}'

خروجی انتظاری ستون CURRENT برای team-a علامت ‎*‎ را نشان می‌دهد و namespace فعال team-a است.

دستور kubectl apply (Kubectl apply)

apply اپلیکیشن‌ها را از طریق فایل‌هایی که resourceهای کوبرنتیز را تعریف می‌کنند مدیریت می‌کند. با اجرای kubectl apply این دستور resourceها را در cluster ایجاد و به‌روزرسانی می‌کند. این روش پیشنهادی برای مدیریت اپلیکیشن‌های کوبرنتیز در production است (مطابق Kubectl Book).

ساختن objectها (Creating objects)

مانیفست‌های کوبرنتیز می‌توانند به‌صورت YAML یا JSON تعریف شوند. پسوند فایل .yaml،‏ .yml و .json قابل استفاده است.

bash
kubectl apply -f ./my-manifest.yaml                 # create resource(s)
kubectl apply -f ./my1.yaml -f ./my2.yaml           # create from multiple files
kubectl apply -f ./dir                              # create resource(s) in all manifest files in dir
kubectl apply -f https://example.com/manifest.yaml  # create resource(s) from url (Note: this is an example domain and does not contain a valid manifest)
kubectl create deployment nginx --image=nginx       # start a single instance of nginx

# create a Job which prints "Hello World"
kubectl create job hello --image=busybox:1.28 -- echo "Hello World"

# create a CronJob that prints "Hello World" every minute
kubectl create cronjob hello --image=busybox:1.28   --schedule="*/1 * * * *" -- echo "Hello World"

kubectl explain pods                           # get the documentation for pod manifests

# Create multiple YAML objects from stdin
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: busybox-sleep
spec:
  containers:
  - name: busybox
    image: busybox:1.28
    args:
    - sleep
    - "1000000"
---
apiVersion: v1
kind: Pod
metadata:
  name: busybox-sleep-less
spec:
  containers:
  - name: busybox
    image: busybox:1.28
    args:
    - sleep
    - "1000"
EOF

# Create a secret with several keys
kubectl apply -f - <<EOF
apiVersion: v1
kind: Secret
metadata:
  name: mysecret
type: Opaque
data:
  password: $(echo -n "s33msi4" | base64 -w0)
  username: $(echo -n "jane" | base64 -w0)
EOF
توضیح تکمیلی

تفاوت kubectl create و kubectl apply: create امری (imperative) است و اگر resource از قبل وجود داشته باشد خطا می‌دهد؛‏ apply اعلانی (declarative) است: با three-way merge بین manifest جدید،‏ آخرین manifest اعمال‌شده (که در annotation به نام kubectl.kubernetes.io/last-applied-configuration ذخیره می‌شود) و state فعلی object در cluster،‏ فقط تغییرات لازم را اعمال می‌کند. مستندات apply را روش پیشنهادی برای production می‌داند،‏ چون idempotent (اجرای چندباره‌اش همان نتیجه‌ی یک بار را دارد) است و می‌توان آن را بارها در CI/CD اجرا کرد. با --server-side همین کار را API server با field management انجام می‌دهد (فصل ۸).

این بخش پرکاربردترین قسمت cheat sheet برای debug روزمره است. نکات کلیدی: --sort-by از JSONPath برای مرتب‌سازی خروجی get استفاده می‌کند؛‏ --selector (یا -l) بر پایه‌ی label filter می‌کند در حالی‌که --field-selector بر پایه‌ی فیلدهای object (مثل status.phase) فیلتر می‌کند و فقط فیلدهایی را می‌پذیرد که آن نوع resource پشتیبانی می‌کند (همه‌ی resourceها metadata.name و metadata.namespace را دارند)؛‏ --subresource امکان خواندن/نوشتن مستقیم subresource (status،‏ scale) بدون دست‌کاری کل object را می‌دهد.

آزمایش عملی: پیدا کردن Podهای مشکل‌دار با field-selector

kubectl get pods --field-selector=status.phase!=Running,status.phase!=Succeeded

patch کردن resourceها (Patching resources)

bash
# Partially update a node
kubectl patch node k8s-node-1 -p '{"spec":{"unschedulable":true}}'

# Update a container's image; spec.containers[*].name is required because it's a merge key
kubectl patch pod valid-pod -p '{"spec":{"containers":[{"name":"kubernetes-serve-hostname","image":"new image"}]}}'

# Update a container's image using a json patch with positional arrays
kubectl patch pod valid-pod --type='json' -p='[{"op": "replace", "path": "/spec/containers/0/image", "value":"new image"}]'

# Disable a deployment livenessProbe using a json patch with positional arrays
kubectl patch deployment valid-deployment  --type json   -p='[{"op": "remove", "path": "/spec/template/spec/containers/0/livenessProbe"}]'

# Add a new element to a positional array
kubectl patch sa default --type='json' -p='[{"op": "add", "path": "/secrets/1", "value": {"name": "whatever" } }]'

# Update a deployment's replica count by patching its scale subresource
kubectl patch deployment nginx-deployment --subresource='scale' --type='merge' -p '{"spec":{"replicas":2}}'
توضیح تکمیلی

سه نوع patch در کوبرنتیز وجود دارد: strategic (پیش‌فرض،‏ فقط برای typeهای built-in و آگاه از merge keyها مثل name در لیست containers)،‏ merge (RFC 7386،‏ جایگزینی ساده‌ی فیلدها/آرایه‌ها) و json (RFC 6902،‏ عملیات دقیق add/remove/replace با path). برای CRDها معمولاً باید از merge یا json استفاده کرد چون strategic merge برای آن‌ها تعریف نشده است.

هشدار

kubectl delete pod unwanted --now همان --grace-period=1 است: SIGTERM ارسال می‌شود و فقط یک ثانیه بعد SIGKILL،‏ پس process عملاً فرصت graceful shutdown و اجرای کامل preStop hook را ندارد. --force --grace-period=0 از این هم شدیدتر است: object بی‌درنگ از API server پاک می‌شود و منتظر تأیید kubelet برای توقف container نمی‌ماند. در production فقط وقتی از این‌ها استفاده کنید که Pod واقعاً stuck است (مثلاً روی Node ازکارافتاده)؛‏ وگرنه ممکن است تراکنش یا اتصال باز از دست برود.

یادداشت نویسنده: توضیح کنار --now در کد بالا («with no grace period») از مستندات است و دقیق نیست. راهنمای خود flag در kubectl v1.37 می‌گوید: same as --grace-period=1. همچنین --grace-period=0 بدون --force را kubectl خودش به ۱ تبدیل می‌کند.

قراردادهای استفاده از kubectl (kubectl Usage Conventions)

توصیه‌های استفاده‌ی مرسوم از kubectl،‏ به‌خصوص وقتی در اسکریپت‌های قابل‌استفاده‌ی مجدد (reusable scripts) به‌کار می‌رود.

استفاده از kubectl در scriptهای قابل‌استفاده‌ی مجدد (Using kubectl in Reusable Scripts)

برای خروجی پایدار در یک اسکریپت:

  • یکی از فرمت‌های خروجی machine-oriented را درخواست کنید،‏ مثل -o name،‏ -o json،‏ -o yaml،‏ -o go-template یا -o jsonpath.
  • نسخه را fully-qualify کنید. برای مثال jobs.v1.batch/myjob. این کار تضمین می‌کند kubectl از نسخه‌ی پیش‌فرض خود که ممکن است در طول زمان تغییر کند استفاده نکند.
  • به context،‏ preferences یا سایر stateهای implicit تکیه نکنید.

subresourceها (Subresources)

  • می‌توانید از آرگومان --subresource برای دستورات فرعی kubectl مثل get،‏ patch،‏ edit،‏ apply و replace استفاده کنید تا subresourceها را برای تمام resourceهایی که از آن‌ها پشتیبانی می‌کنند fetch و update کنید. در کوبرنتیز نسخه‌ی ۱٫۳۷،‏ فقط subresourceهای status،‏ scale و resize پشتیبانی می‌شوند.
    • برای kubectl edit،‏ subresource scale پشتیبانی نمی‌شود. اگر --subresource را با kubectl edit استفاده کنید و scale را به‌عنوان subresource مشخص کنید،‏ دستور با خطا متوقف می‌شود.
  • قرارداد API در برابر یک subresource دقیقاً همانند یک resource کامل است. هنگام به‌روزرسانی subresource status به یک مقدار جدید،‏ در نظر داشته باشید که این subresource ممکن است به‌طور بالقوه توسط یک controller به مقدار دیگری reconcile شود.

بهترین شیوه‌ها (Best Practices)

دستور kubectl run

برای این‌که kubectl run با اصل infrastructure as code سازگار باشد:

  • image را با یک تگ version-specific تگ بزنید و آن تگ را به نسخه‌ی جدید منتقل نکنید. برای مثال از :v1234،‏ v1.2.3،‏ r03062016-1-4 استفاده کنید،‏ نه :latest (برای اطلاعات بیشتر Kubernetes Configuration Good Practices را ببینید).
  • اسکریپت را برای یک image که به‌شدت پارامتری‌سازی شده check in کنید.
  • برای ویژگی‌هایی که لازم‌اند اما از طریق flagهای kubectl run قابل بیان نیستند،‏ از فایل‌های پیکربندی که در source control ذخیره شده‌اند استفاده کنید.

می‌توانید از flag --dry-run=client برای پیش‌نمایش objectی که به cluster شما ارسال می‌شود،‏ بدون ارسال واقعی آن،‏ استفاده کنید.

دستور kubectl proxy
هشدار

مرور endpointهای غیرقابل‌اعتماد Pod یا Service از طریق kubectl proxy خطرناک است،‏ چون محتوایی که از راه proxy ارائه می‌شود،‏ به‌طور ضمنی با credential همان proxy به Kubernetes API دسترسی دارد (صفحه و API هر دو روی یک آدرس localhost هستند). احتیاط کنید و وقتی credential دارای privilege بالا دارید،‏ endpointهای غیرقابل‌اعتماد را باز نکنید.

برای کاهش ریسک:

  • از مرور Podها یا Serviceهای غیرقابل‌اعتماد از طریق kubectl proxy خودداری کنید.
  • از --reject-methods='POST,PUT,PATCH,DELETE' استفاده کنید تا proxy را به عملیات read-only محدود کنید،‏ وقتی فقط نیاز به مشاهده‌ی resourceها دارید.
  • از --reject-paths برای محدودکردن این‌که کدام مسیرهای API توسط proxy expose می‌شوند استفاده کنید.
  • مگر در صورت ضرورت،‏ kubectl proxy را با credential cluster-admin اجرا نکنید.
دستور kubectl apply

می‌توانید از kubectl apply برای ایجاد یا به‌روزرسانی resourceها استفاده کنید. برای اطلاعات بیشتر درباره‌ی استفاده از kubectl apply برای به‌روزرسانی resourceها،‏ Kubectl Book را ببینید.

پشتیبانی از JSONPath (JSONPath Support)

ابزار kubectl از templateهای JSONPath به‌عنوان یک output format پشتیبانی می‌کند. یک JSONPath template از عبارات JSONPath محصور در آکولاد ‎{‎ و ‎}‎ تشکیل شده است. kubectl از عبارات JSONPath برای فیلترکردن فیلدهای مشخص در JSON object و قالب‌بندی خروجی استفاده می‌کند. علاوه‌بر syntax اصلی template JSONPath،‏ توابع و syntax زیر نیز معتبرند:

  1. از double quote برای نقل‌قول متن داخل عبارات JSONPath استفاده کنید.
  2. از عملگرهای range،‏ end برای پیمایش (iterate) لیست‌ها استفاده کنید.
  3. از اندیس‌های منفی slice برای حرکت رو به عقب در یک لیست استفاده کنید. اندیس‌های منفی دور لیست «wrap around» نمی‌شوند و تا زمانی معتبرند که (-index + listLength) ≥ 0.
نکته
  • عملگر ‎$‎ اختیاری است چون عبارت به‌طور پیش‌فرض همیشه از root object آغاز می‌شود.
  • object نتیجه با تابع String() آن چاپ می‌شود.

kubectl get pods -o=jsonpath='{.items[0]}'
kubectl get pods -o=jsonpath='{.items[0].metadata.name}'
kubectl get pods -o=jsonpath="{.items[*]['metadata.name', 'status.capacity']}"
kubectl get pods -o=jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.startTime}{"\n"}{end}'
kubectl get pods -o=jsonpath='{.items[0].metadata.labels.kubernetes\.io/hostname}'

یا،‏ با یک "my_pod" و "my_namespace" (این نام‌ها را متناسب با محیط خودتان تنظیم کنید):

shell
kubectl get pod/my_pod -n my_namespace -o=jsonpath='{@}'
kubectl get pod/my_pod -n my_namespace -o=jsonpath='{.metadata.name}'
kubectl get pod/my_pod -n my_namespace -o=jsonpath='{.status}'
نکته

روی Windows،‏ هر template JSONPath که شامل space باشد باید با double quote محصور شود (نه single quote مانند مثال‌های bash بالا). این به‌نوبه‌ی خود یعنی باید از single quote یا escape شده‌ی double quote دور literalها در template استفاده کنید. برای مثال:

cmd
kubectl get pods -o=jsonpath="{range .items[*]}{.metadata.name}{'\t'}{.status.startTime}{'\n'}{end}"
kubectl get pods -o=jsonpath="{range .items[*]}{.metadata.name}{\"\t\"}{.status.startTime}{\"\n\"}{end}"

regular expression در JSONPath (Regular expressions in JSONPath)

عبارات باقاعده (regular expressions) در JSONPath پشتیبانی نمی‌شوند. اگر می‌خواهید با استفاده از regular expressions تطبیق دهید،‏ می‌توانید از ابزاری مثل jq استفاده کنید.

shell
# kubectl does not support regular expressions for JSONpath output
# The following command does not work
kubectl get pods -o jsonpath='{.items[?(@.metadata.name=~/^test$/)].metadata.name}'

# The following command achieves the desired result
kubectl get pods -o json | jq -r '.items[] | select(.metadata.name | test("test-")).metadata.name'
آزمایش عملی: چند کوئری JSONPath واقعی روی یک Deployment

روی یک namespace با چند Deployment و Pod،‏ این کوئری‌ها را امتحان کنید:

bash
# every Pod name with its IP, one per line
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}'

# name and first image of Pods whose first container has restarted
kubectl get pods -o jsonpath='{range .items[?(@.status.containerStatuses[0].restartCount>0)]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'

# CPU request of the first container of every Pod in the current namespace
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"="}{.spec.containers[0].resources.requests.cpu}{"\n"}{end}'

خروجی انتظاری برای هر سه دستور یک ستون یا جدول ساده‌ی متنی است،‏ مناسب برای pipe کردن به awk/sort/column -t در یک اسکریپت health-check یا capacity-report روزانه.

objectهای اصلی workload (Pods and Controllers)

اصطلاحتوضیح
Podکوچک‌ترین و ساده‌ترین object کوبرنتیز؛‏ نماینده‌ی مجموعه‌ای از containerهای در حال اجرا روی cluster شماست. معمولاً یک container اصلی و به‌صورت اختیاری sidecar containerها را اجرا می‌کند و اغلب توسط یک Deployment مدیریت می‌شود (فصل ۳).
Containerیک image سبک و قابل‌حمل که نرم‌افزار و تمام وابستگی‌های آن را در بر دارد. Containerها اپلیکیشن را از زیرساخت host جدا می‌کنند تا deploy کردن در محیط‌های cloud یا OS مختلف ساده‌تر شود (فصل ۲).
App Containercontainerهایی در یک Pod که پس از تکمیل هر init container شروع می‌شوند. اگر Pod هیچ init containerی نداشته باشد،‏ همه‌ی containerهای آن app container محسوب می‌شوند.
Init Containerیک یا چند container راه‌اندازی که باید پیش از اجرای هر app container به‌طور کامل تمام شوند. init containerها به‌ترتیب اجرا می‌شوند و برخلاف sidecar container پس از راه‌اندازی Pod در حال اجرا باقی نمی‌مانند (فصل ۳).
Sidecar Containercontainerهایی که معمولاً پیش از app containerها شروع می‌شوند و یک سرویس محلی به container اصلی Pod ارائه می‌دهند؛‏ برخلاف init container،‏ پس از راه‌اندازی Pod نیز در حال اجرا باقی می‌مانند (فصل ۳).
Ephemeral Containerنوعی container که می‌توانید به‌طور موقت درون یک Pod در حال اجرا اضافه کنید،‏ عمدتاً برای debug کردن Pod دارای مشکل. هیچ تضمین scheduling یا resource ندارد و توسط static pod پشتیبانی نمی‌شود (فصل ۱۱).
Static Podیک Pod که مستقیماً توسط kubelet روی یک Node مشخص مدیریت می‌شود،‏ بدون این‌که API server آن را مشاهده کند. Static Podها از ephemeral container پشتیبانی نمی‌کنند.
Mirror Podیک Pod object که kubelet برای نمایش یک static pod در API server می‌سازد؛‏ این object قابل کنترل از سمت API server نیست (مثلاً حذف mirror pod،‏ kubelet را از اجرای آن باز نمی‌دارد).
PodTemplateیک API object که template برای ساخت Podها را تعریف می‌کند. PodTemplate API درون تعریف API اشیاء workload management مانند Deployment یا StatefulSet نیز جای گرفته است.
Pod Lifecycleتوالی حالت‌هایی که یک Pod در طول عمر خود طی می‌کند. پنج فاز ممکن وجود دارد: Pending،‏ Running،‏ Succeeded،‏ Failed و Unknown،‏ که در فیلد status.phase خلاصه می‌شود (فصل ۳).
Pod Priorityاهمیت یک Pod نسبت به سایر Podها را نشان می‌دهد و امکان تنظیم اولویت scheduling بالاتر یا پایین‌تر نسبت به سایر Podها را می‌دهد — ویژگی مهم برای workload clusterهای production (فصل ۹).
Controllercontrol loopهایی که وضعیت cluster شما را رصد می‌کنند و سپس تغییرات لازم را اعمال یا درخواست می‌کنند تا current state را به desired state نزدیک‌تر کنند. controllerها از طریق apiserver وضعیت مشترک cluster را رصد می‌کنند و بسیاری از آن‌ها درون kube-controller-manager اجرا می‌شوند.
Replicaیک کپی از یک Pod یا مجموعه‌ای از Podها که برای تأمین high availability،‏ scalability و fault tolerance،‏ چند instance یکسان از یک Pod نگه‌داری می‌شوند.
ReplicaSetتلاش می‌کند مجموعه‌ای از replica Podها را در هر لحظه در حال اجرا نگه دارد. objectهای workload مانند Deployment از ReplicaSet برای تضمین تعداد پیکربندی‌شده‌ی Pod استفاده می‌کنند (فصل ۴).
ReplicationControllerیک API object منسوخ‌شده که یک اپلیکیشن replicated را مدیریت می‌کند. جایگزین آن Deployment است که مشابه اما با قابلیت‌های بیشتر عمل می‌کند.
Deploymentیک API object که یک اپلیکیشن replicated،‏ معمولاً با اجرای Podهای بدون state محلی،‏ مدیریت می‌کند. برای workloadهایی که نیاز به state محلی دارند،‏ StatefulSet مناسب‌تر است (فصل ۴).
StatefulSetdeployment و scaling مجموعه‌ای از Podها را مدیریت می‌کند و درباره‌ی ترتیب و یکتایی این Podها تضمین ارائه می‌دهد؛‏ هر Pod شناسه‌ی پایداری دارد که در طول rescheduling حفظ می‌شود (فصل ۴).
DaemonSetتضمین می‌کند یک کپی از یک Pod روی مجموعه‌ای از Nodeهای cluster در حال اجراست؛‏ برای deploy کردن daemonهای سیستمی مثل log collector یا monitoring agent که باید روی هر Node اجرا شوند به‌کار می‌رود (فصل ۴).
Jobیک وظیفه‌ی محدود یا batch که تا پایان اجرا می‌شود. Job یک یا چند Pod object می‌سازد و تضمین می‌کند تعداد مشخصی از آن‌ها با موفقیت پایان می‌یابند (فصل ۴).
CronJobیک Job را طبق زمان‌بندی دوره‌ای مدیریت می‌کند؛‏ مشابه یک خط در فایل crontab،‏ با فرمت cron زمان‌بندی می‌شود (فصل ۴).
Workloadاپلیکیشنی که روی کوبرنتیز اجرا می‌شود. objectهای اصلی که انواع یا بخش‌های مختلف workload را نشان می‌دهند شامل DaemonSet،‏ Deployment،‏ Job،‏ ReplicaSet و StatefulSet هستند.
PodGroupیک runtime object که مجموعه‌ای از Podها را نشان می‌دهد که به‌عنوان یک واحد با هم schedule می‌شوند؛‏ در حالی‌که Workload API قالب‌های policy مربوط به scheduling را تعریف می‌کند،‏ PodGroup همتای runtime آن است که هم policy و هم وضعیت scheduling را حمل می‌کند.
Conditionیک فیلد در status یک resource کوبرنتیز که current state آن resource را توصیف می‌کند. هر condition دارای type،‏ status (True/False/Unknown) و فیلدهای اختیاری reason/message است؛‏ نمونه: Ready،‏ ContainersReady،‏ PodScheduled.
Eventیک object کوبرنتیز که تغییرات state یا رخدادهای قابل‌توجه در cluster را توصیف می‌کند. Eventها مدت نگه‌داری محدودی دارند و باید به‌عنوان داده‌های اطلاع‌رسانی best-effort در نظر گرفته شوند،‏ نه رکورد دقیق و قابل‌اعتماد (فصل ۱۱).
Probeیک بررسی که kubelet به‌صورت دوره‌ای روی containerهای در حال اجرا در یک Pod انجام می‌دهد و state و سلامت آن container را مشخص و به lifecycle آن اطلاع‌رسانی می‌کند (فصل ۳).
Container Lifecycle Hooksرویدادهایی در lifecycle مدیریت container را در معرض دید قرار می‌دهند و به کاربر اجازه می‌دهند در زمان وقوع آن‌ها کد اجرا کند. دو hook وجود دارد: PostStart که بلافاصله پس از ساخته‌شدن container اجرا می‌شود،‏ و PreStop که blocking بوده و بلافاصله پیش از خاتمه‌ی container فراخوانی می‌شود.
Container Environment Variablesجفت‌های name=value که اطلاعات مفیدی درباره‌ی containerهای در حال اجرا در یک Pod ارائه می‌کنند؛‏ شامل جزئیات filesystem،‏ اطلاعات درباره‌ی خود container،‏ و سایر resourceهای cluster مثل service endpoint.
HostAliasesیک نگاشت بین آدرس IP و hostname که در صورت مشخص‌شدن به فایل hosts یک Pod تزریق می‌شود؛‏ فقط برای Podهایی معتبر است که hostNetwork ندارند.
Applicationsلایه‌ای که اپلیکیشن‌های containerized مختلف در آن اجرا می‌شوند.
Downward APIمکانیزم کوبرنتیز برای در معرض دید قرار دادن مقادیر فیلدهای Pod و container به کدی که در یک container اجرا می‌شود،‏ بدون نیاز به coupling مستقیم کد container با API کوبرنتیز. از طریق environment variables یا یک volume از نوع downwardAPI در دسترس قرار می‌گیرد.

control plane و اجزای Node (Control Plane & Node Components)

اصطلاحتوضیح
Clusterمجموعه‌ای از ماشین‌های worker به نام Node که اپلیکیشن‌های containerized را اجرا می‌کنند؛‏ هر cluster حداقل یک worker node دارد. control plane،‏ Nodeها و Podهای داخل cluster را مدیریت می‌کند (فصل ۱۲).
Nodeیک ماشین worker در کوبرنتیز؛‏ می‌تواند VM یا ماشین فیزیکی باشد. daemonهای محلی لازم برای اجرای Pod را دارد و توسط control plane مدیریت می‌شود؛‏ این daemonها شامل kubelet،‏ kube-proxy و container runtime هستند (فصل ۱۲).
Control Planeلایه‌ی orchestration container که API و رابط‌ها برای تعریف،‏ deploy و مدیریت lifecycle containerها را در معرض دید قرار می‌دهد. این لایه از اجزای گوناگونی مانند etcd،‏ API Server،‏ Scheduler،‏ Controller Manager و Cloud Controller Manager تشکیل شده است (فصل ۱۲).
API server (kube-apiserver)یک کامپوننت control plane که Kubernetes API را expose می‌کند و front-end آن است. kube-apiserver برای مقیاس افقی طراحی شده و می‌توان چند instance از آن اجرا و ترافیک را بین آن‌ها توزیع کرد (فصل ۱۲).
kube-controller-managerکامپوننت control plane که processهای controller را اجرا می‌کند. منطقاً هر controller یک process جداست،‏ اما برای کاهش پیچیدگی همه در یک باینری و یک process اجرا می‌شوند (فصل ۱۲).
kube-proxyیک network proxy که روی هر Node اجرا می‌شود و بخشی از مفهوم Service کوبرنتیز را پیاده‌سازی می‌کند. قوانین شبکه‌ای روی Nodeها نگه‌داری می‌کند که ارتباط شبکه به Podها از داخل یا خارج cluster را ممکن می‌سازد (فصل ۵).
kube-schedulerکامپوننت control plane که Podهای تازه‌ساخته‌شده‌ی بدون Node اختصاص‌یافته را رصد می‌کند و یک Node برای اجرای آن‌ها انتخاب می‌کند. عوامل تصمیم scheduling شامل نیازهای resource،‏ محدودیت‌های hardware/software/policy،‏ affinity و anti-affinity،‏ data locality و deadlineها هستند (فصل ۹).
kubeletعاملی که روی هر Node اجرا می‌شود و اطمینان می‌دهد containerها در یک Pod در حال اجرا هستند. مجموعه‌ای از PodSpec را از مکانیزم‌های مختلف دریافت می‌کند و مطمئن می‌شود containerهای توصیف‌شده در آن‌ها سالم و در حال اجرا هستند (فصل ۱۲).
Cloud Controller Managerکامپوننت control plane که منطق کنترل خاص هر cloud را embed می‌کند و cluster شما را به API ارائه‌دهنده‌ی cloud متصل می‌کند و اجزایی که با آن platform تعامل دارند را از اجزایی که فقط با cluster شما کار می‌کنند جدا می‌کند.
etcdیک key-value store سازگار (consistent) و بسیار در‌دسترس که به‌عنوان backing store کوبرنتیز برای تمام داده‌های cluster استفاده می‌شود. اگر cluster شما از etcd استفاده می‌کند،‏ حتماً یک برنامه‌ی backup برای آن داشته باشید (فصل ۱۲).
Masterاصطلاح قدیمی که به‌عنوان مترادف Nodeهای میزبان control plane استفاده می‌شد. برخی ابزارهای provisioning مانند kubeadm و سرویس‌های managed هنوز از این اصطلاح برای label زدن به Nodeها با kubernetes.io/role استفاده می‌کنند.
Data Planeلایه‌ای که capacity مثل CPU،‏ memory،‏ شبکه و storage را فراهم می‌کند تا containerها بتوانند اجرا شوند و به شبکه متصل شوند.
Proxyیک server که به‌عنوان واسطه برای یک سرویس راه‌دور عمل می‌کند؛‏ client با proxy تعامل می‌کند،‏ proxy داده‌ی client را به سرور واقعی کپی می‌کند و پاسخ سرور واقعی را به client می‌فرستد. kube-proxy نمونه‌ای از این الگو در کوبرنتیز است.
Mixed Version Proxy (MVP)قابلیتی که به یک kube-apiserver اجازه می‌دهد یک resource request را به یک API server همتای دیگر proxy کند. وقتی cluster چندین API server با نسخه‌های متفاوت کوبرنتیز اجرا می‌کند،‏ این ویژگی تضمین می‌کند به درخواست‌ها API server درست پاسخ دهد. متن واژه‌نامه‌ی رسمی می‌گوید پیش‌فرض غیرفعال است و با feature gate به نام UnknownVersionInteroperabilityProxy فعال می‌شود. یادداشت نویسنده: بر اساس فایل همین gate،‏ از v1.36 در مرحله‌ی beta و پیش‌فرض فعال است؛‏ این جمله‌ی واژه‌نامه قدیمی است.
Aggregation Layerبه شما اجازه می‌دهد APIهای اضافی به سبک کوبرنتیز را در cluster خود نصب کنید. پس از پیکربندی API Server برای پشتیبانی از APIهای اضافی،‏ می‌توانید object از نوع APIService اضافه کنید تا یک URL path در Kubernetes API را «claim» کنید.
Watchیک فعل که برای ردیابی تغییرات یک object در کوبرنتیز به‌صورت stream استفاده می‌شود؛‏ برای تشخیص کارآمد تغییرات به‌کار می‌رود،‏ مثلاً یک controller که باید بداند چه زمانی یک ConfigMap تغییر کرده،‏ به‌جای polling از watch استفاده می‌کند.
Cluster Infrastructureلایه‌ی زیرساختی که VMها،‏ شبکه،‏ security group و موارد مشابه را فراهم و نگه‌داری می‌کند.
Cluster Operationsکارهای مرتبط با مدیریت یک cluster کوبرنتیز: مدیریت عملیات روزمره و هماهنگ‌کردن upgradeها؛‏ شامل deploy کردن Node جدید برای scale کردن cluster،‏ اجرای upgrade نرم‌افزار،‏ اعمال کنترل‌های امنیتی،‏ افزودن/حذف storage،‏ پیکربندی شبکه‌ی cluster،‏ مدیریت observability سراسری cluster و واکنش به رویدادها.
Shuffle-shardingیک تکنیک برای اختصاص درخواست‌ها به صف‌ها که ایزوله‌سازی بهتری نسبت به هش‌کردن ساده به‌پیمانه‌ی تعداد صف‌ها ارائه می‌دهد؛‏ استفاده‌شده در kube-apiserver برای جلوگیری از این‌که یک flow درخواست پرحجم،‏ flowهای کم‌حجم را از میدان به‌در کند.

Kubernetes API و metadata (API & Metadata Objects)

اصطلاحتوضیح
Kubernetes APIاپلیکیشنی که عملکرد کوبرنتیز را از طریق یک رابط RESTful ارائه می‌کند و state cluster را ذخیره می‌کند. resourceها و «رکوردهای intent» همگی به‌عنوان API object ذخیره و از طریق فراخوانی‌های RESTful تغییر داده می‌شوند؛‏ می‌توان مستقیم یا از طریق ابزاری مثل kubectl با آن تعامل کرد (فصل ۸).
API Groupمجموعه‌ای از مسیرهای مرتبط در Kubernetes API. می‌توانید هر API group را با تغییر پیکربندی API server فعال یا غیرفعال کنید. API group مشخص‌شده در یک REST path و در فیلد apiVersion یک object سریالایز‌شده قرار دارد (فصل ۸).
API resourceموجودیتی در type system کوبرنتیز که با یک endpoint در Kubernetes API مطابقت دارد. معمولاً یک resource نماینده‌ی یک object است؛‏ برخی resourceها نماینده‌ی یک عملیات روی objectهای دیگرند،‏ مثل یک permission check.
Group Version Resource (GVR)روشی برای نمایش یکتای APIهای مشخص کوبرنتیز؛‏ GVR شامل API group،‏ نسخه‌ی API و resource (نام kind آن‌گونه که در URI ظاهر می‌شود) است و امکان تمایز و دسترسی پایدار به objectها را حتی با تغییر APIها فراهم می‌کند.
Objectیک موجودیت در سیستم کوبرنتیز؛‏ یک API resource که Kubernetes API از آن برای نمایش state cluster شما استفاده می‌کند. یک object کوبرنتیز معمولاً یک «رکورد intent» است — پس از ساختن آن،‏ control plane مدام تلاش می‌کند وجود واقعی آن‌چه نماینده‌اش است را تضمین کند (فصل ۸).
Manifestمشخصات یک API object کوبرنتیز به فرمت JSON یا YAML. یک manifest،‏ desired state آن object را که کوبرنتیز هنگام apply کردن آن نگه می‌دارد مشخص می‌کند؛‏ برای فرمت YAML،‏ هر فایل می‌تواند شامل چند manifest باشد.
Specتعریف می‌کند هر object،‏ مثل Pod یا Service،‏ چگونه باید پیکربندی شود و desired state آن چیست. تقریباً هر object کوبرنتیز شامل دو فیلد تودرتو است که پیکربندی object را کنترل می‌کنند: spec و status.
Nameیک رشته که توسط client ارائه می‌شود و به یک object در یک resource URL اشاره می‌کند،‏ مثل /api/v1/pods/some-name. فقط یک object از یک kind خاص می‌تواند در یک لحظه نام مشخصی داشته باشد؛‏ ولی پس از حذف object می‌توانید object جدیدی با همان نام بسازید.
UIDرشته‌ای که به‌طور سیستمی توسط کوبرنتیز تولید می‌شود تا objectها را به‌طور یکتا شناسایی کند. هر object در کل طول عمر یک cluster کوبرنتیز،‏ یک UID متمایز دارد که برای تمایز نمونه‌های تاریخی موجودیت‌های مشابه به‌کار می‌رود.
Namespaceیک انتزاع که کوبرنتیز برای پشتیبانی از ایزوله‌سازی گروه‌های API resource درون یک cluster واحد استفاده می‌کند. نام‌ها فقط درون یک namespace باید یکتا باشند،‏ نه در سراسر namespaceها؛‏ scoping بر پایه‌ی namespace فقط برای resourceهای namespaced (مثل Pod،‏ Deployment،‏ Service) اعمال می‌شود،‏ نه resourceهای cluster-wide مثل StorageClass،‏ Node یا PersistentVolume (فصل ۸).
Labelویژگی‌های شناساننده‌ی معنادار و مرتبط با کاربر را به objectها تگ می‌زند. labelها جفت‌های key/value متصل به objectهایی مثل Pod هستند و برای سازمان‌دهی و انتخاب زیرمجموعه‌ای از objectها به‌کار می‌روند (فصل ۸).
Annotationیک جفت key-value که برای الصاق متادیتای غیرشناساننده‌ی دلخواه به objectها استفاده می‌شود. متادیتای درون یک annotation می‌تواند کوچک یا بزرگ،‏ ساختاریافته یا غیرساختاریافته باشد و شامل کاراکترهایی باشد که در label مجاز نیستند (فصل ۸).
Selectorبه کاربران اجازه می‌دهد فهرستی از API resourceها را بر پایه‌ی label فیلتر کنند. selectorها هنگام کوئری‌گرفتن از لیست‌های resource برای فیلترکردن آن‌ها بر پایه‌ی label اعمال می‌شوند (فصل ۸؛‏ و --selector و --field-selector در همین پیوست).
Finalizerکلیدهای namespaced که به کوبرنتیز می‌گویند تا برآورده‌شدن شرایط خاص صبر کند پیش از این‌که به‌طور کامل resourceهای علامت‌گذاری‌شده برای حذف را حذف کند. finalizerها به controllerها هشدار می‌دهند تا resourceهایی که object حذف‌شده مالک آن‌ها بود را پاک‌سازی کنند؛‏ تا زمانی‌که metadata.finalizers خالی نشود،‏ کوبرنتیز حذف را کامل نمی‌داند (فصل ۸).
Garbage Collectionاصطلاحی جمعی برای مکانیزم‌های گوناگونی که کوبرنتیز برای پاک‌سازی resourceهای cluster استفاده می‌کند،‏ مثل containerها و imageهای بلااستفاده،‏ Podهای failed،‏ objectهای متعلق به resource هدف،‏ Jobهای تکمیل‌شده و resourceهای منقضی یا failed.
Feature gateراهی برای کنترل این‌که یک ویژگی خاص کوبرنتیز فعال است یا نه. feature gateها مجموعه‌ای از کلیدها (رشته‌های opaque) هستند که با flag خط فرمان --feature-gates در هر کامپوننت کوبرنتیز روشن یا خاموش می‌شوند.
Durationیک مقدار رشته‌ای نماینده‌ی یک بازه‌ی زمانی،‏ بر پایه‌ی نوع time.Duration زبان Go. مقدار به‌صورت سری از اعداد صحیح غیرمنفی به‌همراه پسوند واحد زمان بیان می‌شود (ns،‏ µs/us،‏ ms،‏ s،‏ m،‏ h)؛‏ برای مثال 1m30s یعنی یک دقیقه و سی ثانیه.
Quantityنمایش اعداد کوچک یا بزرگ به‌صورت whole-number با پسوندهای SI. اعداد اعشاری با واحد میلی نمایش داده می‌شوند،‏ در حالی‌که اعداد بزرگ با واحد کیلو،‏ مگا یا گیگا نمایش داده می‌شوند؛‏ برای مثال ‎1.5‎ به‌صورت 1500m و ‎1000000‎ به‌صورت 1M است. واحدهای باینری هم پشتیبانی می‌شوند: Ki،‏ Mi،‏ Gi،‏ Ti،‏ Pi،‏ Ei (فصل ۸).

شبکه (Networking)

اصطلاحتوضیح
Serviceروشی برای در معرض دید قرار دادن یک اپلیکیشن شبکه‌ای که به‌صورت یک یا چند Pod در cluster شما در حال اجراست. مجموعه‌ی Podهای هدف یک Service معمولاً توسط یک selector تعیین می‌شود؛‏ Service تضمین می‌کند ترافیک شبکه به مجموعه‌ی فعلی Podهای workload هدایت شود (فصل ۵).
EndpointSliceآدرس‌های IP endpointهای backend را ردیابی می‌کند. EndpointSliceها معمولاً با یک Service مرتبط‌اند و backend endpointها معمولاً Podها را نمایش می‌دهند. control plane معمولاً EndpointSliceها را به‌طور خودکار مدیریت می‌کند اما برای Serviceهای بدون selector می‌توان آن‌ها را دستی هم تعریف کرد (فصل ۵).
Endpointsیک API منسوخ‌شده که مجموعه‌ی تمام endpointهای یک Service را نمایش می‌دهد. از نسخه‌ی ۱٫۲۱،‏ کوبرنتیز به‌جای Endpoints از EndpointSlice استفاده می‌کند؛‏ API اصلی Endpoints به‌دلیل نگرانی‌های مقیاس‌پذیری منسوخ شد. رسماً از v1.33 منسوخ (deprecated) است و استفاده از آن warning می‌دهد (فصل ۵).
Ingressیک API object که دسترسی خارجی به Serviceهای درون یک cluster،‏ معمولاً بر پایه‌ی HTTP،‏ را مدیریت می‌کند. Ingress می‌تواند load balancing،‏ SSL termination و name-based virtual hosting فراهم کند (فصل ۵).
Gateway APIخانواده‌ای از API kindها برای مدل‌سازی شبکه‌ی سرویس در کوبرنتیز؛‏ خانواده‌ای قابل‌گسترش،‏ role-oriented و protocol-aware از API kindها ارائه می‌دهد (فصل ۵).
Network Policyمشخصاتی از این‌که گروه‌هایی از Podها چگونه مجاز به برقراری ارتباط با یکدیگر و با سایر endpointهای شبکه هستند. NetworkPolicy با استفاده از labelها Podها را انتخاب و قوانینی درباره‌ی ترافیک مجاز تعریف می‌کند؛‏ پیاده‌سازی آن به یک network plugin پشتیبانی‌شده وابسته است — ساختن NetworkPolicy بدون controllerی که آن را پیاده‌سازی کند،‏ اثری ندارد (فصل ۵).
CIDRنمادی برای توصیف بلوک‌های آدرس IP که در پیکربندی‌های شبکه فراوان استفاده می‌شود (Classless Inter-Domain Routing). در کوبرنتیز،‏ هر Node یک محدوده‌ی آدرس IP از طریق آدرس شروع و subnet mask با استفاده از CIDR دریافت می‌کند تا بتواند به هر Pod یک IP یکتا اختصاص دهد.
Container network interface (CNI)پلاگین‌های CNI نوعی network plugin هستند که با مشخصات appc/CNI مطابقت دارند (فصل ۵).

ذخیره‌سازی (Storage)

اصطلاحتوضیح
Volumeیک دایرکتوری حاوی داده که برای containerهای یک Pod قابل‌دسترسی است. یک Volume کوبرنتیز به اندازه‌ی طول عمر Pod دربرگیرنده‌اش زنده می‌ماند؛‏ بنابراین از هر container که درون آن Pod اجرا می‌شود بیشتر عمر می‌کند و داده‌ی آن در طول restart containerها حفظ می‌شود (فصل ۷).
Persistent Volume (PV)یک API object که نماینده‌ی یک قطعه storage در cluster است؛‏ نمایشی از یک resource storage عمومی و pluggable که می‌تواند فراتر از lifecycle هر Pod منفرد باقی بماند. PVها در سناریوهایی که storage از پیش می‌تواند ساخته شود (provisioning استاتیک) مستقیماً استفاده می‌شوند؛‏ برای سناریوهایی که storage on-demand لازم دارند (provisioning پویا)،‏ به‌جای آن از PersistentVolumeClaim استفاده می‌شود (فصل ۷).
Persistent Volume Claim (PVC)منابع storage تعریف‌شده در یک PersistentVolume را claim می‌کند تا آن storage به‌صورت یک volume در یک container mount شود. مقدار storage،‏ نحوه‌ی دسترسی (read-only،‏ read-write و/یا exclusive) و نحوه‌ی بازیابی آن (retained،‏ recycled یا deleted) را مشخص می‌کند (فصل ۷).
Storage Classراهی برای administratorها فراهم می‌کند تا انواع مختلف storage در دسترس را توصیف کنند. StorageClassها می‌توانند به سطوح QoS،‏ سیاست‌های backup یا سیاست‌های دلخواه دیگر نگاشت شوند؛‏ هر StorageClass شامل فیلدهای provisioner،‏ parameters و reclaimPolicy است که هنگام provisioning پویای یک PersistentVolume از آن کلاس استفاده می‌شوند (فصل ۷).
Dynamic Volume Provisioningامکان درخواست ایجاد خودکار storage Volume را برای کاربران فراهم می‌کند و نیاز به provisioning پیشینی storage توسط administratorهای cluster را حذف می‌کند. بر پایه‌ی API object،‏ StorageClass است که به یک Volume Plugin برای ساخت Volume و مجموعه پارامترهای مربوطه اشاره می‌کند (فصل ۷).
Container Storage Interface (CSI)یک رابط استاندارد برای در معرض دید قرار دادن سیستم‌های storage به containerها تعریف می‌کند. CSI به vendorها اجازه می‌دهد پلاگین‌های storage سفارشی برای کوبرنتیز بسازند بدون این‌که آن‌ها را به مخزن کوبرنتیز اضافه کنند (out-of-tree). پس از deploy کردن یک CSI driver در cluster،‏ می‌توانید یک StorageClass بسازید که از آن driver استفاده کند (فصل ۷).
FlexVolumeیک رابط منسوخ‌شده برای ساختن پلاگین‌های volume خارج از درخت (out-of-tree).‏ CSI رابط جدیدتری است که چند مشکل FlexVolume را برطرف می‌کند؛‏ استفاده از FlexVolume نیازمند نصب driver و وابستگی‌های آن روی ماشین‌های host با دسترسی root است.
Volume Pluginیکپارچه‌سازی storage درون یک Pod را ممکن می‌کند و به شما اجازه می‌دهد volumeهای storage را attach و mount کنید. Volume Pluginها می‌توانند in-tree (بخشی از مخزن کد کوبرنتیز و پیرو چرخه‌ی release آن) یا out-of-tree (توسعه‌یافته به‌صورت مستقل) باشند.
ConfigMapیک API object که برای ذخیره‌ی داده‌ی غیرمحرمانه به‌صورت جفت key-value استفاده می‌شود. Podها می‌توانند ConfigMapها را به‌صورت environment variable،‏ آرگومان خط فرمان یا فایل پیکربندی در یک volume مصرف کنند؛‏ ConfigMap پیکربندی وابسته‌به‌محیط را از image containerها جدا می‌کند تا اپلیکیشن‌های شما قابل‌حمل‌تر باشند (فصل ۶).

امنیت (Security)

اصطلاحتوضیح
Secretاطلاعات حساس مثل رمز عبور،‏ token OAuth و کلید SSH را ذخیره می‌کند. Secretها کنترل بیشتری روی چگونگی استفاده از اطلاعات حساس می‌دهند و ریسک افشای تصادفی را کاهش می‌دهند. مقادیر Secret به‌صورت رشته‌ی base64 کدگذاری می‌شوند و به‌طور پیش‌فرض بدون رمزگذاری ذخیره می‌شوند،‏ اما می‌توانند برای encryption at rest پیکربندی شوند. Secret برای داده‌ی محرمانه و ConfigMap برای داده‌ی غیرمحرمانه طراحی شده‌اند (فصل ۶،‏ فصل ۱۴).
Security Contextفیلد securityContext تنظیمات privilege و access control را برای یک Pod یا container تعریف می‌کند: کاربری که process با آن اجرا می‌شود،‏ گروهی که با آن اجرا می‌شود،‏ و تنظیمات privilege؛‏ هم‌چنین امکان پیکربندی سیاست‌های امنیتی مانند SELinux،‏ AppArmor یا seccomp را می‌دهد. PodSpec.securityContext روی تمام containerهای یک Pod اعمال می‌شود (فصل ۱۴).
ServiceAccountهویتی برای processهایی که درون یک Pod اجرا می‌شوند فراهم می‌کند. وقتی processهای درون Pod به cluster دسترسی پیدا می‌کنند،‏ توسط API server به‌عنوان یک service account مشخص،‏ مثلاً default،‏ authentication می‌شوند. اگر هنگام ساخت Pod service account مشخص نکنید،‏ به‌طور خودکار service account پیش‌فرض همان Namespace اختصاص می‌یابد (فصل ۱۴).
RBAC (Role-Based Access Control)تصمیمات authorization را مدیریت می‌کند و به administratorها اجازه می‌دهد سیاست‌های دسترسی را به‌صورت پویا از طریق Kubernetes API پیکربندی کنند. RBAC از چهار نوع object استفاده می‌کند: Role (قوانین دسترسی در یک namespace مشخص)،‏ ClusterRole (قوانین دسترسی در سطح cluster)،‏ RoleBinding (اعطای دسترسی‌های یک role به مجموعه‌ای از کاربران در یک namespace) و ClusterRoleBinding (اعطای دسترسی‌ها در سطح cluster) (فصل ۱۴).
Certificateیک فایل رمزنگاری‌شده‌ی امن برای validate کردن دسترسی به cluster کوبرنتیز. Certificateها به اپلیکیشن‌های درون یک cluster اجازه می‌دهند به‌صورت امن به Kubernetes API دسترسی داشته باشند و تأیید می‌کنند clientهای مجاز به دسترسی به API هستند (فصل ۱۴).
Subject Alternative Name (SAN)یک extension گواهی X.509 که به هویت‌ها اجازه می‌دهد به subject گواهی متصل شوند. استاندارد آن هویت‌ها را به‌صورت آدرس ایمیل،‏ نام DNS،‏ آدرس IP یا یک URI تعریف می‌کند.
JSON Web Token (JWT)روشی برای نمایش claimها که باید بین دو طرف منتقل شوند. JWTها می‌توانند دیجیتالی امضا و رمزگذاری شوند؛‏ کوبرنتیز از JWT به‌عنوان token authentication برای تأیید هویت entityهایی که می‌خواهند در یک cluster عملیاتی انجام دهند استفاده می‌کند (فصل ۱۴).
Admission Controllerقطعه‌کدی که پیش از persist شدن object،‏ درخواست‌ها به Kubernetes API server را رهگیری می‌کند. admission controllerها برای API server قابل‌پیکربندی‌اند و می‌توانند «validating»،‏ «mutating» یا هر دو باشند؛‏ هر admission controller می‌تواند درخواست را رد کند؛‏ controllerهای mutating می‌توانند objectهایی که admit می‌کنند را تغییر دهند،‏ در حالی‌که validating controllerها این اجازه را ندارند (فصل ۱۴).
Pod Security Policyیک API منسوخ‌شده که محدودیت‌های امنیتی را حین ساخت و به‌روزرسانی Pod اعمال می‌کرد. PodSecurityPolicy در نسخه‌ی ۱٫۲۱ منسوخ و در نسخه‌ی ۱٫۲۵ حذف شد؛‏ جایگزین آن Pod Security Admission یا یک admission plugin شخص‌ثالث است (فصل ۱۴).
user namespaceیک ویژگی kernel لینوکس که امکان شبیه‌سازی privilege ابرکاربر برای کاربران غیرممتاز را فراهم می‌کند («rootless containers»)؛‏ برای کاهش آسیب حملات احتمالی container break-out مؤثر است. در این زمینه،‏ namespace یک ویژگی kernel لینوکس است،‏ نه namespace به معنای کوبرنتیزی آن (فصل ۱۴).
Common Expression Language (CEL)یک زبان expression همه‌منظوره که برای سرعت،‏ قابل‌حمل‌بودن و اجرای امن طراحی شده است. در کوبرنتیز،‏ CEL برای اجرای کوئری و فیلترکردن دقیق به‌کار می‌رود؛‏ برای مثال با dynamic admission control برای فیلترکردن فیلدهای خاص در درخواست‌ها،‏ و با dynamic resource allocation (DRA) برای انتخاب resourceها بر پایه‌ی attributeهای خاص (فصل ۱۴،‏ فصل ۱۵).
sysctlیک رابط نیمه‌استاندارد برای خواندن یا تغییر ویژگی‌های kernel در حال اجرای یونیکس. روی سیستم‌های شبه‌یونیکس،‏ sysctl هم نام ابزار و هم نام system call است. container runtimeها و network pluginها ممکن است به تنظیم‌بودن مقادیر sysctl به شکلی خاص وابسته باشند (فصل ۱۴).

scheduling،‏ منابع و eviction (Scheduling, Resources & Eviction)

اصطلاحتوضیح
Affinityمجموعه‌ای از قوانین که به scheduler درباره‌ی مکان قراردادن Podها راهنمایی می‌دهند. دو نوع affinity وجود دارد: node affinity و pod-to-pod affinity. قوانین با استفاده از label و selector مشخص‌شده در Pod تعریف می‌شوند و می‌توانند required یا preferred باشند (فصل ۹).
Taintیک object هسته‌ای شامل سه ویژگی الزامی: key،‏ value و effect.‏ Taintها از scheduling شدن Podها روی Node یا گروه‌های Node جلوگیری می‌کنند؛‏ Taint و Toleration با هم کار می‌کنند تا Podها روی Nodeهای نامناسب scheduling نشوند (فصل ۹).
Tolerationیک object هسته‌ای با سه ویژگی الزامی key،‏ value و effect،‏ که scheduling شدن Podها روی Node یا گروه‌های Node دارای taint متناظر را ممکن می‌سازد. یک toleration نشان می‌دهد که Pod مجاز است (اما ملزم نیست) روی Nodeهای با taint متناظر scheduling شود (فصل ۹).
Preemptionمنطق preemption در کوبرنتیز کمک می‌کند یک Pod در حالت pending با evict کردن Podهای low priority موجود روی یک Node،‏ Node مناسبی پیدا کند. اگر یک Pod قابل scheduling نباشد،‏ scheduler سعی می‌کند Podهای low priority را preempt کند تا scheduling آن Pod pending ممکن شود (فصل ۹).
PriorityClassیک کلاس نام‌گذاری‌شده برای اولویت schedulingی که باید به یک Pod در آن کلاس اختصاص یابد. یک object غیر-namespaced که یک نام را به یک عدد صحیح priority نگاشت می‌کند؛‏ نام در فیلد metadata.name و مقدار priority در فیلد value مشخص می‌شود. محدوده‌ی priorityها از -2147483648 تا 1000000000 شامل خود آن‌هاست؛‏ مقادیر بالاتر یعنی اولویت بالاتر (فصل ۹).
QoS Classروشی برای کوبرنتیز فراهم می‌کند تا Podهای درون cluster را به چند کلاس دسته‌بندی کند و درباره‌ی scheduling و eviction تصمیم بگیرد. کلاس QoS یک Pod در زمان ساخت بر پایه‌ی تنظیمات request/limit resourceهای زیرساختی آن مشخص می‌شود؛‏ کوبرنتیز می‌تواند یکی از کلاس‌های Guaranteed،‏ Burstable یا BestEffort را به یک Pod نسبت دهد (فصل ۹).
LimitRangeمحدودیت‌هایی برای مصرف resource هر container یا Pod در یک namespace مشخص فراهم می‌کند. یک LimitRange می‌تواند یا مقدار API resourceهایی که می‌توان ساخت (برای یک نوع resource خاص) را محدود کند،‏ یا مقدار resourceهای زیرساختی که هر container یا Pod در یک namespace می‌تواند درخواست/مصرف کند (فصل ۶،‏ فصل ۹).
ResourceQuotaObjectی که مصرف تجمیعی resource را در سطح namespace محدود می‌کند؛‏ یا مقدار API resourceهایی که می‌توان در یک namespace ساخت را بر اساس نوع محدود می‌کند،‏ یا سقف کلی مصرف resourceهای زیرساختی برای آن namespace و objectهای درون آن را تعیین می‌کند (فصل ۶).
Evictionفرآیند خاتمه‌دادن یک یا چند Pod روی Nodeها. دو نوع eviction وجود دارد: node-pressure eviction و API-initiated eviction (فصل ۹).
API-initiated evictionفرآیندی که در آن با استفاده از Eviction API یک object Eviction می‌سازید که خاتمه‌ی graceful یک Pod را trigger می‌کند. می‌توانید eviction را مستقیم با فراخوانی Eviction API از طریق یک client از kube-apiserver درخواست کنید،‏ مثل دستور kubectl drain. evictionهای API-initiated به PodDisruptionBudget و terminationGracePeriodSeconds پیکربندی‌شده‌ی شما احترام می‌گذارند و با node-pressure eviction تفاوت دارند (فصل ۹).
Node-pressure evictionفرآیندی که kubelet طی آن به‌طور فعالانه Podها را برای بازپس‌گیری resource روی Nodeها خاتمه می‌دهد. kubelet منابعی مثل CPU،‏ memory،‏ فضای دیسک و inodeهای filesystem را روی Nodeهای cluster رصد می‌کند؛‏ وقتی یک یا چند مورد از آن‌ها به سطح مصرف خاصی برسند،‏ kubelet می‌تواند به‌طور فعال یک یا چند Pod روی Node را fail کند تا از starvation جلوگیری شود؛‏ با API-initiated eviction یکسان نیست (فصل ۹).
Drainفرایند تخلیه‌ی ایمن Podها از یک Node برای آماده‌سازی آن جهت maintenance یا حذف. دستور kubectl drain برای علامت‌گذاری یک Node به‌عنوان out-of-service استفاده می‌شود؛‏ هنگام اجرا،‏ تمام Podهای Node را evict می‌کند. اگر درخواست eviction موقتاً رد شود،‏ kubectl drain تا خاتمه‌ی تمام Podها یا رسیدن به یک timeout قابل‌پیکربندی،‏ تلاش را تکرار می‌کند (فصل ۹ و همین پیوست).
Disruptionرخدادهایی که به خارج از سرویس رفتن یک یا چند Pod منجر می‌شوند. یک disruption برای resourceهای مدیریت workload که به Podهای تحت‌تأثیر متکی‌اند،‏ مثل Deployment،‏ پیامد دارد. اگر شما به‌عنوان cluster operator یک Pod متعلق به یک اپلیکیشن را نابود کنید،‏ کوبرنتیز آن را «voluntary disruption» می‌نامد؛‏ اگر یک Pod به‌دلیل خرابی Node یا یک قطعی گسترده‌تر آفلاین شود،‏ کوبرنتیز آن را «involuntary disruption» می‌نامد (فصل ۹).
Pod Disruptionفرآیندی که در آن Podهای روی Node به‌صورت voluntary یا involuntary خاتمه می‌یابند. disruptionهای voluntary عمدی و توسط صاحبان اپلیکیشن یا مدیران cluster آغاز می‌شوند؛‏ disruptionهای involuntary غیرعمدی‌اند و می‌توانند با مسائل اجتناب‌ناپذیری مثل کمبود resource یک Node یا حذف تصادفی trigger شوند (فصل ۹).
Pod Disruption Budget (PDB)به صاحب اپلیکیشن اجازه می‌دهد یک object برای یک اپلیکیشن replicated بسازد که تضمین می‌کند تعداد یا درصد مشخصی از Podهای دارای یک label،‏ در هیچ لحظه‌ای به‌طور voluntary evict نمی‌شوند. disruptionهای involuntary توسط PDB قابل‌جلوگیری نیستند،‏ هرچند در بودجه‌ی آن محاسبه می‌شوند (فصل ۹).
Horizontal Pod Autoscaler (HPA)objectی که تعداد replica Podها را بر پایه‌ی هدف مصرف resource یا هدف metric سفارشی به‌طور خودکار مقیاس می‌دهد. HPA معمولاً با Deploymentها یا ReplicaSetها استفاده می‌شود؛‏ روی objectهایی که قابل مقیاس‌دهی نیستند مثل DaemonSet قابل‌اعمال نیست (فصل ۱۰).
Resource (infrastructure)قابلیت‌هایی که به یک یا چند Node ارائه می‌شوند (CPU،‏ memory،‏ GPU و غیره) و برای مصرف Podهای در حال اجرا روی آن Nodeها در دسترس قرار می‌گیرند. کوبرنتیز اصطلاح «resource» را برای توصیف یک API resource هم به‌کار می‌برد؛‏ می‌توانید از dynamic resource allocation برای مدیریت خودکار تخصیص‌های پیچیده‌ی resource هم استفاده کنید (فصل ۹).
Deviceیک یا چند resource زیرساختی که مستقیم یا غیرمستقیم به Nodeهای شما متصل‌اند؛‏ می‌توانند محصولات تجاری مثل GPU یا سخت‌افزار سفارشی مثل بردهای ASIC باشند و معمولاً به device driverهایی نیاز دارند که به Podهای کوبرنتیز اجازه‌ی دسترسی به آن‌ها را می‌دهند.
DeviceClassیک دسته از deviceها در cluster که می‌توان با dynamic resource allocation (DRA) از آن‌ها استفاده کرد. administratorها یا صاحبان device از DeviceClass برای تعریف مجموعه‌ای از deviceها که می‌توانند claim و در workload استفاده شوند بهره می‌برند؛‏ deviceها با ساختن ResourceClaimهایی که پارامترهای device خاصی را در یک DeviceClass فیلتر می‌کنند claim می‌شوند (فصل ۶).
Dynamic Resource Allocation (DRA)یک ویژگی کوبرنتیز که به شما اجازه می‌دهد resourceها،‏ معمولاً deviceهای متصل مثل شتاب‌دهنده‌های سخت‌افزاری،‏ را بین Podها درخواست و به‌اشتراک بگذارید. با DRA،‏ device driverها و ادمین‌های cluster «کلاس‌های» device قابل claim در workload را تعریف می‌کنند؛‏ کوبرنتیز deviceهای متناظر را به claimهای مشخص تخصیص می‌دهد و Podهای متناظر را روی Nodeهایی قرار می‌دهد که به آن deviceها دسترسی دارند (فصل ۶ و ۱۴).
ResourceClaimresourceهایی که یک workload نیاز دارد،‏ مثل deviceها،‏ را توصیف می‌کند. ResourceClaimها در dynamic resource allocation (DRA) استفاده می‌شوند تا Podها دسترسی به یک resource خاص داشته باشند؛‏ می‌توانند توسط اپراتورهای workload ساخته شوند یا بر پایه‌ی یک ResourceClaimTemplate توسط کوبرنتیز ساخته شوند (فصل ۱۴).
ResourceClaimTemplateیک template تعریف می‌کند که کوبرنتیز از آن برای ساخت ResourceClaim استفاده می‌کند. ResourceClaimTemplateها در DRA برای فراهم‌کردن دسترسی per-Pod یا per-PodGroup به resourceهای مشابه جداگانه استفاده می‌شوند؛‏ ResourceClaim متناظر با خاتمه‌ی Pod یا حذف PodGroup حذف می‌شود.
ResourceSliceیک یا چند resource زیرساختی،‏ مثل deviceها،‏ متصل به Nodeها را نمایش می‌دهد. driverها ResourceSliceها را در cluster می‌سازند و مدیریت می‌کنند؛‏ ResourceSliceها برای DRA استفاده می‌شوند و وقتی یک ResourceClaim ساخته می‌شود،‏ کوبرنتیز از آن‌ها برای پیدا کردن Nodeهایی که به resourceهای قابل تأمین claim دسترسی دارند استفاده می‌کند.
Container Device Interface (CDI)یک مشخصات CNCF برای توصیف پیکربندی deviceهایی که container runtimeها هنگام ساختن containerها اعمال می‌کنند. کوبرنتیز از CDI به‌همراه device plugin و Dynamic Resource Allocation استفاده می‌کند تا workloadها راه‌اندازی deviceهایی مثل bind mount یا environment variable را از runtime دریافت کنند.

گسترش کوبرنتیز (Extending Kubernetes)

اصطلاحتوضیح
Add-onsresourceهایی که عملکرد کوبرنتیز را گسترش می‌دهند. صفحه‌ی «Installing addons» توضیح بیشتری درباره‌ی استفاده از add-onها با cluster شما می‌دهد و برخی از add-onهای محبوب را فهرست می‌کند.
Extensionsکامپوننت‌های نرم‌افزاری که کوبرنتیز را گسترش می‌دهند و به‌عمق با آن یکپارچه می‌شوند تا انواع جدید سخت‌افزار را پشتیبانی کنند. بسیاری از administratorهای cluster از یک instance از نوع hosted یا distribution کوبرنتیز استفاده می‌کنند که این extensionها از پیش نصب شده‌اند؛‏ در نتیجه اکثر کاربران کوبرنتیز نیازی به نصب extension ندارند و تعداد کمتری نیاز به نوشتن extension جدید دارند (فصل ۱۵).
CustomResourceDefinitionنوعی API object که یک API سفارشی جدید برای افزودن به API server کوبرنتیز شما تعریف می‌کند،‏ بدون این‌که نیاز به ساختن یک server کامل سفارشی باشد. CustomResourceDefinitionها به شما اجازه می‌دهند Kubernetes API را برای محیط خود گسترش دهید،‏ اگر API resourceهای built-in نیازتان را برآورده نمی‌کنند (فصل ۱۵).
Operator patternیک طراحی سیستمی که یک controller را به یک یا چند custom resource متصل می‌کند. می‌توانید کوبرنتیز را با افزودن controllerهایی به cluster خود،‏ فراتر از controllerهای built-in که بخشی از خود کوبرنتیز هستند،‏ گسترش دهید. اگر یک اپلیکیشن در حال اجرا به‌عنوان controller عمل کند و دسترسی API برای انجام کارها در برابر یک custom resource تعریف‌شده در control plane داشته باشد،‏ این نمونه‌ای از Operator pattern است (فصل ۱۵).
Device Pluginروی Node worker اجرا می‌شود و به Pod دسترسی به resourceهای زیرساختی،‏ مثل سخت‌افزار محلی،‏ که نیاز به راه‌اندازی خاص vendor دارند،‏ می‌دهد. Device pluginها resourceها را به kubelet اعلام می‌کنند تا Podهای workload بتوانند به ویژگی‌های سخت‌افزاری مرتبط با Node اجرا دسترسی داشته باشند؛‏ می‌توانید یک device plugin را به‌صورت DaemonSet،‏ deploy کنید یا نرم‌افزار آن را مستقیم روی هر Node هدف نصب کنید (فصل ۱۵).

ابزارها و اکوسیستم (Tools & Ecosystem)

اصطلاحتوضیح
Kubectlابزار خط فرمان برای ارتباط با control plane cluster کوبرنتیز،‏ با استفاده از Kubernetes API. می‌توانید از kubectl برای ساخت،‏ بازرسی،‏ به‌روزرسانی و حذف objectهای کوبرنتیز استفاده کنید (مرجع سریع در همین پیوست).
Kubeadmابزاری برای نصب سریع کوبرنتیز و راه‌اندازی یک cluster امن. می‌توانید از kubeadm برای نصب هم control plane و هم کامپوننت‌های worker node استفاده کنید (فصل ۱۳).
kOps (Kubernetes Operations)kOps نه‌تنها به شما در ساخت،‏ نابودکردن،‏ ارتقا و نگه‌داری یک cluster کوبرنتیز production-grade و بسیار در‌دسترس کمک می‌کند،‏ بلکه زیرساخت cloud لازم را نیز provision می‌کند. AWS به‌طور رسمی پشتیبانی می‌شود،‏ DigitalOcean،‏ GCE و OpenStack در حالت beta و Azure در حالت alpha هستند؛‏ kOps یک سیستم provisioning خودکار با نصب کاملاً خودکار،‏ شناسایی cluster از طریق DNS،‏ self-healing از طریق Auto-Scaling Groups،‏ پشتیبانی چندین سیستم‌عامل و پشتیبانی high-availability است (فصل ۱۳).
Minikubeابزاری برای اجرای کوبرنتیز به‌صورت محلی. Minikube یک cluster کوبرنتیز محلی all-in-one یا multi-node را درون یک VM روی کامپیوتر شما اجرا می‌کند و برای امتحان کردن کوبرنتیز در یک محیط یادگیری مناسب است (فصل ۱۳ و همین پیوست).
Helm Chartبسته‌ای از پیکربندی‌های از‌پیش‌آماده‌ی کوبرنتیز که با ابزار Helm قابل مدیریت است. Chartها روشی قابل‌بازتولید برای ساخت و اشتراک‌گذاری اپلیکیشن‌های کوبرنتیز فراهم می‌کنند؛‏ یک chart واحد می‌تواند برای deploy کردن چیزی ساده مثل یک Pod memcached یا چیزی پیچیده مثل یک stack کامل وب‌اپلیکیشن استفاده شود.
cAdvisorابزاری که به کاربران container درکی از مصرف resource و ویژگی‌های کارایی containerهای در حال اجرای آن‌ها می‌دهد. یک daemon در حال اجراست که اطلاعات درباره‌ی containerهای در حال اجرا را جمع‌آوری،‏ تجمیع،‏ پردازش و export می‌کند؛‏ برای هر container پارامترهای ایزوله‌سازی resource،‏ مصرف resource تاریخی،‏ هیستوگرام‌های مصرف و آمار شبکه را نگه می‌دارد.
containerdیک container runtime با تمرکز بر سادگی،‏ استحکام و قابلیت‌حمل. containerd یک daemon است که روی لینوکس یا Windows اجرا می‌شود و مسئول واکشی و ذخیره‌ی imageها،‏ اجرای containerها،‏ فراهم‌کردن دسترسی شبکه و بیشتر است (فصل ۲).
CRI-Oابزاری که به شما اجازه می‌دهد از runtimeهای OCI با Kubernetes CRI استفاده کنید. CRI-O یک پیاده‌سازی CRI است که استفاده از runtimeهای سازگار با مشخصات runtime Open Container Initiative (OCI) را ممکن می‌کند؛‏ deploy کردن CRI-O به کوبرنتیز اجازه می‌دهد از هر runtime سازگار با OCI به‌عنوان container runtime برای اجرای Podها استفاده کند و imageهای container OCI را از registryهای راه‌دور واکشی کند (فصل ۲).
Container Runtime Interface (CRI)پروتکل اصلی gRPC برای ارتباط بین کامپوننت‌های Node یعنی kubelet و container runtime را تعریف می‌کند (فصل ۲).
Container Runtimeیک کامپوننت بنیادی که کوبرنتیز را قادر می‌سازد containerها را به‌طور مؤثر اجرا کند؛‏ مسئول مدیریت اجرا و lifecycle containerها در محیط کوبرنتیز است. کوبرنتیز از container runtimeهایی مثل containerd،‏ CRI-O و هر پیاده‌سازی دیگر Kubernetes CRI پشتیبانی می‌کند (فصل ۲).
DockerDocker (به‌طور دقیق‌تر،‏ Docker Engine) فناوری نرم‌افزاری است که مجازی‌سازی در سطح سیستم‌عامل — معروف به containerها — را فراهم می‌کند. Docker از ویژگی‌های ایزوله‌سازی resource kernel لینوکس مثل cgroup و kernel namespace،‏ و یک filesystem union-capable مثل OverlayFS استفاده می‌کند تا containerهای مستقل بدون overhead راه‌اندازی و نگه‌داری VM اجرا شوند.
Dockershimکامپوننتی از کوبرنتیز نسخه‌ی ۱٫۲۳ و پیش‌تر که به kubelet اجازه‌ی ارتباط با Docker Engine را می‌داد. از نسخه‌ی ۱٫۲۴،‏ dockershim از کوبرنتیز حذف شده است.
Istioیک platform باز (نه مخصوص کوبرنتیز) که راهی یکنواخت برای یکپارچه‌سازی microserviceها،‏ مدیریت جریان ترافیک،‏ اعمال سیاست‌ها و تجمیع داده‌ی telemetry فراهم می‌کند. افزودن Istio نیازمند تغییر کد اپلیکیشن نیست؛‏ یک لایه‌ی زیرساختی بین یک سرویس و شبکه است که وقتی با deployment سرویس‌ها ترکیب شود،‏ معمولاً service mesh نامیده می‌شود.
Service Catalogیک extension API سابق که اپلیکیشن‌های در حال اجرا روی cluster کوبرنتیز را قادر می‌ساخت به‌راحتی از offeringهای نرم‌افزاری managed خارجی،‏ مثل یک سرویس datastore ارائه‌شده توسط یک cloud provider،‏ استفاده کنند؛‏ راهی برای لیست‌کردن،‏ provision کردن و bind کردن با Managed Serviceهای خارجی بدون نیاز به دانش دقیق از چگونگی ساخت یا مدیریت آن‌ها فراهم می‌کرد.
Managed Serviceیک عرضه‌ی نرم‌افزاری که توسط یک provider شخص‌ثالث نگه‌داری می‌شود. نمونه‌هایی از Managed Serviceها AWS EC2،‏ Azure SQL Database و GCP Pub/Sub هستند،‏ اما می‌تواند هر عرضه‌ی نرم‌افزاری باشد که توسط یک اپلیکیشن قابل‌استفاده است.
Cloud Providerیک کسب‌وکار یا سازمان دیگر که یک platform محاسبات ابری ارائه می‌دهد. Cloud Providerها،‏ که گاهی Cloud Service Provider (CSP) نامیده می‌شوند،‏ platform یا سرویس‌های محاسبات ابری ارائه می‌کنند. بسیاری زیرساخت managed (Infrastructure as a Service یا IaaS) ارائه می‌دهند که در آن cloud provider مسئول سرور،‏ storage و شبکه است در حالی‌که شما لایه‌های روی آن را مدیریت می‌کنید. کوبرنتیز را نیز می‌توان به‌عنوان یک سرویس managed یافت (Platform as a Service یا PaaS) که در آن cloud provider مسئول control plane،‏ Node و زیرساخت مرتبط است (فصل ۱۲،‏ فصل ۱۳).
Cloud Native Computing Foundation (CNCF)اکوسیستم‌های پایدار می‌سازد و جامعه‌ای پیرامون پروژه‌هایی که containerها را به‌عنوان بخشی از معماری microservices orchestrate می‌کنند پرورش می‌دهد. کوبرنتیز یک پروژه‌ی CNCF است؛‏ CNCF یک زیرمجموعه از Linux Foundation است و مأموریتش فراگیر کردن cloud native computing است.
cgroup (control group)گروهی از processهای لینوکس با ایزوله‌سازی،‏ حسابداری و محدودیت‌های resource اختیاری. cgroup یک ویژگی kernel لینوکس است که مصرف resource (CPU،‏ memory،‏ I/O دیسک،‏ شبکه) برای مجموعه‌ای از processها را محدود،‏ حسابداری و ایزوله می‌کند (فصل ۹).
Imageinstance ذخیره‌شده‌ای از یک container که مجموعه‌ای از نرم‌افزار لازم برای اجرای یک اپلیکیشن را در بر دارد. روشی برای بسته‌بندی نرم‌افزار که امکان ذخیره در یک container registry،‏ pull به یک سیستم محلی و اجرا به‌عنوان یک اپلیکیشن را فراهم می‌کند؛‏ متادیتای درون image می‌تواند نشان دهد چه executableای باید اجرا شود،‏ چه کسی آن را ساخته،‏ و اطلاعات دیگر (فصل ۲).
Immutable Infrastructureبه زیرساخت رایانه‌ای (VM،‏ container،‏ تجهیزات شبکه) اشاره دارد که پس از deploy شدن نمی‌تواند تغییر کند. immutability را می‌توان با یک فرایند خودکار که تغییرات غیرمجاز را بازنویسی می‌کند یا سیستمی که از ابتدا اجازه‌ی تغییر نمی‌دهد اعمال کرد. containerها نمونه‌ی خوبی از immutable infrastructure هستند چون تغییرات پایدار در آن‌ها فقط با ساختن نسخه‌ی جدید image یا بازسازی container از image آن ممکن است.
Logginglogها فهرست رویدادهایی هستند که توسط cluster یا اپلیکیشن ثبت می‌شوند. logهای اپلیکیشن و سیستم می‌توانند به شما در درک آن‌چه درون cluster اتفاق می‌افتد کمک کنند و به‌ویژه برای debug کردن مشکلات و نظارت بر فعالیت cluster مفیدند (فصل ۱۱).

جامعه و نقش‌های مشارکت‌کننده (Community & Roles)

این بخش از Glossary رسمی،‏ نقش‌های افراد در پروژه‌ی متن‌باز کوبرنتیز (نه در یک تیم عملیاتی production) را توصیف می‌کند؛‏ برای کامل‌بودن این فصل به‌عنوان مرجع Glossary آورده شده است.

اصطلاحتوضیح
Application Architectفردی که مسئول طراحی سطح‌بالای یک اپلیکیشن است؛‏ اطمینان می‌دهد پیاده‌سازی اپلیکیشن امکان تعامل با اجزای پیرامونی را به‌شکلی مقیاس‌پذیر و قابل‌نگه‌داری فراهم می‌کند (پایگاه‌داده،‏ زیرساخت logging،‏ سایر microserviceها).
Application Developerفردی که اپلیکیشنی می‌نویسد که روی یک cluster کوبرنتیز اجرا می‌شود. تمرکز یک application developer روی یک بخش از اپلیکیشن است و مقیاس آن تمرکز می‌تواند به‌طور چشمگیر متفاوت باشد.
Approverفردی که می‌تواند مشارکت‌های کد کوبرنتیز را بازبینی و تأیید کند. در حالی‌که code review روی کیفیت و صحت کد متمرکز است،‏ approval روی پذیرش کلی یک مشارکت — شامل سازگاری پیشرو/پسرو،‏ پیروی از قراردادهای API و flag،‏ و مسائل ظریف عملکرد و صحت — تمرکز دارد؛‏ وضعیت approver به بخشی از codebase محدود است.
Cluster Architectفردی که زیرساختی طراحی می‌کند که شامل یک یا چند cluster کوبرنتیز است. cluster architectها به بهترین شیوه‌های سیستم‌های توزیع‌شده،‏ مثلاً high availability و امنیت،‏ توجه دارند.
Cluster Operatorفردی که clusterها را پیکربندی،‏ کنترل و نظارت می‌کند. مسئولیت اصلی آن‌ها نگه‌داشتن یک cluster در حالت up-and-running است که می‌تواند شامل فعالیت‌های maintenance دوره‌ای یا upgrade باشد. cluster operator با Operator pattern که Kubernetes API را گسترش می‌دهد متفاوت است.
CLA (Contributor License Agreement)شرایطی که تحت آن یک مشارکت‌کننده به یک پروژه‌ی متن‌باز برای مشارکت‌هایش لایسنس اعطا می‌کند. CLAها به حل‌وفصل اختلافات حقوقی مربوط به مواد مشارکتی و مالکیت فکری کمک می‌کنند.
Code Contributorفردی که کد به codebase متن‌باز کوبرنتیز توسعه و مشارکت می‌دهد. آن‌ها هم‌چنین عضو فعالی از جامعه هستند که در یک یا چند Special Interest Group (SIG) مشارکت می‌کنند.
Contributorکسی که کد،‏ مستندات یا زمان خود را برای کمک به پروژه یا جامعه‌ی کوبرنتیز اهدا می‌کند. مشارکت‌ها شامل pull request (PR)،‏ issue،‏ بازخورد،‏ مشارکت در special interest group (SIG) یا سازمان‌دهی رویدادهای جامعه هستند.
Developer (disambiguation)می‌تواند به Application Developer،‏ Code Contributor یا Platform Developer اشاره داشته باشد؛‏ این اصطلاح چندمعنایی بسته به context معانی متفاوتی دارد.
Memberیک مشارکت‌کننده‌ی مداوماً فعال در جامعه‌ی K8s. اعضا می‌توانند issue و PR به آن‌ها واگذار شود و از طریق تیم‌های GitHub در special interest group (SIG) مشارکت کنند؛‏ تست‌های pre-submit به‌طور خودکار برای PRهای اعضا اجرا می‌شود و انتظار می‌رود عضو یک مشارکت‌کننده‌ی فعال در جامعه باقی بماند.
Platform Developerفردی که platform کوبرنتیز را برای تناسب با نیازهای پروژه‌ی خود سفارشی می‌کند؛‏ برای مثال ممکن است از Custom Resource استفاده کند یا Kubernetes API را با aggregation layer گسترش دهد تا قابلیتی به instance کوبرنتیز خود،‏ به‌طور خاص برای اپلیکیشنش،‏ اضافه کند. برخی platform developerها هم‌چنین contributor هستند و extensionهایی توسعه می‌دهند که به جامعه‌ی کوبرنتیز مشارکت داده می‌شود؛‏ برخی دیگر extensionهای تجاری closed-source یا مختص یک سایت توسعه می‌دهند.
Reviewerفردی که کد را برای کیفیت و صحت روی بخشی از پروژه بازبینی می‌کند. reviewerها هم به codebase و هم به اصول مهندسی نرم‌افزار مسلط‌اند؛‏ وضعیت reviewer به بخشی از codebase محدود است.
SIG (special interest group)اعضای جامعه‌ای که به‌طور جمعی یک بخش یا جنبه‌ی مستمر از پروژه‌ی متن‌باز بزرگ‌تر کوبرنتیز را مدیریت می‌کنند. اعضای درون یک SIG علاقه‌ی مشترکی به پیشبرد یک حوزه‌ی خاص دارند،‏ مثل architecture،‏ API machinery یا documentation؛‏ SIGها باید از رهنمودهای حاکمیتی SIG پیروی کنند اما می‌توانند سیاست مشارکت و کانال‌های ارتباطی خاص خود را داشته باشند.
WG (working group)بحث و/یا پیاده‌سازی یک پروژه‌ی کوتاه‌مدت،‏ محدود یا decoupled را برای یک کمیته،‏ SIG یا تلاش cross-SIG تسهیل می‌کند. working groupها راهی برای سازمان‌دهی افراد جهت انجام یک وظیفه‌ی مشخص هستند.
Upstream (disambiguation)می‌تواند به کوبرنتیز هسته یا مخزن منبعی که یک مخزن از آن fork شده اشاره داشته باشد. در جامعه‌ی کوبرنتیز،‏ «upstream» معمولاً به معنای codebase هسته‌ی کوبرنتیز است که اکوسیستم گسترده‌تر،‏ کد دیگر یا ابزارهای شخص‌ثالث به آن متکی‌اند؛‏ در GitHub یا git،‏ قرارداد این است که به مخزن منبع «upstream» و به مخزن fork‌شده «downstream» گفته می‌شود.
Downstream (disambiguation)می‌تواند به کدی در اکوسیستم کوبرنتیز اشاره داشته باشد که به codebase هسته‌ی کوبرنتیز یا یک مخزن fork‌شده متکی است. در جامعه‌ی کوبرنتیز،‏ «downstream» معمولاً به اکوسیستم،‏ کد یا ابزارهای شخص‌ثالثی اشاره دارد که به codebase هسته متکی‌اند؛‏ در GitHub یا git،‏ قرارداد این است که به یک مخزن fork‌شده «downstream» گفته می‌شود،‏ در حالی‌که مخزن منبع «upstream» تلقی می‌شود.
تمرین‌های فصل ۱۷ ۱۴ تمرین
  1. مفهومیتفاوت kubectl create و kubectl apply چیست و چرا مستندات apply را برای مدیریت اپلیکیشن در production توصیه می‌کنند؟
    پاسخ

    kubectl create امری (imperative) است: یک resource جدید می‌سازد و اگر از قبل وجود داشته باشد با خطای AlreadyExists متوقف می‌شود. kubectl apply اعلانی (declarative) است: با three-way merge بین manifest جدید،‏ آخرین manifest اعمال‌شده (annotation به نام kubectl.kubernetes.io/last-applied-configuration) و state فعلی object،‏ فقط تغییرات لازم را می‌فرستد و اگر resource وجود نداشته باشد آن را می‌سازد. به همین دلیل apply idempotent است و می‌توان آن را بارها در pipeline اجرا کرد؛‏ پایه‌ی GitOps همین است.

    نکته‌ی امتیازآور: three-way merge اجازه می‌دهد فیلدی که از manifest حذف کرده‌اید از object هم حذف شود،‏ بی‌آنکه فیلدهایی که controllerها نوشته‌اند (مثل status یا replicas تحت HPA) پاک شوند. با --server-side همین کار در API server و با field management انجام می‌شود.

  2. عملیروی یک namespace با چند Pod،‏ دستوری با JSONPath بنویسید که برای هر Pod،‏ نام و مجموع CPU request همه‌ی containerهای آن را در یک خط چاپ کند.
    پاسخ

    JSONPath خودش جمع (sum) ندارد،‏ پس برای هر container باید مقدار را جدا چاپ کرد و جمع را در shell انجام داد،‏ یا از custom-columns برای دیدن مقادیر خام استفاده کرد:

    bash
    kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{": "}{range .spec.containers[*]}{.resources.requests.cpu}{" "}{end}{"\n"}{end}'

    خروجی یک خط برای هر Pod با نام و لیست CPU requestهای هر container است؛‏ اگر جمع عددی واقعی لازم باشد،‏ معمولاً از jq که قابلیت محاسبات دارد استفاده می‌شود،‏ چون JSONPath صرفاً یک زبان استخراج است نه محاسبه.

  3. مفهومیتفاوت --selector (label selector) و --field-selector در kubectl get چیست؟ چرا نمی‌توان با --field-selector روی هر فیلد دلخواهی فیلتر کرد؟
    پاسخ

    --selector (یا -l) روی metadata.labels فیلتر می‌کند و هم شرط برابری (app=web،‏ app!=web) و هم شرط مجموعه‌ای (env in (prod,staging)،‏ !canary) را می‌پذیرد. --field-selector روی فیلدهای خود object فیلتر می‌کند و فقط =،‏ == و != دارد. هر دو به شکل query parameter به API server فرستاده می‌شوند و فیلتر در سمت server انجام می‌شود.

    هر نوع resource فقط مجموعه‌ی ثابتی از فیلدها را برای field selector ثبت کرده است: همه metadata.name و metadata.namespace را دارند و Pod مثلاً spec.nodeName،‏ status.phase و status.podIP را هم دارد. فیلد ثبت‌نشده خطای field label not supported می‌دهد.

    نکته‌ی امتیازآور: برای custom resourceها از v1.32 می‌توان در CRD با selectableFields فیلدهای قابل‌انتخاب را تعریف کرد (فصل ۱۵).

  4. سناریوی Productionیک اپلیکیشن e-commerce با ۱۲ replica Pod روی ۳ Node پشت یک Ingress اجرا می‌شود. تیم SRE گزارش می‌دهد که برخی درخواست‌های کاربران با تأخیر بالا مواجه می‌شوند. با دستور زیر بررسی را شروع می‌کنند:
    out
    $ kubectl get pods -n shop -o wide
NAME                        READY   STATUS    RESTARTS       AGE   IP            NODE     NOMINATED NODE   READINESS GATES
shop-api-7d6ff5cd77-2f8kq   1/1     Running   14 (12m ago)   6h    10.244.1.23   node-2   <none>           <none>
shop-api-7d6ff5cd77-9h3lm   1/1     Running   0              6h    10.244.2.11   node-3   <none>           <none>
shop-api-7d6ff5cd77-x9k2p   1/1     Running   16 (4m ago)    6h    10.244.1.24   node-2   <none>           <none>
...
    وظیفه: یک دستور kubectl واحد بنویسید که فقط Podهایی را که restart داشته‌اند نمایش دهد و restartCount را هم در ستون جداگانه‌ای نشان دهد،‏ بدون grep روی خروجی.
    پاسخ

    --field-selector روی restartCount کار نمی‌کند و custom-columns هم فیلتر ردیف ندارد؛‏ اما JSONPath می‌تواند روی خود items فیلتر بگذارد:

    bash
    # only Pods whose first container has restarted, with the count in its own column
kubectl get pods -n shop -o jsonpath='{range .items[?(@.status.containerStatuses[0].restartCount>0)]}{.metadata.name}{"\t"}{.spec.nodeName}{"\t"}{.status.containerStatuses[0].restartCount}{"\n"}{end}'

# alternative: every Pod, sorted so the most restarted ones come last
kubectl get pods -n shop --sort-by='.status.containerStatuses[0].restartCount' \
  -o custom-columns='NAME:.metadata.name,NODE:.spec.nodeName,RESTARTS:.status.containerStatuses[0].restartCount'

    خروجی دستور اول فقط دو Pod روی node-2 است (۱۴ و ۱۶ restart). تجمع restart روی یک Node معمولاً به مشکل سطح Node اشاره دارد (مثلاً memory pressure یا مشکل kernel یا cgroup)،‏ نه به کد اپلیکیشن. گام بعد: kubectl describe pod برای Last State و Reason (مثلاً OOMKilled یا شکست liveness probe)،‏ kubectl logs --previous و kubectl describe node node-2 برای conditionها و eventها.

    نکته‌ی امتیازآور: فیلتر روی containerStatuses[0] فقط container اول را می‌بیند؛‏ در Pod چند containerی باید همه را بررسی کرد. ستون RESTARTS در kubectl جدید زمان آخرین restart را هم نشان می‌دهد (14 (12m ago)) که برای فهم «هنوز ادامه دارد یا نه» مهم است.

  5. عملیدستوری بنویسید که فهرست تمام Nodeهای cluster را به‌همراه وضعیت condition از نوع Ready در قالب custom-columns نشان دهد؛‏ سپس همان کار را با JSONPath و range/end انجام دهید.
    پاسخ
    bash
    # with custom-columns
kubectl get node -o custom-columns='NODE_NAME:.metadata.name,STATUS:.status.conditions[?(@.type=="Ready")].status'

# with JSONPath and range/end
JSONPATH='{range .items[*]}{.metadata.name}{": "}{range .status.conditions[?(@.type=="Ready")]}{.status}{end}{"\n"}{end}'
kubectl get nodes -o jsonpath="$JSONPATH"

    هر دو دستور یک خروجی معادل تولید می‌کنند؛‏ custom-columns برای یک ستون ساده سریع‌تر نوشته می‌شود،‏ در حالی‌که range/end برای منطق تودرتوتر (چند فیلد تو در تو،‏ فرمت دلخواه هر خط) انعطاف بیشتری می‌دهد.

  6. مفهومیآیا JSONPath در kubectl از regular expression پشتیبانی می‌کند؟ برای فیلتر مبتنی بر الگو چه می‌کنید؟
    پاسخ

    نه. مستندات صریحاً می‌گوید regular expression در JSONPath پشتیبانی نمی‌شود و عبارتی مثل ?(@.metadata.name=~/^test$/) کار نمی‌کند. فیلتر ?() فقط مقایسه‌های ساده دارد: ==،‏ !=،‏ <،‏ >،‏ <=،‏ >= و بررسی وجود فیلد. راه پیشنهادی مستندات jq است: kubectl get pods -o json | jq -r '.items[] | select(.metadata.name | test("test-")).metadata.name'.

    نکته‌ی امتیازآور: اگر الگو روی label است،‏ اول label selector را امتحان کنید؛‏ فیلتر در سمت server انجام می‌شود و حجم پاسخ کمتر است. JSONPath برای استخراج ساختاری است و jq برای منطق پیچیده‌تر مثل regex و جمع‌زدن.

  11. مفهومیتفاوت API-initiated eviction و Node-pressure eviction چیست؟ چرا PodDisruptionBudget فقط روی یکی از این دو اعمال می‌شود؟
    پاسخ

    API-initiated eviction با ساختن object از نوع Eviction از راه Eviction API انجام می‌شود (مثلاً kubectl drain). API server پیش از پذیرفتن آن PodDisruptionBudget را بررسی می‌کند و اگر eviction بودجه را نقض کند،‏ درخواست را با خطای 429 Too Many Requests رد می‌کند؛‏ terminationGracePeriodSeconds هم رعایت می‌شود. Node-pressure eviction را kubelet خودش و محلی انجام می‌دهد،‏ وقتی memory،‏ disk یا inode از آستانه رد شود؛‏ این مسیر از API eviction رد نمی‌شود و PDB را نمی‌بیند. در eviction از نوع soft،‏ grace period حداکثر eviction-max-pod-grace-period است و در نوع hard،‏ Pod بی‌درنگ (grace period صفر) خاتمه می‌یابد.

    نکته‌ی امتیازآور: PDB فقط disruptionهای voluntary را از راه Eviction API محدود می‌کند؛‏ kubectl delete pod،‏ scale دستی و Node-pressure eviction را متوقف نمی‌کند.

    رفع: پیام‌هایی را که در صف (مثلاً Kafka یا RabbitMQ) consume شده ولی ack نشده‌اند پیدا و دوباره پردازش کنید و تراکنش‌های ناقص را reconcile کنید.

    نکته‌ی امتیازآور: RBAC نمی‌تواند بین delete معمولی و delete با grace period کوتاه فرق بگذارد؛‏ اگر واقعاً لازم است،‏ یک validating admission webhook می‌تواند DeleteOptions درخواست را ببیند و gracePeriodSeconds کوتاه را رد کند. --grace-period=0 بدون --force را kubectl خودش به ۱ تبدیل می‌کند.

  6. میانیدر rolling update یک Deployment،‏ maxSurge و maxUnavailable چه می‌کنند و rollout خراب را چطور تشخیص می‌دهید و برمی‌گردانید؟
    پاسخ

    هر دو پیش‌فرض ۲۵٪ هستند؛‏ maxSurge به بالا و maxUnavailable به پایین گرد می‌شود،‏ پس با ۴ replica هر دو ۱ و با ۲ replica مقدار maxUnavailable صفر است. هر دو نمی‌توانند هم‌زمان صفر باشند. اگر Podهای جدید Ready نشوند (مثلاً ImagePullBackOff)،‏ rollout می‌ایستد و چون Podهای قدیمی سالم بیش از maxUnavailable حذف نمی‌شوند،‏ سرویس قطع نمی‌شود. پس از progressDeadlineSeconds (پیش‌فرض ۶۰۰ ثانیه) condition به نام Progressing با reason برابر ProgressDeadlineExceeded می‌شود. kubectl rollout status با کد خروج غیرصفر تمام می‌شود و kubectl rollout undo (یا --to-revision=N) برمی‌گرداند.

    نکته‌ی امتیازآور: کوبرنتیز خودکار rollback نمی‌کند؛‏ این کار ابزار CD یا شماست. بدون readiness probe،‏ rollout خراب هم «موفق» گزارش می‌شود.

    نکته‌ی امتیازآور: این کار یک revision تازه در rollout history می‌سازد؛‏ برای StatefulSet و DaemonSet هم کار می‌کند.

  8. میانیcordon،‏ drain و taint چه فرقی دارند؟ drain کدام flagها را لازم دارد؟
    پاسخ

    cordon فقط Node را unschedulable می‌کند و Podهای فعلی می‌مانند. drain اول cordon می‌کند و بعد Podها را با Eviction API بیرون می‌کند،‏ پس PodDisruptionBudget رعایت می‌شود و اگر بودجه اجازه ندهد،‏ دوباره تلاش می‌کند. Podهای DaemonSet را evict نمی‌کند و بدون --ignore-daemonsets متوقف می‌شود؛‏ Pod دارای emptyDir را بدون --delete-emptydir-data و Pod بدون controller را بدون --force evict نمی‌کند. taint ابزار عمومی‌تر است: NoSchedule فقط Pod جدید را راه نمی‌دهد و NoExecute Podهای بدون toleration را هم بیرون می‌کند. پس از کار،‏ uncordon.

    نکته‌ی امتیازآور: cordon در عمل taint به نام node.kubernetes.io/unschedulable:NoSchedule روی Node می‌گذارد.

  9. میانیkubectl port-forward،‏ kubectl proxy و Service از نوع NodePort چه فرقی دارند؟
    پاسخ

    port-forward یک port محلی را از راه API server و kubelet به port یک Pod مشخص tunnel می‌کند؛‏ اگر به svc/... اشاره کنید هم فقط یک Pod انتخاب می‌شود و load balancing ندارد. proxy روی 127.0.0.1:8001 یک proxy با credential شما به خود Kubernetes API می‌سازد؛‏ برای دسترسی به Pod از subresource به نام proxy در API استفاده می‌شود. NodePort دسترسی واقعی شبکه‌ای از بیرون cluster است که kube-proxy بین Podها پخش می‌کند. دو مورد اول ابزار debug هستند و برای ترافیک کاربر نیستند.

    نکته‌ی امتیازآور: هر دو ابزار اول به RBAC نیاز دارند (pods/portforward و pods/proxy یا services/proxy) و در audit log دیده می‌شوند.

  10. میانیمسیر kubectl exec و kubectl logs چیست و برای محدود کردنشان چه RBACی لازم است؟
    پاسخ

    هر دو به API server می‌روند و API server مستقیماً به kubelet همان Node وصل می‌شود؛‏ kubelet هم از container runtime،‏ stream مربوط به exec یا فایل log را می‌گیرد. اتصال‌های تعاملی (exec،‏ attach،‏ port-forward) در نسخه‌های جدید روی WebSocket هستند. در RBAC،‏ exec verb به نام create روی subresource به نام pods/exec و logs verb به نام get روی pods/log می‌خواهد؛‏ پس می‌توان logs را داد و exec را نه.

    نکته‌ی امتیازآور: این یکی از استثناهای «همه‌چیز از راه API server و etcd»: داده‌ی exec و logs در etcd نیست و از kubelet می‌آید؛‏ برای همین قطع بودن kubelet،‏ logs را هم از دسترس خارج می‌کند.

  11. میانیPod در CrashLoopBackOff است و image آن shell ندارد. چطور علت را پیدا می‌کنید؟
    پاسخ

    kubectl describe pod برای Last State،‏ Exit Code و Reason (مثلاً OOMKilled یا Error) و eventها؛‏ kubectl logs <pod> --previous برای log اجرای قبلی که crash کرد. اگر باید داخل محیط Pod را دید،‏ kubectl debug -it <pod> --image=busybox:1.28 --target=<container> یک ephemeral container با ابزار debug اضافه می‌کند که process namespace همان container را می‌بیند؛‏ یا kubectl debug <pod> --copy-to=... یک کپی با command دیگر می‌سازد.

    نکته‌ی امتیازآور: فاز Pod در CrashLoopBackOff همچنان Running است؛‏ پس --field-selector=status.phase!=Running آن را پیدا نمی‌کند. فاصله‌ی restartها به‌صورت نمایی تا ۵ دقیقه زیاد می‌شود.

  12. میانی--dry-run=client،‏ --dry-run=server و kubectl diff چه فرقی دارند؟
    پاسخ

    --dry-run=client فقط در خود kubectl object را می‌سازد و چاپ می‌کند؛‏ برای تولید YAML (مثلاً -o yaml) خوب است،‏ اما validation سمت server و admission را نمی‌بیند. --dry-run=server درخواست را تا انتها از authentication،‏ authorization،‏ mutating و validating admission و validation می‌گذراند و فقط ذخیره در etcd انجام نمی‌شود؛‏ پس خطای واقعی و defaultها را نشان می‌دهد. kubectl diff -f با همین server-side dry run،‏ object نهایی را با object فعلی cluster مقایسه می‌کند.

    نکته‌ی امتیازآور: admission webhookها هم در dry run صدا زده می‌شوند؛‏ برای همین در admissionregistration.k8s.io/v1 فیلد sideEffects فقط None یا NoneOnDryRun را می‌پذیرد و webhookی که side effect دارد باید فیلد dryRun در درخواست را بررسی کند (فصل ۱۵).

خلاصه‌ی فصل ۱۷ در یک نگاه برای مرور سریع؛‏ جزئیات در متن فصل

ایده‌ی محوری: این پیوست جعبه‌ابزار روزمره است؛‏ cluster یادگیری با minikube،‏ نصب درست kubectl،‏ چرخه‌ی deploy تا rollback با kubectl،‏ مرجع سریع دستورها،‏ JSONPath برای استخراج داده و واژه‌نامه‌ی ۱۶۲ اصطلاح رسمی.

۱. minikube و نصب kubectl
  • minikube start: یک Node که هم control plane است و هم worker؛‏ current-context را روی minikube می‌گذارد.
  • status: چهار خط host و kubelet و apiserver و kubeconfig؛‏ وضعیت Misconfigured با minikube update-context درست می‌شود.
  • تفاوت stop و delete: اولی داده را نگه می‌دارد؛‏ دومی ماشین و ورودی kubeconfig را پاک می‌کند.
  • version skew: فاصله‌ی kubectl با control plane حداکثر یک نسخه‌ی minor است.
  • نصب: با curl،‏ checksum با sha256sum --check؛‏ مخزن pkgs.k8s.io برای هر minor جداست.
  • completion: با kubectl completion bash؛‏ alias مثل k فقط برای کار تعاملی است.
  • دام: «connection refused» یعنی API server در دسترس نیست؛‏ «Unauthorized» یعنی credential مشکل دارد؛‏ x509 یعنی CA مطابقت ندارد.
۲. آموزش مبانی: از deploy تا rollback
  1. با create deployment،‏ Deployment و ReplicaSet و Pod ساخته می‌شوند.
  2. با proxy،‏ exec،‏ logs و describe برنامه بررسی می‌شود.
  3. با expose،‏ Service با selector همان label ساخته می‌شود.
  4. با scale،‏ فقط spec.replicas عوض می‌شود.
  5. با set image،‏ rolling update انجام می‌شود و با rollout undo برمی‌گردد.
  • نام Pod: نام Deployment،‏ سپس pod-template-hash و سپس پسوند تصادفی.
  • Service: نوع ClusterIP پیش‌فرض است؛‏ NodePort روی آن و LoadBalancer روی NodePort ساخته می‌شود؛‏ ExternalName فقط CNAME است.
  • توزیع بار: در سطح اتصال (لایه‌ی ۴) و تصادفی؛‏ اتصال طولانی به Pod جدید نمی‌رود.
  • rollout: پیش‌فرض maxSurge و maxUnavailable برابر ۲۵٪ است؛‏ rollout خراب می‌ایستد ولی خودکار برنمی‌گردد.
  • دام: Endpoints خالی یعنی selector یا readiness،‏ نه شبکه.
  • دام: برداشتن label برنامه از Pod آن را orphan می‌کند و ReplicaSet یک Pod تازه می‌سازد.

۴. JSONPath و قراردادهای script

این فصل درباره‌ی container و container image و نقش آن‌ها در عملیات (operations) و توسعه‌ی راه‌حل‌ها است. هر چیزی که در کوبرنتیز اجرا می‌شود در نهایت یک container است که kubelet با کمک container runtime روی یک Node اجرا می‌کند؛‏ پس فهم دقیق image،‏ pull policy،‏ credentialهای registry،‏ RuntimeClass،‏ lifecycle hookها و CRI،‏ پایه‌ی بقیه‌ی فصل‌ها (به‌ویژه فصل ۳ درباره‌ی Pod و فصل ۴ درباره‌ی Workload Management) است.

ماجرای این فصل: API واقعی فروشگاه در یک image

در پایان فصل ۱،‏ Deployment به نام shop-api با سه replica روی cluster اجرا می‌شد،‏ اما داخلش nginx بود،‏ نه API فروشگاه. این هفته سارا کد واقعی API را آماده کرده و شما باید آن را به cluster برسانید. در همین مسیر همان سه مشکلی پیش می‌آید که تقریباً هر تیمی در هفته‌های اول دارد:

  1. روی laptop سارا همه‌چیز درست اجرا می‌شود،‏ اما روی cluster خطای ImagePullBackOff می‌آید؛‏ image در registry خصوصی تیم است و cluster هیچ credentialی برای خواندنش ندارد.
  2. یک هفته بعد،‏ دو Pod از یک Deployment به یک درخواست جواب‌های متفاوت دادند. بررسی نشان داد کسی image تازه‌ای را با همان tag قبلی push کرده و Podهایی که بعد از آن ساخته شده بودند کد دیگری اجرا می‌کردند؛‏ دیگر هیچ‌کس نمی‌دانست کدام Pod کدام کد را اجرا می‌کند.
  3. در هر انتشار،‏ چند درخواست checkout که در میانه‌ی کار بودند با خطای 502 قطع می‌شوند و مشتری نمی‌داند پرداختش ثبت شده یا نه. برنامه سیگنال توقف را نادیده می‌گیرد و حذف هر Pod سی ثانیه طول می‌کشد.

۱. image و container

هر image یک بسته‌ی آماده‌ی اجراست: کد برنامه،‏ runtime زبان (مثلاً Python)،‏ libraryها و تنظیمات پیش‌فرض. هر image تغییرناپذیر است و از چند لایه (layer) روی هم ساخته می‌شود. هر container یک instance در حال اجرا از image است؛‏ مثل رابطه‌ی فایل نصب یک برنامه با خود برنامه‌ی در حال اجرا. اگر چیزی باید عوض شود،‏ image تازه می‌سازید؛‏ داخل container در حال اجرا تغییر نمی‌دهید.

۲. نام کامل یک image

نامی که در فیلد image می‌نویسید چهار جزء دارد و هر جزئی را که ننویسید،‏ مقدار پیش‌فرض می‌گیرد:

جزءدر نمونه‌ی شاپیفایاگر ننویسید

repository (مسیر image)shopify/apiبرای imageهای رسمی پیشوند library/

پس نام کامل nginx:1.27 در واقع docker.io/library/nginx:1.27 است. همین قاعده توضیح می‌دهد چرا در گام ۵ kubelet برای image به نام shopify/api:1.0 سراغ Docker Hub می‌رود.

۳. image چطور به Node می‌رسد؟

ساختن image کار ابزاری مثل Docker است،‏ اما اجرای آن روی Node کار container runtime (در k3s همان containerd) است که kubelet از راه CRI (رابط استاندارد kubelet با runtime) با آن کار می‌کند. این دو،‏ انبار image جداگانه دارند؛‏ imageی که با Docker ساخته‌اید،‏ خودبه‌خود در containerd نیست. راه استاندارد رساندن image،‏ یک registry است: شما push می‌کنید و containerd هر Node pull می‌کند.

۴. kubelet چه وقت image را pull می‌کند؟

فیلد imagePullPolicy این را تعیین می‌کند. اگر آن را ننویسید،‏ API server هنگام ساختن شیء از روی نام image مقدارش را پر می‌کند:

نام imageمقدار پیش‌فرضرفتار kubelet
بدون tag یا با tag برابر latestAlwaysهر بار که container شروع می‌شود از registry می‌پرسد
با tag دیگر (مثلاً 1.0)IfNotPresentاگر image روی Node باشد،‏ سراغ registry نمی‌رود
با digestIfNotPresentمحتوا با hash ثابت شده؛‏ نسخه‌ی موجود همان است

مقدار سوم یعنی Never هیچ‌وقت pull نمی‌کند. این مقدار پیش‌فرض فقط یک بار،‏ هنگام ساختن شیء تعیین می‌شود و با عوض شدن tag تغییر نمی‌کند.

۵. container چطور خاموش می‌شود؟

وقتی Podی حذف می‌شود (با دستور شما،‏ rollout یا drain)،‏ این مراحل به ترتیب رخ می‌دهد:

  1. Pod در وضعیت Terminating قرار می‌گیرد و شمارش معکوس grace period (پیش‌فرض ۳۰ ثانیه) شروع می‌شود؛‏ هم‌زمان Pod از فهرست مقصدهای Service بیرون می‌رود.
  2. اگر preStop hook تعریف شده باشد،‏ kubelet اول آن را اجرا می‌کند و منتظر پایانش می‌ماند.
  3. kubelet به process اصلی container سیگنال SIGTERM می‌فرستد؛‏ برنامه باید کارهای نیمه‌تمام را تمام کند و خارج شود.
  4. اگر تا پایان grace period خارج نشود،‏ با SIGKILL کشته می‌شود و درخواست‌های نیمه‌کاره قطع می‌شوند.
دام PID 1

در هر container،‏ process اصلی PID شماره‌ی ۱ است. در این حالت kernel لینوکس سیگنال SIGTERM را برای PID 1ی که handler ثبت نکرده،‏ نادیده می‌گیرد. برنامه‌ای که SIGTERM را مدیریت نکند،‏ تمام grace period را منتظر می‌ماند و بعد کشته می‌شود؛‏ همان «حذف نیم‌دقیقه‌ای» مشکل سوم شاپیفای. این رفتار را در گام ۳ با Docker و در گام ۱۰ با کوبرنتیز می‌بینید.

گام ۱: کد API فروشگاه

API فروشگاه را عمداً ساده و فقط با کتابخانه‌ی استاندارد Python نوشته‌ایم تا تمرکز روی کوبرنتیز بماند. این کد را در فایل ~/shopify/app.py بگذارید:

app.py (نسخه‌ی 1.0)
import json
import os
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

VERSION = os.environ.get("APP_VERSION", "1.0")
PORT = int(os.environ.get("PORT", "8080"))
PRODUCTS = [
    {"id": 1, "name": "Tea mug", "price": 180000},
    {"id": 2, "name": "Notebook", "price": 95000},
]


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/healthz":
            self.reply(200, {"status": "ok"})
        elif self.path == "/api/products":
            self.reply(200, {"version": VERSION, "pod": os.uname().nodename,
                             "products": PRODUCTS})
        elif self.path == "/api/slow":
            time.sleep(5)
            self.reply(200, {"status": "done"})
        else:
            self.reply(404, {"error": "not found"})

    def reply(self, code, body):
        data = json.dumps(body).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, fmt, *args):
        print(f"{self.address_string()} {fmt % args}", flush=True)


server = ThreadingHTTPServer(("", PORT), Handler)
print(f"shop-api {VERSION} listening on :{PORT}", flush=True)
server.serve_forever()
بخش کدکار آن
متغیرهای VERSION و PORTتنظیمات از environment variable خوانده می‌شوند،‏ نه از کد. در فصل ۶ همین‌ها را از ConfigMap می‌دهیم.
فهرست PRODUCTSداده‌ی نمونه؛‏ در فصل ۴ جایش را PostgreSQL می‌گیرد.
مسیر /healthzبرای probeها: فقط می‌گوید process زنده است. در فصل ۳ کامل‌ترش می‌کنیم.
مسیر /api/productsپاسخ اصلی API،‏ همراه نسخه و hostname؛‏ داخل Pod مقدار hostname همان نام Pod است.
مسیر /api/slowشبیه‌سازی یک خرید پنج‌ثانیه‌ای؛‏ در گام ۱۰ با آن قطع شدن درخواست‌ها را می‌آزماییم.
تابع log_messagelog را در stdout می‌نویسد؛‏ کوبرنتیز همین را با kubectl logs نشان می‌دهد.

گام ۲: Dockerfile؛‏ دستور ساختن image

فایل Dockerfile را در همان پوشه‌ی ~/shopify بسازید. در Dockerfile هر comment باید در خط جداگانه باشد؛‏ برای همین شماره‌ها بالای هر دستور آمده‌اند:

Dockerfile
# (1) base image: Python runtime on slim Debian
FROM python:3.13-slim
# (2) working directory inside the image
WORKDIR /app
# (3) copy our code into the image
COPY app.py .
# (4) build-time argument, set with --build-arg
ARG VERSION=dev
# (5) environment baked into the image
ENV PYTHONUNBUFFERED=1 PORT=8080 APP_VERSION=$VERSION
# (6) never run as root
USER 10001
# (7) document the listening port
EXPOSE 8080
# (8) exec form: python itself becomes PID 1
CMD ["python", "app.py"]
خطیعنی چه؟
(1)image پایه: Python 3.13 روی Debian کم‌حجم. هر image روی یک image دیگر ساخته می‌شود و لایه‌هایش را به ارث می‌برد.
(2)پوشه‌ی کاری داخل image؛‏ دستورهای بعدی در این پوشه اجرا می‌شوند.
(3)کپی کد از ماشین شما به داخل image. هر دستور COPY یک لایه‌ی تازه می‌سازد.
(4)مقداری که فقط هنگام build وجود دارد و با --build-arg VERSION=1.0 داده می‌شود.
(5)environment variableهای پیش‌فرض container. متغیر PYTHONUNBUFFERED باعث می‌شود log بی‌درنگ در stdout برسد.
(6)اجرای برنامه با کاربر غیر root (شماره‌ی ۱۰۰۰۱). اگر برنامه آسیب‌پذیر باشد،‏ مهاجم دسترسی root نمی‌گیرد (فصل ۱۴).
(7)مثل containerPort در کوبرنتیز فقط اطلاع‌رسانی است و portی باز نمی‌کند.
(8)دستور اجرا به شکل exec (فهرست JSON): خود برنامه‌ی python به PID 1 container تبدیل می‌شود و سیگنال‌ها مستقیم به آن می‌رسند. شکل shell (CMD python app.py) یک sh واسطه می‌سازد که سیگنال را به برنامه نمی‌رساند.

گام ۴: آماده کردن shop-api.yaml؛‏ port نام‌دار

برنامه‌ی API ما روی port شماره‌ی ۸۰۸۰ گوش می‌دهد و nginx روی ۸۰. اگر Service مستقیم به عدد ۸۰۸۰ اشاره کند،‏ در میانه‌ی rollout ترافیک به Podهای قدیمی nginx نمی‌رسد. راه تمیز،‏ port نام‌دار است: Service به نام port اشاره می‌کند و هر Pod عدد خودش را دارد. این تغییرها را در shop-api.yaml بدهید (هنوز با nginx):

shop-api.yaml (بخش‌های تغییرکرده)
# Deployment, inside the container
        ports:
        - name: http               # (1)
          containerPort: 80
        readinessProbe:
          httpGet:
            path: /
            port: http             # (2)
        livenessProbe:
          httpGet:
            path: /
            port: http
---
# Service
  ports:
  - port: 80
    targetPort: http               # (3)
خطیعنی چه؟
(1)نام port در container؛‏ حروف کوچک و حداکثر ۱۵ نویسه.
(2)probeها هم می‌توانند به نام port اشاره کنند.
(3)این Service ترافیک را به portی به نام http روی هر Pod می‌فرستد؛‏ هر عددی که آن Pod داشته باشد.
shell
kubectl apply -f shop-api.yaml
kubectl rollout status deployment/shop-api

انتظار: یک rollout کوتاه،‏ چون Pod template عوض شد؛‏ هنوز nginx اجرا می‌شود و Service بدون قطع کار می‌کند.

import signal
import threading
...

def stop(signum, frame):
    print("SIGTERM received: finishing in-flight requests", flush=True)
    threading.Thread(target=server.shutdown).start()


server = ThreadingHTTPServer(("", PORT), Handler)
server.daemon_threads = False  # let in-flight requests finish on shutdown
signal.signal(signal.SIGTERM, stop)
print(f"shop-api {VERSION} listening on :{PORT}", flush=True)
server.serve_forever()
server.server_close()  # waits for in-flight requests
print("bye", flush=True)

Containers

واژه‌ی container یک اصطلاح پربار (overloaded) است. هر بار که از آن استفاده می‌کنید،‏ بررسی کنید که مخاطب شما همان تعریف را در ذهن دارد یا نه (برای یک نفر container یعنی «process ایزوله‌شده با namespace و cgroup در Linux»،‏ برای دیگری «یک Docker container»،‏ و برای کسی دیگر «یک VM سبک»).

هر container که اجرا می‌کنید تکرارپذیر (repeatable) است؛‏ استانداردسازی حاصل از اینکه dependencyها داخل آن قرار گرفته‌اند یعنی هر جا که اجرایش کنید همان رفتار را می‌گیرید.

Containerهای برنامه‌ها را از زیرساخت host زیرین جدا (decouple) می‌کنند. این کار deployment را در محیط‌های مختلف cloud یا سیستم‌عامل‌های مختلف آسان‌تر می‌کند.

هر Node در یک cluster کوبرنتیز،‏ containerهایی را اجرا می‌کند که Podهای assign‌شده به آن Node را تشکیل می‌دهند. Containerهای داخل یک Pod به صورت co-located و co-scheduled روی یک Node اجرا می‌شوند؛‏ یعنی هرگز نیمی از containerهای یک Pod روی یک Node و نیم دیگر روی Node دیگری قرار نمی‌گیرند.

Container images

یک container image یک بسته‌ی نرم‌افزاری آماده‌ی اجرا (ready-to-run) است که همه‌ی چیزهای لازم برای اجرای یک برنامه را دارد: کد و هر runtime که لازم دارد،‏ libraryهای برنامه و سیستم،‏ و مقادیر پیش‌فرض برای هر تنظیم ضروری.

Containerها قرار است stateless و immutable باشند: نباید کد containerی را که در حال اجراست تغییر دهید. اگر یک برنامه‌ی containerized دارید و می‌خواهید تغییری بدهید،‏ روال درست این است که یک image جدید build کنید که تغییر را شامل شود و سپس container را دوباره بسازید تا از image به‌روزشده شروع شود.

Container runtimes

Container runtime جزء بنیادینی است که کوبرنتیز را قادر می‌سازد containerها را به شکل مؤثر اجرا کند. این جزء مسئول مدیریت اجرا و lifecycle containerها در محیط کوبرنتیز است.

کوبرنتیز از container runtimeهایی (نرم‌افزاری که containerها را روی Node اجرا می‌کند،‏ مثل containerd) مثل containerd و CRI-O و هر پیاده‌سازی دیگری از Kubernetes CRI (Container Runtime Interface) پشتیبانی می‌کند.

معمولاً می‌توانید اجازه دهید cluster شما container runtime پیش‌فرض را برای یک Pod انتخاب کند. اگر لازم است بیش از یک container runtime در cluster داشته باشید،‏ می‌توانید RuntimeClass را برای Pod مشخص کنید تا مطمئن شوید کوبرنتیز آن containerها را با یک container runtime خاص اجرا می‌کند.

همچنین می‌توانید از RuntimeClass (شیئی که تعیین می‌کند Pod با کدام پیکربندی container runtime اجرا شود) استفاده کنید تا Podهای مختلف را با همان container runtime ولی با تنظیمات متفاوت اجرا کنید.

توضیح تکمیلی: immutable بودن در عمل یعنی چه؟

فرض کنید در یک container در حال اجرا با kubectl exec یک فایل تنظیمات nginx را ویرایش می‌کنید و مشکل حل می‌شود. این تغییر فقط در لایه‌ی writable همان container وجود دارد. اولین restart (مثلاً به خاطر شکست liveness probe)،‏ اولین rescheduling به Node دیگر یا اولین rollout (فرایند deployment تدریجی نسخه‌ی جدید)،‏ آن را پاک می‌کند و مشکل برمی‌گردد. به همین دلیل کوبرنتیز کل مدل خود را روی «image جدید + ساخت دوباره‌ی container» بنا کرده است: Deployment با تغییر image در Pod template (الگویی که controller،‏ Podها را از روی آن می‌سازد) یک rolling update (جایگزینی تدریجی Podهای قدیمی با جدید،‏ بدون قطعی) انجام می‌دهد و Podهای جدید از image جدید ساخته می‌شوند (فصل ۴).

Images

یک container image داده‌ی binary است که یک برنامه و همه‌ی dependencyهای نرم‌افزاری آن را در بر می‌گیرد. Container imageها بسته‌های نرم‌افزاری اجرایی‌ای هستند که می‌توانند به صورت مستقل (standalone) اجرا شوند و فرض‌های بسیار مشخصی درباره‌ی محیط runtime خود دارند.

معمولاً یک container image از برنامه‌ی خود می‌سازید و آن را قبل از ارجاع دادن به آن در یک Pod،‏ به یک registry می‌فرستید (push می‌کنید).

این بخش طرح کلی مفهوم container image را ارائه می‌دهد.

نکته

اگر به دنبال container imageهای یک نسخه‌ی کوبرنتیز هستید (مثل v1.37،‏ آخرین minor release)،‏ به صفحه‌ی Download Kubernetes مراجعه کنید.

نام image (Image names)

Container imageها معمولاً نامی مثل pause،‏ example/mycontainer یا kube-apiserver دارند. Imageها می‌توانند hostname یک registry را هم شامل شوند؛‏ برای مثال fictional.registry.example/imagename،‏ و احتمالاً یک شماره‌ی port هم داشته باشند؛‏ برای مثال fictional.registry.example:10443/imagename.

اگر hostname یک registry را مشخص نکنید،‏ کوبرنتیز فرض می‌کند منظور شما Docker public registry است. می‌توانید این رفتار را با تنظیم یک default image registry در پیکربندی container runtime تغییر دهید.

پس از بخش نام image می‌توانید یک tag یا digest اضافه کنید (به همان شکلی که با دستورهایی مثل docker یا podman این کار را می‌کنید).‏ Tagها به شما اجازه می‌دهند نسخه‌های مختلف از یک سری image را شناسایی کنید. Digestها یک شناسه‌ی یکتا برای یک نسخه‌ی مشخص از image هستند. Digestها hash محتوای image هستند و immutable‌اند. Tagها را می‌توان جابه‌جا کرد تا به imageهای دیگری اشاره کنند،‏ اما digestها ثابت‌اند.

Image tagها از حروف کوچک و بزرگ لاتین،‏ ارقام،‏ underscore (‎_‎)،‏ نقطه (‎.‎) و خط تیره (‎-‎) تشکیل می‌شوند. یک tag می‌تواند حداکثر ۱۲۸ کاراکتر باشد و باید با الگوی regex زیر مطابقت داشته باشد: [a-zA-Z0-9_][a-zA-Z0-9._-]{0,127}. توضیحات بیشتر و regex validation را در OCI Distribution Specification ببینید. اگر tag مشخص نکنید،‏ کوبرنتیز فرض می‌کند منظور شما tag latest است.

Image digestها از یک الگوریتم hash (مثل sha256) و یک مقدار hash تشکیل می‌شوند. برای مثال: sha256:1ff6c18fbef2045af6b9c16bf034cc421a29027b800e4f9b68ae9b1cb3e9ae07. اطلاعات بیشتر درباره‌ی قالب digest را در OCI Image Specification ببینید.

توضیح تکمیلی: آناتومی کامل یک image reference

یک image reference کامل را می‌توان این‌طور تجزیه کرد:

  • اگر بخش اول پیش از ‎/‎ نه نقطه داشته باشد،‏ نه ‎:‎ (port) و localhost هم نباشد،‏ runtime آن را بخشی از repository روی Docker Hub تفسیر می‌کند؛‏ به همین دلیل example/mycontainer یعنی docker.io/example/mycontainer. برای imageهای رسمی تک‌بخشی مثل busybox هم پیشوند library/ اضافه می‌شود (خارج از مستندات رسمی،‏ رفتار استاندارد تجزیه‌ی نام در containerd و CRI-O).
  • وقتی هم tag و هم digest داده شود،‏ tag فقط نقش «مستندسازی برای انسان» دارد و pull بر اساس digest انجام می‌شود. این الگو در production بسیار مفید است: payments-api:v2.4.1@sha256:... هم خواناست و هم غیرقابل تغییر.

به‌روزرسانی imageها (Updating images)

وقتی برای نخستین بار یک Deployment،‏ StatefulSet،‏ Pod یا object دیگری که یک PodTemplate دارد می‌سازید و pull policy (قاعده‌ای که تعیین می‌کند kubelet کِی image را از registry بگیرد) را صریحاً مشخص نکرده‌اید،‏ به‌طور پیش‌فرض pull policy همه‌ی containerهای آن Pod روی IfNotPresent تنظیم می‌شود. این policy باعث می‌شود kubelet اگر image از قبل وجود داشته باشد،‏ pull را انجام ندهد.

این جمله‌ی مستندات ساده‌شده است: مقدار پیش‌فرض در واقع به tag و image digest بستگی دارد و برای image بدون tag یا با tag برابر latest،‏ مقدار Always است (بخش مقدار پیش‌فرض imagePullPolicy و شکل ۲-۴).

سیاست image pull (Image pull policy)

imagePullPolicy یک container و tag آن image،‏ هر دو روی اینکه چه زمانی kubelet تلاش می‌کند image مشخص‌شده را pull (دانلود) کند اثر می‌گذارند.

مقادیری که می‌توانید برای imagePullPolicy تنظیم کنید و اثر آن‌ها:

مقداررفتار
IfNotPresentimage فقط در صورتی pull می‌شود که از قبل به‌صورت محلی موجود نباشد.
Alwaysهر بار که kubelet یک container را راه می‌اندازد،‏ kubelet از container runtime درخواست می‌کند image را pull کند. container runtime با registry تماس می‌گیرد،‏ tag یا نام image را به یک digest resolve می‌کند و هر layerی را که به‌صورت محلی cache نشده دانلود می‌کند. اگر همه‌ی layerها از قبل موجود باشند،‏ container runtime از image cache‌شده استفاده می‌کند بدون اینکه دوباره دانلودش کند. خود kubelet بررسی نمی‌کند که image به‌صورت محلی cache شده یا نه؛‏ همیشه این کار را به container runtime واگذار می‌کند.
Neverkubelet تلاشی برای گرفتن image نمی‌کند. اگر image به هر شکلی از قبل به‌صورت محلی موجود باشد،‏ kubelet تلاش می‌کند container را start کند؛‏ در غیر این صورت startup شکست می‌خورد. برای جزئیات بیشتر pre-pulled images را ببینید.

معناشناسی caching در container runtime باعث می‌شود حتی imagePullPolicy: Always هم کارآمد باشد،‏ به شرطی که registry به‌طور قابل اعتماد در دسترس باشد. container runtime می‌تواند متوجه شود layerهای image از قبل روی Node وجود دارند و نیازی به دانلود دوباره‌ی آن‌ها نیست.

نکته

هنگام deploy کردن containerها در production باید از tag :latest پرهیز کنید،‏ چون ردیابی اینکه کدام نسخه از image در حال اجراست سخت‌تر است و rollback درست هم دشوارتر می‌شود.

به جای آن،‏ یک tag معنادار مثل v1.42.0 و/یا یک digest مشخص کنید.

برای اینکه مطمئن شوید Pod همیشه از همان نسخه‌ی container image استفاده می‌کند،‏ می‌توانید digest آن image را مشخص کنید؛‏ <image-name>:<tag> را با <image-name>@<digest> جایگزین کنید (برای مثال image@sha256:45b23dee08af5e43a7fea6c4cf9c25ccf269ee113168c19722f87876677c5cb2).

وقتی از image tag استفاده می‌کنید،‏ اگر registry کدی را که آن tag نمایندگی می‌کند تغییر دهد،‏ ممکن است با ترکیبی از Podهایی روبه‌رو شوید که کد قدیم و جدید را اجرا می‌کنند. یک image digest به‌طور یکتا یک نسخه‌ی مشخص از image را شناسایی می‌کند،‏ پس کوبرنتیز هر بار که containerی را با آن نام image و digest start می‌کند همان کد را اجرا می‌کند. مشخص کردن image با digest کدی را که اجرا می‌کنید pin می‌کند تا تغییری در registry نتواند به آن ترکیب نسخه‌ها منجر شود.

admission controllerهای third-party وجود دارند که Podها (و PodTemplateها) را هنگام ایجاد mutate می‌کنند،‏ به طوری که workload (برنامه‌ای که روی cluster اجرا می‌شود) در حال اجرا بر اساس image digest تعریف شود نه tag. این کار زمانی مفید است که بخواهید مطمئن شوید کل workload شما،‏ صرف‌نظر از هر تغییری که در tagهای registry رخ دهد،‏ همان کد را اجرا می‌کند.

توضیح تکمیلی: چرا tag قابل‌جابه‌جایی خطرناک است؟ (سناریوی ترکیب نسخه‌ها)

یک Deployment با ۶ replica و image shop/api:1.8 و imagePullPolicy: IfNotPresent دارید. Node A و B این image را دو هفته پیش pull کرده‌اند. امروز تیم CI به اشتباه یک build جدید را دوباره با همان tag ‎1.8‎ push می‌کند. فردا Node C اضافه می‌شود (مثلاً توسط Node autoscaling) و Podی روی آن schedule می‌شود. Node C image را pull می‌کند و محتوای جدید را می‌گیرد،‏ در حالی که A و B همچنان نسخه‌ی قدیم cache‌شده را اجرا می‌کنند. نتیجه: دو نسخه‌ی متفاوت کد با یک نام image.‏ digest این مسئله را ریشه‌کن می‌کند،‏ چون digest یعنی hash محتوا.

آزمایش عملی: pin کردن image با digest در یک Deployment

ابتدا digest یک tag را پیدا کنید (مثلاً با crane digest یا docker buildx imagetools inspect؛‏ این ابزارها خارج از مستندات رسمی هستند):

shell
docker buildx imagetools inspect nginx:1.27 | grep -m1 Digest
# Digest:    sha256:<64-hex-chars>

سپس Deployment را با ترکیب tag+digest بنویسید:

deploy-pinned.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        # tag for readability, digest for immutability
        image: nginx:1.27@sha256:<64-hex-chars>
        # with a digest, omitting this field also defaults to IfNotPresent
        imagePullPolicy: IfNotPresent
shell
kubectl apply -f deploy-pinned.yaml
kubectl get pods -l app=web -o jsonpath='{range .items[*]}{.status.containerStatuses[0].imageID}{"\n"}{end}' | sort -u

مقدار پیش‌فرض imagePullPolicy (Default image pull policy)

وقتی شما (یا یک controller) یک Pod جدید به API server ارسال می‌کنید،‏ cluster شما در شرایط مشخص فیلد imagePullPolicy را تنظیم می‌کند:

  • اگر فیلد imagePullPolicy را حذف کنید و digest آن container image را مشخص کنید،‏ imagePullPolicy به‌طور خودکار روی IfNotPresent تنظیم می‌شود.
  • اگر فیلد imagePullPolicy را حذف کنید و tag آن container image :latest باشد،‏ imagePullPolicy به‌طور خودکار روی Always تنظیم می‌شود.
  • اگر فیلد imagePullPolicy را حذف کنید و هیچ tagی برای container image مشخص نکنید،‏ imagePullPolicy به‌طور خودکار روی Always تنظیم می‌شود.
  • اگر فیلد imagePullPolicy را حذف کنید و برای container image یک tag غیر از :latest مشخص کنید،‏ imagePullPolicy به‌طور خودکار روی IfNotPresent تنظیم می‌شود.
نکته

مقدار imagePullPolicy یک container همیشه در زمانی که object برای نخستین بار ایجاد می‌شود تنظیم می‌شود و اگر tag یا digest آن image بعداً تغییر کند،‏ به‌روز نمی‌شود.

برای مثال،‏ اگر یک Deployment با imageی بسازید که tag آن نه :latest است و بعداً image آن Deployment را به tag :latest تغییر دهید،‏ فیلد imagePullPolicy به Always تغییر نمی‌کند. باید pull policy هر object را پس از ایجاد اولیه‌اش به‌صورت دستی تغییر دهید.

shell

kubectl set image deploy/web nginx=nginx:latest
kubectl get deploy web -o jsonpath='{.spec.template.spec.containers[0].imagePullPolicy}{"\n"}'

اجبار به image pull (Required image pull)

اگر می‌خواهید همیشه pull اجباری انجام شود،‏ می‌توانید یکی از کارهای زیر را انجام دهید:

  • imagePullPolicy آن container را روی Always تنظیم کنید.
  • imagePullPolicy را حذف کنید و از :latest به عنوان tag image استفاده کنید؛‏ کوبرنتیز هنگام ارسال Pod،‏ policy را روی Always تنظیم می‌کند.
  • imagePullPolicy و tag image را حذف کنید؛‏ کوبرنتیز هنگام ارسال Pod،‏ policy را روی Always تنظیم می‌کند.
  • admission controller (plugin در API server که درخواست را پیش از ذخیره بررسی یا تغییر می‌دهد) AlwaysPullImages را فعال کنید.
توضیح تکمیلی: AlwaysPullImages و امنیت

AlwaysPullImages برای هر Pod جدید imagePullPolicy را به Always تغییر می‌دهد. اهمیت امنیتی آن در بخش Use cases روشن می‌شود: بدون آن،‏ یک Pod در namespace (محدوده‌ی نام‌گذاری برای جدا کردن منابع در cluster) دیگر که هیچ credentialی ندارد می‌تواند با IfNotPresent از imageی استفاده کند که Pod دیگری با credential خودش قبلاً روی همان Node pull کرده است. از v1.35 قابلیت Ensure image pull credential verification به‌طور پیش‌فرض فعال است و همین مشکل را در سطح kubelet و بدون pull اجباری برای همه‌ی Podها حل می‌کند؛‏ جز برای imageهایی که با credential سطح Node pull شده‌اند و برای همه‌ی Podهای آن Node آزادند. هزینه‌ی AlwaysPullImages: وابستگی شدیدتر راه‌اندازی Pod به دسترس‌پذیری registry.

ImagePullBackOff

وقتی kubelet شروع به ساختن containerهای یک Pod با استفاده از container runtime می‌کند،‏ ممکن است container به خاطر ImagePullBackOff در وضعیت Waiting باشد.

وضعیت ImagePullBackOff یعنی یک container نتوانسته start شود چون کوبرنتیز نتوانسته container image را pull کند (به دلایلی مثل نام image نامعتبر،‏ یا pull کردن از یک private registry بدون imagePullSecret). بخش BackOff نشان می‌دهد که کوبرنتیز به تلاش برای pull کردن image ادامه می‌دهد،‏ با یک تأخیر back-off افزایشی.

کوبرنتیز تأخیر بین هر تلاش را افزایش می‌دهد تا به یک سقف compile‌شده (compiled-in) برسد که ۳۰۰ ثانیه (۵ دقیقه) است.

image pull به تفکیک RuntimeClass (Image pull per runtime class)

وضعیت قابلیت: Kubernetes v1.29 [alpha] (به‌طور پیش‌فرض غیرفعال؛‏ feature gate: RuntimeClassInImageCriApi)

کوبرنتیز پشتیبانی alpha برای انجام image pull بر اساس RuntimeClass یک Pod دارد.

اگر feature gate (کلید روشن و خاموش کردن قابلیت‌های جدید یا آزمایشی) RuntimeClassInImageCriApi را فعال کنید،‏ kubelet به جای اینکه فقط با نام image یا digest به container imageها ارجاع دهد،‏ با یک tuple از نام image و runtime handler به آن‌ها ارجاع می‌دهد. container runtime شما ممکن است رفتار خود را بر اساس runtime handler انتخاب‌شده تطبیق دهد. pull کردن image بر اساس runtime class برای containerهای مبتنی بر VM،‏ مثل Windows Hyper-V containerها،‏ مفید است.

توضیح تکمیلی: یک image،‏ دو موجودیت

در runtimeهای مبتنی بر VM (مثلاً Kata Containers یا Hyper-V isolation) ممکن است image لازم باشد در قالب یا محل دیگری آماده شود (مثلاً داخل guest VM). با tuple «image + handler»،‏ runtime می‌داند یک image یکسان برای handler معمولی و handler مبتنی بر VM دو موجودیت متفاوت است. RuntimeClass را در بخش RuntimeClass همین فصل می‌بینیم.

pull سریالی و موازی imageها (Serial and parallel image pulls)

به‌طور پیش‌فرض،‏ kubelet imageها را به صورت سریالی pull می‌کند. به عبارت دیگر،‏ kubelet در هر لحظه فقط یک درخواست image pull به image service می‌فرستد. درخواست‌های image pull دیگر باید صبر کنند تا درخواست در حال پردازش تمام شود.

Nodeها تصمیم‌های image pull را به صورت مستقل از هم می‌گیرند. حتی وقتی از image pull سریالی استفاده می‌کنید،‏ دو Node مختلف می‌توانند یک image یکسان را به صورت موازی pull کنند.

اگر می‌خواهید image pull موازی را فعال کنید،‏ می‌توانید فیلد serializeImagePulls را در kubelet configuration روی false قرار دهید. با false بودن serializeImagePulls،‏ درخواست‌های image pull بلافاصله به image service فرستاده می‌شوند و چند image همزمان pull می‌شوند.

هنگام فعال کردن image pull موازی،‏ مطمئن شوید image service در container runtime شما می‌تواند image pullهای موازی را مدیریت کند.

kubelet هرگز چند image را برای یک Pod به‌صورت موازی pull نمی‌کند. برای مثال،‏ اگر Podی دارید که یک init container و یک application container دارد،‏ image pull برای این دو container موازی نمی‌شود. اما اگر دو Pod دارید که از imageهای مختلف استفاده می‌کنند و قابلیت parallel image pull فعال است،‏ kubelet imageها را برای آن دو Pod مختلف به صورت موازی pull می‌کند.

سقف pullهای موازی (Maximum parallel image pulls)

وضعیت قابلیت: Kubernetes v1.35 [stable]

وقتی serializeImagePulls روی false است،‏ kubelet به‌طور پیش‌فرض هیچ محدودیتی روی حداکثر تعداد imageهایی که همزمان pull می‌شوند ندارد. اگر می‌خواهید تعداد image pullهای موازی را محدود کنید،‏ می‌توانید فیلد maxParallelImagePulls را در kubelet configuration تنظیم کنید. با مقدار n برای maxParallelImagePulls،‏ فقط n image می‌توانند همزمان pull شوند و هر image pull فراتر از n باید صبر کند تا حداقل یکی از image pullهای در حال انجام تمام شود.

محدود کردن تعداد image pullهای موازی،‏ وقتی image pull موازی فعال است،‏ جلوی این را می‌گیرد که pull کردن image پهنای باند شبکه یا disk I/O بیش از حد مصرف کند.

می‌توانید maxParallelImagePulls را روی یک عدد مثبت بزرگ‌تر یا مساوی ۱ تنظیم کنید. اگر maxParallelImagePulls را بزرگ‌تر یا مساوی ۲ قرار دهید،‏ باید serializeImagePulls را روی false تنظیم کنید. kubelet با یک تنظیم نامعتبر maxParallelImagePulls start نمی‌شود.

multi-architecture imageها و image index (Multi-architecture images with image indexes)

علاوه بر ارائه‌ی imageهای binary،‏ یک container registry می‌تواند یک container image index هم ارائه دهد. یک image index می‌تواند به چندین image manifest برای نسخه‌های مخصوص معماری (architecture-specific) یک container اشاره کند. ایده این است که برای یک image یک نام داشته باشید (برای مثال pause،‏ example/mycontainer،‏ kube-apiserver) و به سیستم‌های مختلف اجازه دهید image binary مناسب برای معماری ماشینی که استفاده می‌کنند را بگیرند.

پروژه‌ی کوبرنتیز معمولاً container imageهای releaseهای خود را با نام‌هایی می‌سازد که پسوند -$(ARCH) دارند. برای سازگاری با گذشته (backward compatibility)،‏ imageهای قدیمی‌تر را با پسوند تولید کنید. برای مثال،‏ imageی با نام pause یک multi-architecture image خواهد بود که manifestهای همه‌ی معماری‌های پشتیبانی‌شده را دارد،‏ در حالی که pause-amd64 یک نسخه‌ی backward-compatible برای پیکربندی‌های قدیمی‌تر یا فایل‌های YAML با نام‌های image hardcode‌شده‌ی دارای پسوند است.

توضیح تکمیلی: image index در عمل

ساختار یک image index (خلاصه‌شده‌ی قالب OCI):

    { "digest": "sha256:bbb...", "platform": { "architecture": "arm64", "os": "linux" } }

در یک cluster مختلط (مثلاً Nodeهای amd64 و Nodeهای arm64 ارزان‌تر)،‏ Deployment با یک نام image روی هر دو نوع Node کار می‌کند،‏ چون container runtime هر Node manifest مناسب معماری خودش را انتخاب می‌کند. اگر image فقط برای amd64 ساخته شده باشد،‏ Pod روی Node arm64 معمولاً با خطای exec format error در logها crash می‌کند یا pull با پیام «no matching manifest for linux/arm64» شکست می‌خورد (خارج از مستندات رسمی). نکته‌ی digest:‏ digest خود index با digest هر manifest فرق دارد؛‏ اگر digest index را pin کنید،‏ همچنان روی همه‌ی معماری‌ها کار می‌کنید.

استفاده از private registry (Using a private registry)

Private registryها ممکن است برای کشف و/یا pull کردن imageها به authentication نیاز داشته باشند. Credentialها را می‌توان به چند روش فراهم کرد:

  • مشخص کردن imagePullSecrets هنگام تعریف یک Pod
    • فقط Podهایی که کلیدهای خود را فراهم می‌کنند می‌توانند به private registry دسترسی داشته باشند.
  • پیکربندی Nodeها برای authentication به یک private registry
    • همه‌ی Podها می‌توانند از هر private registry پیکربندی‌شده بخوانند.
    • نیاز به پیکربندی Node توسط مدیر cluster دارد.
  • استفاده از یک plugin از نوع kubelet credential provider (plugin که kubelet برای گرفتن پویای credential registry اجرا می‌کند) برای گرفتن پویای credentialهای private registry
    • kubelet را می‌توان طوری پیکربندی کرد که از credential provider exec plugin برای private registry مربوطه استفاده کند.
  • Pre-pulled Images
    • همه‌ی Podها می‌توانند از هر image cache‌شده روی یک Node استفاده کنند.
    • برای راه‌اندازی به دسترسی root روی همه‌ی Nodeها نیاز دارد.
  • pluginهای مخصوص vendor یا محلی
    • اگر از یک پیکربندی سفارشی Node استفاده می‌کنید،‏ شما (یا cloud provider شما) می‌توانید مکانیزم خود را برای authentication Node به container registry پیاده‌سازی کنید.

دستورالعمل‌های مشخص برای تنظیم credentialها به container runtime و registry که انتخاب کرده‌اید بستگی دارد. برای دقیق‌ترین اطلاعات باید به مستندات راه‌حل خود مراجعه کنید.

kubelet credential provider برای pull با authentication (Kubelet credential provider for authenticated image pulls)

می‌توانید kubelet را طوری پیکربندی کنید که یک plugin binary را برای گرفتن پویای credentialهای registry برای یک container image فراخوانی کند. این مستحکم‌ترین و همه‌کاره‌ترین روش برای گرفتن credentialهای private registryها است،‏ اما برای فعال شدن به پیکربندی در سطح kubelet نیاز دارد.

این تکنیک به‌ویژه برای اجرای static Podهایی (Podی که kubelet مستقیم از فایلی روی Node اجرا می‌کند،‏ بدون API server) مفید است که به container imageهای میزبانی‌شده در یک private registry نیاز دارند. استفاده از یک ServiceAccount (هویتی که processهای داخل Pod با آن با API server کار می‌کنند) یا یک Secret برای فراهم کردن credentialهای private registry در spec یک static Pod ممکن نیست،‏ چون spec آن نمی‌تواند به منابع دیگر API ارجاع داشته باشد.

برای جزئیات بیشتر Configure a kubelet image credential provider را ببینید. خلاصه‌ی کامل آن task در ادامه آمده است.

توضیح تکمیلی: Configure a kubelet image credential provider (از task مربوطه)

وضعیت قابلیت: Kubernetes v1.26 [stable]

از Kubernetes v1.20،‏ kubelet می‌تواند credentialهای یک container image registry را با استفاده از exec pluginها به صورت پویا بگیرد. kubelet و exec plugin از طریق stdio (stdin،‏ stdout و stderr) با استفاده از APIهای نسخه‌دار کوبرنتیز با هم ارتباط برقرار می‌کنند. این pluginها (جزء قابل‌اتصالی که رفتار سیستم را گسترش می‌دهد) به kubelet اجازه می‌دهند به جای ذخیره‌ی credentialهای ایستا روی disk،‏ credential یک container registry را به صورت پویا درخواست کند. برای مثال،‏ plugin ممکن است با یک metadata server محلی صحبت کند تا credentialهای کوتاه‌عمر برای imageی که kubelet در حال pull کردن آن است بگیرد.

اگر یکی از موارد زیر صادق است،‏ ممکن است به این قابلیت علاقه‌مند باشید:

  • برای گرفتن اطلاعات authentication یک registry به فراخوانی API یک cloud provider نیاز است.
  • Credentialها زمان انقضای کوتاهی دارند و لازم است مرتباً credential جدید درخواست شود.
  • ذخیره‌ی credentialهای registry روی disk یا در imagePullSecrets قابل قبول نیست.

token مربوط به ServiceAccount برای image pull (Service Account Token for Image Pulls) — وضعیت قابلیت: Kubernetes v1.34 [beta] (به‌طور پیش‌فرض فعال؛‏ feature gate: KubeletServiceAccountTokenForCredentialProviders). از Kubernetes v1.33،‏ kubelet را می‌توان طوری پیکربندی کرد که یک service account token متصل (bound) به Podی که image pull برای آن انجام می‌شود را به credential provider plugin بفرستد. این کار به plugin اجازه می‌دهد token را با credential دسترسی به image registry مبادله کند. برای فعال کردن،‏ feature gate KubeletServiceAccountTokenForCredentialProviders باید روی kubelet فعال باشد و فیلد tokenAttributes در فایل CredentialProviderConfig برای plugin تنظیم شود. فیلد tokenAttributes اطلاعاتی درباره‌ی service account token ارسالی به plugin دارد،‏ شامل audience موردنظر token و اینکه آیا plugin نیاز دارد Pod یک service account داشته باشد. موارد استفاده: (۱) عدم نیاز به هویت kubelet/Node برای pull از registry؛‏ (۲) اجازه به workloadها برای pull بر اساس هویت runtime خودشان بدون Secretهای بلندمدت/ذخیره‌شده.

پیش از شروع: Nodeهایی که از kubelet credential provider plugin پشتیبانی کنند (در کوبرنتیز 1.37 موجود است؛‏ v1.24 و v1.25 آن را به صورت beta و فعال به‌طور پیش‌فرض داشتند). اگر pluginی را پیکربندی می‌کنید که service account token لازم دارد،‏ Nodeها باید v1.33 یا بالاتر باشند و feature gate KubeletServiceAccountTokenForCredentialProviders روی kubelet فعال باشد. همچنین یک پیاده‌سازی کارا از credential provider exec plugin لازم است (خودتان بسازید یا از plugin ارائه‌شده توسط cloud provider استفاده کنید).

نصب plugin روی Nodeها: credential provider plugin یک binary اجرایی است که kubelet اجرایش می‌کند. مطمئن شوید binary plugin روی همه‌ی Nodeهای cluster در یک دایرکتوری مشخص وجود دارد؛‏ این دایرکتوری بعداً در flagهای kubelet لازم است.

پیکربندی kubelet:‏ kubelet انتظار دارد دو flag تنظیم شوند:

  • --image-credential-provider-config — مسیر فایل پیکربندی credential provider plugin.
  • --image-credential-provider-bin-dir — مسیر دایرکتوری binaryهای credential provider plugin.

فایل پیکربندی‌ای که به --image-credential-provider-config داده می‌شود توسط kubelet خوانده می‌شود تا مشخص کند کدام exec pluginها برای کدام container imageها فراخوانی شوند. مثال زیر پیکربندی‌ای است که اگر از ECR-based plugin استفاده کنید ممکن است به کار ببرید:

فیلد providers فهرستی از pluginهای فعال kubelet است. هر entry چند فیلد اجباری دارد:

  • name: نام plugin که باید با نام binary اجرایی موجود در دایرکتوری داده‌شده به --image-credential-provider-bin-dir یکی باشد.
  • matchImages: فهرستی از رشته‌ها برای تطبیق با imageها تا مشخص شود آیا این provider باید فراخوانی شود.
  • defaultCacheDuration: مدت پیش‌فرضی که kubelet credentialها را در memory cache می‌کند،‏ اگر plugin مدت cache را مشخص نکرده باشد.
  • apiVersion: نسخه‌ی API که kubelet و exec plugin هنگام ارتباط استفاده می‌کنند.

به هر credential provider می‌توان args و environment variableها اختیاری هم داد؛‏ برای اینکه بدانید یک plugin چه args و env لازم دارد به پیاده‌سازان آن مراجعه کنید.

اگر از feature gate KubeletServiceAccountTokenForCredentialProviders استفاده می‌کنید و با تنظیم tokenAttributes plugin را برای استفاده از service account token پیکربندی می‌کنید،‏ این فیلدها اجباری‌اند:

  • serviceAccountTokenAudience: audience موردنظر projected service account token؛‏ نمی‌تواند رشته‌ی خالی باشد. وقتی feature gate ServiceAccountNodeAudienceRestriction فعال است،‏ kubelet باید برای درخواست token برای این audience مجاز باشد؛‏ در غیر این صورت credential provider فراخوانی نمی‌شود. باید با RBAC به گروه system:nodes اجازه‌ی استفاده از verb request-serviceaccounts-token-audience روی این audience را بدهید (فصل ۱۴).
  • cacheType: نوع کلید cache برای credentialهای برگشتی از plugin وقتی service account token استفاده می‌شود. محافظه‌کارانه‌ترین گزینه Token است،‏ یعنی kubelet credentialها را به ازای هر token cache می‌کند؛‏ اگر طول عمر credential برگشتی به طول عمر service account token محدود است همین را بگذارید. اگر منطق plugin فقط به service account بستگی دارد و نه claimهای مخصوص Pod،‏ می‌تواند ServiceAccount باشد؛‏ در این حالت kubelet به ازای هر service account cache می‌کند. وقتی از این استفاده کنید که credential برای همه‌ی Podهای با یک service account معتبر است.
  • requireServiceAccount: آیا plugin نیاز دارد Pod یک service account داشته باشد. اگر true باشد،‏ kubelet فقط وقتی Pod یک service account دارد plugin را فراخوانی می‌کند. اگر false باشد،‏ kubelet حتی بدون service account هم plugin را فراخوانی می‌کند و token را در CredentialProviderRequest قرار نمی‌دهد. این برای pluginهایی مفید است که برای Podهای بدون service account (مثل static Podها) image pull می‌کنند.

تطبیق image (Configure image matching): فیلد matchImages هر credential provider را kubelet برای تعیین اینکه آیا plugin برای یک image خاص فراخوانی شود یا نه استفاده می‌کند. هر entry یک الگوی image است که می‌تواند اختیاراً port و path داشته باشد. globها را می‌توان در domain استفاده کرد،‏ اما نه در port یا path.‏ globها به صورت subdomain مثل *.k8s.io یا k8s.*.io و top-level domain مثل k8s.* پشتیبانی می‌شوند. تطبیق subdomainهای جزئی مثل app*.k8s.io هم پشتیبانی می‌شود. هر glob فقط یک بخش subdomain را تطبیق می‌دهد،‏ پس *.io با *.k8s.io تطبیق ندارد. تطبیق بین نام image و یک entry از matchImages وقتی برقرار است که همه‌ی موارد زیر درست باشند:

  • هر دو تعداد یکسانی بخش domain داشته باشند و هر بخش تطبیق کند.
  • URL path الگوی matchImages پیشوند URL path image هدف باشد.
  • اگر matchImages یک port دارد،‏ port در image هم باید تطبیق کند.

نمونه‌هایی از الگوهای matchImages: 123456789.dkr.ecr.us-east-1.amazonaws.com،‏ *.azurecr.io،‏ gcr.io،‏ *.*.registry.io،‏ foo.registry.io:8080/path.

تفسیر config.json (Interpretation of config.json)

تفسیر config.json بین پیاده‌سازی اصلی Docker و تفسیر کوبرنتیز متفاوت است. در Docker،‏ کلیدهای auths فقط می‌توانند URLهای ریشه (root) را مشخص کنند،‏ در حالی که کوبرنتیز علاوه بر آن URLهای glob و مسیرهای prefix-matched را هم مجاز می‌داند. تنها محدودیت این است که الگوهای glob (‎*‎) باید برای هر subdomain نقطه (‎.‎) را شامل شوند. تعداد subdomainهای تطبیق‌یافته باید با تعداد الگوهای glob (‎*.‎) برابر باشد،‏ برای مثال:

  • *.kubernetes.io با kubernetes.io تطبیق ندارد،‏ اما با abc.kubernetes.io تطبیق دارد.
  • *.*.kubernetes.io با abc.kubernetes.io تطبیق ندارد،‏ اما با abc.def.kubernetes.io تطبیق دارد.
  • prefix.*.io با prefix.kubernetes.io تطبیق دارد.
  • *-good.kubernetes.io با prefix-good.kubernetes.io تطبیق دارد.

این یعنی یک config.json مثل زیر معتبر است:

config.json
{
    "auths": {
        "my-registry.example/images": { "auth": "…" },
        "*.my-registry.example/images": { "auth": "…" }
    }
}

عملیات image pull،‏ credentialها را برای هر الگوی معتبر به CRI container runtime می‌فرستد. برای مثال،‏ نام‌های container image زیر با موفقیت تطبیق می‌یابند:

  • my-registry.example/images
  • my-registry.example/images/my-image
  • my-registry.example/images/another-image
  • sub.my-registry.example/images/my-image

اما این نام‌های container image تطبیق نمی‌یابند:

  • a.sub.my-registry.example/images/my-image
  • a.b.sub.my-registry.example/images/my-image

kubelet برای هر credential پیدا‌شده،‏ image pull را به‌ترتیب (sequentially) انجام می‌دهد. این یعنی چند entry در config.json برای pathهای مختلف هم ممکن است:

config.json
{
    "auths": {
        "my-registry.example/images": {
            "auth": "…"
        },
        "my-registry.example/images/subpath": {
            "auth": "…"
        }
    }
}

حالا اگر یک container image my-registry.example/images/subpath/my-image را برای pull مشخص کند،‏ kubelet در صورتی که یکی از منابع authentication شکست بخورد،‏ تلاش می‌کند با هر دو آن را دانلود کند.

کاربرد production: در یک registry مشترک (مثلاً Harbor) که هر تیم یک project دارد،‏ می‌توانید در یک Secret چند credential با pathهای متفاوت داشته باشید؛‏ kubelet به ترتیب همه‌ی credentialهای منطبق را امتحان می‌کند.

imageهای از پیش pull‌شده (Pre-pulled images)

نکته

این روش در صورتی مناسب است که بتوانید پیکربندی Node را کنترل کنید. اگر cloud provider شما Nodeها را مدیریت می‌کند و آن‌ها را به‌طور خودکار جایگزین می‌کند،‏ به‌طور قابل اعتماد کار نخواهد کرد.

به‌طور پیش‌فرض،‏ kubelet تلاش می‌کند هر image را از registry مشخص‌شده pull کند. اما اگر property imagePullPolicy یک container روی IfNotPresent یا Never تنظیم شده باشد،‏ از یک image محلی استفاده می‌شود (به ترتیب به صورت ترجیحی یا انحصاری).

اگر می‌خواهید به جای registry authentication به pre-pulled imageها تکیه کنید،‏ باید مطمئن شوید همه‌ی Nodeهای cluster همان pre-pulled imageها را دارند.

این روش می‌تواند برای preload کردن برخی imageها برای سرعت،‏ یا به عنوان جایگزینی برای authentication (تشخیص هویت درخواست‌دهنده) به یک private registry استفاده شود.

مشابه استفاده از kubelet credential provider،‏ pre-pulled imageها برای راه‌اندازی static Podهایی که به imageهای میزبانی‌شده در یک private registry وابسته‌اند هم مناسب‌اند.

نکته

وضعیت قابلیت: Kubernetes v1.35 [beta] (به‌طور پیش‌فرض فعال؛‏ feature gate: KubeletEnsureSecretPulledImages)

دسترسی به pre-pulled imageها ممکن است بر اساس image pull credential verification مجاز شمرده شود.

image را روی VM مربوط به k3s با Docker بسازید و مستقیم به containerd همراه k3s بدهید؛‏ همان کاری که در گام ۶ آزمایش شاپیفای کردید:

بررسی credential برای imageهای موجود روی Node (Ensure image pull credential verification)

وضعیت قابلیت: Kubernetes v1.35 [beta] (به‌طور پیش‌فرض فعال؛‏ feature gate: KubeletEnsureSecretPulledImages)

اگر feature gate KubeletEnsureSecretPulledImages برای cluster شما فعال باشد،‏ کوبرنتیز credentialهای image را برای هر imageی که برای pull شدن به credential نیاز دارد validate می‌کند،‏ حتی اگر آن image از قبل روی Node موجود باشد. این validation تضمین می‌کند imageهایی در درخواست یک Pod که با credentialهای ارائه‌شده با موفقیت pull نشده‌اند،‏ باید دوباره از registry pull شوند. علاوه بر این،‏ image pullهایی که از همان credentialهایی استفاده می‌کنند که قبلاً به یک image pull موفق منجر شده‌اند،‏ نیازی به pull دوباره از registry ندارند و به جای آن به صورت محلی و بدون دسترسی به registry validate می‌شوند (به شرطی که image به صورت محلی موجود باشد). این رفتار با فیلد imagePullCredentialsVerificationPolicy در Kubelet configuration کنترل می‌شود.

این پیکربندی کنترل می‌کند که اگر image از قبل روی Node موجود است،‏ چه زمانی credentialهای image pull باید تأیید شوند:

مقداررفتار
NeverVerifyرفتار غیرفعال بودن این feature gate را تقلید می‌کند. اگر image به صورت محلی موجود باشد،‏ credentialهای image pull تأیید نمی‌شوند.
NeverVerifyPreloadedImagesimageهایی که بیرون از kubelet pull شده‌اند تأیید نمی‌شوند،‏ اما همه‌ی imageهای دیگر credentialشان تأیید می‌شود. این رفتار پیش‌فرض است.
NeverVerifyAllowListedImagesimageهایی که بیرون از kubelet pull شده‌اند و در preloadedImagesVerificationAllowlist مشخص‌شده در kubelet config آمده‌اند،‏ تأیید نمی‌شوند.
AlwaysVerifyهمه‌ی imageها قبل از استفاده،‏ credentialشان تأیید می‌شود.

این verification روی pre-pulled images،‏ imageهای pull‌شده با Secretهای سطح Node و imageهای pull‌شده با Secretهای سطح Pod اعمال می‌شود.

نکته

در صورت rotation credential،‏ credentialهایی که قبلاً برای pull کردن image استفاده شده‌اند همچنان بدون نیاز به دسترسی به registry تأیید می‌شوند. credentialهای جدید یا rotate‌شده نیاز دارند image دوباره از registry pull شود.

نخستین فعال‌سازی KubeletEnsureSecretPulledImages (Enabling KubeletEnsureSecretPulledImages for the first time)

وقتی KubeletEnsureSecretPulledImages برای نخستین بار فعال می‌شود،‏ چه با upgrade کردن kubelet و چه با فعال کردن صریح feature،‏ اگر kubelet در آن لحظه به imageهایی دسترسی داشته باشد،‏ همه‌ی آن‌ها pre-pulled در نظر گرفته می‌شوند. این اتفاق می‌افتد چون در این حالت kubelet هیچ سابقه‌ای (record) از pull شدن imageها ندارد. kubelet فقط زمانی می‌تواند شروع به ساختن image pull recordها کند که یک image برای نخستین بار pull شود.

اگر این موضوع نگران‌کننده است،‏ توصیه می‌شود قبل از فعال کردن feature،‏ Nodeها را از همه‌ی imageهایی که نباید pre-pulled در نظر گرفته شوند پاک کنید.

توجه کنید که حذف دایرکتوری نگه‌دارنده‌ی image pulled recordها هم در restart شدن kubelet همین اثر را دارد؛‏ به‌ویژه همه‌ی imageهایی که فعلاً توسط container runtime روی Nodeها cache شده‌اند،‏ pre-pulled در نظر گرفته می‌شوند.

توضیح تکمیلی: مسئله‌ای که این feature حل می‌کند

Namespace team-a با Secret خودش image خصوصی corp.example/team-a/billing:v3 را روی Node-1 pull می‌کند. Pod از namespace team-b که هیچ credentialی برای آن image ندارد،‏ با imagePullPolicy: IfNotPresent همان image را روی Node-1 درخواست می‌کند. بدون این feature (یا با NeverVerify)،‏ image موجود است و بدون هیچ بررسی‌ای اجرا می‌شود؛‏ یعنی نشت image خصوصی بین tenantها. با KubeletEnsureSecretPulledImages و policy پیش‌فرض NeverVerifyPreloadedImages،‏ kubelet می‌داند این image با credential دیگری pull شده؛‏ پس Pod تیم b باید image را با credential خودش از registry pull کند و چون credential ندارد،‏ به ErrImagePull می‌رسد. این همان تضمینی است که قبلاً فقط AlwaysPullImages می‌داد،‏ اما بدون تحمیل pull کامل به همه‌ی Podها. استثنا: imageی که با credential سطح Node (یا بدون credential) pull شده،‏ در سابقه‌ی kubelet «در دسترس همه‌ی Podهای Node» ثبت می‌شود.

KubeletConfiguration (بخشی)
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
imagePullCredentialsVerificationPolicy: NeverVerifyAllowListedImages
preloadedImagesVerificationAllowlist:
- registry.k8s.io/pause
- corp.example/platform/node-agent

ساختن Secret با پیکربندی Docker (Creating a Secret with a Docker config)

برای authentication به registry باید username،‏ password registry و آدرس ایمیل client،‏ و همچنین hostname آن را بدانید. دستور زیر را اجرا کنید و placeholderها را با مقادیر مناسب جایگزین کنید:

shell
kubectl create secret docker-registry <name> \
  --docker-server=<docker-registry-server> \
  --docker-username=<docker-user> \
  --docker-password=<docker-password> \
  --docker-email=<docker-email>

اگر از قبل یک فایل Docker credentials دارید،‏ به جای دستور بالا می‌توانید فایل credentialها را به عنوان یک کوبرنتیز Secret import کنید. بخش Create a Secret based on existing Docker credentials نحوه‌ی انجام آن را توضیح می‌دهد.

این کار به‌ویژه وقتی از چند private container registry استفاده می‌کنید مفید است،‏ چون kubectl create secret docker-registry یک Secret می‌سازد که فقط با یک private registry کار می‌کند.

نکته

Podها فقط می‌توانند به image pull secretهای namespace خودشان ارجاع دهند،‏ پس این فرایند باید یک بار برای هر namespace انجام شود.

ارجاع به imagePullSecrets در Pod (Referring to imagePullSecrets on a Pod)

حالا می‌توانید Podهایی بسازید که با اضافه کردن بخش imagePullSecrets به تعریف Pod،‏ به آن Secret ارجاع دهند. هر آیتم در آرایه‌ی imagePullSecrets فقط می‌تواند به یک Secret در همان namespace ارجاع دهد.

برای مثال:

shell
cat <<EOF > pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: foo
  namespace: awesomeapps
spec:
  containers:
    - name: foo
      image: janedoe/awesomeapp:v1
  imagePullSecrets:
    - name: myregistrykey
EOF

cat <<EOF >> ./kustomization.yaml
resources:
- pod.yaml
EOF

این کار باید برای هر Podی که از یک private registry استفاده می‌کند انجام شود.

اما می‌توانید با مشخص کردن بخش imagePullSecrets در یک resource از نوع ServiceAccount این فرایند را خودکار کنید. برای دستورالعمل کامل Add ImagePullSecrets to a Service Account را ببینید.

می‌توانید این روش را همراه با یک .docker/config.json مخصوص هر Node استفاده کنید. credentialها با هم merge می‌شوند.

افزودن imagePullSecrets به ServiceAccount (Add ImagePullSecrets to a service account)

ابتدا یک imagePullSecret بسازید (همان‌طور که در Specifying ImagePullSecrets on a Pod آمد) و بررسی کنید ساخته شده است:

shell
kubectl create secret docker-registry myregistrykey --docker-server=<registry name> \
        --docker-username=DUMMY_USERNAME --docker-password=DUMMY_DOCKER_PASSWORD \
        --docker-email=DUMMY_DOCKER_EMAIL
kubectl get secrets myregistrykey
output
NAME             TYPE                              DATA    AGE
myregistrykey    kubernetes.io/.dockerconfigjson   1       1d

سپس ServiceAccount پیش‌فرض namespace را طوری تغییر دهید که از این Secret به عنوان imagePullSecret استفاده کند:

shell
kubectl patch serviceaccount default -p '{"imagePullSecrets": [{"name": "myregistrykey"}]}'

همین نتیجه را می‌توانید با ویرایش دستی object به دست آورید (kubectl edit serviceaccount/default). ویرایشگر پیکربندی‌ای شبیه این را باز می‌کند:

ServiceAccount (قبل از ویرایش)
apiVersion: v1
kind: ServiceAccount
metadata:
  creationTimestamp: 2021-07-07T22:02:39Z
  name: default
  namespace: default
  resourceVersion: "243024"
  uid: 052fb0f4-3d50-11e5-b066-42010af0d7b6

در ویرایشگر خط کلید resourceVersion را حذف کنید،‏ خطوط imagePullSecrets: را اضافه کنید و ذخیره کنید. مقدار uid را همان‌طور که هست نگه دارید. پس از تغییرات،‏ ServiceAccount شبیه این است:

ServiceAccount (بعد از ویرایش)
apiVersion: v1
kind: ServiceAccount
metadata:
  creationTimestamp: 2021-07-07T22:02:39Z
  name: default
  namespace: default
  uid: 052fb0f4-3d50-11e5-b066-42010af0d7b6
imagePullSecrets:
  - name: myregistrykey

حالا وقتی یک Pod جدید در namespace جاری با ServiceAccount پیش‌فرض ساخته شود،‏ فیلد spec.imagePullSecrets آن به صورت خودکار تنظیم می‌شود:

shell
kubectl run nginx --image=<registry name>/nginx --restart=Never

output
myregistrykey
توضیح تکمیلی: الگوی production برای private registry با ServiceAccount

در یک cluster واقعی نمی‌خواهید هر تیم در هر Deployment به یاد داشته باشد imagePullSecrets را بنویسد. الگوی رایج:

  1. برای registry یک robot account فقط‌خواندنی (pull-only) بسازید،‏ نه حساب شخصی یک کارمند.
  2. Secret را در هر namespace برنامه بسازید (با ابزاری مثل External Secrets Operator یا یک controller کپی‌کننده؛‏ خارج از مستندات رسمی).
  3. یک ServiceAccount اختصاصی برای برنامه بسازید و Secret را روی آن بگذارید؛‏ Deployment فقط serviceAccountName را ارجاع می‌دهد.
prod-registry.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payments-api
  namespace: payments
imagePullSecrets:
- name: harbor-pull          # kubernetes.io/dockerconfigjson Secret in this namespace
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      serviceAccountName: payments-api
      containers:
      - name: api
        image: harbor.corp.example/payments/api:v2.4.1@sha256:<digest>
        ports:
        - containerPort: 8080
shell
kubectl -n payments create secret docker-registry harbor-pull \
  --docker-server=harbor.corp.example \
  --docker-username='robot$payments-pull' \
  --docker-password="$(cat /secure/robot-token)"
kubectl apply -f prod-registry.yaml
kubectl -n payments get pod -l app=payments-api -o jsonpath='{.items[0].spec.imagePullSecrets}{"\n"}'
# [{"name":"harbor-pull"}]

نکته‌ها: (۱) تزریق imagePullSecrets از ServiceAccount در زمان ایجاد Pod انجام می‌شود؛‏ Podهای موجود پس از patch کردن ServiceAccount تغییری نمی‌کنند تا دوباره ساخته شوند. (۲) اگر Secret حذف یا اشتباه نام‌گذاری شود،‏ event FailedToRetrieveImagePullSecret را می‌بینید. (۳) rotation رمز robot account:‏ Secret را به‌روز کنید؛‏ Podهای در حال اجرا تأثیری نمی‌گیرند،‏ ولی pull بعدی (مثلاً روی Node جدید) با credential جدید انجام می‌شود.

موارد استفاده (Use cases)

راه‌حل‌های متعددی برای پیکربندی private registryها وجود دارد. در اینجا چند مورد استفاده‌ی رایج و راه‌حل‌های پیشنهادی آمده است:

#مورد استفادهراه‌حل‌های پیشنهادی
۱clusterی که فقط imageهای غیرانحصاری (مثلاً open-source) اجرا می‌کند. نیازی به پنهان کردن imageها نیست.از imageهای عمومی یک public registry استفاده کنید.
  • هیچ پیکربندی لازم نیست.
  • برخی cloud providerها imageهای عمومی را به‌طور خودکار cache یا mirror می‌کنند که دسترس‌پذیری را بهتر و زمان pull را کم می‌کند.
۲clusterی که برخی imageهای انحصاری اجرا می‌کند که باید از بیرون شرکت پنهان باشند،‏ اما برای همه‌ی کاربران cluster قابل مشاهده باشند.
  • از یک hosted private registry استفاده کنید. ممکن است روی Nodeهایی که باید به private registry دسترسی داشته باشند پیکربندی دستی لازم باشد.
  • یا یک private registry داخلی پشت firewall با دسترسی خواندن باز اجرا کنید. هیچ پیکربندی کوبرنتیز لازم نیست.
  • از یک سرویس hosted container image registry استفاده کنید که دسترسی به imageها را کنترل می‌کند. این با Node autoscaling بهتر از پیکربندی دستی Node کار می‌کند.
  • یا در clusterی که تغییر پیکربندی Node ناخوشایند است،‏ از imagePullSecrets استفاده کنید.
۳cluster با imageهای انحصاری که چندتایی از آن‌ها کنترل دسترسی سخت‌گیرانه‌تری لازم دارند.
  • مطمئن شوید AlwaysPullImages admission controller فعال است. در غیر این صورت،‏ همه‌ی Podها به‌طور بالقوه به همه‌ی imageها دسترسی دارند.
  • داده‌های حساس را به جای بسته‌بندی در image،‏ به یک resource از نوع Secret منتقل کنید.
۴یک cluster multi-tenant که هر tenant به private registry خودش نیاز دارد.
  • مطمئن شوید AlwaysPullImages admission controller فعال است. در غیر این صورت،‏ همه‌ی Podهای همه‌ی tenantها به‌طور بالقوه به همه‌ی imageها دسترسی دارند.
  • یک private registry با authorization اجباری اجرا کنید.
  • برای هر tenant credentialهای registry تولید کنید،‏ در یک Secret ذخیره کنید و Secret را به هر namespace آن tenant منتشر کنید.
  • سپس tenant آن Secret را به imagePullSecrets هر namespace اضافه می‌کند (در عمل به ServiceAccountهای آن namespace یا به خود Podها).

اگر به چند registry دسترسی لازم دارید،‏ می‌توانید برای هر registry یک Secret بسازید.

نکته

توصیه‌ی AlwaysPullImages در ردیف‌های ۳ و ۴ از مستندات است. از v1.35 قابلیت KubeletEnsureSecretPulledImages به‌طور پیش‌فرض فعال است و بیشتر همین حفاظت را بدون pull اجباری فراهم می‌کند،‏ به شرطی که credential private registryها در سطح Pod یا ServiceAccount باشد،‏ نه در سطح Node.

credential provider داخلی قدیمی kubelet (Legacy built-in kubelet credential provider)

در نسخه‌های قدیمی‌تر کوبرنتیز،‏ kubelet یک یکپارچگی مستقیم با credentialهای cloud provider داشت. این امکان گرفتن پویای credentialها برای image registryها را فراهم می‌کرد.

سه پیاده‌سازی built-in از این یکپارچگی kubelet credential provider وجود داشت: ACR (Azure Container Registry)،‏ ECR (Elastic Container Registry) و GCR (Google Container Registry).

از نسخه‌ی 1.26 کوبرنتیز این مکانیزم قدیمی حذف شده است،‏ پس باید یکی از این کارها را انجام دهید:

  • روی هر Node یک kubelet image credential provider پیکربندی کنید؛‏ یا
  • credentialهای image pull را با استفاده از imagePullSecrets و حداقل یک Secret مشخص کنید.
توضیح تکمیلی: نشانه‌ی کلاسیک پس از ارتقا از نسخه‌های پیش از 1.26

اگر clusterی با Nodeهای خودمدیریت (self-managed) روی AWS،‏ Azure یا GCP را از نسخه‌ای پیش از 1.26 ارتقا می‌دهید،‏ علامت کلاسیک پس از upgrade این است که Podهای جدید روی Nodeهای upgrade‌شده با 401 Unauthorized از ECR/ACR/GCR به ErrImagePull می‌رسند،‏ در حالی که Podهای قدیمی سالم‌اند (چون image از قبل روی Node بود). راه‌حل: نصب binary credential provider مربوطه (مثل ecr-credential-provider) و تنظیم دو flag kubelet که در بالا آمد.

pull کردن image از private registry (Pull an Image from a Private Registry)

این task نشان می‌دهد چطور Podی بسازید که از یک Secret برای pull کردن image از یک private container image registry یا repository استفاده کند. private registryهای زیادی استفاده می‌شوند؛‏ این task از Docker Hub به عنوان registry نمونه استفاده می‌کند.

پیش از شروع (Before you begin)

  • به یک cluster کوبرنتیز و ابزار kubectl متصل به آن نیاز دارید.
  • برای انجام این تمرین به ابزار خط فرمان docker و یک Docker ID که password آن را می‌دانید نیاز دارید.
  • اگر از private container registry دیگری استفاده می‌کنید،‏ به ابزار خط فرمان آن registry و اطلاعات login آن نیاز دارید.

ورود به Docker Hub (Log in to Docker Hub)

روی لپ‌تاپ خود،‏ برای pull کردن یک image خصوصی باید با registry authenticate کنید. از ابزار docker برای login به Docker Hub استفاده کنید (بخش log in در Docker ID accounts را ببینید).

shell
docker login

وقتی از شما خواسته شد،‏ Docker ID خود را وارد کنید و سپس credentialی که می‌خواهید استفاده کنید (access token یا password مربوط به Docker ID).

فرایند login یک فایل config.json که یک authorization token را نگه می‌دارد می‌سازد یا به‌روز می‌کند. نحوه‌ی تفسیر این فایل توسط Kubernetes را مرور کنید.

فایل config.json را ببینید:

shell
cat ~/.docker/config.json

خروجی بخشی شبیه این دارد:

output
{
    "auths": {
        "https://index.docker.io/v1/": {
            "auth": "c3R...zE2"
        }
    }
}
نکته

اگر از Docker credentials store استفاده می‌کنید،‏ آن entry auth را نمی‌بینید،‏ بلکه یک entry credsStore با نام store به عنوان مقدار می‌بینید. در این حالت می‌توانید Secret را مستقیماً بسازید؛‏ Create a Secret by providing credentials on the command line را ببینید.

ساختن Secret از روی credentialهای موجود (Create a Secret based on existing credentials)

یک cluster کوبرنتیز از Secret از نوع kubernetes.io/dockerconfigjson برای authentication به یک container registry برای pull کردن یک image خصوصی استفاده می‌کند.

اگر قبلاً docker login را اجرا کرده‌اید،‏ می‌توانید آن credential را به کوبرنتیز کپی کنید:

shell
kubectl create secret generic regcred \
    --from-file=.dockerconfigjson=<path/to/.docker/config.json> \
    --type=kubernetes.io/dockerconfigjson

اگر کنترل بیشتری لازم دارید (برای مثال برای تعیین namespace یا یک label روی Secret جدید)،‏ می‌توانید Secret را قبل از ذخیره سفارشی کنید. مطمئن شوید که:

  • نام آیتم داده را .dockerconfigjson بگذارید؛‏
  • فایل Docker configuration را base64 encode کنید و آن رشته را به صورت یکپارچه (بدون شکستن خط) به عنوان مقدار فیلد data[".dockerconfigjson"] قرار دهید؛‏
  • type را روی kubernetes.io/dockerconfigjson بگذارید.

مثال:

Secret
apiVersion: v1
kind: Secret
metadata:
  name: myregistrykey
  namespace: awesomeapps
data:
  .dockerconfigjson: UmVhbGx5IHJlYWxseSByZWVlZWVlZWVlZWFhYWFhYWFhYWFhYWFhYWFhYWFhYWFhYWFhYWxsbGxsbGxsbGxsbGxsbGxsbGxsbGxsbGxsbGxsbGx5eXl5eXl5eXl5eXl5eXl5eXl5eSBsbGxsbGxsbGxsbGxsbG9vb29vb29vb29vb29vb29vb29vb29vb29vb25ubm5ubm5ubm5ubm5ubm5ubm5ubm5ubmdnZ2dnZ2dnZ2dnZ2dnZ2dnZ2cgYXV0aCBrZXlzCg==
type: kubernetes.io/dockerconfigjson

اگر پیام خطای error: no objects passed to create را گرفتید،‏ ممکن است یعنی رشته‌ی base64 encode‌شده نامعتبر است. اگر پیامی مثل Secret "myregistrykey" is invalid: data[.dockerconfigjson]: invalid value ... گرفتید،‏ یعنی رشته‌ی base64 در data با موفقیت decode شده اما نتوانسته به عنوان یک فایل .docker/config.json parse شود.

ساختن Secret با دادن credential در خط فرمان (Create a Secret by providing credentials on the command line)

این Secret را با نام regcred بسازید:

shell
kubectl create secret docker-registry regcred --docker-server=<your-registry-server> --docker-username=<your-name> --docker-password=<your-pword> --docker-email=<your-email>

که در آن:

  • <your-registry-server> FQDN مربوط به Private Docker Registry شماست. برای DockerHub از https://index.docker.io/v1/ استفاده کنید.
  • <your-name> username مربوط به Docker شماست.
  • <your-pword> password مربوط به Docker شماست.
  • <your-email> ایمیل Docker شماست.

شما credentialهای Docker خود را با موفقیت به عنوان یک Secret با نام regcred در cluster تنظیم کرده‌اید.

نکته

تایپ کردن Secretها در خط فرمان ممکن است آن‌ها را به شکل محافظت‌نشده در shell history ذخیره کند،‏ و ممکن است آن Secretها در زمانی که kubectl در حال اجراست برای کاربران دیگر روی PC شما قابل مشاهده باشند.

بررسی Secret regcred (Inspecting the Secret regcred)

برای فهم محتوای Secret regcred که ساختید،‏ ابتدا Secret را در قالب YAML ببینید:

shell
kubectl get secret regcred --output=yaml

خروجی شبیه این است:

output
apiVersion: v1
kind: Secret
metadata:
  ...
  name: regcred
  ...
data:
  .dockerconfigjson: eyJodHRwczovL2luZGV4L ... J0QUl6RTIifX0=
type: kubernetes.io/dockerconfigjson

مقدار فیلد .dockerconfigjson نمایش base64 از credentialهای Docker شماست.

برای فهم محتوای فیلد .dockerconfigjson،‏ داده‌ی Secret را به قالب خوانا تبدیل کنید:

shell
kubectl get secret regcred --output="jsonpath={.data.\.dockerconfigjson}" | base64 --decode

خروجی شبیه این است:

output
{"auths":{"your.private.registry.example.com":{"username":"janedoe","password":"xxxxxxxxxxx","email":"jdoe@example.com","auth":"c3R...zE2"}}}

برای فهم محتوای فیلد auth،‏ داده‌ی base64 را به قالب خوانا تبدیل کنید:

shell
echo "c3R...zE2" | base64 --decode

خروجی،‏ یعنی username و password که با ‎:‎ به هم وصل شده‌اند،‏ شبیه این است:

output
janedoe:xxxxxxxxxxx

توجه کنید که داده‌ی Secret شامل authorization tokenی مشابه فایل محلی ~/.docker/config.json شماست.

شما credentialهای Docker خود را با موفقیت به عنوان یک Secret با نام regcred در cluster تنظیم کرده‌اید.

هشدار (خارج از مستندات رسمی)

همان‌طور که دیدید،‏ base64 encryption نیست؛‏ هر کسی که اجازه‌ی get روی Secretهای آن namespace را دارد،‏ password registry را می‌بیند. دسترسی RBAC به Secretها را محدود کنید و برای registry از tokenهای فقط‌خواندنی استفاده کنید (فصل ۱۴).

ساختن Podی که از Secret استفاده می‌کند (Create a Pod that uses your Secret)

این manifest یک Pod نمونه است که به credentialهای Docker شما در regcred نیاز دارد:

pods/private-reg-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: private-reg
spec:
  containers:
  - name: private-reg-container
    image: <your-private-image>
  imagePullSecrets:
  - name: regcred

فایل بالا را روی کامپیوتر خود دانلود کنید:

shell
curl -L -o my-private-reg-pod.yaml https://k8s.io/examples/pods/private-reg-pod.yaml

در فایل my-private-reg-pod.yaml،‏ <your-private-image> را با مسیر یک image در یک private registry جایگزین کنید،‏ مثل:

image
your.private.registry.example.com/janedoe/jdoe-private:v1

برای pull کردن image از private registry،‏ کوبرنتیز به credential نیاز دارد. فیلد imagePullSecrets در فایل پیکربندی مشخص می‌کند که کوبرنتیز باید credentialها را از یک Secret به نام regcred بگیرد.

Podی که از Secret شما استفاده می‌کند را بسازید و بررسی کنید که Pod در حال اجراست:

shell
kubectl apply -f my-private-reg-pod.yaml
kubectl get pod private-reg
نکته

برای استفاده از image pull secretها (Secretی که credential registry را برای image pull نگه می‌دارد) برای یک Pod (یا یک Deployment یا object دیگری که یک pod template دارد و از آن استفاده می‌کنید)،‏ باید مطمئن شوید Secret مناسب در namespace درست وجود دارد. namespaceی که باید استفاده شود همان namespaceی است که Pod را در آن تعریف کرده‌اید.

همچنین اگر Pod با وضعیت ImagePullBackOff start نشد،‏ eventهای Pod را ببینید:

shell
kubectl describe pod private-reg

اگر سپس eventی با reason برابر FailedToRetrieveImagePullSecret دیدید،‏ کوبرنتیز نمی‌تواند Secretی با آن نام (در این مثال regcred) پیدا کند.

مطمئن شوید Secretی که مشخص کرده‌اید وجود دارد و نامش درست نوشته شده است.

output
Events:
  ...  Reason                           ...  Message
       ------                                -------
  ...  FailedToRetrieveImagePullSecret  ...  Unable to retrieve some image pull secrets (<regcred>); attempting to pull the image may not succeed.

استفاده از imageهای چند registry (Using images from multiple registries)

یک Pod می‌تواند چند container داشته باشد و image هر container می‌تواند از registry متفاوتی باشد. می‌توانید چند imagePullSecrets را با یک Pod استفاده کنید و هر کدام می‌تواند چند credential داشته باشد.

image pull با هر credentialی که با registry تطبیق دارد امتحان می‌شود. اگر هیچ credentialی با registry تطبیق نداشته باشد،‏ image pull بدون authorization (بررسی اینکه درخواست‌دهنده اجازه‌ی این کار را دارد یا نه) یا با پیکربندی سفارشی مخصوص runtime امتحان می‌شود.

multi-registry-pod.yaml (نمونه)
apiVersion: v1
kind: Pod
metadata:
  name: multi-reg
spec:
  imagePullSecrets:
  - name: harbor-pull        # for harbor.corp.example
  - name: ghcr-pull          # for ghcr.io
  containers:
  - name: app
    image: harbor.corp.example/shop/api:v3.1.0
  - name: log-shipper
    image: ghcr.io/example-org/log-shipper:1.4.2
  - name: metrics
    image: registry.k8s.io/pause:3.10   # no Secret matches → anonymous pull

Container environment

این بخش منابعی را توضیح می‌دهد که در Container environment در اختیار Containerها قرار دارد.

Container environment در کوبرنتیز چند منبع مهم را برای Containerها فراهم می‌کند:

  • یک filesystem،‏ که ترکیبی از یک image و یک یا چند volume است (فصل ۷).
  • اطلاعاتی درباره‌ی خود Container.
  • اطلاعاتی درباره‌ی objectهای دیگر در cluster.

اطلاعات container (Container information)

hostname یک Container،‏ نام Podی است که Container در آن اجرا می‌شود (اگر فیلد spec.hostname در Pod تنظیم شده باشد،‏ همان مقدار استفاده می‌شود). این مقدار از طریق دستور hostname یا فراخوانی تابع gethostname در libc در دسترس است.

نام Pod و namespace آن از طریق downward API به صورت environment variable در دسترس‌اند.

environment variableهای تعریف‌شده توسط کاربر در تعریف Pod هم در دسترس Container هستند،‏ همین‌طور هر environment variableی که به صورت ایستا در container image مشخص شده است.

اطلاعات cluster (Cluster information)

فهرستی از همه‌ی Serviceهایی که در زمان ایجاد یک Container در حال اجرا بوده‌اند،‏ به صورت environment variable در اختیار آن Container قرار می‌گیرد. این فهرست محدود به Serviceهای همان namespace که Pod جدید در آن است و Serviceهای control plane (اجزای مدیریتی cluster که تصمیم‌ها را می‌گیرند و وضعیت را نگه می‌دارند) است.

برای Serviceی به نام foo که مجموعه‌ای از Podها را expose می‌کند و هر کدام containerی به نام bar اجرا می‌کنند،‏ این متغیرها تعریف می‌شوند:

shell
FOO_SERVICE_HOST=<the host the service is running on>
FOO_SERVICE_PORT=<the port the service is running on>

Serviceها IP address اختصاصی دارند و اگر DNS addon فعال باشد،‏ از طریق DNS در دسترس Container هستند.

آزمایش عملی: دیدن Container environment از داخل container
env-demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: env-demo
spec:
  containers:
  - name: shell
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: APP_MODE            # user-defined variable
      value: production
    - name: MY_POD_NAME         # downward API
      valueFrom:
        fieldRef:
          fieldPath: metadata.name
    - name: MY_POD_NAMESPACE
      valueFrom:
        fieldRef:
          fieldPath: metadata.namespace
shell
kubectl create deployment foo --image=nginx:1.27 --port=80
kubectl expose deployment foo --port=80
kubectl apply -f env-demo.yaml          # Pod is created after the Service
kubectl exec env-demo -- hostname
kubectl exec env-demo -- sh -c 'env | grep -E "APP_MODE|MY_POD|FOO_SERVICE|KUBERNETES_SERVICE" | sort'
output (نمونه)
env-demo

FOO_SERVICE_HOST=10.43.143.21
FOO_SERVICE_PORT=80
KUBERNETES_SERVICE_HOST=10.43.0.1
KUBERNETES_SERVICE_PORT=443
MY_POD_NAME=env-demo

حالا یک Service دیگر به نام bar2 بسازید و دوباره env را در همان Pod ببینید: متغیر BAR2_SERVICE_HOST وجود ندارد،‏ چون فهرست Serviceها فقط «در زمان ایجاد Container» ساخته می‌شود. برای رسیدن به Serviceهای جدید باید از DNS استفاده کنید (bar2.default.svc.cluster.local). به همین دلیل در production به DNS تکیه می‌شود نه به این متغیرها.

توضیح تکمیلی: وابستگی به ترتیب ایجاد

اگر برنامه‌ای به DB_SERVICE_HOST تکیه کند،‏ باید Service db قبل از Pod برنامه وجود داشته باشد؛‏ در غیر این صورت متغیر خالی است و برنامه crash می‌کند و فقط پس از restart container درست می‌شود. این یک وابستگی شکننده به ترتیب deployment است. علاوه بر آن،‏ در namespaceهایی با صدها Service،‏ تعداد زیادی متغیر به هر container تزریق می‌شود (خارج از مستندات رسمی: فیلد enableServiceLinks: false در Pod spec تزریق این متغیرها را برای Serviceهای کاربر خاموش می‌کند).

RuntimeClass

وضعیت قابلیت: Kubernetes v1.20 [stable]

این بخش resource RuntimeClass و مکانیزم انتخاب runtime را توضیح می‌دهد.

RuntimeClass قابلیتی برای انتخاب پیکربندی container runtime است. پیکربندی container runtime برای اجرای containerهای یک Pod استفاده می‌شود.

انگیزه (Motivation)

می‌توانید بین Podهای مختلف RuntimeClass متفاوتی تنظیم کنید تا تعادلی بین کارایی (performance) و امنیت فراهم کنید. برای مثال،‏ اگر بخشی از workload شما سطح بالایی از اطمینان امنیت اطلاعات لازم دارد،‏ ممکن است تصمیم بگیرید آن Podها را طوری schedule کنید که در یک container runtime اجرا شوند که از hardware virtualization استفاده می‌کند. در این صورت از ایزولاسیون بیشتر runtime جایگزین بهره می‌برید،‏ به قیمت مقداری overhead اضافی.

همچنین می‌توانید از RuntimeClass برای اجرای Podهای مختلف با همان container runtime ولی با تنظیمات متفاوت استفاده کنید.

راه‌اندازی (Setup)

  1. پیکربندی پیاده‌سازی CRI روی Nodeها (وابسته به runtime)
  2. ایجاد resourceهای RuntimeClass متناظر

۱. پیکربندی پیاده‌سازی CRI روی Nodeها

پیکربندی‌هایی که از طریق RuntimeClass در دسترس‌اند به پیاده‌سازی Container Runtime Interface (CRI) وابسته‌اند. برای نحوه‌ی پیکربندی،‏ مستندات پیاده‌سازی CRI خود را ببینید (پایین‌تر).

نکته

RuntimeClass به‌طور پیش‌فرض یک پیکربندی همگن Node در سراسر cluster را فرض می‌کند (یعنی همه‌ی Nodeها از نظر container runtime یکسان پیکربندی شده‌اند). برای پشتیبانی از پیکربندی‌های ناهمگن Node،‏ بخش Scheduling را در ادامه ببینید.

پیکربندی‌ها یک نام handler متناظر دارند که RuntimeClass به آن ارجاع می‌دهد. handler باید یک DNS label name معتبر باشد.

۲. ساختن RuntimeClassهای متناظر

پیکربندی‌هایی که در مرحله‌ی ۱ تنظیم شده‌اند هر کدام باید یک نام handler مرتبط داشته باشند که آن پیکربندی را شناسایی می‌کند. برای هر handler یک object RuntimeClass متناظر بسازید.

resource RuntimeClass در حال حاضر فقط ۲ فیلد مهم دارد: نام RuntimeClass (metadata.name) و handler (handler). تعریف object شبیه این است:

RuntimeClass
# RuntimeClass is defined in the node.k8s.io API group
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  # The name the RuntimeClass will be referenced by.
  # RuntimeClass is a non-namespaced resource.
  name: myclass
# The name of the corresponding CRI configuration
handler: myconfiguration

نام یک object RuntimeClass باید یک DNS subdomain name معتبر باشد.

نکته

توصیه می‌شود عملیات نوشتن RuntimeClass (create/update/patch/delete) به مدیر cluster محدود شود. این معمولاً پیش‌فرض است. برای جزئیات بیشتر Authorization Overview را ببینید.

نحوه‌ی استفاده (Usage)

وقتی RuntimeClassها برای cluster پیکربندی شدند،‏ می‌توانید یک runtimeClassName در Pod spec مشخص کنید تا از آن استفاده شود. برای مثال:

Pod
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  runtimeClassName: myclass
  # ...

این به kubelet دستور می‌دهد از RuntimeClass نام‌برده برای اجرای این Pod استفاده کند. اگر RuntimeClass نام‌برده وجود نداشته باشد،‏ یا CRI نتواند handler متناظر را اجرا کند،‏ Pod وارد phase پایانی Failed می‌شود. برای پیام خطا به دنبال event متناظر بگردید.

اگر هیچ runtimeClassName مشخص نشود،‏ RuntimeHandler پیش‌فرض استفاده می‌شود که معادل رفتار زمانی است که قابلیت RuntimeClass غیرفعال است.

توضیح تکمیلی: دو حالت شکست در عمل

جمله‌ی بالا از مستندات است،‏ ولی در clusterی که admission plugin به نام RuntimeClass (به‌طور پیش‌فرض فعال) دارد،‏ دو حالت رفتار متفاوتی دارند:

  • RuntimeClass وجود ندارد: API server همان لحظه درخواست را رد می‌کند و Podی ساخته نمی‌شود: pods "mypod" is forbidden: pod rejected: RuntimeClass "myclass" not found. اگر Pod را یک controller بسازد،‏ همین پیام در event FailedCreate مربوط به ReplicaSet دیده می‌شود.
  • RuntimeClass هست،‏ ولی handler روی Node تعریف نشده: Pod ساخته و schedule می‌شود،‏ اما RunPodSandbox در container runtime شکست می‌خورد. Pod در ContainerCreating می‌ماند و kubelet با event FailedCreatePodSandBox دوباره تلاش می‌کند.

در هیچ‌کدام از این دو حالت،‏ کوبرنتیز بی‌صدا به runtime پیش‌فرض برنمی‌گردد.

پیکربندی CRI (CRI Configuration)

برای جزئیات بیشتر درباره‌ی راه‌اندازی CRI runtimeها،‏ CRI installation را ببینید (فصل ۱۳).

containerd

Runtime handlerها از طریق پیکربندی containerd در /etc/containerd/config.toml پیکربندی می‌شوند. handlerهای معتبر زیر بخش runtimes پیکربندی می‌شوند:

/etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.${HANDLER_NAME}]

برای جزئیات بیشتر config documentation مربوط به containerd را ببینید.

CRI-O

Runtime handlerها از طریق پیکربندی CRI-O در /etc/crio/crio.conf پیکربندی می‌شوند. handlerهای معتبر زیر crio.runtime table پیکربندی می‌شوند:

/etc/crio/crio.conf
[crio.runtime.runtimes.${HANDLER_NAME}]
  runtime_path = "${PATH_TO_BINARY}"

برای جزئیات بیشتر config documentation مربوط به CRI-O را ببینید.

آزمایش عملی: یک handler gVisor در containerd و RuntimeClass متناظر

(خارج از مستندات رسمی: نصب gVisor و نام runsc و runtime_type مربوط به containerd از مستندات gVisor و containerd است.) روی Nodeهای منتخب:

/etc/containerd/config.toml (افزودنی)
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
  runtime_type = "io.containerd.runsc.v1"
shell
sudo systemctl restart containerd
kubectl label node worker-3 sandbox.example.com/gvisor=true

این نحو مربوط به پیکربندی containerd 1.x است. در containerd 2.x (پیکربندی نسخه‌ی ۳)،‏ که در آزمایش crictl پایان این فصل هم می‌بینید،‏ مسیر جدول [plugins."io.containerd.cri.v1.runtime".containerd.runtimes.runsc] است.

runtimeclass-gvisor.yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc            # must equal ${HANDLER_NAME} in config.toml
scheduling:
  nodeSelector:
    sandbox.example.com/gvisor: "true"
overhead:
  podFixed:
    memory: "64Mi"
    cpu: "100m"
---
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-job
spec:
  runtimeClassName: gvisor
  containers:
  - name: c
    image: busybox:1.36
    command: ["sh", "-c", "dmesg | head -3; sleep 3600"]
shell
kubectl apply -f runtimeclass-gvisor.yaml
kubectl get pod untrusted-job -o wide           # lands on worker-3
kubectl get pod untrusted-job -o jsonpath='{.spec.nodeSelector}{"\n"}{.spec.overhead}{"\n"}'
kubectl logs untrusted-job                       # dmesg shows gVisor's emulated kernel messages
output (نمونه)
{"sandbox.example.com/gvisor":"true"}
{"cpu":"100m","memory":"64Mi"}

ببینید که nodeSelector و overhead در زمان admission از RuntimeClass به Pod spec اضافه شده‌اند.

Scheduling

وضعیت قابلیت: Kubernetes v1.16 [beta]

با مشخص کردن فیلد scheduling برای یک RuntimeClass،‏ می‌توانید محدودیت‌هایی تنظیم کنید تا Podهایی که با این RuntimeClass اجرا می‌شوند روی Nodeهایی schedule شوند که از آن پشتیبانی می‌کنند. اگر scheduling تنظیم نشود،‏ فرض بر این است که همه‌ی Nodeها از این RuntimeClass پشتیبانی می‌کنند.

برای اطمینان از اینکه Podها روی Nodeهای پشتیبانی‌کننده از یک RuntimeClass مشخص قرار می‌گیرند،‏ آن مجموعه از Nodeها باید یک label (جفت کلید/مقدار روی اشیا برای گروه‌بندی و انتخاب آن‌ها) مشترک داشته باشند که سپس توسط فیلد runtimeclass.scheduling.nodeSelector انتخاب می‌شود. nodeSelector مربوط به RuntimeClass در admission با nodeSelector مربوط به Pod merge می‌شود،‏ که در عمل اشتراک (intersection) مجموعه‌ی Nodeهای انتخاب‌شده توسط هر کدام را می‌گیرد. اگر تعارض وجود داشته باشد،‏ Pod رد (reject) می‌شود.

اگر Nodeهای پشتیبانی‌کننده taint (علامتی روی Node که Podهای بدون toleration مناسب را دور نگه می‌دارد) شده‌اند تا جلوی اجرای Podهای دیگر RuntimeClassها روی آن Node گرفته شود،‏ می‌توانید tolerations را به RuntimeClass اضافه کنید. مانند nodeSelector،‏ tolerationها (اجازه‌ی Pod برای قرار گرفتن روی Node دارای taint) در admission با tolerationهای Pod merge می‌شوند،‏ که در عمل اجتماع (union) مجموعه‌ی Nodeهای tolerate‌شده توسط هر کدام را می‌گیرد.

برای یادگیری بیشتر درباره‌ی پیکربندی node selector و tolerationها،‏ Assigning Pods to Nodes را ببینید (فصل ۹).

توضیح تکمیلی: intersection در برابر union

nodeSelector یک محدودیت است؛‏ هر چه selectorها بیشتر شوند مجموعه‌ی Nodeها کوچک‌تر می‌شود (intersection). اگر Pod disktype: ssd بخواهد و RuntimeClass sandbox.example.com/gvisor: "true"،‏ Pod فقط روی Nodeهایی می‌رود که هر دو label را دارند. اما اگر Pod sandbox.example.com/gvisor: "false" داشته باشد،‏ کلید یکسان با مقدار متفاوت یک تعارض است و admission،‏ Pod را رد می‌کند. در مقابل،‏ toleration یک اجازه است؛‏ هر چه بیشتر شوند Pod روی Nodeهای بیشتری مجاز است (union). الگوی production:‏ Nodeهای sandbox را با runtime=gvisor:NoSchedule taint کنید و toleration را فقط در RuntimeClass بگذارید،‏ تا Podهای معمولی روی آن‌ها نروند و Podهای gvisor نیاز نداشته باشند خودشان toleration بنویسند.

RuntimeClass با toleration
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
scheduling:
  nodeSelector:
    sandbox.example.com/gvisor: "true"
  tolerations:
  - key: runtime
    operator: Equal
    value: gvisor
    effect: NoSchedule

Pod Overhead

وضعیت قابلیت: Kubernetes v1.24 [stable]

می‌توانید resourceهای overhead مرتبط با اجرای یک Pod را مشخص کنید. اعلام overhead به cluster (از جمله scheduler) اجازه می‌دهد هنگام تصمیم‌گیری درباره‌ی Podها و resourceها آن را در نظر بگیرد.

Pod overhead در RuntimeClass از طریق فیلد overhead تعریف می‌شود. با استفاده از این فیلد می‌توانید overhead اجرای Podهایی که از این RuntimeClass استفاده می‌کنند را مشخص کنید و مطمئن شوید این overheadها در کوبرنتیز محاسبه می‌شوند.

توضیح تکمیلی: overhead چطور حساب می‌شود؟

در runtimeهای مبتنی بر VM (مثل Kata)،‏ هر Pod یک kernel و agent داخل VM دارد که خودش memory و CPU مصرف می‌کند،‏ جدا از requestهای containerها. اگر این مقدار اعلام نشود،‏ scheduler Nodeها را overcommit می‌کند. با overhead.podFixed،‏ مقدار overhead در admission به spec.overhead Pod اضافه می‌شود و scheduler مجموع requestهای containerها به‌علاوه‌ی overhead را در نظر می‌گیرد. مثال: container با request 500m CPU و 1Gi memory و overhead 250m و 120Mi ⇐ scheduler برای Pod 750m و 1Gi + 120Mi جا لازم دارد. جزئیات کامل در صفحه‌ی Pod Overhead (فصل ۹) آمده است.

Container Lifecycle Hooks

این بخش توضیح می‌دهد چگونه Containerهایی که kubelet مدیریت می‌کند می‌توانند از چارچوب Container lifecycle hook (نقطه‌ای از چرخه‌ی عمر container که kubelet در آن کد شما را اجرا می‌کند) برای اجرای کد در پاسخ به رخدادهای lifecycle مدیریتی خود استفاده کنند.

نمای کلی (Overview)

مشابه بسیاری از frameworkهای زبان‌های برنامه‌نویسی که lifecycle hookهای component دارند (مثل Angular)،‏ کوبرنتیز هم برای Containerها lifecycle hook فراهم می‌کند. hookها Containerها را قادر می‌سازند از رخدادهای lifecycle مدیریتی خود آگاه باشند و وقتی lifecycle hook متناظر اجرا می‌شود،‏ کدی را که در یک handler پیاده‌سازی شده اجرا کنند.

Container hooks

دو hook در اختیار Containerها قرار دارد:

PostStart

این hook بلافاصله پس از ایجاد یک container اجرا می‌شود. این hook به صورت همزمان (concurrently) با ENTRYPOINT container (process اصلی) اجرا می‌شود،‏ یعنی hook ممکن است قبل،‏ در حین یا بعد از start شدن process اصلی اجرا شود.

هیچ پارامتری به handler داده نمی‌شود.

نکته

با اینکه hook همزمان با process container اجرا می‌شود،‏ می‌تواند به‌روزرسانی وضعیت container را به تأخیر بیندازد؛‏ ممکن است container تا کامل شدن hook به Running منتقل نشود.

PreStop

این hook بلافاصله قبل از terminate شدن یک container فراخوانی می‌شود،‏ به دلیل یک درخواست API یا یک رخداد مدیریتی مثل شکست liveness/startup probe،‏ preemption (بیرون کردن Podهای کم‌اولویت برای باز کردن جا برای Pod پراولویت)،‏ رقابت بر سر resource (resource contention) و موارد دیگر. اگر container از قبل در وضعیت terminated یا completed باشد،‏ فراخوانی hook PreStop شکست می‌خورد،‏ و hook باید قبل از اینکه سیگنال TERM برای توقف container فرستاده شود کامل شود. شمارش معکوس termination grace period (مهلتی که container پیش از کشته شدن اجباری برای خاموش شدن دارد) مربوط به Pod قبل از اجرای hook PreStop شروع می‌شود،‏ پس صرف‌نظر از نتیجه‌ی handler،‏ container در نهایت در محدوده‌ی termination grace period مربوط به Pod terminate می‌شود. هیچ پارامتری به handler داده نمی‌شود.

توضیح دقیق‌تر رفتار termination را در Termination of Pods می‌توانید پیدا کنید (فصل ۳).

StopSignal

StopSignal lifecycle را می‌توان برای تعریف یک stop signal استفاده کرد که هنگام متوقف شدن container به آن فرستاده می‌شود. اگر این را تنظیم کنید،‏ هر دستور STOPSIGNAL تعریف‌شده در container image را override می‌کند.

توضیح دقیق‌تر رفتار termination با stop signalهای سفارشی را در Stop Signals می‌توانید پیدا کنید؛‏ خلاصه‌ی کامل آن در ادامه آمده است.

توضیح تکمیلی: Stop Signals (از صفحه‌ی Pod Lifecycle)

stop signalی که برای kill کردن container استفاده می‌شود را می‌توان در container image با دستور STOPSIGNAL تعریف کرد. اگر در image هیچ stop signalی تعریف نشده باشد،‏ سیگنال پیش‌فرض container runtime (SIGTERM برای هر دو containerd و CRI-O) برای kill کردن container استفاده می‌شود.

تعریف stop signal سفارشی (Defining custom stop signals) — وضعیت قابلیت: Kubernetes v1.33 [alpha] (به‌طور پیش‌فرض غیرفعال؛‏ feature gate: ContainerStopSignals). اگر feature gate ContainerStopSignals فعال باشد،‏ می‌توانید از Container Lifecycle یک stop signal سفارشی برای containerهای خود پیکربندی کنید. به عنوان پیش‌نیاز تعریف stop signal در container lifecycle،‏ فیلد spec.os.name مربوط به Pod باید وجود داشته باشد. فهرست سیگنال‌های معتبر به سیستم‌عاملی که Pod روی آن schedule می‌شود بستگی دارد. برای Podهایی که روی Nodeهای Windows schedule می‌شوند،‏ فقط SIGTERM و SIGKILL به عنوان سیگنال معتبر پشتیبانی می‌شوند.

Pod spec با stop signal سفارشی
spec:
  os:
    name: linux
  containers:
    - name: my-container
      image: container-image:latest
      lifecycle:
        stopSignal: SIGUSR1

اگر یک stop signal در lifecycle تعریف شده باشد،‏ سیگنال تعریف‌شده در container image را override می‌کند. اگر در container spec هیچ stop signalی تعریف نشده باشد،‏ container به رفتار پیش‌فرض برمی‌گردد.

کاربرد: برخی نرم‌افزارها با SIGTERM به‌سرعت خارج می‌شوند اما با سیگنال دیگری graceful shutdown انجام می‌دهند. مثلاً nginx با SIGQUIT به صورت graceful خاموش می‌شود (image رسمی nginx همین را با STOPSIGNAL SIGQUIT تنظیم کرده است؛‏ خارج از مستندات رسمی). با stopSignal می‌توانید این رفتار را بدون rebuild کردن image تنظیم کنید.

انواع hook handler (Hook handler implementations)

Containerها با پیاده‌سازی و ثبت یک handler برای یک hook می‌توانند به آن hook دسترسی داشته باشند. سه نوع hook handler وجود دارد که می‌توان برای Containerها پیاده‌سازی کرد:

  • Exec — یک دستور مشخص،‏ مثل pre-stop.sh،‏ را داخل cgroupها و namespaceهای Container اجرا می‌کند. resourceهای مصرف‌شده توسط دستور به حساب Container گذاشته می‌شوند.
  • HTTP — یک درخواست HTTP به یک endpoint مشخص روی Container اجرا می‌کند.
  • Sleep —‏ container را برای مدت مشخصی متوقف (pause) می‌کند.
سه نوع handler (نمونه)
lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "echo started > /tmp/started"]
  preStop:
    httpGet:            # or exec / sleep
      path: /shutdown
      port: 8080
# or:
#  preStop:
#    sleep:
#      seconds: 10

اجرای hook handler (Hook handler execution)

وقتی یک Container lifecycle management hook فراخوانی می‌شود،‏ سیستم مدیریت کوبرنتیز handler را بر اساس hook action اجرا می‌کند: httpGet،‏ tcpSocket (deprecated) و sleep توسط process kubelet اجرا می‌شوند و exec داخل container اجرا می‌شود.

فراخوانی handler hook PostStart هنگام ایجاد container آغاز می‌شود،‏ یعنی ENTRYPOINT container و hook PostStart همزمان trigger می‌شوند. (این یعنی معمولاً استفاده از یک HTTP hook برای PostStart منطقی نیست،‏ چون هیچ تضمینی نیست که process container هنگام اجرای hook کاملاً start شده باشد.) اگر اجرای hook PostStart خیلی طول بکشد یا hang کند،‏ می‌تواند جلوی انتقال container به وضعیت running را بگیرد.

hookهای PreStop به صورت asynchronous نسبت به سیگنال توقف Container اجرا نمی‌شوند؛‏ hook باید اجرایش را کامل کند قبل از اینکه سیگنال TERM فرستاده شود. اگر یک hook PreStop در حین اجرا hang کند،‏ phase مربوط به Pod Terminating خواهد بود و همان‌جا می‌ماند تا اینکه پس از منقضی شدن terminationGracePeriodSeconds آن Pod kill شود. این grace period روی مجموع زمانی اعمال می‌شود که هم اجرای hook PreStop و هم توقف عادی Container طول می‌کشد. برای مثال،‏ اگر terminationGracePeriodSeconds برابر ۶۰ باشد،‏ و hook ۵۵ ثانیه طول بکشد تا کامل شود،‏ و Container پس از دریافت سیگنال ۱۰ ثانیه برای توقف عادی نیاز داشته باشد،‏ Container قبل از اینکه بتواند به‌طور عادی متوقف شود kill می‌شود،‏ چون terminationGracePeriodSeconds کمتر از زمان کل (۵۵+۱۰) لازم برای این دو کار است.

اگر یکی از hookهای PostStart یا PreStop شکست بخورد،‏ Container kill می‌شود.

کاربران باید hook handlerهای خود را تا حد امکان سبک نگه دارند. اما مواردی هست که دستورهای طولانی منطقی‌اند،‏ مثل ذخیره‌ی state قبل از توقف یک Container.

توضیح تکمیلی: خط زمانی termination با preStop

قاعده‌ی طراحی: terminationGracePeriodSeconds ≥ زمان preStop + زمان graceful shutdown برنامه + حاشیه‌ی اطمینان. اطلاعات تمدید ۲ ثانیه‌ای و ترتیب همزمانی حذف endpoint از بخش Pod Termination Flow در Pod Lifecycle است (فصل ۳).

توضیح تکمیلی: preStop برای graceful draining پشت load balancer (الگوی production)

مشکل: وقتی Pod حذف می‌شود،‏ دو کار همزمان شروع می‌شوند: (الف) kubelet preStop و سپس TERM را اجرا می‌کند؛‏ (ب) control plane،‏ endpoint را از EndpointSlice (شیئی که نشانی Podهای پشت یک Service را نگه می‌دارد) خارج (ready=false) می‌کند و سپس kube-proxy روی همه‌ی Nodeها،‏ Ingress controller و load balancer بیرونی باید این تغییر را ببینند و اعمال کنند. مسیر (ب) چند ثانیه طول می‌کشد. اگر برنامه با دریافت TERM فوراً خارج شود،‏ در همان چند ثانیه load balancer هنوز درخواست به Pod مرده می‌فرستد ⇐ خطاهای 502/503 و connection reset در هر rollout.

راه‌حل: یک preStop که فقط «صبر» می‌کند تا مسیر (ب) به همه جا برسد،‏ سپس TERM برسد و برنامه اتصالات باز را تمام کند:

deploy-graceful.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 12
  strategy:
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 25%
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout
    spec:
      # 15s preStop + up to 30s app drain + margin
      terminationGracePeriodSeconds: 60
      containers:
      - name: app
        image: harbor.corp.example/shop/checkout:v5.2.0@sha256:<digest>
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          periodSeconds: 5
        lifecycle:
          preStop:
            sleep:
              seconds: 15    # time for endpoint removal to reach kube-proxy / Ingress / LB

در نسخه‌های قدیمی کوبرنتیز که handler sleep ندارند،‏ معادل exec آن command: ["sh", "-c", "sleep 15"] است (که به وجود sh و sleep در image نیاز دارد؛‏ در imageهای distroless وجود ندارند و به همین دلیل handler sleep که توسط خود kubelet اجرا می‌شود مزیت دارد). مقدار ۱۵ ثانیه یک عدد تجربی است (خارج از مستندات رسمی) و باید با تأخیر واقعی propagation در load balancer شما تنظیم شود؛‏ برای load balancerهای cloud با health check فاصله‌دار ممکن است بیشتر لازم باشد.

تضمین تحویل hook (Hook delivery guarantees)

تحویل hook قرار است at least once (حداقل یک بار) باشد،‏ یعنی یک hook ممکن است برای هر رخداد،‏ مثل PostStart یا PreStop،‏ چندین بار فراخوانی شود. مدیریت درست این موضوع بر عهده‌ی پیاده‌سازی hook است.

به‌طور کلی فقط تحویل‌های تکی انجام می‌شوند. اگر،‏ برای مثال،‏ گیرنده‌ی یک HTTP hook از کار افتاده باشد و نتواند ترافیک بگیرد،‏ هیچ تلاشی برای ارسال دوباره نمی‌شود. اما در برخی موارد نادر ممکن است تحویل دوباره رخ دهد. برای مثال،‏ اگر kubelet در میانه‌ی ارسال یک hook restart شود،‏ ممکن است hook پس از اجرای دوباره‌ی kubelet دوباره فرستاده شود.

توضیح تکمیلی: idempotent بودن hook

چون تحویل at least once است،‏ handler باید idempotent باشد. بد: postStart که INSERT INTO nodes ... اجرا می‌کند (دو بار اجرا ⇐ رکورد تکراری). خوب: INSERT ... ON CONFLICT DO NOTHING،‏ یا نوشتن فایل با > به جای >>،‏ یا یک preStop که «deregister اگر ثبت شده» را انجام می‌دهد.

ترتیب را دنبال کنید: container ساخته و start شد،‏ hook شکست خورد (FailedPostStartHook)،‏ kubelet container را kill کرد (Killing با reason همان FailedPostStartHook)،‏ container طبق restartPolicy دوباره ساخته شد (x2) و در نهایت BackOff (یعنی حلقه‌ی CrashLoopBackOff). نکته‌ی مهم debugging: خروجی stdout/stderr handler از نوع exec در kubectl logs نمی‌آید. اگر به log نیاز دارید،‏ handler را طوری بنویسید که در stdout process اصلی بنویسد (مثلاً echo ... > /proc/1/fd/1) یا در فایلی که بعداً بخوانید (خارج از مستندات رسمی).

اتصال handler به رخدادهای lifecycle container (Attach Handlers to Container Lifecycle Events)

این task نشان می‌دهد چگونه handlerها را به رخدادهای lifecycle یک Container متصل کنید. کوبرنتیز از رخدادهای postStart و preStop پشتیبانی می‌کند. کوبرنتیز رخداد postStart را بلافاصله پس از start شدن یک Container و رخداد preStop را بلافاصله قبل از terminate شدن Container می‌فرستد. یک Container می‌تواند برای هر رخداد یک handler مشخص کند.

پیش از شروع (Before you begin)

به یک cluster کوبرنتیز و ابزار kubectl که برای ارتباط با آن پیکربندی شده باشد نیاز دارید (همان cluster k3s فصل ۱ کافی است).

تعریف handlerهای postStart و preStop (Define postStart and preStop handlers)

در این تمرین،‏ یک Pod با یک Container می‌سازید. Container برای رخدادهای postStart و preStop handler دارد.

این فایل پیکربندی Pod است:

pods/lifecycle-events.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-demo
spec:
  containers:
  - name: lifecycle-demo-container
    image: nginx
    lifecycle:
      postStart:
        exec:
          command: ["/bin/sh", "-c", "echo Hello from the postStart handler > /usr/share/message"]
      preStop:
        exec:
          command: ["/bin/sh","-c","nginx -s quit; while killall -0 nginx; do sleep 1; done"]

در فایل پیکربندی می‌بینید که دستور postStart یک فایل message در دایرکتوری /usr/share مربوط به Container می‌نویسد. دستور preStop،‏ nginx را به صورت graceful خاموش می‌کند. این کار وقتی Container به خاطر یک شکست terminate می‌شود مفید است.

Pod را بسازید:

shell
kubectl apply -f https://k8s.io/examples/pods/lifecycle-events.yaml

بررسی کنید که Container در Pod در حال اجراست:

shell
kubectl get pod lifecycle-demo

یک shell در Container در حال اجرای Pod بگیرید:

shell
kubectl exec -it lifecycle-demo -- /bin/bash

در shell خود بررسی کنید که handler postStart فایل message را ساخته است:

shell
root@lifecycle-demo:/# cat /usr/share/message

خروجی متنی را که handler postStart نوشته نشان می‌دهد:

output
Hello from the postStart handler

جمع‌بندی (Discussion)

کوبرنتیز رخداد postStart را بلافاصله پس از ایجاد Container می‌فرستد. اما هیچ تضمینی نیست که handler postStart قبل از فراخوانی entrypoint مربوط به Container فراخوانی شود. handler postStart نسبت به کد Container به صورت asynchronous اجرا می‌شود،‏ اما مدیریت Container توسط کوبرنتیز تا کامل شدن handler postStart مسدود (block) می‌شود. وضعیت Container تا کامل شدن handler postStart روی RUNNING تنظیم نمی‌شود.

کوبرنتیز رخداد preStop را بلافاصله قبل از terminate شدن Container می‌فرستد. مدیریت Container توسط کوبرنتیز تا کامل شدن handler preStop مسدود می‌شود،‏ مگر اینکه grace period مربوط به Pod منقضی شود. برای جزئیات بیشتر Pod Lifecycle را ببینید.

نکته

کوبرنتیز رخداد preStop را فقط وقتی می‌فرستد که یک Pod یا یک container در Pod terminate شود. این یعنی hook preStop وقتی Pod complete می‌شود فراخوانی نمی‌شود. درباره‌ی این محدودیت،‏ برای جزئیات بخش Container hooks را ببینید.

آزمایش عملی: دیدن preStop در عمل و سنجش زمان termination
shell
# terminal 1
kubectl get events -w --field-selector involvedObject.name=lifecycle-demo
# terminal 2
time kubectl delete pod lifecycle-demo

انتظار: حذف تقریباً فوری است (کمتر از چند ثانیه) چون preStop،‏ nginx را با nginx -s quit به خاموشی graceful وادار می‌کند و حلقه‌ی killall -0 به محض خروج nginx تمام می‌شود. حالا preStop را به sleep 120 تغییر دهید و terminationGracePeriodSeconds: 20 بگذارید: حذف حدود ۲۰ ثانیه (به‌علاوه‌ی تمدید ۲ ثانیه‌ای) طول می‌کشد و سپس container با SIGKILL خاتمه می‌یابد. اگر preStop با خطا تمام شود یا grace period منقضی شود،‏ ممکن است event FailedPreStopHook را ببینید.

Container Runtime Interface (CRI)

CRI یک plugin interface است که به kubelet امکان می‌دهد از طیف گسترده‌ای از container runtimeها استفاده کند،‏ بدون اینکه نیازی به recompile کردن componentهای cluster باشد.

روی هر Node در cluster خود به یک container runtime کارا نیاز دارید تا kubelet بتواند Podها و containerهای آن‌ها را راه‌اندازی کند.

Container Runtime Interface (CRI) پروتکل اصلی ارتباط بین kubelet و Container Runtime است.

Kubernetes Container Runtime Interface (CRI) پروتکل اصلی gRPC برای ارتباط بین node components،‏ یعنی kubelet و container runtime،‏ را تعریف می‌کند.

The API

وضعیت قابلیت: Kubernetes v1.23 [stable]

kubelet هنگام اتصال به container runtime از طریق gRPC نقش client را دارد. endpointهای runtime service و image service باید در container runtime در دسترس باشند و می‌توان آن‌ها را به صورت جداگانه در kubelet با استفاده از command line flag --container-runtime-endpoint پیکربندی کرد.

برای Kubernetes v1.26 و بالاتر،‏ kubelet نیاز دارد container runtime از CRI API نسخه‌ی v1 پشتیبانی کند. اگر یک container runtime از API v1 پشتیبانی نکند،‏ kubelet،‏ Node را register نمی‌کند.

ارتقا (Upgrading)

هنگام upgrade کردن نسخه‌ی کوبرنتیز روی یک Node،‏ kubelet restart می‌شود. اگر container runtime از CRI API v1 پشتیبانی نکند،‏ kubelet در register کردن شکست می‌خورد و خطا گزارش می‌کند. اگر به دلیل upgrade شدن container runtime،‏ یک gRPC re-dial لازم باشد،‏ runtime باید برای موفقیت اتصال از CRI API v1 پشتیبانی کند. این ممکن است پس از پیکربندی درست container runtime به restart کردن kubelet نیاز داشته باشد.

دریافت فهرست به‌صورت stream (List streaming)

وضعیت قابلیت: Kubernetes v1.36 [alpha] (به‌طور پیش‌فرض غیرفعال؛‏ feature gate: CRIListStreaming)

RPCهای استاندارد list در CRI (ListContainers،‏ ListPodSandbox،‏ ListImages) همه‌ی نتایج را در یک پاسخ unary برمی‌گردانند. روی Nodeهایی با تعداد زیادی container (برای مثال،‏ بیش از حدود ۱۰٬۰۰۰ شامل containerهای در حال اجرا و متوقف‌شده)،‏ این پاسخ‌ها ممکن است از سقف پیش‌فرض ۱۶ MiB برای اندازه‌ی پیام در gRPC فراتر بروند و باعث شوند kubelet هنگام reconcile کردن state با container runtime شکست بخورد.

با فعال بودن feature gate CRIListStreaming،‏ kubelet از RPCهای server-side streaming (مثل StreamContainers،‏ StreamPodSandboxes،‏ StreamImages) استفاده می‌کند که به container runtime اجازه می‌دهند نتایج را در چند پیام پاسخ تقسیم کند و سقف اندازه‌ی هر پیام را دور بزند. این به‌ویژه برای موارد زیر مفید است:

  • محیط‌های با churn بالای container (سیستم‌های CI/CD)
  • workloadهای batch processing در مقیاس بزرگ

اگر container runtime از streaming RPCها پشتیبانی نکند،‏ kubelet برای سازگاری با گذشته به صورت خودکار به RPCهای unary استاندارد برمی‌گردد.

هفته‌ی بعد: گاهی API قفل می‌کند ولی Running می‌ماند و ترافیک می‌گیرد. در فصل ۳ Pod را از درون می‌شناسیم: probeها،‏ init container و sidecar.

تمرین‌های فصل ۲ ۲۲ تمرین
  1. مفهومیتفاوت imagePullPolicy: Always و IfNotPresent را از نظر تماس با registry توضیح دهید. اگر tag یکسانی (مثلاً v1.2.3) با محتوای جدید دوباره push شود،‏ هر کدام چه رفتاری دارند و چرا این کار خطرناک است؟
    پاسخ

    با Always،‏ kubelet هر بار که containerی را شروع می‌کند (از جمله پس از restart) از container runtime می‌خواهد image را pull کند. runtime نام را در registry به digest تبدیل می‌کند و فقط layerهایی را دانلود می‌کند که روی Node نیستند؛‏ پس همیشه یک درخواست سبک به registry هست،‏ ولی دانلود کامل نه. با IfNotPresent،‏ اگر imageی با همان نام روی Node باشد اصلاً با registry تماس گرفته نمی‌شود.

    اگر tag دوباره push شود،‏ با IfNotPresent هر Node که نسخه‌ی قبلی را دارد همان را اجرا می‌کند و فقط Nodeهای تازه نسخه‌ی جدید را می‌گیرند؛‏ نتیجه،‏ اجرای دو کد متفاوت زیر یک نام است. با Always هم Podهای قدیمی تا restart بعدی نسخه‌ی قبلی را اجرا می‌کنند. به همین دلیل مستندات توصیه می‌کند image را با tag معنادار و یکتا بسازید و برای ثبات کامل digest را مشخص کنید.

    نکته‌ی امتیازآور: ستون status.containerStatuses[].imageID digest واقعی اجراشده را نشان می‌دهد و با آن می‌توان ترکیب نسخه‌ها را ثابت کرد.

  2. مفهومیاگر imagePullPolicy را در manifest ننویسید،‏ چه مقداری ذخیره می‌شود و بر چه اساسی؟ اگر بعداً image tag یک Deployment را عوض کنید،‏ این مقدار هم عوض می‌شود؟
    پاسخ

    API server هنگام ساختن شیء فیلد خالی را فقط از روی متن نام image پر می‌کند: اگر digest داشته باشد IfNotPresent؛‏ اگر tag نداشته باشد یا tag آن latest باشد Always؛‏ و برای هر tag دیگر IfNotPresent. محتوای registry در این تصمیم نقشی ندارد (شکل ۲-۴).

    این مقدار فقط یک بار،‏ هنگام ساختن شیء تعیین می‌شود و با تغییر بعدی tag یا digest به‌روز نمی‌شود. مثلاً Deploymentی که با nginx:1.27 ساخته شده مقدار IfNotPresent گرفته است؛‏ اگر image را به nginx:latest تغییر دهید،‏ همان IfNotPresent می‌ماند و Nodeهایی که یک nginx:latest قدیمی دارند آن را دوباره pull نمی‌کنند:

    shell
    kubectl create deployment web --image=nginx:1.27
kubectl set image deploy/web nginx=nginx:latest
kubectl get deploy web -o jsonpath='{.spec.template.spec.containers[0].imagePullPolicy}{"\n"}'
# IfNotPresent

    نتیجه‌ی عملی: در production imagePullPolicy را صریح بنویسید و به مقدار پیش‌فرض تکیه نکنید.

  3. عملیروی cluster k3s،‏ Podی با imageی که روی Node نیست (مثلاً alpine:3.22) و imagePullPolicy: Never بسازید. وضعیت Pod را بررسی کنید و توضیح دهید چرا این حالت با ImagePullBackOff فرق دارد. (image pause برای این آزمایش مناسب نیست،‏ چون روی Nodeهای k3s از قبل وجود دارد.)
    پاسخ
    never-pull.yaml
    apiVersion: v1
kind: Pod
metadata:
  name: never-pull
spec:
  containers:
  - name: app
    image: alpine:3.22
    command: ["sleep", "3600"]
    imagePullPolicy: Never
    shell
    kubectl apply -f never-pull.yaml
kubectl get pod never-pull
kubectl describe pod never-pull | sed -n '/Events:/,$p'
    output (نمونه)
    NAME         READY   STATUS              RESTARTS   AGE
never-pull   0/1     ErrImageNeverPull   0          8s

Warning  ErrImageNeverPull  kubelet  Container image "alpine:3.22" is not present with pull policy of Never

    با Never،‏ kubelet اصلاً با registry تماس نمی‌گیرد. Pod در فاز Pending می‌ماند و container در حالت Waiting با reason برابر ErrImageNeverPull. kubelet در همگام‌سازی‌های بعدی دوباره بررسی می‌کند؛‏ اگر image را با docker save alpine:3.22 | sudo k3s ctr images import - روی Node بیاورید،‏ container بدون ساختن دوباره‌ی Pod اجرا می‌شود.

    در مقابل،‏ ImagePullBackOff یعنی kubelet واقعاً pull را امتحان کرده و شکست خورده است (نام اشتباه،‏ نبود credential،‏ مشکل شبکه) و بین تلاش‌ها با تأخیر فزاینده تا سقف ۳۰۰ ثانیه صبر می‌کند.

  4. عملییک Secret از نوع kubernetes.io/dockerconfigjson برای یک private registry بسازید،‏ آن را به یک Pod بدهید و محتوای decode‌شده‌ی .dockerconfigjson را بررسی کنید.
    پاسخ
    shell
    kubectl create secret docker-registry regcred \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<user> --docker-password=<token> --docker-email=<email>

kubectl get secret regcred --output=jsonpath='{.data.\.dockerconfigjson}' | base64 -d
    output
    {"auths":{"https://index.docker.io/v1/":{"username":"...","password":"...","email":"...","auth":"..."}}}
    private-image-pod.yaml
    apiVersion: v1
kind: Pod
metadata:
  name: private-reg
spec:
  containers:
  - name: private-reg-container
    image: <your-private-image>

  - name: regcred

    ساختار همان config.json ابزار docker است: زیر کلید auths هر نشانی registry به یک credential نگاشت شده است و فیلد auth همان username:password با base64 است. Secret باید در همان namespace مربوط به Pod باشد و هر کسی که اجازه‌ی get روی Secretهای آن namespace را دارد،‏ رمز را می‌بیند؛‏ پس برای registry از token فقط‌خواندنی استفاده کنید.

  5. مفهومیدر یک Secret از نوع dockerconfigjson دو کلید *.azurecr.io و myregistry.azurecr.io دارید. برای imageهای myregistry.azurecr.io/app:v1،‏ azurecr.io/app:v1 و a.b.azurecr.io/app:v1 کدام کلیدها تطبیق دارند و kubelet چطور از آن‌ها استفاده می‌کند؟
    پاسخ

    طبق قاعده‌ی «Interpretation of config.json»،‏ هر ‎*.‎ دقیقاً با یک بخش subdomain تطبیق دارد:

    • myregistry.azurecr.io/app:v1: هر دو کلید تطبیق دارند.

    پاسخ

    علت: با حذف Pod دو مسیر موازی شروع می‌شوند: kubelet بلافاصله SIGTERM را می‌فرستد و برنامه listener خود را می‌بندد؛‏ هم‌زمان خروج endpoint از EndpointSlice باید به kube-proxy همه‌ی Nodeها،‏ Ingress controller و load balancer بیرونی برسد که معمولاً چند ثانیه طول می‌کشد. در این فاصله درخواست‌ها هنوز به Podی فرستاده می‌شوند که دیگر پاسخ نمی‌دهد (شکل ۲-۷).

    راه‌حل: یک preStop با handler sleep (مثلاً ۱۰ تا ۱۵ ثانیه) تا SIGTERM دیرتر برسد و Pod در این مدت به درخواست‌ها پاسخ دهد؛‏ terminationGracePeriodSeconds را برابر زمان preStop به‌علاوه‌ی زمان خاموش شدن تدریجی برنامه به‌علاوه‌ی حاشیه بگذارید؛‏ برنامه پس از SIGTERM درخواست جدید نپذیرد ولی درخواست‌های در حال اجرا را تمام کند؛‏ و در Deployment مقدار maxUnavailable: 0 را در نظر بگیرید.

  20. سناریوی عملیاتیپس از ارتقای kubelet به v1.37 روی چند Node قدیمی،‏ kubelet اجرا نمی‌شود و Node در وضعیت NotReady است. در journalctl -u kubelet این خطا دیده می‌شود: validate service connection: validate CRI v1 runtime API for endpoint "unix:///run/containerd/containerd.sock": rpc error: code = Unimplemented desc = unknown service runtime.v1.RuntimeService. علت و اقدام لازم چیست؟
    پاسخ

    از v1.26،‏ kubelet فقط CRI API نسخه‌ی v1 را می‌پذیرد و اگر runtime آن را پیاده نکند،‏ kubelet راه‌اندازی نمی‌شود و Node register نمی‌شود. پیام unknown service runtime.v1.RuntimeService یعنی socket پاسخ می‌دهد،‏ ولی سرویس CRI v1 روی آن نیست. دو علت رایج: containerd قدیمی‌تر از 1.6 که CRI v1 ندارد؛‏ یا containerdی که plugin CRI آن در /etc/containerd/config.toml خاموش است (خط disabled_plugins = ["cri"] که در بسته‌های containerd همراه Docker رایج است).

    اقدام: Node را drain کنید،‏ containerd را به نسخه‌ای با CRI v1 ارتقا دهید یا plugin CRI را فعال کنید،‏ containerd و سپس kubelet را restart کنید و با crictl version مطمئن شوید RuntimeApiVersion: v1 است. در برنامه‌ی ارتقا،‏ runtime را پیش از kubelet ارتقا دهید.

  21. سناریوی عملیاتیروی Nodeهایی که هزاران Job کوتاه‌مدت CI اجرا می‌کنند،‏ در log kubelet خطای rpc error: code = ResourceExhausted desc = grpc: received message larger than max (17825792 vs. 16777216) برای ListContainers دیده می‌شود و Node گاهی NotReady می‌شود. علت و راه‌حل چیست؟
    پاسخ

    علت: RPCهای list در CRI همه‌ی نتایج را در یک پاسخ unary برمی‌گردانند. با هزاران container (از جمله containerهای متوقف‌شده‌ی Podهای تمام‌شده)،‏ پاسخ از سقف ۱۶ MiB پیام gRPC بیشتر می‌شود و kubelet نمی‌تواند state را با runtime همسان کند.

    راه‌حل کوتاه‌مدت: تعداد containerهای مرده را کم کنید: Podهای تمام‌شده را پاک کنید،‏ برای Jobها ttlSecondsAfterFinished بگذارید تا Podهایشان خودکار حذف شوند،‏ و تراکم Pod روی هر Node را محدود کنید. بلندمدت: قابلیت CRIListStreaming (آلفا از v1.36 و به‌طور پیش‌فرض خاموش) با runtimeی که RPCهای streaming را پشتیبانی کند،‏ پاسخ را در چند پیام می‌فرستد؛‏ به‌خاطر آلفا بودن،‏ اول در محیط آزمایشی امتحانش کنید.

  22. عملیبا crictl روی یک Node مستقیم به socket CRI وصل شوید،‏ نسخه‌ی runtime،‏ Podها و imageها را ببینید و همین اطلاعات را با kubectl مقایسه کنید.
    پاسخ
    shell (روی Node)
    sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock version
sudo crictl images
sudo crictl pods
    shell (از client)
    kubectl get node <node> -o jsonpath='{.status.nodeInfo.containerRuntimeVersion}'
kubectl get pods -A --field-selector spec.nodeName=<node> -o wide

    crictl مستقیم همان CRI API را صدا می‌زند که kubelet استفاده می‌کند (ImageService برای imageها و RuntimeService برای Podها)،‏ بدون واسطه‌ی API server.‏ kubectl وضعیتی را نشان می‌دهد که kubelet از CRI جمع کرده و به API server گزارش داده است. اگر این دو ناسازگار باشند (مثلاً kubectl می‌گوید Running ولی crictl container را نمی‌بیند)،‏ مشکل معمولاً در ارتباط kubelet با API server یا در خود kubelet است.

سؤال‌های مصاحبه‌ی فصل ۲ ۱۵ سؤال · پاسخ کوتاه و دقیق،‏ همان‌طور که در جلسه‌ی مصاحبه باید گفت
  1. پایهمقادیر imagePullPolicy چیست و اگر آن را ننویسید مقدار پیش‌فرض چطور تعیین می‌شود؟
    پاسخ

    Always،‏ IfNotPresent و Never. پیش‌فرض را API server هنگام ساختن شیء از روی نام image تعیین می‌کند: tag برابر latest یا بدون tag یعنی Always؛‏ tag دیگر یا digest یعنی IfNotPresent. این مقدار بعداً با عوض شدن tag تغییر نمی‌کند.

  2. پایهچرا نباید در production از tag latest استفاده کرد؟ جایگزین درست چیست؟
    پاسخ

    معلوم نیست کدام نسخه در حال اجراست،‏ rollback معنا ندارد و Nodeهای مختلف ممکن است محتوای متفاوتی اجرا کنند. جایگزین: tag نسخه‌دار و یکتا (مثلاً v1.42.0) و برای ثبات کامل digest (image@sha256:…) که hash محتواست و تغییر نمی‌کند.

  3. پایهفرق ErrImagePull و ImagePullBackOff چیست و چطور علتش را پیدا می‌کنید؟
    پاسخ

    ErrImagePull شکست یک تلاش pull است؛‏ ImagePullBackOff یعنی kubelet بین تلاش‌ها با تأخیر فزاینده (تا سقف ۳۰۰ ثانیه) صبر می‌کند. علت در eventهای kubectl describe pod است: not found (نام یا tag اشتباه)،‏ ‎401‎/‎403‎ (credential)،‏ ‎429‎ (محدودیت نرخ registry)،‏ timeout (شبکه،‏ DNS یا firewall)،‏ یا no matching manifest (معماری Node).

  4. پایهچطور یک Pod image را از private registry pull می‌کند؟
    پاسخ

    یک Secret از نوع kubernetes.io/dockerconfigjson (با kubectl create secret docker-registry) در همان namespace می‌سازید و در spec.imagePullSecrets مربوط به Pod ارجاع می‌دهید؛‏ یا آن را به ServiceAccount اضافه می‌کنید تا به همه‌ی Podهای آن ServiceAccount تزریق شود. راه‌های دیگر: credential سطح Node،‏ kubelet credential provider و pre-pulled imageها.

    آنچه مصاحبه‌گر می‌خواهد بشنود: Secret باید در همان namespace مربوط به Pod باشد و نبودنش event FailedToRetrieveImagePullSecret می‌دهد.

  5. پایهCRI چیست و چرا کوبرنتیز dockershim را کنار گذاشت؟
    پاسخ

    CRI یک API مبتنی بر gRPC بین kubelet و container runtime است با دو سرویس RuntimeService و ImageService. هر runtimeی که آن را پیاده کند (containerd،‏ CRI-O) بدون تغییر کد kubelet کار می‌کند. Docker Engine این API را پیاده نمی‌کرد و کوبرنتیز یک لایه‌ی سازگاری به نام dockershim نگه می‌داشت که در v1.24 حذف شد. imageهایی که با Docker ساخته می‌شوند همچنان کار می‌کنند،‏ چون قالب image OCI استاندارد است.

  6. پایهcontainer pause (sandbox) در هر Pod چه کاری انجام می‌دهد؟
    پاسخ

    kubelet برای هر Pod اول با RunPodSandbox یک sandbox می‌سازد. در runtimeهای Linux این sandbox یک container کوچک pause است که network namespace (و در صورت نیاز IPC و PID namespace) مربوط به Pod را نگه می‌دارد. application containerها به همین namespaceها می‌پیوندند؛‏ به همین دلیل همه‌ی containerهای یک Pod یک IP دارند و با localhost به هم دسترسی دارند،‏ و restart یک container IP مربوط به Pod را عوض نمی‌کند.

  7. متوسطوقتی kubectl delete pod می‌زنید،‏ دقیقاً چه اتفاقی می‌افتد؟
    پاسخ

    API server برای Pod deletionTimestamp و grace period (پیش‌فرض ۳۰ ثانیه) ثبت می‌کند و Pod در وضعیت Terminating دیده می‌شود. هم‌زمان: endpoint آن در EndpointSlice غیرفعال می‌شود تا ترافیک جدید نگیرد؛‏ و kubelet اول preStop را اجرا می‌کند،‏ سپس سیگنال توقف (معمولاً SIGTERM) را می‌فرستد. اگر process تا پایان grace period خارج نشود،‏ SIGKILL می‌گیرد. در پایان kubelet حذف را به API server اعلام می‌کند و شیء پاک می‌شود.

    نکته‌ی امتیازآور: grace period پیش از preStop شروع می‌شود و preStop از همان بودجه مصرف می‌کند.

  8. متوسطفرق init container و postStart hook چیست؟ کدام برای آماده‌سازی پیش از اجرای برنامه مناسب است؟
    پاسخ

    init containerها به ترتیب و تا پایان موفق اجرا می‌شوند و فقط پس از آن application containerها شروع می‌شوند؛‏ image جدا دارند و ترتیبشان تضمین‌شده است. postStart هم‌زمان با ENTRYPOINT همان container اجرا می‌شود و هیچ تضمینی نیست که پیش از آن اجرا شود. پس برای آماده‌سازی‌ای که برنامه به آن وابسته است (migration،‏ منتظر ماندن برای یک وابستگی،‏ ساختن فایل پیکربندی) init container درست است؛‏ postStart برای کارهای جانبی مثل ثبت در یک سرویس مناسب است.

  9. متوسطچطور در rolling update از خطاهای 502 هنگام خاموش شدن Podها جلوگیری می‌کنید؟
    پاسخ

    مشکل این است که حذف endpoint از load balancerها چند ثانیه طول می‌کشد،‏ ولی SIGTERM فوراً می‌رسد. راه‌حل: preStop با handler sleep چندثانیه‌ای،‏ برنامه‌ای که پس از SIGTERM درخواست جدید نمی‌پذیرد ولی درخواست‌های جاری را تمام می‌کند،‏ terminationGracePeriodSeconds بزرگ‌تر از مجموع این دو،‏ readinessProbe درست،‏ و maxUnavailable: 0 در Deployment.

  10. متوسطPod به Serviceها چطور دسترسی پیدا می‌کند: environment variable یا DNS؟ کدام بهتر است؟
    پاسخ

    هر دو. متغیرهایی مثل SVC_SERVICE_HOST فقط برای Serviceهایی تزریق می‌شوند که هنگام ساخته شدن container در همان namespace وجود داشته‌اند؛‏ پس به ترتیب ساخت وابسته‌اند. DNS cluster همیشه به‌روز است و Serviceهای namespaceهای دیگر را هم با svc.ns.svc.cluster.local پیدا می‌کند. روش توصیه‌شده DNS است.

  11. متوسطRuntimeClass چیست و چه زمانی از آن استفاده می‌کنید؟
    پاسخ

    یک شیء در سطح cluster (node.k8s.io/v1) که با فیلد handler به یک پیکربندی container runtime روی Node اشاره می‌کند؛‏ Pod با runtimeClassName آن را انتخاب می‌کند. کاربرد اصلی: اجرای workload غیرقابل‌اعتماد با runtime ایزوله مثل gVisor یا Kata. با scheduling Podها را به Nodeهای دارای آن runtime می‌فرستد و با overhead سربار sandbox را در scheduling (انتخاب Node مناسب برای اجرای هر Pod) و quota حساب می‌کند.

  12. متوسطPod روی Node جدید arm64 با پیام exec format error در CrashLoopBackOff است،‏ ولی روی Nodeهای amd64 سالم است. علت چیست؟
    پاسخ

    image فقط برای amd64 ساخته شده است. multi-architecture image یک image index دارد که برای هر معماری manifest جدا دارد و runtime هر Node نسخه‌ی مناسب خودش را انتخاب می‌کند. راه‌حل: ساختن multi-architecture image (مثلاً با docker buildx build --platform linux/amd64,linux/arm64) یا محدود کردن Pod به Nodeهای amd64 با nodeSelector روی label kubernetes.io/arch.

  13. پیشرفتهیک tenant بدون credential چطور ممکن است image خصوصی tenant دیگر را اجرا کند و چطور جلویش را می‌گیرید؟
    پاسخ

    اگر image قبلاً روی همان Node pull شده باشد و Pod از IfNotPresent استفاده کند،‏ kubelet در گذشته بدون بررسی credential آن را اجرا می‌کرد. راه قدیمی admission controller AlwaysPullImages بود. از v1.35 قابلیت KubeletEnsureSecretPulledImages به‌طور پیش‌فرض فعال است: kubelet ثبت می‌کند هر image با کدام credential pull شده و Podی که همان credential را ندارد باید خودش pull کند.

    نکته‌ی امتیازآور: imageی که با credential سطح Node pull شده برای همه‌ی Podهای آن Node آزاد است؛‏ پس credential private registry tenantها نباید در سطح Node باشد.

  14. پیشرفتهروی EKS،‏ Nodeها بدون هیچ imagePullSecret از ECR خصوصی pull می‌کنند. این کار چطور انجام می‌شود و اگر بخواهید هر workload هویت جدا داشته باشد چه می‌کنید؟
    پاسخ

    kubelet با kubelet credential provider (plugin ecr-credential-provider و CredentialProviderConfig با matchImages روی دامنه‌های ECR) هنگام pull credential کوتاه‌عمر را با هویت IAM مربوط به Node می‌گیرد. از v1.26 این منطق دیگر داخل kubelet نیست و حتماً plugin لازم است. برای هویت به ازای هر workload،‏ با tokenAttributes (قابلیت بتای KubeletServiceAccountTokenForCredentialProviders) kubelet token مربوط به ServiceAccount همان Pod را به plugin می‌دهد تا آن را با credential registry مبادله کند.

  15. پیشرفتهPodها روی یک Node در ContainerCreating مانده‌اند. به چه چیزهایی شک می‌کنید و چطور بررسی می‌کنید؟
    پاسخ

    اول eventهای kubectl describe pod. علت‌های رایج: pull طولانی یا گیرکرده‌ی image (به‌خصوص با pull سریالی و یک image حجیم در صف)،‏ شکست ساخت sandbox (FailedCreatePodSandBox) به‌خاطر CNI یا handler نامعتبر RuntimeClass،‏ مشکل mount کردن volume یا Secret و ConfigMap،‏ یا postStart گیرکرده. روی Node با crictl pods،‏ crictl images و journalctl -u kubelet وضعیت واقعی CRI را ببینید.

خلاصه‌ی فصل ۲ در یک نگاه برای مرور سریع؛‏ جزئیات در متن فصل

ایده‌ی محوری: هر چیزی که روی کوبرنتیز اجرا می‌شود یک container است که kubelet از راه CRI و container runtime،‏ از روی یک image اجرا می‌کند؛‏ برای کار درست باید بدانید image از کجا و چه وقت pull می‌شود (نام،‏ tag و digest،‏ pull policy و credential) و container چطور خاموش می‌شود (SIGTERM و preStop و grace period).

۱. image و container
  • image: بسته‌ی آماده‌ی اجرا (کد،‏ runtime،‏ library و تنظیمات پیش‌فرض)؛‏ چندلایه و تغییرناپذیر.
  • container:‏ instance در حال اجرای image؛‏ همه‌ی containerهای یک Pod روی یک Node اجرا می‌شوند.
  • قاعده: برای هر تغییر image تازه بسازید و rollout کنید. دام: تغییر با exec داخل container با اولین restart یا rollout از بین می‌رود.

  • tag: حداکثر ۱۲۸ نویسه؛‏ قابل جابه‌جایی. digest: همان hash محتوا؛‏ تغییرناپذیر. اگر هر دو بیایند،‏ pull با digest است.
  • نشانی registry: بخش اول نام فقط اگر نقطه یا port داشته باشد یا localhost باشد نشانی registry است؛‏ وگرنه بخشی از repository در Docker Hub است.
۳. imagePullPolicy و خطاهای pull
  • مقدارها: گزینه‌ی Always (هر شروع container از registry بپرس)؛‏ IfNotPresent (اگر هست pull نکن)؛‏ Never (هرگز pull نکن).
  • پیش‌فرض: بدون tag یا با latest برابر Always؛‏ tag دیگر یا digest برابر IfNotPresent. دام: فقط هنگام ساختن شیء تعیین می‌شود و با تغییر tag عوض نمی‌شود.
  • اجبار pull: با Always یا tag به نام latest یا admission controller به نام AlwaysPullImages.
  • ErrImagePull در برابر ImagePullBackOff: اولی شکست یک تلاش است و دومی انتظار بین تلاش‌ها تا سقف ۳۰۰ ثانیه. سرنخ در Events: پیام not found یعنی نام؛‏ 401 یا no basic auth credentials یعنی credential؛‏ 429 یعنی rate limit؛‏ timeout یعنی شبکه.
۴. رساندن image به Node (آزمایش شاپیفای)
  • دو انبار: انبار Docker (build) با انبار containerd که kubelet می‌بیند یکی نیست؛‏ «روی ماشین من کار می‌کند» از همین‌جاست.
  • راه موقت: دستور docker save و سپس k3s ctr images import؛‏ فقط یک Node و فقط با IfNotPresent یا Never.
  • راه استاندارد: ابتدا push به registry و pull توسط containerd. در k3s برای registry بدون TLS فایل /etc/rancher/k3s/registries.yaml با endpoint از نوع http:// و restart k3s.
  • port نام‌دار: در Service مقدار targetPort: http تا تغییر عدد port در rollout سرویس را قطع نکند.
  • Dockerfile: دستور CMD به شکل exec (فهرست JSON) تا برنامه PID 1 باشد؛‏ کاربر غیر root با USER.
۵. registry خصوصی
  • چهار راه credential: گزینه‌ی imagePullSecrets روی Pod یا ServiceAccount؛‏ پیکربندی Node؛‏ kubelet credential provider؛‏ pre-pulled images.
  • imagePullSecrets: ساخت Secret با kubectl create secret docker-registry (نوع dockerconfigjson) در همان namespace؛‏ هم‌سطح containers. دام: نبود Secret یعنی event به نام FailedToRetrieveImagePullSecret.
  • ServiceAccount: تزریق imagePullSecrets به Podهای تازه،‏ فقط هنگام ساخت Pod.
  • تطبیق config.json: هر ‎*.‎ دقیقاً یک subdomain؛‏ prefix مسیر مجاز؛‏ همه‌ی credentialهای منطبق به ترتیب امتحان می‌شوند.
  • امنیت: رمز در base64 است،‏ نه رمزنگاری؛‏ حساب robot فقط‌خواندنی و محدود کردن RBAC روی Secretها.
۶. credential provider و بررسی credential
  • credential provider: یک exec plugin با دو flag به نام‌های --image-credential-provider-config و --image-credential-provider-bin-dir؛‏ credential کوتاه‌عمر؛‏ برای static Pod هم کار می‌کند. provider داخلی قدیمی (ECR و ACR و GCR) از v1.26 حذف شده است.
  • tokenAttributes: ارسال token مربوط به ServiceAccount همان Pod به plugin (بتا از v1.34) برای هویت به ازای هر workload.
  • بررسی credential برای image موجود: قابلیت KubeletEnsureSecretPulledImages (بتا و فعال از v1.35)؛‏ سیاست پیش‌فرض NeverVerifyPreloadedImages. دام: imageی که با credential سطح Node pull شده،‏ برای همه‌ی Podهای آن Node آزاد است.
۷. pull سریالی و موازی؛‏ multi-arch
  • پیش‌فرض: انجام pull به‌صورت سریالی روی هر Node؛‏ برای موازی serializeImagePulls: false و سقف با maxParallelImagePulls. دام: سقف ۲ یا بیشتر همراه pull سریالی یعنی kubelet اجرا نمی‌شود.
  • درون یک Pod:‏ imageهای containerهای یک Pod هرگز موازی pull نمی‌شوند.
  • image index: یک نام برای چند معماری؛‏ هر Node manifest مناسب خودش را می‌گیرد. نشانه‌ی image تک‌معماری روی Node دیگر: exec format error یا no matching manifest.
۸. Container environment
  • درباره‌ی خود container: مقدار hostname برابر نام Pod (یا spec.hostname)؛‏ نام Pod و namespace با downward API؛‏ متغیرهای Pod و image.
  • درباره‌ی cluster: متغیرهایی مثل SHOP_API_SERVICE_HOST فقط برای Serviceهایی که هنگام ساخته شدن container وجود داشته‌اند. دام: وابستگی به ترتیب ساخت؛‏ از DNS استفاده کنید. خاموش کردن با enableServiceLinks: false.
۹. RuntimeClass
  • کار: انتخاب پیکربندی runtime با فیلد handler (مثلاً gVisor یا Kata برای workload غیرقابل‌اعتماد)؛‏ Pod با runtimeClassName انتخاب می‌کند.
  • scheduling: ترکیب nodeSelector با اشتراک (تعارض یعنی رد Pod) و tolerations با اجتماع. overhead: مقدار podFixed به requests در scheduling اضافه می‌شود.
  • شکست: نبود RuntimeClass یعنی رد در admission؛‏ نبود handler روی Node یعنی FailedCreatePodSandBox و ماندن در ContainerCreating. بازگشت بی‌صدا به runtime پیش‌فرض وجود ندارد.
۱۰. خاموش شدن و lifecycle hookها

ترتیب: ۱. حذف Pod و شروع grace period (پیش‌فرض ۳۰ ثانیه) و هم‌زمان خروج از EndpointSlice؛‏ ۲. اجرای preStop و انتظار برای پایانش؛‏ ۳. ارسال SIGTERM (یا STOPSIGNAL مربوط به image)؛‏ ۴. پس از پایان مهلت و یک تمدید ۲ ثانیه‌ای،‏ SIGKILL.

  • PID 1: سیگنال SIGTERM بدون handler نادیده گرفته می‌شود؛‏ حذف Pod تمام grace period طول می‌کشد (در Docker،‏ docker stop ده ثانیه). دام: شکل shell در CMD سیگنال را به برنامه نمی‌رساند.
  • handlerها: نوع exec داخل container؛‏ httpGet و sleep (پایدار از v1.34) توسط kubelet. تحویل «حداقل یک بار»،‏ پس idempotent بنویسید؛‏ شکست hook یعنی kill شدن container.
  • postStart: هم‌زمان با ENTRYPOINT و بدون تضمین ترتیب؛‏ تا پایانش container در وضعیت Running اعلام نمی‌شود. خطاها با eventهای FailedPostStartHook و FailedPreStopHook.
  • بدون قطعی: ترکیب preStop از نوع sleep چندثانیه‌ای،‏ handler برای SIGTERM که درخواست‌های جاری را تمام کند،‏ و grace period بزرگ‌تر از مجموع این دو.
۱۱. CRI
  • تعریف: رابط gRPC بین kubelet و runtime با دو سرویس RuntimeService و ImageService؛‏ از v1.26 فقط CRI v1 پذیرفته می‌شود. لایه‌ی dockershim در v1.24 حذف شد؛‏ imageهای ساخته‌شده با Docker همچنان کار می‌کنند (OCI).
  • ابزار crictl: یک client مستقیم همان API؛‏ در k3s با k3s crictl. در هر Pod یک sandbox (container از نوع pause) namespace شبکه را نگه می‌دارد.
  • List streaming: برای Nodeهای با هزاران container و پاسخ بزرگ‌تر از ۱۶ MiB (آلفا از v1.36؛‏ gate به نام CRIListStreaming).
